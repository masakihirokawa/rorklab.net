Every month begins the same way: download sales CSVs from each store's console, paste them into a spreadsheet. With one app that is fine. As the number of apps grows, the fact that every store names its columns and writes its dates differently starts to cost real time.

One month, the total I had pasted did not match the total shown in the store console. The gap was small, and I could not tell where it had gone. In the end the cause was a refund row that I had removed by hand because it was negative. **If you add numbers without any way to check that they are right, the mistake cannot be seen from the numbers alone.**

What follows is the procedure I built after that: reduce each store's CSV to four common columns, convert at one fixed month-end rate, and print the raw per-currency totals next to the converted ones so the two can be reconciled. Column names in store CSVs can change, so the script is written on the assumption that you open your own CSV and edit the mapping.

## Reduce everything to four columns

For monthly, per-app revenue you need only four things: when (the month), which app, how much, and in which currency. Store CSVs carry many more columns, but these four are enough.

Each store gets a small mapping saying "in this CSV, the date is in that column, the app name in this one". Adding a store means adding one entry.

</tbody>

Holding amounts as <code>Decimal</code> keeps rounding from drifting from month to month after conversion. With a few dozen rows the error is invisible, but later, when a total fails to match, you can no longer trace the cause.

## The whole script

Save this as `merge_sales.py`. It needs only a column mapping and a file of fixed exchange rates. **The column names in `MAPPING` are examples.** Open the first line of your own CSV and rewrite them to match.

```python
"""store ごとに形式の違う売上 CSV を共通 4 列に寄せ、アプリ別・月別に集計する。"""
import csv, sys, json
from collections import defaultdict
from decimal import Decimal, InvalidOperation

# Edit this mapping by opening your own CSV (these names are examples)
MAPPING = {
    "storeA": {"date": "Date", "app": "App", "amount": "Net", "currency": "Cur"},
    "storeB": {"date": "Order Charged Date", "app": "Product", "amount": "Payout", "currency": "Currency"},
}

def load(path, store):
    m = MAPPING[store]
    rows, bad = [], []
    with open(path, newline="", encoding="utf-8-sig") as f:
        for n, r in enumerate(csv.DictReader(f), start=2):
            try:
                rows.append({
                    "month": r[m["date"]].strip()[:7].replace("/", "-"),
                    "app": r[m["app"]].strip(),
                    "amount": Decimal(r[m["amount"]].replace(",", "")),
                    "currency": r[m["currency"]].strip().upper(),
                    "store": store,
                })
            except (KeyError, InvalidOperation) as e:
                bad.append((path, n, repr(e)))   # never drop silently; keep the line number
    return rows, bad

def main(rates_path, *pairs):
    rates = json.load(open(rates_path))          # {"2026-09": {"USD": "150.0", "JPY": "1"}}
    totals, raw_sum, bad_all = defaultdict(Decimal), defaultdict(Decimal), []
    for p in pairs:
        store, path = p.split("=", 1)
        rows, bad = load(path, store)
        bad_all += bad
        for r in rows:
            rate = Decimal(rates[r["month"]][r["currency"]])   # a missing rate raises KeyError and stops
            totals[(r["month"], r["app"])] += r["amount"] * rate
            raw_sum[(store, r["currency"])] += r["amount"]
    for (month, app), v in sorted(totals.items()):
        print(f"{month}  {app:<12} {v:>12,.0f} JPY")
    print("-- raw totals per store and currency (for reconciliation)")
    for (store, cur), v in sorted(raw_sum.items()):
        print(f"{store}  {cur}  {v}")
    print(f"-- unreadable rows: {len(bad_all)}")
    for b in bad_all: print("  ", *b)

if __name__ == "__main__":
    main(*sys.argv[1:])
```

Exchange rates live in one JSON file, one entry per month. Why one fixed rate per month rather than per transaction date is covered below.

```json
{"2026-09": {"USD": "150", "JPY": "1"}}
```

Run it by passing the rates file and `store=path` pairs.

```bash
python3 merge_sales.py rates.json storeA=a.csv storeB=b.csv
```

## A small sample, actually run

To check the behavior I ran two sample CSVs with deliberate quirks. The first is in yen and contains a refund (negative) row and a thousands separator. The second is in dollars, with slash-separated dates, a lower-case currency, and one amount that is not a number. I used 1 USD = 150 JPY. These are dummy values to see the behavior, not real revenue.

Checking by hand: Wall is 1,200 − 300 = 900 yen plus 12.50 USD (1,875 yen), so 2,775. Heal is 800 yen plus 7.25 USD (1,087.5 yen), so 1,887.5. It displays as 1,888 because `{:,.0f}` rounds for display only; the value underneath keeps its fraction.

And the `abc` on line 4 appears as an unreadable row with its line number. That is the part of this script I care about most.

## What went against my intuition: finishing without errors is not safe

My first version skipped unreadable rows with `except: continue`. It looked clean and raised nothing. Then one month the total differed from the console, and I spent days looking for the gap.

A script that skips unreadable rows never tells you the numbers are off. I settled on three rules.

## Always print the raw totals beside the converted ones

The converted total changes whenever you change the exchange rate, so it cannot be compared directly with the total in a store console.

That is why the script also prints sums per store and currency with no rate applied: `storeA JPY 1700` and `storeB USD 19.75` above. Those can be set directly against the console's total for the same period.

In the sample, the yen side is 1,200 − 300 + 800 = 1,700. The dollar side is 12.50 + 7.25 = 19.75, which excludes the one unreadable row. If the console total includes that row, the difference points straight at it. **Look at the converted figure only after the raw totals agree.** Fixing that order tells you where a mistake can be hiding.

## One fixed rate per month, not per transaction date

Converting at each transaction date's rate looks more precise. But collecting and pasting daily rates becomes the monthly chore itself.

For a personal operation, "one rate per month, written once into the JSON" is the version that lasts. It is slightly less exact, but you can close every month with the same steps. **I would rather choose a simplicity that continues than a precision that does not.** I treat the converted figures as a monthly working estimate and nothing more.

## The start-of-month routine

1. Download last month's CSV from each store console
2. Add the month-end rate as one line in `rates.json`
3. Run the script and confirm that unreadable rows is 0
4. Compare the raw totals with the console totals
5. If they agree, copy the converted table into your records

If either step 3 or 4 catches something, do not go on to 5. Keeping that order makes it much less likely that you notice a mistake only after you have copied the numbers.

## A side note: keep revenue apart from build-side costs

When you keep revenue records, I suggest keeping subscription and ad revenue in one table and the monthly costs on the build side in another. The balance of Rork credits also needs to be looked at separately from revenue (see [the note on separate credit balances](/en/articles/rork-business/rork-build-credits-cloud-credits-separate-balances-check)). ## What to do at your desk today

- Open each CSV and copy its date, app, amount, and currency column names into `MAPPING`
- Note last month's console total first, so your first reconciliation is immediate
- If an unreadable row shows up, do not discard it. Look at that line. Most often the cause is a shifted column name or a separator character

Adding up numbers is plain work, but the later a mistake is found, the more it costs. As an indie developer running several apps, I find that a five-minute check at the start of the month keeps my mind lighter.
