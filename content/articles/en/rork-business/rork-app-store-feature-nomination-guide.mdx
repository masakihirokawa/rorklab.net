## Why App Store Features Matter — The Numbers Behind a Feature

The night I put an update's release date on my calendar, I caught myself clicking through App Store Connect menu by menu, wondering whether there was any way to let Apple's editors know. There was. My understanding of it, though, was about half assumption.

A spot in the "Today" tab or the "Apps" tab banner is a quiet dream for most indie developers. How much a placement lifts downloads varies a great deal by genre and by surface, and Apple doesn't publish numbers. So this guide skips the after-the-fact figures and sticks to what you can prepare **before you send a nomination**.

App Store features come in several forms:

- **Today tab story**: A written article by Apple's editors — the highest visibility placement
- **Apps tab banner**: Category-level curation with banner display
- **Category "Editors' Choice"**: Curated picks within specific categories

These placements are chosen by Apple's Editorial team. Apple's own guidance mentions things like design quality, uniqueness, accessibility, localization, and use of the latest Apple technologies. What happens inside the selection itself is invisible from outside, but the listed angles are things you can check in your own app. Even for a solo app built with Rork, those checks leave you with more to write in a nomination.

Below are seven points, in the order I'd work through them.

---

## Point 1: Use the Human Interface Guidelines as Your Foundation

The first foundation I'd lay is **Apple's Human Interface Guidelines (HIG)**. I can't tell how heavily the Editorial team weighs them, but whether an app feels at home on Apple's platforms is something people notice the moment they touch it.

### Starting from HIG-Friendly Defaults in Rork

In the React Native / Expo projects Rork outputs, you can use navigation that stays close to native iOS. This is the setup I start from:

```tsx
// ✅ Recommended: Navigation setup that feels native on iOS
import { Stack } from 'expo-router';

export default function AppLayout() {
  return (
    <Stack
      screenOptions={{
        // Keep the standard iOS large-title header
        headerLargeTitle: true,
        headerTransparent: false,
        // Standard transition animation
        animation: 'slide_from_right',
      }}
    />
  );
}
// Expected output: Native iOS navigation stack with card-style transitions enabled
```

**HIG Compliance Checklist**:

- Safe areas (notch, Dynamic Island, home indicator) are properly respected
- SF Symbols are used for iconography, ensuring visual consistency
- Minimum touch target size of 44×44pt is respected throughout
- Dynamic Type (user-adjustable font sizes) is fully supported
- Both dark mode and light mode are fully supported and tested

Adding "please follow iOS Human Interface Guidelines" to your Rork prompt tends to point the output in the right direction. Safe areas and Dynamic Type still slip through, though, so I treat a pass on a real device with the text size at maximum as part of the same job.

## Point 2: Don't Leave Accessibility for Later

Apple has repeatedly shown that it takes **accessibility seriously**, and its featuring guidance lists it as one of the angles. VoiceOver and dynamic text sizes are painful to add late, because every screen needs a second visit. Putting them in while you're still building is cheaper in the end.

```tsx
// ✅ Accessibility implementation example
import { View, Text, TouchableOpacity } from 'react-native';

export function ProductCard({ name, price, onPress }: Props) {
  return (
    <TouchableOpacity
      onPress={onPress}
      // VoiceOver description
      accessible={true}
      accessibilityLabel={`${name}, $${price}`}
      accessibilityHint="Double tap to view details"
      accessibilityRole="button"
    >
      <View>
        <Text>{name}</Text>
        <Text>${price}</Text>
      </View>
    </TouchableOpacity>
  );
}
// Expected output: VoiceOver reads "Product name, $XX. Double tap to view details. Button."
```

**Minimum Accessibility Requirements**:

- All buttons and interactive elements have `accessibilityLabel`
- All images have `accessibilityLabel` (alt text equivalent)
- Animations are suppressed when `reduceMotion` is enabled
- Color contrast ratio meets 4.5:1 minimum for all text

## Point 3: Revisit How Fast the App Feels

The Editorial team is said to actually use the apps it considers. If so, **launch speed, scroll smoothness, and response time** reach the person before your nomination text does.

### Optimizing App Launch Time

```tsx
// ✅ Optimization in App.tsx: defer heavy processing
import { useEffect, useState } from 'react';
import * as SplashScreen from 'expo-splash-screen';

SplashScreen.preventAutoHideAsync();

export default function App() {
  const [isReady, setIsReady] = useState(false);

  useEffect(() => {
    async function prepare() {
      try {
        // Only critical initialization (auth check, essential config)
        await Promise.all([
          checkAuthStatus(),
          loadEssentialConfig(),
        ]);
        // Defer heavy loading (analytics, etc.) to after launch
      } catch (e) {
        console.error(e);
      } finally {
        setIsReady(true);
        await SplashScreen.hideAsync();
      }
    }
    prepare();
  }, []);

  if (!isReady) return null;
  return <RootNavigator />;
}
// Expected output: Splash → essential init complete → main screen displayed immediately
```

Apple doesn't publish specific numbers. The table below is what I use as a rule of thumb in my own apps — not an official threshold.

<table>
<thead>
<tr><th>Situation</th><th>Rule of thumb</th><th>How to check</th></tr>
</thead>
<tbody>
<tr><td>Cold launch (first open after a restart)</td><td>Usable within 2 seconds</td><td>Stopwatch on a real device; don't trust simulator numbers</td></tr>
<tr><td>Warm launch (subsequent opens)</td><td>Within 1 second</td><td>Same, and time returning from the background separately</td></tr>
<tr><td>Scrolling</td><td>Hold 60fps</td><td>Flick through a long list and watch for hitches (Reanimated helps)</td></tr>
<tr><td>API response to screen update</td><td>Within 3 seconds; show a waiting state beyond that</td><td>Throttle the connection on purpose</td></tr>
</tbody>
</table>

The numbers matter less than **deciding where you'll measure in advance**. I tend to call an app "fast enough" based on my development phone, and more than once I only noticed the slowness when I picked up an older device.

## Point 4: Have a Story You Can Actually Tell

A Today tab story isn't advertising — it's **a piece written by Apple's editors**. The question behind it is probably something like: "Does this app have a story worth telling?"

### Story Patterns Apple Tends to Love

- **Solving a social challenge**: Climate, disability, mental health, education equity
- **Fresh perspective or design**: Something that makes users say "I've never seen this before"
- **Born from the developer's own experience**: "I built this because I needed it myself"
- **Serving a specific community**: Local culture, heritage languages, niche hobbies
- **Timely relevance**: Seasonal events, major sporting events, trending cultural moments

When I look for a story in one of my own apps, I don't count features — I look back at the work my hands did. In my ukiyo-e wallpaper app, for example, it's the fact that I repair the damage on old paper myself before each image goes out. It never shows up in a feature list, yet it's the part I most want to write about in a nomination.

A story may not be something you can dress up afterward. Holding this angle at the planning stage is, I think, the shorter road to a feature.

## Point 5: Use Featuring Nominations in App Store Connect

"Submitting your app to Apple's editors" sounds like something that requires an agency or an inside contact. It doesn't. The entry point sits inside App Store Connect, and it's open to everyone.

Go to `Apps > your app > Featuring > Nominations` in the sidebar, then click the "+" next to Nominations and choose Create Nomination. The first time through, you'll click Get Started first. The required role is Account Holder, Admin, App Manager, or Marketing — if you're a solo developer holding your own account, roles are a non-issue.

You'll pick one of three nomination types.

<table>
<thead>
<tr><th>Type</th><th>What Apple says</th><th>When it fits a solo developer</th></tr>
</thead>
<tbody>
<tr><td><strong>App Launch</strong></td><td>The launch or pre-order of a new app or game</td><td>Your first release, or a project you've been sitting on for a while</td></tr>
<tr><td><strong>App Enhancements</strong></td><td>New features, functionality, or other significant updates</td><td>A major update to a shipped app — realistically the most useful slot for indies</td></tr>
<tr><td><strong>New Content</strong></td><td>New content, offers, or events inside your app or game</td><td>Apps where the content library keeps growing: wallpapers, packs, seasonal drops</td></tr>
</tbody>
</table>

**The nomination type and the related apps can't be changed once you submit.** Lock those two down while the nomination is still a draft. Everything else stays editable afterward. You can attach up to 10 apps from the same account, which is useful if you ship a family of related apps.

### The lead time is three weeks, minimum

Apple's App Store Connect help asks you to submit as early as possible, with **a minimum lead time of three weeks**. You can pick either a single publish date or a date range, and the date is interpreted in your device's local time zone.

I once opened the form only after fixing a release date, and realized it was too late. Looking back, what I lacked wasn't knowledge of the form — it was the habit of putting the nomination at the start of the schedule.

Those three weeks sit outside App Review. Submitting your nomination after your build clears review is already too late. Draft the nomination before you cut the build, working backwards from your intended publish date. Reordering those two steps costs nothing and changes whether you make the window at all.

Drafts can sit unsent indefinitely via Save as Draft. There's also CSV bulk import — up to 50 nominations at a time, though anything uploaded that way is submitted immediately and can't be saved as a draft. If you run several apps, download the template once and reuse it.

## How to Budget the 1,000-Character Nomination Description

Only three fields have a stated character limit.

<table>
<thead>
<tr><th>Field</th><th>Limit</th><th>What it's for</th></tr>
</thead>
<tbody>
<tr><td>Nomination Name</td><td>60 characters</td><td>Your own label for finding it later — not part of the evaluation</td></tr>
<tr><td>Nomination Description</td><td>1,000 characters</td><td>The main body. What is happening, and when</td></tr>
<tr><td>Helpful Details</td><td>500 characters</td><td>Accessibility work, team background — the raw material for a story</td></tr>
</tbody>
</table>

Note that the limits are characters, not words. A thousand characters of English runs to roughly 160 words. That's shorter than most people expect.

Here's the split I use.

<table>
<thead>
<tr><th>Budget</th><th>What goes there</th></tr>
</thead>
<tbody>
<tr><td>First ~120 chars</td><td>What the app is, when it ships, what changes. One sentence, no hedging</td></tr>
<tr><td>Next ~300 chars</td><td>The substance of the update: feature names, OS versions, languages. Nouns, not adjectives</td></tr>
<tr><td>Next ~300 chars</td><td>What changes for the person using it — described as a behavior, not a quality</td></tr>
<tr><td>Final ~200 chars</td><td>The publish date and what will be ready by then</td></tr>
<tr><td>Remaining ~80 chars</td><td>Buffer. Editing always pushes you over</td></tr>
</tbody>
</table>

The opening sentence carries the weight. Apple's editors read a lot of these. "A new version of our wallpaper app" gives no one a reason to keep reading. "Adds iOS 26 Lock Screen widgets and ships in 16 languages on day one" puts a picture in someone's head.

The 500 characters of Helpful Details are not an awards shelf. Apple frames the field as wanting to know what makes you stand out. Download counts and press mentions land less well than **something an editor could actually write a paragraph about**: how you rebuilt the VoiceOver reading order, how one person keeps sixteen localizations in sync. The unglamorous work is the work almost nobody else can describe firsthand.

Supplemental Materials takes up to five URLs, and TestFlight public links are explicitly allowed. Rather than promising to send assets later, put a TestFlight link in and let someone hold the build.

### A pre-submission check I run every time

- Paste the description into a character counter and confirm it's under 1,000
- Read only the first sentence and ask whether it means anything to someone who's never seen the app
- Count the calendar days to your publish date — three weeks or more
- Confirm the nomination type and related apps one last time (they lock on submit)
- Open every Supplemental Materials URL in a logged-out browser window

That last one catches a quiet failure: sending a link only you can open.

## Point 6: Protect Quality Right After Launch

How these signals feed into featuring isn't public. Still, if **crash rate, ratings, and engagement** are rough right after release, the people who do arrive get a bad first impression. I treat them as defensive metrics and settle the standards beforehand.

### Run a TestFlight Beta Before You Ship

```bash
# Create a TestFlight build using EAS Build
npx eas build --platform ios --profile preview

# Example output:
# ✅ Build #12 completed
# 📱 TestFlight URL: https://testflight.apple.com/join/xxxxx
# ⏱ Build time: 8m 32s
```

**Pre-Launch Quality Checklist**:

- Gather around 20 beta testers, spread across devices and OS versions
- Decide your own crash-rate ceiling ahead of time and commit to delaying the release if you cross it (measure with Sentry or similar). Apple doesn't give a figure, so choose one per app
- Read all TestFlight feedback and reply to what you can
- Keep time free on launch day and the next to answer early reviews

### Driving Early Reviews the Right Way

```tsx
// ✅ Requesting reviews at the right moment
import * as StoreReview from 'expo-store-review';

async function requestReviewAtRightMoment(
  userHasCompletedAction: boolean,
  sessionCount: number,
) {
  // Only request after the user has experienced real value (3+ sessions, task completed)
  if (userHasCompletedAction && sessionCount >= 3) {
    const canRequest = await StoreReview.hasAction();
    if (canRequest) {
      await StoreReview.requestReview();
    }
  }
}
// Expected output: Review prompt appears only after user has experienced clear value
```

## Point 7: Get the App Store Visual Assets Right

The first thing anyone sees in the store is your **icon, screenshots, and preview video**. If those look rough, people may close the page before the app's strengths get across.

### What to Hold Onto in an Icon

- **Simple and memorable**: Limit to 1–2 visual elements
- **Distinctive background**: Unique gradient or color treatment that stands out
- **Instantly communicates the core value**: Symbolize what the app is fundamentally about
- **Sharp at every size**: Design at 1024×1024px, verify it reads clearly when small

### Tell a Story Through Screenshots

```
Recommended screenshot sequence (6 screenshots):

Screenshot 1: Core value in one headline + the most important screen
Screenshot 2: Primary feature (where users spend the most time)
Screenshot 3: Secondary feature (what makes this app unique)
Screenshot 4: Simplicity / ease of use demonstration
Screenshot 5: Social proof (reviews, user count, awards)
Screenshot 6: Call to action ("Start free today", etc.)
```

For hands-on guidance on creating App Store screenshots, see the [Figma App Store Screenshot Creation Guide](/articles/app-dev/figma-app-store-screenshot-guide).

## Feature Nomination Timeline — Working Backwards

Apple's floor is three weeks before your publish date. But a nomination written in a hurry three weeks out almost always has a weak opening sentence. Here's the order I work in.

- **10 weeks out**: Concept and design locked. Try writing the opening sentence of your Nomination Description. If you can't, the concept isn't articulated yet
- **8 weeks out**: TestFlight beta running. Prepare the public link you'll attach as Supplemental Materials
- **6 weeks out**: Create the nomination as a draft and lock in the type and related apps. Draft your Helpful Details
- **4 weeks out**: Finalize icon, screenshots, and preview video. Check your crash rate
- **3.5 weeks out**: Submit the nomination — the three-week floor plus a few days of slack
- **3 weeks out**: Upload all App Store assets and submit for App Review
- **Release day**: Go live. Turn on your review prompt
- **First 2 weeks post-launch**: Watch engagement daily. Ship fixes same-day

The point of this table is that the nomination (3.5 weeks out) goes in *before* App Review (3 weeks out). Waiting for a review outcome before nominating leaves you squeezed between your launch date and the three-week rule with nowhere to move.

## One Thing to Do Tomorrow

Seven points is a lot to hold at once. You only need one of them tomorrow.

**Open Featuring > Nominations in App Store Connect and create a single draft.** Don't submit it. Give it a name, pick a type, and write only the first sentence of the description. Ten minutes, start to finish.

When that sentence won't come, the problem is usually not the nomination process — it's upstream, in the app. Who, what, and when hasn't been settled yet. I've hit that wall more than once, staring at an empty field late at night. The nomination form turns out to be a quick mirror for that vagueness.

**A nomination isn't something you send once the app is finished; it's a tool you reach for early to put the plan into words.** I try to remember that line most when the release date is close.

If you've been tripped up in review, [Surviving App Store Rejections with Rork](/articles/rork-business/rork-app-store-rejection-survival-playbook) picks up where this leaves off. Featuring gets talked about as luck. The door, at least, is open to everyone. Start by leaving one draft behind it.
