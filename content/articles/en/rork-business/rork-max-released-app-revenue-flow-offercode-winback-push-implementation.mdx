I was staring at a subscription dashboard where new sign-ups were moving nicely and the month-end renewal count simply wasn't. If you ship Rork Max apps, you may know the moment: the numbers say "growth," and the bank balance doesn't quite agree.

Looking only at acquisition is a habit I recognize in myself. Moving my attention to people who had already paid once changed what I could actually do, though I only noticed that well after the fact.

Below, I walk through offer signing, win-back decisions, and push plus email delivery for both StoreKit 2 and Google Play Billing. I re-checked the specifics against Apple's and Google's documentation, and I've marked the places that can look like they work while quietly failing, such as the unit of the signature timestamp.

**Start from your own cancellation reasons, not someone else's averages.** That's the one rule I'd put at the top.

## Why Start With Reactivation

What it costs to acquire a new subscriber and what it costs to win a lapsed one back differ wildly from app to app. Comparing them with your own numbers beats trusting a circulating "average."

Three measures are enough:

<table>
<thead><tr><th>Measure</th><th>Formula</th><th>Where the data comes from</th></tr></thead>
<tbody>
<tr><td>New-subscriber cost</td><td>Ad spend ÷ new paying users</td><td>Ad console plus App Store Connect / Play Console</td></tr>
<tr><td>Win-back cost</td><td>(Total discount given + delivery cost) ÷ returning users</td><td>Offer delivery log and purchase events</td></tr>
<tr><td>Retention after return</td><td>Users still paying 6 months after returning ÷ users who returned</td><td>Your own subscription status history</td></tr>
</tbody>
</table>

A worked example, using **assumed numbers, not results**: a monthly plan at ¥600 with a "50% off for 3 months" offer sent to 1,000 people, of whom 50 return. The discount per returning user is ¥600 × 50% × 3 = ¥900. If delivery costs ¥1,000 in total, that adds ¥20 per returner, so the win-back cost is ¥920.

One thing is easy to miss: that ¥900 isn't revenue you lost. Without the offer, those users would have paid ¥0. What you compare is the cost of bringing the same number of people in through ads, and how long the returners stay.

People who have paid once have already judged the product worth money. Whether the cause was price, timing, or a missing feature decides which message works, which is why the implementation below branches on the cancellation reason.

## Architecture — Four Layers

Before code, divide the system into four layers.

**Layer 1: Data Collection**. Store user behavior, subscription state, and cancellation reasons. Cloudflare D1 or Firestore are good choices.

**Layer 2: Decision Logic**. Decide "who gets which offer when." Start rule-based, evolve to ML-driven once data accumulates.

**Layer 3: Delivery Execution**. Push notifications, email, in-app modals, and App Store offer code distribution.

**Layer 4: Measurement**. Track effect of each campaign and feed back into the decision layer.

## Step 1: StoreKit 2 Offer Signing — Seconds vs. Milliseconds

Start on iOS. StoreKit 2 promotional offers are signed on your server, and the app passes that signature when it calls `purchase`. A wrong signature just surfaces as a failed purchase, so it helps to know the spec first.

According to Apple's "Generating a signature for subscription offers," the signed string is the following fields joined with `U+2063` (INVISIBLE SEPARATOR), in this order:

<table>
<thead><tr><th>#</th><th>Field</th><th>Notes</th></tr></thead>
<tbody>
<tr><td>1</td><td>appBundleId</td><td>Your app's bundle ID</td></tr>
<tr><td>2</td><td>keyIdentifier</td><td>Key ID of the key created in App Store Connect</td></tr>
<tr><td>3</td><td>productIdentifier</td><td>The subscription product ID</td></tr>
<tr><td>4</td><td>offerIdentifier</td><td>The offer ID configured in App Store Connect</td></tr>
<tr><td>5</td><td>applicationUsername</td><td>May be an empty string (the separators then sit next to each other)</td></tr>
<tr><td>6</td><td>nonce</td><td>A server-generated UUID, represented in <strong>lowercase</strong> in the signature</td></tr>
<tr><td>7</td><td>timestamp</td><td>UNIX epoch in <strong>milliseconds</strong>, not seconds</td></tr>
</tbody>
</table>

The algorithm is ECDSA with SHA-256, using the PKCS#8 private key downloaded from App Store Connect. The output is DER-encoded binary, which you send to the app as Base64.

```typescript
// Server side: promotional offer signing (Node.js 20+)
import { createPrivateKey, randomUUID, sign } from "node:crypto";

// Write the invisible separator as an escape; pasted literally it tends to vanish
const SEP = "\u2063";

interface OfferParams {
  appBundleId: string;
  productId: string;
  offerId: string;
  applicationUsername: string; // may be empty; if set, use a value you can look up later
  privateKeyPem: string; // PKCS#8 private key (read from a secret, never hard-coded)
  keyId: string; // Key ID issued by App Store Connect
}

export function signPromotionalOffer(params: OfferParams) {
  const nonce = randomUUID().toLowerCase();
  const timestamp = Date.now(); // milliseconds; Math.floor(Date.now() / 1000) is wrong

  const payload = [
    params.appBundleId,
    params.keyId,
    params.productId,
    params.offerId,
    params.applicationUsername,
    nonce,
    String(timestamp),
  ].join(SEP);

  // sign() on an EC key returns DER by default
  const signature = sign(
    "sha256",
    Buffer.from(payload, "utf8"),
    createPrivateKey(params.privateKeyPem)
  );

  return {
    offerId: params.offerId,
    keyId: params.keyId,
    nonce,
    signature: signature.toString("base64"),
    timestamp,
  };
}
```

A signature, nonce, and timestamp are valid for one purchase request only. Generate a fresh set right before each purchase.

On the app side, decode the Base64 back into `Data` before calling `purchase`.

```swift
// iOS side: applying the promotional offer
import StoreKit

struct SignedOffer: Decodable {
    let offerId: String
    let keyId: String
    let nonce: UUID
    let signature: String // Base64 from the server
    let timestamp: Int
}

enum OfferError: Error {
    case productNotFound
    case invalidSignature
}

func applyPromotionalOffer(productId: String, offer: SignedOffer) async throws {
    guard let product = try await Product.products(for: [productId]).first else {
        throw OfferError.productNotFound
    }
    guard let signatureData = Data(base64Encoded: offer.signature) else {
        throw OfferError.invalidSignature
    }

    let result = try await product.purchase(options: [
        .promotionalOffer(
            offerID: offer.offerId,
            keyID: offer.keyId,
            nonce: offer.nonce,
            signature: signatureData,
            timestamp: offer.timestamp
        )
    ])

    switch result {
    case .success(let verification):
        switch verification {
        case .verified(let transaction):
            await transaction.finish()
        case .unverified(_, let error):
            throw error
        }
    case .userCancelled, .pending:
        break
    @unknown default:
        break
    }
}
```

When a signature is rejected, I work down this table. My rule: check units and letter case before blaming the key or the algorithm.

<table>
<thead><tr><th>Order</th><th>Likely cause</th><th>How to check</th></tr></thead>
<tbody>
<tr><td>1</td><td>Timestamp is in seconds</td><td>Log it; it should be 13 digits</td></tr>
<tr><td>2</td><td>Nonce signed in uppercase</td><td>Pass the signed string through <code>toLowerCase()</code></td></tr>
<tr><td>3</td><td>A normal space or pipe used as the separator</td><td>Confirm it's written as the <code>"\u2063"</code> escape</td></tr>
<tr><td>4</td><td>Fields in the wrong order</td><td>Compare against the table above, 1 through 7</td></tr>
<tr><td>5</td><td>Key ID and private key from different keys</td><td>Keep the ID and its .p8 file together</td></tr>
<tr><td>6</td><td>A signature reused across purchases</td><td>Issue a new one on the server every time</td></tr>
</tbody>
</table>

### Win-back offers are a separate mechanism

The names are close, but App Store Connect has **win-back offers** for lapsed subscribers that are distinct from signed promotional offers: Apple decides eligibility. These are the knobs:

<table>
<thead><tr><th>Setting</th><th>Detail</th></tr></thead>
<tbody>
<tr><td>Scope</td><td>Per subscription product, not per subscription group</td></tr>
<tr><td>Minimum paid duration</td><td>1–24 months, or 3, 4, or 5 years</td></tr>
<tr><td>Time since last subscribed</td><td>1–24 months (required)</td></tr>
<tr><td>Wait before the same offer again</td><td>2–24 months (optional)</td></tr>
<tr><td>Limits</td><td>Up to 350 per subscription; up to 5 running per storefront at a time</td></tr>
<tr><td>Offer types</td><td>Pay as you go, pay up front, free</td></tr>
</tbody>
</table>

A customer can only receive a win-back offer for the most recently lapsed product in a group. If you want to control targeting yourself on your own server, use promotional offers; if you'd rather let Apple judge eligibility and surface the offer in the store, use win-back offers. Check Apple's current documentation for supported OS versions and in-app calls before building (source: [App Store Connect Help, "Set up win-back offers"](https://developer.apple.com/help/app-store-connect/manage-subscriptions/set-up-win-back-offers)).

## Step 2: Choosing a Google Play Billing Offer

Android works differently from iOS, where your server signs. You create offers in Play Console against a base plan; the app calls `queryProductDetails`, picks the offer it wants from `subscriptionOfferDetails`, and passes that offer's `offerToken` in `BillingFlowParams`.

So the offer token isn't something your server hands out. It's read from `ProductDetails`. Your server's job is to decide which offer ID this user should get and tell the app.

```kotlin
// Android side: find the server-specified offer ID and launch the billing flow
import com.android.billingclient.api.BillingClient
import com.android.billingclient.api.BillingFlowParams
import com.android.billingclient.api.QueryProductDetailsParams

suspend fun launchOfferFlow(
    activity: Activity,
    productId: String,
    targetOfferId: String?
) {
    val productList = listOf(
        QueryProductDetailsParams.Product.newBuilder()
            .setProductId(productId)
            .setProductType(BillingClient.ProductType.SUBS)
            .build()
    )

    val params = QueryProductDetailsParams.newBuilder()
        .setProductList(productList)
        .build()

    val productDetailsResult = billingClient.queryProductDetails(params)
    val productDetails = productDetailsResult.productDetailsList?.firstOrNull() ?: return
    val offers = productDetails.subscriptionOfferDetails ?: return

    // If the requested offer isn't returned, fall back to the plain base plan
    val offer = offers.firstOrNull { it.offerId == targetOfferId }
        ?: offers.firstOrNull { it.offerId == null }
        ?: return

    val productDetailsParamsList = listOf(
        BillingFlowParams.ProductDetailsParams.newBuilder()
            .setProductDetails(productDetails)
            .setOfferToken(offer.offerToken) // read from ProductDetails
            .build()
    )

    val billingFlowParams = BillingFlowParams.newBuilder()
        .setProductDetailsParamsList(productDetailsParamsList)
        .build()

    billingClient.launchBillingFlow(activity, billingFlowParams)
}
```

A base plan without an offer comes back with a `null` `offerId`, which is what the fallback relies on.

Read the price and free period you display from the chosen offer's `pricingPhases`. Otherwise you can end up with a button promising "50% off for 3 months" while the purchase runs at full price. For eligibility settings (new customers, upgrades, and so on), see the Play Console help.

## Step 3: Win-Back Offer Decision Logic

Implement the "who/when/which offer" logic. Start rule-based; evolve to ML once data exists.

```typescript
// src/lib/winback-offer-engine.ts
interface UserProfile {
  userId: string;
  cancelDate: Date;
  cancelReason?: "price" | "not_using" | "found_alternative" | "missing_feature" | "other";
  totalLifetimeRevenue: number;
  monthsActive: number;
  lastSessionDays: number;
}

interface OfferRecommendation {
  productId: string;
  offerId: string;
  channel: "push" | "email" | "in_app";
  message: string;
}

export function recommendWinbackOffer(
  profile: UserProfile,
  sentWindows: number[] = [] // windows already sent (7 / 30 / 90), from your ledger
): OfferRecommendation | null {
  const daysSinceCancel = Math.floor(
    (Date.now() - profile.cancelDate.getTime()) / (1000 * 60 * 60 * 24)
  );

  // Timing: day 7 / 30 / 90 windows, and only if not yet sent for that window
  const window = [7, 30, 90].find(
    (d) => daysSinceCancel >= d && daysSinceCancel < d + 3
  );
  if (window === undefined || sentWindows.includes(window)) return null;

  // Differentiate by reason
  switch (profile.cancelReason) {
    case "price":
      return {
        productId: "com.example.app.subscription.monthly",
        offerId: "winback_50_off_3months",
        channel: "push",
        message: "Come back? 3 months at 50% off, just to try.",
      };

    case "not_using":
      return {
        productId: "com.example.app.subscription.monthly",
        offerId: "winback_first_month_free",
        channel: "email",
        message: "Recent updates made the app a lot easier to use. Try the next month free.",
      };

    case "missing_feature":
      return {
        productId: "com.example.app.subscription.monthly",
        offerId: "winback_first_month_free",
        channel: "email",
        message: "If something was missing, one free month is a low-risk way to check whether it's changed.",
      };

    case "found_alternative":
      return {
        productId: "com.example.app.subscription.yearly",
        offerId: "winback_yearly_30_off",
        channel: "in_app",
        message: "Yearly plan is now 30% off.",
      };

    default:
      // High-LTV users get the strongest offer
      if (profile.totalLifetimeRevenue > 50) {
        return {
          productId: "com.example.app.subscription.yearly",
          offerId: "winback_loyal_50_off",
          channel: "push",
          message: "We'd love to have you back. Yearly plan, 50% off, just for you.",
        };
      }
      return null;
  }
}
```

The core idea is a hypothesis: different cancellation reasons need different offers. Price churners may respond to discounts; missing-feature churners to "here's what changed" plus a free period.

The quieter lesson is the window. If a daily batch only picks users whose `daysSinceCancel` is exactly 7, one skipped day means that person never hears from you, and a re-run sends twice. Give each step a three-day window and keep a ledger of windows already sent, and both a skipped day and a re-run become harmless.

## Step 4: Push Notification Integration

Sending offers via push notification using FCM (Firebase Cloud Messaging):

```typescript
// src/lib/push-notification-sender.ts
import { getMessaging } from "firebase-admin/messaging";

interface OfferNotification {
  userId: string;
  fcmToken: string;
  offerId: string;
  productId: string;
  message: string;
  deepLink: string;
}

export async function sendOfferPushNotification(args: OfferNotification) {
  const messaging = getMessaging();

  await messaging.send({
    token: args.fcmToken,
    notification: {
      title: "We have something special for you",
      body: args.message,
    },
    data: {
      type: "winback_offer",
      offerId: args.offerId,
      productId: args.productId,
      deepLink: args.deepLink,
    },
    apns: {
      payload: {
        aps: {
          sound: "default",
          badge: 1,
          "mutable-content": 1,
        },
      },
    },
    android: {
      priority: "high",
      notification: {
        clickAction: "OPEN_OFFER",
      },
    },
  });

  // Log the delivery for A/B testing and analysis
  await logOfferDelivery({
    userId: args.userId,
    offerId: args.offerId,
    sentAt: new Date(),
  });
}
```

The deep link design matters most. Tapping the notification should open the offer screen instantly with a one-tap path to purchase confirmation. Any "open the app and find the offer" friction loses most users.

## Step 5: Collecting Cancellation Reasons

Win-back accuracy depends on cancellation reason quality. Apple and Google don't provide reasons, so collect them yourself.

```swift
// iOS side: ask reason before showing the cancel screen
import SwiftUI
import StoreKit

struct CancellationFlowView: View {
    @State private var selectedReason: CancelReason?
    @State private var feedback: String = ""

    var body: some View {
        VStack(spacing: 16) {
            Text("Before you cancel, would you tell us why?")
                .font(.title2)

            Text("It helps us understand where to improve.")
                .multilineTextAlignment(.center)
                .padding()

            ForEach(CancelReason.allCases) { reason in
                Button {
                    selectedReason = reason
                } label: {
                    HStack {
                        Image(systemName: selectedReason == reason ? "circle.fill" : "circle")
                        Text(reason.label)
                        Spacer()
                    }
                    .padding()
                }
            }

            TextEditor(text: $feedback)
                .frame(height: 100)
                .border(Color.gray.opacity(0.3))

            Button("Send and continue to cancellation") {
                Task {
                    await submitCancellationReason(reason: selectedReason, feedback: feedback)
                    if let scene = UIApplication.shared.connectedScenes
                        .first(where: { $0 is UIWindowScene }) as? UIWindowScene {
                        try? await AppStore.showManageSubscriptions(in: scene)
                    }
                }
            }
        }
        .padding()
    }
}

enum CancelReason: String, CaseIterable, Identifiable {
    case tooExpensive = "price"
    case notUsing = "not_using"
    case foundAlternative = "found_alternative"
    case missingFeature = "missing_feature"
    case other = "other"

    var id: String { rawValue }
    var label: String {
        switch self {
        case .tooExpensive: return "Too expensive"
        case .notUsing: return "Not using it much"
        case .foundAlternative: return "Found something else"
        case .missingFeature: return "Missing a feature I need"
        case .other: return "Other"
        }
    }
}
```

Two design constraints: keep the question optional, and never block the way to cancellation itself. A form that won't let people continue without an answer obstructs cancellation; check section 3.1.2 of the App Store Review Guidelines for how Apple treats this. In practice that means a "continue without answering" button on the same screen. To open the subscription management screen, `AppStore.showManageSubscriptions(in:)` keeps people inside your app, which a raw URL open does not.

## Step 6: A/B Testing and Measurement

Test your offers — randomly split similar users into two groups, show the offer to one, withhold from the other.

```typescript
// src/lib/ab-test.ts
export function shouldShowOffer(userId: string, experimentId: string): boolean {
  const hash = simpleHash(`${userId}:${experimentId}`);
  return hash % 100 < 50; // 50% see the offer
}

interface ExperimentMetrics {
  experimentId: string;
  variant: "control" | "treatment";
  exposureCount: number;
  conversionCount: number;
  revenueGenerated: number;
}

export async function trackExposure(args: {
  userId: string;
  experimentId: string;
  variant: "control" | "treatment";
}) {
  await db.exposures.insert({
    userId: args.userId,
    experimentId: args.experimentId,
    variant: args.variant,
    exposedAt: new Date(),
  });
}

export async function trackConversion(args: {
  userId: string;
  experimentId: string;
  revenueAmount: number;
}) {
  // Only count conversions within 30 days of exposure
  const exposure = await db.exposures.findOne({
    userId: args.userId,
    experimentId: args.experimentId,
    exposedAt: { $gte: new Date(Date.now() - 30 * 24 * 60 * 60 * 1000) },
  });
  if (!exposure) return;

  await db.conversions.insert({
    userId: args.userId,
    experimentId: args.experimentId,
    variant: exposure.variant,
    revenueAmount: args.revenueAmount,
    convertedAt: new Date(),
  });
}
```

Win-back audiences are small by nature, so small improvements are hard to detect statistically. For an indie app, it's realistic to trust only large differences. Decide the duration and sample size before you start, because judging early on small counts is a common source of false signals.

`simpleHash` can be any hash with little bias; what matters is that the same user always lands in the same group.

## Step 7: Pitfalls in Production Operation

Common implementation traps:

**Trap 1: Offer signature expiration**

A signature, nonce, and timestamp work for one purchase request only (Apple's docs also note the nonce is cached for 24 hours). A signature generated ahead of time and reused will fail from the second use. Fetch it when the user taps the purchase button, then show the payment sheet right away.

**Trap 2: Push notification overload**

Too many win-back pushes train users to disable notifications. Start with a cap of 3 messages per user per month and adjust by watching how many people turn notifications off.

**Trap 3: Sending to fully-removed users**

FCM tokens linger after app deletion. Continuing to send to them inflates delivery failures and muddies your delivery metrics. Delete tokens that FCM reports as invalid, and drop long-inactive devices from the list (pick the cutoff to match how often your app is actually opened).

**Trap 4: Broken deep links**

If the deep link doesn't work, users open the app and abandon. Test the full path — push tap → offer screen → purchase confirmation — on real devices before each release.

**Trap 5: Calling A/B tests too early**

"Three days of treatment outperforming control" is not statistically significant. Wait at least two weeks, ideally a month, before drawing conclusions.

## What to Measure — Build the Numbers From Your Own App

Articles like this tend to include "churn fell by N points after we shipped it." Results swing with the app and price point, so another app's numbers don't transfer. Here is what to instrument before you start instead.

<table>
<thead><tr><th>Measure</th><th>Definition</th><th>How to read it</th></tr></thead>
<tbody>
<tr><td>Monthly churn</td><td>Subscriptions that lapsed in the month ÷ active at month start</td><td>Compare against a same-period control group, not just before/after</td></tr>
<tr><td>Win-back rate</td><td>Users who returned within 30 days of the offer ÷ users sent the offer</td><td>Split by reason and by channel</td></tr>
<tr><td>Retention after return</td><td>Share still paying 3 and 6 months after returning</td><td>Line it up against new users at the same point</td></tr>
<tr><td>Net revenue from offers</td><td>Revenue received after return − discount given</td><td>Watch how many months it takes to turn positive</td></tr>
<tr><td>Build effort</td><td>Hours spent putting the system in</td><td>Weigh against service fees or maintenance</td></tr>
</tbody>
</table>

In the first month, before any offer goes out, record only your current monthly churn and the breakdown of cancellation reasons. Without a baseline, nobody can tell afterwards whether the offer worked.

## Looking Back — Start With One Mechanism

Trying everything at once is how work stalls. Month one: collect cancellation reasons and measure current churn. Month two: add one offer for the most common reason.

If it were mine, I'd start with a single push plus offer for people who cancelled over price. A small first step means the tricky parts, such as signing, only have to be solved once, and any effect can be told apart from noise.

An imperfect mechanism that's running teaches more than a perfect design that never ships. A good first action is to write down this month's churn rate on one line of a spreadsheet.

## Five Hypotheses Worth Testing as You Run It

Once the win-back stack is in place, there are five things I'd want to confirm over time. They're hypotheses to test with your own numbers, not results I'm reporting.

The first: **cancellation-reason quality probably decays without maintenance**. Some users will tap through the picker without thinking. Refresh the wording every six months and re-categorize "Other" answers; new categories tend to show up there.

The second: **personalization may matter more than the discount itself**. Compare a message that mentions how the person actually used the app against a generic "come back," under identical conditions, and decide once the sample sizes in the table above are reached.

The third: **win-back is probably a long loop, not a one-time conversion**. Someone who returns, stays, leaves, and returns again should be counted by cumulative revenue; judging a single return undervalues it.

The fourth: **put the retention curve of returning users next to new users'**. If returners churn faster than new subscribers, the offer may be so strong that you're buying back people who weren't interested. Use your own new-user retention as the baseline, and revisit the offer if returners fall below it.

The fifth: **email may reach high-value lapsed users better than push**. People who turned notifications off can't be reached by push. If you record win-back rate by channel, you can test this in your own app.

Build the basic version first; the lessons show up once the data does.

## Building the Email Channel for Win-Back

While push notifications are the obvious channel, email is dramatically underused for app win-back. Here's how to build the email pipeline alongside the push channel.

The fundamentals: collect email addresses during the original signup flow (with explicit opt-in), and store them keyed to the same user ID you use for push tokens. When the win-back engine recommends an offer, decide channel based on user attributes — push for active recently, email for users who've gone fully dark.

```typescript
// src/lib/email-winback-sender.ts
import { Resend } from "resend";

interface EmailWinbackArgs {
  userEmail: string;
  userName?: string;
  offerId: string;
  productId: string;
  discountPercent: number;
  appStoreUrl: string;
```

## Cross-Platform Subscription Sharing

A common architectural question: should iOS and Android subscriptions be unified into one server-side entitlement, or kept separate?

For most apps, unified entitlements via a service like RevenueCat are worth the integration effort. The user pays on iOS and gets entitled on Android, or vice versa. Without unification, you create the friction of "I paid for the iPhone version but my Android tablet shows me nothing."

Implementation pattern: when StoreKit 2 or Google Play Billing reports a successful subscription, your server records the entitlement keyed to your internal user ID. Both platforms read entitlements from your server, not from the platform store directly. This makes win-back also unified — a single offer can target a user across both their devices.

The downside: when entitlement state diverges (refund processed on iOS but not yet reflected in your server), you can briefly show inconsistent state. Build aggressive sync — re-fetch entitlement on every app foregrounding — to minimize visible inconsistency.

## Choosing Between RevenueCat and Self-Hosted Receipts

A practical decision every Rork Max app developer faces: use a service like RevenueCat, or build receipt validation yourself?

The case for RevenueCat: it abstracts away the differences between StoreKit 2 and Google Play Billing, handles edge cases like grace periods and family sharing automatically, and gives you a unified dashboard for cross-platform metrics. For most solo developers, the time savings far exceed the per-revenue fee.

The case against RevenueCat: at scale, the percentage-of-revenue fee becomes meaningful — if the fee were 1% of revenue, that would be $100 per month on $10K of monthly recurring revenue, and it grows linearly (check RevenueCat's current pricing page for the real terms). Self-hosted receipt validation is a one-time engineering investment that scales for free thereafter.

For Rork Max-built apps, I'd start with RevenueCat until about $5K MRR, then evaluate; treat that figure as a rule of thumb, to be settled by putting fees next to the effort of self-hosting. The early-stage time savings are usually worth more than the cost. By the time the cost becomes meaningful, you have data to decide whether the added complexity of self-hosting is worth the savings. Plenty of teams stay on RevenueCat indefinitely because the operational simplicity is valuable.

If you do migrate, plan it carefully. Migrating receipt validation from RevenueCat to self-hosted touches every paying customer — even small bugs cause subscription state corruption that's very expensive to recover from. Allocate at least three weeks for the migration, with extensive parallel-running before cutover.

## Subscription Lifecycle Edge Cases

A few subscription scenarios that catch many developers off guard:

**Grace periods**. When a credit card expires or fails, a grace period keeps the user entitled to access while billing is retried. On Apple, you enable Billing Grace Period in App Store Connect and choose 3, 16, or 28 days (weekly plans cap at 6), and the choice applies to every subscription product in the app. On Google, the length is set per base plan in Play Console. Neither should be assumed on by default; check your own settings. Your app needs to handle "subscription is in grace period" as a distinct state — usually the same as active for entitlement purposes, but with a UI banner asking the user to update payment method.

**Refunds**. Apple processes refunds asynchronously. A user who refunds today might still appear entitled in your records for hours or days. Subscribe to App Store Server Notifications and revoke entitlement immediately on refund events, rather than relying on receipt re-validation.

**Family sharing**. Apple's family sharing means a single subscription can entitle up to six users. RevenueCat handles this automatically; if you self-host, you need to validate the family sharing relationships yourself via App Store Server API.

**Promotional offers vs introductory offers**. These are different StoreKit concepts despite the name overlap. Introductory offers are eligibility-based (only users who haven't subscribed before); promotional offers are signed and arbitrary. Win-back offers are a separate offer type for lapsed subscribers, with eligibility judged by Apple from the conditions you set in App Store Connect. Get the terminology right or you'll waste hours debugging eligibility issues.

**Resubscription within a billing period**. If a user cancels mid-cycle and re-subscribes immediately, both platforms handle this without billing them twice — but your server needs to recognize "this is a resubscription, not a new subscription" and avoid issuing onboarding emails or trial benefits. Track previous subscription state and check before triggering new-user flows.

## Compliance and Legal Considerations

A topic many developers skip until forced: app subscriptions touch consumer protection laws that vary significantly by region.

**EU region**: GDPR requires explicit consent for marketing emails and push notifications, separate from the app's general terms of service. The win-back offer pipeline is marketing communication and falls under this — collect explicit opt-in or risk regulatory exposure.

**California (CCPA/CPRA)**: California users have the right to opt out of "sale of personal information." Even if you don't think you "sell" data, sending data to ad networks for targeting often qualifies. Provide a clear opt-out mechanism in your app settings.

**Japan**: The Specified Commercial Transactions Act requires certain disclosures for subscription products. App Store and Google Play handle most of these automatically, but if you offer subscriptions outside the platforms (web subscriptions for cross-platform access), you need to provide the disclosures yourself.

**Apple App Store Review Guidelines**: section 3.1.2 specifically addresses subscriptions. Read it for what it requires around disclosing recurring billing before purchase, not obstructing cancellation, and handling price changes. Design win-back offers so the terms are plain, and never make re-subscribing look like something it isn't.

These compliance requirements aren't optional, but they're also not as scary as they sound. Apple and Google enforce most of the basics through their review processes. The compliance work is documenting that your win-back flow respects user choice and provides clear information.

## A Realistic Three-Month Roadmap

To make all of this concrete, here's a three-month roadmap for going from "no win-back system" to "a working revenue-compounding stack."

**Month one**: instrument cancellation reason collection. Add the reason picker, store responses, and let data accumulate. Don't send any offers yet — focus entirely on understanding why users actually leave. By month-end, aim to have categorized data on your top 5 cancellation reasons.

**Month two**: implement push notification offers for the top reason. If "too expensive" is your #1 reason, build the 50% off offer for that segment. Run it for two weeks, measure the impact, and decide whether to expand.

**Month three**: layer in email channel and segment-based offers. Add A/B testing infrastructure, implement second and third reason-targeted offers, and build the simple measurement dashboard you'll use ongoing.

After three months, you have a measurable, optimizable revenue-compounding system. The next year is iteration — testing message variants, refining offer terms, expanding to additional segments. Each refinement compounds against the previous, and each refinement builds on the last.

The work isn't glamorous, but the math is unforgiving: apps that compound retain customers, and customers who churn but return generate more lifetime revenue than customers who never had a reason to leave in the first place. Build the win-back stack, and let compounding do the rest.

## A Note on Tone in Win-Back Communications

One subtle factor that disproportionately affects win-back conversion: the tone of the message itself.

Aggressive sales language — "DON'T MISS THIS LAST CHANCE!" — performs poorly with churned users. They've already left once; they're not in a "buy now" mindset. They're in a "convince me you've changed" mindset, which calls for a completely different voice.

Three characteristics are worth building into your own tests. First, acknowledgment that the user left for a reason. Second, specificity about what's different now. Third, a low-friction next step that doesn't feel like a hard commit.

A template to start your own testing from: "We noticed you left in March. Since then, we've shipped [specific change relevant to their cancellation reason]. If you'd like to see what's different, here's a 30-day trial at no cost — and if it's still not for you, no hard feelings." This kind of message respects the user's choice to leave while inviting them to reconsider, and the opt-in trial removes purchase friction.

The opposite — "We've reduced our prices! Come back!" — tends to feel desperate and converts at a fraction of the rate. Test tone variants explicitly; the win-back channel is where copy quality directly translates to revenue.

That's the closing thought worth carrying forward: every layer of this system matters, but the human elements (reason collection, message tone, channel choice) often matter more than the technical elements (signature generation, push token management). Build the technical foundation, then invest in the human details. The compounding effect on retention pays dividends for as long as your app is in the market.
