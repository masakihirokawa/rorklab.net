There was a night I opened the monthly revenue report and realized this month looked almost identical to last month. Downloads kept climbing, but the revenue line lay flat. I remember my stomach going heavy.

The companion article [Mobile App Monetization Foundations With Rork](/en/articles/rork-business/rork-mobile-app-monetization-foundations-ads-iap-subscription) covered the big-picture decision framework. This piece picks up from there: what to build and what to operate once revenue has stopped moving.

One thing up front. The effect of each tactic below varies a lot by app type and region, so please read the numbers as rough guides and test small before rolling anything out.

## What the ¥100k/Month Wall Really Is

I think of ¥100k/month as the first point where solo development works as a side income, and many people stop right there. Up to about ¥10k, you can get by on an app plus ads and some luck. Beyond that, doing more of the same doesn't move the line.

The state I call the wall looks like this: apps ship, they're in the stores, they get a fair number of downloads, and revenue sits at a few thousand yen up to ¥10k a month. To get out, I had to stop treating monetization as an implementation task and start treating it as an operations task.

## The Strategy Map — Four Levers

Four levers are available. I'll take them one at a time.

**Maximize ad eCPM.** eCPM is revenue per 1,000 impressions, so at the same impression count a higher eCPM is simply more revenue.

**Optimize IAP price and pitch.** Product lineup, prices, and the path to purchase affect both conversion and revenue per buyer.

**Protect subscription retention.** Lower monthly churn means each subscriber is worth much more over time.

**Widen the funnel with ASO.** Without touching the app, the way you present it in the store changes how many people walk in.

I once tried to move all four at the same time and lost track of what had worked. These days I look at the app's situation and go deep on one lever at a time.

## Maximizing Ad eCPM

For ad-supported apps, eCPM is the first thing I review. Three changes have held up for me.

**Mediation.** Instead of AdMob alone, combine several ad networks so the highest bid wins each impression. In my apps eCPM improved noticeably. Which networks are available changes often, so I'd check each one's current status when you set this up.

```typescript
// AdMob Mediation baseline setup
import mobileAds, {
  AdsConsent,
  AdsConsentStatus,
  MaxAdContentRating,
} from "react-native-google-mobile-ads";

// Run once at startup
mobileAds()
  .setRequestConfiguration({
    maxAdContentRating: MaxAdContentRating.PG,
    tagForChildDirectedTreatment: false,
    tagForUnderAgeOfConsent: false,
  })
  .then(async () => {
    // GDPR consent (mandatory for EU users)
    const consentInfo = await AdsConsent.requestInfoUpdate();
    if (consentInfo.status === AdsConsentStatus.REQUIRED) {
      await AdsConsent.showForm();
    }

    await mobileAds().initialize();
  });

// Mediation configuration is done in the AdMob dashboard
// Local code remains the standard AdMob implementation
```

**Bidding.** Moving from a waterfall to real-time bidding usually lifts eCPM a bit further. You enable it for the relevant networks in the AdMob dashboard, and the app code doesn't change.

**Format mix.** In my wallpaper apps (such as [Beautiful Wallpapers](https://apps.apple.com/jp/app/id706533906)), what settled was a persistent banner at the bottom of the home screen, an interstitial every few image views, and an optional rewarded ad when setting a wallpaper. Rewarded ads tend to pay far more than banners, and tying them to an optional action keeps the app pleasant to use.

**Place ads only where they don't stop the user's hand.** Early on I wanted more impressions and placed too many, and the reviews turned sour. That rule is what I took from it.

## Optimizing IAP Price and Pitch

For IAP I watch both conversion and revenue per buyer. Three changes made the biggest difference.

**Three price tiers.** With one product, the choice is buy or don't buy. With three, it becomes which one to buy. Having something to compare against pushes people toward the middle option, the decoy effect. In my apps the middle plan was chosen most often.

```typescript
const TIER_PRODUCTS = [
  { sku: "starter", price: "¥240", features: ["Remove ads"] },
  { sku: "standard", price: "¥480", features: ["Remove ads", "Pro features", "50 templates"], recommended: true },
  { sku: "deluxe", price: "¥980", features: ["Remove ads", "Pro features", "200 templates", "Cloud backup"] },
];

function PricingScreen() {
  return (
    <View>
      {TIER_PRODUCTS.map((tier) => (
        <View key={tier.sku} style={tier.recommended ? styles.recommended : styles.normal}>
          {tier.recommended && <Badge text="Recommended" />}
          <Text style={styles.price}>{tier.price}</Text>
          {tier.features.map((f) => <Text key={f}>✓ {f}</Text>)}
          <Button title="Buy" onPress={() => handlePurchase(tier.sku)} />
        </View>
      ))}
    </View>
  );
}
```

**Time-limited offers.** A discount for the first 24 hours after launch moves a share of people who haven't bought yet. It sits close to a dark pattern, though, so I use it only for offers that really expire and never for a fake countdown.

```typescript
function useFirstLaunchTimer() {
  const [secondsLeft, setSecondsLeft] = useState<number>(0);

  useEffect(() => {
    const init = async () => {
      const firstLaunch = await AsyncStorage.getItem("first_launch_at");
      const firstLaunchAt = firstLaunch ? parseInt(firstLaunch) : Date.now();
      if (!firstLaunch) {
        await AsyncStorage.setItem("first_launch_at", String(Date.now()));
      }

      const offerEndsAt = firstLaunchAt + 24 * 60 * 60 * 1000;
      const interval = setInterval(() => {
        const remaining = Math.max(0, offerEndsAt - Date.now());
        setSecondsLeft(Math.floor(remaining / 1000));
      }, 1000);

      return () => clearInterval(interval);
    };
    init();
  }, []);

  return secondsLeft;
}
```

**Let people try before they buy.** I let users preview the ad-free experience for a short time, and conversion went up visibly. The only change was the direction of the design, from "you can't use this unless you buy" to "try it, and buy if you like it."

## Holding Subscription Retention

For subscriptions, bringing monthly churn down is the shortest path. Halve churn and lifetime value roughly doubles. Three measures worked.

**Automatic recovery from failed payments.** Cancellations caused by expired cards or authorization errors aren't the user's decision; they're clerical failures. Followed up properly, a good share of them can be recovered. The example below is for Stripe on the web. For App Store and Google Play subscriptions, each store's grace period and billing retry settings play the same role.

```typescript
// Auto-recovery flow on payment failure (Stripe webhook)
async function handleInvoicePaymentFailed(invoice: Stripe.Invoice) {
  const userId = invoice.metadata?.userId;
  const subscription = await stripe.subscriptions.retrieve(invoice.subscription as string);

  // 1. Notify the user immediately
  await sendEmail(userId, {
    template: "payment_failed_retry",
    data: {
      retryUrl: invoice.hosted_invoice_url,
      nextAttemptAt: new Date(invoice.next_payment_attempt! * 1000),
    },
  });

  // 2. Show an in-app banner
  await db.user.update({
    where: { id: userId },
    data: {
      paymentIssue: true,
      paymentIssueResolveBy: new Date(invoice.next_payment_attempt! * 1000),
    },
  });

  // 3. Stripe Smart Retries handles up to 3 retries
  // If still failing, subscription.deleted will fire
}
```

**Make the value visible.** People decide whether it's worth paying again around the time a billing notice arrives. Just before that, I send a summary of what they did this month. After I began sending usage stats at month-end in one of my apps, churn went down.

```typescript
// Monthly summary on the 25th
async function sendMonthlySummary(userId: string) {
  const monthStart = startOfMonth(new Date());
  const monthEnd = endOfMonth(new Date());

  const usageStats = await db.usageEvent.aggregate({
    where: {
      userId,
      occurredAt: { gte: monthStart, lte: monthEnd },
    },
    _count: { _all: true },
    _sum: { quantity: true },
  });

  await sendEmail(userId, {
    template: "monthly_value_summary",
    data: {
      totalActions: usageStats._count._all,
      timeSavedMinutes: estimateTimeSaved(usageStats),
      topFeatures: await getTopFeatures(userId, monthStart, monthEnd),
    },
  });
}
```

**The cancellation path.** With web billing you can offer "discount next cycle only" or "pause" at the moment someone presses cancel. App Store subscriptions are cancelled in the device settings, so in-app the job is mostly pointing to those settings and using the offers the store provides. Either way, I never remove the one-tap route to cancel.

## Widening the Funnel With ASO

Paying for downloads rarely pays off for a solo developer and tends to wear you down, so I put effort into organic discovery. Three things helped.

**Title, subtitle, and keyword field.** Fit the limited characters with terms that people search for and that few competitors target. I use keyword research tools, but treat their numbers as rough; the final check is searching in the store myself.

**Testing screenshots.** App Store product page optimization and Google Play store listing experiments let you compare image sets by conversion from store visit to install. In my apps, images with a short line stating the benefit tended to beat plain feature screens.

**Localization.** Taking an app from Japanese and English to a dozen or more languages can lift downloads noticeably. AI now handles much of the first-draft translation, which lowered the barrier a lot. I'd still have a native speaker check the store copy before it goes live.

## Common Pitfalls

**Changing several things at once.** You can't tell what worked. Changing one thing and watching for at least two weeks turned out to be the shortest route.

**Chasing short-term revenue.** More ads or pushier purchase screens lift this month's numbers, then reviews drop, rankings slide, and the long-run total shrinks. It took me a few repeats to really learn that.

**Postponing measurement.** Without tracking behavior in something like Firebase Analytics, you can't see where people leave. If you want revenue to move, instrumentation comes first.

**Depending on one app.** Store policy changes, OS updates, or a new competitor can shift revenue overnight. Splitting income across several sources is part of a solo developer's stamina.

**Thin reasoning behind prices.** "Other apps charge ¥480" is not a reason. Work backward from what your users value and how much. Before settling on a new price, I try to talk to a handful of users.

## What Revenue-Stable Apps Had in Common

Looking back over the apps I've run, the ones with stable revenue shared a few traits.

**A one-sentence value proposition.** Apps you can describe as "it does this" grow. "A handy app that does lots of things" gets downloaded and then forgotten.

**A reason to open it daily.** Notifications, fresh content, visible progress — something is built in.

**Ongoing conversation with users.** Replying to reviews and answering inquiries carefully is plain work, but it pays back slowly through word of mouth.

## A Next Step

A stalled line is, I think, a signal to shift from building to operating. Before adding another app, it may be worth spending time on the numbers of the ones you already have.

As a first step, write down your monthly revenue and your monthly revenue per user (ARPU). Then see which of the four levers is thinnest. I still make the same table at the start of each month and begin with the weakest spot.
