The first night I opened a Rork-generated project in my editor, I stalled at the sheer number of files in the sidebar. Out of habit I started with `components/`, and about half an hour later I realized I still couldn't say which screen called which piece. Reading parts before you know how they're used doesn't give you a map.

So here's the thing I'd tell you first: **read from the screen entrance down to the parts, not the other way around.** In a project that uses Expo Router, the entrance is the `app/` folder.

## React Native and Expo, in one line each

React Native takes screens written in JavaScript and renders them as native parts on iOS and Android. Expo sits on top as a toolkit: a dev server, a standard set of native modules, and a way to build and ship.

What Rork outputs is this combination. You don't need to learn anything "Rork-specific"; if you know the Expo way of doing things, you can read the project. That alone narrows what you have to read.

## The app/ folder is the list of screens

Expo Router is file-based routing: where a file lives is the address of the screen. An app with tabs usually looks like this.

```
app/
├── _layout.tsx          // the outer frame (Providers and the Stack are wired here)
├── (tabs)/
│   ├── _layout.tsx      // tab bar definition
│   ├── index.tsx        // Home
│   └── profile.tsx      // Profile
├── login.tsx
└── item/[id].tsx        // dynamic route (/item/42, etc.)
```

Start with the top `app/_layout.tsx`. The Providers that wrap the whole app (auth, theme, data fetching) are lined up there, so you can see at a glance what every screen below shares. Then the tab `_layout.tsx`, then each screen.

Navigation is written with `Link` or `router.push`.

```tsx
import { Link, router } from 'expo-router'

<Link href="/item/42">Details</Link>

// when you need to move in the middle of some logic
router.push('/login')
```

More than once, after asking Rork to add a screen, it didn't appear where I expected. The cause was usually that the file had landed one level off. When a screen goes missing, I check this tree before I ask the AI again.

## Look at state in three layers

In the projects I've read, state tended to split into three layers.

- Values used only inside one screen: `useState`
- Values shared across screens (login state, theme): Context
- Values fetched from a server: a fetching library such as TanStack Query, or functions kept in `services/`

The trick is to follow, one value at a time, who is allowed to change it. If there's one place, it's easy to read; if there are three, that's where bugs tend to breed.

```tsx
// the smallest shape of shared state
export const AuthContext = createContext<{ user: User | null }>({ user: null })

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null)
  return <AuthContext.Provider value={{ user }}>{children}</AuthContext.Provider>
}
```

As a project grows, a light store like Zustand is an option. I don't think you need it on day one, though; adding it after Context starts to hurt has been early enough for me.

## Where Expo Go stops working

Early on, scanning a QR code with Expo Go on a real device is all it takes to see your screens. That convenience is Expo's biggest strength.

But the moment you add a native module that Expo Go doesn't ship with, the app won't open. I once added a storage library, got a red screen, and lost an afternoon asking the AI for the same fix three times. The code wasn't wrong; the container was missing something.

A Dev Client (a development build made for your own app) is how you cross that line. I wrote the steps in [Adding Expo Dev Client to Your Rork App](/articles/rork-dev/rork-expo-dev-client-native-module-setup-guide).

## Leave building and shipping to EAS

When it's time for the stores, building and submitting go through EAS (Expo Application Services).

```bash
eas build --platform ios
eas build --platform android
eas submit --platform ios --latest
```

`expo build:ios`, which you'll still see in older tutorials, is the retired predecessor. If you run into one, I'd read it as EAS Build. Signing and provisioning are where people trip first, but EAS manages the certificates for you, so you don't pile up fiddly Xcode settings by hand.

## Treat ios/ and android/ as generated, hands off

When I see `ios/` and `android/` in a project, I treat them as build output. Native settings go in `app.json` and config plugins, and the folders are recreated with `expo prebuild`. Keep to that flow and upgrading Expo doesn't cause a scramble.

As of SDK 57, `prebuild` clears the native folders by default before regenerating them, so lines you added by hand can disappear. I wrote down how to audit this before upgrading in [Before Upgrading to Expo SDK 57, Audit What prebuild Will Delete](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit).

## Long lists and re-renders can wait

Once the screens work, one thing worth revisiting is long lists: draw them with `FlatList`. It renders only what's visible, so it stays light as the item count grows.

```tsx
<FlatList
  data={items}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <ItemRow item={item} />}
/>
```

If a list shows up blank, [this FlatList blank-screen triage](/articles/rork-dev/rork-flatlist-blank-empty-list-debug) is a good place to start. `useMemo` and `useCallback` are fine to add once you actually feel slowness.

## The line I draw for reading a project

Here's the whole thing in one sentence.

**Screens in app/, shared values in a Provider, hand-touched native code in a config plugin.** If everything stays where it belongs, I can retrace both what the AI added and what I fixed myself. I try to keep this line even on days when I'm rushing.

As a next step, open `app/_layout.tsx` in your project and write down on paper how many screens there are and which ones touch shared state. I find that the next request I give the AI gets much more specific afterward.
