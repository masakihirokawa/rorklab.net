There was a day I opened a freshly generated Rork Max project, ran it in the simulator, and archived it as-is. It passed review. Then I installed the build on a real device, scrolled a list, and watched it visibly stutter — a symptom the simulator had never once reproduced.

Speed of generation and shippable quality live on different axes. Now that Rork Max owns the first one, the second one takes up proportionally more of the day. That's the honest read after six months of running it on solo projects.

What follows is only that second half, in the order the work actually happens — with notes on where the time went.

## Reading a Rork Max Project Structure

Before touching anything, understand what Rork generated.

```
MyApp/
├── MyApp.xcodeproj/
├── Sources/
│   ├── App/              ← application entry point
│   ├── Views/            ← SwiftUI views
│   ├── Models/           ← data models, Codable types
│   ├── Services/         ← API clients, persistence
│   └── Utils/            ← extensions, helpers
├── Resources/
│   ├── Assets.xcassets/
│   ├── Localizations/
│   └── Fonts/
└── .rork/                ← Rork's internal metadata (don't touch)
```

The cardinal rule: never edit `.rork/`. It's how Rork Max tracks what it generated so it can regenerate cleanly later. Hand-editing it breaks regeneration.

Here's the boundary in more detail:

<table>
  <thead>
    <tr><th>Location</th><th>Safe to edit?</th><th>Why</th></tr>
  </thead>
  <tbody>
    <tr><td><code>.rork/</code></td><td>No</td><td>The baseline for regeneration diffs. Editing it corrupts the next output</td></tr>
    <tr><td><code>Sources/Views/</code></td><td>Yes, but expect conflicts</td><td>The area Rork rewrites most. Keep your diffs minimal</td></tr>
    <tr><td><code>Sources/Services/</code></td><td>Yes</td><td>Meant to be replaced post-generation. Swap real API implementations here</td></tr>
    <tr><td><code>Sources/Extensions/</code> (yours)</td><td>Preferred</td><td>A directory Rork never generates, so conflicts can't occur</td></tr>
    <tr><td><code>*.xcodeproj</code></td><td>Yes, carefully</td><td>Build Settings survive; target restructuring gets silently reverted</td></tr>
  </tbody>
</table>

That last row matters most in practice. Build Settings flags persist across regenerations, but split a target or rework a scheme and the next generation may quietly undo it. Restructure the project file only once you're ready to stop regenerating entirely.

## Three Instruments Profiles to Run

Generated code works. At the starting line, though, it stops at "functional." The evidence for pushing past that only comes from measuring on hardware.

The stutter I opened with never appeared in the simulator. Running on a Mac CPU, the expensive computation simply never surfaced as a cost.

### 1. Time Profiler — CPU Hotspots

First thing I check when something feels slow. The classic generated pattern that shows up as a hotspot:

```swift
// Slow: recomputes every frame during scrolling
var body: some View {
    List(items) { item in
        Row(item: item, score: computeScore(for: item))
    }
}
```

If `computeScore` is non-trivial, it recalculates on every frame while scrolling. The fix is a cached version:

```swift
@State private var cachedScores: [UUID: Double] = [:]

var body: some View {
    List(items) { item in
        Row(item: item, score: cachedScores[item.id] ?? 0)
    }
    .task {
        await computeAllScores()
    }
}
```

Profile a Release build on a device, always. An unoptimized Debug build reshapes the profile enough that functions which aren't bottlenecks float to the top. I once spent a full day optimizing a function that turned out to be irrelevant.

### 2. Allocations — Memory Usage

Image handling in generated code is often the biggest memory waste. Look at Persistent allocations (not Transient). Lists that use `AsyncImage` or `UIImage(data:)` without downsampling are a usual suspect.

A helper worth pasting in:

```swift
func downsample(image data: Data, to pointSize: CGSize, scale: CGFloat) -> UIImage? {
    let imageSourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary
    guard let imageSource = CGImageSourceCreateWithData(data as CFData, imageSourceOptions) else {
        return nil
    }
    let maxDimensionInPixels = max(pointSize.width, pointSize.height) * scale
    let downsampleOptions = [
        kCGImageSourceCreateThumbnailFromImageAlways: true,
        kCGImageSourceShouldCacheImmediately: true,
        kCGImageSourceCreateThumbnailWithTransform: true,
        kCGImageSourceThumbnailMaxPixelSize: maxDimensionInPixels
    ] as CFDictionary
    guard let downsampledImage = CGImageSourceCreateThumbnailAtIndex(imageSource, 0, downsampleOptions) else {
        return nil
    }
    return UIImage(cgImage: downsampledImage)
}
```

The `kCGImageSourceShouldCache: false` on the first line is load-bearing. Drop it and `CGImageSource` retains the decoded bitmap internally, roughly cancelling out the savings you get downstream. Every time someone tells me this helper "doesn't do anything," that line is missing.

### 3. SwiftUI Performance — Tracing a Redraw to Its Cause

SwiftUI's declarative model makes redraws non-obvious, and this is the area where Xcode 26 changed the tooling, so it's worth spending some time on.

Instruments 26 ships a dedicated SwiftUI template. Its Update Groups lane lays out, on a timeline, when SwiftUI is doing update work. Where Time Profiler answers "which function is expensive," this answers "which update held the main thread, and for how long."

The more useful half is the Cause & Effect Graph. Select an update, choose "Show Cause & Effect Graph," and you get a node graph showing how a state mutation propagated into body re-evaluation. The nodes to the left of a view are the events that triggered its update.

This lands directly on the pattern Rork-generated code produces most: a view observing an `ObservableObject` redraws for any property change, including unrelated ones. That used to be a guess-and-check exercise. Now the graph names the mutation responsible.

Once you know the cause, there are two ways to fix it:

```swift
// Before: observes the whole object — unrelated changes still redraw
struct ScoreBadge: View {
    @ObservedObject var store: SessionStore
    var body: some View { Text("\(store.score)") }
}

// After: takes only the value it needs; observation stays in the parent
struct ScoreBadge: View, Equatable {
    let score: Int
    var body: some View { Text("\(score)") }
    static func == (l: Self, r: Self) -> Bool { l.score == r.score }
}
```

Passing plain values and conforming to `Equatable` lets SwiftUI skip body re-evaluation when nothing changed. Rork Max tends to hand `@ObservedObject` down to leaf views, so converting just the high-frequency ones — list rows, mostly — measurably shrinks the time spent in Update Groups.

## A Two-Branch Merge Strategy for Regenerations

The trickiest part of operating Rork Max in production is absorbing new Rork-side updates without losing your Xcode-side work. My approach is a two-branch split:

```
main            ← your hand-optimized branch
rork-generated  ← the raw output of Rork Max
```

Every time you regenerate, land the output on `rork-generated`, then merge it into `main` to pull upstream changes while keeping your edits.

The second half — the part that makes the pattern actually work — is **keep your optimizations in separate extension files** whenever possible. Don't edit `Sources/App/AppDelegate.swift` directly; create `Sources/Extensions/AppDelegate+Optimizations.swift`. The merges become vastly cleaner.

### Don't Force-Push Away Your Merge Base

This is where I got the design wrong first.

I originally force-pushed `rork-generated` on every regeneration, reasoning that the output is fresh each time so history was pointless. What that actually does is destroy the common ancestor between `main` and `rork-generated`.

Git's three-way merge decides "who changed what" by diffing both sides against the merge base. When the base regresses to some ancient commit, files Rork never touched get classified as modified-by-both, and the whole project comes back as conflicts. A regeneration that should have been a few files turned into half a day of manual resolution.

The fix is boring: stop force-pushing, and stack each generation on the last as an ordinary commit.

```bash
# run on every regeneration — no force push
git switch rork-generated
rsync -a --delete --exclude='.git/' ./rork-output/ ./
git add -A
git commit -m "Rork regenerate $(date +%Y-%m-%d)"

# pull it into your branch
git switch main
git merge rork-generated
```

The `rsync --delete` is there so files Rork dropped actually leave the tree. Copy the output over the top without it and deleted files linger on `rork-generated`, then merge back into `main` and reappear as ghosts.

With this layout the merge base pins to the previous generation commit, so conflicts narrow to the files Rork genuinely rewrote.

### When Conflicts Happen Anyway

Sometimes you have to touch Rork-owned files. When you do, leave breadcrumbs in comments: `// RORK:ORIGINAL_KEPT` or `// DOLICE:OPTIMIZATION` make the next merge much easier to reason about.

Make the markers greppable and they become history: `git log -S'DOLICE:OPTIMIZATION'` tells you when an optimization landed and when it disappeared. When you work against generated output, your changes silently reverting is always a live possibility.

## The Privacy Manifest Is What Actually Gets You Bounced

This gets its own section for one reason: it's the only item that has ever bounced a Rork Max build of mine.

Since May 1, 2024, new uploads and updates that use a Required Reason API must declare approved reason codes under `NSPrivacyAccessedAPITypes` in `PrivacyInfo.xcprivacy`. Miss it and ITMS-91053 (Missing API declaration) arrives by email minutes after upload.

The awkward part is that the scope isn't limited to code you wrote. If a bundled SDK calls a covered API internally, that counts too. Rork Max output carries template-derived dependencies, so you'll see flagged APIs you never typed.

Here's a minimal `PrivacyInfo.xcprivacy`. Note that plain `UserDefaults` usage alone requires a declaration — the easiest one to overlook.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>NSPrivacyAccessedAPITypes</key>
  <array>
    <dict>
      <key>NSPrivacyAccessedAPIType</key>
      <string>NSPrivacyAccessedAPICategoryUserDefaults</string>
      <key>NSPrivacyAccessedAPITypeReasons</key>
      <array>
        <string>CA92.1</string>
      </array>
    </dict>
  </array>
</dict>
</plist>
```

To catch this before uploading, sweep for the call sites yourself:

```bash
# find Required Reason API usage, dependencies included
grep -rn "UserDefaults\|systemUptime\|creationDate\|modificationDate\|statfs\|activeProcessorCount" \
  Sources/ Pods/ 2>/dev/null | grep -v "/Tests/"
```

Declare whatever categories come back, then confirm `PrivacyInfo.xcprivacy` is listed in the target's Copy Bundle Resources before you archive. Create the file but forget to add it to the target and you get the identical ITMS-91053. That "created it but didn't include it" variant is what cost me half a day.

## Pre-Submission Checklist

With the privacy manifest handled, here's the rest of what I verify every time:

- **Bundle Identifier**: change from the generated default (`com.rork.appname`) to your own — Apple rejects the default
- **Privacy strings in Info.plist**: rewrite `NSCameraUsageDescription` and friends in production-quality language
- **Push entitlement + certificate**: enabling it in Rork is only half the job; the certificate on Apple Developer Portal is separate
- **Dark Mode visual pass**: generated assets sometimes miss dark-mode colors; preview both modes in Xcode
- **VoiceOver labels**: Accessibility Inspector will flag missing labels the generator didn't produce
- **Launch time on-device**: TestFlight install + stopwatch. Simulator numbers lie by 2x or more

## A Note from an Indie Developer

Six months in, the thing that shifted for me was whether to treat generated output as an asset.

At first I read it as my codebase. So I rewrote whatever bothered me, normalized the naming, reorganized directories. All of it came back as conflicts on the next regeneration, and resolving them cost more than the generation had saved.

Now I treat the output as a delivery that arrives on a schedule. You don't edit a delivery; you write your changes on your own side. Hold that line and regeneration takes minutes. The months I didn't hold it, I lost weekends.

The other habit that changed is when I measure. I used to open Instruments after the features were done. Now I profile once on a device as soon as the first list-heavy screen exists. Looking early tells you what quirks that particular generation has, so you stop walking into the same trap for the rest of the build. The stutter I opened with hasn't come back since I started doing this.

Getting a faster tool meant deciding for myself where to slow down. That's roughly where I've landed.
