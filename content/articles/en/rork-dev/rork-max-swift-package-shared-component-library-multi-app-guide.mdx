It was a late evening spent on the tap feedback of a wallpaper card. I tightened the spring `response` from 0.4 seconds to 0.3, and the card finally felt right under my thumb. The next morning I opened a different app in the family — a healing app with what looked like the same card — and it was still moving with the old value. The fix hadn't crossed the wall between projects.

Rork Max makes this drift easier to produce. The SwiftUI it generates is good, but each generation sees one project at a time. Ask for a card in two apps and you get two slightly different cards: a corner radius off by a couple of points, a shadow that's a touch heavier. They multiply quietly with every app you add.

The short answer is a shared UI library built with Swift Package Manager (SPM): one fix, one test, and each app picks it up when you bump the version. One more thing up front — the card code in the first version of this article didn't compile as written, and `Color(hex:)` was used without ever being defined. Both are corrected below, so the steps now run end to end.

---

## Why Rork Max Projects Need a Shared Package

Rork Max generates SwiftUI scoped to a single app, which is sensible — it can't know about your other projects. But for a family of related apps, three things scatter:

**Theme colors.** Each project keeps its own asset-catalog entry, with its own RGB values and dark-mode variants. Moving a brand color from `#7B68EE` to `#6A5ACD` means opening every project.

**Animation constants.** Values like `spring(response: 0.4, dampingFraction: 0.75)` are pasted into individual files, so changing the feel of the app is the same chore repeated.

**Component drift.** "A card" exists everywhere, but one app rounds at 16 pt and another at 14 pt. A 1–2 pt gap is hard to name, yet users read it as a faint roughness.

With a shared package, these collapse into one `Package.swift` and a handful of source files.

## Designing the Library Boundary

Before writing code, I sort things into "what never changes" and "what differs per app." If you skip this step, the library slowly absorbs app-specific code.

<table>
<thead>
<tr><th>Category</th><th>Lives in</th><th>Examples</th></tr>
</thead>
<tbody>
<tr><td>Stable across apps</td><td>Library</td><td>Animation presets, shadow/blur/corner-radius tokens, <code>ButtonStyle</code>s, cards, banners, tag chips, thin haptics wrappers</td></tr>
<tr><td>Differs per app</td><td>App</td><td>Brand colors, font families, app-specific icons, business logic</td></tr>
<tr><td>Touches an external SDK</td><td>App (or a separate target)</td><td>AdMob banners, analytics, purchase SDK wrappers</td></tr>
</tbody>
</table>

I learned the last row the hard way. My first library included a wrapper around AdMob's `GADBannerView`, and the SDK dependency spread into apps that don't even show ads. Every build felt heavier than it should have. These days I check against a single sentence: **the library holds the feel that doesn't change; brand decisions and SDKs stay in the app.**

## Creating the Swift Package

Create the package next to your app projects:

```bash
mkdir -p ~/Developer/DoliceUIKit
cd ~/Developer/DoliceUIKit
swift package init --type library --name DoliceUIKit
```

Set the minimum to iOS 17 so `@Observable` is available:

```swift
// Package.swift
// swift-tools-version: 5.10
import PackageDescription

let package = Package(
    name: "DoliceUIKit",
    platforms: [
        .iOS(.v17)
    ],
    products: [
        .library(
            name: "DoliceUIKit",
            targets: ["DoliceUIKit"]
        ),
    ],
    dependencies: [],
    targets: [
        .target(
            name: "DoliceUIKit",
            dependencies: [],
            path: "Sources/DoliceUIKit"
        ),
        .testTarget(
            name: "DoliceUIKitTests",
            dependencies: ["DoliceUIKit"],
            path: "Tests/DoliceUIKitTests"
        ),
    ]
)
```

Keep `dependencies` empty. If you eventually need an external SDK, put it in its own target.

## The Theme Injection System

Each app needs its own colors and fonts, injected through SwiftUI's environment. First, the helper the samples rely on. SwiftUI has no built-in hex initializer, so without this the build fails:

```swift
// Sources/DoliceUIKit/Theme/Color+Hex.swift

import SwiftUI

public extension Color {
    /// Builds a Color from "#7B68EE" or "7B68EE"
    init(hex: String) {
        let cleaned = hex.trimmingCharacters(in: CharacterSet.alphanumerics.inverted)
        var value: UInt64 = 0
        Scanner(string: cleaned).scanHexInt64(&value)
        let r = Double((value >> 16) & 0xFF) / 255
        let g = Double((value >> 8) & 0xFF) / 255
        let b = Double(value & 0xFF) / 255
        self.init(.sRGB, red: r, green: g, blue: b, opacity: 1)
    }
}
```

Then the theme protocol and the environment key:

```swift
// Sources/DoliceUIKit/Theme/AppTheme.swift

import SwiftUI

/// Each app conforms to this and injects it at the root
public protocol AppThemeable: Sendable {
    var primary: Color { get }
    var secondary: Color { get }
    var surface: Color { get }
    var onSurface: Color { get }
    var fontTitle: Font { get }
    var fontBody: Font { get }
    var fontCaption: Font { get }
}

/// Default theme for development and previews
public struct DefaultAppTheme: AppThemeable {
    public var primary: Color { Color(hex: "#7B68EE") }
    public var secondary: Color { Color(hex: "#48D1CC") }
    public var surface: Color { Color(.systemBackground) }
    public var onSurface: Color { Color(.label) }
    public var fontTitle: Font { .system(.title2, design: .rounded, weight: .bold) }
    public var fontBody: Font { .system(.body) }
    public var fontCaption: Font { .system(.caption) }

    public init() {}
}

private struct AppThemeKey: EnvironmentKey {
    static let defaultValue: any AppThemeable = DefaultAppTheme()
}

public extension EnvironmentValues {
    var appTheme: any AppThemeable {
        get { self[AppThemeKey.self] }
        set { self[AppThemeKey.self] = newValue }
    }
}
```

The `Sendable` requirement is there so the `static let` in the environment key doesn't turn into a concurrency error when you move to the Swift 6 language mode. For how those diagnostics read in practice, see [Swift 6 Strict Concurrency Migration with MainActor and Sendable](/en/articles/rork-dev/rork-max-swift-6-strict-concurrency-migration-mainactor-sendable).

In each app, define one conforming type and inject it:

```swift
// WallpaperApp/WallpaperAppTheme.swift
import SwiftUI
import DoliceUIKit

struct WallpaperAppTheme: AppThemeable {
    var primary: Color { Color(hex: "#FF6B9D") }
    var secondary: Color { Color(hex: "#FFB347") }
    var surface: Color { Color(.systemBackground) }
    var onSurface: Color { Color(.label) }
    var fontTitle: Font { .custom("ZenMaruGothic-Bold", size: 20) }
    var fontBody: Font { .custom("ZenMaruGothic-Regular", size: 16) }
    var fontCaption: Font { .custom("ZenMaruGothic-Regular", size: 12) }
}

@main
struct WallpaperApp: App {
    var body: some Scene {
        WindowGroup {
            RootView()
                .environment(\.appTheme, WallpaperAppTheme())
        }
    }
}
```

The payoff: add a new field to `AppThemeable` and every app that hasn't implemented it fails to compile. A missed brand update stops depending on anyone's memory.

One caution on fonts. Bundle custom font files such as `ZenMaruGothic` in each app target, not in the library. If the name doesn't match, `Font.custom` doesn't raise an error — it quietly falls back to the system font — so check on a real device once.

## Building the Card Component

The first version of this article passed `style == .flat ? RoundedRectangle(...) : nil` straight into `overlay`. There is no `overlay` that accepts `nil` as a `View`, so that never compiled. Use an `if` inside the `overlay` closure instead:

```swift
// Sources/DoliceUIKit/Components/ContentCard.swift

import SwiftUI

public struct ContentCard<Content: View>: View {
    @Environment(\.appTheme) private var theme
    @Environment(\.colorScheme) private var colorScheme

    private let content: Content
    private let style: CardStyle

    public enum CardStyle {
        case standard   // Subtle shadow
        case elevated   // Stronger shadow, premium feel
        case flat       // No shadow, thin border
    }

    public init(style: CardStyle = .standard, @ViewBuilder content: () -> Content) {
        self.style = style
        self.content = content()
    }

    public var body: some View {
        content
            .background(cardBackground)
            .clipShape(RoundedRectangle(cornerRadius: cardCornerRadius))
            .shadow(color: shadowColor, radius: shadowRadius, x: 0, y: shadowY)
    }

    private var cardBackground: some View {
        theme.surface
            .overlay {
                if style == .flat {
                    RoundedRectangle(cornerRadius: cardCornerRadius)
                        .strokeBorder(theme.primary.opacity(0.2), lineWidth: 1)
                }
            }
    }

    private var cardCornerRadius: CGFloat { 16 }

    private var shadowColor: Color {
        switch style {
        case .standard: return Color.black.opacity(colorScheme == .dark ? 0.3 : 0.08)
        case .elevated: return theme.primary.opacity(0.2)
        case .flat:     return .clear
        }
    }

    private var shadowRadius: CGFloat {
        switch style {
        case .standard: return 8
        case .elevated: return 20
        case .flat:     return 0
        }
    }

    private var shadowY: CGFloat {
        switch style {
        case .standard: return 4
        case .elevated: return 8
        case .flat:     return 0
        }
    }
}
```

Compare it with what Rork Max tends to generate in two separate projects:

**Before — two apps, two near-identical cards:**

```swift
// In WallpaperApp
struct WallpaperCard: View {
    var body: some View {
        content
            .background(Color(.systemBackground))
            .clipShape(RoundedRectangle(cornerRadius: 16))
            .shadow(color: .black.opacity(0.08), radius: 8, x: 0, y: 4)
    }
}

// In HealingApp — almost the same, but not quite
struct HealingCard: View {
    var body: some View {
        content
            .background(Color(.systemBackground))
            .clipShape(RoundedRectangle(cornerRadius: 14))   // different
            .shadow(color: .black.opacity(0.1), radius: 6, x: 0, y: 3)  // different
    }
}
```

**After — one component, theme-aware:**

```swift
ContentCard(style: .elevated) {
    WallpaperThumbnailView(item: wallpaper)
}
```

A 16 pt versus 14 pt corner, or 0.08 versus 0.1 shadow opacity, no longer depends on which project you happened to be in.

## Animation Presets

Animation values drift between projects too. Pin them down as `Animation` extensions:

```swift
// Sources/DoliceUIKit/Animation/AnimationPresets.swift

import SwiftUI

public extension Animation {
    /// Standard spring for tap feedback and state changes
    static let doliceSpring = Animation.spring(
        response: 0.4,
        dampingFraction: 0.75,
        blendDuration: 0
    )

    /// Quick snap for button presses
    static let doliceSnap = Animation.spring(
        response: 0.25,
        dampingFraction: 0.8,
        blendDuration: 0
    )

    /// Smooth ease for screen transitions
    static let doliceEase = Animation.easeOut(duration: 0.35)

    /// Crossfade when wallpapers or backgrounds switch
    static let doliceContentTransition = Animation.easeInOut(duration: 0.5)
}

/// Press effect that sinks slightly on touch
public struct DolicePressEffect: ButtonStyle {
    public init() {}

    public func makeBody(configuration: Configuration) -> some View {
        configuration.label
            .scaleEffect(configuration.isPressed ? 0.94 : 1.0)
            .opacity(configuration.isPressed ? 0.85 : 1.0)
            .animation(.doliceSnap, value: configuration.isPressed)
    }
}
```

An earlier draft left an unused `@Environment(\.appTheme)` inside `DolicePressEffect`. A button style that never reads the theme doesn't need it, so it's gone.

## Integrating with Rork Max Projects

Open the Rork Max project in Xcode and choose **File → Add Package Dependencies → Add Local…**, then pick the package folder:

```
/Users/masaki/Developer/DoliceUIKit
```

As a local package, edits to the library show up in the next build of the app. For production, push it to a repository and pin by version tag:

```swift
.package(
    url: "https://github.com/dolice/DoliceUIKit.git",
    from: "1.0.0"
)
```

Once it's wired in, add a line to your Rork Max prompts so new screens don't reinvent the pieces:

```
This project imports DoliceUIKit (ContentCard, DolicePressEffect, Animation.doliceSpring, etc.).
Don't write new cards or buttons; use these. Read colors and fonts from @Environment(\.appTheme).
```

When generated code comes back, ask one question: does this already exist in DoliceUIKit? If yes, swap it in. If not, decide whether it belongs in the library.

For tightening generated code further, see [10 Refactoring Patterns for Rork Max-Generated SwiftUI Code](/en/articles/rork-dev/rork-max-swiftui-generated-code-production-refactoring-patterns). On the React Native side, [Turborepo Monorepo for Shared Components](/en/articles/rork-dev/rork-turborepo-monorepo-shared-components-guide) covers the equivalent idea.

## Testing the Library

View-level unit tests are awkward in SwiftUI, so test the parts that hold logic. The version below adds a check for `Color(hex:)`, which the first version didn't have:

```swift
// Tests/DoliceUIKitTests/ThemeTests.swift

import XCTest
import SwiftUI
@testable import DoliceUIKit

final class ThemeTests: XCTestCase {
    func testHexParsingAcceptsHashPrefix() {
        // With or without "#", the result should match
        let a = UIColor(Color(hex: "#7B68EE"))
        let b = UIColor(Color(hex: "7B68EE"))
        var (ar, ag, ab, aa): (CGFloat, CGFloat, CGFloat, CGFloat) = (0, 0, 0, 0)
        var (br, bg, bb, ba): (CGFloat, CGFloat, CGFloat, CGFloat) = (0, 0, 0, 0)
        a.getRed(&ar, green: &ag, blue: &ab, alpha: &aa)
        b.getRed(&br, green: &bg, blue: &bb, alpha: &ba)
        XCTAssertEqual(ar, br, accuracy: 0.001)
        XCTAssertEqual(ag, bg, accuracy: 0.001)
        XCTAssertEqual(ab, bb, accuracy: 0.001)
    }

    func testAnimationPresetsExist() {
        // Compiling is itself the check that the presets are defined
        _ = Animation.doliceSpring
        _ = Animation.doliceSnap
        _ = Animation.doliceEase
    }
}
```

For visual regression, [`swift-snapshot-testing`](https://github.com/pointfreeco/swift-snapshot-testing) compares rendered views against reference images and fails CI when they change unexpectedly.

## Rolling Out Across Apps

Once the library settles, agree on how versions map to changes. This is the table I keep next to the repository:

<table>
<thead>
<tr><th>Kind of change</th><th>Tag</th><th>Behavior in an app using <code>.upToNextMinor(from: "1.0.0")</code></th></tr>
</thead>
<tbody>
<tr><td>Bug fix</td><td>v1.0.1</td><td>Picked up automatically on the next package resolution</td></tr>
<tr><td>New feature</td><td>v1.1.0</td><td>Not automatic; each app updates on purpose</td></tr>
<tr><td>Breaking change (e.g. a new required protocol field)</td><td>v2.0.0</td><td>Not automatic; fix the compile errors app by app</td></tr>
</tbody>
</table>

```swift
.package(
    url: "https://github.com/dolice/DoliceUIKit.git",
    .upToNextMinor(from: "1.0.0")
)
```

Even when most of the theme is shared, each app's own character stays in its theme type. That balance — a shared floor of quality, a free ceiling of expression — is why `AppThemeable` exists.

## Pitfalls from Real Usage

**Previews crash without environment injection.** Previews don't supply your custom environment values. Add `.environment(\.appTheme, DefaultAppTheme())` to every `#Preview`:

```swift
#Preview {
    ContentCard {
        Text("Preview card")
            .padding()
    }
    .environment(\.appTheme, DefaultAppTheme())
}
```

**Local paths break in CI.** Xcode Cloud and GitHub Actions don't have `~/Developer/DoliceUIKit`. Switch the dependency to the repository URL before pushing a branch that triggers CI; a pre-commit hook that flags local-path references catches the slips. For the wider CI picture, see [CI/CD with Xcode Cloud](/en/articles/rork-dev/rork-max-xcode-cloud-cicd-complete-guide).

**Binary size.** Unused code can inflate a binary. Release builds normally have `DEAD_CODE_STRIPPING` enabled by default, but it takes a minute to confirm it reads `YES` in Build Settings for a generated Rork Max project.

## Starting Small

A shared library looks like overkill while you have one app. The moment you start the second, it begins paying for itself.

Migrating everything at once is how this stalls. Start with the three components you reuse most, see whether the workflow suits you, and widen the scope later. Your next step is small: pull `ContentCard.swift` out of one Rork Max project, load it back as a local package, and build. When you start the next app and that component is already waiting as a finished part, it's a reassuring feeling — and one I intend to keep protecting.
