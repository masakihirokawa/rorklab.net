The first prompt I ever gave Rork Max was one line: "Build a workout tracker with exercises, sets, and reps." What came back ran, but it looked like every other tracker. Screen transitions, empty states, colors: all of it was the AI's guess. I spent several rounds of follow-ups before admitting that starting over would have been faster.

What I'd like to say up front is that **a prompt works better as a user's day than as a spec.** Below are the ten habits that survived my rewrites, each with a weak and a strong example. I won't say which model sits under Rork Max, since that changes over time. This is only about how to write.

## Why the prompt matters so much

During generation the AI decides navigation structure, data storage, colors, animation, and error behavior, countless small choices. Your prompt is nearly the only handle you have on them, and whatever you leave out gets filled with a safe default.

So the quickest way to fewer revisions wasn't getting better at fixing things afterwards. It was writing down, in the first message, the things I didn't want guessed.

## Tip 1: Write the flow, not the feature list

A list of feature names doesn't tell the AI how they connect. Describe what the user sees and taps, in order, from opening the app.

Weak:

```
Build a workout tracker app with exercises, sets, and reps.
```

Strong:

```
Build a workout tracker app. When the user opens the app, they see
today's workout plan with exercises as cards. Tapping a card expands
it to show sets and reps with checkboxes. A floating "+" button adds
a custom exercise. After all sets are done, a celebration animation
plays and the summary is saved to a history screen in the bottom tab.
```

## Tip 2: Fix the visual style with numbers

Without direction you get the default look. My mistake was writing "a calm feel" and nothing else; "calm" meant something different every time.

```
Dark theme. Main background deep navy (#1A1B2E). Interactive accent
blue (#4A90D9), text soft white (#F0F0F5). SF Pro Rounded for headings,
SF Pro Text for body. Cards with a 16pt corner radius and a frosted-glass effect.
```

Hex for color, points for radius, names for fonts. Swap vague adjectives for numbers.

## Tip 3: State the navigation outright

If you let the AI guess how screens connect, transitions turn inconsistent.

```
Tab bar with 4 tabs: Home (house), Search (magnifier), Favorites (heart),
Profile (person). Home uses a NavigationStack for drill-down. Search has
a search bar on top with filter chips below.
```

## Tip 4: Include empty and error states

Real apps show their quality when there's no data, no network, or unexpected input.

```
When the recipe list is empty, show an illustration and "No recipes yet.
Tap + to add your first one." On a failed request, show "Couldn't load
recipes. Check your connection and try again." with a retry button.
While loading, use skeleton views that match the card layout.
```

Skip this and the first thing you meet on a real device is a blank screen.

## Tip 5: Ask in four passes for a bigger app

Splitting the request worked better than one giant prompt.

1. First pass: core screens and navigation
2. Second pass: data persistence and state
3. Third pass: animation and polish
4. Fourth pass: native features such as HealthKit or ARKit

Each pass builds on the last. **Ask for one layer at a time.** Once I held to that, redoing work dropped a lot.

## Tip 6: Name Apple frameworks directly

Rork Max produces native Swift, so you can ask by API name.

```
Use SwiftUI's .matchedGeometryEffect for the list-to-detail transition.
Add haptics with UIImpactFeedbackGenerator on button taps. Show the
timer countdown as a Live Activity in the Dynamic Island.
```

Naming narrows the room for look-alike alternatives. One caution: an API name that doesn't exist can send the AI off improvising to make it fit, so I check names against Apple's documentation first.

## Tip 7: Write data models down to the types

If the app handles structured data, hand over the models first.

```
Data model:
- Recipe: title (String), ingredients ([Ingredient]), steps ([String]),
  prepTime (Int, minutes), difficulty (enum: easy/medium/hard), isFavorite (Bool)
- Ingredient: name (String), quantity (Double), unit (String)
- MealPlan: date (Date), meals (dictionary mapping breakfast/lunch/dinner to Recipe)
```

Skip this and every field you add later risks breaking data you already saved.

## Tip 8: Add a nearby reference, lightly

If you like how some screen looks, name it.

```
Habit tracker with a streak calendar like GitHub's contribution graph:
green for done, gray for missed, shade showing intensity. The weekly
view should resemble Apple Health's rings.
```

One line of reference carries more than a paragraph of description.

## Tip 9: Give motion in seconds

Leave motion to chance and you get a prototype feel.

```
When a task completes, the checkbox fills with a spring animation
(0.4s, slight bounce). The card moves to "Completed" with a 0.3s
ease-in-out. Use .sensoryFeedback(.success) on completion.
```

## Tip 10: Put it on a phone and touch it

You can scan a QR code to install on your iPhone, so I test on the device after every generation. Touch targets, scroll weight, animation smoothness, and legibility are easy to miss in a simulator.

Feed what you notice straight into the next request. "The bottom tab icons are too small; make the tap area at least 44×44pt" gets through far better than "make the UI nicer."

## What I noticed looking at this as an indie developer

I've run wallpaper apps on my own for a long time, so store descriptions, review replies, and multilingual wording are things I touch almost daily. That makes me sensitive to where a user gets stuck, and when I write a Rork Max prompt I keep coming back to that view.

For a wallpaper app, say, the flow comes first: open the list, pick a favorite, save it, set it as the device wallpaper. Writing that flow one sentence at a time gave me screens in a more natural order than a list of feature names did. And when I forgot to describe what happens if saving fails, or how the list looks with no connection, I was the first to notice on a real device. My stomach tightens most when it's a review pointing it out after release.

The other thing is how I split requests. If a styling change and a data-model change land in the same pass, I can't tell which one broke things. One layer per request. When you're the only person checking everything, the request that's easiest to isolate works best.

## A starting template

When I'm stuck, I fill in this shape:

```
Build a [app type] app for [audience].

## Core features
[3-5, with the user flow]

## Visual design
[palette, typography, component shapes]

## Navigation
[tabs or flow]

## Data
[key models and relations]

## Native features
[Apple frameworks to use]

## Empty, error, loading
[what each looks like]
```

## Where to start, and the line I keep

Take an app you already have and add just Tip 1 and Tip 4, then generate again. Flow and empty states cost little to write and change the result the most.

**Write down what you don't want guessed, instead of leaving it to the AI.** I try to hold that line even on rushed days.
