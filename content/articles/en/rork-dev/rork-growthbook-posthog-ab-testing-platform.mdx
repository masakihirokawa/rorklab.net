While re-reading an earlier version of this guide, I noticed that the setup it described could never start an experiment. A GrowthBook instance was created, but nothing ever fetched the feature definitions. `useFeatureValue` kept returning its default, and the dashboard kept saying "no data." You can probably guess how long a night spent hunting for the cause can get.

The places where an experiment platform trips you up are usually upstream of the statistics: a missing initialization call, mismatched identifiers, a package name that doesn't exist. Clear those first, and you can judge the results by the numbers instead of by suspicion.

Here I'll walk through wiring **GrowthBook (the experiment engine) and PostHog (product analytics)** into the React Native app Rork generates, up to your first experiment. I've separated the code I could run locally from the parts you should check against the official docs. I've also redone the sample-size math, because the figure in the old version was wrong.

## Why GrowthBook + PostHog, Not Firebase

Firebase Remote Config plus Firebase Analytics is the shortest path to a first A/B test. Once experimentation becomes routine, a few limits show up.

The first is **how much of the statistics you can adjust**. Firebase A/B Testing runs its statistics internally, and you can't change the prior or the significance level. GrowthBook lets you choose the engine (Bayesian or frequentist) and thresholds in settings, and offers variance-reduction methods like CUPED (Controlled-experiment Using Pre-Experiment Data). Some of these, CUPED and sequential testing among them, may sit in paid plans, so check the pricing page before relying on them.

The second is **where design and analysis live**. Remote Config delivers flags and Analytics collects events, so you can't follow an experiment in one view. GrowthBook keeps definition, delivery rules, and analysis in a single dashboard, and with PostHog as the data source, your PostHog events become experiment metrics directly.

The third is **avoiding lock-in**. The cores of both GrowthBook and PostHog are open source and can be self-hosted with Docker. Some features of each sit under a separate commercial license, though. "It's all MIT, so I'm completely free" is not quite true; check which side of the line the features you want fall on.

The free tiers of GrowthBook Cloud and PostHog Cloud are enough to start. Limits and prices change, so confirm them on each vendor's pricing page before you decide.

The flow is simple. When the app starts, the GrowthBook SDK fetches the feature-definition JSON. Flags are evaluated inside the app, and the moment a user is assigned to an experiment, an exposure event goes to PostHog. GrowthBook aggregates PostHog's events and decides the winner.

One point to hold onto: **flag evaluation happens on the device, and only the definition JSON is delivered.** The delivery side only has to return definitions quickly and keep returning them.

## Step 2: Connect PostHog as the Data Source

After logging in to GrowthBook, add PostHog under `Settings > Data Sources`. You issue a Personal API Key on the PostHog side and register it with the host and project ID. Keep the key's scope to what query reads need.

Then register PostHog events as GrowthBook metrics. For example:

- `subscription_started`: subscription start, the primary metric
- `onboarding_completed`: onboarding completion, a secondary metric
- `app_session_duration`: median session length, the guardrail metric

A guardrail is a safety valve: don't adopt a "winner" if this one got worse. Chasing subscription rate while retention drops is a common failure, and an experiment with a single metric is fragile for that reason.

One thing to verify without fail is the **exposure query**. The data source settings contain an "Experiment Assignment Query" that says which event and properties are read as exposures. Its default may differ between versions, so make the event and property names your app's `trackingCallback` sends match this query exactly. If they drift, the experiment runs fine and the dashboard still says "not enough data."

## Step 3: Cache Feature Delivery on Cloudflare Workers

If the SDK calls your self-hosted GrowthBook directly, every app launch makes a round trip to the main server. Caching just the feature-definition JSON with Workers + KV avoids that.

The old version passed a `kvCacheTtl` setting to `handleRequest` from `@growthbook/edge-cloudflare`, but I couldn't confirm that option exists. The Edge SDK is also mainly aimed at rewriting web-page HTML. For returning definition JSON to a mobile SDK, writing the Worker yourself is easier to reason about.

```javascript
// worker.js — a thin KV cache for the feature-definition JSON
const TTL_MS = 60_000;

export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    const key = env.GROWTHBOOK_CLIENT_KEY;

    // Only let through the path the SDK calls
    if (request.method !== "GET" || url.pathname !== `/api/features/${key}`) {
      return new Response("Not found", { status: 404 });
    }

    const cached = await env.FEATURES_KV.get("features", "json");
    if (cached && Date.now() - cached.at < TTL_MS) {
      return respond(cached.body, "HIT");
    }

    try {
      const upstream = await fetch(`${env.GROWTHBOOK_API_HOST}/api/features/${key}`);
      if (!upstream.ok) throw new Error(`upstream ${upstream.status}`);
      const body = await upstream.text();
      ctx.waitUntil(env.FEATURES_KV.put("features", JSON.stringify({ at: Date.now(), body })));
      return respond(body, "MISS");
    } catch (e) {
      // Even if the origin is down, serve stale definitions so experiments keep running
      if (cached) return respond(cached.body, "STALE");
      return new Response("Bad gateway", { status: 502 });
    }
  },
};

function respond(body, state) {
  return new Response(body, {
    headers: {
      "content-type": "application/json",
      "cache-control": "public, max-age=30",
      "x-features-cache": state,
    },
  });
}
```

```toml
# wrangler.toml
name = "rork-growthbook-edge"
main = "worker.js"
compatibility_date = "2026-04-01"

[[kv_namespaces]]
binding = "FEATURES_KV"
id = "your-kv-namespace-id"

[vars]
GROWTHBOOK_API_HOST = "https://my-rork-growthbook.fly.dev:3100"
# The SDK client key ships inside the app (public), so vars is enough
GROWTHBOOK_CLIENT_KEY = "sdk-xxxxxxxx"
```

Behavior and latency on real Workers are outside that check. The old version claimed "under 30ms," but I couldn't back that number up, so I've withdrawn it. Measure latency from your own network and region.

```bash
# Measure 10 times and look at the trend in total time (use your own URL and key)
for i in $(seq 1 10); do
  curl -s -o /dev/null -w "%{time_total}\n" \
    "https://rork-growthbook-edge.<your-subdomain>.workers.dev/api/features/sdk-xxxxxxxx"
done
```

Three implementation notes:

- **I didn't use the Cache API.** It doesn't take effect on `workers.dev` domains, so KV is used to work even without a custom domain
- **You can't run a 10-second TTL.** KV's `expirationTtl` has a minimum (60 seconds), so expiry isn't delegated to KV; the Worker checks the stored timestamp itself. KV updates can also take a minute or more to propagate across locations, so this isn't suited to experiments that need second-level propagation
- **KV writes have limits.** Frequent refreshes can exceed the free tier, so check the current limits against your cost plan

I also removed the old `X-App-Bundle-Id` header check. Anyone can forge a header, so it isn't authentication. And since the client key is a public value, there's no secret here to protect in the first place.

## Step 4: Wire the SDKs into the Rork App

Rork projects are Expo-based, so install libraries with `npx expo install`. The old version's command was missing the `@` in a package name and wouldn't install as written.

```bash
npx expo install @growthbook/growthbook-react posthog-react-native
npx expo install @react-native-async-storage/async-storage expo-crypto
```

For `posthog-react-native`, check the README for the version you install to see whether it needs additional dependencies (file system and device-info packages), which avoids rework at build time.

For identifiers I use `randomUUID()` from `expo-crypto` instead of the old `uuid` package. React Native lacks the random-number source `uuid` expects, so without a separate polyfill it fails at runtime.

The other key point is to **call GrowthBook's initialization**. Creating the instance alone doesn't load any feature definitions.

```typescript
// src/providers/ExperimentProvider.tsx
// Provider that aligns GrowthBook and PostHog identifiers and finishes loading definitions
import { GrowthBook, GrowthBookProvider } from "@growthbook/growthbook-react";
import PostHog from "posthog-react-native";
import { useEffect, useState, type ReactNode } from "react";
import * as Crypto from "expo-crypto";
import AsyncStorage from "@react-native-async-storage/async-storage";

// Worker URL while developing; the Cloud host if you use Cloud
const API_HOST = process.env.EXPO_PUBLIC_GROWTHBOOK_API_HOST!;
// us.i.posthog.com or eu.i.posthog.com depending on your region
const POSTHOG_HOST = "https://us.i.posthog.com";

export const posthog = new PostHog(process.env.EXPO_PUBLIC_POSTHOG_KEY!, {
  host: POSTHOG_HOST,
});

export function ExperimentProvider({ children }: { children: ReactNode }) {
  const [gb, setGb] = useState<GrowthBook | null>(null);

  useEffect(() => {
    let cancelled = false;
    (async () => {
      let id = await AsyncStorage.getItem("anon_user_id");
      if (!id) {
        id = Crypto.randomUUID();
        await AsyncStorage.setItem("anon_user_id", id);
      }
      posthog.identify(id);

      const instance = new GrowthBook({
        apiHost: API_HOST,
        clientKey: process.env.EXPO_PUBLIC_GROWTHBOOK_KEY,
        attributes: { id, country: "JP" },
        // Exposure log. Make the event and property names match the dashboard's
        // Experiment Assignment Query
        trackingCallback: (experiment, result) => {
          posthog.capture("$feature_flag_called", {
            $feature_flag: experiment.key,
            $feature_flag_response: result.key,
          });
        },
      });

      // Load definitions. Give up after 2 seconds and run on defaults if it fails
      await instance.init({ timeout: 2000 });
      if (!cancelled) setGb(instance);
    })();
    return () => {
      cancelled = true;
    };
  }, []);

  // Blocking render until loading finishes would slow startup
  // Here children render as-is; defaults are returned while loading
  if (!gb) return <>{children}</>;
  return <GrowthBookProvider growthbook={gb}>{children}</GrowthBookProvider>;
}
```

One judgment call in this skeleton: until `gb` is ready it renders `children` as-is, so for the first few hundred milliseconds, screens that use `useFeatureValue` draw in the **flag-not-applied state**. If the experiment target is the first screen people see, that flicker muddies the result. In that case keep the splash screen up until `init` completes.

The `trackingCallback` sends `result.key` (the variation key) with `$feature_flag_called`. Whether the property names fit GrowthBook's default exposure query is for you to settle with what you checked in Step 2. The old version's `result.variationId` is a numeric index and can be a source of mismatch with the query's expectations.

## Step 6: Calculate the Required Sample Size First

Before reading results, decide **how many people you need before you can judge.** The old version said "about 11,000 users per arm," and that was wrong.

The conditions are:

- Baseline subscription-start rate: 3.2%
- Minimum detectable effect (MDE): 15% relative (a rise to 3.68%)
- 5% significance (two-sided), 80% power, two variations

Using the standard formula for comparing two proportions, you get **22,628 users per arm**, nearly double the old figure.

```python
import math
from statistics import NormalDist

def n_per_arm(p1, rel_mde, alpha=0.05, power=0.8):
    p2 = p1 * (1 + rel_mde)
    z = NormalDist().inv_cdf
    za, zb = z(1 - alpha / 2), z(power)
    var = p1 * (1 - p1) + p2 * (1 - p2)
    return math.ceil((za + zb) ** 2 * var / (p2 - p1) ** 2)

print(n_per_arm(0.032, 0.15))  # 22628
print(n_per_arm(0.032, 0.30))  # 6034
```

Relaxing the MDE to 30% relative drops the requirement to 6,034 per arm. The appetite for "I want to see small differences" costs a lot of users, and the numbers make that visible.

How many days it takes depends on **how many new users per day get assigned to the experiment.** That's newly exposed users, not DAU. Divide the combined total of 45,256 across both arms by daily new exposures.

## Step 7: Reading the Bayesian Output

Once an experiment runs, the dashboard shows "Chance to Win" (formerly Chance to Beat Control) and "Risk." Labels vary by UI version. If you're used to p-values, the layout may feel unfamiliar at first.

There are three pillars to reading it.

**A high Chance to Win alone isn't grounds for adopting.** It says "the probability treatment beats control," not "by how much."

**Risk is the expected loss if the decision you adopted turns out wrong.** It's expressed as a relative drop in the metric itself, so 0.5% means "even if wrong, the metric falls by about 0.5% on average." GrowthBook has an organization setting for this tolerance, and its default may not match your situation. Set thresholds from the loss your business can tolerate.

**Judge sample size by whether you reached the Step 6 number.** A rule of thumb like "at least one week, 2,000 per arm" can serve as a floor to smooth out day-of-week effects, but it isn't evidence of power. The old version conflated the two. Keep the one-week floor, but the real target is the pre-computed figure.

GrowthBook's position is that Bayesian statistics hold up better when you peek at interim results. Even so, stacking up stop decisions each time you look raises the chance of picking up a false "win." That's why the official statistics docs also offer other approaches such as sequential testing.

**Write down your stopping conditions before the experiment starts.** "Chance to Win hit 99%, so stop now" changes what the result means the moment the condition is made up afterward.

## SRM (Sample Ratio Mismatch): Suspect It Before the Results

In an experiment split 50/50, exposures that don't land exactly at 50/50 are normal. But if the skew persists as the numbers grow, something upstream is broken. That's SRM.

A chi-square test tells you whether a skew is chance.

```python
import math

def srm_p(a, b):
    t = a + b
    e = t / 2
    chi2 = ((a - e) ** 2 + (b - e) ** 2) / e
    return chi2, math.erfc(math.sqrt(chi2 / 2))  # 1 degree of freedom

print(srm_p(10600, 9400))  # (72.0, about 2e-17)  53/47: very unlikely to be chance
print(srm_p(10100, 9900))  # (2.0, about 0.157)    50.5/49.5: within chance
print(srm_p(10200, 9800))  # (8.0, about 0.0047)   51/49: worth watching
```

The first case is the same scale as the old version's example, "about 10,000 per arm at 53/47." The p-value is far below one in a trillion, which chance can't explain. GrowthBook is designed to warn when the p-value is very small, though the threshold is configurable.

Three places to suspect:

- One variation crashes more and gets re-bucketed on every restart
- Duplicate exposures from `trackingCallback` being called twice
- Stale assignments left in a cache, mixing in users who were installed before the experiment

When SRM appears, what you fix is the foundation, not the results. Reading it as "the platform is lying," not "the result is bad," and checking SRM before looking at metrics, saves a lot of detours.

## Stopping and Cleaning Up Experiments

Once you decide to adopt, set the flag to 100% rollout, mark the experiment Stopped, and remove the branch from your code. Keep the flag itself for a few days: old definitions may linger in KV, and older app versions may still be asking.

```typescript
// Before — with the flag branch
const variant = useFeatureValue("onboarding-cta-7day-trial", "control");
if (variant === "treatment") {
  return <TrialCtaScreen days={7} />;
}
return <SubscribeScreen />;

// After — treatment adopted, flag removed
return <TrialCtaScreen days={7} />;
```

Set a deadline for finished experiments' flags. Review the list at every release and delete anything left alone beyond a set period. Without that written into your process, flags become a graveyard and quietly erode trust in the platform.

## Metric Design: Where Analysis Starts Lying

Sometimes the dashboard says "win" and next month's revenue doesn't move. Most of that mismatch starts with **how you pick the primary metric.**

Before locking a metric, I ask myself one thing: "If this metric moved 10%, would what I actually care about (retention, revenue, support volume) move with it?" If you can't answer with confidence, the metric is a proxy of a proxy.

## Three Pitfalls in Operation

### Identifier drift

At the moment an anonymous ID turns into a logged-in user ID, only PostHog's identifier may change while GrowthBook's `attributes.id` stays old. Exposures and conversions then get recorded as different people. Funnel the switch through one shared hook, and update GrowthBook's attributes right after `posthog.alias()` or `identify()`.

```typescript
// Keep this as the single entry point for switching identifiers
export function switchUserId(gb: GrowthBook, newId: string) {
  posthog.identify(newId);
  gb.setAttributes({ ...gb.getAttributes(), id: newId });
}
```

### Loading on an unstable connection

Launching in airplane mode or a weak-signal area, loading may not finish in time and evaluation falls back to the default `control`. That's safe in itself, but if someone who should have been in `treatment` is counted as `control`, it becomes noise.

Step 4 gives up with `init({ timeout: 2000 })`. A launch where loading failed was never exposed to the experiment, so as long as you don't send an exposure event it doesn't mix into the analysis. **Send the exposure event only at the moment a flag is evaluated.** Don't break that line.

### Variations seen during App Review

A reviewer who opens the app may draw `treatment` and see a screen that differs from your review notes. The safe options are to set `treatment` delivery to 0% during review, or to give the review account a `reviewer` attribute and have a rule that always returns `control`.

## Privacy and App Store Review

PostHog's defaults may collect more than reviewers like. Three items worth confirming before you submit:

- Disable autocapture in production or narrow its scope; the setting's shape differs by SDK version, so check the README of the version you installed
- Settings that avoid sending anything subject to ATT, such as advertising identifiers
- A flow that obtains explicit consent to send usage data during onboarding

If you don't want to send until consent, you can set PostHog's initialization option to opt out by default and enable it after consent (a combination of `defaultOptIn: false` and `posthog.optIn()`; check the type definitions for your SDK version, since option names can vary).

The privacy manifest (iOS 17 and later) and your App Store Connect privacy answers need to match what you actually send to PostHog. Adding an experiment platform also adds a path that hands data to a third party. Building the consent flow in from the start cuts the back-and-forth with review.

## When This Stack Is the Wrong Choice

It doesn't suit every Rork project, and Step 6's calculation explains why.

- **Apps with little new-user inflow.** At a few hundred new exposures a day, seeing a 15% relative difference takes three months or more. Time spent on user interviews and watching people use screens will teach you more than an A/B test
- **Low release cadence, working alone.** Managing flags and experiments will reliably cost you feature time. The break-even is when you ship user-visible changes at least weekly and want to measure their effect
- **Businesses where reacting to the moment is the core.** If "ship it, and roll back if it flops" is faster, such as for seasonal events, the experiment cycle won't fit

This platform pays off when there's enough inflow to detect effects, changes ship regularly, and the core flows already work. Treat it as a tool that lifts the quality of decisions, not a substitute for making them.

## Migration Path from Firebase

If Firebase A/B Testing is already running, this order leads to less rework.

**Run both in parallel for two weeks.** Don't turn Firebase off; send the same events to both and compare. Trust in the new platform builds up, and migration bugs get caught while the old data is still there.

**Move metrics one at a time.** Don't try to recreate everything at once. Finish the three to five metrics your experiments really use in PostHog first, confirm they work in GrowthBook, then add more.

**Switch Remote Config last.** It's the part most likely to still be used somewhere you've forgotten. Even after the experiment use cases move, keep it for non-experiment purposes such as kill switches for a while.

Switch all three at once and you end up rolling back two, three times. Going in order costs an extra week on the calendar, but it saves one weekend.

## Your Next Step

You now have a base that can run experiments. Pick a first experiment that is cheap to change and easy to read, such as comparing two phrasings of a paid-plan price label. The code change is small, the decision is simple, and it doubles as practice for checking the health of the platform itself (identifiers, exposures, SRM).

The platform isn't the goal. I'd like to keep shaping it into a foundation I can live with for a long time, one that delivers a slightly better experience to users every day, and I still feel that way.

As a next step, run the Step 6 calculation once with your own metrics and write down how many days your first experiment will take.
