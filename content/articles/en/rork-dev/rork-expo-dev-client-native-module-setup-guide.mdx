I added `react-native-mmkv` to code Rork had generated, saved, and Expo Go refused to open the app. A red screen appeared right after the splash. Depending on the library version, the message was "Native module cannot be null" or "Failed to create a new MMKV instance." The code looked fine. I asked Rork's AI to fix it, then asked again with different wording, then a third time. Nothing changed, and it took me longer than I'd like to admit to realize the problem wasn't in the code at all.

Expo Go is a playground app. It ships with a fixed set of native libraries, and it can't load anything else. The moment you add a library that brings its own native code, Expo Go has done its job. What you need next is a development build: your own app, built with `expo-dev-client`, that can load JavaScript from your dev server.

One thing has also changed underneath all of this. As of November 2026, Rork no longer creates new Expo (React Native) projects. New apps are Swift for iPhone, Kotlin for Android, or React for the web. So this guide is for people who **already have a Rork Expo project and want to keep growing it as an Expo app**. Let's confirm that first.

## First, check where your project stands

Rork's own page, "[What happened to Expo?](https://docs.rork.com/expo)", says you can no longer create Expo projects, but existing ones keep working: you can build them, publish them, and export them to GitHub as before. The same page strongly recommends moving to Swift.

That splits readers into three cases.

To build a development build yourself, the code has to leave Rork. According to Rork's [Code Export FAQ](https://docs.rork.com/faq/code-export), export requires a paid plan and goes through GitHub only. There is no separate ZIP download, and the GitHub sync is two-way. If you add `expo-dev-client` locally and push, Rork sees the change too.

When the red screen shows up, I'd suggest starting from this table before touching any code. Once I settled on this order, I stopped sending the AI the same request three times.

## Expo Go vs. a development build

Expo's FAQ describes Expo Go as a playground for learners. It has a fixed set of native libraries and can't be changed after you install it. To rename the app, change its icon, or add a native library, you build your own app instead.

Expo's docs call a development build "your own version of Expo Go." It is close to a production build and includes every native library you added. The differences are that it loads JavaScript from the Metro dev server, and it has the developer menu and a launcher screen.

Once it's on your device, JavaScript changes still reload the usual way. You only rebuild when the native side changes. **The build is the native generation; the reload is the JavaScript generation.** Keeping those two apart removed most of my second-guessing.

## Libraries that usually force the switch

These come up often in Rork Expo projects and usually don't run in Expo Go:

- `react-native-mmkv` (fast local storage; v4 also needs `react-native-nitro-modules`)
- `react-native-purchases` (RevenueCat subscriptions)
- `react-native-vision-camera` (advanced camera)
- `@react-native-firebase/*` (native Firebase SDKs)
- `react-native-onesignal` (push notifications)

While you only use Expo SDK libraries such as `expo-image`, `expo-secure-store` or `expo-notifications`, Expo Go often keeps working. Note, though, that Expo's docs use `expo-secure-store` as the example of a library that requires rebuilding your development build. "Does it run in Expo Go?" and "Do I need to rebuild?" are separate questions.

## Three ways to build, compared

Expo's "Introduction to development builds" lists three methods (as of November 2026). All three produce the same build; they differ in where it compiles.

<table>
<thead>
<tr><th>Method</th><th>Command</th><th>What you need</th><th>When it fits</th></tr>
</thead>
<tbody>
<tr><td>Build locally</td><td><code>npx expo run:ios</code> / <code>npx expo run:android</code></td><td>Xcode or Android Studio; no Expo account</td><td>You have a Mac and are rebuilding often</td></tr>
<tr><td>Expo Build (cloud)</td><td><code>eas build --profile development --platform ios</code></td><td>An Expo account; no local native tools</td><td>No Mac, or you just want iOS running once</td></tr>
<tr><td>Expo Build on your machine</td><td><code>eas build --profile development --platform ios --local</code></td><td>An Expo account plus local native tools</td><td>You want Expo to manage signing and profiles, without counting builds</td></tr>
</tbody>
</table>

The docs also include a host support table for local builds: macOS covers Android, the iOS Simulator and physical iPhones; Windows and Linux cover Android only. Per the same page, building locally is the only way to put a development build on an iPhone without a paid Apple Developer account. The `--local` flag supports macOS and Linux; Windows via WSL may work but isn't officially supported.

You'll also see new names. "EAS Build" is now "Expo Build," and "EAS Update" is now "Expo Update." Expo says the services themselves didn't change, and the `eas` commands and `eas.json` keep their names — which is why older commands still run.

My own rule fits in a sentence: **while a Mac is within reach I build locally, and I hand iOS device signing to the cloud only on the days it's needed.**

## Step 1: Check the config (prebuild is optional)

Make sure `app.json` has the identifiers a build needs.

```json
{
  "expo": {
    "name": "MyRorkApp",
    "slug": "my-rork-app",
    "ios": {
      "bundleIdentifier": "com.yourcompany.myrorkapp"
    },
    "android": {
      "package": "com.yourcompany.myrorkapp"
    }
  }
}
```

Reverse-domain strings are the convention. They can't be changed once the app is in a store, so settle them now.

One misunderstanding worth correcting: `npx expo prebuild` generates `ios/` and `android/` from `app.json`, but if you only build in the cloud you don't need to run it yourself. The real trap is the opposite case. If you prebuilt locally and committed `ios/` and `android/`, those folders become the source of truth, and later `app.json` edits silently stop reaching the build.

I lost an evening to exactly that. I fixed the icon in `app.json`, rebuilt again and again, and kept getting the old icon. I was rereading `app.json` the whole time; the stray `ios/` folder in the repo didn't occur to me until much later. Now, when a config change won't show up, the first thing I type is `git ls-files ios android`.

```bash
# Run when you want to inspect the native side, or before a local build
npx expo prebuild --clean
```

`--clean` deletes and regenerates `ios/` and `android/`. If you've edited native files by hand, move them somewhere safe first. I wrote up how I count those hand edits and move them into config plugins in [counting what prebuild --clean erases](/articles/rork-dev/rork-expo-prebuild-native-drift-inventory-config-plugin).

## Step 2: Install expo-dev-client and build

```bash
npx expo install expo-dev-client
```

To build locally, run one of these. Each compiles, installs on the simulator or emulator, and starts the dev server. Add `--device` for a physical device.

```bash
npx expo run:ios
npx expo run:android
```

For Expo Build in the cloud, sign in with `eas-cli` and add a development profile to `eas.json`.

```bash
npm install -g eas-cli
eas login
eas build:configure
```

```json
{
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "channel": "development",
      "ios": {
        "simulator": true
      }
    },
    "preview": {
      "distribution": "internal",
      "channel": "preview"
    },
    "production": {
      "channel": "production"
    }
  }
}
```

`developmentClient: true` marks the profile as a development build. `ios.simulator: true` targets the iOS Simulator; remove it to build for a device, which also needs an Apple Developer account and device registration. The `channel` values matter in Step 4, so I set them now.

```bash
eas build --profile development --platform ios
eas build --profile development --platform android
```

Cloud queue times vary. Build quotas differ by plan and can change, so please check [Expo's pricing page](https://expo.dev/pricing) for current numbers. If a `--local` build stops with exit code 0 and no further output, I documented that case in [the build that stopped at exit code 0](/articles/rork-dev/eas-local-build-exit-code-0-quiet-empty-stub-check).

## Step 3: Start the dev server

```bash
npx expo start
```

With `expo-dev-client` installed, plain `npx expo start` targets your development build. Press `i` or `a` for a simulator, or scan the QR code on a device. If you open the development build from the home screen, the launcher lists dev servers on your network.

The earlier version of this guide recommended `npx expo start --dev-client`. Expo's current docs describe that flag as the option for development builds made **without** the `expo-dev-client` library. It does no harm, but you don't need it.

Even with the table, I can't always remember which libraries carry native code. So right after each build I save a list of the native dependencies, and compare against it later.

```js
// scripts/native-deps.mjs
// Usage:
//   node scripts/native-deps.mjs save   — right after a development build, save the native dependency list
//   node scripts/native-deps.mjs check  — compare with the current deps; exits 1 when a rebuild is needed
import { readFileSync, writeFileSync, existsSync, readdirSync } from "node:fs";
import { join } from "node:path";

const SNAPSHOT = ".native-deps.json";
const pkg = JSON.parse(readFileSync("package.json", "utf8"));
const names = Object.keys({ ...pkg.dependencies, ...pkg.devDependencies });

// Signs of native code: ios/, android/, a *.podspec, or expo-module.config.json
function hasNative(dir) {
  if (!existsSync(dir)) return false;
  if (["ios", "android", "expo-module.config.json"].some((n) => existsSync(join(dir, n)))) return true;
  return readdirSync(dir).some((f) => f.endsWith(".podspec"));
}

const current = {};
for (const name of names) {
  const dir = join("node_modules", name);
  if (!hasNative(dir)) continue;
  current[name] = JSON.parse(readFileSync(join(dir, "package.json"), "utf8")).version;
}

const mode = process.argv[2];
if (mode === "save") {
  writeFileSync(SNAPSHOT, JSON.stringify(current, null, 2) + "\n");
  console.log(`Saved ${Object.keys(current).length} native deps -> ${SNAPSHOT}`);
  process.exit(0);
}
if (mode !== "check") { console.error("Pass save or check"); process.exit(2); }
if (!existsSync(SNAPSHOT)) { console.error(`${SNAPSHOT} not found. Run save right after a build`); process.exit(2); }

const saved = JSON.parse(readFileSync(SNAPSHOT, "utf8"));
const lines = [];
for (const [n, v] of Object.entries(current)) {
  if (!(n in saved)) lines.push(`added    ${n}@${v}`);
  else if (saved[n] !== v) lines.push(`changed  ${n} ${saved[n]} -> ${v}`);
}
for (const n of Object.keys(saved)) if (!(n in current)) lines.push(`removed  ${n}`);

if (lines.length === 0) { console.log("No native changes: a reload is enough for JavaScript edits"); process.exit(0); }
console.log("Native dependencies changed. Rebuild your development build:");
for (const l of lines) console.log("  " + l);
process.exit(1);
```

Run `save` after a build and `check` when the red screen appears. A package counts as native if its folder in `node_modules` has `ios/`, `android/`, a `.podspec`, or `expo-module.config.json`. Here's the output on Node.js 22, saving with only `expo-image` installed, then adding MMKV v4 and Nitro Modules:

```text
$ node scripts/native-deps.mjs save
Saved 1 native deps -> .native-deps.json
$ node scripts/native-deps.mjs check
Native dependencies changed. Rebuild your development build:
  added    react-native-mmkv@4.0.0
  added    react-native-nitro-modules@0.31.0
$ echo $?
1
```

The script doesn't look at `app.json`. If you want everything covered, the `"fingerprint"` runtime version policy that Expo documents is the thorough option: it detects any change that may affect the native runtime. I use the script as a quick local check and fingerprint as the guard on what gets shipped.

## Step 4: Expo Update without crossed wires

If you use Expo Update (formerly EAS Update) and your development and production builds share a channel, the development build can fetch old production JavaScript, and a bug you fixed seems to come back. The per-profile `channel` values from Step 2 prevent most of that.

The other trap is a native change with an unchanged `runtimeVersion`. Expo's docs explain that the `"appVersion"` policy only bumps the runtime version when you bump the app version, so forgetting that after adding a native library lets incompatible updates reach old builds. The `"fingerprint"` policy bumps automatically whenever something native may have changed, at the cost of more frequent builds.

```json
{
  "expo": {
    "runtimeVersion": {
      "policy": "fingerprint"
    }
  }
}
```

Expo's [Runtime versions page](https://docs.expo.dev/eas-update/runtime-versions/) compares the policies. If you're unsure, switching to fingerprint at least while you're swapping native libraries makes the mix-ups much less likely.

## Three common misunderstandings

**"If it won't run in Expo Go, the code is wrong."** After adding a native library, the red screen is usually the runtime, not your code. No amount of rewriting puts a missing native module into Expo Go.

**"I'll just start a fresh Expo project in Rork to test."** As of November 2026 Rork doesn't create Expo projects. To experiment, export your existing Expo project to GitHub and build locally.

**"Once I have a development build, every change shows up."** Only JavaScript changes do. After a native library or `app.json` change, you're still on the old generation until you rebuild and reinstall.

## What to keep in Rork, and what to do locally

Once you're building locally, you'll start wondering whether to just continue in Xcode or Android Studio. I split it by the kind of change.

<table>
<thead>
<tr><th>Change</th><th>Where I do it</th><th>Why</th></tr>
</thead>
<tbody>
<tr><td>Screens, copy, new logic</td><td>Rork's chat</td><td>Easy to delegate, and the GitHub sync brings it back locally</td></tr>
<tr><td>Native libraries and development builds</td><td>Locally</td><td>Building and installing happen on my machine, and triage is faster there</td></tr>
<tr><td>Hand edits inside <code>ios/</code> or <code>android/</code></td><td>Moved into config plugins where possible</td><td>Prebuild erases them otherwise</td></tr>
<tr><td>Rebuilding in Swift or Kotlin</td><td>Rork's "Add iOS app"</td><td>Per Rork's docs, it adds the native app to the same project and leaves the Expo app untouched</td></tr>
</tbody>
</table>

Because the sync is two-way, the one rule I hold to is never editing the same files in Rork and locally at the same time. I add `expo-dev-client` locally, push, confirm it in Rork, and only then send the next request. If you want to check that exported code actually rebuilds somewhere else, I covered that in [checking exported code before a plan change](/articles/rork-basics/rork-export-rebuild-check-before-plan-change).

## Where you'll get stuck next

With a working development build, the next wall for most people is signing and store submission for TestFlight or Google Play internal testing, where store-side settings come into play. [Release automation with Fastlane and EAS](/articles/rork-dev/rork-fastlane-eas-release-automation-complete-guide) walks through that path.

And if you haven't reached development builds yet because Expo Go itself won't open, [the two sign-ins to check when Expo Go won't open](/articles/rork-basics/expo-go-login-both-terminal-and-app-preview-not-opening) removes one candidate cause.

## What to do next

Add one small native library, and take it all the way from build to launch once. Then run `node scripts/native-deps.mjs save` right there. The next time a red screen appears, your first move becomes `check`, and the long way around gets a lot shorter.

**Before fixing code in front of a red screen, I check which build generation is actually running.** It's the one question I make myself ask before sending the AI another request.
