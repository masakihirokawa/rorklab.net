An earlier version of this article stated flatly that machine-learning optimizations run inside Rork. Reading it again, I can see I filled the gaps in the official documentation with impressions and guesses: the name of a dedicated optimizer component, a table of features by plan, and a tidy set of benchmark figures. If you went looking for that API, I apologize for the lost time.

So I have rewritten it. This version separates what can be verified from what is only a hunch, and then walks you through measuring the lightness of your own app. In this revision I also added the traps in measuring itself — timing things in development mode, and confusing the JavaScript bundle with the size of the app.

## What I most want you to know: what can actually be said

Rork generates Expo and React Native projects. Most of the "lightness" people notice is explained by standard Expo and React Native behavior rather than anything unique to Rork.

What the model does internally during generation is not visible from the outside. Going back through Rork's official documentation in November 2026, I could not find any feature or API described as a runtime machine-learning optimizer. If an app feels light to me, I cannot tell whether the generation deserves the credit or whether the app simply has few dependencies and a plain structure. I think the honest thing is to say that I do not know.

## Lightness usually means "nothing extra got in"

When I rebuilt one of the wallpaper apps I run on my own, every feature I added made startup heavier, and my stomach tightened each time. Tracing it back, a large package I no longer used was still being loaded at launch.

The same dynamic may explain why a generated app feels light. With minimal dependencies, screens that each own one job, and simple state handling, an app tends to stay light by itself.

So the question worth asking is less "what did Rork do?" and more "what is in my project right now?"

## Three misunderstandings worth clearing up first

Before you measure anything, here are the assumptions I tripped over myself. Each one leads to misreading the numbers.

**"It's slow in the preview, so the app is slow."** The Performance page of the React Native docs says plainly that JavaScript thread performance suffers greatly in development mode, because of the extra warnings and checks running there. What you feel in the Rork preview or in Expo Go is not what your users will feel. Always compare release builds with release builds.

**"A small bundle means a small download."** The exported JavaScript bundle is only one part of the app. Native libraries, images, fonts, and per-platform processing all add to the size the store shows. Treat JavaScript weight and binary weight as two separate problems.

**"One measurement is enough."** Startup time drifts with the device's temperature and whatever else is running. Judge on a single number and you end up chasing noise instead of change. The dull rule of five runs and a median helped me more than anything else.

## Step 0: Build a release version before you measure

Measure on a release-configured build. If you can run the project you exported from Rork locally, these commands install a release build on a connected device:

```bash
# iOS (needs Xcode and a connected device)
npx expo run:ios --configuration Release --device

# Android (connect a device with USB debugging enabled)
npx expo run:android --variant release --device
```

An internal-distribution build from EAS Build, or a TestFlight or internal-testing build, works just as well. What matters is comparing the same kind of build each time, and never putting a development-build number next to a release-build number.

## Step 1: Export the bundle and look inside

Export the project and check the size of the output.

```bash
npx expo export --platform ios
ls -lh dist/_expo/static/js/ios/
```

On iOS and Android the output is a `.hbc` file compiled for Hermes. Its size gives you a rough sense of how heavy your JavaScript is. The number shifts with the SDK version too, so write it down as the baseline for your project. Run the same command after each feature and you will see how much each one added.

For a per-package breakdown, Expo's own **Expo Atlas** is the tool. The routine in [Expo's guide to analyzing bundles](https://docs.expo.dev/guides/analyzing-bundles/) is to export with an environment variable set, then open the recorded data in Atlas:

```bash
# Export and record bundle data to .expo/atlas.jsonl
EXPO_ATLAS=true npx expo export --platform ios

# Open the recording in the browser to see each package's share
npx expo-atlas .expo/atlas.jsonl
```

If you prefer the dev server, start it with `EXPO_ATLAS=true npx expo start` and press `shift+m` in the terminal to open Atlas from the dev tools list. The first thing I found this way was a library I had added only to format dates, taking up far more room than I had assumed.

For ways to bring the size down, see [When Your Rork App Binary Tops 150MB: 5 Causes to Isolate and a Step-by-Step Slim-Down Plan](/en/articles/rork-dev/rork-app-bundle-size-reduction-guide).

## Step 2: Measure cold start on a real device

Measure on a physical device, not the simulator. Repeating the same action about five times and recording the median is realistic.

- Fully quit the app, then launch it (a cold start)
- Time from launch until the first screen accepts input
- Measure at least once on a low-end or older device

On Android, with the device connected, the following returns the launch time in milliseconds as `TotalTime`. The package name is the `android.package` value in `app.json`.

```bash
# Stop the app first, then time a fresh launch
adb shell am force-stop com.example.myapp
adb shell am start -W -n com.example.myapp/.MainActivity
```

On iOS, the "App Launch" template in Xcode's Instruments does the job. If setting that up is a hurdle, screen-recording and stepping through frames is enough to see the trend. What matters is being able to compare before and after a change, not precision. The concrete ways to shorten startup are covered in [Practical Techniques to Cut the Startup Time of Rork-Generated Apps](/en/articles/rork-dev/rork-app-startup-time-optimization-techniques).

## Step 3: Stress the lists and the images

Heavy screens tend to cluster around lists and images.

For lists, push a few hundred rows in and scroll to see whether frames drop. Opening "Performance Monitor" from the dev menu overlays the frame rate of both the UI thread and the JavaScript thread. Which one drops tells you where to look. Keep in mind this overlay runs in a development build, so use it to read trends and make the final call against how the release build feels.

When stutter shows up, it is time to revisit how the list renders. The migration steps are in [When Your FlatList Starts Stuttering: Migrating Rork Apps to FlashList v2](/en/articles/rork-dev/rork-flashlist-v2-flatlist-migration-performance).

For images, the disk cache growing over time matters more than display speed. The longer an app lives on a device, the more its "Documents & Data" swells. See [Your Rork App's 'Documents & Data' Keeps Growing — Taming expo-image's Disk Cache](/en/articles/rork-dev/rork-expo-image-disk-cache-bloat-fix) for the fix.

## A symptom-to-cause table for narrowing things down

When the numbers come back disappointing, this is the order in which I narrow down where to look.

  <thead>
    <tr><th>Symptom</th><th>Likely cause</th><th>How to check</th><th>How to fix</th></tr>
  </thead>
  <tbody>
    <tr><td>Heavy in the preview, fine in a release build</td><td>Development-mode warnings and checks</td><td>Repeat the same action on the Step 0 release build</td><td>Nothing to fix. Compare release with release</td></tr>
    <tr><td>Startup slowed after adding one feature</td><td>A large dependency loaded at launch</td><td>Compare the Expo Atlas breakdown before and after</td><td>Defer loading until the screen that needs it, or switch to a lighter option</td></tr>

    <tr><td>UI frames drop while scrolling</td><td>Oversized images, heavy shadows or layered transparency</td><td>Swap in images sized for display and compare</td><td>Load images close to display size through expo-image</td></tr>
    <tr><td>Storage keeps growing with use</td><td>The image disk cache</td><td>Record the app's "Documents & Data" in Settings over time</td><td>Set a cache limit and decide when to clear it</td></tr>

</table>

## Which tool to use, and when

There are not many tools. If you are unsure, pick just one using this guide.

<table>
  <thead>
    <tr><th>What you want to know</th><th>Tool</th><th>When to reach for it</th></tr>
  </thead>
  <tbody>
    <tr><td>How heavy the JavaScript is</td><td><code>npx expo export</code> and the output size</td><td>A fixed checkpoint after every feature</td></tr>
    <tr><td>Which package is heavy</td><td>Expo Atlas</td><td>When the bundle has grown noticeably since last time</td></tr>
    <tr><td>How long startup takes</td><td><code>adb shell am start -W</code> on Android, Instruments on iOS</td><td>Before a release, and after touching the launch path</td></tr>
    <tr><td>Which thread is stuck</td><td>Performance Monitor in the dev menu</td><td>When scrolling or navigation stutters</td></tr>
  </tbody>
</table>

In short: **watch the export size as your checkpoint, and use Atlas and Performance Monitor to find causes.** You do not need all of them on day one.

## Guardrails for keeping performance after you add your own code

Adding hand-written code to a generated app can make it suddenly heavy. These are the lines I try to hold.

- Before adding a dependency, pause and ask whether you truly need it
- Render long lists with a virtualized list component, always
- Load images close to their display size through `expo-image`
- Push heavy work until after the first screen has appeared

None of this is special technique. It is a modest brake that helps you keep the plain structure the generation gave you. I keep my measurements in a tiny table with only four columns: the date, the build type, the export size, and the median startup time. Every time I added more columns, I stopped keeping it up, so I settled on these four.

## Telling Rork what you care about

When you ask Rork to generate something, a line about performance can help the result land closer to your intent. For example: "Prioritize running on older devices," or "The list screen shows many images."

I have no evidence, though, that this "triggers" a particular optimization. Treat it as a rule of thumb: stating the conditions tends to bring back a structure nearer to what you meant. Verify the outcome with Steps 0 to 3 every time.

## Where you will probably get stuck next: setting a startup budget

Once you start measuring, the next question is usually "how many milliseconds counts as good enough?" I got stuck there too. What helped was not an absolute target but a budget: never make it worse than last time. How I decide what gets to run on the launch path is in [Managing Startup Time as a Budget: How I Deferred SDK Init Across Six Apps](/en/articles/rork-dev/rork-startup-time-budget-deferred-sdk-init-six-apps).

## Wrapping up

**Talk about a generated app's lightness with your own numbers from a release build, not with rumors.** That is the line I was reminded of while rewriting this.

As a next step, run `npx expo export` on a Rork-built app you have at hand and record the size of the output file. One number is enough to make your next "should I add this?" decision far calmer.
