It was September 11, 2026, and I had just added 67 new prints to my ukiyo-e wallpaper app, IDs 1353 through 1419. I uploaded the images, bumped the ID limit on the server, opened the app, and saw the new prints sitting at the top of New. I closed the laptop feeling done.

I wasn't. Filter by artist, and not one of the 67 appeared. They were in New, they were in the full list, and they were nowhere in the category screens.

The cause was almost embarrassing. I had raised the limit and never shipped the per-category ID files. Nothing errored. Nothing crashed. That was exactly why it took a while to notice.

**A change that adds items and a change that gives them a home should travel in the same shipment.** Of everything I've learned keeping wallpaper apps running as an indie developer, this rule is the dullest and the one that has paid off most. If your Rork-built Expo app pulls its catalog from a server, the same gap is waiting there. Below is how I close it from both sides.

## What actually happened

My server answers two kinds of questions. The config answer includes the highest wallpaper ID currently served, which is effectively the item limit. The app counts up to that ID to build the full list and New.

The category answer is separate. Each category is a plain text file of IDs on the server, and `category_list.php` holds a map from category number to file name. When the app asks for `?category=32`, the server reads that file and returns comma-separated IDs.

The piece that matters is the **range filter** on the category answer. The server only returns IDs between the minimum ID and the current limit. It exists so the app never sees IDs whose images aren't uploaded yet.

Here's the state I left things in:

- Limit: raised to 1419, so New and the full list showed 1353–1419
- Category files: the old versions, ending at 1352
- Result: no new ID appeared in any filtered list

And when a file is missing, or a category isn't in the map, the server returns a fixed fallback of `1` and stops. It's an ordinary safety net that keeps the app from crashing. It also hid the problem beautifully.

## The ordering surprise

My first instinct was that the limit and the category files had to go up at exactly the same moment. Rereading the range filter changed my mind: **category files are safe to ship first.**

Any ID above the limit is dropped by the server, even if a file lists it. So once the category files are live, the new IDs still appear nowhere. The moment you raise the limit, they appear in the full list and every filter at once.

Only the reverse order is dangerous. Raise the limit first and you open a window where items exist but have no home. I had opened that window and walked away from it.

So the order that is safe to stop at any step looks like this:

1. Upload the images (above the limit, so nobody sees them)
2. Ship the category files and the map (outside the range, still invisible)
3. Run the check script, then raise the limit (everything appears together)
4. Count the origin's answers, bypassing caches

The check before step 3 is the part I most wanted to add.

## A check before raising the limit

Before touching the limit, I want three answers. Is there a file on disk that isn't in the map? Is there a mapped file that isn't on disk? And does every newly visible ID belong to at least one category?

```python
#!/usr/bin/env python3
"""Before raising wallpaper_num, confirm every new ID belongs to a category.

Usage: python3 preflight_bump.py <app_dir> <current_limit> <new_limit>
exit 0 = safe to raise / exit 1 = fix the category side first
"""
import re
import sys
from pathlib import Path

SKIP = {"popular"}  # lists that are a hand-picked subset, not a full classification


def read_ids(path: Path) -> set[int]:
    return {int(t) for t in re.split(r"[^0-9]+", path.read_text()) if t}


def registered_files(php: Path) -> set[str]:
    # pick up only the right-hand side of $categoryFiles = [ 1 => '1_ad_1780_to_1804', ... ];
    block = re.search(r"\$categoryFiles\s*=\s*\[(.*?)\];", php.read_text(), re.S)
    if not block:
        sys.exit(f"NG  $categoryFiles not found in {php.name}")
    return set(re.findall(r"=>\s*'([^']+)'", block.group(1)))


def main(app_dir: str, old_num: int, new_num: int) -> int:
    root = Path(app_dir)
    files = {p.stem: p for p in (root / "categories").glob("*.txt") if p.stem not in SKIP}
    registered = registered_files(root / "category_list.php")
    problems = []

    # 1) on disk but not mapped / mapped but not on disk
    for stem in sorted(set(files) - registered):
        problems.append(f"not mapped: categories/{stem}.txt is missing from category_list.php")
    for stem in sorted(registered - set(files)):
        problems.append(f"not uploaded: {stem}.txt is missing (the server will return its fallback)")

    # 2) does every newly visible ID have a home?
    covered: set[int] = set()
    for stem in registered & set(files):
        covered |= read_ids(files[stem])
    new_ids = range(old_num + 1, new_num + 1)
    orphans = [i for i in new_ids if i not in covered]
    if orphans:
        head = ", ".join(map(str, orphans[:10]))
        problems.append(f"IDs in no category: {len(orphans)} ({head} ...)")

    for p in problems:
        print("NG ", p)
    if problems:
        print("-> not raising the limit yet; fix the category side and rerun")
        return 1
    print(f"OK  all {len(new_ids)} IDs have a category; safe to set the limit to {new_num}")
    return 0


if __name__ == "__main__":
    if len(sys.argv) != 4:
        sys.exit(__doc__)
    sys.exit(main(sys.argv[1], int(sys.argv[2]), int(sys.argv[3])))
```

Against a small mock directory with three holes punched on purpose, it stops like this:

```text
NG  not mapped: categories/9_extra.txt is missing from category_list.php
NG  not uploaded: 3_new.txt is missing (the server will return its fallback)
NG  IDs in no category: 1 (12 ...)
-> not raising the limit yet; fix the category side and rerun
```

Leaving `popular` out is deliberate. A popularity list is a curated slice, so counting it as a "home" would let an item pass the check while still missing from every real filter.

I'd also suggest calling this from inside whatever script bumps the limit, rather than keeping it as a separate command to remember. On a rushed day, a separate command is the first thing to get skipped. On my side, the procedure now says "raise the limit and the lists as a pair," followed by a cache-busting count after release.

## Spotting the silent fallback in the app

However tidy the server gets, a forgotten upload will happen again someday. The hardest failure to notice is the app taking that `1` at face value and rendering a category with one lonely wallpaper.

In a Rork-built Expo app, it helps to route every category fetch through one place and make the kind of answer explicit:

```ts
// lib/catalog.ts — read a category's ID list and tell a silent fallback apart from data
export const SERVER_FALLBACK = "1"; // what the server sends when it can't read a file

export type CategoryResult =
  | { kind: "ok"; ids: number[] }
  | { kind: "fallback"; reason: string } // missing, empty, or unmapped
  | { kind: "error"; reason: string };

export function parseIdList(raw: string): number[] {
  // accept "1060, 1061, 1062" or newline-separated; anything non-numeric is a separator
  return raw
    .split(/[^0-9]+/)
    .filter((t) => t.length > 0)
    .map((t) => Number.parseInt(t, 10))
    .filter((n) => Number.isSafeInteger(n) && n > 0);
}

export function classify(raw: string, maxId: number): CategoryResult {
  const body = raw.trim();
  if (body === SERVER_FALLBACK) {
    return { kind: "fallback", reason: "server returned the fixed fallback" };
  }
  const ids = parseIdList(body);
  if (ids.length === 0) return { kind: "fallback", reason: "empty list" };
  // IDs above the limit may not have images yet, so keep them off screen
  const visible = maxId > 0 ? ids.filter((id) => id <= maxId) : ids;
  return visible.length > 0
    ? { kind: "ok", ids: visible }
    : { kind: "fallback", reason: "all ids above maxId" };
}

export async function fetchCategory(
  baseUrl: string,
  categoryId: number,
  maxId: number,
  report: (msg: string) => void,
): Promise<CategoryResult> {
  try {
    const res = await fetch(`${baseUrl}?category=${categoryId}`);
    if (!res.ok) return { kind: "error", reason: `HTTP ${res.status}` };
    const result = classify(await res.text(), maxId);
    if (result.kind === "fallback") {
      // don't crash, but don't stay quiet either: record which category it was
      report(`category ${categoryId}: ${result.reason}`);
    }
    return result;
  } catch (e) {
    return { kind: "error", reason: String(e) };
  }
}
```

Feeding typical answers into `classify` sorts them like this:

```text
classify("1", 1419)               -> fallback (fixed fallback)
classify("", 1419)                -> fallback (empty list)
classify("1353, 1360, 1500", 1419) -> ok [1353, 1360]
classify("1500", 1419)            -> fallback (everything above the limit)
```

On screen, I'd show something like "This category is being prepared" for a `fallback` instead of a one-item grid. For `report`, passing your crash reporter's log call is enough. The app stays crash-proof, and the one fact you need still leaves the device.

Filtering by the limit on the client as well may look redundant. It isn't: an older server version or a slightly stale cache can still hand you IDs whose images don't exist yet.

## Counting the origin right after release

The last step is confirming what you shipped, and two traps were waiting here.

The first is caching. Hit the plain URL and you may read an older answer held at the edge, then panic that nothing changed. Appending a random query value lets you see what the origin is actually serving. I came at edge caching from a different direction in [the post about a 404 that stuck at the edge](/en/articles/app-dev/image-404-held-at-edge-split-ttl-by-status-and-pair-upload-with-purge).

The second is the counting range. Local files may already list IDs above the limit, and the server drops those. Count the local file raw and the numbers disagree even when everything is fine. **Count the local side within the same range the server uses.**

```python
#!/usr/bin/env python3
"""After release, compare per-category counts: local source of truth vs. the origin's live answer.

Usage: python3 check_live.py <app_dir> <category_list_url> <min_id> <limit>
"""
import random
import re
import sys
import urllib.request
from pathlib import Path


def ids_in(text: str, lo: int, hi: int) -> list[int]:
    # count within the server's range, or correct data will still look mismatched
    out = []
    for t in re.split(r"[^0-9]+", text):
        if t and lo <= int(t) and (hi <= 0 or int(t) <= hi):
            out.append(int(t))
    return out


def fetch(url: str) -> str:
    sep = "&" if "?" in url else "?"
    busted = f"{url}{sep}cb={random.randint(1, 10**9)}"  # skip intermediate caches and ask the origin
    with urllib.request.urlopen(busted, timeout=15) as r:
        return r.read().decode("utf-8", "replace")


def main(app_dir: str, api: str, lo: int, hi: int) -> int:
    php = (Path(app_dir) / "category_list.php").read_text()
    block = re.search(r"\$categoryFiles\s*=\s*\[(.*?)\];", php, re.S).group(1)
    ng = 0
    for cid, stem in re.findall(r"(\d+)\s*=>\s*'([^']+)'", block):
        path = Path(app_dir) / "categories" / f"{stem}.txt"
        if not path.exists():
            print(f"NG  {cid:>3} {stem:<28} no local file (mapped before the file was written)")
            ng += 1
            continue
        local = ids_in(path.read_text(), lo, hi)
        remote_raw = fetch(f"{api}?category={cid}").strip()
        remote = ids_in(remote_raw, lo, hi)
        if remote_raw == "1" and local != [1]:
            print(f"NG  {cid:>3} {stem:<28} got the fallback '1' (not uploaded or not mapped)")
            ng += 1
        elif len(local) != len(remote):
            print(f"NG  {cid:>3} {stem:<28} local={len(local)} server={len(remote)}")
            ng += 1
    print("OK  all categories match" if ng == 0 else f"-> {ng} mismatches; check which file was left behind")
    return 1 if ng else 0


if __name__ == "__main__":
    if len(sys.argv) != 5:
        sys.exit(__doc__)
    sys.exit(main(sys.argv[1], sys.argv[2], int(sys.argv[3]), int(sys.argv[4])))
```

Pointed at a local mock server that returns one stale file and one missing file, it reports:

```text
NG    2 2_meiji                      local=3 server=2
NG    3 3_new                        got the fallback '1' (not uploaded or not mapped)
-> 2 mismatches; check which file was left behind
```

Even with well over a hundred categories, it's just one request and one count per category. Had I run it on the day of those 67 prints, I'd have caught the gap before closing the laptop.

## Pitfalls

- **A category whose only ID is 1.** It's indistinguishable from the fallback, and `classify` will treat it as one. Either avoid such a category or change the fallback to a distinct string.
- **The limit lives in more than one place.** On my server, besides the shared file, each version's entry script carries a default for when the shared file can't be read. Update only the shared file and the old limit comes back exactly when something else is already broken. I update all of them with one script.
- **iOS and Android may keep settings apart.** Category data can be shared while the limit is configured per platform. Raise one and you get "new on iOS, missing on Android."
- **A new category needs both halves.** Without the map entry or without the file, the server falls back. The "not mapped" and "not uploaded" lines in the check exist for exactly this.

When a config value is added after a version has shipped and that version can't read it, you hit a different wall, which I wrote up in [the Remote Config keys post](/en/articles/rork-dev/remote-config-keys-shipped-version-cannot-read-freeze-window). If serving images from a server instead of bundling them is new to you, [the post on keeping the binary small](/en/articles/app-dev/wallpaper-app-binary-size-remote-asset-delivery) is a good starting point.

## What to do first tomorrow

Check whether your app receives "how many items exist" and "which list each item belongs to" as separate answers. If it does, even just the second check above, whether every new ID has a home, placed right before the limit goes up, would already close most of the gap.

That's where I rebuilt my own procedure from. Adding new prints still gives me a small lift every time, but I've kept one habit fixed: stop once before the limit changes.
