The night my first build finally passed, I assumed all that was left was pressing a submit button. Then I opened App Store Connect: screenshot sizes, privacy declarations, a demo account for the reviewer, and a dozen more fields. I didn't get to submit until the next morning. Preparing the store listing took far longer than writing the code.

What I'd like to say up front is that publishing is mostly store-side preparation, not building. Here is the order I follow now, with the places I tripped.

## Decide first: Rork or Rork Max

A Rork app is built on Expo (React Native), so one codebase can ship to both iOS and Android. Rork Max, as far as I've been able to confirm, is a native iOS path, and its publishing flow centers on the App Store. If you also want Android, the Expo-based route is the one to take.

Neither is better in the abstract; the store you need decides it.

- iOS and Android both: the Expo-based route (the steps below)
- iOS only, with deeper native features: Rork Max
- Not sure: start Expo-based, ship to both, and move toward native only when you need to

I cover the Rork Max flow in a separate article, so this one stays with the Expo route.

## Apply for developer accounts early

Account approval won't wait for your app. I once applied for the Apple Developer Program only after the app was finished, and spent several days unable to do anything. Now I apply on the day I start building.

The **Apple Developer Program** costs $99 per year, for individuals or organizations. An organization needs a D-U-N-S number, which can take a while to obtain. If you enroll as an individual, your legal name is shown as the seller on the store page.

**Google Play Console** is a one-time $25 fee. One condition is easy to miss: for newly created personal accounts, Google has required a closed test with a minimum number of testers over a minimum period before you can go to production. The numbers change, so check Play Console's current guidance when you sign up. Without knowing this, you can find yourself two weeks away from a launch date you thought was tomorrow.

## Get app.json right

Store identifiers are hard to change later, so settle them first.

```json
{
  "expo": {
    "name": "My App",
    "slug": "my-app",
    "version": "1.0.0",
    "icon": "./assets/icon.png",
    "ios": {
      "bundleIdentifier": "com.example.myapp",
      "supportsTablet": true,
      "buildNumber": "1"
    },
    "android": {
      "package": "com.example.myapp",
      "versionCode": 1
    }
  }
}
```

Three things to keep in mind:

- `bundleIdentifier` and `package` cannot be changed once registered with a store
- `version` is what users see; `buildNumber` and `versionCode` are internal numbers you must raise on every submission
- The tablet flag is `supportsTablet` (older samples use a different spelling)

I once forgot to bump `versionCode` and Play Console rejected the upload because the code was already used. Counting by hand works until the one time you forget, so I let EAS count.

```json
{
  "cli": { "appVersionSource": "remote" },
  "build": {
    "production": { "autoIncrement": true }
  }
}
```

That goes in `eas.json`. **Numbers are counted by the build system, not by me.** It removes one small thing that used to make my stomach tighten before every submission.

## Build with EAS

Let EAS handle signing; it's the least effort.

```bash
eas build --platform ios --profile production
eas build --platform android --profile production
```

On the first iOS build, EAS walks you through generating the distribution certificate and provisioning profile. On Android it creates an upload key and stores it for you. Google Play also offers Play App Signing, where Google manages the final signing key. What matters is the upload key: lose it and you can't ship updates, so run `eas credentials` once and confirm where it's stored.

The outputs are an `.ipa` for iOS and an `.aab` for Android. Play Console takes the `.aab`, not an `.apk`.

## Submit to the App Store

### Create the app record

In App Store Connect, create a new app and make the bundle ID match `app.json` exactly. A mismatch means your uploaded build won't attach to the record.

### Submitting with `eas submit`

```bash
eas submit --platform ios --latest
```

After the upload, App Store Connect processes the build. That can take a few minutes to a few dozen, so give it time.

### Fields to fill before review

What trips people up is rarely code. It's these:

- Screenshots (the required sizes appear in App Store Connect; follow that screen rather than an old article)
- App Privacy (if you include ad or analytics SDKs, what they collect counts too)
- A privacy policy URL
- A demo account and reviewer notes, if the app requires login
- The age rating questionnaire

My first rejection had nothing to do with bugs. **The app needed a login and I hadn't given the reviewer an account.** The reviewer is someone opening your app for the first time. Leave enough in the notes for them to reach the end.

Review typically takes a day or two, though it varies.

## Submit to Google Play

### Start with internal testing

Create the app in Play Console and upload the `.aab` to the internal testing track first. I don't go straight to production because I want to see how it behaves through the real delivery path. Signing and permission problems often show up here.

```bash
eas submit --platform android --latest
```

### Store listing limits

My earlier notes said 50 characters for the Android title. It's 30 now. Store specs shift quietly, so I trust the input field's counter over my memory.

### Data safety and target API level

Play Console has a Data safety form where you must honestly declare what your app collects. If the declaration doesn't match actual behavior, updates can be blocked. Also, the target Android API level required for new apps and updates is raised every year. Leave your Expo SDK alone for too long and one day an upload is simply refused. I think of SDK upgrades less as feature work and **more as the upkeep cost of staying on the store**.

### Staged rollout

On the production track you can set a rollout percentage.

1. Start at around 5–10%
2. Watch crash rates and reviews for a few days
3. If it's clean, widen to 50%, then 100%

Ship a bug to everyone and the rating drop takes a long time to recover from. A limited percentage buys you room to stop.

## Common rejection reasons

Across both stores, these are the reasons I've seen:

- A crash at launch (usually from never testing on a real device)
- Screenshots or descriptions that don't match actual behavior
- A privacy policy URL that doesn't open or doesn't exist
- Login required but no way for the reviewer to get in
- Permissions or SDKs in use that weren't declared
- Dead buttons or "coming soon" screens left in

Apple leans on human review, so the care you put into the notes shows directly in the outcome. Google seems to run automated checks first and moves to manual review when a policy issue turns up. For both, the check that paid off most was **using the app once as the reviewer would**.

## After release

Updates follow the same road every time.

```bash
# after bumping the version
eas build --platform all --profile production
eas submit --platform all --latest
```

Three things are enough to watch: crash rate (via Crashlytics or similar), review content, and download counts in each console. I look at them on release day and again three days later. Bugs reported in reviews become the draft of my next update.

## The one rule for a first release

If I had to compress all of this into one line:

**The last check before submitting isn't the build; it's trying the app as the person who will review it.**

If you only do one thing today, apply for both developer accounts. The waiting can overlap with finishing the app, and that's how I finally started shipping one store at a time.
