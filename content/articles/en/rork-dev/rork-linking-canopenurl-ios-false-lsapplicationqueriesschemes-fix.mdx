The morning after I added "follow us on TikTok" and "share on X" buttons to one of my wallpaper apps, reviewers started writing in to say that nothing happened when they tapped them on iPhone. Everything worked in the simulator and in my development build, so narrowing it down to store-distributed builds took half a day.

The cause was embarrassingly small: my `Info.plist` had no `LSApplicationQueriesSchemes` entries at all. I had spent those hours suspecting my code, when the answer was sitting in a config file I had not opened.

**Before you ask whether an app can be opened, declare who you are allowed to ask.** That one sentence is the whole lesson here.

This walkthrough is for anyone building with Rork (which follows Expo's app config) whose external-app buttons fail only on iOS. It goes from pinning down the cause to a pattern that will not break the same way again. Everything below reflects what I could confirm in the React Native, Expo, and Apple documentation as of November 2026.

## The short answer

There are only three places to fix:

1. Declare every scheme you query in `ios.infoPlist.LSApplicationQueriesSchemes` in `app.json`.
2. Rebuild, because that declaration is baked into the native binary.
3. Stop depending on the result of `canOpenURL`; try `openURL` and fall back to the web when it fails.

The first two make today's bug go away. The third is insurance for the day a scheme changes name or the OS tightens its rules again.

## Triage by symptom

These bugs look alike, but where they stop is usually visible from the behavior. I run down this table from the top and only do the "how to confirm" step for the row that matches.

The React Native docs state it plainly: on iOS 9 and later, if a scheme is not listed under `LSApplicationQueriesSchemes` in `Info.plist`, `canOpenURL()` always resolves to `false`. Apple added this as a privacy measure, so that apps cannot quietly probe which other apps you have installed.

## Three misunderstandings worth clearing up

A lot of what turns up in search results is half right. Here are the three that caught me.

**"`openURL` also needs the declaration."** The declaration governs `canOpenURL`, the query that asks whether something can be opened. Apple's documentation frames it that way too. You can still attempt `openURL` without it. So the real failure is not "nothing can open"; it is "the query returns `false` and your branch goes the wrong way."

**"Saving `app.json` applies the change."** `infoPlist` is native configuration, so a JavaScript update cannot deliver it, and neither can an over-the-air update such as EAS Update. You have to rebuild. Miss this and a correct fix looks broken, and you start doubting the right answer.

**"Android has nothing to do with it."** If you target Android 11 (API level 30) or later, queries about apps that are not listed under `<queries>` in your manifest do not get a real answer. The React Native docs say the same for `canOpenURL` on Android 11+. That is why the identical symptom often shows up on Android right after you fix iOS.

## Fix 1: Add `LSApplicationQueriesSchemes` in your app config

Rork follows Expo's app config, so you never need to edit `Info.plist` by hand. Add this key to `app.json` (or `app.config.ts`) at the project root. Expo's "Linking into other apps" guide describes the same approach.

```json
{
  "expo": {
    "name": "MyApp",
    "ios": {
      "bundleIdentifier": "com.example.myapp",
      "infoPlist": {
        "LSApplicationQueriesSchemes": [
          "tiktok",
          "twitter",
          "instagram",
          "fb",
          "fb-messenger",
          "youtube",
          "comgooglemaps",
          "spotify",
          "slack"
        ]
      }
    }
  }
}
```

With `app.config.ts`:

```ts
import type { ExpoConfig } from "expo/config";

const config: ExpoConfig = {
  name: "MyApp",
  slug: "myapp",
  ios: {
    bundleIdentifier: "com.example.myapp",
    infoPlist: {
      LSApplicationQueriesSchemes: [
        "tiktok",
        "twitter",
        "instagram",
        "fb",
        "fb-messenger",
        "youtube",
        "comgooglemaps",
        "spotify",
        "slack",
      ],
    },
  },
};

export default config;
```

Standard schemes such as `http`, `https`, `mailto`, `tel`, and `sms` opened fine without a declaration on my devices. I used to list them anyway, just in case. These days I would rather list only what I actually query, because the list is much easier to audit later, and, as you will see below, there is a cap on how many entries count.

## Fix 2: Use the scheme the app really registers

The classic trap is assuming the scheme matches the app's name. Writing `"x"` to open X does not do what you expect; in my testing, `"twitter"` was the one that worked. Apps can change this on their own schedule, so I check on a real device before every release. For LINE friend links, the Universal Link (`https://line.me/R/ti/p/...`) is the safer choice over `line://`.

## Fix 3: Rebuild, then check inside the binary

This is where most people get stuck, so it is worth repeating: editing `app.json` does nothing for Expo Go or for a Development Build you already installed. `infoPlist` is **baked into the native build**, so you need one of these:

```bash
# Rebuild the development client
eas build --profile development --platform ios

# Rebuild production (add --clear-cache when you suspect the cache)
eas build --profile production --platform ios --clear-cache

# Or prebuild locally and run on a device
npx expo prebuild --clean
npx expo run:ios --device
```

`expo prebuild --clean` regenerates the `ios/` directory. If you added files there by hand, set the diff aside first.

Once it is rebuilt, confirm the declaration made it in before you even launch the app. The half day I lost went to tapping around in an old build that never had the fix. Reading the built `Info.plist` is now part of the same step for me:

```bash
# After prebuild: read the generated Info.plist (replace MyApp with your project name)
plutil -p ios/MyApp/Info.plist | grep -A 12 LSApplicationQueriesSchemes

# For an .ipa downloaded from EAS Build: unzip it and read the Info.plist inside (macOS)
mkdir -p /tmp/ipa-check && unzip -oq MyApp.ipa -d /tmp/ipa-check
plutil -p /tmp/ipa-check/Payload/*.app/Info.plist | grep -A 12 LSApplicationQueriesSchemes
```

If the declaration is there, you will see the array. If nothing prints, that build does not have it.

```text
  "LSApplicationQueriesSchemes" => [
    0 => "tiktok"
    1 => "twitter"
    2 => "instagram"
  ]
```

That check separates "the config is wrong" from "the build is old" in under a minute. Doubt the artifact before you doubt the fix; that order has saved me more than once.

## Fix 4: Don't depend on `canOpenURL`

Even with the declaration in place, if your code has no fallback, the same symptom returns the moment a scheme changes. According to the React Native docs, `canOpenURL` can reject on iOS when the scheme is undeclared, and `openURL` rejects when no app can handle the URL.

There are three broad ways to write this, and the choice decides whether you need the declaration and what happens when the app is missing.

<table>
<thead><tr><th>Pattern</th><th>iOS declaration</th><th>When the app is missing</th><th>Good fit</th></tr></thead>
<tbody>
<tr><td>Branch on `canOpenURL`, then `openURL`</td><td>Required</td><td>Branch goes to the web</td><td>You want to show or hide the button in advance</td></tr>
<tr><td>Try `openURL(appUrl)`, fall back to the web on failure</td><td>Not required</td><td>Catch the reject, open the web</td><td>A button that just needs to open something when tapped</td></tr>
<tr><td>Open an `https` link from the start</td><td>Not required</td><td>Opens in the browser</td><td>The target supports Universal Links / App Links</td></tr>
</tbody>
</table>

For a button that only needs to open something when tapped, I pick the second pattern. It never queries, so it does not depend on the declaration, and every failure lands on the web. I reserve the first pattern for screens where people without the app should not see the button at all.

```ts
// utils/openExternalApp.ts
import { Linking } from "react-native";

type AppLink = {
  /** URL that opens the native app (scheme or Universal Link) */
  appUrl: string;
  /** Web fallback when the app cannot be opened */
  webUrl: string;
};

export async function openExternalApp({ appUrl, webUrl }: AppLink): Promise<void> {
  try {
    // Try to open without asking first. Rejects if no app can handle it
    await Linking.openURL(appUrl);
    return;
  } catch (e) {
    if (__DEV__) {
      console.warn("[openExternalApp] fallback to web:", appUrl, e);
    }
  }
  await Linking.openURL(webUrl);
}

// Usage
// await openExternalApp({
//   appUrl: "tiktok://user?username=example",
//   webUrl: "https://www.tiktok.com/@example",
// });
```

The key is wrapping `openURL` itself in `try/catch`. The catch is that a fallback also **hides** mistakes. Keep the warning on in development builds so a broken scheme cannot quietly route everyone to the web in production.

If you do need the first pattern to toggle buttons, check once at startup and keep the result:

```ts
// hooks/useInstalledApps.ts
import { useEffect, useState } from "react";
import { Linking } from "react-native";

const CHECKS = { tiktok: "tiktok://", x: "twitter://" } as const;
type Key = keyof typeof CHECKS;

export function useInstalledApps(): Partial<Record<Key, boolean>> {
  const [installed, setInstalled] = useState<Partial<Record<Key, boolean>>>({});
  useEffect(() => {
    let alive = true;
    (async () => {
      const result: Partial<Record<Key, boolean>> = {};
      for (const key of Object.keys(CHECKS) as Key[]) {
        // Undeclared schemes may reject, so treat failure as false
        result[key] = await Linking.canOpenURL(CHECKS[key]).catch(() => false);
      }
      if (alive) setInstalled(result);
    })();
    return () => {
      alive = false;
    };
  }, []);
  return installed;
}
```

That is far less wasteful than querying on every render. The schemes checked here must match the declaration from Fix 1 exactly.

## Fix 5: Add Android 11+ `<queries>` with a config plugin

On Android, `app.json` has no key for `<queries>`. You add it to `AndroidManifest.xml` with an Expo config plugin. Open the manifest after a prebuild first to see whether an `https` `<queries>` block is already there, so you do not duplicate it.

```js
// plugins/withQueriesSchemes.js
const { withAndroidManifest } = require("expo/config-plugins");

module.exports = function withQueriesSchemes(config, schemes = []) {
  return withAndroidManifest(config, (cfg) => {
    const manifest = cfg.modResults.manifest;
    manifest.queries = manifest.queries ?? [{}];
    const q = manifest.queries[0];
    q.intent = q.intent ?? [];
    for (const scheme of schemes) {
      const exists = q.intent.some((i) =>
        (i.data ?? []).some((d) => d.$?.["android:scheme"] === scheme)
      );
      if (exists) continue;
      q.intent.push({
        action: [{ $: { "android:name": "android.intent.action.VIEW" } }],
        data: [{ $: { "android:scheme": scheme } }],
      });
    }
    return cfg;
  });
};
```

```json
{
  "expo": {
    "plugins": [
      ["./plugins/withQueriesSchemes", ["tiktok", "twitter", "instagram"]]
    ]
  }
}
```

After `npx expo prebuild --clean`, you should see `<queries>` with one `<intent>` per scheme in `android/app/src/main/AndroidManifest.xml`. I have not run this plugin end to end on a device for this write-up, and the shape of `modResults` may differ across SDK versions, so please read the generated manifest with your own eyes.

Note that the second pattern from Fix 4, opening without asking, does not depend on `<queries>` on Android either. On both platforms, the fewer queries you make, the less configuration you have to carry.

## Call limits, entry limits, and the iOS 27 SDK

The React Native docs note that when an app linked against an older iOS version runs on iOS 9 or later, `canOpenURL` can be called only **50 times**; after that it always returns `false` until the app is reinstalled or upgraded.

On the declaration side, Apple's `canOpenURL` documentation says, in effect, that apps linked on or after iOS 15 can only use the first 50 entries of `LSApplicationQueriesSchemes` for queries. Third-party SDKs can quietly add entries, so the list deserves an occasional audit.

One more thing. As of November 2026, several open-source projects have filed issues reporting that `canOpenURL` is deprecated in the iOS 27 SDK. I have also seen claims that the entry cap was lowered further, but I could not confirm the details in Apple's own documentation, so I will not state them as fact. The direction is clear enough, though: asking which other apps are installed keeps getting narrower. The "open without asking, fall back to the web" pattern from Fix 4 goes with that current rather than against it.

## If `canOpenURL` still returns `false`

If it is still `false` after all of the above, I check in this order:

1. **The build is old.** Does the build number match what TestFlight is serving? I once fixed `app.json` and resubmitted the previous build anyway, and lost half a day. The `plutil` check from Fix 3 prevents exactly this.
2. **The EAS cache.** Re-run `eas build` with `--clear-cache`. EAS builds in the cloud, so clearing Xcode's DerivedData on your machine changes nothing.
3. **The spelling.** Compare the declared strings with the URLs you call, including case. Declarations are written without `://`, as in `tiktok`.
4. **`app.config.ts` overriding `app.json`.** If you have both, run `npx expo config --type introspect` to print the final config and confirm `LSApplicationQueriesSchemes` survived.

## Don't let the fallback replace your own check

The pattern in Fix 4 has a side effect that is easy to miss: the cleaner the fallback, the less visible a misspelled scheme becomes. Users simply see "the web opened." Part of why my original bug took half a day was that the symptom looked less like "nothing happens" and more like "something else opens."

So my pre-release checklist now includes tapping every external-app button on a device that actually has that app installed, and confirming the app itself opens. If the web opens instead, I count it as a failure. The fallback is a safety net for the people using the app; it is not a reason for me to skip looking.
