I went to make a small fix to an app I hadn't touched in a while, and the build stayed red and would not pass. As an indie developer running several apps on the App Store and Google Play, I hit this scene about once every six months. I changed nothing in the code; only the surrounding dependencies had grown stale, on the world's schedule rather than mine.

What Rork exports is an Expo (React Native) project, and its foundation rests on dozens of packages. Leave it alone, and that foundation quietly drifts. By the time you notice, the gap can be wide enough that it's unclear which piece to fix to make it run again.

What you need here is not a heroic all-at-once update, but a small rhythm one person can sustain. Split the update cadence into three, reduce the audit to a single command, and keep the project in a state you can bisect when it breaks. Let's walk through exactly how.

## Why it breaks when you "didn't touch it"

It feels unfair to break without changing your own code. But the cause is clear.

One reason is that dependencies keep shipping new versions. The other is that OS and store review requirements get updated, and old packages fall behind the new bar. When Apple imposes a new build requirement, for example, an old SDK that hasn't caught up gets rejected there.

In other words, your code is the thing standing still, and the world is moving. That is exactly why following along a little at a time, regularly, avoids the one-day disaster.

## Think of updates at three speeds

You don't need to track every package at the same cadence. I split them into three and run each on its own rhythm.

<thead>
<tr><th>Category</th><th>Cadence</th><th>Why</th></tr>
</thead>
<tbody>
<tr><td>Expo SDK itself</td><td>2-3x a year (per major release)</td><td>It's the foundation, so impact is large and worth verifying together</td></tr>
<tr><td>Ordinary libraries</td><td>About monthly, in a batch</td><td>Many small fixes; the gap widens if you wait too long</td></tr>
<tr><td>Revenue / billing native SDKs</td><td>As needed</td><td>AdMob and billing SDKs tie directly to store requirements</td></tr>
</tbody>

The Expo SDK update carries the biggest blast radius, so I do it deliberately, 2-3 times a year. Ordinary libraries get a monthly batch. Native SDKs tied to revenue, like AdMob, I bump as needed when store requirements change or a bug report comes in.

The benefit of this three-way split is that less breaks at once. Bump everything together, and when it breaks you can't tell which part caused it.

## Reduce the audit to a single command

Before and after an update, always run two checks: whether there are vulnerabilities, and whether the project is compatible as an Expo app. Both are one command.

```bash
# 1) check for known vulnerabilities
npm audit

# 2) narrow to severities that affect production
npm audit --audit-level=high

# 3) check Expo project consistency (detects version drift)
npx expo-doctor
```

`npm audit` surfaces every warning, so the count overwhelms you at first. But for indie development, what matters is `high` and above. Chasing minor warnings about dev-only tools will eat all the time you have.

`expo-doctor` tells you where the versions Expo expects diverge from what's actually installed. I use its output as a map for updating, fixing the packages it flags first.

## Pin the lockfile as the source of truth

The most effective yet most overlooked part of dependency management is how you treat the lockfile (`package-lock.json`). It is the exact table of every installed package version — and because it exists, you can reproduce the same state on another day.

```bash
# reinstall clean to reproduce exactly what the lockfile says
rm -rf node_modules
npm ci   # ci, not install: strictly follows the lockfile
```

`npm install` can move versions under certain conditions, but `npm ci` follows the lockfile strictly. Much of the "works locally but the build fails" phenomenon comes from drift right here. I recommend always aligning with `npm ci` before a production build.

Always include the lockfile in your commits. Recording it on each update lets you trace "when did I bump what" later.

## When a batch update breaks, bisect it

For the monthly ordinary-library update, bumping in a batch and then testing is efficient. Still, a batch can break because of one of the items. Deciding the bisect routine in advance keeps you calm.

1. First, revert to the pre-update state (before committing: `git checkout -- package.json package-lock.json`)
2. Update only half, then confirm the build and app launch
3. If it passes, update half of the remaining half
4. Once you find the broken group, narrow down to one item at a time within it

This "test by halves" approach reaches the cause in a few tries even with 20 packages. It is the middle path — faster than one-by-one, safer than all-at-once.

When you find the culprit package, stopping at the previous stable version instead of forcing the latest is a perfectly good decision. In indie development, "keeping it running" is the top priority; being on the latest has no value in itself.

## Leave a one-line update record

You remember the update the moment you do it, but six months later you've completely forgotten. I keep a single short note in the repository.

```text
2026-06-19 Expo SDK not bumped / monthly ordinary-library update / AdMob SDK held / npm ci + expo-doctor passed
```

Just one line, but it's a handoff to your future self. Knowing "last time I held AdMob" makes the call on whether to bump it this time faster. Without a record, you reconstruct the situation from zero every time, and that is the biggest time thief.

## Your next step

Today, run `npx expo-doctor` once against your app. If there's nothing flagged, it's healthy; if there is, that's your map of what to fix next.

Dependency management isn't flashy work, but it pays off the longer you live with generated code. Just holding a 30-minute monthly update rhythm steadily cuts down how often you break into a cold sweat over a red build six months later.
