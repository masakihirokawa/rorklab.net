Close a few social apps at 10 p.m. — it sounds like a one-line spec. Then you start building, and the first wall isn't the UI or the logic. It's a capability Apple hands out by review, and a separate process that runs without your main app.

Family Controls, DeviceActivity and ManagedSettings all hinge on the Family Controls entitlement, and when the schedule fires, your main app is not guaranteed to be running. Start from the JS side without knowing that and you will redo work.

What follows is the smallest "night shield" for an Expo-based Rork project, from entitlement request to review submission. It assumes some custom-native-module experience, but each step is laid out in order.

**What I'd put first is this line: JS handles authorization, launching the picker and registering the schedule — the extension does the actual blocking.**

I'd draw that line on paper before opening Swift; swapping the order may be where most of the rework comes from.

## Why Rork Defaults Cannot Ship a Screen Time App

Out of the box, Rork Max bundles the standard Expo SDK modules: camera, notifications, location, secure storage, and so on. None of the three Screen Time frameworks ride on that train. Specifically:

- The `FamilyControls` framework refuses to even compile without the `com.apple.developer.family-controls` entitlement on your provisioning profile
- The `DeviceActivity` framework's "fire a callback when this time window starts" mechanism is delivered as an App Extension target — not in your main app — because the OS calls it when your app is not running
- `ManagedSettings`, which actually applies the shield, depends on shared state between the main app and the extension via an App Group container

For a typical "swipe through screens" app, Rork's Vibe Coding loop covers 95% of what you need. Screen Time work, however, crosses three boundaries at once: OS-level permissions, extension targets, and shared data. Trying to fake any of these layers is the fastest way to lose a weekend. **The pragmatic move is to set up the right architecture from day one — Rork main app, Swift native module, Extension target, App Group — and never look back.**

## Architecture: The Three Frameworks at a Glance

Before we start writing code, let's pin down what each framework actually does. Confusing them is the most common source of "why won't this work" sessions later.

- **FamilyControls** is the consent and selection layer. It owns the prompt that asks the user to grant Screen Time access, and it owns `FamilyActivityPicker`, the SwiftUI component that lets the user pick which apps and categories to govern. The user's choice comes back as a `FamilyActivitySelection` — a privacy-preserving opaque token, not a list of bundle IDs
- **DeviceActivity** is the scheduling layer. It says "when this time window opens, wake up an extension" or "when this app has been used for 30 minutes today, notify me." The extension runs even when your main app is terminated
- **ManagedSettings** is the enforcement layer. Hand a `FamilyActivitySelection` to a `ManagedSettingsStore`, and the OS immediately blocks those apps with a system shield UI

So the architecture is a three-stage rocket: pick targets (FamilyControls) → register schedule (DeviceActivity) → block on cue (ManagedSettings).

### How This Maps to a Rork Project

This is the layout used throughout the article:

- **Main app (Rork Max build)**: React Native UI, calls into Swift via the custom Expo module
- **Native Module (Swift)**: bridges authorization requests, picker presentation, schedule registration, and shield management to JS
- **DeviceActivityMonitor Extension (Swift)**: a separate target. The OS wakes it up at schedule boundaries; it pulls the saved selection from shared storage and applies the shield
- **App Group**: `group.{your-bundle-id}.shield` added to both targets, used as the single source of truth for the user's blocklist via `UserDefaults(suiteName:)`

## Step 1: Entitlement Request and Xcode Configuration

The Family Controls entitlement is gated by a manual Apple review. You request it through Apple's "Requesting the Family Controls entitlement" page. Review times are not fixed, so leave yourself room in the schedule.

The easy-to-miss part: **the request is not covered by the main app alone.** Apple Developer Technical Support has stated on the Developer Forums that extensions such as DeviceActivityMonitor and DeviceActivityReport need their own Family Controls (Distribution) request; approval for the main app does not carry over. Plan on one request per bundle ID you ship.

Here is the unit of each request as a table:

<thead><tr><th>Target</th><th>Example Bundle ID</th><th>Family Controls request</th><th>Role</th></tr></thead>
<tbody>
<tr><td>Main app</td><td>com.example.screentimecontrol</td><td>Required</td><td>Authorization, picker, schedule registration</td></tr>
<tr><td>DeviceActivityMonitor</td><td>com.example.screentimecontrol.deviceactivitymonitor</td><td>Separate request</td><td>Applies the shield when the time comes</td></tr>
<tr><td>Shield Configuration (if used)</td><td>com.example.screentimecontrol.shield-config</td><td>Separate request</td><td>Look of the shield screen</td></tr>
</tbody>
</table>

In practice, drawing up this table first heads off half of the pitfalls later on. I recommend counting your requests before you add targets.

Before approval you can still develop and test on a device with the development entitlement, but a build uploaded to App Store Connect needs the Distribution one. Make the request your first move.

In Xcode, both the main app target and the extension target need these entries in their `.entitlements`:

```xml
<!-- ScreenTimeControl.entitlements -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>com.apple.developer.family-controls</key>
  <true/>
  <key>com.apple.security.application-groups</key>
  <array>
    <string>group.com.example.screentimecontrol.shield</string>
  </array>
</dict>
</plist>
```

Expected outcome: the build no longer fails with "Provisioning profile doesn't include the com.apple.developer.family-controls entitlement." If it does, your request hasn't been approved yet, or you need to regenerate the profile after approval.

## Step 2: A Custom Native Module in Rork Max

There are several ways to add a native module to a Rork Max project; here we use a local Expo Modules API module. Modules under `modules/` are autolinked, so the Swift code doesn't need to be pasted back in at every `eas build`.

The extension target is a different story. In Expo's managed workflow the `ios/` directory is regenerated by `prebuild`, so a target you added by hand in Xcode disappears on the next prebuild. Declare the extension through a config plugin such as `expo-apple-targets`, which offers the target types `device-activity-monitor`, `shield-config` and `shield-action`; `npx create-target device-activity-monitor` scaffolds one.

```bash
# Run from the project root
npx create-expo-module@latest --local modules/screen-time-control
```

This scaffolds `modules/screen-time-control/`. Replace `ios/ScreenTimeControlModule.swift` with the following bridge:

```swift
// modules/screen-time-control/ios/ScreenTimeControlModule.swift
import ExpoModulesCore
import FamilyControls
import ManagedSettings
import DeviceActivity

public class ScreenTimeControlModule: Module {
  // Shared between main app and extension via App Group
  private let appGroup = "group.com.example.screentimecontrol.shield"

  public func definition() -> ModuleDefinition {
    Name("ScreenTimeControl")

    // Ask for Family Controls authorization (call once on first launch)
    AsyncFunction("requestAuthorization") { (promise: Promise) in
      Task {
        do {
          try await AuthorizationCenter.shared.requestAuthorization(for: .individual)
          promise.resolve(true)
        } catch {
          promise.reject("AUTH_FAILED", "Family Controls authorization failed: \(error.localizedDescription)")
        }
      }
    }

    Function("authorizationStatus") { () -> String in
      switch AuthorizationCenter.shared.authorizationStatus {
        case .approved: return "approved"
        case .denied: return "denied"
        case .notDetermined: return "notDetermined"
        @unknown default: return "unknown"
      }
    }

    // Schedule a recurring shield window (e.g. 22:00 -> 07:00)
    AsyncFunction("scheduleNightShield") { (startHour: Int, endHour: Int, promise: Promise) in
      let intervalStart = DateComponents(hour: startHour)
      let intervalEnd = DateComponents(hour: endHour)
      let schedule = DeviceActivitySchedule(
        intervalStart: intervalStart,
        intervalEnd: intervalEnd,
        repeats: true
      )
      let center = DeviceActivityCenter()
      do {
        try center.startMonitoring(.nightShield, during: schedule)
        promise.resolve(true)
      } catch {
        promise.reject("SCHEDULE_FAILED", error.localizedDescription)
      }
    }

    AsyncFunction("stopShield") { () -> Bool in
      DeviceActivityCenter().stopMonitoring([.nightShield])
      let store = ManagedSettingsStore()
      store.shield.applications = nil
      store.shield.applicationCategories = nil
      return true
    }
  }
}

extension DeviceActivityName {
  static let nightShield = Self("nightShield")
}
```

The detail worth explaining: the module **only registers and cancels the schedule** (`startMonitoring` / `stopMonitoring`); applying the shield at the start time is left to the extension. Nothing guarantees your main app is running at 22:00, so anything triggered by the clock belongs in the process the OS wakes up on its own. The one exception is `stopShield`, which runs when the user taps a button on screen, so it touches `ManagedSettingsStore` from the main app.

## Step 3: Calling FamilyActivityPicker from JS

The "let the user pick which apps to block" UI must use Apple's first-party `FamilyActivityPicker`. Trying to reproduce this picker in React Native is a dead end — the tokenization model breaks the moment you cross the bridge.

```swift
// PickerView.swift - SwiftUI wrapper
import SwiftUI
import FamilyControls

struct AppPickerView: View {
  @State private var selection = FamilyActivitySelection()
  @Environment(\.dismiss) var dismiss
  let onComplete: (FamilyActivitySelection) -> Void
  let onCancel: () -> Void

  var body: some View {
    NavigationView {
      FamilyActivityPicker(selection: $selection)
        .navigationBarItems(
          leading: Button("Cancel") {
            onCancel()
            dismiss()
          },
          trailing: Button("Done") {
            onComplete(selection)
            dismiss()
          }
        )
    }
  }
}
```

Add a method to the native module to present this view:

```swift
// Append to ScreenTimeControlModule.swift
AsyncFunction("presentAppPicker") { (promise: Promise) in
  DispatchQueue.main.async {
    guard let rootVC = UIApplication.shared.connectedScenes
      .compactMap({ ($0 as? UIWindowScene)?.keyWindow?.rootViewController })
      .first else {
      promise.reject("NO_VC", "No root view controller")
      return
    }
    let picker = AppPickerView(onComplete: { selection in
      // Encode and persist to the App Group container
      let encoder = PropertyListEncoder()
      if let data = try? encoder.encode(selection),
         let defaults = UserDefaults(suiteName: self.appGroup) {
        defaults.set(data, forKey: "blockedApps")
        promise.resolve([
          "applicationCount": selection.applicationTokens.count,
          "categoryCount": selection.categoryTokens.count
        ])
      } else {
        promise.reject("ENCODE_FAILED", "Could not encode selection")
      }
    }, onCancel: {
      // Always settle the promise on cancel, or the JS await hangs forever
      promise.resolve(["cancelled": true])
    })
    let host = UIHostingController(rootView: picker)
    rootVC.present(host, animated: true)
  }
}
```

Expected behavior: from React Native, `await ScreenTimeControl.presentAppPicker()` opens Apple's native app picker. Once the user taps "Done," the JS call resolves with the count of selected apps and categories; on "Cancel" it resolves with `cancelled: true`. The actual token data — for privacy reasons — never crosses the JS bridge; it lives in the App Group and is consumed by the extension.

## Step 4: Implementing the DeviceActivityMonitor Extension

This is the linchpin. The OS calls into this extension at the moment your schedule window opens.

You can add the target with `File > New > Target > Device Activity Monitor Extension` in Xcode, or with `npx create-target device-activity-monitor` as above — the latter is the safer choice in a managed workflow. Replace the generated `DeviceActivityMonitorExtension.swift` with:

```swift
// DeviceActivityMonitorExtension.swift
import DeviceActivity
import ManagedSettings
import Foundation

class DeviceActivityMonitorExtension: DeviceActivityMonitor {
  let store = ManagedSettingsStore()
  let appGroup = "group.com.example.screentimecontrol.shield"

  override func intervalDidStart(for activity: DeviceActivityName) {
    super.intervalDidStart(for: activity)

    // Pull the FamilyActivitySelection out of the App Group
    guard let defaults = UserDefaults(suiteName: appGroup),
          let data = defaults.data(forKey: "blockedApps") else {
      return
    }
    let decoder = PropertyListDecoder()
    guard let selection = try? decoder.decode(FamilyActivitySelection.self, from: data) else {
      return
    }
    // Apply the shield
    store.shield.applications = selection.applicationTokens.isEmpty
      ? nil : selection.applicationTokens
    store.shield.applicationCategories = selection.categoryTokens.isEmpty
      ? nil : .specific(selection.categoryTokens)
  }

  override func intervalDidEnd(for activity: DeviceActivityName) {
    super.intervalDidEnd(for: activity)
    store.shield.applications = nil
    store.shield.applicationCategories = nil
  }
}
```

The OS launches this extension in the background. Its time and memory budgets are tight, and Apple does not publish the limits, so keep network calls and heavy work out. **Treat this extension as "load the saved selection, apply or remove the shield, exit."** Anything more belongs in the main app.

## Step 5: The React Native Surface

With the native side in place, the JS side stays small:

```typescript
// app/screens/ScheduleScreen.tsx
import { useEffect, useState } from "react";
import { View, Text, Button, Alert } from "react-native";
import ScreenTimeControl from "@/modules/screen-time-control";

export default function ScheduleScreen() {
  const [authStatus, setAuthStatus] = useState<string>("notDetermined");
  const [pickedCount, setPickedCount] = useState(0);

  useEffect(() => {
    setAuthStatus(ScreenTimeControl.authorizationStatus());
  }, []);

  const handleAuthorize = async () => {
    try {
      await ScreenTimeControl.requestAuthorization();
      setAuthStatus(ScreenTimeControl.authorizationStatus());
    } catch (e) {
      Alert.alert(
        "Permission required",
        "Open Settings > Screen Time and approve this app."
      );
    }
  };

  const handlePick = async () => {
    const result = await ScreenTimeControl.presentAppPicker();
    if (result.cancelled) return;
    setPickedCount(result.applicationCount + result.categoryCount);
  };

  const handleSchedule = async () => {
    await ScreenTimeControl.scheduleNightShield(22, 7);
    Alert.alert("Night shield enabled (22:00 - 07:00)");
  };

  return (
    <View style={{ padding: 16, gap: 12 }}>
      <Text>Authorization: {authStatus}</Text>
      {authStatus !== "approved" ? (
        <Button title="Authorize Screen Time" onPress={handleAuthorize} />
      ) : (
        <>
          <Button title="Pick apps to block" onPress={handlePick} />
          <Text>Selected: {pickedCount} items</Text>
          <Button title="Enable 22:00 - 07:00 shield" onPress={handleSchedule} />
          <Button
            title="Disable shield"
            onPress={() => ScreenTimeControl.stopShield()}
          />
        </>
      )}
    </View>
  );
}
```

Expected flow on first run: tapping Authorize triggers the OS Screen Time dialog. After approval, the user picks apps via the system picker, then enables the schedule. At 22:00 sharp, the OS wakes the extension, applies the shield, and the user sees the system-level block screen on every selected app — exactly as in Apple's first-party Screen Time UI.

## Common Pitfalls and How to Avoid Them

These are five spots where Screen Time projects commonly lose time. Apple's docs don't cover them in one place.

### 1. "I'm trying to send the FamilyActivitySelection over to JS and it's empty"

The contents of `FamilyActivitySelection` (the application tokens) are opaque by design for privacy. There is no design path for pulling bundle IDs or app names out and handing them to JavaScript. **The correct pattern is to return only the count to JS, persist the selection to the App Group, and let the extension consume it.**

### 2. "The shield never fires when the schedule opens"

Most often this is a misconfiguration on the extension target. Run through this checklist:

- Is the extension's Bundle ID a child of the main app, e.g. `{main-app-id}.deviceactivitymonitor`?
- Does the extension's `.entitlements` include both `com.apple.developer.family-controls = true` and the App Group?
- Has the extension's own Bundle ID been through the Family Controls request and approval (separate from the main app, as covered above)?
- Do both targets belong to the same App Group?
- Does the extension's Info.plist set `NSExtensionPrincipalClass` to `$(PRODUCT_MODULE_NAME).DeviceActivityMonitorExtension`?

### 3. "UserDefaults(suiteName:) reads come back nil from the extension"

If the App Group string differs by a single character, the read just returns `nil` — no warning, no log. Something like `group.com.example.screentimecontrol.shield` versus `group.com.example.screentime.shield` is enough. **Open the Capabilities pane on both targets and copy-paste the App Group string between them; do not type it twice.**

### 4. "Release builds crash where Debug builds were fine"

DeviceActivity extensions have little memory headroom, and code that passes in Debug can be killed by jetsam in Release. Apple doesn't publish the cap, so don't rely on a remembered number — keep the extension's body minimal, and keep crash-reporting SDKs and heavy logging out of it.

### 5. ".child authorization fails on the simulator"

`requestAuthorization(for: .child)` assumes a child device tied to a parent's Family Sharing group, and Screen Time features are best verified on a real device rather than the simulator. Budget time for building a real test family of Apple IDs. If the app is for a user's own focus, `.individual` is enough.

## Getting Past App Review

Screen Time apps get a close look at purpose. The single most useful step is making it dead obvious to the reviewer **what the app controls, on whose device, and how the user consents**. Put these three points in the App Review Notes:

- The purpose of the app (e.g. "personal focus support" or "parental controls for minors")
- The authorization flow: which screen asks, and after what explanation
- That `FamilyActivitySelection` data stays on-device and is never transmitted to a server

The text of the system authorization dialog cannot be changed by the app — Apple has said on the Developer Forums that it isn't customizable — and an `Info.plist` usage-description key added for it has no effect. So explain the request on **your own screen just before** calling `requestAuthorization`.

One more thing to align: if that screen says "from 22:00 to 07:00, only the apps you choose are blocked," the shield's actual scope should match those words. Treat the explanation and the behavior as a single contract.

## Wrapping Up — Ship the Smallest Possible Version First

Framework, entitlement, extension and shared container all have to line up, which makes this one of the more hands-on categories on iOS. The UI and most of the logic stay in React Native; the Apple-side integration is Swift.

Two first steps: **request the Family Controls entitlement for the main app and for the extension, and add the `device-activity-monitor` target through a config plugin.** While approval is pending, wire up the code from this guide so you can build the day it lands.

A basic schedule that fires the shield fits in half a day. After that it's iteration: more schedules, web-domain blocking via `store.webDomains`, usage statistics via `DeviceActivityReport`. Because the app intervenes in what people do, re-check that the explanation and the behavior still match every time you add a feature.

Your next action is one test: on a real device, schedule the night shield to start two minutes from now, close the app, and confirm that it fires.
