The most common piece of feedback I get when I put a freshly built Rork app in front of testers is: "those first few seconds after launch feel a little uncertain." The app is working. Data is loading. But a blank screen with a spinner in the middle makes people wonder whether something is stuck.

Skeleton screens are the classic answer to that feeling. They don't shorten the load time at all — what they do is show people what is about to appear, and in my testing that makes the wait feel lighter. I can't prove that with numbers, so please read what follows as hands-on experience rather than a benchmark.

Here is the scope, up front. This is for anyone whose Rork app (React Native / Expo) still shows only a spinner while loading, and who wants a skeleton that **doesn't flicker, doesn't shift the layout, and doesn't punish people who have reduced motion turned on**. I'll go from the smallest static version, to a shimmer driven by a single shared clock, to hand-off timing, and finish with a symptom-first troubleshooting table — in the order I actually reach for these things.

> Assumptions (as of November 2026, checked against the official docs): Reanimated 4.x works only with React Native's New Architecture, and in Expo you install it with `npx expo install react-native-reanimated react-native-worklets`. The code below assumes Reanimated 4.x and `expo-linear-gradient`.

## Why ActivityIndicator alone isn't enough

The code Rork generates often falls back on `ActivityIndicator`. That is better than nothing, but it carries almost no information — it only says "something is happening." It feels worst in a few places:

- Screens led by a large hero image (home, profile)
- Lists where ten or more cells appear at once
- Right after a tab switch or a navigation transition

A skeleton goes further: it **pre-announces the layout** that is about to arrive. Because elements barely move when real data lands, people's eyes don't have to go hunting.

I use a simple rule on every Rork project: any screen that may take more than a second to settle gets a skeleton. Testers who try the skeleton version often describe the app as "lighter," even though nothing measurable has changed.

Skeletons are not the right answer for every wait, though. I once put one behind a save button and the whole screen felt restless for no reason. This table is the rough draft I now start from on each screen:

</thead>

## The smallest possible skeleton

Start static. A handful of grey rectangles already tells people more than a spinner does.

```tsx
import { View, StyleSheet, type DimensionValue } from 'react-native';

// Minimal placeholder unit (width can be a number or a percentage like '70%')
export function SkeletonBlock({ width, height, radius = 8 }: {
  width: DimensionValue;
  height: number;
  radius?: number;
}) {
  return (
    <View
      style={[
        styles.block,
        { width, height, borderRadius: radius },
      ]}
    />
  );
}

const styles = StyleSheet.create({
  block: {
    backgroundColor: '#e5e7eb', // roughly Tailwind's gray-200
  },
});
```

A profile-card skeleton built from it looks like this. For screen-reader users, the parent announces "Loading" and is marked busy, while the blocks inside are hidden from accessibility.

```tsx
import { View, StyleSheet } from 'react-native';
import { SkeletonBlock } from './SkeletonBlock';

export function ProfileSkeleton() {
  return (
    <View
      style={styles.card}
      accessible
      accessibilityLabel="Loading"
      accessibilityState={{ busy: true }}
    >
      {/* Hide the inner blocks from screen readers on both iOS and Android */}
      <View
        style={styles.row}
        accessibilityElementsHidden
        importantForAccessibility="no-hide-descendants"
      >
        <SkeletonBlock width={64} height={64} radius={32} />
        <View style={styles.body}>
          <SkeletonBlock width="70%" height={16} />
          <View style={{ height: 8 }} />
          <SkeletonBlock width="40%" height={12} />
        </View>
      </View>
    </View>
  );
}

const styles = StyleSheet.create({
  card: { padding: 16 },
  row: { flexDirection: 'row', alignItems: 'center' },
  body: { flex: 1, marginLeft: 12 },
});
```

At this point the blank screen has become a preview of the layout. Even without motion, that alone changes how the first seconds feel.

## Choosing the motion — static, pulse, or shimmer

Once static blocks start to feel flat, the question is which kind of motion to add. I compare four options and decide per screen:

<table>
<thead>
<tr><th>Approach</th><th>What you need</th><th>Where it fits</th><th>Watch out for</th></tr>
</thead>
<tbody>
<tr><td>Static blocks</td><td>Plain React Native</td><td>Screens that settle in under a second; people with reduced motion on</td><td>On long waits, it can read as "frozen"</td></tr>
<tr><td>Pulse (Reanimated 4 CSS animation)</td><td>Reanimated 4.x</td><td>Lists with many blocks; when you want minimal code</td><td>No direction of travel, so less sense of progress</td></tr>
<tr><td>Shimmer (one shared clock)</td><td>Reanimated + expo-linear-gradient</td><td>The first screen people see — home, profile</td><td>Giving every block its own clock gets heavy on older Android devices</td></tr>
<tr><td>Off-the-shelf library</td><td>The library and its dependencies</td><td>When you have no time to write your own</td><td>Check each library's compatibility notes for Reanimated 4.x before adopting; I haven't verified them across the board</td></tr>
</tbody>
</table>

If I had to compress the decision into one line: **shimmer for the first screen people see, pulse for long lists, and no motion at all for screens that settle in under a second.** Motion is there to say "we're waiting," not to decorate.

A pulse takes only a few lines with Reanimated 4's CSS animations — you pass keyframes to `animationName`:

```tsx
import Animated, { useReducedMotion } from 'react-native-reanimated';
import { StyleSheet, type DimensionValue } from 'react-native';

// Pulsing skeleton (Reanimated 4.x CSS animation)
export function PulseBlock({ width, height, radius = 8 }: {
  width: DimensionValue;
  height: number;
  radius?: number;
}) {
  const reduceMotion = useReducedMotion();
  return (
    <Animated.View
      style={[
        styles.block,
        { width, height, borderRadius: radius },
        !reduceMotion && {
          animationName: { from: { opacity: 1 }, to: { opacity: 0.45 } },
          animationDuration: '900ms',
          animationIterationCount: 'infinite',
          animationDirection: 'alternate',
          animationTimingFunction: 'ease-in-out',
        },
      ]}
    />
  );
}

const styles = StyleSheet.create({
  block: { backgroundColor: '#e5e7eb' },
});
```

When reduced motion is on, the animation properties are simply not passed, and the block renders static.

## Running the shimmer on one clock

On the first screen people see, I use a shimmer — a highlight sweeping left to right. My first version gave every block its own animation. That was fine for a single profile card, but once I laid out eight rows of list skeleton — 24 blocks — the highlights on my older Android test phone drifted out of sync and scrolling started to feel sticky.

So I moved to one clock per screen: a value that runs from 0 to 1, which each block maps onto its own width. **Blocks don't own clocks; the screen owns exactly one.** Since then I haven't had to trim skeletons to keep things smooth.

```tsx
import { createContext, useContext, useEffect, type ReactNode } from 'react';
import { StyleSheet, View, type DimensionValue } from 'react-native';
import Animated, {
  cancelAnimation,
  Easing,
  interpolate,
  useAnimatedStyle,
  useReducedMotion,
  useSharedValue,
  withRepeat,
  withTiming,
  type SharedValue,
} from 'react-native-reanimated';
import { LinearGradient } from 'expo-linear-gradient';

// One clock per screen (0 -> 1 every 1.2 seconds, repeating)
const ShimmerClock = createContext<SharedValue<number> | null>(null);

export function ShimmerProvider({ children }: { children: ReactNode }) {
  const progress = useSharedValue(0);
  const reduceMotion = useReducedMotion(); // value at app start

  useEffect(() => {
    if (reduceMotion) {
      cancelAnimation(progress);
      progress.value = 0; // park the highlight just off the left edge
      return;
    }
    progress.value = withRepeat(
      withTiming(1, { duration: 1200, easing: Easing.linear }),
      -1,
      false,
    );
    return () => cancelAnimation(progress);
  }, [reduceMotion]);

  return <ShimmerClock.Provider value={progress}>{children}</ShimmerClock.Provider>;
}

// A block that only reads the clock. Width can be a number or a percentage
export function ShimmerBlock({ width, height, radius = 8 }: {
  width: DimensionValue;
  height: number;
  radius?: number;
}) {
  const progress = useContext(ShimmerClock);
  const measured = useSharedValue(0); // real width, measured via onLayout

  const style = useAnimatedStyle(() => {
    const w = measured.value;
    const p = progress ? progress.value : 0;
    return {
      // Hide the highlight until width is known, or when there is no clock
      opacity: w > 0 && progress ? 1 : 0,
      transform: [{ translateX: interpolate(p, [0, 1], [-w, w]) }],
    };
  });

  return (
    <View
      onLayout={(e) => {
        measured.value = e.nativeEvent.layout.width;
      }}
      style={[styles.container, { width, height, borderRadius: radius }]}
    >
      <Animated.View style={[StyleSheet.absoluteFill, style]}>
        <LinearGradient
          colors={['transparent', 'rgba(255,255,255,0.6)', 'transparent']}
          start={{ x: 0, y: 0 }}
          end={{ x: 1, y: 0 }}
          style={StyleSheet.absoluteFill}
        />
      </Animated.View>
    </View>
  );
}

const styles = StyleSheet.create({
  container: {
    backgroundColor: '#e5e7eb',
    overflow: 'hidden', // clip the gradient to the rounded corners
  },
});
```

On the consuming side, you wrap the whole skeleton once:

```tsx
<ShimmerProvider>
  <ProfileSkeleton />
  <ListSkeleton />
</ShimmerProvider>
```

Why it's written this way, in four points. The clock lives on the UI thread through `useSharedValue` and `withRepeat`. Each block only maps that value to its own width with `interpolate`. Because width is measured with `onLayout`, percentage widths like `'80%'` get a highlight that travels edge to edge. And `overflow: 'hidden'` keeps the highlight inside the rounded corners — drop it and the corners flicker.

## Being considerate of reduced motion

A while after shipping my first shimmer, I realised I had never once looked at how the skeleton behaved for people who had "Reduce Motion" turned on. For people sensitive to movement, a highlight sweeping across the whole screen over and over can be genuinely uncomfortable.

Reanimated animations default to `ReduceMotion.System`, which disables an animation when the device setting is on. So, left alone, things already lean toward stopping. I still call `useReducedMotion` explicitly because I want to decide *where* the highlight ends up when it stops. Resetting the clock to 0 parks the highlight just outside the left edge, leaving only the grey block.

One caveat: `useReducedMotion` returns the setting **as it was when the app started**, and changing the setting doesn't re-render your components (the official docs say so explicitly). When you test it, quit the app and reopen it after flipping the setting.

Colours need a second look in dark mode, too. A bright white highlight sliding over a dark background reads less like light and more like a white stripe.

```tsx
import { useColorScheme } from 'react-native';

// In dark mode, darken the base and soften the highlight
const scheme = useColorScheme();
const base = scheme === 'dark' ? '#2a2a2a' : '#e5e7eb';
const highlight = scheme === 'dark' ? 'rgba(255,255,255,0.08)' : 'rgba(255,255,255,0.6)';
```

## List skeletons: match the real count

The mistake I made most often early on was rendering only three skeleton rows. On a list that shows seven rows, three placeholders means the screen **suddenly stretches downward** the moment real data arrives, and people lose their place.

What keeps it stable:

- Render a little more than the visible maximum (roughly `screen height / row height`, plus one or two).
- Match the row height to the real cell **exactly**.
- Stack rows from the top with the same spacing as the real list.

```tsx
import { FlatList, View, useWindowDimensions } from 'react-native';
import { ShimmerBlock } from './ShimmerBlock';

const ROW_HEIGHT = 80; // share this constant with the real cell

export function ListSkeleton() {
  const { height } = useWindowDimensions();
  const count = Math.ceil(height / ROW_HEIGHT) + 1; // rows that fit + 1
  return (
    <FlatList
      data={Array.from({ length: count })}
      keyExtractor={(_, i) => `sk-${i}`}
      renderItem={() => (
        <View style={{ height: ROW_HEIGHT, paddingHorizontal: 16, flexDirection: 'row', alignItems: 'center' }}>
          <ShimmerBlock width={48} height={48} radius={24} />
          <View style={{ flex: 1, marginLeft: 12 }}>
            <ShimmerBlock width="80%" height={14} />
            <View style={{ height: 6 }} />
            <ShimmerBlock width="50%" height={12} />
          </View>
        </View>
      )}
      scrollEnabled={false}
    />
  );
}
```

I compute the count from screen height instead of hard-coding eight, because eight rows is too few on a tablet and too many on a small phone. Reading `ROW_HEIGHT` from the same constant as the real cell means the skeleton can't quietly fall behind when the design changes.

`scrollEnabled={false}` is there because if someone scrolls during loading, the position jumps when real data lands. On my older Android test device, the version with that one line felt noticeably less jerky right after the swap.

## Timing the hand-off

The swap from skeleton to real content can flicker if you're careless. Two habits help.

**1. Enforce a minimum display time**

If loading finishes very quickly, a skeleton that appears for a few milliseconds reads as a flash. Holding it for 200–300 ms smooths that out.

Here's the mistake in my first version. I waited a flat 250 ms *after* data arrived — so on a slow connection, people who had already watched the skeleton for several seconds got another 250 ms tacked on. I noticed one evening while testing on a throttled connection and thinking, "why is the swap so sluggish?" **A minimum display time stretches displays that would be too short; it should never add waiting on top of a long one.** Now I record when the skeleton first appeared and wait only for whatever is left.

```tsx
import { useEffect, useRef, useState } from 'react';

// Remember when the skeleton appeared; wait only for the remaining minimum time
export function useMinSkeletonTime(isLoading: boolean, minMs = 250) {
  const startedAt = useRef<number | null>(null);
  const [showSkeleton, setShowSkeleton] = useState(isLoading);

  useEffect(() => {
    if (isLoading) {
      if (startedAt.current === null) startedAt.current = Date.now();
      setShowSkeleton(true);
      return;
    }
    // If we never entered a loading state (e.g. cache hit), don't wait at all
    const elapsed =
      startedAt.current === null ? minMs : Date.now() - startedAt.current;
    const id = setTimeout(() => {
      startedAt.current = null;
      setShowSkeleton(false);
    }, Math.max(0, minMs - elapsed));
    return () => clearTimeout(id);
  }, [isLoading, minMs]);

  return showSkeleton;
}
```

Usage:

```tsx
const { data, isLoading } = useProfile();
const showSkeleton = useMinSkeletonTime(isLoading);

return showSkeleton || !data ? <ProfileSkeleton /> : <Profile data={data} />;
```

What to expect: a fetch that finishes in 80 ms keeps the skeleton up until 250 ms; a fetch that takes three seconds swaps at exactly three seconds. If nothing extra is added in the slow case, the hook is doing its job.

**2. Leave room for one fade-in**

A fade of about 150 ms on the incoming content softens the seam. Reanimated's layout animations make it a one-liner:

```tsx
import Animated, { FadeIn } from 'react-native-reanimated';

// Put this only on the real content's wrapper (not on the skeleton)
<Animated.View entering={FadeIn.duration(150)}>
  <Profile data={data} />
</Animated.View>
```

When I also gave the skeleton an exit animation, the two would overlap for a split second. These days only the incoming side animates.

## Three common misconceptions

**"A skeleton makes loading faster."** Only the perception changes; the fetch takes exactly as long. If people still call the screen slow after you add a skeleton, the place to look is caching and the number of requests. Presentation can only hide so much.

**"A skeleton needs a shimmer."** Motion is optional. On screens that settle in under a second, and for people with reduced motion on, static blocks feel calmer. I decide per screen, based on how long it actually waits.

**"Reanimated follows Reduce Motion automatically, so there's nothing to do."** The default `ReduceMotion.System` does disable the animation, but where the highlight ends up — and how a CSS animation looks in that state — is still yours to decide. Open the app once on a device with the setting on and look with your own eyes; that's the most reliable check I know.

## Pitfalls I keep pointing out in reviews

- **Forgetting the image area.** Text gets placeholders, the image doesn't, and when the image finally lands, everything jolts. Fix `width` and `height` on the image's parent and show a skeleton at that exact size.
- **Cutting shimmer count to fix jank.** The weight almost always comes from the number of clocks, not the number of blocks. One clock means you don't have to cut anything.
- **Painting skeletons in brand colours.** A pale brand tint feels friendly but blurs the line with real content. Neutral grey (around `#2a2a2a` in dark mode) reads better.
- **Showing a skeleton when data is cached.** On repeat visits there's no need to hide what you already have. Show the cached data and refresh in the background; the wait disappears entirely.

## The next thing you'll hit — a skeleton that never leaves

The problem that shows up soon after adding skeletons is "the request failed, but the skeleton is still there." The more polished your loading state, the harder it is for people to tell that something has actually stopped. I now ship skeletons together with a small hook that gives up after a set time and switches to an error state.

```tsx
import { useEffect, useState } from 'react';

// Returns true once isLoading has stayed true for longer than limitMs
export function useLoadTimeout(isLoading: boolean, limitMs = 10000) {
  const [timedOut, setTimedOut] = useState(false);
  useEffect(() => {
    if (!isLoading) {
      setTimedOut(false);
      return;
    }
    const id = setTimeout(() => setTimedOut(true), limitMs);
    return () => clearTimeout(id);
  }, [isLoading, limitMs]);
  return timedOut;
}
```

When `timedOut` turns true, replace the skeleton with a "Couldn't load" message and a retry button. Ten seconds is my own rule of thumb; tune it to how heavy your data is.

The other confusing case is a list where you can't tell "still loading" from "genuinely empty." How I track that down is in [When a list is empty and no error shows, open Rork's Logs panel before asking for a fix](/en/articles/rork-basics/rork-list-empty-no-error-ask-for-logs-before-fix-request). For audio, where the wait is the few seconds before playback starts, I apply the same idea in a different shape in [Catching the Few Seconds Before Streaming Audio Starts: A Loading State and a Timeout](/en/articles/rork-dev/expo-audio-streaming-start-delay-loading-state-timeout-fallback). And if you want to tune first-touch feel as a whole, loading states included, [The Three Implementation Details That Decide First-Touch Feel in Rork Apps](/en/articles/rork-dev/rork-first-touch-feel-ui-implementation) is a good companion.

## What I'd try next

You don't need to rebuild every screen. Wrap just the **home screen right after launch** in `ShimmerProvider`, swap in a skeleton, and then ask your testers again how those first few seconds feel. If the answer changes, it's worth extending to your lists. If it doesn't, check whether the skeleton's dimensions actually match the real content — that's usually the quickest win.

Those few seconds of loading may be the least noticed part of an app. Even so, I've come to believe that not making people anxious there is a large part of whether they stay long enough to see the rest.
