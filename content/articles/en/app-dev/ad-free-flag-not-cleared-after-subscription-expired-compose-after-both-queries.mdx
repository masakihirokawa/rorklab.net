I was writing out a decision flow line by line one night. One of my wallpaper apps, which I run as an indie developer, removes ads after a purchase. What I had never done, I realized, was trace what happens to that "ads removed" state after the subscription expires.

When I traced it, I stopped. The branch that brings ads back was not written anywhere.

What I had was a lapsed subscription with the ads still off. An ad shown to a paying user gets noticed fast and turns into a support message. The opposite accident, ads that stay off for someone who no longer pays, bothers nobody, so nobody reports it. It simply continues. I found it on the Android side, and it became the first item on the checklist I wrote before carrying the same logic over to iOS.

What I want to say first is that the fix was not about how to use a billing SDK. It was about the direction of the check and the way it waits. What follows is a write-up of that idea, rebuilt as code I could run, and then run.

## One sentence that describes the bug: the direction was reversed

Put into words, the broken check read: "if the flag is not ad-free right now, set it to false." What it should have said was: "if no purchase is confirmed, set it to false." The subject was the flag's own current value instead of a confirmed fact.

I will not paste the original code. Here is the idea, reconstructed in TypeScript.

```ts
// adfree.ts — composing the ad-free flag from two purchase queries
export type Source = "subscription" | "oneTime"; // subscription / one-time purchase

export type QueryResult =
  | { ok: true; active: boolean }
  | { ok: false; reason: string };

export type Results = Record<Source, QueryResult>;

// A reconstruction of the broken direction (the idea, not a quote of the real code)
export function applyBuggy(prev: boolean, r: Results): boolean {
  const purchased =
    (r.subscription.ok && r.subscription.active) ||
    (r.oneTime.ok && r.oneTime.active);
  if (purchased) return true;
  if (!prev) return false; // "if not ad-free right now, set false": the direction is backwards
  return prev;             // even after expiry, the previous true stays
}
```

This code works correctly up to the moment a purchase is confirmed, which is why checking right after a purchase reveals nothing. It breaks only once, after the subscription lapses. When the query answers "none" and `prev` is still true, it keeps returning true.

Tests on the working side never find this kind of bug. "Buy it and the ads disappear" stays green no matter how often you repeat it. **Test the direction that removes ads and the direction that brings them back separately.** I put that at the top of my checklist.

## Wait for both sources, then decide only from confirmed facts

There was not one purchase query but two, for example a subscription and a one-time purchase. If you set false the moment one source says "none", ads flash on screen when the other source is about to say "active".

I rewrote the decision as three rules.

<table>
<thead>
<tr><th>Outcome of the two queries</th><th>Value to set</th><th>Why</th></tr>
</thead>
<tbody>
<tr><td>At least one confirmed "active"</td><td>true</td><td>One piece of proof is enough, even if the other call failed</td></tr>
<tr><td>Both confirmed "inactive"</td><td>false</td><td>You may only clear the flag after hearing "inactive" from every source</td></tr>
<tr><td>A failure and no proof of active</td><td>keep the previous value</td><td>Do not manufacture an answer when you cannot decide</td></tr>
</tbody>
</table>

Here are those rules as a function.

```ts
// Fixed: decide only from confirmed facts; keep the previous value when undecidable
export function composeAdFree(prev: boolean, r: Results): boolean {
  const list = [r.subscription, r.oneTime];
  // One confirmed "active" is enough, even if the other source failed
  if (list.some((x) => x.ok && x.active)) return true;
  // false only when every source confirmed "inactive"
  if (list.every((x) => x.ok && !x.active)) return false;
  // A failure and no proof of active: undecidable, so keep the previous value
  return prev;
}
```

Why write it this way? The key is giving `QueryResult` a third state, "failed". `active: false` means "I asked and it was inactive". `ok: false` means "I could not ask". If both collapse into one false, a dropped connection becomes a change in billing state.

## A controller that stale responses cannot overwrite

The function alone was not enough. In a real app the check runs every time the app returns to the foreground and right after a purchase. When checks overlap, an older one can return late and overwrite a newer result.

First I reproduced the form that applies each source as it arrives.

```ts
// naive.ts — applying each source as it arrives (for reproduction)
import type { QueryResult } from "./adfree.ts";
export function makeNaive(initial: boolean, log: (s: string) => void) {
  let state = initial;
  return (r: QueryResult) => {
    const next = r.ok ? r.active : state; // decides from the one result that just arrived
    if (next !== state) { state = next; log(`naive -> ${next}`); }
  };
}
```

Giving it a subscription "inactive" first and a one-time "active" afterwards produced `naive -> false / naive -> true`. Ads come back, then vanish again: a brief flicker for a paying user.

The fixed version gives the controller a generation number.

```ts
// Controller with a generation number: waits for both, ignores stale responses
export type Query = () => Promise<QueryResult>;

export class AdFreeController {
  private generation = 0;
  private current: boolean;
  private queries: Record<Source, Query>;
  private onChange: (adFree: boolean) => void;
  constructor(
    queries: Record<Source, Query>,
    initial: boolean,
    onChange: (adFree: boolean) => void = () => {},
  ) {
    this.queries = queries;
    this.current = initial;
    this.onChange = onChange;
  }
  get adFree(): boolean {
    return this.current;
  }
  async refresh(): Promise<boolean> {
    const mine = ++this.generation;
    const wrap = (q: Query): Promise<QueryResult> =>
      q().catch((e: unknown): QueryResult => ({ ok: false, reason: String(e) }));
    const [subscription, oneTime] = await Promise.all([
      wrap(this.queries.subscription),
      wrap(this.queries.oneTime),
    ]);
    if (mine !== this.generation) return this.current; // a newer refresh has started: discard this one
    const next = composeAdFree(this.current, { subscription, oneTime });
    if (next !== this.current) {
      this.current = next;
      this.onChange(next);
    }
    return this.current;
  }
}
```

Inside `refresh()` it does three things: waits for both sources with `Promise.all`, turns a thrown exception into a "failed" value so nothing crashes, and discards its result if a newer refresh has started.

This is what I observed when I delayed and reordered the responses.

The second row is my favorite. The old answer says active and the new answer says inactive. Which one is right is not decided by speed. **A newer answer must never lose to an older one.** A generation number keeps that promise with a single integer.

## A sketch for wiring this into an Expo app

From here on it is a sketch whose types I have not checked and which I have not run on a device. I wrote it assuming an app generated with Rork could connect the same way.

```tsx
// useAdFree.tsx — re-ask both sources whenever the app returns to the foreground (sketch, not run on a device)
import { useEffect, useRef, useState } from "react";
import { AppState } from "react-native";
import AsyncStorage from "@react-native-async-storage/async-storage";
import { AdFreeController, type QueryResult } from "./adfree";

const KEY = "adfree:last";

// Wrap your billing SDK calls here (report failures as ok:false)
async function querySubscription(): Promise<QueryResult> {
  return { ok: false, reason: "not implemented" };
}
async function queryOneTime(): Promise<QueryResult> {
  return { ok: false, reason: "not implemented" };
}

export function useAdFree(): boolean {
  const [adFree, setAdFree] = useState(false);
  const ctl = useRef<AdFreeController | null>(null);

  useEffect(() => {
    let alive = true;
    (async () => {
      const saved = (await AsyncStorage.getItem(KEY)) === "1";
      if (!alive) return;
      setAdFree(saved);
      ctl.current = new AdFreeController(
        { subscription: querySubscription, oneTime: queryOneTime },
        saved,
        (v) => {
          setAdFree(v);
          AsyncStorage.setItem(KEY, v ? "1" : "0").catch(() => {});
        },
      );
      await ctl.current.refresh();
    })();
    const sub = AppState.addEventListener("change", (s) => {
      if (s === "active") ctl.current?.refresh();
    });
    return () => {
      alive = false;
      sub.remove();
    };
  }, []);

  return adFree;
}
```

What does it solve? It stores the last value on the device and uses it as the initial value at launch. When both queries are in, it replaces it. Until then, someone whose last value was true sees no ads, and someone whose last value was false does. The previous value decides how the app looks while it waits.

When the ad layer reads this value is another matter. The order of startup and ad initialization is covered in [Initializing Ads Before Restoring Purchases Flashed an Ad at a Paying User: Startup Ordering in a Rork (Expo) App](/en/articles/rork-dev/rork-expo-cold-start-sdk-orchestration-consent-att-ads-billing-order).

## Four places to trip

**1. Do not give "none" and "could not ask" the same value.** Folding `false`, `undefined`, and an exception into a single false turns a flaky connection straight into a billing-state change. Give failure its own place in the result type.

**2. Write the returning-direction test first.** Alongside "buying removes ads", write "expiry brings ads back" with equal weight. The broken version failed only in case A.

**3. Keep grace periods and holds out of this component.** How to treat a payment grace period or an account hold is a separate design. For the story of cutting access because a cancellation was assumed, see [The User I Cut Off as Cancelled Still Meant to Pay: Payment Grace Periods and Keeping Entitlements](/en/articles/rork-dev/rork-subscription-billing-grace-period-account-hold-recovery). This component handles only the merging of what it asked.

**4. OR a time-limited ad pause on separately.** If a rewarded ad pauses ads for a while, keep that as its own state and combine it with OR at the end. Mixed into the purchase decision, you can no longer tell which reason made it true when it expires.

## What to do first tomorrow

In your own app, find the place where the ad-free value goes back to false when no purchase is confirmed. If you cannot find it, you may be in the state I was in.

If you do find it, check once whether that branch reads a confirmed fact or the flag's own current value. Then replace the six-row table above with your own two sources and fill it in.

**When a question could not be answered, do not invent the answer.** I try to keep to that line even on days with a bad connection, and even on days when I would like the ads back.

What I ran here is the TypeScript component rebuilt from the idea and its automated tests, and nothing more. I have not included device behavior in the original Android app or a check against StoreKit on the iOS side.
