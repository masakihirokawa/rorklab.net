I was refreshing the screenshots for one of my wallpaper apps one evening and dragged a freshly exported PNG into App Store Connect. A red message appeared and the upload stopped. In Figma the image looked perfect, but the file was exactly twice the required size—I had left the export multiplier at "2x" from an earlier job.

The same week, Google Play stopped me for a different reason. I tried to reuse the tall image I had made for the App Store, and it failed the aspect-ratio rule. Neither problem had anything to do with design. It took me a few rounds of this before I noticed the cause was always the same kind of missed check.

So here is what I'd like to say first: **most of the time lost on store screenshots goes to three dull things—dimensions, transparency and export scale.** Below is the setup I actually use: two master frames in Figma, one export pass, and a script that checks every file before it goes anywhere.

## What you'll take away

- Why the same image can't serve both stores, and how to size your master frames
- A table for working out why an upload was rejected
- A Figma structure that survives new languages (Auto Layout plus string variables)
- A script that checks dimensions and alpha right after export

## Decide the sizes first — the two stores look alike but aren't

Size tables go stale the moment you copy them. The numbers below follow each store's official help as of November 2026; please re-check the official pages and the App Store Connect screen on the day you work.

### What App Store Connect accepts

The [App Store Connect screenshot specifications](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications) list accepted sizes per display class. Your master should use the largest class.

<table>
<thead>
<tr><th>Class</th><th>Accepted sizes (portrait, px)</th><th>Use as master?</th></tr>
</thead>
<tbody>
<tr><td>iPhone 6.9-inch</td><td>1320 × 2868 / 1290 × 2796 / 1260 × 2736</td><td>Yes — 1320 × 2868</td></tr>
<tr><td>iPad 13-inch</td><td>2064 × 2752 / 2048 × 2732</td><td>A separate master, only if you support iPad</td></tr>
<tr><td>Smaller iPhone and iPad classes</td><td>See the official table</td><td>Skip them if your UI is the same; they're scaled down from the larger class</td></tr>
</tbody>
</table>

Three other rules matter:

- Up to 10 screenshots per class.
- JPEG, JPG or PNG, with no alpha channel or transparency.
- If the UI doesn't change across devices or languages, one set at the largest class is enough; App Store Connect scales it for smaller devices.

Which class shows as "required" depends on the devices your app supports, and the media manager in App Store Connect is the final word. Trust the required slots on the submission screen over any table, including mine.

### What Google Play accepts

The [Play Console Help page on preview assets](https://support.google.com/googleplay/android-developer/answer/9866151) is generous about dimensions but caps the aspect ratio.

I couldn't find a file-size limit in the phone screenshot section of the page I checked, so I don't hard-code one; I rely on the console's upload warnings.

### Why one image can't serve both stores

This is the point I missed for the longest time. At 1320 × 2868, the long side is about 2.17 times the short side. Google Play allows at most 2×, so **an App Store export cannot be uploaded to Google Play as it is.** The ratio rule sits in the last line of the table, which is probably why it's so easy to skim past.

So I keep two masters:

<table>
<thead>
<tr><th>Master</th><th>Size</th><th>Ratio</th><th>Used for</th></tr>
</thead>
<tbody>
<tr><td>appstore</td><td>1320 × 2868</td><td>about 1:2.17</td><td>App Store (iPhone)</td></tr>
<tr><td>play</td><td>1080 × 1920</td><td>9:16</td><td>Google Play (phone); also meets the promotional bar</td></tr>
</tbody>
</table>

Both masters share the same components—headline, device frame, background. Only the vertical spacing differs, so any design fix happens once, in the component.

## Building the masters in Figma

### Pages and frames

Split pages by purpose:

- Components: headline, device frame, background, badges
- Master: the appstore and play master frames
- Export: output-only frames, one per language and sequence number

Name frames like `appstore_1320x2868_ja_01` or `play_1080x1920_en_03`: store, size, language, sequence. Figma uses the frame name as the file name, which is exactly what the check script reads later.

### Treat device frames as decoration

Device-frame plugins are handy, but screen areas change with each hardware generation. If a thin gap appears above or below your pasted capture, suspect a size mismatch first—it's the quickest tell.

Use real captures from a device or simulator. Apps built with Rork are no different: drop the captured PNG inside the frame. App Review dislikes screenshots that don't reflect the actual app, so real screens are the safer choice over polished mock-ups.

### Design text for the longest language

I put the headline in the top 20–30% of the frame. On a 1320 px master I start around 64–80 px for headlines and 36–44 px for supporting text, then check on a real phone.

English often runs 1.2–1.3× the length of Japanese, and German can exceed 1.5×. Early on I'd polish a Japanese layout, pour in the English, watch the headline spill onto four lines, and rebuild. Now **I paste the longest translation into the master first and size everything for that.**

Put headline text inside Auto Layout so the background band grows with extra lines. Post-translation fixes nearly disappear.

### Switch languages with string variables

Duplicating a page per language and retyping text stopped scaling for me at around three languages. These days I use Figma's **string variables**:

1. In local variables, create a collection called "copy".
2. Add one mode per language (ja, en, de…).
3. Create string variables such as `headline_01` and `sub_01`, and fill in each mode.
4. Select the headline text in the master and bind its content to the variable.
5. On the Export page, set each frame to the right mode.

A translation fix becomes one edit in the variables panel, reflected in every frame. The number of modes is capped by plan, and I haven't confirmed the exact limits this time—please check [Figma's "Modes for variables" help page](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables) for your plan. If you hit the cap, combining modes with duplicated pages works fine.

## Export settings — PNG or JPG, 1x or 2x

There are really only two decisions:

<table>
<thead>
<tr><th>Choice</th><th>When it fits</th><th>Watch out for</th></tr>
</thead>
<tbody>
<tr><td>PNG at 1x</td><td>UI and text must stay crisp (the default)</td><td>A frame without a fill exports with transparency</td></tr>
<tr><td>JPG at 1x</td><td>Photos or artwork carry the image and you want smaller files</td><td>No alpha possible, so no alpha rejections; thin text may get halos</td></tr>
<tr><td>2x or 3x</td><td>Never, here</td><td>Your master already has the required pixel size; any multiplier breaks it</td></tr>
</tbody>
</table>

The rule fits in one line: **PNG at 1x when UI and text lead; JPG at 1x when a photo leads and the type is bold.** My wallpaper screenshots are image-led, so I sometimes use JPG—but the one time thin headline text picked up halos, I went back to PNG.

## Check every file right after export

This is where I won back the most time. You can't see an alpha channel by looking at an image, and a 2× size error is invisible in a thumbnail. So every export goes through this script before upload.

**What it solves**: for every file in the export folder, it checks store-specific dimensions, aspect ratio and alpha in one pass.

```python
#!/usr/bin/env python3
"""Check exported store screenshots before upload.
Usage: python3 check_shots.py export/*.png
The file-name prefix decides the store (appstore_ / play_)."""
import sys
from pathlib import Path
from PIL import Image

APPSTORE_SIZES = {  # (width, height) portrait; landscape is checked swapped
    (1320, 2868), (1290, 2796), (1260, 2736),   # iPhone 6.9-inch
    (2064, 2752), (2048, 2732),                 # iPad 13-inch
}

def check(path: Path) -> list[str]:
    errors = []
    with Image.open(path) as im:
        w, h = im.size
        has_alpha = im.mode in ("RGBA", "LA") or "transparency" in im.info
    if has_alpha:
        errors.append("has alpha channel (fill the background and re-export)")
    name = path.name
    if name.startswith("appstore_"):
        if (w, h) not in APPSTORE_SIZES and (h, w) not in APPSTORE_SIZES:
            errors.append(f"not an accepted App Store size: {w}x{h}")
    elif name.startswith("play_"):
        short, long_ = sorted((w, h))
        if short < 320 or long_ > 3840:
            errors.append(f"outside Google Play dimension range: {w}x{h}")
        if long_ > short * 2:
            errors.append(f"Google Play aspect ratio exceeded (long side > 2x short): {w}x{h}")
    else:
        errors.append("file name does not start with appstore_ / play_")
    return errors

if __name__ == "__main__":
    failed = 0
    for arg in sys.argv[1:]:
        p = Path(arg)
        errs = check(p)
        print(("NG " if errs else "OK ") + p.name + ("" if not errs else " — " + " / ".join(errs)))
        failed += bool(errs)
    sys.exit(1 if failed else 0)
```

If Pillow is missing, run `python3 -m pip install pillow` first. Here's a run on Python 3.10 with Pillow 12.3, with some deliberately broken files mixed in:

```text
$ python3 check_shots.py export/*.png
NG appstore_1320x2868_en_01.png — has alpha channel (fill the background and re-export)
OK appstore_1320x2868_ja_01.png
NG appstore_1320x2868_ja_02.png — not an accepted App Store size: 2640x5736
OK play_1080x1920_ja_01.png
NG play_1320x2868_ja_01.png — Google Play aspect ratio exceeded (long side > 2x short): 1320x2868
```

The second NG is a 2x export; the last is the App Store master reused for Google Play. Both of the mistakes from the opening, side by side.

**Why it's written this way**: the check keys off the file-name prefix because Figma turns frame names into file names, so a naming habit replaces a config file. And any NG makes the script exit with 1, so you can drop it into a shell step before syncing the export folder.

If transparency slipped through, the proper fix is to add a fill to the master and re-export. When I'm in a hurry, this flattens it onto a background colour:

```python
#!/usr/bin/env python3
"""Flatten transparent PNGs onto a solid background.
Usage: python3 fix_alpha.py export/appstore_*.png --bg "#FFFFFF" """
import sys
from PIL import Image
args = sys.argv[1:]
bg = "#FFFFFF"
if "--bg" in args:
    i = args.index("--bg"); bg = args[i + 1]; del args[i:i + 2]
for path in args:
    im = Image.open(path)
    if im.mode in ("RGBA", "LA") or "transparency" in im.info:
        rgba = im.convert("RGBA")
        base = Image.new("RGB", rgba.size, bg)
        base.paste(rgba, mask=rgba.split()[3])
        base.save(path)
        print("fixed", path)
```

```text
$ python3 fix_alpha.py export/appstore_1320x2868_en_01.png
fixed export/appstore_1320x2868_en_01.png
$ python3 check_shots.py export/appstore_1320x2868_en_01.png
OK appstore_1320x2868_en_01.png
```

One caveat: the script judges by image mode, so a PNG that looks opaque but carries an alpha layer still fails. The store checks for the channel too, so I'd rather be strict.

<tr><th>Symptom</th><th>Likely cause</th><th>How to confirm</th><th>Fix</th></tr>
</thead>
<tbody>
<tr><td>App Store Connect rejects the file over its dimensions</td><td>Exported at 2x or 3x</td><td>check_shots.py, or width/height in Finder's info</td><td>Set export back to 1x</td></tr>
<tr><td>Dimensions are right but App Store still rejects it</td><td>An alpha channel remains</td><td>"has alpha channel" from check_shots.py</td><td>Fill the master and re-export; fix_alpha.py if urgent</td></tr>

## Common misconceptions

**"You need a set for every device size."** Today's App Store accepts one set at the largest class if your UI is the same; smaller classes are scaled down, as the official spec page notes. Make extra sets only when the layout really differs.

**"There's one size that works for both stores."** Every iPhone 6.9-inch size has a long side more than twice the short side, which conflicts with Google Play's ratio rule. Two masters is the reliable route.

**"Export at 2x for Retina."** Store sizes are already actual pixels. If your master is built at that size, 1x is correct.
