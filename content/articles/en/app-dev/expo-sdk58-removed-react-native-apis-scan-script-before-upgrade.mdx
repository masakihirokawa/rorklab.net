The last thing I want the night before an upgrade is to bump the version, meet a red screen, and only then start hunting for the cause. Rereading the SDK 58 announcement on expo.dev/changelog, I noticed that a cluster of React Native APIs had been removed. SDK 58 moves React Native from 0.86 to 0.88, so the changes from two React Native releases land at once.

Each change is small. But in an app I have maintained for years as an indie developer, I cannot count from memory where each of these still hides. So I wrote a short script that walks the source and prints the matching lines.

The first version passed my sample, and I believed it worked. Then I added a few screens written in styles I don't normally use, ran it again, and it caught only half of the places that would actually break. This article is the revised version, with those misses fixed.

## The short version

For removed APIs, one script that keeps all the rules in one place misses less than a handful of `grep` commands. But a script has blind spots too, and they come from how code happens to be written. Mine missed four things: multi-line imports, imports with an alias, arrow functions inside props, and a same-named component from a different package.

**Don't search for the name; search for where the name was imported from.** The revised script is rebuilt around that one rule.

"Removed" and "type error" items stop the build or the type check on upgrade day. "Behavior" items don't stop anything; only the result changes, which makes them the hardest to notice. "Deprecated" items still work, so they can wait for a later pass.

## The four things my first version missed

Here is what the first version printed on a sample written in slightly varied styles:

```text
app/home.tsx:1  InteractionManager  → requestIdleCallback に置き換えます
app/home.tsx:11  InteractionManager  → requestIdleCallback に置き換えます
app/home.tsx:14  StatusBar の削除済み props  → 削除された props です。背景色は画面側の View に持たせます
app/store.ts:2  react-native 深い import  → react-native の公開 export へ。急ぐなら tsconfig の customConditions で先送りできます
app/store.ts:7  File.write() が await されていません  → await を付けるか、従来の挙動なら writeSync() を使います

5 件
```

The sample actually holds eight places that would break. One of the five hits (line 14) is the `StatusBar` from `expo-status-bar`, not the React Native one. So it found four of the eight.

All four misses had the same cause: judging by the line, or by the name alone.

<table>
<thead><tr><th>How the code was written</th><th>What the first version did</th><th>What the revision does</th></tr></thead>
<tbody>
<tr><td><code>import {</code>, a line break, then <code>Touchable,</code> on its own line</td><td>It read line by line, so it needed <code>from 'react-native'</code> on the same line</td><td>Reads import braces across the whole file</td></tr>
<tr><td>An alias such as <code>StatusBar as RNStatusBar</code></td><td>It searched for <code>&lt;StatusBar</code> only, so <code>&lt;RNStatusBar</code> slipped through</td><td>Searches for the tag under its imported local name</td></tr>
<tr><td><code>animated</code> after <code>onRequestClose={() =&gt; onClose()}</code></td><td>It took the <code>&gt;</code> in <code>=&gt;</code> as the end of the tag and never read further</td><td>Counts nested <code>{ }</code> and stops at the outer <code>&gt;</code></td></tr>
<tr><td><code>&lt;StatusBar backgroundColor=… /&gt;</code> from <code>expo-status-bar</code></td><td>Reported it as if it were the React Native component</td><td>Only looks at tags imported from <code>react-native</code></td></tr>
</tbody>
</table>

A single small sample only tests your own habits. I tend to keep imports on one line and rarely write multi-line ones, which is probably why the first version never bothered me. These days, when I write an audit script, I treat **adding one sample in a style I never use** as part of the same task, not an extra.

## The audit script (revised)

It depends only on Node; I ran it on Node 22.23. Pass your project root, as in `node sdk58-removed-api-scan.mjs ./my-app`. It exits with 1 if anything "removed" or "behavior" is found, and 0 if only "deprecated" items remain, so CI won't fail on deprecations alone.

```js
// sdk58-removed-api-scan.mjs — Expo SDK 58 で削除・変更された API の使用箇所を洗い出します
// 使い方: node sdk58-removed-api-scan.mjs <プロジェクトのルート>
// 終了コード: 削除済み API が 1 件でもあれば 1（非推奨・設定の警告だけなら 0）
import { readdirSync, readFileSync, statSync, existsSync } from 'node:fs';
import { join, extname, relative } from 'node:path';

const root = process.argv[2] ?? '.';
const EXT = ['.ts', '.tsx', '.js', '.jsx', '.mjs', '.cjs'];
const SKIP = new Set(['node_modules', 'ios', 'android', 'dist', 'build', 'web-build']);

const walk = (d) =>
  readdirSync(d).flatMap((n) => {
    if (SKIP.has(n) || n.startsWith('.')) return [];
    const p = join(d, n);
    return statSync(p).isDirectory() ? walk(p) : EXT.includes(extname(p)) ? [p] : [];
  });

const lineOf = (text, index) => text.slice(0, index).split('\n').length;

// react-native から import している名前（複数行の import・as の別名にも対応）
const rnImports = (text) => {
  const names = new Map(); // ローカル名 → 元の名前
  for (const m of text.matchAll(/import\s*(?:type\s*)?\{([^}]*)\}\s*from\s*['"]react-native['"]/g)) {
    for (const part of m[1].split(',')) {
      const [orig, local] = part.replace(/\btype\s+/, '').trim().split(/\s+as\s+/);
      if (orig) names.set((local ?? orig).trim(), { orig: orig.trim(), line: lineOf(text, m.index) });
    }
  }
  return names;
};

// 開始タグを、{ } の入れ子を数えながら > まで読みます（props の中の => で切れないように）
const openingTags = function* (text, tag) {
  const re = new RegExp(`<${tag}(?=[\\s/>])`, 'g');
  for (const m of text.matchAll(re)) {
    let depth = 0, i = m.index + m[0].length;
    for (; i < text.length; i++) {
      const c = text[i];
      if (c === '{') depth++;
      else if (c === '}') depth--;
      else if (c === '>' && depth === 0) break;
    }
    yield { index: m.index, body: text.slice(m.index, i + 1) };
  }
};

// 行単位の規則: [重さ, 名前, 正規表現, 直し方]
const LINE_RULES = [
  ['削除', 'InteractionManager', /\bInteractionManager\b/, 'requestIdleCallback に置き換えます'],
  ['削除', 'react-native 深い import', /['"]react-native\/Libraries\//, '公開 export へ。急ぐなら tsconfig の customConditions で先送り（React Native 0.89 のあとに外れる予定）'],
  ['削除', 'NativeMethods 型', /\bNativeMethods\b/, 'ViewInstance などの instance 型へ置き換えます'],
  ['削除', 'expo-sqlite libSQL', /\bsyncLibSQL\b|\blibSQLOptions\b/, 'libSQL は削除されています。同期の仕組みを別に用意します'],
];

// react-native から import したタグだけを見る規則: [重さ, タグ名, 属性の正規表現, 直し方]
const TAG_RULES = [
  ['削除', 'Modal', /\sanimated(?=\s*=|\s|\/?>)/, 'animationType に置き換えます'],
  ['削除', 'StatusBar', /\s(backgroundColor|translucent|networkActivityIndicatorVisible)(?=\s*=|\s|\/?>)/, '削除された props です。背景色は画面側の View に持たせます'],
];

const hits = [];
const add = (sev, rel, line, name, fix) => hits.push({ sev, rel, line, name, fix });

for (const p of walk(root)) {
  const text = readFileSync(p, 'utf8');
  const rel = relative(root, p);
  const lines = text.split('\n');
  const rn = rnImports(text);

  lines.forEach((l, i) => {
    if (/^\s*(\/\/|\*|\/\*)/.test(l)) return; // コメント行は数えません
    for (const [sev, name, re, fix] of LINE_RULES) if (re.test(l)) add(sev, rel, i + 1, name, fix);
  });

  for (const [local, { orig, line }] of rn) {
    if (orig === 'Touchable') add('削除', rel, line, 'Touchable（ルート export）', 'Pressable などへ置き換えます');
    if (orig === 'ImageBackground') add('非推奨', rel, line, 'ImageBackground', 'View と絶対配置の Image へ。今は動きます');
    for (const [sev, tag, attr, fix] of TAG_RULES) {
      if (orig !== tag) continue;
      for (const t of openingTags(text, local)) if (attr.test(t.body)) add(sev, rel, lineOf(text, t.index), `${tag} の削除済み props`, fix);
    }
  }

  // expo-file-system の File.write() は SDK 58 から非同期です
  if (/from\s*['"]expo-file-system(\/next)?['"]/.test(text)) {
    lines.forEach((l, i) => {
      const prev = i > 0 ? lines[i - 1] : '';
      if (/\.write\(/.test(l) && !/\b(await|return)\s/.test(l) && !/\.then\(/.test(l) && !/\bawait\s*$/.test(prev)) {
        add('挙動', rel, i + 1, 'File.write() が await されていません', 'await を付けるか、従来の挙動なら writeSync() を使います');
      }
    });
  }
}

// 設定ファイル: useLibSQL は SDK 58 で効かなくなりました（エラーにはなりません）
for (const f of ['app.json', 'app.config.js', 'app.config.ts']) {
  const p = join(root, f);
  if (existsSync(p) && /useLibSQL/.test(readFileSync(p, 'utf8'))) add('非推奨', f, 1, 'expo-sqlite の useLibSQL', '効果がなくなりました。設定から外します');
}

hits.sort((a, b) => a.rel.localeCompare(b.rel) || a.line - b.line);
for (const h of hits) console.log(`[${h.sev}] ${h.rel}:${h.line}  ${h.name}  → ${h.fix}`);
const blocking = hits.filter((h) => h.sev !== '非推奨').length;
console.log(hits.length ? `\n${hits.length} 件（止まるもの ${blocking} 件）` : '該当なし');
process.exitCode = blocking ? 1 : 0;
```

The hint strings are in Japanese because I wrote the script for my own use; translate them if you share it with a team. The rules sit in three layers: things a name alone identifies (`LINE_RULES`), things that depend on whether they came from `react-native` (`rnImports` and `TAG_RULES`), and the config files. `Modal` and `StatusBar` are checked as whole tags so that a `<RNStatusBar` spread over three lines before its `/>` is still caught. When a new item appears, you add one line to an array.

```text
[削除] app/home.tsx:19  Modal の削除済み props  → animationType に置き換えます

```

`[削除]` means removed, `[挙動]` behavior, `[非推奨]` deprecated, and the last line reads "10 hits (8 that block)". The exit code was 1. The `expo-status-bar` `StatusBar` (line 14), the `InteractionManager` inside a comment (line 9), and the `File.write()` that already has `await` (line 6) were all left out. The empty project printed "該当なし" (no matches) and exited with 0.

Keep in mind that this is the result on a small sample I prepared, not a count from a real app. How many hits your own app produces is something only a run on your machine can tell you.

## grep, the type checker, or the script

All three can "find removed APIs", but each is good at different things.

<table>
<thead><tr><th>Tool</th><th>Good at</th><th>Weak at</th></tr></thead>
<tbody>
<tr><td><code>grep -rn InteractionManager src</code></td><td>Unique names (<code>InteractionManager</code>, <code>syncLibSQL</code>) in seconds</td><td>Multi-line tags, telling import sources apart, aliases</td></tr>
<tr><td><code>npx tsc --noEmit</code> (after upgrading)</td><td>Type errors from deep imports, <code>NativeMethods</code>, removed props</td><td>Unusable before the upgrade; silent on plain JS files and on a missing <code>await</code></td></tr>
<tr><td>The script in this article (before upgrading)</td><td>A list before you upgrade, regression checks in CI, separating deprecations</td><td>Dynamic imports, names built from strings, native-side changes</td></tr>
</tbody>
</table>

The choice fits in one sentence: **count with the script before the upgrade, confirm with the type checker after it, and reach for grep when there is only one name to find.** I do it in two passes: the script before, `tsc --noEmit` after, to catch what the script let through.

## Three common misreadings

**First: "customConditions only needs the legacy name."** The announcement says to set `"customConditions": ["react-native", "react-native-legacy-deep-imports"]` and to keep `"react-native"`, which `expo/tsconfig.base` already sets. The point is not to drop it when you override the array. The opt-out is set to be removed after React Native 0.89, and the notes ask you to migrate during the SDK 58 cycle.

**Second: "The `StatusBar` from `expo-status-bar` lost the same props."** The removal is on React Native's `StatusBar`. `expo-status-bar` is a separate component, so I left it out of the script. For how its props behave, I'd check the `expo-status-bar` documentation rather than take my word for it.

**Third: "A leftover `useLibSQL` will break the build."** The notes call the `useLibSQL` config property deprecated and say it no longer has any effect. What breaks is `syncLibSQL()` and `libSQLOptions` in code; a forgotten `useLibSQL` in the config still builds. That difference is why the script reports "deprecated" and "removed" separately.

## Reading the output, and the order I fix things

1. Type errors first (deep imports, `NativeMethods`). `customConditions` can defer them, but I treat that as a one-time loan
2. Behavior changes next (`File.write()` becoming async). Forget the `await` and the next step starts before the write finishes. Nothing looks wrong on screen; it shows up later as a file that reads back empty
3. Visual changes after that (`StatusBar`, `Modal`), since checking them on a real device doubles as the visual test
4. Deprecations (`ImageBackground`, `useLibSQL`) I leave alone on upgrade day. A smaller diff is easier to roll back if something goes wrong

## Changes the source cannot reveal

Three things this script cannot see, written down so they are not forgotten:

- **Node.js**: Expo tooling needs 22.13+ on the 22 line, 24.3+ on the 24 line, or 26 and later; the odd-numbered 23 and 25 are unsupported. Check with `node -v`
- **R8**: Release builds now default to `android.enableMinifyInReleaseBuilds=true`. Libraries that rely on reflection may need ProGuard keep rules. To opt out, set it to `false` through `expo-build-properties`. The numbers worth measuring before the switch are in [Four Numbers to Record Before R8 Becomes the Default](/articles/rork-dev/expo-sdk58-r8-default-android-baseline-measurement)
- **iOS scene life cycle**: The iOS 27 SDK requires the UIScene life cycle, so prebuild generates `SceneDelegate.swift` and a `UIApplicationSceneManifest` entry in `Info.plist`. If you manage the `ios` directory by hand or override app delegate methods directly, follow the official migration guide (expo.fyi/ios-scene-lifecycle)

## What tends to come next

Once the list is empty, what I watch for is the fixes coming undone. A dependency update or a screen copied from an older project can bring a removed `InteractionManager` right back. That is why the script returns an exit code: one line in CI stops the regression.

```yaml
# one line to add to the steps in .github/workflows/check.yml
- run: node scripts/sdk58-removed-api-scan.mjs .
```

The other thing is the rest of SDK 58. The environment-variable rules are in [Expo SDK 58 No Longer Loads .env.staging. A 70-Line Script to Audit Your .env Files](/articles/app-dev/expo-sdk58-env-staging-file-not-loaded-local-wins-audit-script), the build trouble for projects using Stripe is in [Expo SDK 58 With Stripe: pod install Stops, and Whether to Turn Off Precompiled Modules or Wait](/articles/app-dev/expo-sdk58-stripe-pod-install-fails-precompiled-modules-turn-off-or-wait), and how many dependency recommendations move after one bump is counted in [I counted how many versions expo install starts recommending after one patch bump](/articles/rork-dev/expo-install-bundled-native-modules-patch-drift-audit). A version that sorts everything into removed, behavior, and deprecated, and lays out the upgrade-day steps, is in [Before Moving to Expo SDK 58, List What Disappears in Your Own Code](/articles/rork-basics/expo-sdk58-removed-api-audit-script-before-upgrade).

Start by running the script once at your project root and writing down the number of items that block. That one number makes a good first draft of your upgrade-day plan, or at least it still does for me.
