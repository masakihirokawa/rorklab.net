The widget sits happily in the iOS simulator. Then you run `npx expo run:android`, and Kotlin errors fill the terminal. All you did was bump one dependency, and a build that passed yesterday now stops — I suspect that is the morning that brought most people to this page.

The short answer first: **this bug is fixed in expo-widgets 58.0.20.** Only three versions are affected — 58.0.17, 58.0.18 and 58.0.19 — and the latest as of November 18, 2026 is 58.0.29. If you are dealing with it today, upgrading is usually all it takes.

When people say "I upgraded and it still fails," the cause is almost always something left behind on their machine rather than the package itself. So this page walks through how to recognize the broken versions, how to narrow things down when an upgrade doesn't help, and how to undo the workarounds (pinning, autolinking exclusion) that an earlier version of this article suggested.

## If you see these lines, suspect this issue

If Kotlin compilation prints lines like these from `CustomNotificationBuilder.kt` or `CustomNotificationRenderer.kt`, you are almost certainly looking at this bug:

```text
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationBuilder.kt:17:18 Unresolved reference 'jakex7'.
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationBuilder.kt:30:12 Unresolved reference 'PeekNotificationViews'.
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationBuilder.kt:36:8 Unresolved reference 'setPeekContent'.
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationRenderer.kt:11:18 Unresolved reference 'jakex7'.
```

That is an excerpt of the output in expo/expo issue #51653. The reporter reproduced it with a fresh `create-expo-app` project plus `npx expo install expo-widgets` (which installed 58.0.18 at the time) and nothing else. No amount of reading your own code will explain it. **A specific package version refers to classes that don't exist in its Android dependencies.**

The cause was a naming mismatch. When 58.0.17 added custom notifications on Android, the new code imported `io.github.jakex7.peek`, but `build.gradle` pulls in `io.github.expo.peek:peek-emittables`. The imported classes simply aren't on the classpath, so compilation stops. iOS doesn't touch this code, which is why testing on iOS alone hides it.

The 58.0.20 entry in CHANGELOG.md lists a second fix next to this one: Android apps using expo-widgets crashing at launch with `constructor cannot be null`. If your build passed but the app died right after opening on one of these versions, the same upgrade covers you.

I also checked what the SDK itself recommends. In `expo@58.0.26`, bundledNativeModules.json lists expo-widgets as `~58.0.29`, so installing the SDK's recommended version keeps you out of the broken range.

## The fix: move to the recommended version

Rather than typing a range by hand, let the Expo CLI pick the version that matches your SDK:

```bash
npx expo install expo-widgets
npx expo install --check        # also flags other packages that drifted from the SDK's recommendation
```

Then confirm what actually landed in `node_modules`. That number — not what `package.json` says — is the one that matters:

```bash
node -p "require('expo-widgets/package.json').version"
# 58.0.20 or later (for example 58.0.29) means you have the fix
```

If you generate and keep a native `android` folder, regenerate it before building:

```bash
npx expo prebuild -p android --clean
cd android && ./gradlew :expo-widgets:compileDebugKotlin
```

`--clean` deletes the existing `android` folder before regenerating it, so back up any hand-edited native files first. If you only build on EAS and have no local `android` folder, you can skip this step.

## Undoing the old workarounds

When I first wrote this on October 20, I looked at the issue page, wrote that it was "still open," and offered pinning to 58.0.16 and excluding Android as the two ways out. In fact the issue had been closed the day it was filed, and 58.0.20 shipped that same day. I never compared the issue status with what was inside the published package — that was my miss, and the thought of readers still carrying those workarounds sat heavily with me.

The line I drew from it is simple: **judge by what is inside the version in node_modules, not by whether an issue is open or closed.** Since then, whenever I write about a dependency bug, I read both the changelog and the shipped files before I write a word.

To undo the workarounds:

1. If `expo.autolinking.android.exclude` in package.json lists `expo-widgets`, remove it (drop the whole `autolinking` block if the list becomes empty).
2. Run `npx expo install expo-widgets` to replace the `"58.0.16"` pin with the recommended range (such as `~58.0.29`).
3. Run `npx expo prebuild -p android --clean` to regenerate the Android project.
4. If you wrapped widget calls in `Platform.OS` checks to keep Android away from them, decide again whether those branches should stay.

While the exclusion was in place, Android builds didn't contain the widget at all. After removing it, it's worth confirming once on a real Android device that you can add the widget to the home screen.

In one sentence: **if you want the widget on Android, upgrade; if you don't, exclude it; and treat a pin as a temporary shelter with an end date.** In my wallpaper app the widget started as an iOS-side extra, but I've come to see exclusion as a product decision ("no widget on Android"), not as a tool for dodging bugs.

## Three common misreadings

- **"The issue is closed, so my app is fixed."** The fix landed upstream. If your lockfile still points at 58.0.17–19, nothing changes for you. Check the version in `node_modules`.
- **"58.0.16 is the safe version, so pinning is the careful choice."** It is unaffected by this bug, but a pin also blocks the Android fixes that arrived between 58.0.20 and 58.0.29 — the launch crash, the WorkManager upgrade, the move to Peek 0.3.3.
- **"Exclusion is a side-effect-free workaround."** Exclusion removes expo-widgets from the Android build entirely. The error goes away because the widget goes away.

## A script that checks your project in seconds

Comparing `package.json` and `node_modules` by hand gets old, so here is a small checker. Compared with the earlier version, it now narrows the broken range to 58.0.17–58.0.19 and also tells you when a pin or exclusion has been left behind. It needs only Node and makes no network calls.

```js
// check-expo-widgets-android.mjs
// Usage: node check-expo-widgets-android.mjs [project path]
import { readFileSync, existsSync } from "node:fs";
import { join, resolve } from "node:path";

const root = resolve(process.argv[2] ?? ".");
const readJson = (p) => JSON.parse(readFileSync(p, "utf8"));

const pkgPath = join(root, "package.json");
if (!existsSync(pkgPath)) {
  console.error(`package.json not found: ${pkgPath}`);
  process.exit(2);
}
const pkg = readJson(pkgPath);
const declared = { ...pkg.dependencies, ...pkg.devDependencies }["expo-widgets"];
if (!declared) {
  console.log("expo-widgets is not a dependency. This issue does not apply.");
  process.exit(0);
}

const installedPath = join(root, "node_modules", "expo-widgets", "package.json");
if (!existsSync(installedPath)) {
  console.error("expo-widgets is not in node_modules. Run npm install first.");
  process.exit(2);
}
const installed = readJson(installedPath).version;
const [major, minor, patch] = installed.split(/[.-]/).map(Number);

const excluded = (pkg.expo?.autolinking?.android?.exclude ?? []).includes("expo-widgets");
const pinned = /^\d+\.\d+\.\d+$/.test(declared); // no ^ or ~ means pinned
const broken = major === 58 && minor === 0 && patch >= 17 && patch <= 19;
const old = major === 58 && minor === 0 && patch <= 16;

console.log(`Declared: ${declared} (${pinned ? "pinned" : "range"})`);
console.log(`Installed: ${installed}`);
console.log(`Excluded from Android autolinking: ${excluded ? "yes" : "no"}`);

const notes = [];
if (broken) notes.push("Action needed: 58.0.17-58.0.19 break the Android build. Run npx expo install expo-widgets to get 58.0.20 or later");
if (excluded) notes.push("Check: the exclusion is still there. Remove it if you want widgets on Android");
if (old && pinned) notes.push("Check: pinned to 58.0.16 or earlier. If that was meant to be temporary, return to the recommended range");

if (notes.length === 0) {
  console.log("Result: OK (not affected by this issue)");
  process.exit(0);
}
notes.forEach((n) => console.log(`Result: ${n}`));
process.exit(broken ? 1 : 3);
```

Exit codes: 0 when everything is fine, 1 for the broken range, 2 when prerequisites are missing, and 3 when a leftover workaround is found. Put it at the start of CI, and if a dependency bot or a mixed-up lockfile brings a broken version back, you'll know within seconds instead of after a long Gradle run.

To be clear about what I verified: I ran the script against four mock projects (just a `package.json` and `node_modules/expo-widgets/package.json`) — 58.0.18, 58.0.20, a 58.0.16 pin, and 58.0.29 with the exclusion — and got exit codes 1, 0, 3 and 3. I have not run a full Gradle build of a real app with it.

## The next wall: Android widgets don't change on a schedule

Once the build passes and the widget appears, the next thing most people hit is that it never changes over time. That is not a bug; as of November 18, 2026 it's how expo-widgets behaves.

- `updateTimeline()` is marked `@platform ios` in the type definitions and does nothing on Android.
- Even in 58.0.29, the config plugin that writes the Android widget definition emits `android:updatePeriodMillis="0"`.
- Issue #51633, which reports this, is still open. Expo's automated triage classified it as a feature request (current behavior is expected), and PR #51697, which documents it, was still unmerged on November 18.

So on Android, the widget only changes when you call `updateSnapshot()` while the app is running. A wallpaper widget that flips at midnight every day can't be built on expo-widgets alone today. I wrote up a design that works around it in [A Widget That Updates on Time in iOS Stays on "Initial" in Android](/en/articles/rork-dev/expo-widgets-android-update-timeline-no-op-widget-stays-initial).

Expo patches also arrive at a quick pace. For a routine way to see which version your app really ships, see [Nine Expo patches shipped in thirty days. Which one is your app actually running?](/en/articles/rork-basics/expo-patch-cadence-which-version-your-app-actually-has), and for how much `expo install` recommendations move per patch, see [I counted how many versions expo install starts recommending after one patch bump](/en/articles/rork-dev/expo-install-bundled-native-modules-patch-drift-audit). If your Android failure looks cache-related, [When Only EAS Build Fails with "No matching variant", Check Your Local android/build First](/en/articles/app-dev/eas-build-no-matching-variant-stale-windows-autolinking-cache) may help too.

## What to do today

Run `node -p "require('expo-widgets/package.json').version"` once at the root of your project and see whether it prints 58.0.20 or later. If it shows 58.0.17 to 58.0.19, upgrade; if it's anything else and a pin or exclusion is still there, remove it. That's the whole decision. Reading inside the package before writing about it is a line I intend to keep holding.
