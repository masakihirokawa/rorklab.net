I was building a new wallpaper app with EAS for the first time. The terminal sat at "Compressing project files" for a long while, then printed a single red line.

`Project archive is too big. Maximum allowed size is 2.0 GB.`

The project had a few hundred source files. A 2 GB figure made no sense to me, and my stomach sank a little.

Here is the point I'd like to start with: this failure is rarely about your code being large. It happens because something you never meant to send is riding along. The cause usually sits at the edge of the project, not in `src/`.

Three conclusions up front:

- The limits apply to the compressed archive. Over 150 MiB you get a warning; over 2 GiB the build fails before upload.
- The most reliable way to see what goes in is the official `eas build:inspect --stage archive`. When you want a quick look without logging in, the script further down sorts the upload by size.
- `.easignore` does not add to `.gitignore`. It replaces every `.gitignore` in the repository, and it is read only from the repository root.

Everything below was checked in November 2026 against Expo's documentation (the .easignore page and the expo.fyi note on how projects are uploaded) and the eas-cli source code.

## Two thresholds, measured after compression

EAS CLI copies your project into a temporary directory, packs it into a gzipped tar, and uploads that file. In the eas-cli source, the size of that tarball decides what happens.

<table>
<tr><th>Compressed archive</th><th>What happens</th><th>Message (gist)</th></tr>
<tr><td>Up to 150 MiB</td><td>Nothing special</td><td>"Compressed project files (time and size)"</td></tr>
<tr><td>Over 150 MiB</td><td>A warning; the build continues</td><td>"Your project archive is …. You can reduce its size … in .easignore file."</td></tr>
<tr><td>Over 2 GiB</td><td>Fails before uploading</td><td>"Project archive is too big. Maximum allowed size is …"</td></tr>
</table>

The word that's easy to miss is *compressed*. Source code and JSON shrink well under gzip. PNG, JPEG and video are already compressed and barely shrink at all. **In an image-heavy project, the raw size of your images is roughly the size of your archive.** Keeping that in mind saves a lot of guessing.

The warning is the moment you can still turn back. I read mine as "the network is just slow", and that was the wrong turn.

`node_modules` never goes into the archive, whatever your settings, and the `.git` directory isn't sent by default either. So you can rule out "my dependencies are heavy" early.

## The official check: dump the archive with eas build:inspect

Expo documents a command that copies exactly what would be uploaded into a local directory. It doesn't start a build.

```bash
# Requires eas login. The output directory must not exist yet
eas build:inspect --platform android --stage archive --output ./eas-archive

# What is heavy? (KB, largest first)
du -ak ./eas-archive | sort -rn | head -15

# Close to what will actually be sent (bytes after gzip)
tar -czf - -C ./eas-archive . | wc -c
```

Three things I've learned to watch for:

- It stops if the output directory already exists. Delete it first, or add `--force`.
- If `cli.requireCommit` is `true` in `eas.json`, commit first. The command won't prompt you to.
- If you create `./eas-archive` inside the project, it gets uploaded on your next build. Delete it afterwards, or list it in `.easignore`.

This is the ground truth. Because it needs a login and a full copy, though, I reach for the script below first when I'm only trying to find the suspect.

## A no-login script that sorts the upload by size

The first version of this article had a script that fed one ignore file to `git ls-files`. When I re-tested it on a small repository, it disagreed with the real upload in two ways, so I'm correcting it here.

- Without `.easignore`, EAS also applies `.gitignore` files in subdirectories. Reading only the root file counted things EAS would have excluded.
- Files excluded by `.easignore` still showed up if git was tracking them. EAS removes them regardless of whether they're tracked.

Here is the fixed version. Run it from inside your project with `sh eas-upload-size.sh`.

```bash
#!/bin/sh
# Count what EAS would upload, locally, before you send anything
set -eu
cd "$(git rev-parse --show-toplevel)"   # .easignore is read from the repo root

if [ -f .easignore ]; then
  echo "Active rules: .easignore (no .gitignore is read)"
  set -- --exclude-from=.easignore
else
  echo "Active rules: .gitignore in every directory"
  set -- --exclude-per-directory=.gitignore
fi

LIST=$(mktemp); IGN=$(mktemp)
# List tracked (-c) and untracked (-o) files, then subtract tracked files the rules match (-c -i)
git ls-files -c -o "$@" | grep -v -e '^node_modules/' -e '/node_modules/' | sort -u > "$LIST"
git ls-files -c -i "$@" | sort -u > "$IGN"
comm -23 "$LIST" "$IGN" > "$LIST.final"

echo "--- largest first (KB) ---"
tr '\n' '\0' < "$LIST.final" | xargs -0 -r du -k 2>/dev/null | sort -rn | head -10
echo "--- totals per top two levels (KB) ---"
tr '\n' '\0' < "$LIST.final" | xargs -0 -r du -k 2>/dev/null \
  | awk '{n=split($2,p,"/"); k=(n>2)?p[1]"/"p[2]:p[1]; s[k]+=$1} END{for(k in s) print s[k], k}' | sort -rn | head
echo "--- file count / raw bytes / estimated bytes after gzip ---"
wc -l < "$LIST.final"
tr '\n' '\0' < "$LIST.final" | xargs -0 -r cat 2>/dev/null | wc -c
tar -czf - -T "$LIST.final" 2>/dev/null | wc -c
rm -f "$LIST" "$IGN" "$LIST.final"
```

In short: it lists tracked and untracked files using the same rule-reading that EAS uses, subtracts tracked files the rules match, and prints both the raw total and a gzip estimate.

This is the output from a test repository on Linux (git 2.34). The root `.gitignore` held only `node_modules/`, `app/.gitignore` excluded `big.bin`, and `assets/original/` held a 3 MB and a 0.5 MB image, one committed and one untracked.

```text
Active rules: .gitignore in every directory
--- largest first (KB) ---
2932	assets/original/a.png
492	assets/original/b.png
4	src/index.ts
...
--- file count / raw bytes / estimated bytes after gzip ---
5
3500024
3501211
```

`app/sub/big.bin` doesn't appear, because the nested `.gitignore` is respected. The images didn't shrink under gzip, so the estimate matched the raw total almost exactly. It should behave the same on macOS, but I've only run this version on Linux. If the numbers look off with macOS `du` or `tar`, trust `eas build:inspect`.

## The weight usually comes from three places

What I actually found was always something I thought git was already ignoring.

- Full-size source material, such as `assets/original/` holding high-resolution images or video from before delivery.
- Leftovers from a local build: `android/app/build/`, `android/.gradle/`, `ios/Pods/`, `ios/build/` and similar.
- Half-finished exports: zip files, `.psd`, screen recordings.

With wallpaper apps the images are the product, and I had a habit of keeping the originals inside the project. The app ships a few dozen resized files, yet the folder held every original.

Local build output costs more than upload time, too. I wrote about a case where a leftover `android/build` made only the EAS build fail in [When only EAS Build fails with "No matching variant"](/articles/app-dev/eas-build-no-matching-variant-stale-windows-autolinking-cache).

## Three misunderstandings worth correcting

**"I never ran git add, so it won't be uploaded."** In the default workflow, where commits aren't required, EAS CLI copies your working directory in a way that approximates `git clone --depth 1`. Uncommitted and untracked files go in unless a rule excludes them. Setting `cli.requireCommit` to `true` in `eas.json` switches to a real shallow clone, so untracked files stay out. Even then, `.easignore` still applies and matching files are deleted from the clone, with a warning that the upload no longer matches your commit.

**".easignore adds to .gitignore."** Expo's documentation says that once `.easignore` exists, it is used instead of every `.gitignore` in the repository, including the ones in subdirectories. I wrote more about this in [.easignore replaces .gitignore](/articles/rork-dev/easignore-replaces-gitignore-eas-build-upload-scope).

**"Put .easignore next to eas.json."** As of November 2026, the docs say the normal Git workflow reads `.easignore` only from the repository root. In a monorepo, a file inside the app directory is ignored. A change that would also look next to `eas.json` has been proposed to eas-cli, but it hadn't been merged when I checked. In the no-VCS workflow (`EAS_NO_VCS=1`), it's read from the directory in `EAS_PROJECT_ROOT`.

## When it's in .gitignore but still uploaded

Check which rule matches the path.

```bash
# Without .easignore: shows which .gitignore line matches, if any
git check-ignore -v assets/original/wall_0001.png
echo "exit=$?"   # 0 = ignored, 1 = not ignored

# With .easignore: check-ignore doesn't read it, so ask ls-files instead
git ls-files -c -o -i --exclude-from=.easignore | grep 'assets/original/' | head
```

`git check-ignore` reads `.gitignore` and git's own settings, never `.easignore`. Mixing the two up sends you back to the same line again and again, which is why I've kept them apart.

Exit code 1 means the file is not ignored. A common cause is writing `assets/original` while the folder actually lives at `app/assets/original`. A leading `/` anchors a pattern to the directory of the file it's in, so it's worth reading the path one segment at a time.

## Three ways to shrink it, and when I use each

<table>
<tr><th>Approach</th><th>Fits when</th><th>Watch out for</th></tr>
<tr><td>Exclude with <code>.easignore</code></td><td>You want files on disk, but the build doesn't need them</td><td>Rules not copied from .gitignore; excluding too much</td></tr>
<tr><td><code>cli.requireCommit: true</code></td><td>Lots of large untracked files, and you want the upload to match your commit</td><td>You must commit before every build; .easignore still applies</td></tr>
<tr><td>Move material out of the project</td><td>Originals and video that belong outside the app anyway</td><td>Scripts that point at the old path need updating</td></tr>
</table>

My own split: originals live outside the project, and local build output is excluded with `.easignore`. Moving the originals out also makes editor search and backups lighter, not just EAS.

When writing `.easignore`, copy every `.gitignore` rule first, then add the heavy items.

```
# Start by copying what your .gitignore files already say (nested ones too)
node_modules/
.expo/
dist/
.env

# Then add what caused this failure and the build doesn't need
/assets/original/
android/app/build/
android/.gradle/
ios/Pods/
ios/build/
*.psd
*.zip

# The directory you dumped with build:inspect
/eas-archive/

# Untracked files the build does need go last, re-included with !
# !generated/config.json
```

Expo's example also excludes `/android` and `/ios` entirely. That's for projects without native directories, where the build server runs prebuild to generate them. If you've committed hand edits under `ios/` or `android/`, the same line throws those edits away. I'd check what's there first, using the steps in [Count what prebuild --clean will erase before you upgrade](/articles/rork-dev/rork-expo-prebuild-native-drift-inventory-config-plugin).

## The night I excluded too much

The first time I wrote `.easignore`, I came close to excluding all of `assets/`. The total dropped beautifully. Then I opened the `eas build:inspect` output and couldn't find the app icon or the splash image. Had I built right then, the build server would have stopped on missing images.

That was when I realized that a smaller archive and a complete archive are two separate things to check.

**When cutting, watch the total; when keeping, look at the contents.** I now check both, in that order, every time I touch `.easignore`.

## What to do next

Run the script once on your current project. If the gzip estimate is over 150 MiB, revisit `.easignore` before your next build, then confirm the contents with `eas build:inspect --stage archive`. If nothing stands out, you've at least ruled the upload out.
