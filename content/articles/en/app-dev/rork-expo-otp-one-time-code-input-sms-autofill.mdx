When I added phone verification to one of my apps, my first attempt was the obvious one: six TextInputs sitting side by side. It looked tidy, but the feedback arrived fast. "The code from the SMS never shows up above the keyboard." "When I paste, only the first box fills in." The moment I split the field into boxes, I had quietly broken both iOS autofill and clipboard paste. As an indie developer shipping several apps to the App Store, this one screen — the verification code field — is something I have rebuilt more times than I would like to admit.

A code entry screen sits right before sign-up or payment, exactly where you least want people to drop off. A single moment of friction here loses someone who was already interested. Let me walk through building an input in Expo (React Native) where SMS autofill, pasting, and deleting all feel natural.

## Splitting into boxes cuts off autofill

The first snag in a code field is the mismatch between how it looks and how input actually works. Visually you want each digit in its own box. But OS autofill treats one field as the target and tries to drop the whole six-digit string into it.

Split that into six TextInputs and iOS cannot decide which field to inject into, so the keyboard suggestion (the code chip) never appears at all. Android's SMS autofill assumes a single field too. Paste lands only in the one focused box.

That leads to a single guiding principle: split the appearance, keep the input as one. Place a single transparent TextInput, then draw its value one character at a time so it reads as a row of boxes.

## Set the autofill attributes first

Lock down autofill before anything else. Leave it for later and you will build the whole UI, then lose an afternoon to "why is the suggestion not showing." The required attributes differ by OS.

One caution: copying an `importantForAutofill` value from an old blog post can actually make Android ignore `sms-otp`. Start from the minimal setup above and add attributes only when you truly need them.

```tsx
import { TextInput } from "react-native";

// The single real input. It stays transparent because the boxes are drawn separately
<TextInput
  value={code}
  onChangeText={handleChange}
  keyboardType="number-pad"
  textContentType="oneTimeCode" // iOS: surfaces the SMS code as a suggestion
  autoComplete="sms-otp"        // Android: SMS autofill
  maxLength={6}
  autoFocus
  style={{ position: "absolute", opacity: 0 }}
/>
```

## A segmented look from one TextInput

With the foundation in place, draw the value one character at a time to form the boxes. The key idea: the drawn boxes are display-only, while the hidden TextInput handles taps and keystrokes. All you add is a bridge — tapping a box refocuses the hidden input.

```tsx
import { useRef, useState } from "react";
import { Pressable, TextInput, View, Text } from "react-native";

const LENGTH = 6;

export function OtpInput({ onComplete }: { onComplete: (v: string) => void }) {
  const [code, setCode] = useState("");
  const inputRef = useRef<TextInput>(null);

  const handleChange = (raw: string) => {
    // Strip non-digits, then cap at the length
    const next = raw.replace(/[^0-9]/g, "").slice(0, LENGTH);
    setCode(next);
    if (next.length === LENGTH) {
      onComplete(next); // auto-advance once all six are in
    }
  };

  const cells = Array.from({ length: LENGTH }, (_, i) => code[i] ?? "");

  return (
    <Pressable onPress={() => inputRef.current?.focus()}>
      <View style={{ flexDirection: "row", gap: 8 }}>
        {cells.map((ch, i) => (
          <View
            key={i}
            style={{
              width: 44, height: 52, borderRadius: 10,
              borderWidth: 1,
              borderColor: i === code.length ? "#3b82f6" : "#d1d5db",
              alignItems: "center", justifyContent: "center",
            }}
          >
            <Text style={{ fontSize: 22 }}>{ch}</Text>
          </View>
        ))}
      </View>
      <TextInput
        ref={inputRef}
        value={code}
        onChangeText={handleChange}
        keyboardType="number-pad"
        textContentType="oneTimeCode"
        autoComplete="sms-otp"
        maxLength={LENGTH}
        autoFocus
        style={{ position: "absolute", opacity: 0 }}
      />
    </Pressable>
  );
}
```

Changing the border color of the currently focused box (`i === code.length`) gives a clear "you are here" cue even without a visible caret. That small touch does a lot for how reassuring the field feels on a real device.

## Make paste and delete painless

Autofill and the segmented look still are not enough — real usage trips here. Two pitfalls to close off in advance.

### Paste: receive all six at once

The first is paste. Plenty of people long-press the code in the SMS body and paste it. A six-box implementation fills only one box, but with the single-TextInput approach `handleChange` receives all six characters at once, so `slice(0, LENGTH)` distributes them across the boxes correctly. The code above already absorbs paste.

### Delete: catch Backspace in one place

The second is delete. On some devices the number-pad delete key does not fire `onChangeText` when the value is empty. To reliably remove one box at a time, catch Backspace in `onKeyPress` and drop the last character.

```tsx
import type { NativeSyntheticEvent, TextInputKeyPressEventData } from "react-native";

const handleKeyPress = (e: NativeSyntheticEvent<TextInputKeyPressEventData>) => {
  if (e.nativeEvent.key === "Backspace") {
    setCode((prev) => prev.slice(0, -1));
  }
};

// attach as <TextInput ... onKeyPress={handleKeyPress} />
```

On some devices `onChangeText` and `onKeyPress` both fired, deleting two characters per tap. I settled it by routing deletion solely through `onKeyPress` and letting `onChangeText` handle only "what was added," keeping their roles separate. A small detail, but one you will not catch without testing across a few physical devices.

## Where problems stopped me during testing

Load this onto real hardware and a few production-relevant notes emerge.

### Split what you verify on simulator vs device

The iOS simulator never shows the SMS suggestion, so it is easy to conclude the feature is broken. The chip only appears once a real SMS arrives, so limit simulator checks to the segmented display and paste, and confirm autofill on a device.

Android's `sms-otp` sometimes requires an app-linked hash or a specific format in the SMS body. When that is missing, no suggestion appears even though nothing is wrong with the UI — and you end up endlessly doubting your layout. If autofill will not show, suspect the message format first.

Code fields also have a subtle snag where the keyboard lingers after paste and hides the confirm button. Call `Keyboard.dismiss()` once six digits are in, so attention moves to the confirm button and the final tap feels light.

## The call I make

For a verification code field, I recommend placing a transparent single TextInput and drawing your own boxes rather than pulling in a heavy library. With no extra dependency it holds up better across Expo updates, and you keep direct control over the three things that matter — autofill, paste, and delete.

I keep the box count behind a single `LENGTH` constant, so the same component covers both four-digit and six-digit cases. It is a plain-looking screen, but when it is smooth the whole sign-up leaves a better impression. I hope this helps with your own build, and thank you for reading.
