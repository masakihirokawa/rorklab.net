I might have shipped a production build that still talks to the development API. The first hint would not be the app's behavior. It would be one line in the build log.

```
> Task :app:createBundleReleaseJsAndAssets UP-TO-DATE
```

Say you change `EXPO_PUBLIC_API_URL` to the production value and run the Android release build again. Gradle prints "BUILD SUCCESSFUL". The app it produced may still carry the development value from the previous run. Someone reported exactly this on Expo's GitHub.

I switch values per environment too, for ad settings and endpoints in my wallpaper apps. For a while I treated "the build passed" as proof that the switch had worked, so reading this report gave me a small cold feeling in the stomach.

Here is the short version first. **A build where only a value changed looks, to Gradle, like a build where nothing changed, and it can skip re-creating the JavaScript bundle.** Below I keep three things apart: what the official report confirms, what I reproduced in a small model of my own, and what I have not checked.

## Who this is for

You will probably recognize one of these:

- You changed only `.env` or an environment variable and re-ran the Android release build in the same folder.
- A production APK or AAB seems to be calling your development server.
- The build log is full of `UP-TO-DATE` lines and you can't tell which one matters.

If you build from a clean checkout every time, or you changed JavaScript source in the same build, you are less likely to hit this. The next sections explain why.

## Triage: which problem do you actually have?

Similar symptoms can come from different causes, and the fix depends on the cause.

The first row is the subject of this article. Rows two to four are "the task runs but the value is wrong" cases, where the cause is Expo's loading rules rather than Gradle.

The report is [Issue 49630 on expo/expo](https://github.com/expo/expo/issues/49630), opened on September 1, 2026, on SDK 57, React Native 0.86, macOS, and a bare Android project. Expo's automated verification on the same issue says it reproduced. The reporter also notes that editing a `.env` file, not just a shell variable, behaves the same way.

## Why the task gets skipped

Values that start with `EXPO_PUBLIC_` are not read at runtime. They are inlined into the bundle as strings when it is built. `babel-preset-expo` does the inlining: in a production bundle, the expression `process.env.EXPO_PUBLIC_API_URL` becomes the literal value at that moment. Change the value, and the bundle's contents should change.

Gradle, though, only looks at what a task declares as inputs. According to the description in the fix's pull request, React Native's bundle task declares the project's `.js`, `.jsx`, `.ts`, and `.tsx` files, plus settings such as the entry file, `--dev`, and `--minify`. The bundler inherits the process environment, but that environment is not on the input list.

`.env` files fall outside the inputs for two reasons. They are not `.js` or `.ts` files, and the Expo CLI reads them inside its own process, so they never reach Gradle as variables.

Inputs and outputs look the same as last time, so Gradle decides there is nothing to do and prints `UP-TO-DATE`. The bundler depends on the environment; Gradle doesn't know it does — that mismatch is the whole bug.

## A minimal reproduction

Reading a report didn't give me much of a feel for it, so I built the same mismatch with plain Gradle, no Android and no Expo. A task imitates the bundle step: its only input is `src`, it writes one file, and it embeds an environment variable.

```groovy
tasks.register('createBundle') {
  inputs.dir('src')                                   // input: source only
  outputs.file(layout.buildDirectory.file('index.bundle'))
  doLast {
    def out = layout.buildDirectory.file('index.bundle').get().asFile
    out.parentFile.mkdirs()
    // stand-in for the bundler inlining an env var
    out.text = "var API = '" + (System.getenv('EXPO_PUBLIC_API_URL') ?: '') + "';\n"
  }
}
```

Two runs with different values (Gradle 8.14.3):

```
# Run 1: EXPO_PUBLIC_API_URL=https://dev.example.invalid
> Task :createBundle
var API = 'https://dev.example.invalid';

# Run 2: EXPO_PUBLIC_API_URL=https://prod.example.invalid
> Task :createBundle UP-TO-DATE
var API = 'https://dev.example.invalid';
```

The second run is `UP-TO-DATE`, and the output still holds the development value. The build counts as a success, so if you skim the log you will almost certainly miss it.

## The fix: declare the environment as an input

The idea is to tell Gradle that `EXPO_PUBLIC_*` variables are inputs of the bundle task. I added that to my model:

```groovy
def pub = providers.environmentVariablesPrefixedBy('EXPO_PUBLIC_')
tasks.named('createBundle') { inputs.property('expoPublicEnv', pub) }
```

`environmentVariablesPrefixedBy` is a Gradle API that reads only the variables with a given prefix. If you made every environment variable an input, tiny unrelated differences would force a rebuild every time, so the prefix matters.

Three runs, same order as before:

```
# Run 1: dev value
> Task :createBundle                 → https://dev.example.invalid
# Run 2: prod value
> Task :createBundle                 → https://prod.example.invalid
# Run 3: prod value again
> Task :createBundle UP-TO-DATE
```

The run where the value changed re-ran; the run where nothing changed was skipped. You keep the speed and lose the mix-up.

In a real project, I'd expect the equivalent to sit at the end of `android/app/build.gradle`, applied to every task whose name starts with `createBundle` and ends with `JsAndAssets`, with both the variables and the `.env` files as inputs:

```groovy
// end of android/app/build.gradle (stopgap until Expo ships a fix)
def expoPublicEnv = providers.environmentVariablesPrefixedBy('EXPO_PUBLIC_')
def projectRoot = rootProject.projectDir.parentFile   // one level above android/
def envFiles = files(['.env', '.env.local', '.env.production', '.env.production.local']
  .collect { new File(projectRoot, it) })

tasks.matching { it.name.startsWith('createBundle') && it.name.endsWith('JsAndAssets') }
  .configureEach {
    inputs.property('expoPublicEnv', expoPublicEnv)
    inputs.files(envFiles).withPathSensitivity(PathSensitivity.RELATIVE)
  }
```

To be clear about the limits: I verified the behavior in my model, but I have not tried this `build.gradle` addition in a real Android project. The file list follows the production-mode files in Expo's documentation. And if you regenerate `android/` with `npx expo prebuild`, the addition disappears; in that case one of the other options below is safer.

## Workarounds until it's fixed, and how to choose

Expo has a fix open as [Pull Request 49839](https://github.com/expo/expo/pull/49839). Its description says it declares both the `EXPO_PUBLIC_*` variables and the project's `.env` and `.env.*` files as inputs of every `createBundle*JsAndAssets` task. When I checked on November 24, 2026, it had not been merged. The PR also states up front that it came from an automated verification run and has not been reviewed by a person.

Until it lands, there are four realistic options:

If it were my project, I'd start with **`--rerun-tasks` for production builds only**. I give up a little speed and get one less thing to think about. If you manage `android/` by hand and switch between dev and prod often, declaring the inputs will probably be lighter day to day.

Whether this also happens on EAS cloud builds is marked "not verified" in the report. I haven't checked either, so I won't claim it one way or the other.

## Three assumptions worth letting go of

First: "It said BUILD SUCCESSFUL, so the value must be new." Gradle's success means every task that needed to run finished. Tasks skipped as `UP-TO-DATE` count as successful too. Whether the contents are what you meant is a separate question.

Second: "If I edit `.env`, the next build will pick it up." As above, `.env` is read by the Expo CLI, and Gradle never sees the change. The dev server reflects edits quickly, which makes the release-build gap even easier to miss.

Third: "Any way of reading `process.env` works." Expo's documentation says only statically written dot access such as `process.env.EXPO_PUBLIC_KEY` is inlined; `process.env['EXPO_PUBLIC_KEY']` and destructuring are not. In that case the task runs and the value still isn't there — row three of the triage table.

## Check what's inside the APK before you publish

In the end, the most reliable check is to look at what you built. An APK is a zip file, so you can pull out the bundle and search for your endpoint strings:

```bash
# Count leftover dev endpoints (0 means none found)
unzip -p android/app/build/outputs/apk/release/app-release.apk \
  assets/index.android.bundle | grep -a -c 'dev.example.invalid'

# Confirm the production endpoint is there (1 or more means present)
unzip -p android/app/build/outputs/apk/release/app-release.apk \
  assets/index.android.bundle | grep -a -c 'prod.example.invalid'
```

Replace `dev.example.invalid` with your own development endpoint. Release bundles are often Hermes bytecode rather than plain text; `grep -a` searches the raw bytes for the string. I haven't tried this against my model, so before concluding "it's not in there" from a zero, search for the production value as well and read the two results together.

**A success message is not a guarantee of contents.** On the days I'm tempted to forget that, I go back to searching the log for `UP-TO-DATE`.

## Where people tend to get stuck next

Even with this bug handled, environment variables have another trap. From SDK 58, files that don't match a mode, such as `.env.staging`, are no longer loaded. I wrote up a way to have a script count which file wins in [Expo SDK 58 No Longer Loads .env.staging](/en/articles/app-dev/expo-sdk58-env-staging-file-not-loaded-local-wins-audit-script).

A wrong endpoint can also surface during review as "the app launches to a blank screen." The places I'd look first are in [App Review Says "Guideline 2.1, Blank Screen"](/en/articles/app-dev/app-review-guideline-2-1-blank-screen-expo-release-build-checklist).

The web side has a similar shape, where stale state survives a deploy. I dug into that from the cause side in [Why redeploying doesn't fix the Application error right after a deploy](/en/articles/rork-dev/why-redeploy-does-not-fix-application-error-stale-html-calls-missing-chunk).

Next time you switch a build's endpoint, open the build log first and check one thing: whether the `createBundle` line says `UP-TO-DATE`.
