I scanned the QR code and two lines of English appeared in Expo Go: "Project is incompatible with this version of Expo Go," followed by "This project requires a newer version of Expo Go."

I had just installed the app. So I assumed my project was the broken part. I deleted node_modules, reinstalled, cleared the cache, restarted, and got the same screen again. Only then did I stop typing.

What I realized later is that the message never says anything is broken. **It says two things didn't match, and it doesn't tell you which one is wrong.** So before I touch anything now, I split the question into three comparisons.

## The message is the result of comparing three numbers

Expo Go compares the SDK version the project claims against the SDK version it supports itself. If they don't match, you get that screen and nothing loads. Expo's troubleshooting page puts it plainly: each build of Expo Go includes one Expo SDK version, and the `expo` version in package.json sets the project's SDK.

That means the project isn't the only suspect. The Expo Go build on your phone can be the one that's off.

<tr><th>Order</th><th>What to check</th><th>What a mismatch looks like</th></tr>
<tr><td>1</td><td>The SDK your project uses</td><td>It disagrees with Expo Go, so every project shows the same screen</td></tr>
<tr><td>2</td><td>The SDK Expo Go supports</td><td>An old build, or a build for a different SDK, is installed</td></tr>
<tr><td>3</td><td>The Android Expo Go build itself</td><td>The SDK matches, yet one specific build rejects it</td></tr>
</table>

The first two you can verify by reading a number. The third is rare, but it really happened in summer 2026, so I'll cover it below.

## Check one: turn the project's SDK into a number

Start by finding out what your project claims to be. This works the same for a project exported from Rork and one you created by hand.

```bash
# Run from the project root
grep -E '"(expo|react-native)"' package.json

# List dependencies that don't match what this SDK expects
npx expo install --check
```

The first line shows the expo version (for example, `~56.0.11` means SDK 56) and the react-native version. The second lists packages that don't fit the SDK. If red lines pile up there, fix the project first and leave Expo Go alone.

I'd write the number down in one line, because you'll set it next to the Expo Go side in the next step.

```js
// check-sdk.js — a small note-to-self script
// Usage: node check-sdk.js
const pkg = require('./package.json');
const dep = { ...pkg.dependencies, ...pkg.devDependencies };

const expo = dep.expo || '(expo not found)';
const major = String(expo).match(/(\d+)\./)?.[1] ?? '?';

console.log(`expo        : ${expo}`);
console.log(`SDK (guess) : ${major}`);
console.log(`react-native: ${dep['react-native'] ?? '(not set)'}`);
// Compare this SDK number with the "Supported SDK"
// shown in Expo Go's settings screen.
```

Why a script for something this small? Because three numbers in a row keep my hands moving, while reopening package.json and rereading an English error screen does not.

## Check two: which SDK does your Expo Go accept?

Next, find out what your installed Expo Go supports. The app's settings screen shows the supported SDK. In one thread, someone reported that the build from the Play Store showed "Supported SDK 54," so SDK 55 and 56 projects would not open.

From here, a physical iPhone and everything else go separate ways. My own first mistake was not knowing that, and assuming I could reinstall an older build on an iPhone the way I could on Android.

### On a physical iPhone or iPad

Expo's troubleshooting page (updated September 3, 2026) says Expo Go on the Apple App Store stops at SDK 54, and SDK 55 and later are not available there. A May 2026 announcement explained that the SDK 55 build was still waiting for App Store approval.

The SDK 58 release notes from October 15 say something newer, though: a new Expo Go will reach the App Store and Google Play "within a few weeks," and it will support only SDK 58. As of November 2026 I haven't confirmed which build the stores are actually serving. That is exactly why I trust the Supported SDK number on the device over anything a store listing says.

When the App Store build doesn't match your project, these are the routes Expo documents:

<table>
<tr><th>Project SDK</th><th>Options on a physical iPhone</th><th>What you need</th></tr>
<tr><td>Same as the App Store Expo Go</td><td>Open it in the App Store build as usual</td><td>Nothing extra</td></tr>
<tr><td>SDK 54 or later, different from the store build</td><td>Build your own Expo Go with <code>eas go</code> and install it through your TestFlight internal team</td><td>Apple Developer Program ($99/year)</td></tr>
<tr><td>SDK 53 or earlier</td><td>You can't install an older Expo Go on a device. Upgrade the project, or use Android, the iOS Simulator, or a development build</td><td>—</td></tr>
</table>

`eas go` doesn't need a local project. Per Expo's guide, the build runs in the cloud on EAS, so no Mac is required, and `--sdk-version` lets you pick the SDK.

```bash
# Update EAS CLI first (you'll be asked to sign in to Apple Developer)
npm install -g eas-cli
eas go
# Add --sdk-version when you need a specific SDK
```

The FAQ says it counts as workflow minutes rather than build usage. I haven't run it myself, so I can't tell you how long it takes.

### On Android, the Android Emulator, or the iOS Simulator

Here you have more room, including builds for older SDKs. On expo.dev/go, pick your project's SDK and target platform, and it shows you how to install the matching build.

If you'd rather use the terminal, there's a standalone `expo-go` CLI:

```bash
# Download the latest Expo Go for Android
npx expo-go download android latest

# Print the download URL instead of downloading
npx expo-go url ios latest
```

Expo's docs say you can pass an SDK version in place of `latest` to pin a specific release. The file lands in the current directory and is cached under `~/.expo`. The CLI doesn't work for a physical iPhone, because Apple doesn't allow side-loading older app versions there.

### If nothing matches, move the project instead

The other option is to move the project to the SDK your Expo Go supports. But changing an SDK ripples through your dependencies. I try reinstalling Expo Go before I touch the project's SDK. **Easy-to-undo steps first, hard-to-undo steps last.** I keep to that even when I'm in a hurry, maybe especially then.

Starting fresh is a little different. Since SDK 56, `create-expo-app` asks whether you want a project that matches the store build of Expo Go or the latest SDK, and you can choose a version with a template tag such as `--template default@sdk-55`.

## Check three: the SDK matches, and it still fails

Sometimes checks one and two both pass and you still see the same screen. In June 2026, exactly this was reported in the expo/expo repository on GitHub.

According to the report, Expo Go 56.0.1 for Android rejected every SDK 56 project, including a fresh empty template. It failed whether the project loaded from the dev server or from an EAS Update.

The reporter isolated the cause carefully. The project declared SDK `56.0.0`, and the server's version table said a 56.0.1 client should accept it. When they rewrote only that manifest value to `56.0.1` through a local proxy, the project opened. Installing the previous release, Expo Go 56.0.0, opened the same project with no rewrite at all.

Their reading was that the 56.0.1 client compared the project's SDK string against its own app version string. That would mean it wasn't asking "is this SDK 56?" at all. I only read the report; I did not reproduce this, and the root cause is the reporter's inference.

Per the comments, two things helped:

<table>
<tr><th>Fix</th><th>What it involves</th><th>Caveat</th></tr>
<tr><td>Install the previous build</td><td>Download the Expo Go 56.0.0 APK from the official releases page and install it over the existing app</td><td>This was the workaround at the time. Check the official page first today</td></tr>
<tr><td>Follow the official page</td><td>Choose SDK 56 and Android on expo.dev/go and reinstall</td><td>A maintainer pointed people to this route</td></tr>
</table>

The issue was closed on October 26, 2026. The maintainers noted that a working Expo Go for SDK 56 is available on the official page and that no new reports had come in since June. If you meet this screen today, reinstalling from that page comes first.

## Three assumptions I had to drop

There are three things I believed about this screen until I read Expo's own explanation.

First, that deleting node_modules would fix it. The screen reports a comparison between the project's SDK and Expo Go's SDK. Deleting node_modules doesn't change the `expo` version in package.json, so the SDK the project claims stays the same. If it looked fixed after a wipe, something else was probably resolved at the same moment.

Second, that the newest Expo Go opens projects on any SDK. Each build includes exactly one SDK, and the SDK 58 notes say the new Expo Go supports only SDK 58. Updating can actually make an older project stop opening.

Third, that I could reinstall an older build on an iPhone. Expo's docs are clear that a physical iPhone can't take side-loaded older versions. On an iPhone, your options are `eas go`, a development build, or upgrading the project.

## The counterintuitive part: newest wasn't safest

I had always assumed the latest app build was the safest one. This case went the other way. Within the same SDK 56, a single patch number decided which projects opened and which didn't.

That doesn't mean you should always install an older build. The lesson I took is narrower: when updating doesn't fix it, keep "try the previous release" on your list of options.

## When it still won't open

If all three checks pass and nothing changes, consider switching from Expo Go to a development build, which installs as your own app. Expo itself describes Expo Go as first and foremost an educational tool, and recommends a development build once you're building something to ship.

When I can't decide, this is the table I use:

<table>
<tr><th>Option</th><th>Best when</th><th>Effort and cost</th></tr>
<tr><td>Store Expo Go</td><td>You're learning or prototyping and can keep the project on the store build's SDK</td><td>Lightest. Only the native modules bundled in Expo Go</td></tr>
<tr><td>Your own Expo Go via <code>eas go</code></td><td>You want Expo Go on a physical iPhone for an SDK the store doesn't carry</td><td>Needs an Apple Developer membership, but no per-project build</td></tr>
<tr><td>Development build</td><td>You use custom native modules or plan to ship to the stores</td><td>Requires a build, and in return you stop fighting SDK matching</td></tr>
</table>

Put simply: **if there's any chance you'll ship it, use a development build; while it's still a sketch, Expo Go is fine.**

## My first three minutes next time

As an indie developer, I tend to skip steps in the week an app update is due. When I meet this screen now, I run the grep for the SDK number, open Expo Go's settings, and open the official install page, in that order. Deleting node_modules comes after.

For today, write the expo version from your package.json on a single line somewhere you'll find it. With that line in hand, the next time this screen appears, you'll spend noticeably less time guessing.
