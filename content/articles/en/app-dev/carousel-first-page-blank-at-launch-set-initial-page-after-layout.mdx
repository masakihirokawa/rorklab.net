I was trying out an update of my wallpaper app on a test phone when the main screen came up as one flat color. No wallpaper, no spinner. I swiped left and page two appeared instantly. I swiped back, and page one was still empty.

As an indie developer, my first instinct was the network. A slow connection, a corrupted cache, a bad URL. But once I traced it, the first page had not failed to load an image. The page itself had never been built. Everything went wrong before the image library was even involved.

The real cause was timing. I was telling the pager which page to start on before it had measured itself, so the binding for that first page was simply skipped. What follows is the Android fix I actually shipped, and the way the same gap shows up, and closes, in the Expo code that Rork tends to generate.

## What was actually happening

Three symptoms lined up:

- Only the page meant to appear first was empty at launch
- Swiping drew page two and beyond normally
- Swiping forward and back again did not bring page one back

That last one was the giveaway. If swiping proves the image path works, but page one still never returns, the problem sits upstream of image loading. It sits where the pager decides which pages to build.

On Android, I was passing the start position to ViewPager2 synchronously, right after creating the screen. The adapter had not finished measuring itself. The pager accepted the jump, but the bind for the page it jumped to fell through the cracks. Every later page got bound fresh on swipe, which is why everything else looked fine.

## The Android fix I shipped

The change itself was almost embarrassingly small. I moved the position call to after layout.

```java
// Before: position set synchronously right after the screen is created.
// The adapter has not been measured yet, so the initial page bind is skipped.
viewPager.setAdapter(adapter);
viewPager.setCurrentItem(adapter.getStartPosition(), false);

// After: queue it with post so it runs once measure/layout has completed.
viewPager.setAdapter(adapter);
viewPager.post(() ->
    viewPager.setCurrentItem(adapter.getStartPosition(), false)
);
```

Anything handed to `post` goes onto that view's message queue and runs after a full measure and layout pass. Swapping the order was enough for the first page to be built properly.

What made me pause was the thought that the same ordering mistake could live elsewhere. I added an item to my iOS checklist: look for any place that hands UIPageViewController its first page inside viewDidLoad. I have not seen the symptom on iOS. It is a preventive check, based on the fact that the same screen structure invites the same ordering mistake.

**A pager gets its position only after it knows its size.** That is the one ordering rule I now settle before writing any carousel, on any platform.

## How the same gap opens in an Expo FlatList

When Rork builds a carousel, it usually comes out as a horizontal FlatList with `pagingEnabled`. The timing problem shows up here too, wearing different clothes.

Here is the version I see most often. It calls `scrollToIndex` from a ref right after mount, to jump back to the page the user last viewed.

```tsx
// ❌ Can leave page one blank, or never leave the first item, at launch
import { useEffect, useRef } from "react";
import { FlatList, Image, useWindowDimensions } from "react-native";

type Wallpaper = { id: string; uri: string };

export function WallpaperCarousel({
  items,
  startIndex,
}: {
  items: Wallpaper[];
  startIndex: number;
}) {
  const listRef = useRef<FlatList<Wallpaper>>(null);
  const { width } = useWindowDimensions();

  useEffect(() => {
    // Right after mount, no page positions have been measured yet.
    // With neither getItemLayout nor onScrollToIndexFailed, dev builds stop with
    // "scrollToIndex should be used in conjunction with getItemLayout or onScrollToIndexFailed"
    listRef.current?.scrollToIndex({ index: startIndex, animated: false });
  }, [startIndex]);

  return (
    <FlatList
      ref={listRef}
      data={items}
      horizontal
      pagingEnabled
      keyExtractor={(w) => w.id}
      renderItem={({ item }) => (
        <Image source={{ uri: item.uri }} style={{ width, height: "100%" }} />
      )}
    />
  );
}
```

There are three holes stacked on top of each other:

- **The position arrives too early.** `useEffect` runs right after commit, before FlatList has measured its children
- **There is no way to compute positions.** Without `getItemLayout`, FlatList cannot know where unrendered pages are. Dev builds stop with the message in the comment above; release builds just fail to scroll, silently
- **The width comes from the whole screen.** `useWindowDimensions` gives you the device width. Put the carousel inside padding or a split-screen pane, and the page width and the snap unit drift apart, so it stops halfway between pages

The third one is the hardest to notice. On a phone in full screen, the two widths match, so the bug only surfaces once you add margins or run in split view.

## Measure first, then hand over the first page

In the fixed version, the View wrapping the carousel measures its real width, and the FlatList is not rendered at all until that width is known. The start position is no longer pushed in later through a ref. It goes into the very first render as `initialScrollIndex`.

```tsx
// ✅ Measure the frame, then render FlatList with the start page in its first render
import { useCallback, useState } from "react";
import {
  ActivityIndicator,
  FlatList,
  Image,
  LayoutChangeEvent,
  StyleSheet,
  View,
} from "react-native";

type Wallpaper = { id: string; uri: string };

export function WallpaperCarousel({
  items,
  startIndex,
}: {
  items: Wallpaper[];
  startIndex: number;
}) {
  const [pageWidth, setPageWidth] = useState(0);

  const onLayout = useCallback((e: LayoutChangeEvent) => {
    // Round so sub-pixel jitter does not trigger endless re-renders
    const w = Math.round(e.nativeEvent.layout.width);
    setPageWidth((prev) => (prev === w ? prev : w));
  }, []);

  // Rendering before data arrives would lock initialScrollIndex to the first item
  const ready = pageWidth > 0 && items.length > 0;
  const safeIndex = Math.min(Math.max(startIndex, 0), Math.max(items.length - 1, 0));

  return (
    <View style={styles.frame} onLayout={onLayout}>
      {!ready ? (
        <ActivityIndicator size="large" style={StyleSheet.absoluteFill} />
      ) : (
        <FlatList
          // Rebuild when the width changes (rotation, split-screen)
          key={`carousel-${pageWidth}`}
          data={items}
          horizontal
          pagingEnabled
          showsHorizontalScrollIndicator={false}
          keyExtractor={(w) => w.id}
          initialScrollIndex={safeIndex}
          // Every page has the same width, so position is simple multiplication
          getItemLayout={(_, index) => ({
            length: pageWidth,
            offset: pageWidth * index,
            index,
          })}
          // Build only the start page and its neighbours first
          initialNumToRender={1}
          windowSize={3}
          onScrollToIndexFailed={({ index }) => {
            // Should not fire while getItemLayout exists. If it does, log it
            // instead of silently snapping back to the first page.
            console.warn(`carousel: scrollToIndex failed at ${index}`);
          }}
          renderItem={({ item }) => (
            <Image
              source={{ uri: item.uri }}
              style={{ width: pageWidth, height: "100%" }}
              resizeMode="cover"
            />
          )}
        />
      )}
    </View>
  );
}

const styles = StyleSheet.create({
  frame: { flex: 1, backgroundColor: "#d9d9d9" },
});
```

Here is the reasoning behind each choice:

- **Measure with onLayout because the frame defines the page.** Use the frame width rather than the screen width, and the snap unit stays correct inside padding or split view
- **Do not render the list while the width is 0.** With a zero width, `getItemLayout` puts every page at offset 0, and the list sticks to the first item
- **Do not render it while the data is empty either.** `initialScrollIndex` is read only on the first render. If the list renders once with an empty array, data arriving later will not move it. This was the part I could not have learned from the docs alone
- **Put the width in the key.** When rotation or split view changes the width, the list is rebuilt instead of keeping stale offsets. Rebuilding sends it back to `startIndex`, so if you want to keep the current page, hold it in the parent and pass it back in
- **Give the frame a background color.** Even if the first image is late, the user sees a color that says something is coming, not a bare white screen. On Android, I set the page background and the image placeholder to the same color, and the "nothing is here" white disappeared

## A watcher that only runs in dev builds

A blank page you fixed once tends to come back the day you touch the layout. So I added a small hook that, in dev builds only, checks whether the first page actually seen matches the one you asked for.

```tsx
// Dev-only watcher for the initial page
import { useCallback, useEffect, useRef } from "react";
import type { ViewToken } from "react-native";

export function useInitialPageWatch(expectedIndex: number, label: string) {
  const firstSeen = useRef<number | null>(null);

  const onViewableItemsChanged = useCallback(
    ({ viewableItems }: { viewableItems: ViewToken[] }) => {
      if (firstSeen.current !== null) return;
      const first = viewableItems.find((v) => v.isViewable)?.index;
      if (typeof first === "number") firstSeen.current = first;
    },
    []
  );

  useEffect(() => {
    if (!__DEV__) return;
    // Give the first render and image swap a moment to settle
    const t = setTimeout(() => {
      if (firstSeen.current === null) {
        console.warn(`[${label}] no page visible after 1.5s`);
      } else if (firstSeen.current !== expectedIndex) {
        console.warn(
          `[${label}] first visible page was ${firstSeen.current}, expected ${expectedIndex}`
        );
      }
    }, 1500);
    return () => clearTimeout(t);
  }, [expectedIndex, label]);

  return onViewableItemsChanged;
}
```

On the FlatList side, pass the returned function as `onViewableItemsChanged` and add `viewabilityConfig={{ itemVisiblePercentThreshold: 60 }}`. Recreating `onViewableItemsChanged` on every render triggers a warning in dev builds, which is why the hook wraps it in `useCallback`.

In production it does nothing. Whenever I change the padding or frame around a carousel, I launch it once in the simulator and glance at the log. It takes a few seconds, so it feels less like a test and more like a habit.

## Pitfalls I ran into

A few things tripped me up while rebuilding this:

<table>
<thead>
<tr><th>Symptom</th><th>Cause</th><th>Fix</th></tr>
</thead>
<tbody>
<tr><td>Stops between page two and three</td><td>Page width came from the screen, not the frame</td><td>Measure the frame with onLayout and use the same value in getItemLayout</td></tr>
<tr><td>Remembers the last page, but always opens on the first</td><td>FlatList rendered once before data arrived</td><td>Hold the list back until both width and data are ready</td></tr>
<tr><td>Stops halfway after rotation</td><td>Old offsets survived the width change</td><td>Include the width in the key and keep the current page in the parent</td></tr>
<tr><td>scrollToIndex warning in dev builds</td><td>Position requested without getItemLayout</td><td>If all pages share one width, always write getItemLayout</td></tr>
</tbody>
</table>

The same idea applies if you use `react-native-pager-view`. Pass the start page as `initialPage` from the beginning instead of calling `setPage` right after mount; that sidesteps the ordering problem. I went with FlatList because I wanted finer control over how paging feels, but whichever you choose, the rule I keep is the same: the position belongs in the first render.

## What to check next

If you have a carousel in front of you right now, this is the order I'd suggest:

1. Log the frame width from `onLayout` once, next to the `useWindowDimensions` width. If they differ, that is very likely where your blank page or half-stop comes from
2. Search for any place that moves to the start page through a ref and `scrollToIndex`. Replace it with `initialScrollIndex` plus `getItemLayout`
3. Use the watcher above to confirm that FlatList is not rendering once before the data arrives

Each of these takes a few minutes. Even the first one alone is worth doing today.

When I finally realised that the culprit was the order of a single line, after suspecting image loading for so long, I felt relieved and a little sheepish at the same time. If this shortens the hunt for anyone staring at the same empty page, that would make me glad.
