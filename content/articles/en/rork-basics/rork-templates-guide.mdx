The hardest part of your first Rork app is often the blank prompt box — you know what you want, but not which words turn into something that actually runs. I have been building apps solo since 2014, and even now, that first step is where I stall. Rork's templates exist to take that first step for you.

## What Are Rork Templates?

Rork provides a library of **app templates** — pre-built starting points for common app types. Instead of writing prompts from scratch, you choose a template and customize it, and you get a working prototype that already includes navigation and data storage.

The real value of a template isn't that it saves typing. It's that you get a working example of *how an app should be structured* — and for first-time builders, that example is worth more than any explanation.

## How to Use Templates

### 1. Select a template

On the Rork project creation screen, choose "Start from template" and pick one close to your use case. It does not have to match exactly — as you'll see below, a similar structure is enough to start from.

### 2. Enter basic info

Provide your app name and a brief description. Rork generates code based on the selected template.

### 3. Customize with prompts

Once generated, customize via prompts:

```
"Change the color theme to blue"
"Add a category filter"
"Add dark mode support"
```

## Why Use Templates

**Save time**: Basic CRUD operations and navigation structure are already implemented, so you skip the entire foundation-building phase.

**Best practices built in**: Templates follow Rork's recommended code structure, making them easy to extend.

**Pre-built features**: Many templates include authentication flows, data persistence, and common UI components, so there's less wiring to do yourself.

## Template or From Scratch — How I Decide

The usual advice is "template for common apps, scratch for unique ones," but in practice the line is blurrier. Here's how I think about it. When the app is a common type and I just want something running fast, a template wins. When the UI and logic are genuinely unusual, a template's built-in assumptions can become a drag, and scratch is faster. And if it's your very first app, I strongly suggest starting from a template even if it isn't quite what you want — just to see, once, what the inside of a working app looks like. For pure learning, taking a template apart and writing from scratch are both good teachers.

## From a Template to "My Own App"

Here's a concrete story. I run several image-heavy apps — wallpaper and relaxation apps with over 50 million combined downloads — and I rebuilt a prototype of one of them in Rork by deliberately starting from the **Notes app** template.

That sounds odd, but a wallpaper app is structurally "show a grid, tap to open a detail view, save favorites" — almost the same skeleton as a notes list, detail, and save. The first lesson was that you don't need a perfect-fit template: **pick one whose screen structure is close, and it becomes a valid starting point.**

To turn it into *my* app, the very first thing I changed was the data layer. Most templates assume on-device storage (like AsyncStorage), but a wallpaper app needs to swap its images from the server side, so I had to fetch the list remotely:

```
"Change storage from on-device to fetching from an external API (a JSON image list).
 On fetch failure, fall back to showing the last cached list."
```

The next thing I removed was the authentication flow. My wallpaper apps are ad-supported and intentionally login-free. The sign-in screen the template shipped with would only cause drop-off, so I prompted "Remove auth and make the gallery visible from first launch."

This pattern — take a structurally close template, then swap only the data layer and the flows you don't need — has been clearly faster and more stable for me than stacking prompts onto a blank project. Because you're starting from something that already runs, it's also much easier to see exactly where things break.

## A Closing Thought

A template covers the first step for you, but everything that makes an app *yours* comes afterward — the data layer, what flows you keep or cut, and the small details of feel. Build one working thing from a template, then swap out just one part that bothers you. That single change will teach you more about the tool than anything else. Thank you for reading.
