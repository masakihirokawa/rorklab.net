The build had uploaded. All that was left was pasting the release notes and sending the update for review. Then a red warning appeared near the release notes field, and I couldn't move forward.

What I'd pasted was a memo written for my internal testers: every bug fixed, every screen touched, every odd behavior I'd noticed. It was a good memo for me. It was far too long for a store field.

Here's the thing to know up front: **Google Play's "What's new in this release" text accepts 500 characters per language.** The limit applies to each language separately, so if you've added Japanese and English, one language going over is enough to stall the whole release.

I wrote this for anyone updating a Rork or Expo app on Google Play for the first time who has stalled one step before the submit button, so you can see where to look and what to change. Screen names and limits are as of November 2026; I checked them against Google's help page, [Prepare and roll out a release](https://support.google.com/googleplay/android-developer/answer/9859348).

The first row is by far the most common. The second one, the unclosed tag, is the one that eats time: no amount of recounting fixes it.

## What the 500-character limit actually applies to

The Play Console takes release notes in a single field, with each language wrapped in a tag. For Japanese and English it looks like this:

```text
<ja-JP>
・壁紙の読み込みが速くなりました
・一部の端末で起動しない不具合を修正しました
</ja-JP>
<en-US>
- Wallpapers now load faster
- Fixed a crash on launch on some devices
</en-US>
```

The 500-character limit applies to the content inside each pair of tags. Three things I got wrong at first:

**Misconception 1: 500 characters across all languages.** It's per language. Adding languages doesn't shrink your budget for each one, but it does mean more blocks to check.

**Misconception 2: Japanese is counted in bytes, so it's at a disadvantage.** The limit is in characters, not bytes. Japanese usually fits more easily; when I translate the same notes, it's the English block that overflows first.

**Misconception 3: it's the same limit as the App Store.** App Store Connect's "What's New in This Version" is a separate field with its own limit of 4,000 characters (see Apple's [Platform version information](https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information)). Text that went through fine on iOS can still stop you on Play.

If you're unsure which to write first, I'd suggest **making the 500-character Play version the master copy and pasting that into the App Store**. Squeezing long text into a short field is painful; putting short text into a long field never causes trouble.

## Keep the long memo, write the store version separately

My first instinct was to trim the long memo. It went badly. Every cut felt like losing something important, and I stalled just short of 500.

What I do now is keep the long memo as a memo and write the store text from scratch:

1. Save the long memo as a file. Don't throw it away.
2. List only what users can see, one feature per line.
3. Count characters per language and stay comfortably under 500.
4. Save the short version too, so next time you just paste it.

Side by side, the difference is obvious:

```text
# Before (the tester memo pasted as-is, excerpt)
- Raised ImageCache LRU from 64 to 128 to cut reloads on low-memory devices
- Fixed SettingsScreen button layout (right edge clipped on Pixel devices)
- Fixed launch crash (NullPointer on some Android 10 devices)
- Cleaned up logging, removed debug-build instrumentation
```

```text
# After (what goes in the store)
- Wallpapers now load faster
- Adjusted button positions on the settings screen
- Fixed a crash on launch on some devices
```

What disappeared were the cache numbers, the class names, and the logging cleanup. All of it mattered to me as the person who fixed things. A reader only wants to know what changed and what got fixed. I also leave out device models and OS versions unless people had been writing in about that exact bug.

## Count before you paste

It's kinder to your nerves to count first than to find out from a red warning at night. This Python script reads either one file per language or a single file in the Play Console's tagged format, using only the standard library. (Its printed messages are in Japanese, since that's how I run it; the logic is the same.)

```python
# check_release_notes.py
# Usage:
#   python3 check_release_notes.py notes/ja-JP.txt notes/en-US.txt   (one file per language)
#   python3 check_release_notes.py notes/play_console.txt            (one file with <ja-JP>…</ja-JP> tags)
import re
import sys
import unicodedata

LIMIT = 500   # Google Play limit per language
MARGIN = 30   # cushion for differences in how the console counts
TAG = re.compile(r"<([a-z]{2,3}(?:-[A-Za-z0-9]+)*)>(.*?)</\1>", re.S)
broken = False  # problems found before counting, such as unclosed tags

def blocks(path):
    global broken
    raw = open(path, encoding="utf-8").read().replace("\r\n", "\n")
    found = TAG.findall(raw)
    if found:
        rest = TAG.sub("", raw).strip()
        if rest:
            print(f"{path}: text outside tags (unclosed tag?) -> {rest[:30]!r}")
            broken = True
        return [(lang, body.strip()) for lang, body in found]
    if re.search(r"</?[a-z]{2,3}(-[A-Za-z0-9]+)*>", raw):
        print(f"{path}: unclosed language tag")
        broken = True
        return [("?", raw.strip())]
    return [(path, raw.strip())]

ng = False
for path in sys.argv[1:]:
    for lang, text in blocks(path):
        n = len(unicodedata.normalize("NFC", text))
        risky = any(c in text for c in ("‍", "️"))
        if n > LIMIT:
            status = "over"
        elif n > LIMIT - MARGIN:
            status = "tight"
        else:
            status = "OK"
        note = " (joined emoji found; the console may count differently)" if risky else ""
        print(f"{lang}: {n} chars {status}{note}")
        ng = ng or status != "OK"

sys.exit(1 if (ng or broken) else 0)
```

Here's what it printed on my machine (Python 3.10) when I left the internal lines in the English file:

```text
$ python3 check_release_notes.py notes/ja-JP.txt notes/en-US.txt
notes/ja-JP.txt: 59 chars OK
notes/en-US.txt: 589 chars over
$ echo $?
1
```

Give it a file where the Japanese tag was never closed, and it reports that before any counts:

```text
$ python3 check_release_notes.py notes/broken.txt
notes/broken.txt: text outside tags (unclosed tag?) -> '<ja-JP>\n・壁紙の読み込みが速くなりました\n・設定画面'
en-US: 121 chars OK
```

A few notes on why it's written this way:

- It converts Windows line endings (CRLF) to LF before counting; otherwise each line break counts as two characters.
- `unicodedata.normalize("NFC", …)` merges characters that were typed as a base letter plus a separate combining mark, so they count as one.
- Emoji built from several joined characters, such as a family emoji, count as more than one with Python's `len()`. I haven't been able to confirm how the Play Console counts them, so the script only flags them and keeps a 30-character margin.
- It exits non-zero, so if you drop it into CI or a pre-submit script, an overflow or an unclosed tag stops you early.

## The second trap: an unpublished draft release

The same day I hit another wall: I couldn't create a new release. The cause was an old draft release I'd started and never published. A leftover draft can block the way to a new one.

I didn't delete it. I opened the draft and swapped in this build and these release notes, and that got me through. If you aren't sure a draft is safe to delete, editing it is the safer move.

Looking back, I hadn't created that draft by hand at all. When I sent the Android build with EAS Submit, `releaseStatus` under `submit` in eas.json was set to `draft`, so every submission landed in the Play Console as a draft release (field names as of November 2026; see Expo's [Configuration with eas.json](https://docs.expo.dev/eas/json/)).

```json
{
  "submit": {
    "production": {
      "android": {
        "track": "production",
        "releaseStatus": "draft"
      }
    }
  }
}
```

Receiving builds as drafts isn't bad in itself. It lets you paste the release notes in the Play Console and publish from there. The trouble starts when you send the next build without clearing the last draft, and you can no longer tell which one is current. My rule now: on any day I send a draft with EAS Submit, I paste the notes and publish it in the Play Console that same day.

Separately, if you try to create a release through the API before the app has ever been published, you'll get `Only releases with status draft may be created on draft app`. That has nothing to do with character counts. Send the first release as a draft and publish it by hand in the Play Console.

## What I keep next to me on submission day

- A long memo for me and a short, per-language version for the store, as separate files
- A script run across every language, checking both counts and unclosed tags, before pasting
- If EAS Submit sends drafts, publishing or clearing that draft the same day
- A check the day before for any leftover draft release in the Play Console

**Long records are for me; short text is for the user.** I try to hold that line even when I'm tired on submission night.

Start with your current release: go through the update notes line by line, keep only what users will see, save that short version in a tagged file, and run it through the script once. That's where I started too.
