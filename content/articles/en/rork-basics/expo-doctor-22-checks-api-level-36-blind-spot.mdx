Yesterday evening I was going through my published Android apps, recounting the targetSdkVersion of each one. Google Play's API level 36 requirement lands tomorrow, and when you are an indie developer carrying several apps at once, memory is not a reliable inventory system.

After the manual pass, I ran `npx expo-doctor` as a final sanity check. Everything came back green.

I almost stopped there. Then I paused, because I could not answer a simple question: green on what, exactly?

I had never read the actual list of checks expo-doctor runs. It is all sitting in the published package, so I opened it. What I found about the deadline was not what I expected.

I wrote this the day before the deadline, on August 30, and came back to it on November 21 with expo-doctor 1.21.8, retracing every step. The deadline and the extension window have both passed since then. What the green means has not changed, and if anything, I suspect it is easier to over-trust now that the deadline is behind us.

## The 22 checks registered in expo-doctor 1.20.4

I wanted to inspect the package without installing anything into a project, so I pulled the tarball straight from the npm registry.

```bash
META=$(curl -s https://registry.npmjs.org/expo-doctor)

echo "$META" | node -e "
let s=''; process.stdin.on('data',d=>s+=d).on('end',()=>{
  const j=JSON.parse(s); const v=j['dist-tags'].latest;
  console.log('latest =', v);
  console.log('tarball =', j.versions[v].dist.tarball);
});"
# latest  = 1.20.4
# tarball = https://registry.npmjs.org/expo-doctor/-/expo-doctor-1.20.4.tgz

curl -sL https://registry.npmjs.org/expo-doctor/-/expo-doctor-1.20.4.tgz -o expo-doctor.tgz
tar xzf expo-doctor.tgz
```

`package/build/index.js` is a single 984 KB bundle, and every check sits in it as a class. One command pulls out the class names, their descriptions, and the SDK version range each one applies to.

```bash
node -e "
const s = require('fs').readFileSync('package/build/index.js', 'utf8');
const re = /class\s+(\w+Check\w*)\s*\{description=\"([^\"]+)\";sdkVersionRange=\"([^\"]*)\"/g;
let m;
while ((m = re.exec(s))) console.log(m[1].padEnd(46), m[3].padEnd(20), m[2]);
"
```

Reading down the list, the shape becomes obvious. Almost all of it is a health check on your dependency tree and project layout: package versions, config file syntax, duplicates, lock files. As a tool for confirming your working copy is not quietly broken, it is very good at its job.

And exactly one of those 22 checks touches store requirements at all.

## Only one check looks at the store, and its threshold is from 2024

Pull out the definition of `StoreCompatibilityCheck` and the constants it judges against are right there in plain text.

```js
// extracted from package/build/index.js (expo-doctor 1.20.4; minified names change between releases)
u.PLAY_STORE_MINIMUM_REQS = {
  effectiveDate: "August 31 2024",
  AndroidSdkVersion: 34,
  ExpoSdkVersion: 50
};
```

The effective date is 31 August 2024 and the threshold API level is 34. That is Google Play's requirement from two years ago, not the API level 36 requirement that takes effect tomorrow, 31 August 2026.

The logic follows from the constant. A warning is raised only when `targetSdkVersion` reads below 34, so 34, 35, and 36 are all treated as fine. An app still sitting on targetSdkVersion 35 gets a green result from expo-doctor today.

For a CNG project with no android directory, the check falls back to the `android.targetSdkVersion` value in the `expo-build-properties` plugin, and if that is absent, to whether the Expo SDK version is 50 or higher. On SDK 57 that branch passes without hesitation.

The name is plural, but the only constant it consults is `PLAY_STORE_MINIMUM_REQS`. I could not find any App Store equivalent in the bundle. Minimum iOS version and Xcode requirements live outside these 22 checks entirely, so if you ship to both App Store and Google Play, read this check as covering one of them.

I do not read this as a defect so much as a question of scope. expo-doctor is built to validate the integrity of your project, not to track shifting store policy deadlines. Still, given the name and the shape of the output, I doubt I am the only person who has quietly treated it as a pre-submission gate.

## November's 1.21.8 still says 34

Back in August I assumed someone would bump the constant soon. By November, npm's `latest` tag had moved to 1.21.8, so I reopened the bundles side by side. These few lines do the comparison:

Google Play, meanwhile, has moved on. As of November 2026, the official [target API level requirements](https://developer.android.com/google/play/requirements/target-sdk) page says:

- From August 31, 2026, new apps and app updates must target Android 16 (API level 36) or higher (Wear OS and Android Automotive OS need API 35; Android TV and Android XR need API 34)
- Existing apps must target API 35 or higher to remain available to new users on devices running a newer Android than the app targets
- Developers who needed more time could request an extension to November 1, 2026

So in late November, even the extension window is closed. Only expo-doctor's threshold is still sitting two years back.

## When the value in build.gradle never gets read

Digging one level deeper, I found that in projects with an android directory the check often stops even earlier. Here is the regular expression it uses to read the value.

```js
const E = /^\s*targetSdkVersion\s*=\s*(?:Integer\.parseInt\(findProperty\('android\.targetSdkVersion'\)\s*\?:\s*'(\d+)'\)|'(\d+)')/m;
const w = i.match(E)?.[1];   // only the first capture group is read
```

There are two capture groups. The first covers the `Integer.parseInt(findProperty(...) ?: '35')` form; the second covers a plain quoted literal such as `targetSdkVersion = '35'`. The consuming line reads only the first one. So when the value is written as a plain quoted literal, the regex matches but the extracted value comes back `undefined`.

I copied the same constant and the same expression into a standalone script and ran a handful of spellings through it.

```js
// check-store-gate.mjs
const PLAY_STORE_MINIMUM_REQS = { AndroidSdkVersion: 34 };
const TARGET_SDK_RE =
  /^\s*targetSdkVersion\s*=\s*(?:Integer\.parseInt\(findProperty\('android\.targetSdkVersion'\)\s*\?:\s*'(\d+)'\)|'(\d+)')/m;

function judge(gradleText) {
  const raw = gradleText.match(TARGET_SDK_RE)?.[1];
  const value = raw ? parseInt(raw, 10) : undefined;
  const flagged = !!(value && value < PLAY_STORE_MINIMUM_REQS.AndroidSdkVersion);
  return { matched: TARGET_SDK_RE.test(gradleText), value, verdict: flagged ? 'warns' : 'silent' };
}

const samples = [
  ["targetSdkVersion = '33'", "ext {\n  targetSdkVersion = '33'\n}"],
  ["targetSdkVersion = '35'", "ext {\n  targetSdkVersion = '35'\n}"],
  ['targetSdkVersion = 35',   'ext {\n  targetSdkVersion = 35\n}'],
  ["parseInt(... ?: '33')",   "ext {\n  targetSdkVersion = Integer.parseInt(findProperty('android.targetSdkVersion') ?: '33')\n}"],
  ["parseInt(... ?: '35')",   "ext {\n  targetSdkVersion = Integer.parseInt(findProperty('android.targetSdkVersion') ?: '35')\n}"],
  ['(no ext block)',          'apply plugin: "expo-root-project"'],
];

for (const [label, text] of samples) {
  const r = judge(text);
  console.log(label.padEnd(26), 'matched=' + String(r.matched).padEnd(6),
              'value=' + String(r.value).padEnd(10), r.verdict);
}
```

Run on Node.js 22.23.2, this is what came back.

Writing `targetSdkVersion = '33'` produces no warning at all. The only spelling that yields a usable value is the `Integer.parseInt(findProperty(...))` form.

I then pulled the SDK 57 bare template, `expo-template-bare-minimum@57.0.20`, and looked at its `android/build.gradle` directly. There is no `targetSdkVersion` entry in the `ext` block at all. Line 94 of `android/app/build.gradle` reads `targetSdkVersion rootProject.ext.targetSdkVersion`, and that value is resolved by the `expo-root-project` Gradle plugin. In that layout there is simply no string for the regex to land on.

So on a current standard SDK setup, `StoreCompatibilityCheck` finds the android directory, fails to read a value, and passes. The green was inevitable. In November I also opened the SDK 58 template (`expo-template-bare-minimum@58.0.35`); its root `android/build.gradle` ends with `apply plugin: "expo-root-project"` in exactly the same shape.

Continuous Native Generation projects without an android directory have the same hole in a different place. If `expo-build-properties` says `targetSdkVersion: 35`, the check only asks whether that is below 34, so it passes.

## Finding the values it never reads, in your own project

To check this against my own projects, I wrote a small script. The goal is to put "the value expo-doctor read" next to "where the value that actually reaches the build comes from", on one screen, with no dependencies.

```js
// targetsdk-gap.mjs - compare what expo-doctor reads with where the build value comes from
// usage: node targetsdk-gap.mjs <project root> [required API level=36]
import fs from 'node:fs';
import path from 'node:path';

const root = path.resolve(process.argv[2] ?? '.');
const required = Number(process.argv[3] ?? 36);
const read = (p) => (fs.existsSync(path.join(root, p)) ? fs.readFileSync(path.join(root, p), 'utf8') : null);

// Same regex and same capture group as StoreCompatibilityCheck in expo-doctor 1.21.8
const DOCTOR_RE =
  /^\s*targetSdkVersion\s*=\s*(?:Integer\.parseInt\(findProperty\('android\.targetSdkVersion'\)\s*\?:\s*'(\d+)'\)|'(\d+)')/m;

const rootGradle = read('android/build.gradle');
const appGradle = read('android/app/build.gradle');
const props = read('android/gradle.properties');
const appJson = read('app.json');

const rows = [];
if (rootGradle !== null) {
  const v = rootGradle.match(DOCTOR_RE)?.[1];
  rows.push(['value expo-doctor reads (android/build.gradle)', v ?? 'unreadable']);
} else {
  rows.push(['android/ directory', 'none (CNG)']);
}
if (appGradle !== null) {
  const line = appGradle.match(/^\s*targetSdkVersion\s+(.+)$/m)?.[1]?.trim();
  rows.push(['android/app/build.gradle refers to', line ?? 'not set']);
}
if (props !== null) {
  rows.push(['gradle.properties android.targetSdkVersion',
    props.match(/^android\.targetSdkVersion=(\d+)/m)?.[1] ?? 'not set (SDK default)']);
}
if (appJson !== null) {
  const plugins = JSON.parse(appJson).expo?.plugins ?? [];
  const bp = plugins.find((p) => Array.isArray(p) && p[0] === 'expo-build-properties');
  rows.push(['expo-build-properties android.targetSdkVersion',
    bp?.[1]?.android?.targetSdkVersion ?? 'not set']);
}

for (const [k, v] of rows) console.log(k.padEnd(48), String(v));

const explicit = rows.map(([, v]) => Number(v)).filter((n) => Number.isFinite(n));
const low = explicit.filter((n) => n < required);
console.log('-'.repeat(60));
if (low.length) console.log(`ACTION: ${low.join(', ')} is below API ${required}`);
else console.log(`No explicit value below API ${required} in config files. Confirm the effective value in the build artifact.`);
```

I ran it on Node.js 22.23.5 against the SDK 58 bare template in three variations:

```
## template as shipped
value expo-doctor reads (android/build.gradle)   unreadable
android/app/build.gradle refers to               rootProject.ext.targetSdkVersion
gradle.properties android.targetSdkVersion       not set (SDK default)
------------------------------------------------------------
No explicit value below API 36 in config files. Confirm the effective value in the build artifact.

## 35 written in gradle.properties and expo-build-properties
value expo-doctor reads (android/build.gradle)   unreadable
android/app/build.gradle refers to               rootProject.ext.targetSdkVersion
gradle.properties android.targetSdkVersion       35
expo-build-properties android.targetSdkVersion   35
------------------------------------------------------------
ACTION: 35, 35 is below API 36

## no android/ (CNG), expo-build-properties set to 35
android/ directory                               none (CNG)
expo-build-properties android.targetSdkVersion   35
------------------------------------------------------------
ACTION: 35 is below API 36
```

The second and third cases are ones where expo-doctor returns green. The script points straight at the file that still says 35.

It reads `gradle.properties` because `expo-build-properties` writes its value there as `android.targetSdkVersion` during prebuild, and the root `expo-root-project` plugin picks it up from there. If you compute the value in `app.config.js`, the script cannot see it; reading `gradle.properties` after prebuild covers that case well enough for me.

Config files are still not the final word. The value that reached the build lives in the artifact. Download the `.aab` from your EAS Build and read its manifest with [bundletool](https://developer.android.com/tools/bundletool); that is the most reliable check I know.

```bash
# Read the targetSdkVersion that actually went into an .aab
bundletool dump manifest --bundle=app-release.aab \
  --xpath=/manifest/uses-sdk/@android:targetSdkVersion
# 36 means the store will see 36
```

If this prints 35 while your config says 36, something such as a stale native folder or a plugin may be overriding the value. The troubleshooting table below is where I would go next.

## What you can silence, and what I would leave alone

While reading the bundle I found something else worth keeping: several checks respond to environment variables and to a `package.json` config block.

<table>
<thead>
<tr><th>Setting</th><th>Effect</th><th>How I use it</th></tr>
</thead>
<tbody>
<tr><td><code>EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK</code></td><td>The SDK version alignment check is never registered</td><td>Not routinely. Only for short windows with a deliberately pinned dependency</td></tr>
<tr><td><code>EXPO_DOCTOR_ENABLE_DIRECTORY_CHECK</code></td><td>Forces the React Native Directory check on or off, overriding config</td><td>Off in CI when I do not want a build depending on an external API</td></tr>
<tr><td><code>EXPO_DOCTOR_WARN_ON_NETWORK_ERRORS</code></td><td>Skips the failing exit code when every failure was a network error</td><td>Always on in CI, so a flaky connection does not stop a build</td></tr>
<tr><td><code>expo.doctor.reactNativeDirectoryCheck.exclude</code></td><td>Packages excluded from directory validation; <code>/regex/</code> strings supported</td><td>For in-house and self-authored modules</td></tr>
<tr><td><code>expo.doctor.reactNativeDirectoryCheck.listUnknownPackages</code></td><td><code>false</code> suppresses warnings for packages with no metadata</td><td>Only when the noise gets in the way</td></tr>
<tr><td><code>expo.doctor.appConfigFieldsNotSyncedCheck.enabled</code></td><td>Turns the non-CNG config sync check on or off</td><td>I leave it alone</td></tr>
</tbody>
</table>

The `EXPO_DOCTOR_WARN_ON_NETWORK_ERRORS` behaviour is nicely bounded once you read it. It counts the failing checks whose cause was a network error, and only skips the failing exit when that count equals the total number of failures. If even one non-network failure is mixed in, the run fails normally. That is why it is safe to leave on in CI.

`EXPO_DOCTOR_SKIP_DEPENDENCY_VERSION_CHECK` is the one I avoid making permanent. With it set, the check is not registered at all and you get a single log line saying it has been disabled. The fact is recorded, but the version of me who opens that repository three months from now is not guaranteed to read the log.

## Which tool vouches for what

In August I had quietly filed expo-doctor under "final pre-submission check", and I came close to moving on to the release steps on the strength of that green. I stopped by luck. Had I not, the first warning would have been the Play Console upload screen. Since then I keep my checks sorted by what each one actually vouches for.

## Three misreadings worth correcting

**"Updating expo-doctor will make it check API 36."** Release 1.21.8, published November 11, still uses API 34. Upgrading does not close this gap.

**"I requested an extension, so I am fine until the end of the year."** The extension on the official requirements page ran to November 1, 2026. In late November, a build below 36 cannot go out as a new app or as an update.

**"Staying on 35 will get my existing app pulled from the store."** The official wording is that existing apps targeting API 35 or higher remain available to new users. The app does not disappear; what you lose is the ability to ship the next update until you move to 36. The painful version of this is discovering it on the day you need to push an urgent fix.

If you do one thing today, I would suggest this: download your most recent release `.aab` and read its targetSdkVersion with `bundletool dump manifest`. It takes a few minutes, and seeing that number next to expo-doctor's green makes the boundary of what the green covers feel concrete.

Less a case of doubting the tool, more a case of my having misread what it was responsible for. I am still a little relieved that I noticed the day before the deadline rather than the day after.
