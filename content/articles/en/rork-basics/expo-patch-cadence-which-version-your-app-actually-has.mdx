One of my apps had been sitting with a slow-startup review for a while. When I heard that Expo had shipped a patch fixing a startup-time regression, I opened package.json expecting a quick win.

It said `"expo": "~57.0.9"`. A tilde, so patches come along automatically — that was my assumption. I rebuilt without changing anything.

Nothing improved. The build was still on 57.0.9, nine patches behind.

I knew the range syntax well enough to recite it, and had never once checked what it actually resolves to in a project that was already running. As an indie developer juggling several apps at once, an assumption like that can sit undisturbed for months. This is what I found when I ran the checks properly.

## Nine patches in thirty days

Before anything else, it helps to know how fast patches arrive. The npm registry stores publish timestamps, so you can ask it directly.

```bash
npm view expo time --json
```

Nine releases between 29 July and 28 August. Thirty days, so roughly one patch every three days.

The practical consequence is that a patch number you noted down a few days ago is quite likely no longer the newest one. If you carry a number over from a blog post, a changelog you skimmed last week, or your own notes, your starting assumption may already be stale. Ask the registry each time instead.

## The range in package.json does not decide what you get

Next, what does each range style actually resolve to? I made an empty project with nothing but expo in dependencies, and asked npm to generate only the lockfile.

```bash
npm install --package-lock-only
```

Five different specifiers, same day, same registry.

<table>
  <thead>
    <tr><th>Specifier in package.json</th><th>Resolved version</th></tr>
  </thead>
  <tbody>
    <tr><td><code>57.0.9</code></td><td>57.0.9</td></tr>
    <tr><td><code>~57.0.9</code></td><td>57.0.18</td></tr>
    <tr><td><code>^57.0.9</code></td><td>57.0.18</td></tr>
    <tr><td><code>57.0.x</code></td><td>57.0.18</td></tr>
    <tr><td><code>"*"</code> (unconstrained)</td><td>57.0.18</td></tr>
  </tbody>
</table>

Tilde and caret both landed on 57.0.18, and so did the wildcard forms. While no new minor has been published, the difference between `~` and `^` simply does not surface.

The two are not equivalent, though. A tilde allows patch updates within the minor you named, so `~57.0.9` will accept 57.0.18 but stop before 57.1.0. A caret allows minor updates too, so `^57.0.9` would happily take 57.1.0 or 57.4.2 once those exist. Right now no 57.1.x has been published, which is the only reason both rows read the same. The day the first new minor lands, a project on a caret starts pulling in changes the tilde project will not see, without anyone editing a file. That is worth knowing before you decide which one you want in a project you ship from — although, as I found out later, the `expo` package itself behaves a little differently. More on that further down.

But notice what this table is really measuring: what npm picks when it resolves from scratch. It says nothing about what happens when you run `npm install` in a project that already has a lockfile — which is every real project.

## The lockfile is what decides

So I ran the same check starting from an existing lockfile.

1. Pin `"expo": "57.0.9"` and generate the lockfile.
2. Edit package.json only, changing the range to `"expo": "~57.0.9"`.
3. Run `npm install` with the lockfile still in place.

The output:

```text
step 1, pinned lock:        57.0.9
step 2, install with lock:  57.0.9
step 3, install without:    57.0.18
```

Step 2 is the whole answer. Even with `~57.0.9` written in package.json, npm keeps 57.0.9 as long as the locked version still satisfies the range. It has no reason to move, so it doesn't.

Step 3 is the same package.json with the lockfile deleted first. Now 57.0.18 goes in. Which means that if package-lock.json is not committed to Git, your machine and your build server can install different versions of Expo from identical source. It is the same shape of problem as filenames that look identical on your Mac and differ on the build server, which I wrote about in [Sunset.png and sunset.png: one file on your Mac, two on the build server](/articles/rork-basics/asset-filename-case-mac-vs-build-server).

If you exported your code from Rork and started developing locally, check that package-lock.json made it into your first commit. If it lands in your ignore file, your dependency versions drift on every build. [Write .gitignore Before You Run git init on an Exported Rork Project](/articles/rork-basics/rork-export-gitignore-before-git-init) covers the setup.

## npm ci will tell you when they disagree

A mismatch between package.json and the lockfile gets silently reconciled by `npm install`. When you want to hear about it, use `npm ci`.

Here is the real output with the lockfile on 57.0.9 and package.json asking for `~57.0.15`:

```text
npm error code EUSAGE
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json or npm-shrinkwrap.json are in sync.
npm error Invalid: lock file's expo@57.0.9 does not satisfy expo@57.0.18
```

It stops. That refusal is exactly why build scripts and CI pipelines should use `npm ci` rather than `npm install` — failing at the point of disagreement costs far less than tracing a mystery difference days later.

When you just want to read the version currently locked, go straight to the file:

```bash
node -p "require('./package-lock.json').packages['node_modules/expo'].version"
```

Cloud build services follow the same rule. By default EAS Build installs dependencies in a lockfile-respecting mode such as `npm ci`, so a lockfile that has not moved since March produces a March build today, no matter what range sits above it in package.json. As long as the locked version still fits the range, nothing warns you, because from npm's point of view nothing is wrong. (The documentation behind this is quoted in the misconceptions section below.)

If your project uses a different package manager the file name changes but the logic does not. Yarn writes yarn.lock, pnpm writes pnpm-lock.yaml, and both resolve from the lock first and the range second. Whichever one you have, that file is the honest record of your dependency versions, and package.json is closer to a statement of intent.

## When you only want to know how far behind you are: npm outdated

Before deciding whether to upgrade, it helps to measure where you stand. The standard command for that is `npm outdated`.

```bash
npm outdated expo
```

The output has three columns: Current (what is installed in node_modules right now), Wanted (the newest version your package.json range allows) and Latest (the newest on the registry). If Current and Wanted differ, you are behind inside your own range. If Wanted and Latest differ, something newer exists outside the range.

I used to glance at the Latest column alone and relax because no big release had appeared. The gap I should have been reading was between Current and Wanted, and that is where my nine patches were hiding. Reading all three columns together is a habit that would have saved me the month.

## What to run when you do decide to upgrade

Upgrading is an explicit act. Name the version, and the lockfile updates along with it because the new specifier falls outside the locked range.

```bash
npm install expo@57.0.18
npx expo install --fix
```

The second line realigns the packages that Expo manages so they match the combination the SDK expects. Bumping expo alone and leaving everything else where it was gets you a set of versions nobody tested together.

One more thing if you keep native directories in your repository: running prebuild after an upgrade can wipe hand-edited native changes. Take an inventory before you upgrade rather than after — [Find the native edits expo prebuild will erase before you upgrade to SDK 57](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit) walks through it.

The ordering lesson generalises. Before you go hunting through your own code for a memory problem, confirm which versions you are actually running, which is the same argument I made in [Count your worklets before you start deleting your own code](/articles/rork-dev/hermes-v1-worklet-memory-count-before-blaming-your-code).

What re-measuring taught me is that the number I trusted was always one I had written down somewhere, not one I had just asked the registry or the lockfile for. The rule I keep now is short:

**Trust the recorded line, not the range you wrote.**

## Three misconceptions, checked against the docs

**"A caret will drag me onto the next SDK."** It won't. npm's caret never moves the left-most non-zero digit, and Expo ships each SDK as a new major version of the `expo` package (57 → 58). So `^57.0.9` can never resolve to SDK 58, which is why the table above stops at 57.0.33. The tilde-versus-caret distinction I described earlier is correct semver, but for the `expo` package itself minor releases are rare, so the practical gap is small. Moving to a new SDK only ever happens when you change the version yourself.

**"Current in `npm outdated` is the lockfile version."** The npm documentation defines Current as what is installed, Wanted as the highest version satisfying the range in package.json, and Latest as the version tagged `latest` on the registry. Run it before node_modules exists and Current reads MISSING. To read the locked version, use the `node -p` one-liner from earlier, or `npm ls expo --package-lock-only`.

**"The cloud build always picks up the newest patch."** Expo's own documentation (the Immutable lockfiles note under Cache dependencies) says EAS Build installs Node packages with your package manager's immutable-lockfile mode by default — `npm ci`, `yarn --frozen-lockfile` and so on. An old lockfile gives you an old build; a lockfile that disagrees with package.json stops the build at the install step. There is an `EAS_NO_FROZEN_LOCKFILE` variable to turn that off. I leave it on.

## A symptom-first troubleshooting table

Version drift rarely announces itself as version drift. Start from the row that matches what you are seeing.

<table>
  <thead>
    <tr><th>Symptom</th><th>Likely cause</th><th>How to check</th><th>Fix</th></tr>
  </thead>
  <tbody>
    <tr><td>A bug fixed upstream is still there despite a tilde range</td><td>The lockfile still points at the old version</td><td><code>npm ls expo</code></td><td><code>npm install expo@&lt;version&gt;</code></td></tr>
    <tr><td>Fixed on your machine, still broken in the built app</td><td>package-lock.json is not committed, or is ignored</td><td><code>git ls-files package-lock.json</code> prints nothing</td><td>Commit the lockfile and remove it from .gitignore</td></tr>
    <tr><td>The cloud build fails while installing dependencies</td><td>package.json was edited but the lockfile was not regenerated</td><td>Run <code>npm ci</code> locally and look for EUSAGE</td><td>Run <code>npm install</code>, commit both files</td></tr>
    <tr><td>Version warnings at startup or build time after bumping expo</td><td>Expo-managed packages left on an older combination</td><td><code>npx expo install --check</code></td><td><code>npx expo install --fix</code></td></tr>
    <tr><td><code>npm outdated</code> shows Current as MISSING</td><td>node_modules has not been created yet</td><td><code>ls node_modules/expo</code></td><td><code>npm ci</code> to install exactly what is locked</td></tr>
  </tbody>
</table>

The third row is the one that cost me the most time. I kept reading my app code for a cause, and it took me far too long to notice that the failing line in the build log came from npm, not from Expo.

According to the Expo CLI docs, `npx expo install --check` exits non-zero in CI when anything is out of line. One extra line before your build catches a mismatched set early:

```bash
CI=1 npx expo install --check
```

## Where people tend to get stuck next

If checking versions tempts you into bumping the SDK as well, Expo Go on your phone may refuse to open the project. I wrote up how to tell a client mismatch from a project problem in [three places to look when Expo Go says your project is incompatible](/articles/app-dev/expo-go-project-incompatible-error-check-client-version-before-project).

The other one is that an SDK bump can quietly move the Xcode and package-manager versions on the build image too, depending on how eas.json is written. [What moves on SDK-bump day when eas.json has no image set](/articles/app-dev/eas-json-image-alias-auto-what-moves-on-sdk-bump) explains which line controls that.

## Start here today

Close package.json and open package-lock.json instead. Read one line: the version under node_modules/expo. That single line tells you whether your app is at the front of the queue or nine patches behind it.

I never checked, and left a fixed regression sitting in one of my indie developer builds for a month. If this saves you that detour, it was worth writing down.
