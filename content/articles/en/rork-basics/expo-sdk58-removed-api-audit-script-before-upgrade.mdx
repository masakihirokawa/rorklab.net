My first reaction to the SDK 58 changelog was simply that it is long.

Removals, behavior changes, deprecations, each in its own section. By the time I reached the end, I could no longer say what the first section had contained. Understanding the notes is one task. Finding where they apply to your own project is another, and it is still waiting when you finish reading.

So this time I reversed the order. I pulled out only the items that can be searched for, turned them into a small script, and ran it against the project first. Judgment comes after the list exists.

Expo SDK 58 was released on October 15, 2026, according to the expo.dev changelog, and it moves React Native from 0.86 to 0.88. A project exported from Rork is an ordinary Expo project underneath, but as far as I could confirm, there is no announcement yet about when Rork itself will support SDK 58. Everything below is about upgrading an exported repository on your own.

## Sort the items into three bins first

Listing the changelog as it stands does not make a checklist. I sorted by what you must do about each one.

- **REMOVED**: the build or the type check stops if it remains. Highest priority
- **BEHAVIOR**: it still runs, but the result differs. A human has to decide if that matches intent
- **DEPRECATED**: it works today. Fix it next time, not on upgrade day

The changelog also says some deprecated StatusBar props are removed, but I could not pin down which ones. The script includes `networkActivityIndicatorVisible` purely as an example, and you should check the official list to see whether it applies.

## The full audit script

It runs on Node.js alone. SDK 58 expects Node 22.13 or later on the 22 line, 24.3 or later on the 24 line, or Node 26 and above; the odd-numbered 23 and 25 are not supported. There are no dependencies.

```js
// audit-sdk58.mjs — SDK 58 へ上げる前に、プロジェクト内の「消える・変わる」API を一覧にする
// 使い方: node audit-sdk58.mjs [プロジェクトのパス]
import { readdirSync, readFileSync, existsSync, statSync } from 'node:fs';
import { join, relative, extname, resolve } from 'node:path';
import { fileURLToPath } from 'node:url';

const SELF = fileURLToPath(import.meta.url); // 自分自身は検査対象から外す

const root = process.argv[2] ?? '.';
const SKIP = new Set(['node_modules', '.git', 'ios', 'android', '.expo', 'dist']);
const EXT = new Set(['.ts', '.tsx', '.js', '.jsx', '.mjs']);

// level: REMOVED=消える／BEHAVIOR=挙動が変わる／DEPRECATED=非推奨（今は動く）
const RULES = [
  { id: 'rn-interactionmanager', level: 'REMOVED', re: /\bInteractionManager\b/, why: 'RN から削除。requestAnimationFrame か、描画後に走らせたい処理を useEffect 側へ' },
  { id: 'rn-touchable-root', level: 'REMOVED', re: /import\s*\{[^}]*\bTouchable\b[^}]*\}\s*from\s*['"]react-native['"]/, why: 'Touchable のルート export が削除。Pressable へ' },
  { id: 'rn-nativemethods', level: 'REMOVED', re: /\bNativeMethods\b/, why: 'NativeMethods 型が削除。ViewInstance など instance 型へ' },
  { id: 'rn-modal-animated', level: 'REMOVED', re: /<Modal\b[^>]*\banimated\b/, why: 'Modal の animated prop が削除。animationType を使う' },
  { id: 'rn-deep-import', level: 'REMOVED', re: /from\s*['"]react-native\/Libraries\//, why: 'Strict TypeScript API が既定。Libraries/* の deep import は型エラー' },
  { id: 'rn-statusbar-ios-props', level: 'REMOVED', re: /<StatusBar\b[^>]*\bnetworkActivityIndicatorVisible\b/, why: 'StatusBar の非推奨 prop の一部が削除対象。この prop が該当するかは公式の変更履歴で確認（ここは例）' },
  { id: 'fs-file-write', level: 'BEHAVIOR', re: /\.write\(/, why: 'expo-file-system の File.write() は非同期に。同期のままなら writeSync()（File 以外の .write も拾うので目視）' },
  { id: 'fs-md5', level: 'DEPRECATED', re: /\.md5\b/, why: 'File.md5 は非推奨。File.digest() へ' },
  { id: 'sqlite-libsql', level: 'REMOVED', re: /\b(syncLibSQL|libSQLOptions|useLibSQL)\b/, why: 'expo-sqlite の libSQL 対応が削除' },
  { id: 'rn-imagebackground', level: 'DEPRECATED', re: /\bImageBackground\b/, why: '非推奨。View ＋ 絶対配置の Image へ' },
  { id: 'router-withlayoutcontext', level: 'DEPRECATED', re: /\bwithLayoutContext\b/, why: '非推奨。integrateWithRouter へ' },
  { id: 'notif-foreground', level: 'BEHAVIOR', re: /from\s*['"]expo-notifications['"]/, why: 'フォアグラウンド通知が既定で表示される。意図した挙動か確認' },
  { id: 'nodeenv-test', level: 'BEHAVIOR', re: /NODE_ENV=test/, why: 'NODE_ENV=test で expo start すると .env.development を読む' },
];

function* walk(dir) {
  for (const name of readdirSync(dir)) {
    if (SKIP.has(name)) continue;
    const p = join(dir, name);
    const st = statSync(p);
    if (resolve(p) === SELF) continue;
    if (st.isDirectory()) yield* walk(p);
    else if (EXT.has(extname(name)) || name === 'package.json') yield p;
  }
}

const hits = [];
for (const file of walk(root)) {
  const lines = readFileSync(file, 'utf8').split('\n');
  lines.forEach((line, i) => {
    for (const r of RULES) if (r.re.test(line)) hits.push({ r, file: relative(root, file), line: i + 1, text: line.trim() });
  });
}

// ネイティブ側の確認（CNG でない場合に効く）
const notes = [];
if (existsSync(join(root, 'ios'))) notes.push('ios/ があります。CNG なら削除して再生成、手書き管理なら AppDelegate のシーン対応（SceneDelegate.swift）を確認');
if (existsSync(join(root, 'android'))) notes.push('android/ があります。R8 が release で既定オンになるため keep ルールを確認');

const order = { REMOVED: 0, BEHAVIOR: 1, DEPRECATED: 2 };
hits.sort((a, b) => order[a.r.level] - order[b.r.level] || a.file.localeCompare(b.file));
for (const h of hits) console.log(`[${h.r.level}] ${h.file}:${h.line}  ${h.r.id}\n    ${h.text}\n    → ${h.r.why}`);
const c = (l) => hits.filter((h) => h.r.level === l).length;
console.log(`\n集計: REMOVED ${c('REMOVED')} / BEHAVIOR ${c('BEHAVIOR')} / DEPRECATED ${c('DEPRECATED')}`);
notes.forEach((n) => console.log('NOTE: ' + n));
process.exit(c('REMOVED') > 0 ? 1 : 0);
```

A few notes on the design choices follow.

1. **The rules are an array, and each `why` names the replacement.** The output tells you the next action as you read it, and adding a rule is one line
2. **The exit code depends on whether any REMOVED item exists.** If you later put it in CI, "stop unless REMOVED is zero" works as is
3. **It ends with a note about `ios/` and `android/`.** Native code cannot be seen by a text search, so the script only says "this needs a separate check"

## Three pitfalls I only found by running it

### 1. The audit script flagged itself

The first run reported REMOVED 10, BEHAVIOR 3, DEPRECATED 3. The fixture only contained 8, 1, and 2. The difference was the script sitting in the project root: its rules contain words like `InteractionManager` and `NativeMethods` as strings, and it reacted to its own source.

The fix is two lines. Take the script's own path from `import.meta.url` and skip it during the walk. What tripped me for a moment was that `walk()` was handed relative paths, so a plain string comparison never matched; resolving to an absolute path first produced the expected 8, 1, and 2.

**Never leave an audit tool where it audits itself. If you must, exclude it explicitly.** I intend to carry that single line into my other checks.

### 2. The count is not the number of fixes

Lines 1 and 5 of `app/index.tsx` are the same `InteractionManager`, one hit for the import and one for the usage. What you actually fix is a single usage, with the import removed along the way. Treat the count as a rough guide and read the output grouped by file.

### 3. `.write(` also catches other writes

`fs-file-write` reacts to any `.write(` on a line, not only `File`. Streams and your own classes match too. This is the one rule I left to eyeball filtering, and the "check by eye" wording in its `why` keeps that assumption visible in the output.

## Run time, and a check for false alarms

On the fixture, the run took 0.05 seconds on all three tries, using about 48MB of memory. For a sanity check I also pointed it at this site's own repository (79 TypeScript and JavaScript files, a Next.js project unrelated to RN). It finished in 0.11 seconds with 0, 0, and 0 hits, so it stays quiet where nothing applies. I wrote "thirty minutes" earlier, but the script itself finishes in an instant; the time goes into reading the output and deciding.

My recommendation is to run it the day before the upgrade and save the output. On the day, you only watch that list shrink.

## What this approach cannot see

Here is the boundary. The script finds only things whose names appear as strings.

- **Aliased imports** such as `import * as RN from 'react-native'` followed by `RN.InteractionManager` still match on the name, but anything reassigned to another variable is out of reach
- **Third-party libraries using removed APIs internally** are invisible, because `node_modules` is excluded. A dependency calling a removed API will not show up here
- **Native code** (the iOS scene life cycle, R8 on by default for Android) is not searchable at all. SDK 58 changes build behavior there, so it needs its own check

Covering the last two comes down to upgrading and verifying with a build and a real device. The script only widens the part you can say "I checked this myself" about, before that step.

## Native side, and what to check next

The changelog describes the upgrade steps like this.

```bash
# Align dependencies with SDK 58
npx expo install expo@^58.0.0 --fix

# Check for known issues
npx expo-doctor@latest
```

If you use Continuous Native Generation, delete the `android` and `ios` directories so they regenerate on the next build. If you manage them by hand, you need `npx pod-install` and the native project upgrade changes. Development builds must be recreated after the upgrade.

For Expo Go, the SDK 58 version is expected in the stores "within a few weeks." Until then `npx create-expo-app` creates SDK 57 projects. To start on SDK 58 now, add `--template default@sdk-58` and run it in a development build.

Other articles on this site cover what comes next.

- When AppDelegate stops on the scene life cycle, see [the three lines to check when prebuild stops at "requires the standard Expo SDK 57 Swift AppDelegate"](/articles/app-dev/expo-enable-scene-support-prebuild-standard-appdelegate-error)
- For the numbers worth measuring before R8 becomes the default, see [four numbers to measure before R8 becomes the default](/articles/rork-dev/expo-sdk58-r8-default-android-baseline-measurement)
- For finding native changes that prebuild will wipe, see [auditing native changes that prebuild removes before moving to SDK 57](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit)

## The procedure

1. Put the script outside the project or keep the self-exclusion, then run `node audit-sdk58.mjs <path>`
2. Read REMOVED grouped by file and count the places to fix, not the hits
3. Go through BEHAVIOR one at a time against your intent. For notifications, check on a real device whether any screen would be bothered by a foreground banner
4. Leave DEPRECATED as a note for the next opportunity
5. After fixing, run it again until REMOVED reaches zero, then move on to `npx expo install expo@^58.0.0 --fix`

As an indie developer, I find that shifting pre-upgrade work from reading to running makes it feel lighter. With the list in hand, the changelog stops being something to read in full and becomes something to check the list against.

The rules array can be rebuilt for SDK 59. Few of today's thirteen lines will survive, and still, having the shape ready is worth more to me than any single rule.
