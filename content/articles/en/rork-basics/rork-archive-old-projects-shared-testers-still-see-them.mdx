On the morning of November 23, I scrolled through my Rork project list and stopped halfway. There was the clone I made to try a new grid screen for my wallpaper app, the copy where I only swapped the onboarding copy, the one I used for a single evening to test a category filter — all sitting at the same height as the projects I actually open every day.

Reading the end of each name to find today's project is a small chore. Done every morning, it starts to weigh on you. Deleting them didn't feel right either; I'd lose the chance to look back at what I tried that night.

The day before, Rork's changelog had added project archiving. The one thing I'd like you to take away first: **archiving tidies your own list, not the lists of the people you shared with.** If you miss that, an old prototype can sit on a tester's screen for months.

## What shipped on November 22

The November 22 entry in the official [Changelog](https://rork.com/changelog) says:

- You archive a project from its menu, or by right-clicking it, and choosing "Archive"
- A message offers "Undo", so a wrong click can be reversed on the spot
- An archived project leaves your lists, and nothing is deleted
- It moves under the new "Archived" filter on the projects page, where "Unarchive" brings it back
- Archiving is only for you; people you share the project with still see it

That last line is the one I'd underline. Only your own list changes. The project itself, and who it is shared with, stay exactly as they were.

## The clutter comes from a good habit

Rork's own guide, "[When to clone your Rork project](https://rork.com/guides/clone-rork-project)", recommends cloning before a risky change or when you are stuck in a loop of bad generations. As an indie developer, that habit has saved me more than once.

The catch is that the habit grows the list. Even after you fold a clone's result back into the main project, the clone stays. Needing to tidy up is, in a way, a sign you've been following good practice.

I used to tell myself I'd delete them "someday." It didn't go well. When I went back to an old prototype months later, I couldn't tell from the names which copy was the last one that actually worked.

## Sort into three boxes before touching anything

These days I sort projects first:

<table>
<thead><tr><th>Box</th><th>What goes in</th><th>Why</th></tr></thead>
<tbody>
<tr><td>Keep</td><td>Anything live on a store, or opened in the last 30 days</td><td>I open these daily and want them near the top</td></tr>
<tr><td>Archive</td><td>Prototypes and clones not opened for 30+ days and not shared</td><td>Nothing is lost and it is reversible, so this is the safe default</td></tr>
<tr><td>Review sharing first</td><td>Not opened for 30+ days but shared with someone</td><td>Archiving on my side leaves it on their list</td></tr>
</tbody>
</table>

The 30-day cut-off simply matches how often I update my apps. Use 14 or 60 if that fits your rhythm better.

Keeping store-live projects out of the archive is my own rule. The changelog doesn't say how archiving relates to a published app. Leaving a list and leaving a store should be separate things, but since I haven't verified it, I'd rather keep anything I watch daily in plain sight.

## Write the list down, then decide

Deciding project by project while staring at the Rork screen makes me second-guess. So I type a tiny CSV by hand — name, last opened, shared with, on a store — which takes a few minutes:

```text
name,last_opened,shared_with,on_store
wallpaper-grid-v2,2026-11-20,,yes
wallpaper-grid-v2 (clone),2026-10-02,,no
onboarding-test,2026-09-14,tester@example.com,no
category-filter-try,2026-08-30,,no
healing-timer,2026-11-18,,no
```

This script reads that CSV and drops each row into one of the three boxes. It needs nothing beyond Python 3.

```python
import csv
import sys
from datetime import date

TODAY = date.fromisoformat(sys.argv[2]) if len(sys.argv) > 2 else date.today()
QUIET_DAYS = 30  # projects idle longer than this become tidy-up candidates

def decide(row):
    last = date.fromisoformat(row["last_opened"])
    idle = (TODAY - last).days
    shared = row["shared_with"].strip()
    if row["on_store"].strip().lower() == "yes":
        return idle, "keep", "live on a store, stays in the list"
    if idle < QUIET_DAYS:
        return idle, "keep", "still being worked on"
    if shared:
        return idle, "review sharing first", f"still on {shared}'s list"
    return idle, "archive", "reversible tidy-up is enough"

with open(sys.argv[1], newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))

for row in sorted(rows, key=lambda r: r["last_opened"]):
    idle, verdict, reason = decide(row)
    print(f"{verdict:<22} {idle:>4} days  {row['name']}  ({reason})")
```

Running `python3 sort_projects.py projects.csv 2026-11-23` printed:

```text
archive                  85 days  category-filter-try  (reversible tidy-up is enough)
review sharing first     70 days  onboarding-test  (still on tester@example.com's list)
archive                  52 days  wallpaper-grid-v2 (clone)  (reversible tidy-up is enough)
keep                      5 days  healing-timer  (still being worked on)
keep                      3 days  wallpaper-grid-v2  (live on a store, stays in the list)
```

The checks run in the order "store → recently opened → shared" because that's the order in which mistakes hurt. Tucking away a live app is the worst; forgetting a shared tester comes next; archiving a prototype by mistake is undone with one Unarchive. The date argument lets me run the same CSV for "a month from today" and see what will become a candidate.

## Archiving, and one check afterwards

With the sorting done, I archive only the rows in the archive box:

1. On the projects page, right-click the project or open its menu
2. Choose "Archive"
3. While the "Undo" message is showing, read the name once more; if it's the main project rather than the clone, undo now
4. When finished, open the "Archived" filter and count whether it matches the archive rows in your CSV

Step 4 exists because I once got it wrong. A clone's name is nearly identical to the original, and I'd archived the original instead. Nothing was lost — Unarchive brought it back — but until I noticed, the door I use every morning was simply missing from my list.

**Do the reversible tidying first, and the irreversible steps last, one at a time.** Since I settled on that order, list-cleaning days feel much lighter.

## For shared prototypes, think about their screen first

Anything in the review-sharing-first box stays on the other person's list even after you archive it. To a tester, a finished prototype keeps looking like the latest build.

For those, I send a short note — "this prototype is done" — before archiving on my side. Whether to remove the share depends on whether they still want to look back at it. I'd rather not make something vanish from someone else's hands just to tidy my own view.

I've written more about handling testers in [the morning one of my 12 Google Play testers dropped out](/en/articles/rork-basics/google-play-12-testers-one-drops-out-14-days-restart-or-not).

## Think about deleting only after exporting

If a day comes when archiving isn't enough — before a plan change, or when you decide to let a project go — check first that your exported code rebuilds outside Rork. I've written that process up in [checking that exported code rebuilds outside Rork before a plan change](/en/articles/rork-basics/rork-export-rebuild-check-before-plan-change).

For today, try typing your list into a CSV and filling in just the "shared with" column. In my case, filling in that one column showed me there was one person I needed to message before archiving anything.
