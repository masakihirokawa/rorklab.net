One night I was rebuilding the settings screen of a wallpaper app, and when the generation finished I opened the preview on my phone. Black. No red error screen, nothing to read, nothing to point at.

What I'd like to say up front is that a black screen is not one symptom. The cause can sit in at least three places, and each one is fixed by a different person or tool. Early on I skipped that step and sent the same "it's black, please fix it" request again and again. It didn't go well. The list screen that had been working got rewritten too, and after that I couldn't even tell where things had broken.

Here is the order I follow now, so you don't have to take the same detour. The short version:

- The stall is in one of three places: device and app, rendering, or native
- A single yellow banner tells you whether it's the first half or the second half
- When you ask again, attach three lines: where it stalls and what you already checked

Error messages, screen names, and plan details below were checked against Expo's and Rork's official docs as of November 2026.

## 1. Rule out the device and app first

If scanning the QR code shows nothing at all, suspect the step before your generated code. The answer here is usually written on the Expo Go screen.

The first thing is sign-in. According to Expo's changelog (September 3, 2026), the latest Expo Go for iOS requires you to be signed in to both Expo CLI in the terminal and the Expo Go app, with the same account, before it will open a project in development. As of November 2026 the docs say this applies only to physical iOS devices: Android will follow later, and simulators and development builds are not affected. So if your black screen is on Android, look elsewhere first. I wrote up the order of checks separately:

- [Two logins to check first when Expo Go stops opening your preview](/en/articles/rork-basics/expo-go-login-both-terminal-and-app-preview-not-opening)
- [Fixing a Rork Companion preview that won't run](/en/articles/rork-basics/rork-companion-preview-not-working-fix)

The second is the SDK version. Each build of Expo Go carries exactly one Expo SDK. When the `expo` version in your project's `package.json` doesn't match it, you get "Project is incompatible with this version of Expo Go." Store builds of Expo Go can lag behind a new SDK; Expo's recommended way out is a development build rather than waiting.

The third question is simple: does fully closing the app and reopening it change anything? If it does, the problem was device state, not code. Asking the AI for a fix at this point only rewrites code that never needed touching.

## 2. Then suspect rendering

Expo's Runtime issues guide suggests that when the stack trace doesn't explain things, you go back to a working version of your code and re-apply changes one at a time. With a silent black screen, that's the approach that pays off.

As an indie developer I've tripped over the same four things in my own apps:

- A black background with black text, because a dark-theme setting only took effect on one of the two
- A component that returns `null` until data arrives, and the data never does
- A parent View with no height, so its children collapse to zero
- A splash screen that never gets dismissed, so the first screen never takes over

### Drop in a yellow banner

The fastest way to tell them apart is a temporary diagnostic component placed at the top of the screen:

```tsx
import { View, Text } from "react-native";

// Diagnostic only: checks whether content is hiding against a black background.
// Remove it once you've seen the result.
export default function DebugBanner({ label }: { label: string }) {
  return (
    <View style={{ backgroundColor: "#ffd54f", padding: 12, zIndex: 9999 }}>
      <Text style={{ color: "#000", fontWeight: "700" }}>{label}</Text>
    </View>
  );
}
```

If the yellow banner shows, the app is alive and whatever sits below it is rendering nothing. If it doesn't, the stall is more likely earlier — device or native.

Feed some state into the label and you narrow it further. Show the list's item count, or "not loaded" while it's still missing, and you can tell on the spot whether the data never arrived or arrived and wasn't drawn.

One caution: a missing banner doesn't automatically mean the stall is earlier than rendering. A full-screen `position: "absolute"` View can simply be sitting on top of it. That's why the code above sets a high `zIndex`. Only if the banner is still hidden do you move on to layer 3.

### Before and after: a splash screen that never closes

The fourth pattern is easy to miss, so here it is in code. If you call `preventAutoHideAsync()` from `expo-splash-screen` and never reach `hideAsync()`, the app can be running while the screen stays on the splash. If your splash background is black, users simply see "black and frozen."

Before: if loading throws, the ready flag never flips.

```tsx
import { useEffect, useState } from "react";
import * as SplashScreen from "expo-splash-screen";

SplashScreen.preventAutoHideAsync();

export default function App() {
  const [ready, setReady] = useState(false);

  useEffect(() => {
    (async () => {
      await loadFontsAndSettings(); // if this throws, the next line never runs
      setReady(true);
    })();
  }, []);

  useEffect(() => {
    if (ready) SplashScreen.hideAsync();
  }, [ready]);

  if (!ready) return null;
  return <MainScreen />;
}
```

After: ready is set whether loading succeeds or fails, and a failure is left on screen and in the logs. Expo's own splash-screen example also sets ready in a `finally` block.

```tsx
import { useEffect, useState } from "react";
import * as SplashScreen from "expo-splash-screen";

SplashScreen.preventAutoHideAsync();

export default function App() {
  const [ready, setReady] = useState(false);
  const [loadError, setLoadError] = useState<string | null>(null);

  useEffect(() => {
    (async () => {
      try {
        await loadFontsAndSettings();
      } catch (e) {
        console.error("Initial load failed:", e); // shows up as [error] in Rork's Logs panel
        setLoadError(String(e));
      } finally {
        setReady(true); // always dismiss the splash, success or not
      }
    })();
  }, []);

  useEffect(() => {
    if (ready) SplashScreen.hideAsync();
  }, [ready]);

  if (!ready) return null;
  if (loadError) return <DebugBanner label={`Load failed: ${loadError}`} />;
  return <MainScreen />;
}
```

Replace `loadFontsAndSettings` and `MainScreen` with your own loading code and first screen. I once spent an evening polishing styles because I was sure it was a rendering problem; looking back, I should have checked the `try / finally` around the loading code first.

### Open the logs inside Rork first

If you're stalled at rendering, you often don't need device logs at all. Rork's docs describe a **Logs** panel under **More → Code**, below the file tree. It streams whatever your app printed while running in the preview, tagged `[log]`, `[warn]`, `[error]` and so on.

With a `console.error` line like the one in the After version, the reason lands right there. And if the preview shows a visible error, the docs point you to **Fix with Rork** on the error itself as the quickest route.

## 3. Check whether the app crashes natively

No banner and no change after a reload usually means the app is dying right after launch. In that case the JavaScript side often leaves nothing behind, and the Logs panel stays quiet. Expo's documentation treats native crashes as a device-log job.

On Android, stream logs from a USB-connected device with `adb logcat`. You don't need to read everything. These three steps are how I catch just the moment of the crash:

```bash
# 1) Clear old logs, then reopen the app
adb logcat -c
# 2) Stream only error-level lines and above
adb logcat '*:E'
# 3) Or narrow to crash lines and JavaScript output
adb logcat | grep -E "FATAL EXCEPTION|AndroidRuntime|ReactNativeJS"
```

On iOS, open the Console app on a Mac, pick your device in the sidebar, start streaming, then reopen the app. Typing your app's name into the search field removes most of the noise.

If you're on Windows only, you don't have to chase the iOS side. Knowing that it crashed is already enough to word your next request.

Opening logs can feel heavy. The first time, I stared at a wall of text and froze. But you only need the few lines around the moment of the crash. Find one `FATAL EXCEPTION` or `Error` line and paste it straight into your request.

## Three misunderstandings worth correcting

**"It's black, so the AI's code must be broken."** As layer 1 showed, an unsigned Expo Go on iOS or an SDK mismatch also keeps the preview from opening. Reading the message Expo Go shows before touching code saves you a whole round trip.

**"Going back costs credits, or wipes everything."** Rork's docs say every answer is saved as a version of the whole project and that going back costs no credits (as of November 2026). The catch is **Revert**: it isn't reversible, and the versions after your target drop off the top of the history. If only the last change broke things, **Undo** is enough.

**"Send the same request enough times and it'll work."** Rork's FAQ, for an error loop, suggests three things: have Rork search the web for the error, switch to a different AI model, or revert to a working version and implement the feature again with a different approach. Repeating the same wording isn't among them.

## Undo, Revert, or Edit message

There are three ways back, and they differ in what you lose. Names follow Rork's docs as of November 2026 (the FAQ still calls this Restore).

<table>
<thead><tr><th>Action</th><th>Where it is</th><th>What happens</th><th>Choose it when</th></tr></thead>
<tbody>
<tr><td>Undo</td><td>Under the latest answer</td><td>Rolls back only the last change and removes that exchange; no confirmation dialog</td><td>The very last answer turned the screen black</td></tr>
<tr><td>Revert</td><td>Under any earlier answer</td><td>Returns to the state right after that answer; later versions leave the top of history, and it can't be undone</td><td>You know where it broke and need to go back two or more steps</td></tr>
<tr><td>Edit message</td><td>Hover one of your earlier messages</td><td>Goes back to just before that message and answers your rewritten request</td><td>You know the request itself was badly worded</td></tr>
</tbody>
</table>

My rule for choosing: **if you can say for certain the last answer caused it, Undo; if you can't, open Review changes and read the diff before you Revert.** Review changes sits in the **⋯** menu under each answer and shows every file that answer touched against the previous version. Checking whether the black-screen answer also changed layout or theme files keeps you from reverting further than you need.

## Change what you tell the AI

The wording changes with the layer you found:

- Banner visible: "The screen runs, but the list area draws nothing. Check whether it returns null before the data loads."
- Stuck on the splash: "Wrap the initial load in try / finally so hideAsync is called even if loading throws."
- No banner, and a FATAL line in the logs: paste the line and say "The app crashes on launch with this exception. List three likely causes and try the smallest change first."
- Nothing found: Undo or Revert to the last working version, then re-request changes one at a time.

"It's black" leaves the AI guessing. One sentence about which layer stalls narrows the fix a lot.

## Three lines to attach to your request

Whatever you found can go straight to the top of your prompt. This is the shape I use:

```text
Stalled at: layer 2 (rendering)
Checked: yellow banner is visible; it shows "items: not loaded"; closing and reopening changes nothing
Suspect: the list screen may return nothing before data has loaded
```

With those three lines, the fix that comes back is less likely to drift toward "rebuild everything." Without them, repeated requests can rewrite parts that were working — which is exactly what happened to me that first night.

**Before asking again, be able to say in one sentence where it stops.** I keep to that rule hardest on tired nights.
