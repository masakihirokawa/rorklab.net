One night I was rebuilding the settings screen of a wallpaper app, and when the generation finished I opened the preview on my phone. Black. No red error screen, nothing to read, nothing to point at.

What I'd like to say up front is that a black screen is not one symptom. The cause can sit in at least three places, and each one is fixed by a different person or tool. Early on I skipped that step and sent the same "it's black, please fix it" request again and again. It didn't go well.

## A black screen stops in one of three places

Work from the top. Each layer you rule out makes your next request to the AI more specific.

## 1. Rule out the device and app first

If scanning the QR code shows nothing at all, suspect the step before your generated code. Since September 2026, running a project in Expo Go requires a login, and the terminal side and the app side both need to be in a matching state. I wrote up the order of checks separately:

- [Two logins to check first when Expo Go stops opening your preview](/en/articles/rork-basics/expo-go-login-both-terminal-and-app-preview-not-opening)
- [Fixing a Rork Companion preview that won't run](/en/articles/rork-basics/rork-companion-preview-not-working-fix)

The question to ask here is simple: does fully closing the app and reopening it change anything? If it does, the problem was device state, not code.

## 2. Then suspect rendering

Expo's debugging guide suggests reading the stack trace and, when that gives you nothing, going back to a working version and re-applying changes one at a time. With a silent black screen, the second approach is the one that pays off.

As an indie developer I've tripped over the same four things in my own apps:

- A black background with black text, because a dark-theme setting only took effect on one of the two
- A component that returns `null` until data arrives, and the data never does
- A parent View with no height, so its children collapse to zero
- A splash screen that never gets dismissed, so the first screen never takes over

The fastest way to tell them apart is a temporary diagnostic component placed at the top of the screen:

```tsx
import { View, Text } from "react-native";

// Diagnostic only: checks whether content is hiding against a black background.
// Remove it once you've seen the result.
export default function DebugBanner({ label }: { label: string }) {
  return (
    <View style={{ backgroundColor: "#ffd54f", padding: 12 }}>
      <Text style={{ color: "#000", fontWeight: "700" }}>{label}</Text>
    </View>
  );
}
```

If the yellow banner shows, the app is alive and whatever sits below it is rendering nothing. If it doesn't, the stall happens earlier — device or native.

The fourth one is easy to miss. If you call `preventAutoHideAsync()` from `expo-splash-screen` and the code never reaches `hideAsync()`, the app can be running fine while the screen stays on the splash. A font or initial-data load that throws before `hideAsync()` is a common way to get there. I once spent an evening polishing styles because I was sure it was a rendering problem; looking back, I should have checked the `try / finally` around the loading code first.

One more caution: a missing yellow banner doesn't automatically mean the stall is earlier than rendering. A full-screen `position: "absolute"` View can simply be sitting on top of it. Raise the banner's `zIndex` temporarily and look again.

## 3. Check whether the app crashes natively

No banner and no change after a reload usually means the app is dying right after launch. Expo's documentation treats native crashes as a log-reading job:

- Android: stream device logs with `adb logcat`
- iOS: open the Console app on a Mac, pick your device, and start streaming

If you're on Windows only, you don't have to chase this one. Knowing that it crashed is already enough to word your next request.

Opening logs can feel heavy. The first time, I stared at a wall of text and froze. But you don't need to read all of it — only the few lines around the moment of the crash. Find one red `FATAL EXCEPTION` or `Error` line and paste it straight into your request.

## Change what you tell the AI

Rork's FAQ says AI errors don't cost credits, offers Restore to return to an earlier working version, and suggests asking Rork to search the web or switching models when you're stuck. So trying again isn't something to fear.

What changes is the wording:

- Banner visible: "The screen runs, but the list area draws nothing. Check whether it returns null before the data loads."
- No banner: Restore the last working version first, then re-request changes one at a time.

"It's black" leaves the AI guessing. One sentence about which layer stalls narrows the fix a lot.

## Three lines to attach to your request

Whatever you found can go straight to the top of your prompt. This is the shape I use:

```text
Stalled at: layer 2 (rendering)
Checked: yellow banner is visible; closing and reopening the app changes nothing
Suspect: the list screen may return nothing before data has loaded
```

With those three lines, the fix that comes back is less likely to drift toward "rebuild everything." Without them, repeated requests can rewrite parts that were working. When that happens, restoring the last working version and starting over usually ends up faster.

**Before asking again, be able to say in one sentence where it stops.** I keep to that rule hardest on tired nights.

Next time you meet a black screen, drop in the yellow banner before you send anything. Whether you see it decides which screen to open next.
