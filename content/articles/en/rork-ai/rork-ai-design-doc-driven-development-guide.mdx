When you first build an app with Rork, it usually goes like this: you describe what you want, an app comes out, and it's close but not quite right. You refine it, adjust it, and eventually realize that if you'd been more specific at the start, you'd have gotten there in a fraction of the time.

This isn't a Rork problem. It's a specification problem. With natural language app generation, the same principle holds that applies to every AI coding tool: *the design of what you ask determines the speed you get*.


## The Core Framework: 3-Layer Specification

The ideal Rork prompt is structured in three layers:

```
Layer 1: Core features (what the app does — one sentence plus scope)
Layer 2: Screen design (what screens exist and what happens on each)
Layer 3: Data design (what is stored, where, and how it's accessed)
```

When all three layers are present, Rork can parse your intent accurately. When one is missing, it fills the gap with assumptions — and those assumptions are rarely what you wanted.

## Layer 1: Defining Core Features

Define what the app *does* and what it *explicitly doesn't do* in this phase.

**Too vague:**
```
Build a journal app
```

**Specific enough:**
```
A daily journal app where users can write text entries, attach photos (up to 3),
and rate their mood (1–5). Entries are viewable in a calendar view.
No search, no social sharing, no tags — out of scope for this version.
```

Explicitly listing what's excluded is critical. Without it, Rork may add "nice to have" features it infers you might want. The "not this version" clause closes that door.

## Layer 2: Screen-by-Screen Detail

The more precisely each screen is specified, the closer the output is to your intent.

```
## Screen Design

### Home Screen (shown on launch)
- Today's date and day of week (large, prominent)
- If no entry today: "Write today's entry" button
- If entry exists: one-line preview + "Edit" button
- Week calendar strip at bottom (dots on days with entries)

### Entry Screen
- Text input area (max 1,000 characters)
- Photo attachment button (up to 3 photos from camera roll)
- Mood slider (1–5 with icon display)
- Save button (active only when text is present)
- Back button (shows unsaved changes dialog if applicable)

### Calendar Screen
- Monthly calendar view
- Days with entries show colored dots (color by mood)
- Tap a date to open the entry detail for that day
```

At this level of detail, "it doesn't look like what I had in mind" drops from a frequent occurrence to a rare one.

## Layer 3: Data Design

Being explicit about what data is stored, in what format, and where eliminates a category of questions Rork would otherwise resolve by guessing.

```
## Data Design

### Journal Entry
- id: string (UUID)
- date: string (YYYY-MM-DD)
- text: string (max 1,000 characters)
- mood: number (1–5)
- photos: string[] (URL array, max 3)
- createdAt: timestamp
- updatedAt: timestamp

### Storage
- Firebase Firestore
- Collection: diary_entries
- Document ID matches entry.id

### Authentication
- Firebase Authentication (email + password)
- No anonymous login
- Data is scoped per user
```

With data design specified, the type definitions and data access code Rork generates are typically usable on the first pass rather than requiring type fixes.

## The Complete Prompt Template

Combining all three layers:

```
# [App Name]

## Core Features
[One-sentence description]

### In scope
- Feature 1
- Feature 2
- Feature 3

### Out of scope (not this version)
- Feature A
- Feature B

## Tech Stack
- Framework: React Native / Expo
- Backend: Firebase / Supabase / None (local only)
- Auth: Firebase Auth / None

## Screen Design
### [Screen Name]
- Display elements: 〜
- User actions: 〜
- Navigation: 〜

### [Next Screen]
(same structure)

## Data Design
### [Entity Name]
- Fields: 〜 (types)

### Storage structure
(collection names, document structure)

## Design Direction
- Color palette: dark / light / [specific colors]
- Tone: minimal / colorful / professional
- Font: [font name] (or default)

## Non-Functional Requirements
- Offline support: required / not required
- Performance: 〜
```

## Checklist Before Sending to Rork

Before submitting a prompt, verify these five things:

- [ ] "Not this version" items are explicitly listed
- [ ] Every screen has "what's shown" and "what user can do" defined
- [ ] Data types and storage destination are specified
- [ ] Authentication requirement is stated
- [ ] Design tone is specified (otherwise Rork defaults)

## Building a Reusable Parts Library

If you build multiple apps, stocking reusable spec components saves time on every new project.

### Authentication Component (Email)

```
## Authentication
Firebase Authentication. Email + password registration and login.
Login state persisted in AsyncStorage.
Unauthenticated users redirected to login screen.
Password reset via email.
```

### Error Handling Component

```
## Error Handling
- Network error: toast at top of screen (dismisses after 3 seconds), retry button
- Auth error: modal with specific message
- Validation error: inline below input field
- Empty state: dedicated empty state component when no data exists
```

### Firebase Configuration Component

```
## Firebase Setup
- Authentication: email auth only enabled
- Firestore: read/write rules scoped per user
- Storage: image files, max 10MB per file
- Security rules: authenticated users only
```

Save these as snippets. Paste them into new specs as needed.

## Minimizing the Revision Cycle

The workflow that produces the fewest revisions:

**First prompt**: Submit the full spec to generate the skeleton
**Verify**: Does the navigation flow work? Is data saving correctly?
**Subsequent revisions**: One change per prompt, explicitly scoped

"Fix the home screen's header color. Don't change anything else." beats "make it look better generally." When revising, specify *what not to change* alongside what to change — this is the core practice of the Rork × design doc approach.

Applied consistently, this cuts development time per app and makes the process feel less like wrestling with a tool and more like directing one.
