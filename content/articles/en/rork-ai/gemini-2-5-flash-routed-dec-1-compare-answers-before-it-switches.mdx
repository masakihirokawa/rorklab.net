I was reworking the part of my wallpaper app that suggests categories for new images when I opened the Gemini API deprecations page and stopped scrolling. The December 1 row did not say "shutdown." It said the calls would be **automatically routed** to another model.

I had been assuming that a deprecation means errors. Errors show up in Crashlytics, and I would catch them in the logs the next morning. Rerouting is different: the app keeps running as if nothing happened. What changes is the wording and length of the answers, and the price per token.

The one thing I want to say up front: **a deadline that reroutes is harder to notice than a deadline that breaks.** There are five days left before December 1, counting today. If you added an AI feature to an app built with Rork, here is how I'd check it before then, and how I'd narrow things down if something feels off afterwards.

## What happens on December 1 (as of November 2026, checked against the official page)

The Gemini API [Deprecations](https://ai.google.dev/gemini-api/docs/deprecations) page says that from December 1 the following calls are routed to successor models.

<table>
<thead><tr><th>Name your app calls today</th><th>Routed to from December 1</th><th>Worth noticing</th></tr></thead>
<tbody>
<tr><td><code>gemini-2.5-flash</code></td><td><code>gemini-3.5-flash-lite</code></td><td>It lands on the Flash-Lite line, not plain Flash</td></tr>
<tr><td><code>gemini-2.5-pro</code></td><td><code>gemini-3.8-flash</code></td><td>It moves from Pro to the Flash line</td></tr>
</tbody>
</table>

The part that is easy to skip: once rerouted, usage is billed at **the successor model's rates**. If you set a monthly cap based on 2.5 pricing, that cap needs another look. Prices can move, so I'm not quoting numbers here; please check the [pricing page](https://ai.google.dev/gemini-api/docs/pricing) on the day you do the math. There is also a thread on the developer forum asking Google to keep 2.5 Pro around. My guess is that the more a feature was tuned to one model's habits, the more it will feel the move.

If you call a pinned name like `-001`, a `-preview` name, or a purpose-specific one such as `-tts`, look up that exact row on the same page. The handling and the date are not necessarily the same. I once found that a recommended replacement had already been shut down before the model it was replacing, and I wrote that audit up in [The recommended replacement was already shut down](/articles/rork-ai/gemini-deprecation-recommended-replacement-already-shutdown-audit).

## Three assumptions I almost made

Before the steps, here are three assumptions I nearly acted on.

**1. "It will throw errors when it's retired, so I'll fix it then."** December 1 is a reroute, not a shutdown. Responses still come back with a success status, so error monitoring stays quiet. The clues show up in answer shape, length, and the bill.

**2. "It's routed to a newer model, so answers can only get better."** `gemini-2.5-flash` goes to the Flash-Lite line. It is a newer generation, but a lighter tier, so how closely it follows long instructions and how much it writes can shift. Whether it's better or worse for you is something you only learn by running your own inputs.

**3. "If I change the model name in the app, everyone gets it this week."** A name baked into the app binary needs store review *and* users actually updating. On devices that never update, the old name keeps being called after December 1 and keeps receiving the rerouted answers.

## Step 1: Find every model name your app calls

In apps built with Rork, it's common not to know exactly where the model name lives. I assumed it wasn't in the screen code, and it turned out to be hardcoded in a server-side function.

The most reliable move is to ask Rork once, in chat:

> List every place in this project that calls the Gemini API, with the file name and the model name. If the model name is read from an environment variable or a config file, include the variable name. Please don't change any code.

If you have the exported code locally, you can search it yourself. This catches both hardcoded strings and names pushed out into env or config files.

```bash
# Run at the root of the exported project (macOS / Linux)
grep -rnE "gemini-2\.5-(flash|pro)" \
  --include='*.ts' --include='*.tsx' --include='*.js' --include='*.mjs' \
  --include='*.json' --include='*.toml' --include='.env*' . \
  | grep -v node_modules

# Also look for places that take the model name from a variable
grep -rnE "GEMINI_MODEL|modelName|model:\s*['\"]gemini" \
  --include='*.ts' --include='*.tsx' --include='*.js' . | grep -v node_modules
```

If the first search finds nothing and only the second one hits, the name probably lives outside the code: a `.env` file, Cloudflare Workers' `wrangler.toml`, or Supabase Secrets. Open the dashboard values too.

Then sort each hit: is it **inside the app itself**, or **on the server side**, such as a Supabase Edge Function or a Cloudflare Worker? That split decides Step 4. I wrote more about where to put these values in [Environment variables vs. a Supabase Edge Function for your API key](/articles/rork-ai/rork-api-key-placement-env-variables-vs-supabase-edge-function).

## Step 2: Send the same inputs to the current model and its successor

You don't have to wait for December 1. The successor models can be called by name today, so send the same inputs to both and put the answers side by side.

The script below runs on Node.js 18+ with no extra packages. Put around ten real prompts your app sends into `inputs.json` as an array of strings. If your app expects JSON back, list the keys it can't live without in `REQUIRED_KEYS`, and the script will flag shape breaks for you.

```javascript
// compare-models.mjs — send the same inputs to two models and compare shape, length, and time
// Run: GEMINI_API_KEY=YOUR_API_KEY node compare-models.mjs inputs.json
import { readFile } from "node:fs/promises";

const PAIRS = [["gemini-2.5-flash", "gemini-3.5-flash-lite"]]; // add ["gemini-2.5-pro", "gemini-3.8-flash"] if you use Pro
const REQUIRED_KEYS = []; // e.g. ["category", "confidence"]; leave empty if you don't parse JSON
const KEY = process.env.GEMINI_API_KEY;
if (!KEY) throw new Error("GEMINI_API_KEY is not set");

function inspect(out) {
  const cleaned = out.replace(/^\x60{3}(json)?\s*|\x60{3}\s*$/g, "").trim();
  try {
    const obj = JSON.parse(cleaned);
    const missing = REQUIRED_KEYS.filter((k) => !(k in obj));
    return { isJson: true, fenced: cleaned !== out.trim(), missing };
  } catch {
    return { isJson: false, fenced: false, missing: REQUIRED_KEYS };
  }
}

async function ask(model, text) {
  const started = Date.now();
  const res = await fetch(
    `https://generativelanguage.googleapis.com/v1beta/models/${model}:generateContent`,
    {
      method: "POST",
      headers: { "Content-Type": "application/json", "x-goog-api-key": KEY },
      body: JSON.stringify({ contents: [{ parts: [{ text }] }] }),
    }
  );
  const ms = Date.now() - started;
  if (!res.ok) return { model, ms, error: `${res.status} ${await res.text()}` };
  const data = await res.json();
  const out = data.candidates?.[0]?.content?.parts?.map((p) => p.text ?? "").join("") ?? "";
  return {
    model,
    servedBy: data.modelVersion, // model version reported in the response
    ms,
    chars: out.length,
    tokens: data.usageMetadata?.totalTokenCount,
    ...inspect(out),
    head: out.slice(0, 60),
  };
}

const inputs = JSON.parse(await readFile(process.argv[2], "utf8"));
for (const [oldModel, newModel] of PAIRS) {
  for (const [i, text] of inputs.entries()) {
    const [a, b] = [await ask(oldModel, text), await ask(newModel, text)];
    console.log(`#${i + 1}`, JSON.stringify(a), "\n   ", JSON.stringify(b));
  }
}
```

Each input prints two lines: the current model on top, the successor below. Before judging which answer is *better*, check whether the **shape is the same**. `isJson` false on only one side, `fenced` true on only one side (the answer arrives wrapped in a code block), `chars` nearly doubling, or a new lead-in sentence showing up in `head`: in my experience, one of these is what breaks a screen or a parser.

Compare `ms` and `tokens` on the same line too; they give you a rough sense of cost and wait time. Ten inputs are noisy, so when one shows a gap I care about, I rerun just that one three times. I'm not pasting my own output here on purpose: my inputs and yours will behave very differently, and the only numbers worth trusting are the ones from your own prompts.

## Step 3: Pin the answer shape on your side

If the shapes drift, fix the shape before you touch the model name. In the Gemini API, passing `responseMimeType: "application/json"` and a `responseSchema` inside `generationConfig` asks the model to return JSON in a shape you define (see the [official structured output docs](https://ai.google.dev/gemini-api/docs/generate-content/structured-output)).

Before: the shape is only requested in the prompt text.

```javascript
// Before: the format is only asked for in words. A different model may add fences or a preamble
body: JSON.stringify({
  contents: [{ parts: [{ text: `Pick one category for this image description and reply in JSON: ${caption}` }] }],
}),
```

After: the shape itself is handed to the API.

```javascript
// After: the API enforces the shape, so keys and types hold up better when the model changes
body: JSON.stringify({
  contents: [{ parts: [{ text: `Pick the one category that fits this image description: ${caption}` }] }],
  generationConfig: {
    responseMimeType: "application/json",
    responseSchema: {
      type: "OBJECT",
      properties: {
        category: { type: "STRING", enum: ["nature", "city", "abstract", "animal", "other"] },
        confidence: { type: "NUMBER" },
      },
      required: ["category"],
    },
  },
}),
```

The `enum` does the most work. Even if the successor phrases things differently, variants like `"Nature"` never reach your UI. Swap this `body` into the Step 2 script and run the comparison again to see how much of the gap closes.

If you cache AI answers, check that the cache key includes the model name. If it doesn't, old-model answers will keep showing up after the switch. I covered that in [Sweeping the answer cache on the day you swap models](/articles/rork-ai/ai-answer-cache-key-model-and-prompt-version-sweep-on-swap).

## Step 4: Switch it yourself, or let the routing happen?

This is where the Step 1 sort pays off. There are three paths, and which one fits depends on where the name lives.

<table>
<thead><tr><th>Approach</th><th>Fits when</th><th>Upside</th><th>Watch out for</th></tr></thead>
<tbody>
<tr><td>Change the name yourself before December 1</td><td>The name is server-side and Step 2 showed small differences</td><td>You know when it changed and can roll back on your own call</td><td>Read the logs at least once right after</td></tr>
<tr><td>Let the routing happen</td><td>The name is in the app binary and review won't finish in time</td><td>No extra work this week</td><td>You won't see the moment it changes. Step 3's shape pinning needs to be in first</td></tr>
<tr><td>Move the name to the server</td><td>You don't want to repeat this at the next deprecation</td><td>Future model swaps skip review</td><td>The move itself needs one review, which may miss this deadline</td></tr>
</tbody>
</table>

If I had to put it in one sentence: **if the name is on the server, switch it yourself; if it's in the app, pin the shape and let it route, then move the name to the server in your next update.** That order has caused me the least rework.

My own rule is that **Google sets the deadline, but I pick the moment of the switch.** If I wait for the reroute, I don't get to watch the change happen. When I switch on the server, I do it at a quiet hour and read a handful of log lines that night, the same way I read the Step 2 output.

## If something feels off after December 1

Problems after a reroute rarely arrive as an error screen. They arrive as "something seems a bit off." Here are the symptoms I'm preparing for and the order I'd check them in.

<table>
<thead><tr><th>Symptom</th><th>Likely cause</th><th>How to check</th><th>Fix</th></tr></thead>
<tbody>
<tr><td>Categories or results come back empty, or always the default</td><td>Answers arrive wrapped in a code block or with a preamble, and parsing fails</td><td>Log one raw answer in the app and look at its first few characters</td><td>Add <code>responseMimeType</code> and <code>responseSchema</code> from Step 3</td></tr>
<tr><td>Text on screen is cut off or overflows</td><td>Answer length changed</td><td>Compare <code>chars</code> old vs. new in Step 2</td><td>Set a length in the prompt and clamp lines in the UI</td></tr>
<tr><td>The monthly bill moved more than expected</td><td>Both the successor's rate and the token count changed</td><td>Read the per-model lines in billing and line them up with <code>tokens</code> from Step 2</td><td>Recalculate your cap with the successor's rates</td></tr>
<tr><td>Old and new answers appear mixed</td><td>The cache key doesn't include the model name</td><td>Send the same input through the cached and uncached paths and compare</td><td>Add the model name and prompt version to the key, then sweep once</td></tr>
<tr><td>Only some calls return 404 or 400</td><td>You're using a pinned or <code>-preview</code> name that isn't covered by the routing</td><td>Match the model name in the error body against the Deprecations page</td><td>Switch that name to the current one listed there</td></tr>
<tr><td>Responses get slower and hit timeouts</td><td>The successor's latency is different</td><td>Compare <code>ms</code> old vs. new in Step 2</td><td>Revisit the timeout value and what it covers (headers only or the whole body)</td></tr>
</tbody>
</table>

I expect the first row to be the most common. The content of the answer is fine; only the wrapper changes, and the app decides "no answer" and shows a default. For the last row, my write-up on [measuring header, total, and idle timeouts against the same response](/articles/rork-ai/stalled-response-body-header-total-idle-timeout-measured-three-ways) may help.

The Step 2 script also prints the response's `modelVersion` as `servedBy`. I have not confirmed whether that field will show the successor's name after December 1. I plan to call the old name once on the day and see what comes back.

## The other deadline that same week

On November 30, the same week, Sonnet 4.5 retires from the Claude API. That one stops rather than reroutes, so it's easier to notice, but by the time you notice, the feature is already down. If your app uses both, run the Step 1 search alongside the [Sonnet 4.5 model ID scan](/articles/rork-ai/scan-app-for-old-claude-model-ids-before-sonnet-4-5-retires) in one pass.

## What to do next

Build the Step 1 list today, and get as far as sorting each name into "in the app" or "on the server." With that list in hand, the comparison and the Step 4 choice are not heavy. Not letting the day your answers change pass by unnoticed is the one thing I try to hold to, even for a small app.
