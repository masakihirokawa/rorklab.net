壁紙アプリの更新告知を書いていた夜、日付の欄でふと手が止まりました。作業そのものは、あと 2 日で終わる見込みでした。それなのに「公開は来週です」と書いてよいのか、自信が持てなかったのです。

結局その日は、日付を空欄にしたまま保存しました。待ち時間は私の手の外にあり、見積もりに入れていなかったことに、そこで気づきました。

Rork でアプリが形になると、「あとは出すだけ」という気持ちになりやすいと思います。ですが、初めてストアに出す場合は、**作る時間より待つ時間のほうが長くなる**ことが珍しくありません。

最初にお伝えしたいのは、「1 週間でリリース」という約束は、条件がそろったときにだけ成り立つ、ということです。ここから、待たされる日数を内訳にして、自分の日付を逆算できるところまで書き残します。数字はすべて 2026 年 11 月時点で公式ヘルプを確かめたものです。

## 待ち時間は 5 種類に分けると見えてきます

「審査が長い」とひとまとめにすると、どこで時間を使うのかが見えません。私は次の 5 つに分けて数えています。以前は 4 つで数えていましたが、Google Play の「本番アクセスの申請」を一つの待ちとして数えていなかったことに、あとから気づきました。

目安はあくまで目安で、時期やアカウントの状態で変わります。見積もりの当日に、Apple の [App Review](https://developer.apple.com/distribute/app-review/) と Google の [新しい個人デベロッパー アカウントのテスト要件](https://support.google.com/googleplay/android-developer/answer/14151465) を一度だけ開いて、数字が変わっていないかを確かめていただければと思います。

## 見落としやすいのは、Google Play の 14 日です

個人で作る方がいちばん計算を外しやすいのは、ここだと感じています。公式ヘルプの条件は「本番アクセスを申請する時点で、12 人以上のテスターが、直前の 14 日間ずっとオプトインしたままであること」です。

この書き方を読み返して、私は二つのことに気づきました。

一つは、**14 日は 12 人目がそろった日から数える**ことになる、という点です。早く参加した人が 14 日を超えていても、12 人目の参加がテスト開始から 3 日目なら、申請できるのは 17 日目以降です。見積もりに入れるべきなのは 14 日だけではありません。

- テスターを集めるまでの日数（ここがいちばんぶれます）
- 12 人目がそろってからの連続 14 日
- 途中で抜けた人を補う余裕

もう一つは、**抜けて戻った人は、戻った日から数え直し**になる点です。公式の FAQ にも、オプトアウトしてから再びオプトインした場合は、14 日が連続していなければ数に入らないと書かれています。端末を買い替えた方や、テスト用の Google アカウントを切り替えた方がいると、ここで静かに日数が延びます。

人が集まる速さは、自分の力ではどうにもなりません。私は、集める日数を「3 日から 3 週間」と幅で置き、12 人ちょうどではなく 15 人ほどに声をかけるようにしています。

## 14 日のあとに、もう一つの待ちがあります

14 日を数え終えても、すぐに公開ボタンが押せるわけではありません。Play Console のダッシュボードから「本番環境へのアクセスを申請」を出し、Google の審査を待つ段階があります。公式ヘルプでは、この審査は通常 7 日以内、ときにそれより長くかかるとされています。

申請フォームは 3 つの区分に分かれています。

- 非公開テストについて（テスターは集めやすかったか、全機能を使ってもらえたか、どんなフィードバックをどう集めたか）
- アプリについて（対象ユーザー、アプリが提供する価値、初年度のインストール数の見込み）
- 本番公開の準備について（テストで分かったことをもとに何を変えたか、公開できると判断した理由）

ここで私が最初につまずいたのは、フィードバックの「要約」を求められることでした。テスト期間中に感想を集めていないと、書く材料がありません。12 人が 14 日間インストールしていただけ、という状態では、申請が通っても通らなくても、手応えのない 2 週間になってしまいます。

テスターが 12 人に届かなかった場合や、テスト中の利用が乏しかった場合は、非公開テストを続けるよう求められることがある、と公式にも書かれています。ですので、テストを始める日に、感想を送ってもらう窓口（メールでも、Play Console の「テストのフィードバック」でも構いません）を決めておきます。

## 日付を逆算するスクリプト

「最短ならいつ、遅れたらいつ」を毎回手で足し算するのは、手が止まる原因になります。次のスクリプトは、待ち時間の最小値と最大値を順番に積み、iOS と Android の 2 本の道の日付を並べます。Apple が年末に「審査が少し長くなる」と告知する期間にかかったときだけ、余分を 1 回積むようにしています。

```ts
// release-eta.ts
// 目的: 待ち時間の幅から「最短で出せる日」と「遅れた場合の日」を、iOS と Android の道ごとに逆算します
// 実行: node --experimental-strip-types release-eta.ts（Node 22.6 以降）または npx tsx release-eta.ts
// 日数は公式の目安と私の見込みを混ぜたものです。保証値ではないので、見積もる当日に確かめて書き換えてください

type Wait = { label: string; min: number; max: number; appleReview?: boolean }; // 暦日で数えます

const DAY = 86_400_000;
const parse = (s: string) => new Date(`${s}T00:00:00Z`); // UTC で読んで UTC で書くので、日付はずれません
const addDays = (d: Date, n: number) => new Date(d.getTime() + n * DAY);
const fmt = (d: Date) => d.toISOString().slice(0, 10);

// Apple が「審査が少し長くなる」と告知する年末の期間。毎年 12 月の告知で日付を確かめて書き換えます
const SLOW = { from: parse("2026-12-23"), to: parse("2026-12-27"), extra: 3 };

function eta(startStr: string, steps: Wait[]) {
  let early = parse(startStr);
  let late = parse(startStr);
  let slowUsed = false; // 年末の余分は 1 本の道につき 1 回だけ
  for (const s of steps) {
    const nextLate = addDays(late, s.max);
    // 遅れた場合の道が年末の期間にかかるときだけ、Apple の審査に余分を 1 回積みます
    const hit = !slowUsed && s.appleReview && late <= SLOW.to && nextLate >= SLOW.from;
    if (hit) slowUsed = true;
    early = addDays(early, s.min);
    late = hit ? addDays(nextLate, SLOW.extra) : nextLate;
    console.log(`  ${s.label}: ${fmt(early)} 〜 ${fmt(late)}${hit ? "（年末の分を加算）" : ""}`);
  }
  return { early, late };
}

const iosSteps: Wait[] = [
  { label: "Apple Developer の登録承認", min: 1, max: 7 },
  { label: "App Store 初回審査", min: 1, max: 2, appleReview: true }, // 公式: 90% が 48 時間以内
  { label: "差し戻し 1 回分の再提出", min: 0, max: 3, appleReview: true },
];

const androidSteps: Wait[] = [
  { label: "テスター 12 人を集める", min: 3, max: 21 },
  { label: "非公開テストの連続 14 日", min: 14, max: 14 },
  { label: "本番アクセス申請の審査", min: 1, max: 7 }, // 公式: 通常 7 日以内
  { label: "初回公開の審査", min: 1, max: 7 },       // 公式: 一部のアカウントは最大 7 日以上
  { label: "差し戻し 1 回分の再提出", min: 0, max: 3 },
];

for (const start of ["2026-11-24", "2026-12-14"]) {
  console.log(`\n開始日 ${start}`);
  console.log("[iOS]");
  const ios = eta(start, iosSteps);
  console.log("[Android]");
  const android = eta(start, androidSteps);
  // 両方そろえて出すなら、遅いほうの道が公開日を決めます
  const slower = ios.late > android.late ? "iOS" : "Android";
  const both = new Date(Math.max(ios.late.getTime(), android.late.getTime()));
  console.log(`両方そろう日（遅れた場合）: ${fmt(both)}  ← 日付を決めているのは ${slower} の道`);
}
```

11 月 24 日に始めた場合、iOS は遅れても 12 月上旬に出せますが、Android は年をまたぎます。最短でも 19 日後、遅れた場合は 52 日後です。「年内に両方」と書くつもりだった方は、ここで一度手が止まるかもしれません。

数字そのものよりも、**どちらの道が日付を決めているか**が一目で分かることのほうが、役に立ちます。「1 週間」と書く前に、この出力を一度ご覧になってください。

なお、このスクリプトの初版では、日付を表示するときに「最大で 1 日ずれる」と書いていました。実際には、`"2026-11-24"` のような日付だけの文字列は UTC の 0 時として読まれ、`toISOString()` も UTC で書き出すので、ずれは起きません。ずれるのは `new Date(2026, 10, 24)` のように端末のローカル時刻で作った日付を UTC で表示したときです。ここは入力も出力も UTC にそろえる、と決めておくと迷いません。

## 個人アカウントと組織アカウントでは、待ち方が違います

「14 日がつらいなら、組織アカウントで作ればよいのでは」と考える方もいらっしゃると思います。実際、テスト要件の対象は 2023 年 11 月 13 日以降に作った**個人**アカウントです。ただ、組織には組織の待ちがあります。

判断の基準は一つです。**すでに法人があり、ストアに法人名で出したいなら組織アカウント、そうでなければ個人アカウントで 14 日を見積もりに入れます**。14 日を避けるためだけに法人を用意するのは、待ちの種類を入れ替えているだけになりやすいと感じています。

## よくある誤解を 3 つ

**「内部テストで 14 日回せば足りる」**——足りません。要件は「非公開テスト（クローズドテスト）」です。内部テストは数秒で配れて便利ですが、14 日の数には入りません。内部テストで動作を確かめ、非公開テストを早めに始める、という順番にしておくと日数を無駄にしません。

**「Apple の審査は 24 時間で終わる」**——半分は当たっています。公式の目安は「少なくとも 50% が 24 時間以内、90% が 48 時間以内」です。初回はさらに、差し戻しの往復が入ることがあります。私は 2 日と差し戻し 1 回分の 3 日を、別々に積んでいます。

**「14 日を数え終えた日が公開日」**——その後に本番アクセス申請の審査と、初回公開の審査があります。どちらも 7 日前後を見ておくと、14 日目から最大 2 週間ほど後ろにずれます。告知文に書く日付は、ここまで足した日です。

## 差し戻しは「起きるもの」として 3 日だけ積みます

初めての審査では、一度で通らない可能性も見込んでおきたいところです。スクリプトで差し戻しに 3 日を置いているのは、修正して再提出し、もう一度待つ分の目安です。

差し戻しの理由は、アプリの出来そのものより、説明文やプライバシー情報、ログイン用のテストアカウントの不足といった「書類側」であることも少なくありません。Google Play の公式ヘルプにも、ログインが必要なアプリは、審査担当が使えるログイン情報を Play Console に入れておくよう書かれています。ですので、審査に出す前に、審査担当の方が迷わず触れる状態になっているかを一度だけ見直します。

私は、この見直しに半日をあてています。半日を惜しんで 3 日を失うよりも、はるかに安く済むからです。

## 書き方を変えると、約束が軽くなります

見積もりが長くなっても、がっかりする必要はありません。伝え方を変えるだけで、約束はずいぶん軽くなります。

- 「◯日公開」ではなく「◯月の第 2 週から順次」と、幅で書く
- iOS と Android の日付を分けて書く（同時公開にこだわりすぎない）
- 待ち時間のあいだに、スクリーンショットや説明文など、自分の手で進められる作業の前倒し

公開の瞬間そのものを自分で決める方法は、別の記事（[審査がいつ明けるか読めないなら、公開日は審査の外側で決めます](/articles/rork-basics/rork-release-date-outside-the-review-queue)）にまとめています。こちらは「いつ出せるか」を知る側、あちらは「出す瞬間を決める」側の話です。

## 次に詰まりやすいのは、14 日の途中です

見積もりを立てて非公開テストを始めると、次に当たりやすいのは「途中で 1 人抜けた」という場面です。数え直しになるのか、補えば済むのかは、[Google Play のテスター 12 人のうち 1 人が抜けたときの記事](/articles/rork-basics/google-play-12-testers-one-drops-out-14-days-restart-or-not)で順に確かめています。

iOS の道で先に済ませておきたい登録まわりは、[Rork が代わりにできない Apple 側の準備](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)にまとめました。バンドル ID のように、あとから変えられない値を決める作業も、待ち時間の前に済ませておきたい仕事です。[最初のリリース前に決めておきたいアプリ ID の話](/articles/rork-basics/rork-app-id-immutable-before-first-release)も、あわせてご覧ください。

## 約束の日付は、相手の待ち時間まで足してから置きます

私が日付の欄で手を止めた夜から、線引きは一つだけ変わりました。

**約束の日付は、自分の作業日数ではなく、相手の待ち時間まで足した日に置きます。**

それ以来、告知文の日付は「遅れた場合」の列から選ぶようにしています。早く出せたときは、ただ嬉しいだけで済みます。

明日の最初の作業として、上のスクリプトの開始日を自分の日付に書き換え、公式ヘルプで確かめた日数を入れて、一度だけ走らせてみてください。出てきた日付が、いまの「1 週間」とどれだけ離れているか。その差を知るところから、始めていただければと思います。
