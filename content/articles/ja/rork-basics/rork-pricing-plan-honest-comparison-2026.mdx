自分のアカウントの請求画面と、公式の料金ページを並べて見比べた朝がありました。以前は有料の段階が三つほど並んでいたはずなのに、画面にあるのは「Free」と「Rork Max」の二つだけ。しかも Max の最初の段階は、私の記憶よりひと桁安い月$20でした。

手元のメモをそのまま信じて計算していたら、払わなくてよいお金を払う判断をしていたかもしれません。料金は、覚えた日から古くなっていく情報なのだと、あらためて胃のあたりが冷えました。

最初にお伝えしたいのは、**2026年11月時点の Rork は「無料で設計し、Rork Max で作って出す」という二段の構造になっている**ということです。そのうえで、Max のどの段階を選ぶか、足りない分をどう埋めるかで、同じ使い方でも月の支払いが数倍変わります。ここからは、公式ドキュメントの数字だけを使って、その判断を一つずつ辿り直します。

この表でいちばん伝えたいのは、**Rork Max のどの段階も機能はまったく同じで、違うのはクレジットの量だけ**という点です。公式にも「Every Rork Max option includes the full feature set」と書かれています。$200 を払えば何か特別な機能が開く、という作りではありません。

もう一つ、クレジット1つあたりの単価を割り出すと、$20〜$500 の段階はどれも $0.20、$900 と $1,800 の段階が $0.18 です。追加購入（top-up）は1クレジット $0.22。つまり**上の段階に上げても、単価はほとんど下がりません**。この事実が、後で出てくる「$20＋追加購入」という選び方の土台になります。

なお、インドでは Rork Start（₹649/月・40クレジット・軽量モデルのみ）という入口の段階が別に用意されています。日本から申し込む場合は対象外です。

## 無料プランでできること・できないこと

無料プランは、カード登録なしで使い続けられます。期限が来たら止まる、という試用版ではありません。ただし、2026年11月時点の無料プランで動くのは**デザインモードだけ**です。

デザインモードでは、作りたいアプリを言葉で伝えると、Rork が画面構成と見た目を提案してくれます。iPhone・Android・Web・iPad・Apple Watch・Vision Pro のどれを想定した設計も試せます。一方で、その設計を動くアプリに変えるビルドモード、端末での動作確認、App Store や Google Play への公開は、どれも有料プランが前提です。

無料のクレジットには二つの上限がかかります。日本を含む主要国では月35クレジット、そして1日5クレジットまで。リセットは毎月1日（暦月の始まり）です。1日の上限があるので、月の半ばに思い立って一気に35を使う、という使い方はできません。この1日5という上限との付き合い方は、[Rork の無料枠は月35クレジットですが、実際にぶつかるのは1日5という上限のほうです](/articles/rork-basics/rork-free-tier-daily-five-credit-cap-planning)に分けて書いています。

私が無料の期間に意識しているのは、**設計の迷いをここで出し切っておく**ことです。どの画面が要るか、どの順に遷移するか、何を保存するか。この段階で決め切れていないことは、有料に移ってからビルドのたびにやり直しとなり、そのままクレジットに跳ね返ってきます。

## クレジットは「1回の指示で1つ」ではありません

消える分から先に使われ、買った分はいちばん最後まで残ります。2026年10月30日までは「Cloud Credits」という別の残高がありましたが、同じ価値（$1＝5クレジット）で Usage credits に統合されました。

リセットの日にも違いがあります。**有料プランは最初に購入した日が毎月の更新日**、無料プランは毎月1日です。月初に増えると思い込んでいると、月末の判断を一週間単位でずらしてしまいます。

## $20 で始めて、足りない月は追加購入で埋める

単価がほぼ同じで、プランの分は消え、買った分は残ります。この三つを並べると、選び方の順序が見えてきます。**月の使用量が読めないうちは、$20 の段階に留まって、足りない月だけ追加購入で埋める**ほうが、上の段階に上げるより安く済むことが多いのです。

どこで逆転するかは、割り算で出せます。$200 の段階との差額 $180 を、追加購入の単価 $0.22 で割ると約818クレジット。$20 の段階に含まれる100を足して、**月およそ918クレジット**が境目です。これより少ない月は「$20＋追加購入」、多い月が続くなら $200 の段階、という線になります。

毎月の数字を当てはめられるよう、スクリプトにしておきました。Node.js が入っていれば、そのまま動きます。

```js
#!/usr/bin/env node
// plan-vs-topup.mjs — 月に使うクレジット数から、Rork Max のどの段階＋追加購入が最安かを出す。
// 単価は 2026年11月時点の公式（docs.rork.com/introduction/subscriptions）。改定されたら書き換えてください。
// 使い方: node plan-vs-topup.mjs <月の使用クレジット> [<月の使用クレジット> ...]
const OPTIONS = [
  { usd: 20, credits: 100 },
  { usd: 200, credits: 1000 },
  { usd: 500, credits: 2500 },
  { usd: 900, credits: 5000 },
  { usd: 1800, credits: 10000 },
];
const TOPUP_USD = 0.22; // 追加購入1クレジット（翌月に繰り越される）

const needs = process.argv.slice(2).map(Number);
if (needs.length === 0 || needs.some(Number.isNaN)) {
  console.error("使い方: node plan-vs-topup.mjs <月の使用クレジット> [...]");
  process.exit(1);
}
for (const need of needs) {
  const rows = OPTIONS.map((o) => {
    const short = Math.max(need - o.credits, 0);
    const cost = o.usd + short * TOPUP_USD;
    return { ...o, short, cost, unused: Math.max(o.credits - need, 0) };
  }).sort((a, b) => a.cost - b.cost);
  const best = rows[0];
  const line = best.short > 0
    ? `$${best.usd} の段階＋追加 ${best.short} クレジット`
    : `$${best.usd} の段階のみ（${best.unused} クレジットは月末に消えます）`;
  console.log(`${String(need).padStart(5)} クレジット/月 → 最安 $${best.cost.toFixed(2)}：${line}`);
}
```

手元で、月の使用量をいくつか入れて走らせた結果です。

```

  150 クレジット/月 → 最安 $31.00：$20 の段階＋追加 50 クレジット
  300 クレジット/月 → 最安 $64.00：$20 の段階＋追加 200 クレジット
  600 クレジット/月 → 最安 $130.00：$20 の段階＋追加 500 クレジット
  900 クレジット/月 → 最安 $196.00：$20 の段階＋追加 800 クレジット
  920 クレジット/月 → 最安 $200.00：$200 の段階のみ（80 クレジットは月末に消えます）
 1200 クレジット/月 → 最安 $244.00：$200 の段階＋追加 200 クレジット
```

月300クレジット使う月でも、$20＋追加200で $64。$200 の段階に上げていたら、$136 を余計に払い、そのうえ700クレジットを月末に失っていた計算です。

一点だけ補足します。追加購入は実際には「+25（$5.50）〜+1,000（$220.00）」の選択肢から選ぶので、スクリプトのように1クレジット単位では買えません。端数は少し多めに買うことになりますが、買った分は翌月に繰り越されるので、無駄にはなりにくいところです。自動追加（auto top-up）をオンにすると、残高が尽きるたびに $20 ずつ追加されます。月ごとの上限額も設定できるので、使う場合は上限と一緒にオンにしておくと安心です。

### 以前の私の失敗と、いまの線引き

正直にお伝えすると、私は以前、作り込みの月に合わせて上の段階を先に掴み、そのまま翌月も下げ忘れたことがあります。翌月は画面の文言を少し直しただけで、残ったクレジットはほとんど手つかずのまま更新日を迎えました。払った額そのものより、何も確かめずに払い続けていたことのほうに、しばらく手が止まりました。

いまは、**段階は実績で上げ、見込みでは上げない**と決めています。2か月続けて境目の918を超えたときだけ上の段階に移り、それまでは $20 と追加購入で受け止めます。

## 消化ペースを、更新日から逆算する

追加購入で埋めるにしても、月の途中で「このままだと足りるのか」は体感では分かりません。私は更新日から12日ほど経ったころに一度だけ、次のスクリプトに三つの数字を入れて確かめています。経過日数は、毎月1日ではなく**自分の更新日から**数えるのがこつです。

```js
#!/usr/bin/env node
// credit-pace.mjs — 繰り越されないプランのクレジットを、次の更新日までの配分に翻訳する。
// 有料プランは「最初に購入した日」が毎月の更新日、無料プランは毎月1日に戻ります。
// 使い方: node credit-pace.mjs <月のクレジット> <更新日からの経過日数> <使用済み> [周期の日数] [--free]
const args = process.argv.slice(2);
const isFree = args.includes("--free");
const [total, elapsed, used, cycleDays = 30] = args.filter((a) => a !== "--free").map(Number);
if ([total, elapsed, used].some(Number.isNaN)) {
  console.error("使い方: node credit-pace.mjs <月のクレジット> <経過日数> <使用済み> [周期の日数] [--free]");
  process.exit(1);
}
const remain = total - used;
const daysLeft = Math.max(cycleDays - elapsed, 1);
const pace = used / Math.max(elapsed, 1);     // いまの1日あたりの消費
const landing = Math.round(pace * cycleDays); // このペースで進んだときの着地
const allowance = remain / daysLeft;          // 使い切るための1日あたりの目安

console.log(`残り        : ${remain} クレジット / 残り ${daysLeft} 日`);
console.log(`現ペース    : ${pace.toFixed(2)} / 日 → 着地 ${landing}（上限 ${total}）`);
console.log(`使い切る配分: ${allowance.toFixed(2)} / 日（週あたり ${(allowance * 7).toFixed(1)}）`);
if (isFree && allowance > 5) {
  console.log(`※ 無料プランは1日5クレジットまでです。配分が5を超える分は、使い切れずに消えます。`);
}
if (landing > total) {
  console.log(`⚠ ${Math.floor(total / pace)} 日目で尽きる見込みです。シミュレーターの止め忘れと、同じ指示の言い直しを先に疑います。`);
} else if (landing < total * 0.7) {
  console.log(`△ ${total - landing} クレジットが使われないまま消える見込みです（プランの分は繰り越されません）。`);
} else {
  console.log(`✔ 使い切るペースに乗っています。`);
}
```

$20 の段階（100クレジット）で、更新日から12日で70を使ってしまった月に走らせるとこうなります。

```
$ node credit-pace.mjs 100 12 70
残り        : 30 クレジット / 残り 18 日
現ペース    : 5.83 / 日 → 着地 175（上限 100）
使い切る配分: 1.67 / 日（週あたり 11.7）
⚠ 17 日目で尽きる見込みです。シミュレーターの止め忘れと、同じ指示の言い直しを先に疑います。
```

17日目に尽きる、という具体的な日が出ると、追加購入で越えるのか、残りの作業を翌月に回すのかを落ち着いて選べます。そしてこのペースになる月は、たいてい指示の量より先に、シミュレーターのつけっぱなしが効いています。1時間で12クレジットという数字は、画面を眺めて考え込んでいるあいだにも減り続けます。

反対側も見ておきます。無料プランで、12日目にまだ6しか使っていない月です。

```
$ node credit-pace.mjs 35 12 6 30 --free
残り        : 29 クレジット / 残り 18 日
現ペース    : 0.50 / 日 → 着地 15（上限 35）
使い切る配分: 1.61 / 日（週あたり 11.3）
△ 20 クレジットが使われないまま消える見込みです（プランの分は繰り越されません）。
```

無料のクレジットは1日5までなので、月末にまとめて使い切ることはできません。設計を詰めたい画面があるなら、早めの日に少しずつ回しておく必要があります。

### 1回の指示に情報を寄せる

メッセージの消費が仕事量で決まるようになっても、往復の回数を減らす工夫は変わらず効きます。同じ画面を三回に分けて頼むと、そのたびに前提の読み直しやビルドが走るからです。

```
❌ 往復が増える頼み方
1. 「設定画面を作って」
2. 「ダークモードの切り替えを足して」
3. 「切り替えた状態を保存して」

✅ 1回にまとめた頼み方
「設定画面を作ってください。ダークモードの切り替えトグルを含め、
選んだ状態は端末に保存し、次回起動時に復元してください。
画面上部にタイトル、その下に設定項目を縦に並べてください。」
```

まとめた指示が三回分より必ず安くなる、と言い切れるほどの実測は、私はまだ取れていません。ただ、まとめて頼んだ日は「⋯」メニューで見る1通あたりの消費が読みやすくなり、月末の着地も外しにくくなりました。

## 残高が想定より減るときの切り分け

料金で詰まる場面は、だいたい次のどれかに当てはまります。症状から引いていただければと思います。

## よくある誤解の訂正

**誤解1：「Rork Max は$200の上位製品」**——2026年11月時点では、Rork Max は $20 から始まる唯一の有料プランで、段階による機能差はありません（公式：「Every Rork Max option includes the full feature set, from $20/mo」）。以前の「Max＝$200 の別製品」という理解のまま比較すると、必要のない $200 を選びがちです。

**誤解2：「無料のままでもストアに出せる」**——無料プランはデザインモードだけで、ビルドも公開もできません。公式の FAQ にも、動くアプリを作って公開するには Rork Max が必要だと書かれています。

**誤解3：「Rork は Expo（React Native）でアプリを作る」**——新しいプロジェクトは、iPhone が Swift、Android が Kotlin、Web が React です。Expo のプロジェクトは新しく作れなくなりましたが、既存のものはビルド・公開・GitHub への書き出しを続けられます（[What happened to Expo?](https://docs.rork.com/expo)）。手元の Expo プロジェクトをどうするかは、[Rork の新規作成から Expo が消えました。手元のプロジェクトを続けるか、SwiftUI へ作り直すか](/articles/rork-basics/rork-expo-no-longer-new-keep-or-rebuild-swiftui)で判断の順を書いています。

年払いについても触れておきます。2026年11月時点の公式の料金ドキュメントには月額の段階だけが載っており、年払いの選択肢は私の確認した範囲では見つかりませんでした。年払いの割引を前提にした計算は、公式で確かめられるまで置いておくのが安全です。

## 広告収益から、どの段階まで回収できるかを逆算する

ツール代が高いか安いかは、感覚ではなく「回収に必要なユーザー規模」に直すと判断がぶれません。私は広告収益型の壁紙アプリを長く運用してきたので、月額を見るとつい「何 DAU 分か」に換算してしまいます。

前提は控えめに置きます。1 DAU（1日のアクティブユーザー）あたり1日3回の広告表示、30日。eCPM は $1・$2・$5 の三通りです。

```js
#!/usr/bin/env node
// breakeven.mjs — Rork Max の段階ごとの月額を「回収に必要な DAU」へ翻訳する。
// eCPM と1 DAU あたりの表示回数は、AdMob の実測値に差し替えて使います。
const OPTIONS = [20, 200, 500];   // 2026年11月時点の Rork Max の段階（USD/月）
const IMPRESSIONS_PER_DAU = 3;    // 1 DAU が1日に見る広告の回数（控えめな値）
const DAYS = 30;
const ECPMS = [1, 2, 5];          // 控えめ / 標準 / 良好

for (const ecpm of ECPMS) {
  const perDau = (IMPRESSIONS_PER_DAU * DAYS * ecpm) / 1000;
  const cells = OPTIONS.map((usd) => `$${usd}: ${Math.ceil(usd / perDau).toLocaleString("en-US")} DAU`);
  console.log(`eCPM $${ecpm}（1 DAU あたり月 $${perDau.toFixed(3)}） → ${cells.join(" / ")}`);
}
```

```
$ node breakeven.mjs
eCPM $1（1 DAU あたり月 $0.090） → $20: 223 DAU / $200: 2,223 DAU / $500: 5,556 DAU
eCPM $2（1 DAU あたり月 $0.180） → $20: 112 DAU / $200: 1,112 DAU / $500: 2,778 DAU
eCPM $5（1 DAU あたり月 $0.450） → $20: 45 DAU / $200: 445 DAU / $500: 1,112 DAU
```

$20 の段階なら、eCPM $2 のアプリで112 DAU。1本きちんと回っているアプリがあれば届く水準です。$200 の段階は四桁の DAU が見えてから、という線になります。

ここで見落としやすいのが、アプリの中で Rork AI Cloud を使っている場合です。利用者が AI を呼ぶたびに、その原価（$1＝5クレジット）が自分の残高から引かれます。広告で回収する前に、**1 DAU あたりの AI の原価を差し引いた残りで損益分岐を見る**必要があります。AI 機能を入れたアプリでは、Cloud Usage の数字を月に一度は確かめておくと安心です。

`IMPRESSIONS_PER_DAU` の 3 は控えめな値です。表示回数を増やせば表の数字は良くなりますが、離脱も同時に増えます。定数を大きくして損益分岐を下げるのは、計算の上だけの改善になりやすいところでした。

## 必要になってから、必要な分だけ払う順番

ここまでの数字を、私自身の進め方に並べ直します。

1. **無料のうちに、設計を出し切ります**。画面・遷移・保存するものをデザインモードで決め、1日5クレジットの範囲で毎日少しずつ詰めます。
2. **ビルドを始める日に、$20 の段階へ移ります**。公開の締め切り直前ではなく、余裕をもって切り替えます。決済まわりで何か引っかかっても、締め切りに追われずに済むからです。
3. **足りない月は、追加購入で受け止めます**。買った分は繰り越されるので、多めに買っても次の月に回ります。
4. **境目の918を2か月続けて超えたときだけ、$200 の段階を検討します**。それまでは上げません。

ストアに出すまでには、Rork の外で払う費用もあります。Apple Developer Program の登録は Rork が代わりにできない手続きで、その手順は[Rork では自動化できない Apple Developer アカウントの手続き](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)にまとめています。初年度にどの請求がどの順で来るかは、[Rork で作ったアプリの初年度の請求の順番](/articles/rork-business/rork-first-year-bill-order-apple-google-eas-supabase-timeline)で時系列に並べました。料金を決めたあとに詰まりやすいのは、むしろこちらの手続きのほうです。

## 次に詰まる一歩：課金を足した日から、請求先が二つになる

$20 の段階でアプリを公開し、無事に動き始めた直後に当たりやすいのが、アプリ内の AI の請求です。自分がビルドで使うクレジットと、利用者が AI を呼ぶたびに減るクレジットが、同じ残高から引かれていきます。公開前には気にならなかった減り方が、利用者が増えるほど目立ってきます。

公開した週のうちに、Rork AI Cloud の月の上限額と、残高が少なくなったときの通知メール（既定は $5）を設定しておくと、月末に気づいて慌てることを防げます。上限に達しても止まるのはアプリの AI だけで、ビルドには影響しません。

料金の表は、覚えた日から古くなっていきます。まずは今日、ご自分の Settings → Credits を開いて、Subscription credits の行にある更新日を確かめてみていただければと思います。その日付から `credit-pace.mjs` を一度走らせるだけで、来月の段階をどうするかは、はるかに決めやすくなります。

料金ページの前で手が止まっていた方に、この整理がほんの少しでも役立てば幸いです。
