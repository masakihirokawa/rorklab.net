毎週火曜日にお届けしている Rork Lab の週間ピックアップです。5/19〜5/26 の8日間も、Rork で生成したアプリを本番運用に乗せる過程で生まれた実装記録が多く集まりました。今週特に読者の方が時間をかけて読んでくださったのは、いずれも「Rork で作って終わり」ではなく、「作ったあとに事業として回す」フェーズの記事です。

アーティスト・クリエイターの廣川政樹です。2014 年から個人でアプリ事業（累計5,000万DL）を続けながら、Rork を実際の壁紙アプリ運営に組み込んで検証しています。今週ピックアップする5本は、私自身の本番環境で動かして手応えがあった構成と、ハマったポイントの両方を等身大で書いたものです。

## 第1位：Rewarded × Interstitial × App Open を3層連携させて、ARPDAU を 1.4 倍にした設計メモ

[Rewarded × Interstitial × App Open を3層連携させて、壁紙アプリのARPDAUを1.4倍にした設計メモ](/articles/rork-business/rork-rewarded-interstitial-appopen-three-layer-arpdau-design)

今週もっとも読まれたのは、壁紙アプリの広告配信を「種別ごとにバラバラに最適化する」のではなく、3 層を連携させて設計しなおした記録です。Rewarded で「機能の解放」、Interstitial で「セッション切り替え」、App Open で「復帰時の収益化」を担当させ、それぞれの頻度ルールを互いに参照しあう構成にしてから ARPDAU が 1.4 倍になりました。

私自身、Rewarded だけを単独で見ていた時期は、Interstitial の頻度が読みにくく、ユーザーが離れる気配を感じていました。3 層連携にすると、「直近 X 分以内に Rewarded を見たユーザーには Interstitial を出さない」のような条件を自然に書けます。記事には、私が実際に使っている頻度ルールの JSON と、Rork 側からどう参照しているかのサンプルを共有しています。

```json
// 頻度ルールの簡易版（抜粋）
{
  "interstitial": {
    "min_session_seconds": 60,
    "skip_if_rewarded_within": 300
  },
  "app_open": {
    "min_background_seconds": 30,
    "skip_if_interstitial_within": 120
  }
}
```

## 第2位：Rork で作る iOS アプリに StoreKit 2 で買い切り課金を実装するノート

[Rork で作る iOS アプリに StoreKit 2 で買い切り課金を実装するノート](/articles/rork-dev/rork-storekit-2-in-app-purchase-implementation-memo)

Rork で生成した iOS アプリに買い切り課金を入れる場合、StoreKit 2 で書くのが結果的にいちばん見通しが良いと感じています。記事では、Product の取得から購入処理、トランザクション監視、復元処理までを async/await ベースで丁寧に追っており、Rork で出力したコードに「あとからどう被せるか」を実装サンプル付きで整理しました。

私の場合、壁紙アプリ 4 本に同じ買い切り課金ロジックを展開する必要があったので、共通レイヤを Swift Package として抽出し、Rork プロジェクトからは Package 越しに使う形に落ち着きました。記事ではその切り出しの判断と、Sandbox / TestFlight で詰まったポイントも共有しています。

## 第3位：Rork iOS アプリのメモリプレッシャー対策 — 5 段階解放アーキテクチャ

[Rork iOSアプリのメモリプレッシャー対策 — 壁紙アプリ運用で磨いた5段階解放アーキテクチャ](/articles/rork-dev/rork-ios-memory-pressure-5tier-release-architecture)

壁紙アプリは画像を大量に扱う性質上、メモリ管理の良し悪しがそのままクラッシュ率に跳ね返ります。記事では、私が個人開発 12 年で磨いてきた「メモリプレッシャーが警告→重大→緊急と上がるにつれて、どの段階で何を解放するか」を 5 段階に分けて整理しました。

特に、UIImage キャッシュ・遅延読み込みの中間バッファ・WebView の DOM・バックグラウンドタスクの一時データ、といった解放の優先順を間違えると「肝心の表示画像だけが消える」事故が起きます。Rork で生成したコードに対しても、この 5 段階を上から順に差し込んでいけば、デバイス世代の幅広いユーザーを取りこぼしません。

## 第4位：Rork で月額 100 円のアプリを黒字化するまで — AdMob と RevenueCat の 5 月実測値

[Rork で月額 100 円のアプリを黒字化するまで — AdMob と RevenueCat の 5 月実測値で見る個人開発の判断軸](/articles/rork-business/rork-100yen-monthly-app-breakeven-admob-revenuecat-may-2026-actual-metrics)

「月額 100 円のサブスクで黒字になるのか？」という問いに、5 月の実測値を持って答える記事です。AdMob の併用、RevenueCat の Trial 設定、解約タイミングの分布、サポートにかかる工数まで含めた P/L を、できるだけ生のままで載せました。

結論から言えば、月額 100 円であっても、AdMob 併用と適切な Trial 設定があれば、私のような個人開発（1 アプリ）でも黒字化に届きます。ただし、サポート工数が見積もりより重く乗ってくる点だけは要注意です。記事では、その「想定外コスト」をどう減らしたかも具体例で書いています。

## 第5位：Rork プロジェクトに AppLovin MAX を後付けした実装ノート — 初期化順序・ATT 同意・eCPM 検証

[Rork プロジェクトに AppLovin MAX を後付けした実装ノート — 初期化順序・ATT 同意・eCPM 検証の三軸メモ](/articles/app-dev/rork-applovin-max-ios-integration-att-ecpm-notes)

Rork で生成したプロジェクトに、あとから AppLovin MAX を組み込んだ際の実装記録です。初期化の順序を間違えると、ATT の同意ダイアログより先にメディエーション SDK が動き出してしまい、結果として配信が大きく落ちます。記事ではこの初期化順序の罠と、確実に直す手順を共有しています。

その後、AppLovin MAX を本番に乗せてからの eCPM 検証は、第 1 位の記事と同じく多層的に設計するのが効きました。Rork で素早く土台を作り、収益化のロジックを後から重ねるアプローチが、個人開発のスピード感には合っています。
