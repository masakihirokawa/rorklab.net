承認のメールが届いたのは、日本時間の午前3時すぎでした。

そのときは「自動でリリース」を選んだまま提出していたので、私が寝ているあいだにストアの表示が新しいバージョンへ切り替わっていました。告知の文面はまだ下書きで、スクリーンショットの差し替えも翌日に回す予定でした。実害はありませんでしたが、順番が逆になったことだけが妙に後を引きました。

審査にかかる時間は、こちらから短くできません。ただ、**審査が明けた瞬間にそのまま公開する必要はありません**。承認と公開は、両ストアとも別々のスイッチとして用意されています。ここを分けておくだけで、待ち時間の読めなさが公開作業に波及しなくなります。

この記事は、Rork で作ったアプリを EAS でストアへ出している方が、「審査がいつ終わるか分からないせいで告知や差し替えの段取りが崩れる」状態から抜け出すためのものです。設定画面の名前と挙動は 2026年11月時点で確認した内容で、画面の文言は今後変わる可能性があります。

いちばん見落としやすいのは最後の行です。Rork から書き出したプロジェクトを EAS で提出していると、公開のタイミングまで `eas.json` で決まっていそうに見えます。実際にはストア側の設定が上位にあり、片方だけ変えると噛み合わなくなります。

もう一つ、表の中段に「公開後の広がり方」を入れました。公開の**瞬間**を選ぶ設定と、公開した版を**どこまで一度に配るか**の設定は別物です。前者は告知の段取りを守り、後者は不具合が出たときの被害の範囲を小さくします。両方を組み合わせて、ようやく「審査の外側で決める」が完成するのだと思います。

3つめの日時は、入力した時点の自分のタイムゾーンで解釈されます。海外向けの告知と合わせる場合、ここで時差を一度計算しておかないと、意図した時間帯からずれます。また、指定日より審査が長引いた場合は、承認された時点で公開されます。「指定日に必ず出る」設定ではなく、「指定日より前には出ない」設定だと捉えておくと誤解がありません。

私は既定を「手動でリリース」にしています。理由は単純で、**承認の連絡が来る時刻をこちらで選べない**からです。深夜に承認されても、朝いちばんに自分の目でストアの表示を確認してから押せば、順番が入れ替わりません。

なお、この設定はバージョンごとに保持されるため、次のバージョンを提出するときにまた選ぶことになります。提出前チェックの項目に入れておくと取りこぼしが減ります。

### 「手動」を選んだあとに押す場所

承認されると、バージョンの状態が「デベロッパによるリリース待ち」になります。バージョン画面の右上に「このバージョンをリリース」のボタンが出るので、それを押した時点から公開の処理が始まります。押してから実際に検索や商品ページへ反映されるまでには、数時間のずれが出ることがあります。告知を投稿する時刻は、ボタンを押した時刻ではなく、自分の端末の App Store で新しいバージョンが見えた時刻を基準にしています。

## 段階的リリースは「公開の瞬間」のもう半分です

手動リリースで公開の瞬間を選べるようになっても、押した直後に全員へ新しい版が届くなら、不具合が出たときの逃げ場がありません。そこで、App Store には**段階的リリース**、Google Play には**段階的公開**が用意されています。

ここで、どちらをどんなときに選ぶかを一文にまとめると、**告知を伴う更新は「手動リリース＋段階的リリース」、告知のない修正版は「自動リリース＋段階的リリース」、緊急の不具合修正だけは段階を挟まず全員へ**、というのが私の線引きです。

最初のころ、私は段階的リリースを「慎重すぎる設定」だと思って使っていませんでした。ある更新で、特定の古い端末だけ起動直後に落ちる不具合を出してしまい、気づいたときには自動アップデートでほぼ全員に届いていました。結果は芳しくありませんでした。レビュー欄が荒れる速さに、胃が痛くなったのを覚えています。それ以来、告知のない修正版でも段階的リリースを外さないようにしています。

Google Play 側は、`eas submit` の設定から最初の割合を指定できます。

```json
{
  "submit": {
    "production": {
      "android": {
        "serviceAccountKeyPath": "./secrets/play-service-account.json",
        "track": "production",
        "releaseStatus": "inProgress",
        "rollout": 0.05
      }
    }
  }
}
```

`releaseStatus` を `inProgress` にすると段階的公開として扱われ、`rollout` に 0〜1 の割合を書きます。上の例は 5% から始める設定です。割合を上げる操作は Play Console のリリース画面で行います。最初の数パーセントでどこまで数字を信じてよいかは、[段階公開の最初の5%で見えた Crash-free 99.7%、何ユーザーから信じてよいのか](/articles/app-dev/staged-rollout-first-five-percent-crash-free-needs-sample-size-wait-before-proceed) で、私が待った日数と考え方をまとめています。

## Google Play は「公開の管理」を先に入れておきます

Play Console 側は、アプリ単位で **公開の管理**（Managed publishing）を有効にします。有効にすると、審査を通った変更が公開の概要に溜まり、こちらが「変更を公開」を押すまで公開されません。既定では、承認され次第そのまま公開されます。

有効にしておくと助かるのは、ストア掲載情報の変更とアプリ本体の更新を同時に出せることです。スクリーンショットだけ先に新しくなって、機能はまだ古い、という中途半端な状態を避けられます。

ここで、EAS で提出している場合に一度は踏みやすい箇所があります。Play Console 側に「審査に送信されていない変更」が残っている状態で `eas submit` を実行すると、変更を自動で審査へ送る動作とぶつかり、次のようなエラーで提出が止まることがあります。

```text
Google Api Error: Invalid request - Changes cannot be sent for review automatically. Please set the query parameter changesNotSentForReview to true. Once committed, the changes in this edit can be sent for review from the Google Play Console UI.
```

この場合は `eas.json` 側で、審査へは自分で送る旨を明示しておきます。

```json
{
  "submit": {
    "production": {
      "android": {
        "serviceAccountKeyPath": "./secrets/play-service-account.json",
        "track": "production",
        "releaseStatus": "completed",
        "changesNotSentForReview": true
      }
    }
  }
}
```

`changesNotSentForReview` を `true` にすると、アップロードまでが EAS の担当になり、審査へ送る操作と公開の操作は Play Console 側に残ります。公開の管理を使い、Console で変更をまとめて送る運用なら、この2つはセットだと考えておくと迷いません。

逆に、Console 側に未送信の変更が無い状態でこの値を `true` にしていると、`changesNotSentForReview must not be set` という逆向きのエラーで止まることがあります。テスト用のアプリと本番のアプリで設定を使い回すときは、ここだけ見直してください。どちらのエラーも、設定ファイルの書き方より先に、Play Console の公開の概要に何が溜まっているかを見るほうが早く片づきます——いま思えば、私はこの順番を逆にして半日を使っていました。

## よくある誤解を3つ

**「手動リリースにすると審査が遅くなる」**——そうはなりません。リリース設定は承認された**あと**の挙動を決めるもので、審査の順番や所要時間には関係しません。Apple も Google も、審査の時間は開発者側で短縮できないものとして案内しています。

**「段階的リリース中は、新しい版を手に入れられない人がいる」**——App Store では半分だけ正しい言い方です。段階的リリースが絞るのは自動アップデートで、ストアの商品ページから自分で更新する人には最初から新しい版が届きます。Google Play の段階的公開は割合の外にいる人には届かないので、ここは両ストアで挙動が違います。

**「`eas.json` に書けば公開のタイミングまで決まる」**——決まるのはアップロードの扱いまでです。iOS のリリース設定は App Store Connect のバージョン画面、Android の公開の管理は Play Console が持っています。`eas.json` はそこに合わせて書く側だと考えておくと、噛み合わない事故が減ります。

## 期限のある配信は、逆算の起点を審査の手前に置きます

公開日を自分で決められるようにしても、審査の所要時間そのものは不確定なままです。対象 API レベルの期限のように、外側から日付が決まっている配信では、そのぶんを見込んで逆算します。

私が実際に使っている見込みは、次の3つです。

1. **リジェクト1回ぶんの往復を最初から日程に入れておく**。初回で通ることを前提にすると、指摘が来た時点で日程が崩れます。
2. **TestFlight の外部テストを先に通しておく**。外部テスターへの配布にはベータ App Review が必要で、これは製品版の審査とは別の枠です。バージョンの初回ビルドで一度通しておくと、権限の説明文やメタデータのような、審査で指摘されやすい部分を前倒しで拾えます。内部テスターだけならこの審査は挟まりません。外部テストと段階的リリースのどちらに時間を使うかは、[TestFlight の外部テストと段階公開、個人開発ではどちらに時間を使うか](/articles/app-dev/rork-testflight-external-beta-vs-phased-release-decision) で比べています。
3. **提出そのものの締切を、公開希望日から数日前に置く**。「この日までに出す」を決めておかないと、審査待ちの時間を微修正で食い潰します。

Android 側の期限が絡む更新については、[Rork のプロジェクトで targetSdkVersion 36 を通すまでに直した3か所](/articles/app-dev/rork-android-target-api-36-effective-targetsdkversion-audit) に、実際に直した箇所をまとめてあります。提出まわりで番号が衝突したときは [「Version code 1 has already been used」の番号は、app.json と EAS のどちらが持っているか](/articles/rork-dev/rork-play-version-code-already-used-who-owns-the-number) が近い話です。

## 次に詰まりやすいのは、リジェクトの返信です

公開の瞬間を握れるようになると、次に日程を揺らすのはリジェクトです。白い画面や権限の説明不足のように、指摘の文面だけでは原因が見えにくいものほど往復が長くなります。Expo のリリースビルドで起きやすいものは [App Review で「Guideline 2.1・白い画面」と言われたとき、Expo のリリースビルドで疑う3か所](/articles/app-dev/app-review-guideline-2-1-blank-screen-expo-release-build-checklist) に書き残しました。返信する前に、手元のリリースビルドで同じ画面が再現するかを確かめておくと、往復を1回減らせることが多いと感じています。

## 今日のうちに変えておける設定

次の提出を待たずに済ませられるものが2つあります。

Play Console を開いて、対象のアプリで公開の管理を有効にしてください。`eas submit` を使っているなら、あわせて提出プロファイルの `changesNotSentForReview` を、Console で審査へ送る運用に合わせて見直します。これはアプリ単位の設定なので、一度入れれば以降の提出に効き続けます。

App Store Connect のほうは、提出のたびに選び直す項目です。提出前の手順書に「リリース設定を手動へ・段階的リリースを有効に」の1行を足しておくのがいちばん確実でした。

**承認はストアが、公開の瞬間と広がり方は私が。** 審査の列に並んでいるあいだ、こちらにできることは多くありません。それでも、列を抜けた先の手順だけは自分の手元に残せます。まずは次の提出の前に、手順書へその1行を足すところから始めていただければと思います。
