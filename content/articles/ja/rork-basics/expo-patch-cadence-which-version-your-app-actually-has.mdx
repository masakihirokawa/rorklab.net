「起動が遅い」というレビューがついたまま、しばらく手を付けられずにいたアプリがあります。Expo 側で起動時間の退行が直ったパッチが出たと知り、これでひとつ片づくと思って package.json を開きました。

そこには `"expo": "~57.0.9"` と書いてありました。チルダが付いているのだから、パッチは自動的に新しいものが入っているのだろうと考え、何も変えずにビルドを回しました。

結果は変わりませんでした。入っていたのは、9つ前の 57.0.9 のままでした。

レンジの書き方を覚えているつもりで、実際に何が入るのかを一度も確かめていなかったのだと気づきました。恥ずかしい話ですが、個人開発で複数のアプリを抱えていると、この種の思い込みは静かに何か月も残ります。npm のふるまいを実際に走らせて確かめた記録を残します。

## package.json のレンジは「入る版」を決めていません

次に、レンジの書き方ごとに実際どの版が選ばれるのかを確かめます。空のプロジェクトを作り、dependencies に expo だけを書いて、lockfile だけを生成させます。

```bash
npm install --package-lock-only
```

書き方を5通り試した結果です。

<table>
  <thead>
    <tr><th>package.json の指定</th><th>解決された版</th></tr>
  </thead>
  <tbody>
    <tr><td><code>57.0.9</code></td><td>57.0.9</td></tr>
    <tr><td><code>~57.0.9</code></td><td>57.0.18</td></tr>
    <tr><td><code>^57.0.9</code></td><td>57.0.18</td></tr>
    <tr><td><code>57.0.x</code></td><td>57.0.18</td></tr>
    <tr><td><code>"*"</code>（制約なし）</td><td>57.0.18</td></tr>
  </tbody>
</table>

チルダもキャレットも、この場面では同じ 57.0.18 に落ちました。57.0.x でも、何も制約しない場合でも同じです。マイナーをまたぐ更新がまだ出ていない時期には、チルダとキャレットの差は表に出てきません。

ただし、両者が同じものというわけではありません。チルダは指定したマイナーの内側でパッチだけを許すので、`~57.0.9` は 57.0.18 まで受け入れて 57.1.0 の手前で止まります。キャレットはマイナーの更新も許すので、`^57.0.9` は 57.1.0 や 57.4.2 が出ればそちらを取ります。いまは 57.1.x がまだ公開されていないため、結果として同じ行になっているだけです。最初の新しいマイナーが出た日から、キャレットで書かれたプロジェクトだけが、誰もファイルを触っていないのに新しい変更を取り込み始めます。公開しているアプリでどちらを使うかは、そのうえで決めたいところです。ただ、expo 本体については事情が少し違います。その点は後半の思い込みの節で触れます。

そして、これがつまずきの元でした。この表が示しているのは「ゼロから解決させたときに何が選ばれるか」です。すでに動いているプロジェクトで `npm install` を打ったときに何が入るか、ではありません。

## 決めているのは package-lock.json のほうです

同じ検証を、lockfile がある状態から始めてみます。

1. `"expo": "57.0.9"` と固定して lockfile を作ります
2. package.json のほうだけ `"expo": "~57.0.9"` に書き換えます
3. lockfile を残したまま `npm install` を打ちます

実行した結果です。

```text
step1 lock固定:        57.0.9
step2 lockあり install: 57.0.9
step3 lockなし install: 57.0.18
```

step2 が答えでした。package.json に `~57.0.9` と書いてあっても、lockfile が 57.0.9 を指していて、それがレンジの内側に収まっている限り、npm はその版を維持します。上げにいってはくれません。

step3 は lockfile を消してから打った場合です。同じ package.json から 57.0.18 が入りました。つまり lockfile を Git に入れていないと、手元とビルドサーバーで別の版が入りうるということでもあります。ファイル名の大文字小文字が手元とサーバーで違って見える問題と、原因の形はよく似ています。関連する話は[Sunset.png と sunset.png は、手元の Mac では同じファイル、ビルドサーバーでは別のファイルです](/articles/rork-basics/asset-filename-case-mac-vs-build-server)に書きました。

Rork からコードをエクスポートして手元で開発を始めた場合は、最初のコミットに package-lock.json が含まれているかを確認しておくと安心です。無視する側に入れてしまうと、ビルドのたびに版が動きます。[Rork のコードをエクスポートしたら、git init より先に .gitignore を用意します](/articles/rork-basics/rork-export-gitignore-before-git-init)も併せてどうぞ。

## ずれているかどうかは npm ci が教えてくれます

package.json と lockfile の食い違いは、`npm install` では黙って解決されてしまいます。声を上げてほしいときは `npm ci` を使います。

lockfile が 57.0.9 を、package.json が `~57.0.15` を指す状態で走らせた実際の出力です。

```text
npm error code EUSAGE
npm error `npm ci` can only install packages when your package.json and
npm error package-lock.json or npm-shrinkwrap.json are in sync.
npm error Invalid: lock file's expo@57.0.9 does not satisfy expo@57.0.18
```

止まってくれます。CI やビルド用のスクリプトで `npm install` ではなく `npm ci` を使う理由のひとつがここにあります。食い違ったまま気づかずに進むのではなく、その場で落ちてくれるほうが、後から原因を探すより安く済みます。

いま入っている版を1行で見たいだけなら、lockfile を直接読むのが速いです。

```bash
node -p "require('./package-lock.json').packages['node_modules/expo'].version"
```

クラウドのビルドサービスも同じ規則で動きます。EAS Build は既定で `npm ci` のように lockfile を書き換えない方法で依存を入れるので、3月から動いていない lockfile があれば、今日回したビルドも3月の中身になります。package.json にどんなレンジが書かれていても関係ありません。レンジの内側に収まっている限り npm から見れば何も間違っていないので、警告も出ません（根拠となる公式の記述は後半の思い込みの節に書きます）。

パッケージマネージャが違っても、考え方は変わりません。Yarn なら yarn.lock、pnpm なら pnpm-lock.yaml が同じ役割を担い、どちらもレンジより先に lockfile を見ます。手元にあるのがどのファイルであれ、実際の版を記録しているのはそちらで、package.json のほうは意思表明に近いものだと捉えると混乱が減ります。

## 遅れの大きさだけ知りたいときは npm outdated です

上げるかどうかを決める前に、いまの位置を測っておきたい場面があります。そのための標準コマンドが `npm outdated` です。

```bash
npm outdated expo
```

出力には Current（いま node_modules に入っている版）、Wanted（package.json のレンジの範囲で取れる最新）、Latest（レジストリの最新）の3列が並びます。Current と Wanted が離れていれば、レンジ内でも上げ忘れている状態です。Wanted と Latest が離れていれば、レンジの外に新しい版があります。

私は以前、Latest の列だけを見て「まだ大きな更新は出ていない」と安心していました。ところが本当に見るべきだったのは Current と Wanted の差で、そこに9つぶんの開きがあったのだと、後から気づきました。3列をセットで読む癖をつけておくと、同じ読み違いは減らせるのではないかと思います。

## 上げると決めたときに打つもの

上げる意思があるときは、版を明示して install します。レンジの外を指定すれば、lockfile も一緒に書き換わります。

```bash
npm install expo@57.0.18
npx expo install --fix
```

2行目は、expo に紐づく他のパッケージの版を、その SDK が想定する組み合わせへ揃えるためのものです。expo だけを上げて周辺を放置すると、噛み合わない組み合わせのまま動かすことになります。

もうひとつ。ネイティブのディレクトリを手元に持っている構成では、上げたあとの prebuild で手を入れた変更が消えることがあります。上げる前に何が消えるのかを見ておく手順は[Expo SDK 57 に上げる前に、prebuild で消えるネイティブ変更を洗い出す](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit)にまとめています。

メモリの膨らみを疑って自分のコードを読み込む前に、まず版を確かめるという順番も同じ話です。そちらは[メモリが膨らむ原因を自分のコードに探す前に、worklet の数を数えてください](/articles/rork-dev/hermes-v1-worklet-memory-count-before-blaming-your-code)で触れました。

測り直してみて気づいたのは、私が信じていたのはいつも「どこかに書いた数字」のほうで、レジストリと lockfile に聞いた結果ではなかった、ということでした。同じ思い込みは、別のパッケージでもまだどこかに残っているのかもしれません。いまは次の線引きにしています。

**版は、書いた範囲ではなく、記録された一行で確かめます。**

## よくある思い込みを三つ、公式の記述で正します

一つ目は「キャレットにしておくと、次の SDK まで勝手に上がってしまう」という心配です。npm のキャレットは、いちばん左の 0 でない桁を動かしません。expo パッケージは SDK の切り替えをメジャー番号の更新（57 → 58）として出しているため、`^57.0.9` が SDK 58 を取ることはありません。上の表で 57.0.33 に止まったのはそのためです。前の節で書いたチルダとキャレットの違いは semver の規則としては正しいのですが、expo 本体に限っては、マイナー番号の更新がほとんど出ないため、実際の差は小さいのです。SDK を上げるのは、いつでも自分で版を書き換えたときだけです。

二つ目は「`npm outdated` の Current は lockfile の版」という理解です。npm の公式ドキュメントでは、Current はいまインストールされている版、Wanted は package.json のレンジを満たす最大の版、Latest はレジストリで latest タグが付いた版と説明されています。node_modules がまだ無い状態で打つと、Current には MISSING と出ます。lockfile に書かれた版を知りたいときは、前の節の `node -p` の1行か、`npm ls expo --package-lock-only` を使います。

三つ目は「クラウドのビルドは、毎回いちばん新しいパッチで組み立ててくれる」という期待です。EAS Build の公式ドキュメント（Cache dependencies の Immutable lockfiles）には、Node のパッケージは既定でパッケージマネージャの「lockfile を書き換えない」方法（`npm ci` や `yarn --frozen-lockfile` など）で入れると書かれています。lockfile が古ければ古い版のまま組み立てられ、package.json と食い違っていればインストールの段階で止まります。この挙動を外す `EAS_NO_FROZEN_LOCKFILE` という環境変数もありますが、私は外さずに使っています。

版のずれは、症状だけを見ると別の不具合に見えることが多いです。詰まったときに当てはまる行から確かめてください。

三行目は、私がいちばん長く手を止めた症状です。ビルドのログに出ているのが Expo のエラーではなく npm のエラーだと気づくまで、アプリのコードを疑い続けていました。

`npx expo install --check` は、公式ドキュメントによると CI の環境（`CI=1`）では食い違いがあると 0 以外で終わります。ビルドの前に1行足しておくと、組み合わせのずれを早いうちに止められます。

```bash
CI=1 npx expo install --check
```

## 版を上げた直後に、次に詰まりやすいところ

版を確かめたついでに SDK まで上げると、手元の Expo Go で開けなくなることがあります。プロジェクトの SDK と Expo Go 側の対応がずれているときの見分け方は、[「Project is incompatible with this version of Expo Go」と出たとき、プロジェクトを疑う前に見る三か所](/articles/app-dev/expo-go-project-incompatible-error-check-client-version-before-project)に書きました。

もうひとつは、SDK そのものを上げる日に、ビルド環境の Xcode やパッケージマネージャまで一緒に動いてしまう件です。eas.json の書き方ひとつで変わるので、[eas.json に image を書かないままだと、SDK を上げた日に Xcode も pnpm も一緒に動きます](/articles/app-dev/eas-json-image-alias-auto-what-moves-on-sdk-bump)も併せてご覧いただければ幸いです。

## 今日、最初にやること

エディタで package.json を眺めるのをやめて、package-lock.json のほうを開いてください。node_modules/expo の version を1行見ます。それだけで、自分のアプリが9つ前にいるのか、先頭にいるのかが分かります。

私自身、個人開発で回しているアプリのひとつで、これを確かめずに、直ったはずの退行を1か月ぶんそのままにしていました。同じ回り道をされないよう、この記録が少しでも役に立てば幸いです。
