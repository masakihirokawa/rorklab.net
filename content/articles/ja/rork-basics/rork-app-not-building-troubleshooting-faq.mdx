個人開発でアプリを作っていると、ビルドが通らない夜に必ず当たります。エラーの文面を検索して、出てきた手順を片っ端から試して、気づけば別の場所まで壊していました。最初のうち、私はこの回り道をたびたびしていました。

いま振り返ると、原因は「手順を知らなかったこと」より、**どの層で起きているのかを見ずに直そうとしたこと**にありました。依存パッケージの問題なのか、開発環境の問題なのか、Rork 側の生成の問題なのか。層がわかれば、試す手順はほとんど一つに絞れます。

この FAQ は 8 つの症状を、その層ごとに並べ直したものです。上から順に読むより、いま出ている症状の Q だけ開いていただければ十分です。

## Q1: 「ビルドに失敗しました」と出ます。依存関係の競合とは何ですか？

**A:** もっとも多い原因は、複数のパッケージが互いに合わないバージョンを要求している状態です。たとえばパッケージ A はライブラリ X の 1.x を、パッケージ B は 2.x を必要としている、といった具合です。

エラーログに `conflicting peer dependency` や `ERESOLVE` と出ていれば、ほぼこれです。

```bash
# 依存を作り直す（node_modules と lock を捨てて入れ直す）
rm -rf node_modules package-lock.json
npm cache clean --force
npm install
```

それでも `npm install` が止まる場合は、`--legacy-peer-deps` を付けると peer 依存の厳密なチェックを緩めて進められます。

```bash
npm install --legacy-peer-deps
```

:::warning
`--legacy-peer-deps` は競合を「解決」するのではなく「見ないことにする」オプションです。通ったあとでアプリが起動するか必ず確かめ、動かなければ、ログに名前が出ているパッケージのバージョンを揃える方向へ戻ります。
:::

Expo SDK に紐づくパッケージ（`expo-*` や `react-native-*` の一部）は、`npm install` ではなく次のコマンドで SDK 版に合う版へ揃えるのが安全です。

```bash
npx expo install --fix
```

最初のうち、私は `ERESOLVE` が出るたびに `--legacy-peer-deps` で押し通していました。ビルドは通るのですが、数日後に実機でだけ落ちるようになり、原因を辿ると、通したときに版のずれたネイティブモジュールが混ざっていました。胃が痛くなったのは、どこで混ざったのか履歴から追えなかったことです。

**フラグで通すのは確認のため、直すのは版を揃えることで。** いまはこの順番を崩さないようにしています。

## Q2: Expo モジュールが見つからないというエラーが出ます

**A:** `Unable to resolve module` や `Cannot find module` は、依存が入っていないか、Metro のキャッシュが古いかのどちらかであることがほとんどです。

Metro が出す文言は、だいたい次のかたちです。

```
Unable to resolve module expo-image from /app/(tabs)/index.tsx:
expo-image could not be found within the project or in these directories:
  node_modules
```

この場合、`expo-image` がまだ入っていないか、入れたのに Metro が古い一覧を覚えているかのどちらかです。

```bash
# 1. lock ファイルどおりに入れ直す（package-lock.json の場合）
npm ci

# 2. Metro のキャッシュを捨てて起動
npx expo start --clear
```

以前の記事や古い解説では `npm install -g expo-cli` を勧めているものがありますが、グローバルの expo-cli は現在は使わず、プロジェクト内の `npx expo ...` を使うのが基本です。グローバルに古い版が残っていると、プロジェクトの SDK 版とずれて余計な混乱を呼びます。

```bash
npx expo --version   # プロジェクトに入っている Expo の版が出れば OK
```

**手触りとして覚えておきたいのは**、`npm ci` は「lock に書かれた状態を再現する」コマンドで、`npm install` は「いまの状態から良さそうに整える」コマンドだということです。再現したいときは `ci` です。bun や yarn の lock を使っているプロジェクトでは、それぞれの「lock どおりに入れる」コマンド（`bun install --frozen-lockfile` など）に読み替えていただければ同じ考え方で進められます。

入れ直しても同じ文言が出るときは、import の綴りと、パッケージ名の大文字小文字を確かめます。macOS は大文字小文字を区別しない設定が多いため、手元では動くのにビルドサーバーでだけ失敗する、ということが起きます。

## Q3: iOS シミュレーターが起動しません

**A:** 層は開発環境です。コードはほぼ関係しません。順に疑う場所は 3 つです。

**Xcode とコマンドラインツール**（macOS のみ）

```bash
xcode-select --install
xcode-select -p   # パスが表示されれば有効
```

ここで `xcode-select -p` が `/Library/Developer/CommandLineTools` を指していると、`xcrun: error: unable to find utility "simctl"` が出ます。Xcode.app 側へ向け直します。

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

**シミュレーターの実体**

```bash
xcrun simctl list devices available
xcrun simctl boot "iPhone 16 Pro"   # 一覧に出た名前を指定
```

**ポート 8081 の取り合い**

```bash
lsof -i :8081          # 占有しているプロセスを確認
npx expo start -p 8082 # 別ポートで起動
```

:::tip
どうしてもシミュレーターが言うことを聞かない夜は、実機の Expo Go で確認する手があります。シミュレーター固有の不具合を丸ごと迂回できるので、アプリ側の問題かどうかを先に確かめられます。
:::

## Q4: Android エミュレーターが白い画面のまま動きません

**A:** 白い画面は「何も描画できていない」状態で、原因はビルド未完了、JDK、エミュレーターの余力、接続の 4 か所に分かれます。

まず Metro のキャッシュを捨てて再起動します。

```bash
npx expo start --clear
```

ターミナルに bundling の進行が出ているのを確かめてから、エミュレーターを `r` でリロードします。進行が出ていない場合は、エミュレーターではなくターミナル側に原因があります。

JDK を確認します。

```bash
java -version
```

React Native 公式の環境構築ページは、2026年11月時点で JDK 17 を推奨しています。別の版が出る場合は、Android Studio に同梱の JDK を指すよう `JAVA_HOME` を設定し直すのが近道です。将来この推奨は変わりうるので、お使いの版の公式ページで一度だけ確かめていただければ安心です。

ビルドの途中で `SDK location not found` が出る場合は、JDK ではなく Android SDK の場所が分からない状態です。

```bash
echo $ANDROID_HOME   # 空ならまだ設定されていない
# macOS の既定の場所（Android Studio で変えていなければ）
export ANDROID_HOME=$HOME/Library/Android/sdk
export PATH=$PATH:$ANDROID_HOME/emulator:$ANDROID_HOME/platform-tools
```

シェルの設定ファイル（`~/.zshrc` など）に書いておかないと、ターミナルを開き直すたびに消えてしまいます。

エミュレーターのメモリが少ない場合は、Android Studio の Device Manager から該当デバイスを編集し、RAM を増やします。それでも改善しなければ、一度 Cold Boot（保存済み状態を使わない起動）を試します。

:::warning
白い画面のとき、画面そのものを見つめても答えは出ません。**答えはたいていターミナルの赤い行に書いてあります。**
:::

## Q5: プロンプトからアプリが生成されません。生成が止まってしまいます

**A:** 層は Rork 側と通信です。コードを触る前にできることが 3 つあります。

1 つ目は、**プロンプトを小さくすること**。機能を一度にすべて書き込むと、生成が長引いて止まったように見えます。基本機能だけで作らせて、あとから足すほうが結果は安定します。

```
// 詰め込みすぎ
「チャットアプリ。リアルタイム通知、プロフィール画像、検索、
グループ、ボイスメッセージ、ビデオ通話、ブロック、既読…」

// 小さく始める
「チャットアプリ。ユーザーはメッセージを送受信できる。
UI はシンプルで十分。」
```

2 つ目は、通信の確認です。Wi-Fi が不安定なときは生成が途中で止まります。切り替えてから、もう一度試します。

3 つ目は、ブラウザ側の余裕です。タブを多く開いていると重くなります。不要なタブを閉じ、改善しなければ別のブラウザで試します。

## Q6: 画像やアイコンが表示されません

**A:** 多くはパスかパッケージ名の取り違えです。

画像は相対パスの階層を 1 つ間違えるだけで消えます。

```javascript
// ファイルの位置に対してパスを数え直す
<Image source={require('../../assets/images/my-image.png')} />
```

アイコンは、`@expo/vector-icons` を使うのが標準です。パッケージ名の取り違えがよくあります。

```bash
npx expo install @expo/vector-icons
```

ファイル名にスペースや日本語が入っていると、環境によって解決に失敗します。英数字とハイフンかアンダースコアだけにしておくと安全です。表示が古いままなら、`npx expo start -c` でキャッシュを捨てます。

## Q7: ホットリロードが効きません。変更が反映されません

**A:** 現在の Expo では Fast Refresh が既定で有効なので、`--hot` のようなフラグは不要です。効かないときは、次の順で確認します。

1. **保存されているか**。エディタのタブに未保存の印が付いていないか。
2. **構文エラーがないか**。赤いエラー画面が出ていれば、直すまで反映されません。
3. **接続が切れていないか**。端末と開発 PC が同じネットワークにいるかを確認します。
4. **開発者メニューから Reload**。iOS シミュレーターは `Cmd + D`、Android エミュレーターは `Cmd + M`（Windows は `Ctrl + M`）です。Metro を動かしているターミナルで `m` を押しても開けますし、`r` だけでリロードできます。

それでも直らなければ、Metro を止めて `npx expo start --clear` で起動し直します。

:::tip
React コンポーネント以外のもの（定数や関数）も export しているファイルを編集すると、Fast Refresh はその部分だけの差し替えをあきらめて、関係するモジュールを読み直します。コンポーネントの外から import されているファイルなら、アプリ全体のリロードになります。入力中の状態が消えるのはこのためで、故障ではありません。
:::

## Q8: 「Fix Now」ボタンは使っても大丈夫ですか？

**A:** 使いどころを選べば、とても頼れます。Rork はビルドや実行でエラーが起きると、エラー内容のすぐ下に「Fix Now」を表示することがあります。エラーメッセージと前後のコードを AI に渡し、修正案を適用する機能です。

**得意なのは、原因がメッセージに書いてあるエラーです。** 閉じ忘れた括弧、import の書き忘れ、存在しない関数名、型の不一致など。この種類は、一度押すだけで解決することが多いです。

**苦手なのは、コードの外に原因があるエラーです。** 依存関係の競合（Q1）、シミュレーターやエミュレーターの不調（Q3・Q4）、生成のフリーズ（Q5）。これらは「コードを直す」問題ではないので、見当違いの修正が当たってしまうことがあります。

私は次の順で使っています。

1. まず、メッセージを一度自分で読みます
2. 構文や import 系のエラーなら、Fix Now を押します
3. 適用された差分に、必ず目を通します
4. 同じ Fix Now を 2 回続けても直らなければ、止めて Q1〜Q7 の層の切り分けに戻ります

**中身を見ずに押し続けないこと**——この一線だけは守るようにしています。AI が別の場所まで書き換えて、状況がかえって複雑になることがあるからです。

## npm install・npm ci・npx expo install の使い分け

3 つとも「パッケージを入れる」コマンドですが、守ってくれるものが違います。私が迷ったときの判断の基準は、表の右端の列です。

<table>
<thead><tr><th>コマンド</th><th>やること</th><th>lock ファイル</th><th>選ぶとき</th></tr></thead>
<tbody>
<tr><td><code>npm ci</code></td><td>lock の状態を丸ごと再現</td><td>変えない（ずれていれば止まる）</td><td>昨日まで動いていた状態に戻したい</td></tr>
<tr><td><code>npm install</code></td><td>package.json の範囲で良さそうな版を入れる</td><td>書き換えることがある</td><td>Expo と無関係なパッケージを足す</td></tr>
<tr><td><code>npx expo install</code></td><td>SDK 版に合う版を選んで入れる</td><td>書き換える</td><td><code>expo-*</code>・ネイティブを含むパッケージを足す・直す</td></tr>
</tbody>
</table>

**ネイティブのコードを含むパッケージは `npx expo install`、それ以外は `npm install`、戻したいときは `npm ci`。** この一文だけ覚えておけば、Q1 と Q2 の大半は起きる前に避けられます。

## よくある誤解

**「`--legacy-peer-deps` で通れば解決」**——通るのは依存の確認を飛ばしただけで、版のずれは残ります。Q1 のとおり、通ったあとに起動を確かめ、ずれたパッケージを揃えるところまでが一続きの作業です。

**「`expo-cli` をグローバルに入れ直せば直る」**——グローバルの旧 `expo-cli` は Expo 公式ドキュメントで旧版（アーカイブ）扱いになっており、現在はプロジェクトに入っている CLI を `npx expo` で呼ぶ形です。入れ直すほど、プロジェクトの版とずれる原因が増えてしまいます。

**「Fix Now が直せないなら Rork の不具合」**——Q8 のとおり、Fix Now が触れられるのはコードだけです。依存や開発環境の層にある原因は、コードをどれだけ書き換えても消えません。止まったら層を疑う、という順番で十分なのです。

## 直したあとに当たりやすい次の壁

ビルドが通った直後に、もう一段先で詰まる方が多いところを挙げておきます。

`npx expo-doctor` が全部通ったのに Play Console で弾かれる場合は、[expo-doctor の点検項目に入っていない API レベルの確認](/articles/rork-basics/expo-doctor-22-checks-api-level-36-blind-spot)をご覧ください。ビルドは通ったのに、実機の Expo Go でプレビューが開かない場合は、[ターミナルとアプリ両方のログイン状態を揃える手順](/articles/rork-basics/expo-go-login-both-terminal-and-app-preview-not-opening)が近道です。

Q1 の版ずれが何度も起きる方は、そもそも手元のアプリがどの Expo の版で動いているかを一度確かめておくと、次の更新が楽になります。[手元のアプリの Expo の版を確かめる方法](/articles/rork-basics/expo-patch-cadence-which-version-your-app-actually-has)と、[SDK を上げる前に削除済み API を洗い出すスクリプト](/articles/app-dev/expo-sdk58-removed-react-native-apis-scan-script-before-upgrade)をあわせて読んでいただければと思います。

## 次の一歩

ビルドエラーに出会ったら、まずエラーメッセージを最後まで読み、「パッケージ・開発環境・Rork 側・コード」のどの層かを一つ決めます。そのうえで、その層の Q だけを試します。

いま振り返ると、焦っているときほど最初の赤い行を飛ばしていたのだと思います。今夜ビルドが通らずに困っている方は、ターミナルの最初の赤い行をコピーして、早見表の症状と見比べてみていただければと思います。
