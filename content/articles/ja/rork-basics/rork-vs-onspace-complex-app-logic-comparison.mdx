「複雑なロジックのあるアプリを作るとき、RorkとOnspaceどちらが向いているんだろう」という質問に、「場合によります」という答えしか返せなかったのが少し前のことです。実際に両方を使ってみてから、もう少し具体的な判断基準が持てるようになりました。

ここでは単純なCRUDアプリではなく、バックエンド連携・状態管理・エラーハンドリングが絡む中〜複雑度のアプリ開発における両ツールの実際の挙動を比較します。

## Onspaceとはなにか

知らない方のために簡単に。Onspaceは2025年後半から注目を集めてきたAIアプリビルダーです。Rorkとの大きな違いは、バックエンドロジックをノーコード/ローコードで定義する仕組みを重視していること。フロントエンド生成よりも「データフローと処理の自動化」寄りの設計思想があります。

一方のRork Maxは、React Nativeコードを直接生成してExpoプロジェクトとして出力するアプローチ。コードが手元に残るため、複雑なカスタマイズもコードレベルで対応できます。

## 複雑なロジックの定義

「複雑なロジック」が何を指すかを先に整理しておきます。この記事では以下を想定しています:

- 外部API（決済、地図、AI）との連携が複数ある
- 非同期処理でエラーが起きたときのフォールバック処理が必要
- ユーザーの状態（認証・サブスクリプション・権限）によって表示内容が変わる
- バックグラウンド処理（プッシュ通知、定期実行）がある

これらを含むアプリを両ツールで試した印象をまとめます。

## Rork Maxが有利な場面

**コードの透明性とカスタマイズ性**
Rork Maxが生成するのはReact Native + Expo のTypeScriptコードです。生成されたコードはそのままGitHubにpushして管理できます。複雑なロジックで「AIが想定外のコードを書いた」ときでも、自分でコードを修正できる余地が大きいです。

実際に試したパターン:

```typescript
// Rork Maxが生成したStripe連携のエラーハンドリング骨格
const handlePayment = async (amount: number) => {
  try {
    const paymentIntent = await createPaymentIntent(amount);
    const { error } = await stripe.confirmPayment({
      clientSecret: paymentIntent.clientSecret,
    });
    if (error) {
      // ここを自分でカスタマイズできる
      handlePaymentError(error.type, error.message);
    }
  } catch (e) {
    // ネットワークエラー等のフォールバック
    showToast("接続エラーが発生しました。もう一度お試しください。");
  }
};
```

この骨格をベースに細部を調整する作業は、ゼロから書くよりずっと速いです。

**React Nativeエコシステムとの親和性**
npm パッケージをそのまま追加できるため、既存のReact Nativeライブラリ（react-query、zustand、react-native-reanimated等）を組み合わせられます。複雑なロジックを既存ライブラリで解決しやすい。

## Onspaceが有利な場面

**ノーコードでのデータフロー定義**
単純なデータの流れ（フォーム → バックエンド保存 → 通知送信）は、Onspaceのビジュアルフローエディタで素早く定義できます。コードを書かずにワークフローを組めるため、技術的な背景が薄いチームメンバーも参加しやすいです。

**バックエンドの自動スケーリング**
Onspaceは内蔵のバックエンドインフラを提供しているため、サーバー管理が不要です。アクセスが増えたときの対応を自動でやってくれます。Rork MaxはFirebaseやSupabaseを自分で選んで設定する必要があります。

## 複雑なロジックでの正直な評価

両ツールを使って気づいた「想定外の挙動」を正直に書きます。

**Rork Maxの限界:**
生成されるコードの品質は要件の書き方に大きく依存します。「複数の非同期処理が直列・並列で混在する」ような複雑な処理フローは、1回のプロンプトで正確に生成されることは少ないです。反復的な修正が必要になります。

また、生成されたコードのテストを書いてもらうのは苦手で、複雑なロジックほどバグが残りやすいです。

**Onspaceの限界:**
ビジュアルフローの表現力には上限があります。条件分岐が深くなったり、カスタムロジックが必要になったりすると、結局コードを書く必要が出てきます。また、生成されるフロントエンドのカスタマイズ性はRork Maxより低いです。

## 私の判断基準

実際にどちらを使うか判断するときの基準を整理しました:

**Rork Maxを選ぶとき:**
- React Nativeの知識がある（または学ぶ意欲がある）
- 最終的にコードを手元に持ちたい
- App Store/Google Playへの配信が目標
- 複雑なUIアニメーションやネイティブ機能（カメラ、Bluetooth等）が必要

**Onspaceを選ぶとき:**
- バックエンドのワークフロー自動化が主目的
- 技術的な背景が混在するチームで使う
- プロトタイプを素早く作って内部で使う（外部配信よりも社内ツール寄り）

「複雑なロジック」の意味がバックエンド処理の自動化に近いならOnspace、モバイルアプリとしての複雑さ（UI・ネイティブ機能・配信）に近いならRork Max、というのが今の私の結論です。

どちらのツールも進化が速いので、数ヶ月後には状況が変わっている可能性もあります。最終的には小さなプロトタイプで両方を試してみるのが一番確実だと思います。
