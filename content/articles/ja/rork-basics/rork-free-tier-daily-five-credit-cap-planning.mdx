新しいツールを触りはじめるとき、私がいちばん先に数えるのは機能の数ではなく、「一日で使い切れてしまうかどうか」です。使い切れる枠なら、その日のうちに向き不向きが分かります。使い切れない枠なら、判断は何日かに分かれます。

Rork の無料枠を数え直していた夜、手が止まりました。月に35クレジット。数字だけ見れば、小さなアプリを一本組むには足りそうに思えます。ところが日次の上限が5と書かれていて、そこで前提がひっくり返りました。さらに請求画面を公式の案内と並べてみると、無料で動くのは画面と見た目を提案してもらう「デザインモード」だけになっていました。

35は「一度に使える量」ではありません。**5 × 7日**です。そして無料で確かめられるのは「作れるか」ではなく「何を作るか」のほうです。この二つを最初に知っておくだけで、無料の一週間の使い方はずいぶん変わります。

以前は「Pro（月$25・100クレジット）」という段階が紹介されていましたが、いまの料金ページにあるのは Free と Rork Max の二つです。2026年8月4日より前に作ったアカウントにだけ、旧 Pro が残っています。古いまとめ記事の数字で予算を組むと、ここで食い違います。

## 「1日5」は回数ではなく、最大回数です

以前の Rork は「やり取り1回で1クレジット」という数え方でした。いまの公式の説明は「A message costs what its work costs」で、指示がした仕事の量で消費が決まります。無料の月間分から払う場合は、1通につき最低1クレジットです。

つまり1日5は「5回送れる」ではなく、「多くて5回」です。画面をまとめて作り直させたり、Web 検索や画像の生成を伴ったりする指示は、1通で1を超えることがあります。1通ごとの実際の消費は、回答の下にある「⋯」メニューから確認できます。

月の途中から始める方には、もう一つ見落としやすい点があります。月末が近いと、月間枠の35を日次上限が追い越せません。11月25日に始めた場合、11月の残りは今日を含めて6日、5 × 6 = 30 が上限で、使われなかった5は12月1日に消えます。

この計算を毎回手でするのは面倒なので、スクリプトにしておきました。Node.js が入っていれば、そのまま動きます。

```js
#!/usr/bin/env node
// free-credit-pace.mjs — Rork の無料枠（月35・1日5）で、今月あと何クレジット使えるかを出す
// 使い方: node free-credit-pace.mjs <今月すでに使った量> [<今日すでに使った量>] [YYYY-MM-DD]
// 上限の数字は 2026年11月時点の公式（docs.rork.com）。改定されたら書き換えてください。
const MONTHLY = 35; // 日本などの主要国の月間枠
const DAILY = 5;    // 1日の上限

const [usedMonthArg = "0", usedTodayArg = "0", dateArg] = process.argv.slice(2);
const usedMonth = Number(usedMonthArg);
const usedToday = Number(usedTodayArg);

if ([usedMonth, usedToday].some((n) => Number.isNaN(n) || n < 0) ||
    usedToday > DAILY || usedMonth > MONTHLY || usedToday > usedMonth) {
  console.error("使い方: node free-credit-pace.mjs <今月の使用量> [<今日の使用量>] [YYYY-MM-DD]");
  process.exit(1);
}

const today = dateArg ? new Date(`${dateArg}T00:00:00`) : new Date();
if (Number.isNaN(today.getTime())) {
  console.error("日付は YYYY-MM-DD で指定してください");
  process.exit(1);
}

const daysInMonth = new Date(today.getFullYear(), today.getMonth() + 1, 0).getDate();
const daysLeft = daysInMonth - today.getDate() + 1; // 今日を含めた残り日数

const capByDaily = (DAILY - usedToday) + (daysLeft - 1) * DAILY; // 日次上限から見た残り
const capByMonthly = MONTHLY - usedMonth;                         // 月間枠から見た残り
const usable = Math.min(capByDaily, capByMonthly);

console.log(`残り日数（今日を含む）: ${daysLeft}日`);
console.log(`日次上限から見た残り: ${capByDaily} / 月間枠から見た残り: ${capByMonthly}`);
console.log(`今月あと使える上限: ${usable}（効いているのは${capByDaily < capByMonthly ? "日次上限" : "月間枠"}）`);
console.log(`月末に使われずに消える見込み: ${capByMonthly - usable}`);
```

実行すると、次のように出ます。

```text
$ node free-credit-pace.mjs 0 0 2026-11-25
残り日数（今日を含む）: 6日
日次上限から見た残り: 30 / 月間枠から見た残り: 35
今月あと使える上限: 30（効いているのは日次上限）
月末に使われずに消える見込み: 5
```

月間枠と日次上限を別々に計算してから小さいほうを取るのは、月の前半と後半で効いてくる上限が入れ替わるからです。10日に12クレジット使っている状態なら、効いているのは月間枠のほうで、日次上限は気にしなくてよくなります。なお、リセットがどのタイムゾーンの1日で起きるのかは、公式の記述で確認できていません。スクリプトは手元の日付で数えていますので、月末の最終日は余裕を持って見ていただければと思います。

## 無料で動くのはデザインモードだけ、という前提から組み直しました

私は最初のうち、無料枠を「小さな予算」だと思っていました。少ないけれど、骨格を作らせて、実機で触って、直すところまで一通り試せる枠だと考えていたのです。結果は芳しくありませんでした。

一日目に骨格を作らせようとして、ビルドもプレビューも有料側にあることに気づきました。五日間の計画のうち、半分以上が無料では実行できない作業だったのです。枠が足りないのではなく、計画が無料の範囲を見ていなかったのだと分かったのは、三日目の夜でした。

そこから引いた線引きが一つあります。**無料の5回は、作るためではなく、有料の初日に迷わないために使います。** デザインモードで画面と流れを決め切っておけば、有料に移った日のビルドは「決めたものを形にする」作業だけになります。迷いを無料のうちに出し切るほど、有料のクレジットは手戻りに消えなくなります。

## 5日間の割り当て表

具体的には、次の割り当てにしています。各日の「止める条件」を先に決めておくのがいちばんの要で、答えが出たらその日の残りは送らずに閉じます。

<table>
<thead>
<tr><th>日</th><th>決める問い</th><th>送る内容</th><th>止める条件</th></tr>
</thead>
<tbody>
<tr><td>1日目</td><td>画面は何枚要るか</td><td>目的と、思いつく画面名の一覧</td><td>画面の数と名前が固まった</td></tr>
<tr><td>2日目</td><td>どの順に移るか</td><td>起動直後から目的を果たすまでの流れ</td><td>戻る・閉じるを含めた遷移が一枚に描けた</td></tr>
<tr><td>3日目</td><td>各画面に何を並べるか</td><td>一覧と詳細に出す項目、空のときの表示</td><td>項目名が保存するデータの名前と一致した</td></tr>
<tr><td>4日目</td><td>見た目の方向</td><td>色・文字の大きさ・暗い場所で使うかどうか</td><td>参考にしたい画面が一つに絞れた</td></tr>
<tr><td>5日目</td><td>有料に移るか</td><td>ここまでの提案を通して見直す依頼</td><td>まだ同じアプリを触っていたいかが分かった</td></tr>
</tbody>
</table>

3日目の「項目名をデータの名前と一致させる」は、あとから効いてきます。ここが揃っていないと、ビルドモードで画面とデータを結び付けるたびに言い直すことになり、そのぶん1通の仕事量が増えるからです。

## 1回で決め切る指示の書き方

クレジットが減る原因の大半は、機能の多さではなく往復の多さでした。「作って」「違う」「こうして」を繰り返すと、決めていないことの数だけ回数が増えます。

Before として、私が最初に送っていた指示はこうでした。

```text
家計簿アプリを作りたいです。いい感じのデザインでお願いします。
```

これだと、画面の数も対象の端末も Rork が推測で埋めます。推測が外れた分だけ、次の1通が要ります。いまはテキストエディタで200字ほどの下書きを作ってから送っています。After はこの骨子です。

```text
# 目的
（誰が、どんな場面で、何を1回でできるようにするか）

# 想定する端末
iPhone のみ（今回は Android・iPad を考えない）

# 画面
1. 一覧: 何を、どの順で並べるか / 空のときに何を出すか
2. 詳細: 表示する項目 / 編集できる項目
3. 設定: 変更できる値だけを列挙

# 今日決めたいこと
（上の5日間の表の、その日の問いを一つだけ）

# 今回やらないこと
- 通知・課金・共有・ログイン（提案に含めない）
```

いちばん効いたのは最後の「今回やらないこと」でした。書いておかないと、頼んでいない画面が付いてきて、それを外すためにもう1回使うことになります。「今日決めたいこと」を一つに絞っているのも同じ理由で、1通の仕事量を小さく保つと、最低1クレジットの範囲に収まりやすくなります。最初の一行で何を書いておくと後が楽になるかは、[家計簿アプリの最初の指示で、あとから効く3つの一行](/articles/rork-basics/kakeibo-first-prompt-yen-integer-local-month-input-normalize-three-checks)で具体例を挙げています。

## よくある誤解

**「無料は試用期間で、いずれ止まる」**——いまの無料プランはカード登録なしで続けて使え、期限で止まる試用版ではありません。毎月1日に枠が戻ります。

**「35を好きな日に一気に使える」**——1日5の上限があるため、一日に使えるのは多くて5です。月の後半に始めると、35すべては使い切れません。

**「無料でビルドして、実機で触ってから決められる」**——2026年11月時点の無料で動くのはデザインモードだけで、ビルド・端末での確認・公開は Rork Max が前提です。無料の5日間は「何を作るか」を決めるために使うほうが、無駄がありません。

ここまでを、選択肢ごとに並べます。

<thead>
<tr><th>選択肢</th><th>向いている人</th><th>注意点</th></tr>
</thead>
<tbody>
<tr><td>無料のまま続ける</td><td>まだ作るものが一つに決まっていない</td><td>デザインの提案までで、動くアプリにはならない</td></tr>
<tr><td>Rork Max $20 で始める</td><td>画面と流れが決まり、動く版を触りたい</td><td>シミュレーターは起動中も減るので、つけっぱなしにしない</td></tr>
<tr><td>いきなり上の段階を契約する</td><td>月の使用量がすでに読めている</td><td>機能は同じで量だけが増えるため、最初の月は割高になりやすい</td></tr>
</tbody>
</table>

私の判断はこうです。**5日目に、まだ同じアプリを触っていたいと思えたなら $20 の段階へ。そうでなければ、題材のほうを変えます。** 金額の妥当性というより、続ける気力の有無を測る問いなのかもしれません。3日目で興味が薄れていたなら、それはツールではなくアイデアへの合図だと受け取っています。

上の段階との境目や、追加購入と組み合わせたときの損益は、[Rork の料金プランを正直に比較した記事](/articles/rork-basics/rork-pricing-plan-honest-comparison-2026)で計算しています。そもそも Max のどの機能が自分に要るのかを先に洗い出したい方には、[料金表ではなく権限の棚卸しで判断する方法](/articles/rork-basics/rork-max-or-standard-capability-inventory-decision)が役に立つと思います。

## 有料の初日に、次に詰まるところ

無料で設計を決め切って有料に移ると、最初に当たるのは二つです。

一つは、ビルドモードでの1通の重さです。デザインモードより仕事量が大きいので、モデルの選び方で減り方が変わります。どの直しにどのモデルを当てると減りが穏やかになるかは、[直しの種類でモデルを選び、クレジットの行き先を一週間記録した記事](/articles/rork-ai/rork-model-menu-three-fix-types-credit-destination-ledger)に書き残しました。

もう一つは、あとから変えられない名前です。アプリの識別子（Bundle ID やパッケージ名）は、最初のビルドをストアへ上げた時点で固定され、あとから変えられません。デザインの段階で決めたアプリ名と一緒に、[最初の公開前に決めておく名前](/articles/rork-basics/rork-app-id-immutable-before-first-release)も確かめておくと、有料の初日がずっと落ち着いたものになります。

## 明日の5回を、先に決めておきます

今日できることを一つだけ挙げるなら、上の5日間の表から明日の問いを一つ選び、止める条件と一緒にメモへ書き出しておくことです。答えが出たら止まれる粒度にしておくと、翌朝の自分が最初の1通で迷いません。

私自身、無料枠を「試用期間」と考えていた頃はうまく使えませんでした。有料の初日のために決める枠だと思い直してから、ようやく前へ進むようになりました。皆さまの5回が、少しでも実りあるものになりますように。
