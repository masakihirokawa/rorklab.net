壁紙アプリ6本を1つのコードベースから出し分ける構成に切り替えたときのことです。ビルド設定を書き換えながら、ふと手が止まりました。

`android.package` の文字列が、6本のうち2本だけ命名の規則からずれていました。

その2本は、私がまだ「あとで整えればいい」と思っていた時期に公開したものです。整えることは、もうできませんでした。気づいたのは公開から何年も過ぎたあとで、そのときにはもう、直す道はストアの側に残っていなかったのです。

アプリには名前が3種類あります。ストアに表示される名前、開発中に使う slug、そしてアプリそのものを識別する ID です。このうち公開したあとで自由に変えられるのは、最初の1つだけです。

Rork は生成の時点で ID を自動的に埋めてくれます。動くものがすぐ手元に届くので、そのまま提出まで進んでしまいがちです。けれどストアに登録してビルドを上げた瞬間、その文字列は動かせなくなります。

この記事は、Rork で作った最初のアプリを App Store や Google Play に出す直前の方に向けて、「どの名前が後戻りできず、提出前の30分で何を確かめればよいか」を持ち帰っていただくためのものです。内容は2026年11月時点の App Store Connect・Play Console・Expo の挙動に基づいています。

## 公開したあとで変えられるのは、表示名だけです

ストアに関わる項目を、変更できるものとできないもので分けると次のようになります。

  <thead>
    <tr><th>項目</th><th>App Store</th><th>Google Play</th><th>公開後の変更</th></tr>
  </thead>
  <tbody>
    <tr><td>表示名（アプリ名）</td><td>新しいバージョンの審査と一緒に変更</td><td>ストア掲載情報から変更（審査あり）</td><td><strong>できます</strong></td></tr>
    <tr><td>アイコン・スクリーンショット</td><td>バージョン単位で差し替え</td><td>ストア掲載情報から差し替え</td><td><strong>できます</strong></td></tr>
    <tr><td>説明文・カテゴリ</td><td>審査と一緒に変更</td><td>ストア掲載情報から変更</td><td><strong>できます</strong></td></tr>
    <tr><td>Bundle ID / パッケージ名</td><td>ビルドをアップロードした時点で固定</td><td>最初のビルドを上げた時点で固定</td><td><strong>できません</strong></td></tr>

    <tr><td>ストアの URL</td><td>登録時に割り当てられる数値 ID</td><td>パッケージ名がそのまま URL に入ります</td><td><strong>できません</strong></td></tr>
  </tbody>

見ていただきたいのは最後の行です。Google Play のストア URL には、パッケージ名がそのまま文字列として現れます（`play.google.com/store/apps/details?id=<パッケージ名>`）。つまり Android では、ID は開発者だけの都合ではなく、利用者の目に触れる情報でもあります。

App Store の Bundle ID は、App Store Connect でアプリを登録するときにプルダウンから選びます。私は長いあいだ「審査に出すまでは変えられる」と思い込んでいましたが、実際にはビルドを1本でもアップロードした時点で、そのアプリの記録と結びついて動かせなくなります。TestFlight で試すためだけに上げたビルドでも同じです。

なお署名鍵は少し事情が異なり、Google Play ではアップロード鍵の再設定を Play Console から申請できます。名前と鍵を同じ「変えられないもの」の箱に入れてしまうと、直せる問題まで諦めてしまうので、ここは分けて覚えておくのが安全です。

## 3つの名前は、それぞれ別の場所に効いています

表の前提になっている「3つの名前」を、Rork が書き出す `app.json` の項目に対応させると、次のようになります。

<table>
  <thead>
    <tr><th>名前</th><th>app.json の項目</th><th>どこに効くか</th><th>あとで変えると</th></tr>
  </thead>
  <tbody>
    <tr><td>表示名</td><td><code>expo.name</code></td><td>ホーム画面のアイコン下（ストア名は別に入力）</td><td>次のビルドから反映されます</td></tr>
    <tr><td>slug</td><td><code>expo.slug</code></td><td>Expo / EAS 上のプロジェクトの URL</td><td>EAS のプロジェクトとの対応が崩れます</td></tr>
    <tr><td>ID</td><td><code>ios.bundleIdentifier</code> / <code>android.package</code></td><td>OS とストアがアプリを見分ける鍵</td><td>ストア上は別のアプリになります</td></tr>
  </tbody>
</table>

中間の slug は、見落とされやすい場所です。ストアの利用者からは見えませんが、EAS Build を一度でも使うと `extra.eas.projectId` にプロジェクトの ID が書き込まれ、slug とひと組で管理されます。この状態で slug だけを書き換えると、ビルドの開始時に次のような文言で止まります。

```text
Slug for project identified by "extra.eas.projectId" (xxxxxxxx-...) does not match the "slug" field (new-slug).
```

slug は ID ほど固くはありませんが、気軽に触ってよい場所でもありません。表示名を変えたくなったときに、ついでに slug まで揃えようとして止まる——私がいちばん多く見かけるのはこの流れです。**表示名だけを変え、slug と ID はそのまま**にしておけば、この種の停止は起きません。

## Rork が入れる ID は、雛形のままのことがあります

Rork が書き出したプロジェクトの `app.json`（もしくは `app.config.ts`）には、次のような記述が入っていることがあります。

```json
{
  "expo": {
    "name": "wallpaper",
    "slug": "wallpaper",
    "ios": { "bundleIdentifier": "com.anonymous.wallpaper" },
    "android": { "package": "com.anonymous.wallpaper" }
  }
}
```

`com.anonymous.` で始まる文字列は、ID が未指定のときに Expo の側で補われる雛形です。生成物としては正しく、ビルドも通り、実機にも入ります。動いてしまうので、疑う理由がありません。

ここを自分のものに置き換える基準は、そう複雑ではありません。

- ドメインを持っているなら、逆順にしたものを先頭に置きます（`dolice.net` なら `net.dolice.`）
- 持っていないなら、実在するアカウント名に紐づけます（`io.github.<アカウント名>.` など）
- 末尾はプロダクトを表す短い語にします

避けたほうがよいのは、後から意味がずれる語を入れてしまうことです。`free`、`v2`、`2026`、`ios` といった語を末尾に足すと、無料版を有料化したときや作り直したときに、ID だけが過去の判断を指し続けます。私は一度これをやって、2本目以降の命名を引きずりました。

もう一つ、Bundle ID は Apple のアカウント全体で一意です。別の開発者がすでに使っている文字列は登録できず、Xcode や EAS の資格情報の設定で「An App ID with Identifier '…' is not available.」と返されます。`com.<ありふれた語>.<ありふれた語>` を避けたいのは、見た目のためだけではないのです。

## 公開前に、機械で確かめます

目視での確認は、6本目あたりから確実に精度が落ちます。私は次のスクリプトを提出前に走らせるようにしました。依存パッケージはありません。Node があれば動きます（Node 18 以降で確認しています）。

```js
// check-app-ids.mjs
import { readFileSync, existsSync } from "node:fs";

const RESERVED = new Set(["abstract","assert","boolean","break","byte","case","catch",
  "char","class","const","continue","default","do","double","else","enum","extends",
  "final","finally","float","for","goto","if","implements","import","instanceof","int",
  "interface","long","native","new","package","private","protected","public","return",
  "short","static","strictfp","super","switch","synchronized","this","throw","throws",
  "transient","try","void","volatile","while"]);

const PLACEHOLDER = [/^com\.anonymous\./i, /^host\.exp\./i, /^com\.example\./i,
  /\byourname\b/i, /\byourcompany\b/i, /\bmyapp\b/i, /\btest\b/i];

function readConfig(path) {
  if (!existsSync(path)) return null;
  const raw = JSON.parse(readFileSync(path, "utf8"));
  return raw.expo ?? raw;
}

function checkAndroidPackage(pkg) {
  const errs = [];
  if (!pkg) return ["android.package が未設定です"];
  const segs = pkg.split(".");
  if (segs.length < 2) errs.push("ドット区切りが2つ未満です");
  for (const s of segs) {
    if (!/^[a-zA-Z][a-zA-Z0-9_]*$/.test(s)) errs.push(`セグメント "${s}" が英字始まりの条件を満たしません`);
    if (RESERVED.has(s)) errs.push(`セグメント "${s}" は Java の予約語です`);
  }
  return errs;
}

function warnAndroidPackage(pkg) {
  // 大文字は Android では使えますが、慣例は小文字です。止めずに知らせます
  return (pkg ?? "").split(".").filter((s) => /[A-Z]/.test(s))
    .map((s) => `セグメント "${s}" に大文字が含まれます（小文字が慣例です）`);
}

function checkBundleId(id) {
  const errs = [];
  if (!id) return ["ios.bundleIdentifier が未設定です"];
  if (!/^[A-Za-z0-9.-]+$/.test(id)) errs.push("使用できない文字が含まれます");
  if (id.split(".").length < 2) errs.push("ドット区切りが2つ未満です");
  if (/_/.test(id)) errs.push("アンダースコアは使えません");
  return errs;
}

const path = process.argv[2] ?? "app.json";
const cfg = readConfig(path);
if (!cfg) { console.error(`✗ ${path} が見つかりません`); process.exit(2); }

const ios = cfg.ios?.bundleIdentifier;
const android = cfg.android?.package;
const findings = [];

for (const e of checkBundleId(ios)) findings.push(["BLOCK", "ios.bundleIdentifier", e]);
for (const e of checkAndroidPackage(android)) findings.push(["BLOCK", "android.package", e]);
for (const e of warnAndroidPackage(android)) findings.push(["WARN", "android.package", e]);

for (const [key, val] of [["ios.bundleIdentifier", ios], ["android.package", android]]) {
  if (val && PLACEHOLDER.some((re) => re.test(val))) {
    findings.push(["BLOCK", key, `"${val}" は雛形のままの疑いがあります`]);
  }
}
if (ios && android && ios.toLowerCase() !== android.toLowerCase()) {
  findings.push(["WARN", "ios/android", `ID が一致しません（iOS: ${ios} / Android: ${android}）`]);
}
if (!cfg.name) findings.push(["WARN", "name", "表示名が未設定です"]);
if (!cfg.slug) findings.push(["WARN", "slug", "slug が未設定です"]);

console.log(`# ${path}`);
console.log(`  ios  : ${ios ?? "(なし)"}`);
console.log(`  and  : ${android ?? "(なし)"}`);
if (findings.length === 0) { console.log("✓ 公開前に固定してよい状態です"); process.exit(0); }
for (const [lv, key, msg] of findings) console.log(`  ${lv === "BLOCK" ? "✗" : "!"} [${lv}] ${key}: ${msg}`);
process.exit(findings.some(([lv]) => lv === "BLOCK") ? 1 : 0);
```

検査したいのは3つです。雛形のまま残っていないか、Android のパッケージ名に使えない語が入っていないか、iOS と Android で食い違っていないか。

2つ目について補足させてください。Expo は `android.package` を、Gradle の `applicationId` だけでなく、生成されるネイティブコードのパッケージ名（`namespace`）にも使います。そのため `new` や `class` のような Java の予約語をセグメントに入れると、設定としては自然に見えるのに、生成されたソースのコンパイルで失敗する例が報告されています。原因がパッケージ名にあるとは思いにくい種類の失敗なので、スクリプトでは止める側に入れました。

一方で、大文字は Android の規則としては使えます。慣例として小文字に揃えることが勧められているだけなので、ここは WARN にとどめています。

手元の4パターンで実際に走らせた出力が、次のものです。

```text
$ node check-app-ids.mjs a-default.json
# a-default.json
  ios  : com.anonymous.wallpaper
  and  : com.anonymous.wallpaper
  ✗ [BLOCK] ios.bundleIdentifier: "com.anonymous.wallpaper" は雛形のままの疑いがあります
  ✗ [BLOCK] android.package: "com.anonymous.wallpaper" は雛形のままの疑いがあります
exit=1

$ node check-app-ids.mjs b-mismatch.json
# b-mismatch.json
  ios  : net.dolice.calmwall
  and  : net.dolice.calm_wall
  ! [WARN] ios/android: ID が一致しません（iOS: net.dolice.calmwall / Android: net.dolice.calm_wall）
exit=0

$ node check-app-ids.mjs c-reserved.json
# c-reserved.json
  ios  : net.dolice.new.zentimer
  and  : net.dolice.new.zentimer
  ✗ [BLOCK] android.package: セグメント "new" は Java の予約語です
exit=1

$ node check-app-ids.mjs d-ok.json
# d-ok.json
  ios  : net.dolice.zentimer
  and  : net.dolice.zentimer
✓ 公開前に固定してよい状態です
exit=0
```

2番目を BLOCK ではなく WARN にしてある理由も書いておきます。`calm_wall` は Android では正当なパッケージ名です。アンダースコアが使えないのは iOS 側だけで、両者を揃えようとした結果としてずれただけ、という場合があります。機械が判断を代わりに下せない箇所なので、止めずに知らせるにとどめました。

`exit` の値を返すようにしてあるので、`package.json` の `scripts` に `"precheck": "node check-app-ids.mjs app.json"` のように書いておけば、`npm run precheck` でいつでも同じ確認ができます。`app.config.ts` を使っている場合は、`npx expo config --json > resolved.json` で解決後の設定を書き出し、そのファイルを渡してください。

## 登録や提出で止まったときの切り分け

名前に起因する停止は、エラーの文言だけでは原因が分かりにくいことがあります。私が実際に当たったもの、または問い合わせで見かけたものを、症状から引ける形にまとめました。

<table>
  <thead>
    <tr><th>症状</th><th>原因の候補</th><th>確かめ方</th><th>直し方</th></tr>
  </thead>
  <tbody>
    <tr><td>「An App ID with Identifier '…' is not available.」</td><td>その Bundle ID を別のチームがすでに登録している</td><td>Apple Developer の Identifiers に自分の登録があるか見る</td><td>まだビルドを上げていなければ、別の文字列に変えて登録し直す</td></tr>

    <tr><td>Android のビルドだけがコンパイルエラーで落ちる</td><td>パッケージ名のセグメントに予約語が入っている</td><td>上のスクリプトで BLOCK が出るか見る</td><td>ストアに上げる前ならセグメントを差し替える</td></tr>
  </tbody>
</table>

表の3行目だけは、直し方が「戻す」しかありません。ほかの行は公開前なら取り返しがつきます。順番を決めて確かめる意味は、この差にあるのだと思います。

## よくある誤解を3つ、ほどいておきます

**「アプリを削除すれば、同じ ID で作り直せる」——作り直せません。** App Store Connect では、一度アプリに使った Bundle ID は、そのアプリを削除しても再利用できないと案内されています。Google Play でも、パッケージ名は一意で恒久的なもので、アプリを削除したあとも別のアプリには使えません。取り戻す道を探すより、新しい ID を決めるほうが早い場面です。

**「iOS と Android の ID は同じでなければならない」——その必要はありません。** 2つは別々の仕組みで、それぞれのストアが個別に管理しています。揃えておくと、ログや課金の管理画面で見分けやすくなるという実務上の利点があるだけです。上のスクリプトが不一致を WARN にとどめているのも、このためです。

**「表示名を変えると、ストアでは別のアプリ扱いになる」——なりません。** 評価もレビューもダウンロードの履歴も、ID にひもづいて残ります。名前を変えたいだけなら、出し直す理由はありません。

## 複数本を出すつもりなら、規則を先に決めます

1本で終わるつもりでも、うまくいけば2本目を作ることになります。そのときに効いてくるのが、最初の1本で決めた規則です。

私が6本で使っている形は `<逆ドメイン>.<プロダクト略称>` だけの2〜3セグメントです。プラットフォーム名も、版数も、配布形態も入れません。ID に情報を持たせるほど、情報が古くなったときに動かせない部分が増えていきます。

規則が揃っていると、もう一つ助かることがあります。ビルド設定の中で、プロダクト名の変数ひとつから ID を組み立てられるのです。手で書かない ID は、夜中の作業で打ち間違えることもありません。

表示名のほうには、いくらでも情報を持たせて構いません。そちらは後から変えられるからです。**変えられる場所に変わりうる情報を置き、変えられない場所には変わらない情報だけを置く**、という切り分けが結局いちばん長持ちしました。

## すでに公開してしまった場合に取れる道

もう出してしまった、という方もいらっしゃると思います。取れる道は2つで、比べると次のようになります。

<table>
  <thead>
    <tr><th>観点</th><th>そのまま使い続ける</th><th>新しい ID で出し直す</th></tr>
  </thead>
  <tbody>
    <tr><td>評価・レビュー</td><td>残ります</td><td>ゼロからになります</td></tr>
    <tr><td>既存ユーザーの自動更新</td><td>続きます</td><td>届きません（新アプリへの誘導が必要）</td></tr>
    <tr><td>課金商品</td><td>そのまま</td><td>ストア側で作り直し</td></tr>
    <tr><td>手間</td><td>ほぼなし</td><td>ストア掲載情報・審査・告知をすべてやり直し</td></tr>
    <tr><td>向いている場面</td><td>不揃いが自分にしか見えない</td><td>レビューがまだ数件で、名前に誤解を招く語が入っている</td></tr>
  </tbody>
</table>

**そのまま使い続けます。** ID は Android のストア URL を除けば、利用者の目にほとんど触れません。表示名を変えれば見た目の問題は解消します。私の6本のうち、規則からずれた2本はこの判断で残してあります。数年後に見返す自分だけが気にする種類の不揃いだと考えたためです。

**新しい ID で出し直します。** 引き継げないものが多いことは、先に把握しておいたほうがよいと思います。コードとアセットは移せますが、旧アプリから新アプリへ誘導する導線は自分で作る必要があります。

判断の分かれ目は、レビュー件数だと思っています。レビューがまだ数件であれば出し直しの損失は小さく、三桁に届いているなら、ID の不揃いを抱えたまま進むほうがおそらく合理的です。

## 名前の次に詰まるのは、アカウントの名義です

ID を決め終えた方が次に当たりやすいのは、Apple Developer Program を個人で登録するか法人で登録するか、という問題です。ストアに表示される販売元の名前はアカウントの名義から決まり、これも ID と同じく、あとから軽く変えられる場所ではありません。

Rork の側では代行できない Apple 側の手続きは、[Rork のアプリを公開する前に、Apple 側で自分が済ませておく手続き](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)に順番どおりまとめています。すでに個人で出していて、あとから法人へ移したくなった場合は、[個人アカウントで出した iOS アプリを、あとから法人へ移せるか](/articles/rork-basics/ios-app-transfer-individual-to-organization-account-checklist)で、移す前に外しておくものを書きました。App Transfer で移ってもアプリの ID はそのまま残るので、ここでも最初の命名が効いてきます。

## 公開前の30分でやること

1. `app.json` または `app.config.ts` を開き、`ios.bundleIdentifier` と `android.package` を確認します
2. 上のスクリプトを走らせ、BLOCK が0件になるまで直します
3. 末尾に `free` `v2` `2026` `ios` のような、後から意味がずれる語が入っていないか読み返します
4. 表示名を変える予定があっても、slug は触らないと決めておきます
5. 2本目を出すときにどう伸ばすかを、1行でよいのでメモに残します

この5つを終えてから、App Store Connect と Play Console にアプリを登録し、最初のビルドを上げてください。順番が逆になると、直せるものが直せなくなります。

個人で開発していると、審査に出すまでの工程を全部ひとりで抱えることになります。だからこそ、機械に任せられる確認は機械に渡しておきたいと私は考えています。上のスクリプトは、その最初の一枚です。

最初の1本を出す日は、決めることが多すぎて、名前のような地味な項目が後回しになりがちです。私もそうでした。まずは手元の `app.json` を開いて、`com.anonymous.` が残っていないかだけでも確かめていただければと思います。
