## 1位：Rork の AI に古いライブラリのコードを生成されないために — 私が使っている「バージョン明示プロンプト」の実例

Rork が React Navigation v5 系のコードを書いてしまう、Reanimated 2 系の API を出してくる——「古いライブラリのコードを生成される」現象は、Rork ユーザーが必ずどこかで踏む落とし穴です。ここでは私が普段使っているバージョン明示プロンプトの組み立て方を、実例つきで共有しました。

特に手応えを感じたのは、「ライブラリ名 + バージョン + 既知の破壊的変更」を1つの定型ブロックとしてプロンプトの先頭に置くと、AI が古い書き方に引きずられる頻度が大きく下がる、という発見でした。ここを整えるだけで、後続のリファクタ工数が体感で半減します。

## 2位：Rork Max の Cloud Compile が失敗する原因と、すぐに試せる対処法

Cloud Compile が失敗するときは、ログだけ見ても原因がつかめないことが多くあります。ここでは私が遭遇したケースを「依存関係系」「Provisioning Profile 系」「ネイティブモジュール系」「リソース系」の4カテゴリに分類し、それぞれ「最初に試す手」をまとめました。

書きながら自分で発見だったのは、Cloud Compile のキャッシュをクリアするだけで解決するケースが意外と多い、という点です。ローカル開発のキャッシュとは異なる挙動をするので、一度疑ってみる価値があります。

## 3位：Rork アプリで「閉じてる間も最新」を本番品質で実装する — iOS BGTaskScheduler × Silent Push × Android WorkManager 完全ガイド

「アプリを閉じている間にもデータを最新化する」という要件は、ユーザー体験の観点では地味ですが、本番品質で実装しようとすると iOS と Android で別々の知識が必要になります。この記事は、BGTaskScheduler・Silent Push・WorkManager をつなげる本番設計を、Rork のコード生成パターンと合わせて整理しました。

私自身、リリース直後にバックグラウンド更新が動かず、ユーザーから「数時間前のデータが表示される」というクレームをいただいた経験があります。その反省を、設計の優先順位として記事に反映しています。

## 4位：Rork で作ったアプリの「原因不明クラッシュ」を撲滅する — Error Boundary と Unhandled Promise の実戦的な捕捉法

クラッシュレポートに「Unhandled Promise Rejection」とだけ出ていて、何のコードでクラッシュしたのか追えない——React Native の運用でよく見る光景です。この記事は、Error Boundary の置き場所と Unhandled Promise の捕捉設計を、Rork が生成しがちなコード形状を踏まえて整理しました。

特に効いたのは、「画面単位ではなく、機能単位で Error Boundary を配置する」設計です。画面単位だと粒度が粗く、機能単位だと根本原因に近いログが取れる——この粒度設計の話に、特に多くの反応をいただきました。

[Rork で作ったアプリの「原因不明クラッシュ」を撲滅する — Error Boundary と Unhandled Promise の実戦的な捕捉法](/articles/rork-dev/rork-error-boundary-unhandled-promise-production-guide)

## 5位：Rork でつくった iOS アプリで App Tracking Transparency のダイアログが出ない時の原因と対処法

ATT のダイアログが出ない原因は「呼び出し前後のタイミング」「Info.plist の不足」「権限ステータスの誤判定」の3つに集約されることが多いです。ここではそれぞれの判定方法と修正手順を、Rork のコード生成パターンに合わせて整理しました。

書きながら確認できたのは、「呼び出しタイミングが SceneDelegate の外側にあるとダイアログが出ない」という挙動です。Rork が生成するアプリ起動フローでは、初回判定が JS 側に寄っているため、Native 起点で呼び出すための小さな調整が必要になります。

## バージョン明示プロンプトの最小例

1 位の記事から、最も基本となるプロンプト構造を抜粋します。Rork に限らず、AI コード生成全般で応用できます。

```text
[依存ライブラリと現行バージョン]
- React Native: 0.74.x
- React Navigation: 6.x（v5 と v6 で API が大きく変わっています）
- React Native Reanimated: 3.x（v2 の "useAnimatedStyle" 例は使わないでください）

[実装してほしいこと]
- 画面 A から画面 B への遷移時に、フェードアニメーションを 200ms で適用する。

[制約]
- React Navigation 6 系の "screenOptions" を使ってください。
- 戻る操作時のリバースアニメーションも明示的に対応してください。
```

ポイントは、「使ってほしいバージョン」だけでなく「使ってほしくないバージョンの典型的な書き方」を明記することです。AI は "正解" だけを与えても古い書き方に揺り戻されるので、否定形のヒントを混ぜると安定します。

## よくいただくご質問

### Q. Rork と Rork Max はどちらを選ぶべきですか？

「軽い検証や個人プロジェクトは Rork、本番品質を狙うなら Rork Max」という線引きが、現状の私の理解です。今週の3〜5位のような本番設計の話は、Rork Max を前提にすると話が進めやすくなります。

### Q. AI が生成するコードを、最初から本番品質にする方法はありますか？

率直に言うと、現時点では「ない」と考えています。1位の記事のようにバージョン明示で精度を上げ、4位・5位のような実戦的な捕捉設計を組み合わせる、という二段構えが現実的です。

### Q. ATT のダイアログが出ないときに最初に見るべき場所は？

私の経験上、まず Info.plist の `NSUserTrackingUsageDescription` の存在と、呼び出し位置のタイミングを疑います。5位の記事の冒頭で、その判定の仕方を3ステップで整理しています。
