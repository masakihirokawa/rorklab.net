SDK 58 の変更履歴を開いて、最初に感じたのは「長い」ということでした。

削除されるもの、挙動が変わるもの、非推奨になるもの。それぞれが別の節に分かれていて、読み終えたころには、最初の節に何が書いてあったかが曖昧になっております。読んで理解したつもりでも、いざ自分のプロジェクトに当てはめると、どこが該当するのかは別の作業として残ります。

そこで、読む順番を逆にしてみました。変更履歴から「検索できる形のもの」だけを先に拾い出して、自分のプロジェクトを走査する小さなスクリプトにします。読んで判断するのは、その一覧が出てからです。

Expo SDK 58 は 2026 年 10 月 15 日に公開されました（expo.dev/changelog の掲載による）。React Native は 0.86 から 0.88 へ上がります。Rork から書き出したプロジェクトも中身は普通の Expo プロジェクトですが、Rork 側が SDK 58 にいつ対応するかは、私の確認した範囲では案内がありません。ここで書くのは、書き出したあとのリポジトリを自分で上げる場合の話です。

## 先に、何を拾うかを三つに分けます

変更履歴の項目を、そのまま並べても点検にはなりません。点検の優先度で三つに分けました。

- **REMOVED（消える）**: 残っているとビルドか型検査が止まります。最優先です
- **BEHAVIOR（挙動が変わる）**: 動きはするが結果が変わります。意図と合っているかを人間が見る必要があります
- **DEPRECATED（非推奨）**: 今は動きます。上げる当日ではなく、次の機会に直せば足ります

変更履歴の記載から、検索の対象にしたのは次の項目です。

StatusBar の非推奨 prop も削除対象と書かれていますが、どの prop かまでは私は特定できておりません。スクリプトには一例として `networkActivityIndicatorVisible` を入れてあり、該当するかどうかは公式の一覧で確かめる前提にしています。

## 検査スクリプト全文

Node.js だけで動きます（SDK 58 は Node 22.13 以上、24.3 以上、または 26 以降が前提です。奇数の 23・25 は対象外と書かれています）。依存パッケージはありません。

```js
// audit-sdk58.mjs — SDK 58 へ上げる前に、プロジェクト内の「消える・変わる」API を一覧にする
// 使い方: node audit-sdk58.mjs [プロジェクトのパス]
import { readdirSync, readFileSync, existsSync, statSync } from 'node:fs';
import { join, relative, extname, resolve } from 'node:path';
import { fileURLToPath } from 'node:url';

const SELF = fileURLToPath(import.meta.url); // 自分自身は検査対象から外す

const root = process.argv[2] ?? '.';
const SKIP = new Set(['node_modules', '.git', 'ios', 'android', '.expo', 'dist']);
const EXT = new Set(['.ts', '.tsx', '.js', '.jsx', '.mjs']);

// level: REMOVED=消える／BEHAVIOR=挙動が変わる／DEPRECATED=非推奨（今は動く）
const RULES = [
  { id: 'rn-interactionmanager', level: 'REMOVED', re: /\bInteractionManager\b/, why: 'RN から削除。requestAnimationFrame か、描画後に走らせたい処理を useEffect 側へ' },
  { id: 'rn-touchable-root', level: 'REMOVED', re: /import\s*\{[^}]*\bTouchable\b[^}]*\}\s*from\s*['"]react-native['"]/, why: 'Touchable のルート export が削除。Pressable へ' },
  { id: 'rn-nativemethods', level: 'REMOVED', re: /\bNativeMethods\b/, why: 'NativeMethods 型が削除。ViewInstance など instance 型へ' },
  { id: 'rn-modal-animated', level: 'REMOVED', re: /<Modal\b[^>]*\banimated\b/, why: 'Modal の animated prop が削除。animationType を使う' },
  { id: 'rn-deep-import', level: 'REMOVED', re: /from\s*['"]react-native\/Libraries\//, why: 'Strict TypeScript API が既定。Libraries/* の deep import は型エラー' },
  { id: 'rn-statusbar-ios-props', level: 'REMOVED', re: /<StatusBar\b[^>]*\bnetworkActivityIndicatorVisible\b/, why: 'StatusBar の非推奨 prop の一部が削除対象。この prop が該当するかは公式の変更履歴で確認（ここは例）' },
  { id: 'fs-file-write', level: 'BEHAVIOR', re: /\.write\(/, why: 'expo-file-system の File.write() は非同期に。同期のままなら writeSync()（File 以外の .write も拾うので目視）' },
  { id: 'fs-md5', level: 'DEPRECATED', re: /\.md5\b/, why: 'File.md5 は非推奨。File.digest() へ' },
  { id: 'sqlite-libsql', level: 'REMOVED', re: /\b(syncLibSQL|libSQLOptions|useLibSQL)\b/, why: 'expo-sqlite の libSQL 対応が削除' },
  { id: 'rn-imagebackground', level: 'DEPRECATED', re: /\bImageBackground\b/, why: '非推奨。View ＋ 絶対配置の Image へ' },
  { id: 'router-withlayoutcontext', level: 'DEPRECATED', re: /\bwithLayoutContext\b/, why: '非推奨。integrateWithRouter へ' },
  { id: 'notif-foreground', level: 'BEHAVIOR', re: /from\s*['"]expo-notifications['"]/, why: 'フォアグラウンド通知が既定で表示される。意図した挙動か確認' },
  { id: 'nodeenv-test', level: 'BEHAVIOR', re: /NODE_ENV=test/, why: 'NODE_ENV=test で expo start すると .env.development を読む' },
];

function* walk(dir) {
  for (const name of readdirSync(dir)) {
    if (SKIP.has(name)) continue;
    const p = join(dir, name);
    const st = statSync(p);
    if (resolve(p) === SELF) continue;
    if (st.isDirectory()) yield* walk(p);
    else if (EXT.has(extname(name)) || name === 'package.json') yield p;
  }
}

const hits = [];
for (const file of walk(root)) {
  const lines = readFileSync(file, 'utf8').split('\n');
  lines.forEach((line, i) => {
    for (const r of RULES) if (r.re.test(line)) hits.push({ r, file: relative(root, file), line: i + 1, text: line.trim() });
  });
}

// ネイティブ側の確認（CNG でない場合に効く）
const notes = [];
if (existsSync(join(root, 'ios'))) notes.push('ios/ があります。CNG なら削除して再生成、手書き管理なら AppDelegate のシーン対応（SceneDelegate.swift）を確認');
if (existsSync(join(root, 'android'))) notes.push('android/ があります。R8 が release で既定オンになるため keep ルールを確認');

const order = { REMOVED: 0, BEHAVIOR: 1, DEPRECATED: 2 };
hits.sort((a, b) => order[a.r.level] - order[b.r.level] || a.file.localeCompare(b.file));
for (const h of hits) console.log(`[${h.r.level}] ${h.file}:${h.line}  ${h.r.id}\n    ${h.text}\n    → ${h.r.why}`);
const c = (l) => hits.filter((h) => h.r.level === l).length;
console.log(`\n集計: REMOVED ${c('REMOVED')} / BEHAVIOR ${c('BEHAVIOR')} / DEPRECATED ${c('DEPRECATED')}`);
notes.forEach((n) => console.log('NOTE: ' + n));
process.exit(c('REMOVED') > 0 ? 1 : 0);
```

なぜこう書くかを三点だけ補足します。

1. **ルールを配列にして、`why` に直し先まで書いておきます。** 出力を読んだ時点で次の行動が決まるようにするためです。ルールを足すのも一行で済みます
2. **終了コードを REMOVED の有無で変えています。** 後から CI に載せるとき、REMOVED がゼロでなければ止める、という使い方がそのままできます
3. **ios/ と android/ の存在を最後に注記します。** ネイティブ側は文字列検索では見えないので、「ここは別の確認が要ります」と出すだけに留めました

## 試験プロジェクトで走らせた結果

手元に、わざと古い書き方を詰め込んだ小さなプロジェクトを作って走らせました（SDK 57 相当の package.json と、`app/index.tsx`・`src/db.ts`・空の `ios/` ディレクトリだけの構成です）。実際のアプリではなく、スクリプトの挙動を確かめるための試験用です。

```text

    import { InteractionManager, ImageBackground, Modal, StatusBar } from 'react-native';
    → RN から削除。requestAnimationFrame か、描画後に走らせたい処理を useEffect 側へ
[REMOVED] app/index.tsx:2  rn-touchable-root
[REMOVED] app/index.tsx:5  rn-interactionmanager
[REMOVED] app/index.tsx:7  rn-modal-animated

[REMOVED] src/db.ts:2  rn-deep-import
[REMOVED] src/db.ts:3  sqlite-libsql
[REMOVED] src/db.ts:4  sqlite-libsql
[BEHAVIOR] app/index.tsx:6  fs-file-write
```

8 件が出ました。ただし、ここで「直す箇所は 8 つ」と読むのは早計です。

## 走らせて初めてわかった、三つの落とし穴

### 1. 検査スクリプトが、自分自身を検出しました

最初の実行では、集計が REMOVED 10 件・BEHAVIOR 3 件・DEPRECATED 3 件でした。試験プロジェクトに仕込んだのは 8 件・1 件・2 件のはずです。差分の正体は、プロジェクトのルートに置いたスクリプト自身でした。ルールの正規表現が文字列としてスクリプトの中にあるため、`InteractionManager` や `NativeMethods` という単語に、自分で反応していたのです。

この落とし穴は、次の二行で回避できます。`import.meta.url` から自分のパスを取り、走査のときに飛ばします。ここで一度つまずいたのは、`walk()` が相対パスを渡していたため、単純な文字列比較では一致しなかったことでした。`resolve()` で絶対パスにそろえてから比べると、期待した 8 件・1 件・2 件になりました。

**検査道具は、検査の対象になるところに置かないようにします。** 置くなら自分を除外しておく、というこの一行は、他の検査にも持ち込むつもりです。

### 2. 件数は「直す回数」ではありません

`app/index.tsx` の 1 行目と 5 行目は、同じ `InteractionManager` です。import と使用箇所がそれぞれ一件として数えられます。実際に直すのは「InteractionManager の使い方」一か所で、import を消すのはそのついでです。件数は目安に留め、ファイルごとにまとめて眺めるのがちょうどよいと感じました。

### 3. `.write(` は、他の write も拾います

`fs-file-write` は、`File` に限らず、行内の `.write(` すべてに反応します。ストリームでも、自作クラスでも同じです。このルールだけは、出力を目で見て絞る前提にしました。ルールの `why` に「目視」と書いてあるのは、この前提を出力の側に残すためです。

## 走らせる時間と、空振りの確認

実行時間は、試験プロジェクトで 3 回とも 0.05 秒、メモリは約 48MB でした。念のため、このサイトのリポジトリ（TypeScript／JavaScript が 79 ファイル、RN とは無関係の Next.js）にも向けてみると、0.11 秒で終わり、集計は 0 件・0 件・0 件でした。該当がない場所では何も出さない、という動きも確かめられたことになります。三十分の点検と書きましたが、スクリプト自体は一瞬で終わります。かかるのは、出力を読んで判断する時間のほうです。

私の場合は、上げる作業の前日に一度走らせて、出力を保存しておくことを推奨します。当日は、その一覧が減っていく様子を見るだけで済みます。

## この方法で拾えないもの

線引きもお伝えします。このスクリプトが拾えるのは「名前が文字列として現れるもの」だけです。

- **別名で包んだ import**（`import * as RN from 'react-native'` のあとの `RN.InteractionManager`）は、名前だけの検索には掛かります。一方、変数に代入し直されると追えません
- **サードパーティのライブラリが内部で使っているもの**は見えません。`node_modules` を走査から外しているので、依存先が削除された API を呼んでいても、ここでは出てきません
- **ネイティブ側**（iOS のシーンライフサイクル、Android の R8 既定オン）は、そもそも検索では見えません。SDK 58 ではビルドの動作が変わる部分なので、別の確認が要ります

最後の二つを補うのは、結局のところ上げてみて、ビルドと実機で確かめる工程です。このスクリプトは、その工程の前に「ここまでは自分で確かめた」と言える範囲を広げるためのものです。

## ネイティブ側と、続けて確認しておきたいこと

変更履歴には、上げるときの手順が次のように書かれています。

```bash
# 依存を SDK 58 に合わせる
npx expo install expo@^58.0.0 --fix

# 既知の問題の検査
npx expo-doctor@latest
```

Continuous Native Generation を使っている場合は、`android` と `ios` ディレクトリを消して、次のビルドで再生成させます。手書きで管理しているなら、`npx pod-install` と、ネイティブプロジェクトの差分の適用が要ります。開発ビルドは、上げたあとで作り直す必要があります。

Expo Go については、SDK 58 対応版がストアに並ぶまで「数週間」とされています。それまでは `npx create-expo-app` が SDK 57 のプロジェクトを作ります。SDK 58 で始めたいときは、`--template default@sdk-58` を付けて、開発ビルドで動かす形になります。

ここから先は、このサイトの別の記事が補ってくれます。

- シーンライフサイクル対応で AppDelegate が止まるときは[「prebuild が requires the standard Expo SDK 57 Swift AppDelegate で止まったとき、まず確かめる3行」](/articles/app-dev/expo-enable-scene-support-prebuild-standard-appdelegate-error)
- Android の R8 既定オンの前に測っておく数字は[「R8 が既定になる前に測っておく4つの数字」](/articles/rork-dev/expo-sdk58-r8-default-android-baseline-measurement)
- prebuild で消えるネイティブ変更の洗い出しは[「Expo SDK 57 に上げる前に、prebuild で消えるネイティブ変更を洗い出す」](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit)

## 使い方の手順

1. スクリプトをプロジェクトの外か、除外つきで置いて `node audit-sdk58.mjs <パス>` を実行します
2. REMOVED をファイル単位でまとめて眺め、直す箇所を数えます（件数でなく箇所で）
3. BEHAVIOR は、意図と合っているかを一つずつ見ます。notifications は、フォアグラウンドで通知が出て困る画面があるかを実機で確かめる必要があります
4. DEPRECATED は、次の機会のメモに回します
5. 直したら、もう一度走らせて REMOVED がゼロになるのを確かめ、それから `npx expo install expo@^58.0.0 --fix` に進みます

私は個人開発で、上げる前の作業を「読む」から「走らせる」に寄せておくほうが、気持ちが楽になると感じています。一覧が手元にあると、変更履歴は「全部読むもの」から「一覧の意味を確かめるもの」へ役割が変わります。

ルールの配列は、SDK 59 のときにも作り直せます。今回の十三行のうち、次に残るものは少ないはずです。それでも、型が手元にあることのほうが、私には価値があります。
