新しいアプリの課金商品 ID を決めていた夜、手が止まりました。この ID は、個人のアカウントに置いてよいのだろうか。いずれ法人にするかもしれないのに、と。

画面には App Store Connect の「新規サブスクリプション」の入力欄が開いたままで、カーソルが点滅していました。ID は一度使うと後から変えにくいものです。それなのに、置き場所であるアカウントのほうは「いつか考えればよい」と思っていたのです。

最初にお伝えしたいのは、個人から法人へ移る道は **2つ** ある、という点です。1つは、アカウントそのものを個人から組織へ切り替える更新リクエスト。もう1つは、新しく作った法人アカウントへアプリを1本ずつ移す App Transfer です。どちらを選ぶかで、外す作業の量も、待つ日数も変わります。

Rork で作ったアプリも、公開すれば自分の Apple アカウントに並びます。ですので、この問いは遅かれ早かれ届きます。以下は、2026年11月時点で Apple の公式ページを一つずつ開き、本文を読んで確かめた内容です。

## 2つの道の違いを先に並べます

この記事の旧版で、私は「アカウントの種類を個人から法人へ切り替える方法は公式ページに見当たらない」と書いていました。これは誤りでした。Apple の[アカウント情報の更新ページ](https://developer.apple.com/help/account/manage-your-team/update-your-account-information/)には、個人のメンバーシップを組織のメンバーシップへ更新するリクエストの節があります。お詫びして訂正いたします。

公式の記述を要約すると、更新リクエストの条件は次のとおりです。

- 組織の創業者または共同創業者であること
- 組織の D-U-N-S 番号などを提出すること
- 組織の実在を確かめるため、事業書類の提出を求められる場合があること

一方の App Transfer は、すでにある（または新しく作った）法人アカウントへ、アプリを1本ずつ移す仕組みです。2つを並べると、違いは次のようになります。

<tr><td>動くもの</td><td>アカウントの種類そのもの</td><td>アプリ1本ずつ</td></tr>

更新リクエストのほうが軽く見えます。実際、アプリを何本も持っている人にとっては、機能ごとに外す作業が要らない点は大きいはずです。

ただし、確かめきれていない点もあります。アカウントの種類を切り替えたとき Team ID がそのまま残るのか、公式ページには明記がありませんでした。また、同じページには「組織名を変えると全アプリのベンダー名が変わり、既存ユーザーの identifierForVendor（IDFV）が次の更新でリセットされる」とあります。個人から組織への更新で同じことが起きるかは、私には確認できていません。広告の計測で IDFV を使っている方は、申請の前に Apple へ問い合わせておくほうが安全です。

もう1つ、Apple Developer フォーラムには、個人から組織への更新が数週間から数か月保留されたという投稿がいくつも並んでいます。公式の目安ではありませんが、「申請したら翌週には法人名で売れる」とは考えないほうがよさそうです。

## どちらを選ぶかの線引き

私が決めている判断の基準は、次の一文です。

**本人が創業者で、同じ人が同じアプリを続けて運用するなら更新リクエスト。アプリの持ち主そのものが変わるなら App Transfer。**

たとえば、自分ひとりで合同会社を作り、これまでのアプリをその会社で売りたい場合は前者です。共同で始めた会社の既存アカウントへ合流する、取引先にアプリを納める、アプリを売る、といった場合は後者になります。

<tr><td>すでに法人アカウントを持つ会社に参加する</td><td>App Transfer</td><td>アカウントを1つにまとめられる</td></tr>

アプリを譲る・売るときの引き継ぎの実務は、[アプリを手放す日の実務](/articles/rork-business/rork-app-store-app-transfer-handover-checklist)に分けて書きました。この記事では、自分の事業の形が変わるときの話に絞ります。

## App Transfer を選んだときの条件

ここからは App Transfer を選んだ場合です。[App Transfer の条件ページ](https://developer.apple.com/help/app-store-connect/transfer-an-app/app-transfer-criteria)には、アプリの状態と両方のアカウントの状態についての条件が並んでいます。引っかかりやすいものを抜き出します。

<table>
<thead>
<tr><th>条件（公式の記述の要旨）</th><th>見落としやすい場面</th></tr>
</thead>
<tbody>
<tr><td>両方のアカウントが「保留中・変更中」の状態でなく、最新の有料・無料アプリ契約に同意済みであること</td><td>受ける側の法人アカウントで、契約の同意だけが残っている</td></tr>
<tr><td>App Store に公開されたバージョンが1つ以上あること</td><td>初回の審査が通る前に移そうとする</td></tr>
<tr><td>Processing for Distribution・Waiting for Review・In Review・Accepted・Pending Developer Release・Pending Apple Release のいずれでもないこと</td><td>更新を出した直後に移そうとする</td></tr>
<tr><td>どの国・地域でも予約注文の対象でないこと</td><td>新作の予約を先に開けている</td></tr>
<tr><td>アプリ内課金の商品が Approved・Ready to Submit・Developer Removed from Sale・Rejected のいずれかであること</td><td>新しい課金商品を審査に出したまま</td></tr>
<tr><td>アプリ内課金の商品 ID が、受ける側のアカウントのどのアプリとも重複しないこと</td><td>受ける側のテスト用アプリに同じ商品 ID を使い回している</td></tr>
</tbody>
</table>

一番上の行は、2つの道を混ぜたときに効いてきます。個人から組織への更新リクエストを出している最中は、アカウントが「変更中」にあたる可能性が高く、その間は App Transfer の条件を満たせません。**2つの道は、同時に走らせない**——これが、私が今回いちばん強く書き残しておきたい点です。

最後の行は、私にとって一番ひやりとしたものでした。課金商品 ID を「あとで整理すればよい」ものとして扱うと、移す段階で止まります。

## 外す作業を、アプリごとに書き出す

[移管の概要ページ](https://developer.apple.com/help/app-store-connect/transfer-an-app/overview-of-app-transfer/)には、機能ごとの注意が並んでいます。課金・通知・ログインを使う個人のアプリで、実際に作業が発生しやすいものに絞ります。

**1. TestFlight。** 移管を始める前に、すべてのベータ版で TestFlight を止めます。ビルドとテスターを外し、各言語の「テスト情報」の欄も空にします。

**2. 自動更新サブスクリプションの共有シークレット。** App 専用の共有シークレットを使う必要があります。申請の前に生成して受け側へ渡し、受け側はサーバーの検証をそれに切り替えます。移管が終わったら、受け側でもう一度生成し直します。

**3. Sign in with Apple。** ユーザーごとに「transfer identifier」を作る作業が要ります。他のアプリとグループ化している場合は、先にグループを解除します。関連づいた Service ID もアプリと一緒に移るため、移したくなければ先に関連づけを外します。

**4. プッシュ通知と Keychain 共有。** 受け側の APNs 証明書は有効期限まで使えますが、その後は新しい証明書か鍵が必要です。Keychain 共有はアプリを更新するまでしか動かず、更新後は利用者に1度だけ再ログインしてもらう形になります。

**5. iCloud（CloudKit）と Apple Pay。** CloudKit のコンテナは受け側に移ります。同じコンテナを別のアプリと共有していると、その別のアプリは読み書きできなくなります。Apple Pay の merchant ID は移らず、次の更新を出すときに受け側で新しく作ります。

ほかに、Xcode Cloud を使っていれば関連データを先に消すこと、App Groups は完了後に受け側で登録し直せることも書かれています。

アプリが2本以上あると、どのアプリで何を外すのかが頭の中だけでは追えなくなります。私は次の小さなスクリプトで書き出しています。App Store Connect を開きながら、各アプリの機能に true を入れるだけです。

```js
// transfer-prep.mjs — App Transfer の前に外すものと、60日の期限を並べる
// 使い方: node transfer-prep.mjs <申請日> [受け側の承認日]   例: node transfer-prep.mjs 2026-12-01 2026-12-03
// 日付は暦の日として扱う（UTC の 0 時に固定し、時差で日付がずれないようにする）
const day = (s) => new Date(`${s}T00:00:00Z`);
const requested = day(process.argv[2] ?? "2026-12-01");
const accepted = process.argv[3] ? day(process.argv[3]) : null;

// アプリごとに「使っている機能」を true にする（App Store Connect を見ながら埋める）
const apps = [
  { name: "WallpaperApp", testflight: true, subscription: true, siwa: false, push: true, cloudkit: false, applePay: false },
  { name: "NoteApp",      testflight: false, subscription: false, siwa: true, push: false, cloudkit: true, applePay: false },
];

const tasks = {
  testflight:   "TestFlight のビルドとテスターを外し、全言語のテスト情報を空にする",
  subscription: "App 専用共有シークレットを生成して受け側に渡す（完了後に受け側で再生成）",
  siwa:         "全ユーザーの transfer_sub を作る（グループ化していれば先に解除）",
  push:         "受け側チームの APNs キーを用意し、送信サーバーの鍵を差し替える",
  cloudkit:     "同じ CloudKit コンテナを使う別アプリがないか確かめる",
  applePay:     "受け側で新しい merchant ID を作る（次の更新を出す前）",
};

const addDays = (d, n) => new Date(d.getTime() + n * 86400000).toISOString().slice(0, 10);

for (const app of apps) {
  const todo = Object.keys(tasks).filter((k) => app[k]).map((k) => `  - ${tasks[k]}`);
  console.log(`${app.name}: 外す作業 ${todo.length} 件`);
  console.log(todo.length ? todo.join("\n") : "  - なし（バックアップだけ取る）");
  if (app.siwa && accepted) {
    console.log(`  ※ transfer_sub を新しい ID に交換する期限: ${addDays(accepted, 60)}（承認日から60日）`);
  }
}
console.log(`申請 ${addDays(requested, 0)} → 受け側の承認期限 ${addDays(requested, 60)}（申請から60日）`);
```

Node.js 22 で `node transfer-prep.mjs 2026-12-01 2026-12-03` と実行すると、次のように出ます。

```text
WallpaperApp: 外す作業 3 件
  - TestFlight のビルドとテスターを外し、全言語のテスト情報を空にする
  - App 専用共有シークレットを生成して受け側に渡す（完了後に受け側で再生成）
  - 受け側チームの APNs キーを用意し、送信サーバーの鍵を差し替える
NoteApp: 外す作業 2 件
  - 全ユーザーの transfer_sub を作る（グループ化していれば先に解除）
  - 同じ CloudKit コンテナを使う別アプリがないか確かめる
  ※ transfer_sub を新しい ID に交換する期限: 2027-02-01（承認日から60日）
申請 2026-12-01 → 受け側の承認期限 2027-01-30（申請から60日）
```

日付を UTC の0時に固定しているのには理由があります。最初は日本時間の0時で日付を作っていたのですが、`toISOString()` が UTC に直すため、出てくる日付がすべて1日前にずれていました。期限の計算で1日ずれるのは、いちばん避けたい種類の間違いです。

## Sign in with Apple を使っているときの手順

Sign in with Apple を入れているアプリは、外す作業の中でここがいちばん重くなります。Apple の[開発者ドキュメント](https://developer.apple.com/documentation/signinwithapple/transferring-your-apps-and-users-to-another-team)によると、流れは次のとおりです。

1. 移す側が、クライアント認証（`grant_type=client_credentials`、`scope=user.migration`）でアクセストークンを取ります
2. ユーザーごとに `https://appleid.apple.com/auth/usermigrationinfo` へ、そのユーザーの `sub` と受け側の Team ID（`target`）を送り、`transfer_sub` を受け取ります
3. 受け側へ渡すデータからは、移す側のユーザー ID と private relay のメールアドレスを外し、`transfer_sub` だけで人を識別します
4. 受け側は、承認から60日以内に `transfer_sub` を自分のチームの ID へ交換します

公式ドキュメントに載っているリクエストの形は、次のとおりです（私の環境では実行していません）。

```http
POST /auth/usermigrationinfo HTTP/1.1
Host: appleid.apple.com
Content-Type: application/x-www-form-urlencoded
Authorization: Bearer {access_token}

sub={sub}&target={recipient_team_id}&client_id={client_id}&client_secret={client_secret}
```

返ってくるのは `{"transfer_sub":"..."}` という1項目です。移す側は、受け側の承認前から、承認後60日までのあいだに作れます。

見落としやすいのは、ほかのアプリを使っていないユーザーには、移管のあと private relay のメールで連絡できなくなる、という点です。ログイン方法の変更などを知らせたいなら、移す前に送っておく必要があります。

申請の画面で止まったときに、私が見る順番です。画面に出る文言は状況によって変わるため、ここでは症状で書きます。

## よくある誤解

**「個人から法人へは切り替えられない」**——前述のとおり、公式に更新リクエストの道があります。私も旧版でこの誤解をそのまま書いていました。

**「移管するとレビューが消え、Bundle ID も変わる」**——公式の概要ページには、レビューと評価は残り、Bundle ID も維持されると書かれています。ダウンロードできる状態のまま移せるため、利用者には更新が届き続けます。

**「屋号で法人として登録できる」**——[登録ページ](https://developer.apple.com/programs/enroll/)には、DBA・屋号・商号・支店は受け付けないと明記されています。法人として契約を結べる組織であること、D-U-N-S 番号、組織のドメインのメールアドレス、公開されて機能しているウェブサイトが必要です。個人で登録した場合は、本人の法的な氏名が販売者名として表示されます。

**「承認されたらその日のうちに終わる」**——受け側の承認は申請から60日以内、承認後の処理は最大2営業日です。Sign in with Apple を使っていれば、その後さらに60日以内の交換作業が残ります。

## 引き継がれるもの、引き継がれないもの

引き継がれると明記されているのは、レビューと評価、そして Bundle ID です。

Bundle ID は、ビルドを1度アップロードしたあとは変えられません。この点は、別の記事で[アプリ ID を最初のリリース前に決める理由](/articles/rork-basics/rork-app-id-immutable-before-first-release)として書きました。移管の話は、その続きにあたります。

引き継がれないのは、Apple Pay の merchant ID、Game Center のマッチメイキング設定、Wallet パスの識別子（パスの再発行が必要）などです。課金とログインだけのアプリなら、影響の中心は共有シークレットと Sign in with Apple に集まります。

## 移したあとに詰まる一歩

移管が終わった直後に当たるのは、署名です。公式の承認ページには、受け側の Apple Developer アカウントで新しいプロビジョニングプロファイルを作り、移したアプリの App ID と配布用証明書に結びつけるよう書かれています。Expo の EAS でビルドしている場合も、署名に使う Apple のチームが変わるため、次のビルドの前に資格情報を受け側のチームで作り直すことになります。

もう1つは、販売者名が変わることに伴う表記です。アプリ内やサイトの特定商取引法の表記、プライバシーポリシーの運営者名も、販売者名に合わせて書き換えます。表記の決め方は[課金を入れる前に決める特商法表記](/articles/rork-business/tokushoho-notation-before-paid-plan-address-phone-decision)にまとめました。法人で新しく登録する手続きそのものは、[Apple 側で自分が済ませておく手続き](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)をご覧いただければと思います。

## あの夜に引いた線

最初のうち、私はアカウントの種類も課金商品 ID も「後でまとめて片づければよい」ものとして同じ箱に入れていました。調べ直して分かったのは、片方は後から直す道があり、もう片方はほとんど無い、ということです。

**アカウントの形は後から変えられても、アプリに刻んだ ID は後から変えにくいものです。** ですので、ID だけは最初から「どのアカウントに移っても困らない名前」にしておく——いまはこの線引きで、新しい課金商品の ID を決めています。

## 次のアクションは1つだけ

App Store Connect を開き、自分のアプリごとに TestFlight・課金・Sign in with Apple・プッシュ通知・iCloud の5つのうちどれを使っているかを書き出してみてください。上のスクリプトの true を埋めるだけでも足ります。

いま思えば、あの夜に手が止まったのは、この表が頭の中にしか無かったからなのだと思います。表が空欄に近いほど、どちらの道を選んでも移す日は軽くなります。
