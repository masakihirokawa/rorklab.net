更新版を提出しようとした夜のことです。ビルドのアップロードは終わり、あとは「リリースノート」を貼って審査に送るだけ、のはずでした。

ところが、リリースノートの欄の近くに赤い警告が出て、先へ進めません。

貼ったのは、内部テストの仲間に向けて書いた更新メモでした。直した不具合、触った画面、気になった挙動まで、思いつくままに網羅してあります。自分用には良いメモでしたが、ストアの入力欄には長すぎたのです。

最初にお伝えしたいのは、**Google Play のリリースノート（「このリリースの新機能」）は、言語ごとに500文字までという点**です。しかも制限は言語それぞれに掛かります。日本語と英語を入れていれば、どちらか片方が超えているだけで、リリース全体が先へ進めません。

この記事は、Rork や Expo で作ったアプリを初めて Google Play で更新する方が、提出ボタンの手前で止まったときに「どこを見て、何を直せば先へ進めるか」を持ち帰れるように書いています。画面の名前や制限は2026年11月時点のもので、公式ヘルプ「[リリースを準備して公開する](https://support.google.com/googleplay/android-developer/answer/9859348)」で確かめながら整理しました。

## 先に結論: 止まったときの切り分け表

提出が止まる原因は、私の場合ほぼ次のどれかでした。上から順に見ていくと、たいてい数分で見当がつきます。

<table>
<thead><tr><th>症状</th><th>原因の候補</th><th>確かめ方</th><th>直し方</th></tr></thead>
<tbody>
<tr><td>リリースノート欄の近くに赤い警告が出て、次へ進めない</td><td>どれか1言語が500文字を超えている</td><td>言語タグごとに文字数を数える（下のスクリプト）</td><td>その言語だけ短い版に差し替える</td></tr>

<tr><td>新しいリリースを作る入口が見当たらない</td><td>以前に作りかけた下書きのリリースが残っている</td><td>同じトラックのリリース一覧に「下書き」がないか見る</td><td>下書きを開き、今回のビルドとノートに差し替えて使う</td></tr>

表のうち、いちばん多いのは一行目です。ただ、二行目のタグの閉じ忘れは、文字数を何度数え直しても直らないので、気づくまでに時間を取られやすいと感じています。

## 500文字は、どこに掛かる制限なのか

Play Console のリリースノート欄は、1つの入力欄に言語タグで区切って書く形式です。たとえば日本語と英語なら、次のようになります。

```text
<ja-JP>
・壁紙の読み込みが速くなりました
・一部の端末で起動しない不具合を修正しました
</ja-JP>
<en-US>
- Wallpapers now load faster
- Fixed a crash on launch on some devices
</en-US>
```

500文字の上限は、このタグに挟まれた中身ひとつずつに掛かります。ここで、私自身が最初に取り違えていたことを3つ書き残しておきます。

**誤解1: 全言語を合わせて500文字。** そうではなく、言語ごとに500文字です。言語を増やしても、1言語あたりの余裕は減りません。そのぶん、どの言語が超えているのかを1つずつ確かめる手間が要ります。

**誤解2: 日本語はバイト数で数えるので不利。** 上限は文字の数で、バイト数ではありません。日本語のほうがむしろ短く収まりやすく、同じ内容を訳すと英語側が先に溢れることが多いのです。

**誤解3: App Store と同じ上限。** App Store Connect の「このバージョンの新機能」は、別の画面に別の上限（4,000文字・Apple のヘルプ「[Platform version information](https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information)」で確認）が決まっています。iOS で通った文章をそのまま Play に貼ると、Play 側だけ止まることがあります。

## Google Play と App Store の書き分け

両方のストアに出している場合、私は次の表を手元に置いて書き分けています。

<thead><tr><th>項目</th><th>Google Play</th><th>App Store</th></tr></thead>

<tr><td>欄の名前</td><td>このリリースの新機能（リリースノート）</td><td>このバージョンの新機能</td></tr>

<tr><td>止まりやすい場所</td><td>どれか1言語の超過・タグの閉じ忘れ</td><td>入れ忘れた言語がないか</td></tr>

どちらを先に書くか迷ったら、**Play の500文字で書いた短い版を正本にして、App Store にはそれを貼る**のがいちばん手戻りが少ないと思います。短いほうに長いほうを合わせるのは苦しく、長いほうに短いほうを貼るのは何の問題も起きないからです。

## 長文を捨てずに、短い版を作る

最初のうち、私は長文を削る方向で直そうとしました。結果は芳しくありませんでした。削るたびに「これも大事」と迷い、500文字の手前で手が止まります。

いまは考え方を変えています。**長いメモはメモとして残し、ストア用は最初から別に書く**、という線引きです。

手順は短く済みます。

1. 長い更新メモを、そのままファイルに保存します（捨てません）。
2. ユーザーに見える変化だけを、1機能1行で書き出します。
3. 言語ごとに文字数を数え、500文字より余裕を持たせて収めます。
4. 短い版もファイルに保存し、次回からは貼るだけにします。

Before と After で比べると、違いがはっきりします。

```text
# Before（内部テスト向けのメモをそのまま貼ったもの・一部）
- ImageCache の LRU を 64 → 128 に変更、低メモリ端末での再読込を抑制
- SettingsScreen のボタン配置を修正（Pixel 系で右端が切れていた件）
- 起動時クラッシュ（Android 10 の一部端末、NullPointer）を修正
- ログ出力を整理、debug ビルドの計測コードを削除
```

```text
# After（ストアに貼る短い版）
・壁紙の読み込みが速くなりました
・設定画面のボタンの位置を調整しました
・一部の端末で起動しない不具合を修正しました
```

After から消えたのは、キャッシュの数値・画面のクラス名・ログの整理です。どれも直した本人には大事ですが、読む方が知りたいのは「何が変わって、何が直ったか」だけなのだと思います。端末名や OS の版も、問い合わせが来ていた不具合でない限り、書かないことにしています。

## 貼る前に文字数を数えておく

画面で赤くなってから直すより、貼る前に数えておくほうが夜の心臓に優しいです。次の Python スクリプトは、言語ごとのファイルでも、Play Console に貼る形（言語タグつきの1ファイル）でも読めるようにしてあります。標準ライブラリだけで動きます。

```python
# check_release_notes.py
# 使い方:
#   python3 check_release_notes.py notes/ja-JP.txt notes/en-US.txt   （言語ごとのファイル）
#   python3 check_release_notes.py notes/play_console.txt            （<ja-JP>…</ja-JP> 形式の1ファイル）
import re
import sys
import unicodedata

LIMIT = 500   # Google Play の1言語あたりの上限
MARGIN = 30   # 画面側の数え方との差に備えた余裕
TAG = re.compile(r"<([a-z]{2,3}(?:-[A-Za-z0-9]+)*)>(.*?)</\1>", re.S)
broken = False  # タグの閉じ忘れなど、数える前の問題

def blocks(path):
    global broken
    raw = open(path, encoding="utf-8").read().replace("\r\n", "\n")
    found = TAG.findall(raw)
    if found:
        rest = TAG.sub("", raw).strip()
        if rest:
            print(f"{path}: タグの外に文字があります（閉じ忘れの疑い） → {rest[:30]!r}")
            broken = True
        return [(lang, body.strip()) for lang, body in found]
    if re.search(r"</?[a-z]{2,3}(-[A-Za-z0-9]+)*>", raw):
        print(f"{path}: 閉じていない言語タグがあります")
        broken = True
        return [("?", raw.strip())]
    return [(path, raw.strip())]

ng = False
for path in sys.argv[1:]:
    for lang, text in blocks(path):
        n = len(unicodedata.normalize("NFC", text))
        risky = any(c in text for c in ("‍", "️"))
        if n > LIMIT:
            status = "超過"
        elif n > LIMIT - MARGIN:
            status = "ギリギリ"
        else:
            status = "OK"
        note = "（絵文字の結合文字あり・画面と数が食い違うことがあります）" if risky else ""
        print(f"{lang}: {n}文字 {status}{note}")
        ng = ng or status != "OK"

sys.exit(1 if (ng or broken) else 0)
```

手元（Python 3.10）で、英語側に内部向けの行を残したまま流したときの出力は次のとおりです。

```text
$ python3 check_release_notes.py notes/ja-JP.txt notes/en-US.txt
notes/ja-JP.txt: 59文字 OK
notes/en-US.txt: 589文字 超過
$ echo $?
1
```

日本語のタグを閉じ忘れたファイルを渡すと、文字数より先にそちらを知らせてくれます。

```text
$ python3 check_release_notes.py notes/broken.txt
notes/broken.txt: タグの外に文字があります（閉じ忘れの疑い） → '<ja-JP>\n・壁紙の読み込みが速くなりました\n・設定画面'
en-US: 121文字 OK
```

いくつか、書き方の理由を添えておきます。

- Windows で書いたファイルの改行（CRLF）を LF にそろえてから数えています。そろえないと、改行1つが2文字に数えられてしまうためです。
- `unicodedata.normalize("NFC", …)` は、濁点が別の文字として入っているような表記を1文字にまとめてから数えるためのものです。
- 家族の絵文字のように、いくつかの文字をつないで1つに見せる絵文字は、Python の `len()` では複数に数えられます。Play Console 側がそれをどう数えるかは、私は確認できていません。そのため、結合文字を見つけたら注意書きを出すだけにして、余裕を30文字取っています。
- 終了コードを返すので、CI や提出前のスクリプトに組み込めば、超過や閉じ忘れがあるときに手前で止まります。

## もう一つの罠: 公開していない下書きが残っている

同じ日に、別の壁にも当たりました。新しいリリースを作ろうとして、先へ進めなかったのです。

原因は、以前に作りかけたまま公開していない下書きのリリースでした。下書きが残っていると、新しいリリースを作る入口が塞がることがあります。

私は下書きを消さず、**その下書きを開いて、中身を今回のビルドとリリースノートに差し替えて使いました**。それで先へ進めました。消してもよい下書きかどうか分からないときは、消すより編集して使うほうが安全です。

あとから振り返ると、この下書きは自分の手で作ったものではありませんでした。EAS Submit で Android 版を送るとき、eas.json の `submit` にある `releaseStatus` を `draft` にしていたため、送るたびに Play Console 側へ下書きのリリースとして届いていたのです（項目名は2026年11月時点・Expo の「[Configuration with eas.json](https://docs.expo.dev/eas/json/)」で確認）。

```json
{
  "submit": {
    "production": {
      "android": {
        "track": "production",
        "releaseStatus": "draft"
      }
    }
  }
}
```

下書きで受け取ること自体は悪くありません。リリースノートを Play Console で貼ってから公開する、という流れにできるからです。ただ、その下書きを片づけないまま次のビルドを送ると、下書きが重なって、どれが今回のものか分からなくなります。いまは「EAS Submit で下書きを送った日のうちに、Play Console でノートを貼って公開まで進める」と決めています。

また、アプリを一度も公開していない段階で API 経由のリリースを作ろうとすると、`Only releases with status draft may be created on draft app` というエラーが返ります。これは文字数とは関係がなく、最初の1回は下書きとして送り、Play Console から手で公開すれば通ります。

## 次に詰まりやすい一歩

リリースノートが通ったあと、同じ夜にもう一度手が止まりやすいのは、公開の割合と、テストの期間です。

段階公開で最初に5%だけ出したとき、数字がどこまで信じられるのかは、[段階公開の最初の5%で見えた Crash-free 99.7%、何ユーザーから信じてよいのか](/articles/app-dev/staged-rollout-first-five-percent-crash-free-needs-sample-size-wait-before-proceed) にまとめました。まだ本番に出す前で、閉鎖テストの14日間を待っている段階の方は、[閉鎖テストの14日間は、待つ時間ではなく申請フォームに書く材料を集める時間です](/articles/app-dev/play-closed-test-14-days-production-access-form-material) のほうが先に役立つと思います。アプリの ID のように、公開後には変えられない名前を確かめておきたい方は、[変えられる名前と、変えられない名前 — Rork で最初の1本を公開する前の30分](/articles/rork-basics/rork-app-id-immutable-before-first-release) もあわせてご覧ください。

## 提出日の前に、手元に置いておくもの

- 長い更新メモ（保存用）と、言語ごとの短い版（貼る用）を別ファイルで持っておきます。
- 貼る前に、スクリプトで全言語の文字数とタグの閉じ忘れを確かめます。
- EAS Submit で下書きを送っている場合は、その日のうちに公開まで進めるか、下書きを片づけます。
- 提出の前日に、Play Console に古い下書きのリリースが残っていないかを見ておきます。

**長い記録は自分のために、短い文章はユーザーのために。** この線引きは、提出日の夜に疲れていても崩さないようにしています。

まずは今回のリリースの更新メモを1行ずつ見直して、ユーザーに見える変化だけを残した短い版を、言語タグつきのファイルに1つ保存し、上のスクリプトに一度通すところから始めていただければと思います。私もそこから直しました。
