以前、この記事には「Rork の内部で機械学習による最適化が走っている」と断定する書き方をしていました。いま読み返すと、公式の説明で裏づけられない部分を、体感と推測で埋めてしまっていたのです。具体的には、専用の最適化コンポーネントの名前や、プラン別の機能差の表、きれいに並んだ計測値がそれにあたります。読んでくださった方が、その API を探して時間を使ってしまったかもしれません。

そこで、書き直すことにしました。確かめられることと推測にとどまることを分け、「自分のプロジェクトで軽さを測る」ところまでを一続きにします。今回の改訂では、測り方そのものの落とし穴——開発モードのまま測ってしまう、バンドルの大きさとアプリの大きさを混同する——を加えました。

## 最初にお伝えしたいのは「何が公式に言えるのか」

Rork が生成するのは Expo と React Native のプロジェクトです。軽さの大半は、Rork 固有の仕組みというより、Expo と React Native の標準的な仕組みで説明がつきます。

  <thead>

  </thead>
  <tbody>
    <tr><td>起動が速い</td><td>Hermes によるバイトコード事前コンパイル</td><td>Expo の既定設定です</td></tr>
    <tr><td>バンドルが小さい</td><td>Metro の不要コード除去と、依存パッケージの少なさ</td><td>生成時に選ばれる依存の量に左右されます</td></tr>
    <tr><td>画像表示が滑らか</td><td>expo-image のキャッシュとプレースホルダー</td><td>ライブラリ側の機能です</td></tr>

生成の過程でモデルがどのような最適化をしているかは、外から見えません。2026年11月時点で Rork の公式ドキュメントを読み返しても、「機械学習による実行時の最適化」にあたる機能や API の説明は見つけられませんでした。私が「軽い」と感じたアプリがあったとしても、それが生成の工夫なのか、単に依存が少なく素直な構成だったからなのかは、切り分けられていないのです。ここは「分からない」と書くのが誠実だと考えています。

## 軽さの正体は、たいてい「余計なものを入れていない」こと

個人で運用している壁紙アプリを作り直したとき、機能を足すほど起動が重くなり、胃が痛くなる思いをしました。原因を辿ると、使っていない大きな依存パッケージが、起動時に読み込まれていたのです。

生成されたアプリが軽く感じられるときも、同じ構図が働いている可能性があります。依存が最小限で、画面ごとに責務が分かれていて、状態管理も素朴であれば、アプリは自然に軽くなります。

つまり、見るべきなのは「Rork が何をしたか」より「いま手元のプロジェクトに何が入っているか」です。

## よくある誤解を三つ、先にほどいておきます

測り始める前に、私自身が引っかかった思い込みを置いておきます。どれも、測った数値の読み違いにつながるものです。

**誤解 1: 「プレビューで重いから、アプリが重い」**。React Native の公式ドキュメント（Performance の章）には、開発モードでは JavaScript スレッドの性能が大きく落ちると書かれています。開発用の警告やチェックが動いているためです。Rork のプレビューや Expo Go で感じる重さは、そのまま製品版の重さではありません。比べるのは、いつも release ビルド同士です。

**誤解 2: 「バンドルが小さければ、ストアのサイズも小さい」**。書き出した JavaScript バンドルは、アプリ全体の一部にすぎません。ネイティブのライブラリ、画像やフォントなどのアセット、OS ごとの最適化が加わって、ストアに表示されるサイズになります。JavaScript の重さとバイナリの重さは、別の問題として分けて追います。

**誤解 3: 「一度測れば十分」**。起動時間は、端末の温度や裏で動くアプリでぶれます。1 回の数値で良し悪しを決めると、変化ではなく揺らぎを追いかけることになります。5 回測って中央値を取る、という地味な決まりごとが、いちばん効きました。

## 手順 0: 測る前に release ビルドを用意する

計測は release 構成のビルドで行います。Rork から書き出したプロジェクトを手元で動かせる状態なら、次のコマンドで release 構成のまま実機に入れられます。

```bash
# iOS（Xcode と実機の接続が必要です）
npx expo run:ios --configuration Release --device

# Android（USB デバッグを有効にした実機を接続します）
npx expo run:android --variant release --device
```

EAS Build で作った内部配布用のビルドや、TestFlight・内部テストのビルドでも構いません。大切なのは「前回と同じ種類のビルドで比べる」ことで、開発ビルドと release ビルドの数値を並べないことです。

## 手順 1: バンドルを書き出して中身を見る

まずプロジェクトを書き出し、出力されたファイルの大きさを確認します。

```bash
npx expo export --platform ios
ls -lh dist/_expo/static/js/ios/
```

iOS と Android では、Hermes 向けにコンパイルされた `.hbc` のファイルが出力されます。その大きさが、そのアプリの JavaScript の重さのおおよその目安です。数値は SDK のバージョンでも変わるため、「自分のプロジェクトの基準値」としてメモしておきます。機能を足すたびに同じコマンドを叩けば、増えた分が見えてきます。

依存ごとの内訳を見たいときは、Expo 公式の **Expo Atlas** が使えます。[Expo のバンドル分析ガイド](https://docs.expo.dev/guides/analyzing-bundles/)にある手順は、環境変数を付けて書き出し、その記録を Atlas で開くというものです。

```bash
# 書き出しと同時に、バンドルの記録を .expo/atlas.jsonl に残します
EXPO_ATLAS=true npx expo export --platform ios

# 記録をブラウザで開いて、パッケージごとの大きさを見ます
npx expo-atlas .expo/atlas.jsonl
```

開発サーバーで見たいときは `EXPO_ATLAS=true npx expo start` で起動し、ターミナルで `shift+m` を押すと開発ツールの一覧から Atlas を開けます。私が最初に見つけたのは、日付の整形のためだけに入れていたライブラリが、思っていたよりずっと大きな面積を占めていたことでした。

サイズの削減そのものについては、[Rork アプリのバイナリサイズが 150MB を超えた時に切り分ける 5 つの要因と実践的な削減手順](/articles/rork-dev/rork-app-bundle-size-reduction-guide)に手順をまとめています。

## 手順 2: 起動時間を「自分の端末」で測る

起動時間は、シミュレータではなく実機で測ります。同じ操作を 5 回ほど繰り返し、中央値を記録するのが現実的です。

- アプリを完全終了してから起動（コールドスタート）
- 起動から最初の画面が操作できるようになるまでを計測
- 低価格帯の端末か、古めの端末でも一度は計測

Android では、端末をつないだ状態で次のコマンドを使うと、起動にかかった時間が `TotalTime` としてミリ秒で返ってきます。パッケージ名は `app.json` の `android.package` に書かれているものです。

```bash
# いったん終了させてから、起動にかかった時間を測ります
adb shell am force-stop com.example.myapp
adb shell am start -W -n com.example.myapp/.MainActivity
```

iOS では、Xcode の Instruments にある「App Launch」のテンプレートで計れます。道具を用意しにくいときは、画面録画を撮ってコマ送りで確かめる方法でも傾向は十分につかめます。厳密さより、「変更の前後で比べられること」が大切です。起動を短くする具体策は、[Rork で生成したアプリの起動時間を短くする実践テクニック](/articles/rork-dev/rork-app-startup-time-optimization-techniques)で扱っています。

## 手順 3: リストと画像の負荷を見る

画面が重くなる場面は、リストと画像に集中しがちです。

リストは、数百件のデータを流し込んで、スクロール中にコマ落ちがないかを見ます。開発メニューの「Performance Monitor」を開くと、UI スレッドと JavaScript スレッドのフレームレートが画面の上に出ます。どちらのスレッドが落ちているかで、疑う場所が変わります。ただし、この表示は開発ビルドでのものなので、傾向を見る道具として使い、最終的な判断は release ビルドの体感と合わせて行います。

カクつきが出たら、描画の仕組みを見直す段階です。移行の手順は、[FlatList でカクつき始めたら読む — Rork アプリを FlashList v2 で快適にする実装手順](/articles/rork-dev/rork-flashlist-v2-flatlist-migration-performance)にまとめました。

画像は、表示速度よりもディスクキャッシュの膨らみに注意が要ります。長く使われるアプリほど、端末内の「書類とデータ」が増えていきます。対処は[Rork 製アプリの『書類とデータ』が数 GB に膨らむときの原因と対処](/articles/rork-dev/rork-expo-image-disk-cache-bloat-fix)にまとめています。

## 道具の選び方 — どれを、いつ使うか

道具は多くありません。迷ったときは、次の基準で一つだけ選んでいただければ足ります。

要するに、**定点観測は export の大きさ、原因探しは Atlas と Performance Monitor** という分け方です。最初から全部を揃える必要はありません。

## 手書きのコードを足したあとに性能を保つ線引き

生成されたアプリに自分でコードを足していくと、あるとき急に重くなることがあります。私が守っている線引きは、次のとおりです。

- 新しい依存を入れる前に、本当に必要かを一度立ち止まって確認
- 長いリストは、必ず仮想化されたリストコンポーネントで描画
- 画像は、表示サイズに近い大きさのものを `expo-image` で読み込み
- 重い処理は、画面の初回表示のあとへ後回し

どれも特別な技術ではありません。ただ、生成直後の素直な構成を崩さないための、地味な歯止めになります。私は計測の記録を、日付・ビルドの種類・export の大きさ・起動の中央値の四つだけを書く小さな表にしています。項目を増やすと続かなかったので、この四つに絞りました。

## プロンプトで性能の方向性を伝える

Rork に生成を頼むとき、性能について一言添えておくと、方向性が揃いやすくなります。たとえば「古い端末でも動くことを優先してください」「画像は一覧で多く表示します」といった、使われ方の条件です。

ただし、これで最適化が「発動する」と断言できる根拠は、私の手元にはありません。あくまで、条件を明確にしたほうが意図に近い構成が返ってきやすい、という経験則にとどめておきます。結果は、手順 0 から 3 で確かめていただければ幸いです。

## 次に詰まりやすいのは「起動の予算」の決め方

計測を始めると、次は「何ミリ秒なら合格か」で手が止まるはずです。私もそうでした。そこで役に立ったのは、絶対値の目標ではなく「前回より悪くしない」という予算の考え方です。起動経路に処理を足すときの具体的な決め方は、[起動時間を『予算』として管理する — 6本のアプリでSDK初期化を後ろ倒しにした設計記録](/articles/rork-dev/rork-startup-time-budget-deferred-sdk-init-six-apps)にまとめています。

## まとめ — 記録と計測は自分で、解釈は慎重に

**生成されたアプリの軽さは、噂ではなく、release ビルドで測った自分の数値で語ります**。これが、今回の書き直しで改めて確認した線引きです。

次の一歩としては、いま手元にある Rork 製アプリを `npx expo export` で書き出して、出力ファイルの大きさを一つだけ記録してみてください。数値が一つあるだけで、次に機能を足すときの判断が、はるかに落ち着いたものになります。
