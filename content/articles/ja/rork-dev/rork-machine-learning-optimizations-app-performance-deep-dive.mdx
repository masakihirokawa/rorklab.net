以前、この記事には「Rork の内部で機械学習による最適化が走っている」と断定する書き方をしていました。いま読み返すと、公式の説明で裏づけられない部分を、体感と推測で埋めてしまっていたのです。具体的には、専用の最適化コンポーネントの名前や、プラン別の機能差の表、きれいに並んだ計測値がそれにあたります。読んでくださった方が、その API を探して時間を使ってしまったかもしれません。

そこで、書き直すことにしました。確かめられることと推測にとどまることを分け、「自分のプロジェクトで軽さを測る」ところまでを一続きにします。

## 最初にお伝えしたいのは「何が公式に言えるのか」

Rork が生成するのは Expo と React Native のプロジェクトです。軽さの大半は、Rork 固有の仕組みというより、Expo と React Native の標準的な仕組みで説明がつきます。

  <thead>
    <tr><th>観察されること</th><th>確かめられる要因</th><th>Rork 固有かどうか</th></tr>

    <tr><td>起動が速い</td><td>Hermes によるバイトコード事前コンパイル</td><td>Expo の既定設定です</td></tr>

生成の過程でモデルがどのような最適化をしているかは、外から見えません。私が「軽い」と感じたアプリがあったとしても、それが機械学習の成果なのか、単に依存が少なく素直な構成だったからなのかは、切り分けられていないのです。ここは「分からない」と書くのが誠実だと考えています。

## 軽さの正体は、たいてい「余計なものを入れていない」こと

個人で運用している壁紙アプリを作り直したとき、機能を足すほど起動が重くなり、胃が痛くなる思いをしました。原因を辿ると、使っていない大きな依存パッケージが、起動時に読み込まれていたのです。

生成されたアプリが軽く感じられるときも、同じ構図が働いている可能性があります。依存が最小限で、画面ごとに責務が分かれていて、状態管理も素朴であれば、アプリは自然に軽くなります。

つまり、見るべきなのは「Rork が何をしたか」より「いま手元のプロジェクトに何が入っているか」です。

## 手順 1: バンドルを書き出して中身を見る

まずプロジェクトを書き出し、出力されたファイルの大きさを確認します。

```bash
npx expo export --platform ios
ls -lh dist/_expo/static/js/ios/
```

出力されたバイトコードの大きさが、そのアプリの JavaScript の重さのおおよその目安になります。数値は端末や SDK のバージョンで変わるため、「自分のプロジェクトの基準値」としてメモしておきます。機能を足すたびに同じコマンドを叩けば、増えた分が見えてきます。

依存ごとの内訳を見たいときは、バンドルの可視化ツールを併用すると、どのパッケージが大きいかが分かります。サイズの削減そのものについては、[Rork アプリのバイナリサイズが 150MB を超えた時に切り分ける 5 つの要因と実践的な削減手順](/articles/rork-dev/rork-app-bundle-size-reduction-guide)に手順をまとめています。

## 手順 2: 起動時間を「自分の端末」で測る

起動時間は、シミュレータではなく実機で測ります。同じ操作を 5 回ほど繰り返し、中央値を記録するのが現実的です。

- アプリを完全終了してから起動します（コールドスタート）
- 起動から最初の画面が操作できるようになるまでを計ります
- 低価格帯の端末か、古めの端末でも一度は測ります

画面録画を撮ってコマ送りで確認する方法でも、傾向は十分つかめます。厳密さより、「変更の前後で比べられること」が大切です。起動を短くする具体策は、[Rork で生成したアプリの起動時間を短くする実践テクニック](/articles/rork-dev/rork-app-startup-time-optimization-techniques)で扱っています。

## 手順 3: リストと画像の負荷を見る

画面が重くなる場面は、リストと画像に集中しがちです。

リストは、数百件のデータを流し込んで、スクロール中にコマ落ちがないかを見ます。カクつきが出たら、描画の仕組みを見直す段階です。移行の手順は、[FlatList でカクつき始めたら読む — Rork アプリを FlashList v2 で快適にする実装手順](/articles/rork-dev/rork-flashlist-v2-flatlist-migration-performance)にまとめました。

画像は、表示速度よりもディスクキャッシュの膨らみに注意が要ります。長く使われるアプリほど、端末内の「書類とデータ」が静かに増えていきます。対処は[Rork 製アプリの『書類とデータ』が数 GB に膨らむときの原因と対処](/articles/rork-dev/rork-expo-image-disk-cache-bloat-fix)を参考にしてください。

## 手書きのコードを足したあとに性能を保つ線引き

生成されたアプリに自分でコードを足していくと、あるとき急に重くなることがあります。私が守っている線引きは、次のとおりです。

- 新しい依存を入れる前に、本当に必要かを一度立ち止まって考えます
- 長いリストは、必ず仮想化されたリストコンポーネントで描画します
- 画像は、表示サイズに近い大きさのものを `expo-image` で読み込みます
- 重い処理は、画面の初回表示のあとに回します

どれも特別な技術ではありません。ただ、生成直後の素直な構成を崩さないための、地味な歯止めになります。

## プロンプトで性能の方向性を伝える

Rork に生成を頼むとき、性能について一言添えておくと、方向性が揃いやすくなります。たとえば「古い端末でも動くことを優先してください」「画像は一覧で多く表示します」といった、使われ方の条件です。

ただし、これで最適化が「発動する」と断言できる根拠は、私の手元にはありません。あくまで、条件を明確にしたほうが意図に近い構成が返ってきやすい、という経験則にとどめておきます。結果は、手順 1 から 3 で必ず確かめてください。

## まとめ — 記録と計測は自分で、解釈は慎重に

**生成されたアプリの軽さは、噂ではなく自分の計測値で確かめます**。これが、今回の書き直しで改めて確認した線引きです。

次の一歩としては、いま手元にある Rork 製アプリのバンドルを書き出して、基準値を一つだけ記録してみてください。数値が一つあるだけで、次に機能を足すときの判断が、はるかに落ち着いたものになります。
