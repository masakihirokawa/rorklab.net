リリースしたばかりの Rork アプリをユーザーテストに出したとき、一番よくもらうフィードバックが「起動したあとの数秒が、なんとなく不安」という感想です。処理自体はきちんと動いているのに、真っ白な画面の真ん中でスピナーが回っているだけだと、ユーザーには「止まっているのでは？」「通信がおかしいのでは？」と映ってしまうのです。

この「体感の待ち時間」を和らげる定番のテクニックがスケルトンスクリーンです。実測の読み込み時間は変わりませんが、これから何が出てくるのかを先に見せることで、待たされているという感覚が軽くなる — そんな方向に働いてくれる、地味ですが実用性の高い UI パターンです。数字で証明できる話ではなく、テスターの反応から私が積み上げてきた手触りとして読んでいただければと思います。

扱う範囲を、先にはっきりさせておきます。対象は、Rork で作ったアプリ（React Native / Expo）の「読み込み中」がスピナーだけになっていて、**ちらつかず、レイアウトもずれず、動きを減らす設定の方にも負担をかけないスケルトン**をそのまま組み込みたい方です。最小構成から、Shimmer を1本の時計で動かす形、切り替えのタイミング、症状から引ける切り分け表まで、私が実際に使い分けている順番で並べました。

> 前提（2026年11月時点・公式ドキュメントで確認）: Reanimated 4 系は React Native の New Architecture 専用で、Expo では `npx expo install react-native-reanimated react-native-worklets` で入れます。以下のコードは Reanimated 4 系と `expo-linear-gradient` を前提にしています。

## なぜ ActivityIndicator だけでは足りないのか

Rork が自動生成するコードには、デフォルトで `ActivityIndicator`（いわゆるスピナー）が入っていることが多いです。これは何もないよりは遥かに良いのですが、次のような場面では体感が悪くなります。

- ヒーロー画像が大きい画面（ホームやプロフィール）
- リスト表示で 10 件以上のセルが同時に現れる画面
- タブ切り替えや画面遷移の直後

スピナーは「処理中」以上の情報を伝えません。一方、スケルトンスクリーンは「あとここに画像が出て、ここにタイトルが入るんだな」という**これから現れる情報の予告**を兼ねています。データが届いたときに要素の位置が大きく動かないので、視線が迷いにくいのも利点です。

私は Rork で案件を作るとき、1 秒以上待つ可能性がある画面はスケルトンに置き換えるようにしています。置き換えた版を触ったテスターの方から「軽くなった」という感想が返ってくることが増えたからです。

ただし、すべての待ち時間にスケルトンが向いているわけではありません。ボタンを押した直後の送信中にまでスケルトンを出して、かえって画面が落ち着かなくなったことがありました。いまは次の表を叩き台にして、画面ごとに使い分けています。

<table>
<thead>
<tr><th>場面</th><th>向いている表示</th><th>そう考える理由</th></tr>
</thead>
<tbody>
<tr><td>ホームや一覧の初回表示</td><td>スケルトン</td><td>これから並ぶ要素の位置を予告でき、データ到着時のレイアウトのずれも小さくなります</td></tr>
<tr><td>ボタン押下後の送信・保存</td><td>ボタン内のスピナー</td><td>画面全体の形が変わらないので、予告するものがありません</td></tr>
<tr><td>ほぼ一瞬で終わる取得</td><td>最低表示時間つきのスケルトン、または何も出さない</td><td>一瞬だけ出て消えると、点滅のように見えてしまいます</td></tr>
<tr><td>画像が主役の画面</td><td>サイズを固定した画像プレースホルダー</td><td>画像が後から入っても、周りの文字が押し下げられません</td></tr>
<tr><td>2 回目以降の表示（キャッシュあり）</td><td>古いデータをそのまま出し、裏で更新</td><td>手元にある情報を隠してまで予告を見せる理由がありません</td></tr>

## もっとも小さなスケルトンを書いてみる

最小構成を見てもらうのが早いので、まずは静的なスケルトンから始めます。グレーのブロックを並べるだけです。

```tsx
import { View, StyleSheet, type DimensionValue } from 'react-native';

// プレースホルダーの最小単位（幅は数値でも '70%' でも受け取れる）
export function SkeletonBlock({ width, height, radius = 8 }: {
  width: DimensionValue;
  height: number;
  radius?: number;
}) {
  return (
    <View
      style={[
        styles.block,
        { width, height, borderRadius: radius },
      ]}
    />
  );
}

const styles = StyleSheet.create({
  block: {
    backgroundColor: '#e5e7eb', // Tailwind でいう gray-200 相当
  },
});
```

これを使ってプロフィールカードのスケルトンを組み立てると、次のようになります。読み上げ機能を使う方のために、親ビューに「読み込み中」と伝える属性を付け、中のブロックは読み上げの対象から外しています。

```tsx
import { View, StyleSheet } from 'react-native';
import { SkeletonBlock } from './SkeletonBlock';

export function ProfileSkeleton() {
  return (
    <View
      style={styles.card}
      accessible
      accessibilityLabel="読み込み中"
      accessibilityState={{ busy: true }}
    >
      {/* 中身のブロックは iOS・Android とも読み上げ対象から外す */}
      <View
        style={styles.row}
        accessibilityElementsHidden
        importantForAccessibility="no-hide-descendants"
      >
        <SkeletonBlock width={64} height={64} radius={32} />
        <View style={styles.body}>
          <SkeletonBlock width="70%" height={16} />
          <View style={{ height: 8 }} />
          <SkeletonBlock width="40%" height={12} />
        </View>
      </View>
    </View>
  );
}

const styles = StyleSheet.create({
  card: { padding: 16 },
  row: { flexDirection: 'row', alignItems: 'center' },
  body: { flex: 1, marginLeft: 12 },
});
```

この段階で、真っ白な画面が「コンテンツのレイアウト予告」に変わります。動きがなくても、スピナーよりは確実に伝わる情報が増えます。まずはここまで入れるだけでも、体感は変わります。

## 動きをどう付けるか — 静的・明滅・Shimmer の選び方

静的なスケルトンに物足りなさを感じたら、動きを足します。ここで迷うのが「どの動きにするか」です。私は次の4つを比べたうえで、画面ごとに決めています。

<table>
<thead>
<tr><th>方式</th><th>必要なもの</th><th>向いている場面</th><th>気を付けること</th></tr>
</thead>
<tbody>
<tr><td>静的なブロック</td><td>React Native だけ</td><td>表示が 1 秒未満で終わる画面、動きを減らす設定の方</td><td>長く待つ画面では「固まった」と受け取られることがあります</td></tr>
<tr><td>明滅（Reanimated 4 の CSS アニメーション）</td><td>Reanimated 4 系</td><td>ブロックが多い一覧、コード量を抑えたいとき</td><td>動きの方向がないぶん、読み込みの「進んでいる感」は弱めです</td></tr>
<tr><td>Shimmer（共有の時計 1 本）</td><td>Reanimated＋expo-linear-gradient</td><td>ホームやプロフィールなど、最初に目に入る画面</td><td>ブロックごとに時計を持たせると、古い Android で重くなります</td></tr>
<tr><td>既製のライブラリ</td><td>ライブラリと、その依存</td><td>自分で書く時間が取れないとき</td><td>Reanimated 4 系との組み合わせは、導入前に各ライブラリの対応表で確かめる必要があります（私は網羅的には確認できていません）</td></tr>
</tbody>
</table>

判断の基準を一文にすると、**最初に目に入る画面には Shimmer、件数の多い一覧には明滅、1 秒未満で終わる画面には動きを付けない**、です。動きは「待っていること」を伝えるための道具であって、飾りではないと考えています。

明滅は、Reanimated 4 の CSS アニメーションを使うと数行で書けます。`animationName` にキーフレームを渡すだけです。

```tsx
import Animated, { useReducedMotion } from 'react-native-reanimated';
import { StyleSheet, type DimensionValue } from 'react-native';

// 明滅するスケルトン（Reanimated 4 系の CSS アニメーション）
export function PulseBlock({ width, height, radius = 8 }: {
  width: DimensionValue;
  height: number;
  radius?: number;
}) {
  const reduceMotion = useReducedMotion();
  return (
    <Animated.View
      style={[
        styles.block,
        { width, height, borderRadius: radius },
        !reduceMotion && {
          animationName: { from: { opacity: 1 }, to: { opacity: 0.45 } },
          animationDuration: '900ms',
          animationIterationCount: 'infinite',
          animationDirection: 'alternate',
          animationTimingFunction: 'ease-in-out',
        },
      ]}
    />
  );
}

const styles = StyleSheet.create({
  block: { backgroundColor: '#e5e7eb' },
});
```

動きを減らす設定が有効なら、アニメーションの指定そのものを渡さずに静的なブロックとして描きます。

## Shimmer を「1本の時計」で動かす

ホーム画面のように最初に目に入る場所では、ハイライトが左から右へ流れる Shimmer を使っています。最初に書いた版は、ブロック 1 つずつが自分のアニメーションを持つ作りでした。プロフィールカード程度なら問題ありませんでしたが、一覧のスケルトン 8 行ぶん、合計 24 個のブロックを並べたところで、手元の古めの Android 実機ではハイライトの流れがばらばらにずれて見え、スクロールの手触りも重くなりました。

そこで、時計（0 から 1 へ進む値）を画面に 1 本だけ置き、各ブロックはその値を自分の幅に合わせて読み替える形に変えました。**ブロックは時計を持たず、時計は画面に1本だけ。** 以来、Shimmer の数を気にして削ることはなくなっています。

```tsx
import { createContext, useContext, useEffect, type ReactNode } from 'react';
import { StyleSheet, View, type DimensionValue } from 'react-native';
import Animated, {
  cancelAnimation,
  Easing,
  interpolate,
  useAnimatedStyle,
  useReducedMotion,
  useSharedValue,
  withRepeat,
  withTiming,
  type SharedValue,
} from 'react-native-reanimated';
import { LinearGradient } from 'expo-linear-gradient';

// 画面に 1 本だけ置く時計（0 → 1 を 1.2 秒で繰り返す）
const ShimmerClock = createContext<SharedValue<number> | null>(null);

export function ShimmerProvider({ children }: { children: ReactNode }) {
  const progress = useSharedValue(0);
  const reduceMotion = useReducedMotion(); // 起動時の設定値を返す

  useEffect(() => {
    if (reduceMotion) {
      cancelAnimation(progress);
      progress.value = 0; // ハイライトを左端の外に置いたまま止める
      return;
    }
    progress.value = withRepeat(
      withTiming(1, { duration: 1200, easing: Easing.linear }),
      -1,
      false,
    );
    return () => cancelAnimation(progress);
  }, [reduceMotion]);

  return <ShimmerClock.Provider value={progress}>{children}</ShimmerClock.Provider>;
}

// 時計を読むだけのブロック。幅は数値でも割合でもよい
export function ShimmerBlock({ width, height, radius = 8 }: {
  width: DimensionValue;
  height: number;
  radius?: number;
}) {
  const progress = useContext(ShimmerClock);
  const measured = useSharedValue(0); // 実際の幅（onLayout で測る）

  const style = useAnimatedStyle(() => {
    const w = measured.value;
    const p = progress ? progress.value : 0;
    return {
      // 幅が測れるまで、または時計がないときはハイライトを出さない
      opacity: w > 0 && progress ? 1 : 0,
      transform: [{ translateX: interpolate(p, [0, 1], [-w, w]) }],
    };
  });

  return (
    <View
      onLayout={(e) => {
        measured.value = e.nativeEvent.layout.width;
      }}
      style={[styles.container, { width, height, borderRadius: radius }]}
    >
      <Animated.View style={[StyleSheet.absoluteFill, style]}>
        <LinearGradient
          colors={['transparent', 'rgba(255,255,255,0.6)', 'transparent']}
          start={{ x: 0, y: 0 }}
          end={{ x: 1, y: 0 }}
          style={StyleSheet.absoluteFill}
        />
      </Animated.View>
    </View>
  );
}

const styles = StyleSheet.create({
  container: {
    backgroundColor: '#e5e7eb',
    overflow: 'hidden', // 内側のグラデーションを角丸で切り抜く
  },
});
```

使う側は、スケルトン全体を `ShimmerProvider` で 1 回包むだけです。

```tsx
<ShimmerProvider>
  <ProfileSkeleton />
  <ListSkeleton />
</ShimmerProvider>
```

なぜこう書くのかを補っておきます。ポイントは 4 つです。時計を `useSharedValue` と `withRepeat` で UI スレッドに置くこと、各ブロックは `interpolate` で自分の幅に読み替えるだけにすること、`onLayout` で実際の幅を測るので `'80%'` のような割合指定でもハイライトが端から端まで流れること、そして `overflow: 'hidden'` で角丸の内側にハイライトを閉じ込めること。最後の 1 つを外すと、角の外にハイライトがはみ出してチラついて見えます。

## 「動きを減らす」設定を使っている方への配慮

Shimmer を入れてしばらく経ってから、気づいたことがあります。OS で「視差効果を減らす」や「アニメーションを減らす」を有効にしている方の画面で、スケルトンがどう見えているのかを、私は一度も確かめていなかったのです。動きに敏感な方にとって、画面全体で光が繰り返し流れるのは負担になることがあります。

Reanimated のアニメーションは、既定で `ReduceMotion.System`（端末の設定が有効なら、そのアニメーションを無効にする）になっています。つまり何もしなくても止まる方向には働きます。それでも上のコードで `useReducedMotion` を明示しているのは、止まったときにハイライトがどこに残るかを自分で決めておきたいからです。時計を 0 に戻しておけば、ハイライトは左端の外に隠れ、グレーのブロックだけが残ります。

1 点だけ注意があります。`useReducedMotion` が返すのは**アプリ起動時の設定**で、途中で設定を切り替えても再描画は起きません（公式ドキュメントに明記されています）。設定を変えて確かめるときは、アプリを一度終了してから開き直してください。

Shimmer の色はダークモードでも見直しが要ります。明るい白のハイライトを暗い背景の上で流すと、光というより白い帯に見えてしまいます。

```tsx
import { useColorScheme } from 'react-native';

// ダークモードではベースを暗く、ハイライトを控えめにする
const scheme = useColorScheme();
const base = scheme === 'dark' ? '#2a2a2a' : '#e5e7eb';
const highlight = scheme === 'dark' ? 'rgba(255,255,255,0.08)' : 'rgba(255,255,255,0.6)';
```

## リストのスケルトンは「実際に出す件数」を意識する

一覧画面のスケルトンを作るとき、私が最初の頃によくやっていた失敗が、スケルトンを 3 件しか出さないことでした。画面に 7 件見えるリストで 3 件分しかプレースホルダーを出さないと、**実データに切り替わった瞬間に画面が一気に下に伸びて**、ユーザーの視線が迷子になります。

実装の指針として、以下を意識すると安定します。

- 画面に見える最大件数より少し多めの件数（目安は `画面の高さ / セルの高さ` に 1〜2 件足した数）
- 実データと**厳密に**揃えたセルの高さ
- リストのトップから連続した並びと、本物と同じ間隔

```tsx
import { FlatList, View, useWindowDimensions } from 'react-native';
import { ShimmerBlock } from './ShimmerBlock';

const ROW_HEIGHT = 80; // 実データのセルと同じ値を共有する

export function ListSkeleton() {
  const { height } = useWindowDimensions();
  const count = Math.ceil(height / ROW_HEIGHT) + 1; // 画面に収まる件数 + 1
  return (
    <FlatList
      data={Array.from({ length: count })}
      keyExtractor={(_, i) => `sk-${i}`}
      renderItem={() => (
        <View style={{ height: ROW_HEIGHT, paddingHorizontal: 16, flexDirection: 'row', alignItems: 'center' }}>
          <ShimmerBlock width={48} height={48} radius={24} />
          <View style={{ flex: 1, marginLeft: 12 }}>
            <ShimmerBlock width="80%" height={14} />
            <View style={{ height: 6 }} />
            <ShimmerBlock width="50%" height={12} />
          </View>
        </View>
      )}
      scrollEnabled={false}
    />
  );
}
```

件数を決め打ちにせず画面の高さから求めているのは、小さい端末とタブレットで同じ 8 件を出すと、片方では足りず、片方では余るからです。`ROW_HEIGHT` を実データのセルと同じ定数から読むようにしておけば、デザインを変えたときにスケルトンだけ取り残されることもありません。

`scrollEnabled={false}` にしているのは、読み込み中にスクロールされると、実データが届いた瞬間に位置がずれて見えるからです。私の手元の古めの Android 実機では、この 1 行を入れた版のほうが、切り替え直後の引っかかりが少ない印象でした。

## 切り替えのタイミングで気を付けていること

スケルトンから実データへの切り替えは、油断するとちらつきます。私がよく入れている対策は次の 2 つです。

**1. 最低表示時間を設ける**

読み込みが速すぎる場合にスケルトンが一瞬だけ出てしまうと、逆に「画面が点滅した」ように見えます。最低 200 〜 300 ミリ秒は出す、という下駄を履かせることで、安定感が出ます。

ここで、私が最初に書いた版の失敗をお伝えします。データが届いてから一律 250 ミリ秒待つ作りにしていて、回線が遅いときは、すでに何秒もスケルトンを見せたうえで、さらに 250 ミリ秒を足していたのです。気づいたのは、低速回線で試した夜に「切り替わるのが妙に遅い」と感じたときでした。**最低表示時間は、待たせる時間ではなく、短すぎる表示を引き延ばす時間です。** いまは、スケルトンを出し始めた時刻を覚えておき、足りない分だけ待つ形にしています。

```tsx
import { useEffect, useRef, useState } from 'react';

// スケルトンの表示開始時刻を覚え、最低表示時間に足りない分だけ待つ
export function useMinSkeletonTime(isLoading: boolean, minMs = 250) {
  const startedAt = useRef<number | null>(null);
  const [showSkeleton, setShowSkeleton] = useState(isLoading);

  useEffect(() => {
    if (isLoading) {
      if (startedAt.current === null) startedAt.current = Date.now();
      setShowSkeleton(true);
      return;
    }
    // キャッシュ命中などで一度も読み込み中にならなかった場合は待たない
    const elapsed =
      startedAt.current === null ? minMs : Date.now() - startedAt.current;
    const id = setTimeout(() => {
      startedAt.current = null;
      setShowSkeleton(false);
    }, Math.max(0, minMs - elapsed));
    return () => clearTimeout(id);
  }, [isLoading, minMs]);

  return showSkeleton;
}
```

実際の呼び出しはこんな形です。

```tsx
const { data, isLoading } = useProfile();
const showSkeleton = useMinSkeletonTime(isLoading);

return showSkeleton || !data ? <ProfileSkeleton /> : <Profile data={data} />;
```

期待する動きを並べると、取得が 80 ミリ秒で終わったときはスケルトンが 250 ミリ秒まで引き延ばされ、取得に 3 秒かかったときは 3 秒ちょうどで切り替わります。後者に余計な待ちが足されていなければ、この下駄は正しく働いています。

**2. フェードイン 1 枚分の余裕を入れる**

スケルトンを消して実データを出すとき、150 ミリ秒ほどのフェードインを挟むと、切り替えの境目が柔らかくなります。Reanimated のレイアウトアニメーションを使えば 1 行で足せます。

```tsx
import Animated, { FadeIn } from 'react-native-reanimated';

// 実データ側の外枠にだけ付ける（スケルトン側には付けない）
<Animated.View entering={FadeIn.duration(150)}>
  <Profile data={data} />
</Animated.View>
```

スケルトン側に退場アニメーションまで付けると、ほんの一瞬、両方が重なって見えることがありました。いまは入ってくる側だけに付けています。

## 症状から引く切り分け表

## よくある誤解を3つ

**誤解 1:「スケルトンを入れると読み込みが速くなる」という思い込み。** 速くなるのは体感だけで、実際の取得時間は変わりません。スケルトンを入れたのに「遅い」と言われ続けるなら、見直すべきはキャッシュや取得の回数のほうです。見せ方で隠せる待ち時間には限りがあります。

**誤解 2:「スケルトンには Shimmer が必須」という思い込み。** 動きは必須ではありません。表示が 1 秒未満で終わる画面や、動きを減らす設定の方には、静的なブロックのほうが落ち着いて見えます。私は動きを付けるかどうかを、画面ごとの待ち時間で決めています。

**誤解 3:「Reanimated は動きを減らす設定に自動で従うので、何もしなくてよい」という思い込み。** 既定の `ReduceMotion.System` でアニメーションは無効になりますが、無効になったときのハイライトの位置や、CSS アニメーションでの見え方までは自分で決めておく必要があります。設定を有効にした端末で一度開いて、目で確かめるのがいちばん確実です。

## つまずきやすいポイント

最後に、Rork 案件のレビューで何度も指摘したことがある落とし穴を挙げておきます。

- **画像領域だけスケルトンを忘れる**: テキストはプレースホルダー化したのに、画像プレースホルダーだけ抜けていて、画像が後から「バン」と挿し込まれて画面が揺れるケースです。`Image` の親に `width` / `height` をしっかり固定し、そのサイズでスケルトンを出してください。
- **Shimmer の数を減らして解決しようとする**: 重さの原因はブロックの数より、時計の数にあることがほとんどです。時計を 1 本にまとめれば、数を削らずに済みます。
- **スケルトンにブランドカラーを使う**: 良かれと思ってブランドカラーの薄い色でスケルトンを塗ると、本物のコンテンツと紛らわしくなります。ニュートラルなグレー（ダークモードでは `#2a2a2a` 付近）にとどめたほうが、読みやすさは上です。
- **キャッシュがあるのにスケルトンを出す**: 2 回目以降の表示で、手元にあるデータを隠してまでスケルトンを見せる必要はありません。古いデータを出したまま裏で更新するほうが、待ち時間そのものがなくなります。

## 次に詰まる一歩 — スケルトンが消えないとき

スケルトンを入れた直後に当たりやすいのが、「通信に失敗したのに、スケルトンが出たまま」という状態です。読み込み中の表示を丁寧にしたぶん、ユーザーには止まっていることがかえって分かりにくくなります。私は、一定時間を過ぎたらスケルトンをやめてエラー表示に切り替える小さなフックを、スケルトンと必ずセットで入れるようにしています。

```tsx
import { useEffect, useState } from 'react';

// isLoading が続いたまま limitMs を過ぎたら true を返す
export function useLoadTimeout(isLoading: boolean, limitMs = 10000) {
  const [timedOut, setTimedOut] = useState(false);
  useEffect(() => {
    if (!isLoading) {
      setTimedOut(false);
      return;
    }
    const id = setTimeout(() => setTimedOut(true), limitMs);
    return () => clearTimeout(id);
  }, [isLoading, limitMs]);
  return timedOut;
}
```

`timedOut` が true になったら、スケルトンの代わりに「読み込めませんでした」と再試行ボタンを出します。10 秒という値は私の目安で、扱うデータの重さに合わせて調整してください。

もう 1 つ紛らわしいのが、「読み込み中」なのか「本当に 0 件」なのかが区別できない一覧です。エラーが出ないのに一覧が空のままのときの調べ方は、[一覧が空なのにエラーが出ないとき、直してと頼む前に Rork の Logs パネルを開きます](/articles/rork-basics/rork-list-empty-no-error-ask-for-logs-before-fix-request)にまとめています。音声のように再生が始まるまでの数秒を受け止める場面では、[ストリーミング音声の再生が始まるまでの数秒を、読み込み表示と時間切れで受け止める](/articles/rork-dev/expo-audio-streaming-start-delay-loading-state-timeout-fallback)で同じ考え方を別の形で使っています。読み込みの見せ方を含めた「触った瞬間の印象」全体を整えたい方は、[Rork アプリの『触った瞬間の印象』を決める3つの実装](/articles/rork-dev/rork-first-touch-feel-ui-implementation)もあわせてご覧ください。

## 次にやってみてほしいこと

いきなり全画面を作り替える必要はありません。まずは**起動直後のホーム画面**だけを `ShimmerProvider` で包み、スケルトンに置き換えてみてください。そのうえでテスターの方に、起動後の数秒の感想をもう一度聞いていただければと思います。感想が変わっていれば、一覧画面へ広げる価値があります。変わっていなければ、スケルトンの寸法が実データとずれていないかを先に疑うのが近道です。

読み込みの数秒は、アプリの中でいちばん目立たない場所かもしれません。それでも、そこで不安にさせないことが、最後まで触ってもらえるかどうかを左右するのだと、いまも感じています。
