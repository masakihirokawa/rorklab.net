壁紙アプリの宣伝枠に「TikTok を開く」「X でシェアする」を追加した翌日、レビュアーから「iPhone で押しても何も起きない」という連絡が立て続けに届いたことがあります。シミュレーターでも開発用クライアントでも動いていたので、ストア配布ビルドだけで起きる症状の切り分けに半日かかりました。

原因は拍子抜けするほど単純で、`Info.plist` に `LSApplicationQueriesSchemes` を一行も書いていなかっただけでした。コードを疑い続けた半日は、いま思えば設定ファイルを開くまでの遠回りだったのだと思います。

**「開けるか」を聞く前に、聞いてよい相手を宣言しておきます。** 今回の線引きは、この一文に尽きます。

Rork（Expo の app config を踏襲したプロジェクト）で外部アプリへ飛ばすボタンが iOS だけ動かない方に向けて、原因の特定から再発しない書き方までを一続きでお伝えします。手順や仕様は、2026年11月時点で React Native・Expo・Apple の公式ドキュメントを確認した範囲で書いております。

## 最初に結論を三つだけ

最初にお伝えしたいのは、直すべき場所が三つしかないということです。

1. `app.json` の `ios.infoPlist.LSApplicationQueriesSchemes` に、問い合わせるスキームを宣言すること
2. 宣言はネイティブビルドに焼き込まれるので、ビルドを作り直すこと
3. そもそも `canOpenURL` の結果に頼らず、`openURL` の失敗を受けてウェブへ逃がす書き方にしておくこと

一つ目と二つ目で目の前の不具合は消えます。三つ目は、スキームの名前が変わったときや、OS の方針が変わったときにも行き止まりを作らないための保険です。以下、症状の切り分けから順に辿っていきます。

React Native の公式ドキュメントにも、iOS 9 以降は `LSApplicationQueriesSchemes` を `Info.plist` に書かないと `canOpenURL()` が常に `false` に解決される、と明記されています。Apple がプライバシー保護として導入した制限で、他アプリのインストール状況を探る行為を防ぐためのものです。

## よくある誤解を三つほどいておく

検索で見つかる解説には、半分だけ正しいものが混ざっています。私自身がつまずいたものを三つ、根拠と一緒に書き残します。

**誤解 1: 「`openURL` にも宣言が必要」。** 宣言が必要なのは「開けるかを問い合わせる」`canOpenURL` の側です。Apple のドキュメントでも、宣言の対象は `canOpenURL` による問い合わせとして説明されています。宣言がなくても `openURL` 自体は試せるので、「宣言を忘れたから何も開けない」のではなく、「問い合わせが `false` になって、分岐が誤った側へ流れる」のが実態です。

**誤解 2: 「`app.json` を保存すれば、すぐ反映される」。** `infoPlist` はネイティブの設定なので、JavaScript の更新では届きません。EAS Update のような OTA 配信でも変わらず、ビルドを作り直す必要があります。ここを取り違えると、直したはずの設定が「効かない」ように見えて、正しい修正を疑い始めてしまうのです。

**誤解 3: 「Android は関係ない」。** Android 11（API レベル 30）以降を対象にすると、マニフェストの `<queries>` に書いていないアプリへの問い合わせは結果が得られません。React Native の公式ドキュメントも、Android 11 以降で `canOpenURL` を使う場合は `<queries>` が必要だと記しています。iOS を直した直後に Android で同じ症状が出るのは、このためです。

## 修正 1: app.json に `ios.infoPlist.LSApplicationQueriesSchemes` を追加する

Rork は Expo の app config を踏襲しているので、`Info.plist` を直接いじる必要はありません。プロジェクトルートの `app.json`（または `app.config.ts`）に次のキーを足します。Expo の公式ドキュメント「Linking into other apps」でも、この書き方が案内されています。

```json
{
  "expo": {
    "name": "MyApp",
    "ios": {
      "bundleIdentifier": "com.example.myapp",
      "infoPlist": {
        "LSApplicationQueriesSchemes": [
          "tiktok",
          "twitter",
          "instagram",
          "fb",
          "fb-messenger",
          "youtube",
          "comgooglemaps",
          "spotify",
          "slack"
        ]
      }
    }
  }
}
```

`app.config.ts` を使っている場合は次のようになります。

```ts
import type { ExpoConfig } from "expo/config";

const config: ExpoConfig = {
  name: "MyApp",
  slug: "myapp",
  ios: {
    bundleIdentifier: "com.example.myapp",
    infoPlist: {
      LSApplicationQueriesSchemes: [
        "tiktok",
        "twitter",
        "instagram",
        "fb",
        "fb-messenger",
        "youtube",
        "comgooglemaps",
        "spotify",
        "slack",
      ],
    },
  },
};

export default config;
```

`http` / `https` や `mailto`・`tel`・`sms` のような標準スキームは、私の手元では宣言なしでも開けていました。以前は念のため並べていましたが、いまは「問い合わせるものだけを書く」ほうが、あとから棚卸しするときに迷わないと感じています。後述する件数の上限を考えても、使っていないスキームを残しておく理由はありません。

## 修正 2: 実際の URL Scheme を間違えない

ハマりやすいのが「アプリ名と Scheme 名が一致しない」ケースです。X を開きたいときに `"x"` と書いても期待どおりには動かず、私が確認した範囲では `"twitter"` を使っていました。ただしアプリ側の都合で将来変わる可能性があるため、出荷前に実機で確かめる習慣をおすすめします。LINE の友だち追加は `line://` より、Universal Link（`https://line.me/R/ti/p/...`）のほうが安全です。

## 修正 3: ビルドを作り直し、成果物の中身で確かめる

ここでつまずく方がとても多いので、強調しておきます。`app.json` を編集しただけでは、開発中の Expo Go や既存の Development Build には反映されません。`infoPlist` は **ネイティブビルドに焼き込まれる設定** なので、次のいずれかで作り直す必要があります。

```bash
# 開発用クライアントを作り直す
eas build --profile development --platform ios

# 本番ビルドを作り直す（キャッシュを疑うときは --clear-cache を付ける）
eas build --profile production --platform ios --clear-cache

# ローカルで prebuild して実機へ
npx expo prebuild --clean
npx expo run:ios --device
```

`expo prebuild --clean` は `ios/` ディレクトリを再生成します。独自に追加したファイルがある場合は、事前に差分を退避しておいていただければ安心です。

作り直したら、「宣言が本当に入ったか」をアプリを起動する前に確かめます。私が半日を失ったのは、直したつもりの設定が入っていない古いビルドを触り続けていたからでした。いまは、成果物の `Info.plist` を直接読むところまでを一つの手順にしています。

```bash
# prebuild した場合: 生成された Info.plist を見る（MyApp はプロジェクト名に読み替え）
plutil -p ios/MyApp/Info.plist | grep -A 12 LSApplicationQueriesSchemes

# EAS Build の .ipa をダウンロードした場合: 展開して中の Info.plist を見る（macOS）
mkdir -p /tmp/ipa-check && unzip -oq MyApp.ipa -d /tmp/ipa-check
plutil -p /tmp/ipa-check/Payload/*.app/Info.plist | grep -A 12 LSApplicationQueriesSchemes
```

宣言が入っていれば、次のように配列が表示されます。何も出なければ、そのビルドには宣言がありません。

```text
  "LSApplicationQueriesSchemes" => [
    0 => "tiktok"
    1 => "twitter"
    2 => "instagram"
  ]
```

この確認を挟むと、「設定が悪いのか、ビルドが古いのか」を数十秒で切り分けられます。直し方を疑う前に、まず成果物を疑う——私にはこの順番が合っていました。

## 修正 4: `canOpenURL` に頼らない書き方を持っておく

設定が入っても、コード側に「失敗時にウェブ版へ飛ばす」処理がなければ、スキームが変わった瞬間にまた同じ症状が出ます。React Native の公式ドキュメントによれば、`canOpenURL` は iOS でスキーム未宣言のとき reject されることがあり、`openURL` は開けるアプリがないとき reject されます。

書き方は大きく三つあります。どれを選ぶかで、宣言の要否と、未インストール時の振る舞いが変わります。

<table>
<thead><tr><th>書き方</th><th>iOS の宣言</th><th>未インストールのとき</th><th>向いている場面</th></tr></thead>
<tbody>
<tr><td>`canOpenURL` で分岐してから `openURL`</td><td>必要</td><td>分岐でウェブへ</td><td>ボタンの表示・非表示を事前に切り替えたいとき</td></tr>
<tr><td>`openURL(appUrl)` を試し、失敗したらウェブへ</td><td>不要</td><td>reject を受けてウェブへ</td><td>押されたら開けばよいだけのボタン</td></tr>
<tr><td>最初から `https` のリンクを開く</td><td>不要</td><td>ブラウザで開く</td><td>相手が Universal Link / App Links に対応しているとき</td></tr>
</tbody>
</table>

私は「押されたら開く」だけのボタンなら、二つ目を選びます。問い合わせをしないので宣言に依存せず、失敗はすべてウェブへ逃げるからです。一つ目は、アプリが入っていない人にはボタン自体を見せたくない、という画面設計のときだけに限っています。

```ts
// utils/openExternalApp.ts
import { Linking } from "react-native";

type AppLink = {
  /** ネイティブアプリを開く URL（Scheme または Universal Link） */
  appUrl: string;
  /** 開けなかった場合のウェブフォールバック */
  webUrl: string;
};

export async function openExternalApp({ appUrl, webUrl }: AppLink): Promise<void> {
  try {
    // 問い合わせずに開いてみる。アプリがなければ reject される
    await Linking.openURL(appUrl);
    return;
  } catch (e) {
    if (__DEV__) {
      console.warn("[openExternalApp] fallback to web:", appUrl, e);
    }
  }
  await Linking.openURL(webUrl);
}

// 使い方
// await openExternalApp({
//   appUrl: "tiktok://user?username=example",
//   webUrl: "https://www.tiktok.com/@example",
// });
```

`try/catch` で `openURL` そのものを囲む点が肝です。ただし、このフォールバックは失敗を**隠す**働きもします。開発ビルドでは警告を必ず出し、本番で静かにウェブへ流れ続けることのないよう、確認の機会を残しておくと安心です。

ボタンの表示を切り替えたい一つ目の書き方を選ぶ場合は、起動時に一度だけ調べて結果を保持します。

```ts
// hooks/useInstalledApps.ts
import { useEffect, useState } from "react";
import { Linking } from "react-native";

const CHECKS = { tiktok: "tiktok://", x: "twitter://" } as const;
type Key = keyof typeof CHECKS;

export function useInstalledApps(): Partial<Record<Key, boolean>> {
  const [installed, setInstalled] = useState<Partial<Record<Key, boolean>>>({});
  useEffect(() => {
    let alive = true;
    (async () => {
      const result: Partial<Record<Key, boolean>> = {};
      for (const key of Object.keys(CHECKS) as Key[]) {
        // 未宣言だと reject されることがあるので、失敗は false 扱いにする
        result[key] = await Linking.canOpenURL(CHECKS[key]).catch(() => false);
      }
      if (alive) setInstalled(result);
    })();
    return () => {
      alive = false;
    };
  }, []);
  return installed;
}
```

画面のたびに問い合わせるより、こちらのほうが回数の面でも無駄がありません。ここで調べるスキームは、修正 1 の宣言と必ず一致させます。

## 修正 5: Android 11 以降の `<queries>` を config plugin で足す

Android 側は、`app.json` に `<queries>` を直接書くキーがありません。Expo の config plugin で `AndroidManifest.xml` に追記します。prebuild 後のマニフェストを開いて、既に `https` 用の `<queries>` が入っているかを先に確かめておくと、重複を避けられます。

```js
// plugins/withQueriesSchemes.js
const { withAndroidManifest } = require("expo/config-plugins");

module.exports = function withQueriesSchemes(config, schemes = []) {
  return withAndroidManifest(config, (cfg) => {
    const manifest = cfg.modResults.manifest;
    manifest.queries = manifest.queries ?? [{}];
    const q = manifest.queries[0];
    q.intent = q.intent ?? [];
    for (const scheme of schemes) {
      const exists = q.intent.some((i) =>
        (i.data ?? []).some((d) => d.$?.["android:scheme"] === scheme)
      );
      if (exists) continue;
      q.intent.push({
        action: [{ $: { "android:name": "android.intent.action.VIEW" } }],
        data: [{ $: { "android:scheme": scheme } }],
      });
    }
    return cfg;
  });
};
```

```json
{
  "expo": {
    "plugins": [
      ["./plugins/withQueriesSchemes", ["tiktok", "twitter", "instagram"]]
    ]
  }
}
```

`npx expo prebuild --clean` のあと、`android/app/src/main/AndroidManifest.xml` に `<queries>` と各スキームの `<intent>` が出ていれば反映されています。このプラグインは、ここでは実機での実行まで確認できておりません。お使いの SDK のバージョンによって `modResults` の形が異なる可能性もあるため、出力されたマニフェストを必ず目で確かめていただければと思います。

なお、修正 4 の二つ目の書き方（問い合わせずに開く）なら、Android でも `<queries>` に頼らずに済みます。どちらの OS でも、問い合わせを減らすほど設定の持ち物は軽くなります。

## 回数・件数の上限と、iOS 27 SDK の動き

React Native の公式ドキュメントには、古い iOS 向けにリンクされたアプリが iOS 9 以降で動く場合、`canOpenURL` を呼べるのは **50 回まで** で、超えると以降は常に `false` になり、再インストールやアップグレードでリセットされる、という記述があります。

宣言できる件数についても、Apple の `canOpenURL` のドキュメントには、iOS 15 以降でリンクしたアプリは `LSApplicationQueriesSchemes` の先頭 50 件までしか問い合わせに使えない、という趣旨の記載があります。SDK を次々に組み込んでいると、知らないうちに宣言が膨らむことがあるので、ときどき棚卸しする価値があります。

もう一つ、2026年11月時点で、iOS 27 SDK で `canOpenURL` が非推奨（deprecated）扱いになったという報告が、複数のオープンソースプロジェクトの Issue で上がっています。件数の上限がさらに絞られたという情報も見かけましたが、私は Apple の公式文書で詳細を確認できておりません。ですので、ここでは断定しません。ただ、方向としては「他アプリの有無を問い合わせる」ことが狭まっていく流れにあるのは確かで、修正 4 の「問い合わせずに開き、失敗したらウェブへ」という書き方は、その流れにも逆らわないのだと思います。

## それでも `false` が返るときに疑うこと

ここまでやってもなお `false` が返るときは、次の順に確認します。

1. **ビルドが古い**: ビルド番号と、TestFlight で配信されているものが一致しているか。私は `app.json` を直したのに古いビルドを再提出してしまい、半日を無駄にしたことがあります。修正 3 の `plutil` の確認を挟めば防げます。
2. **EAS のキャッシュ**: `eas build` に `--clear-cache` を付けて再実行します。EAS はクラウド上でビルドするため、手元の Xcode の DerivedData を消しても効きません。
3. **スキームの綴り**: 大文字小文字や `://` の有無を含め、宣言した文字列と呼び出す URL が一致しているかを見直します。宣言には `tiktok` のように `://` を付けずに書きます。
4. **`app.config.ts` が `app.json` を上書きしている**: 両方あるときは、`npx expo config --type introspect` で最終的な設定を表示して、`LSApplicationQueriesSchemes` が残っているかを確かめます。

## フォールバックは、確認を省く理由にしない

修正 4 の書き方には、見落としやすい副作用があります。フォールバックをきれいに書くほど、スキームを綴り間違えていても、利用者には「ウェブが開いた」としか見えなくなるのです。最初の不具合で私が半日迷ったのも、症状が「何も起きない」ではなく「別のものが開く」に近かったからでした。

そこで、出荷前のチェックに「外部アプリのボタンを、そのアプリが入っている実機で一つずつ押し、アプリ側が開くことを見る」を入れております。ウェブが開いたら失敗として扱う——フォールバックは利用者のための安全網であって、私の確認を省く理由にはしない、という線引きです。

## 次に詰まりやすい一歩

外部アプリを開けるようになると、次は「自分のアプリへ、ウェブやほかのアプリから戻ってきてもらう」側で詰まることが多いと思います。Universal Links と遅延ディープリンクの組み立ては[Rork Max でのディープリンク・ユニバーサルリンク実装](/articles/rork-dev/rork-max-deep-linking-universal-links)に、Android で App Links が開かないときの切り分けは[assetlinks.json より先に署名鍵を疑う話](/articles/rork-dev/expo-android-app-links-assetlinks-fingerprint-mismatch-check)にまとめています。

また、修正 5 のような config plugin を増やしていくと、`prebuild --clean` で何が再生成され、何が消えるのかを把握しておく必要が出てきます。その棚卸しの手順は[prebuild --clean で消える手入れを、上げる前に数える](/articles/rork-dev/rork-expo-prebuild-native-drift-inventory-config-plugin)に書き残しています。

## 次にやること

今日のうちに、いちばん新しい本番ビルドの `Info.plist` を `plutil` で表示し、外部アプリへ飛ばしているスキームが `LSApplicationQueriesSchemes` に載っているかを一つずつ照らし合わせていただければと思います。載っていないものが一つでもあれば、iOS のユーザーは気づかないまま、毎回ウェブへ流れているかもしれません。
