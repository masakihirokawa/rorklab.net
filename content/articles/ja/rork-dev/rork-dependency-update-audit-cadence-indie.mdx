しばらく更新していなかったアプリに小さな修正を入れようとして、ビルドが赤いまま通らなくなっていた——個人開発で複数のアプリを App Store と Google Play に出していると、半年に一度はこの場面に出会います。コードは何も変えていないのに、周りの依存パッケージだけが世界の都合で古びていた、というわけです。

Rork が書き出すのは Expo（React Native）のプロジェクトで、その土台は数十のパッケージの上に成り立っています。放っておくと、この土台が静かにズレていきます。気づいたときには、どれを直せば動くのか分からないほど差が開いていることも珍しくありません。

ここで必要なのは、気合いの一括更新ではなく、一人でも続けられる小さなリズムです。更新の頻度を3つに分け、監査をコマンド一発で済ませ、壊れたときに切り分けられる状態を保つ——その具体的な進め方を順に見ていきます。

## なぜ「触っていない」のに壊れるのか

自分のコードを変えていないのに動かなくなるのは、理不尽に感じます。けれど原因ははっきりしています。

ひとつは、依存パッケージが新しいバージョンを出し続けていること。もうひとつは、OS やストアの審査要件が更新され、古いパッケージがその新しい要件に追いつけなくなることです。たとえば Apple が新しいビルド要件を課すと、対応していない古い SDK はそこではじかれます。

つまり、止まっているのは自分のコードのほうで、世界が動いているのです。だからこそ、定期的に少しずつ追従しておくと、ある日の大事故を避けられます。

## 更新は3つの速度に分けて考える

すべてのパッケージを同じ頻度で追う必要はありません。私は次の3つに分けて、別々のリズムで回しています。

<table>
<thead>
<tr><th>分類</th><th>更新頻度の目安</th><th>理由</th></tr>
</thead>
<tbody>
<tr><td>Expo SDK 本体</td><td>年2〜3回(メジャー公開ごと)</td><td>土台なので影響が大きく、まとめて検証したい</td></tr>
<tr><td>通常のライブラリ</td><td>月1回ほど、まとめて</td><td>小さな修正が多く、ためすぎると差が開く</td></tr>
<tr><td>収益・課金系ネイティブSDK</td><td>必要が出たら都度</td><td>AdMob や課金SDKはストア要件に直結する</td></tr>
</tbody>
</table>

いちばん事故が大きいのは Expo SDK 本体の更新なので、これは腰を据えて年2〜3回。通常のライブラリは月に一度まとめて。収益に直結する AdMob のようなネイティブSDKは、ストアの要件変更や不具合報告が出たタイミングで都度上げる、という分け方です。

この3分割の利点は、一度に壊れる範囲が小さくなることです。全部を同時に上げると、壊れたときにどれが原因か分からなくなります。

## 監査はコマンド一発で済ませる

更新の前後で、必ず2つのチェックを通します。脆弱性の有無と、Expo としての互換性です。どちらもコマンド一発で確認できます。

```bash
# 1) 既知の脆弱性を確認する
npm audit

# 2) 本番に影響する深刻度だけに絞る
npm audit --audit-level=high

# 3) Expo プロジェクトの整合性を確認する(バージョンのズレを検出)
npx expo-doctor
```

`npm audit` は全部の警告を出すので、最初は件数に圧倒されます。けれど個人開発で大事なのは、`high` 以上だけです。開発時にしか使わないツールの軽微な警告まで追いかけると、時間がいくらあっても足りません。

`expo-doctor` は、Expo SDK が期待するバージョンと実際のバージョンのズレを教えてくれます。私はこの出力を更新の地図として使っていて、ここで指摘されたパッケージから先に直すようにしています。

## ロックファイルを正として固定する

依存管理でいちばん効くのに見落とされがちなのが、ロックファイル(`package-lock.json`)の扱いです。これは「実際に入っている全パッケージの正確なバージョン表」で、これがあるからこそ、別の日でも同じ状態を再現できます。

```bash
# クリーンに入れ直して、ロックファイルどおりの状態を再現する
rm -rf node_modules
npm ci   # install ではなく ci。ロックファイルに厳密に従う
```

`npm install` は条件次第でバージョンを動かしますが、`npm ci` はロックファイルに厳密に従います。「手元では動くのにビルドだけ失敗する」現象の多くは、ここのズレが原因です。本番ビルドの前には必ず `npm ci` で揃える運用を推奨します。

ロックファイルは必ずコミットに含めます。これを更新のたびに記録しておくと、後で「いつ何を上げたか」をたどれます。

## まとめ更新で壊れたら、1つずつ切り分ける

月一の通常ライブラリ更新は、まとめて上げてからテストするのが効率的です。とはいえ、まとめて上げると、どれかが原因で壊れることもあります。そのときの切り分け手順を決めておくと、慌てません。

1. まず更新前の状態に戻す(コミット前なら `git checkout -- package.json package-lock.json`)
2. 半分だけ更新して、ビルドとアプリ起動を確認する
3. 通れば、残り半分のうちさらに半分を更新する
4. 壊れたまとまりを見つけたら、その中の1つずつに絞り込む

この「半分ずつ試す」進め方なら、20個のパッケージでも数回の試行で原因にたどり着けます。一個ずつ上げるより速く、まとめて上げるより安全な、ちょうど中間のやり方です。

原因のパッケージが見つかったら、無理に最新へ上げず、一つ前の安定版で止めるのも立派な判断です。個人開発では「動いている状態を保つ」ことが最優先で、最新であること自体には価値がありません。

## 更新の記録を1行だけ残す

更新作業は、やった瞬間は覚えていても、半年後には完全に忘れています。私はリポジトリに短いメモを1行だけ残すようにしています。

```text
2026-06-19 Expo SDK 上げず / 通常ライブラリ月次更新 / AdMob SDK は据え置き / npm ci + expo-doctor 通過
```

たった1行ですが、次に開いたときの自分への申し送りになります。「前回は AdMob を据え置いた」と分かれば、今回それを上げるかどうかの判断が早くなります。記録がないと、毎回ゼロから状況を思い出すことになり、それがいちばんの時間泥棒です。

## 次の一歩

まずは今日、手元のアプリで `npx expo-doctor` を一度走らせてみてください。何も指摘がなければ健康ですし、指摘があれば、それが次に直すべき場所の地図になります。

依存管理は派手な作業ではありませんが、生成コードと長く付き合うほど効いてきます。月に30分の更新リズムを持っておくだけで、半年後のビルド赤信号に冷や汗をかく回数が、確実に減っていくと感じています。
