`targetSdkVersion` を 36 に上げたあと、プレビュー画面で端から内側へスワイプしたときの見え方が変わっていました。画面が少し縮んで、後ろが覗く。Android 側の予測型「戻る」のアニメーションです。

そこまでは知っていた変更でした。手が止まったのは、その先です。プレビューから一覧へ戻るつもりの操作が、アプリの終了として扱われる場面がありました。

React Native 側の告知には「`BackHandler` は引き続き動作します」と書かれています。実際、`BackHandler` は動いていました。それでも戻る操作の結果は変わっていました。この二つが同時に成り立つ理由と、もう一つ——Expo の既定ではそもそもこの挙動にならないはずだった理由——が分かったのは、しばらく調べたあとのことでした。

Google Play の対象 API レベル 36 の期限（2026年8月31日、延長申請をした場合は11月1日）はすでに過ぎています。いま更新を出しているアプリは、ほぼすべて targetSdk 36 で動いているはずです。この記事は、その状態で「戻る」の本対応をいつ・どこまでやるかを決めるための整理です（2026年11月時点・Expo SDK 58 の公式ドキュメントで確認）。

## 「BackHandler は動く」と「戻る操作が変わらない」は別の話です

Android 16 を対象にするアプリでは、[予測型「戻る」が既定で有効](https://developer.android.com/about/versions/16/behavior-changes-16#predictive-back)になります。このとき OS 側で起きているのは、次の二つです。

<table>
<tr><th>従来（targetSdk 35 以下）</th><th>targetSdk 36（Android 16 以降の端末）</th></tr>
<tr><td><code>onBackPressed()</code> が呼ばれる</td><td>呼ばれない</td></tr>
<tr><td><code>KeyEvent.KEYCODE_BACK</code> が配送される</td><td>配送されない</td></tr>
</table>

React Native 0.81 では、この変化を吸収して JS 側の `BackHandler` を動かし続けるための修正が入っています。[コミュニティのアナウンス](https://github.com/react-native-community/discussions-and-proposals/discussions/921)には、`onBackPressed` はもう呼ばれないが `BackHandler` は動作を続けるはずで、独自のネイティブ側の戻る処理を持っている場合は `OnBackPressedDispatcher` へ手で移行する必要がある、と書かれています。

ここで私が読み違えていたのが、「`BackHandler` が動く」の射程でした。動くのは、自分で `hardwareBackPress` に登録したハンドラです。ハンドラを登録していない画面——つまりナビゲーションライブラリに戻る操作を任せている画面——の挙動までが保証されているわけではありません。

そして React Navigation 7.x は、予測型「戻る」にまだ対応していません。[公式の導入手順](https://reactnavigation.org/docs/getting-started/)には「システムの戻るジェスチャーを正しく動かすために無効にする必要がある」として、`android:enableOnBackInvokedCallback` を `false` にする手順が載っています。Expo 側でも [スタック内の戻る操作が効かなくなる報告](https://github.com/expo/expo/issues/39092)が上がっており、本対応は `react-native-screens` の新しいネイティブスタックで進められている段階です。

つまり、壊れうるのは自分が書いた `BackHandler` ではなく、書かなかった箇所のほうでした。自分のコードを読み返しても、壊れる理由は見つかりません。

## Expo の既定は、すでに opt-out です

調べ直していて気づいたのは、私が最初に読むべきだったのは Android のドキュメントではなく、Expo の app config のほうだったという点です。

Expo は [SDK 54 のリリースノート](https://expo.dev/changelog/sdk-54)で、予測型「戻る」を全プロジェクトで既定無効にし、`app.json` の `android.predictiveBackGestureEnabled` で有効にできる形にしました。[SDK 58 の app config リファレンス](https://docs.expo.dev/versions/latest/config/app/#predictivebackgestureenabled)でも、この値の既定は `false` のままです。

中身も確かめました。Expo の config plugin（`@expo/config-plugins` の `PredictiveBackGesture`）は、prebuild のたびに `<application>` 要素へ `android:enableOnBackInvokedCallback` を書き込みます。値は `predictiveBackGestureEnabled` が `true` のときだけ `"true"`、それ以外はすべて `"false"` です。`<activity>` 側には触れません。

ここから、次のことが言えます。

- 何も設定していない Expo（CNG）プロジェクトは、targetSdk 36 でも従来の戻る挙動のまま
- 戻る操作が変わったのなら、既定から外れた指定がどこかに残っているということ
- 疑う場所は三つ——`app.json` の `predictiveBackGestureEnabled: true`、手で管理している `android/` の manifest、`<activity>` に残った個別の指定

私の症状も、この三つのどれかに当てはまる側でした。最初に「Android 16 のせいで壊れた」と考えて OS 側の資料から読み始めたのは、遠回りだったのかもしれません。

**OS の変更を読む前に、自分の設定が既定のままかを確かめます。** この順序だけは、次の Android の大きな変更でも崩さないつもりです。

なお SDK 54 のリリースノートには「SDK 55 か 56 で既定を有効にする予定」と書かれていましたが、2026年11月時点の SDK 58 のリファレンスでも既定は `false` です。アップグレードのたびに、この1行の既定値は確かめ直す価値があります。

## opt-out フラグが止めるものと、止めないもの

`android:enableOnBackInvokedCallback="false"` は、[一時的な回避として公式に案内されている](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture#opt-out)フラグです。効き方には、把握しておかないと判断を誤る非対称があります。

<table>
<tr><th>対象</th><th>フラグを false にしたとき</th></tr>
<tr><td>予測型「戻る」のシステムアニメーション</td><td>無効になる</td></tr>
<tr><td><code>OnBackInvokedCallback</code></td><td>無視される</td></tr>
<tr><td><code>OnBackPressedCallback</code>（AndroidX）</td><td>値によらず呼ばれ続ける</td></tr>
<tr><td><code>onBackPressed()</code> の呼び出し（targetSdk 36）</td><td>Android 16 の変更により呼ばれない前提で扱う</td></tr>
</table>

AndroidX の作法で戻るを扱っている部分は、opt-out を入れても入れなくても動きます。フラグで戻せるのは、あくまで OS 側のアニメーションと新しいコールバック経路のほうです。独自のネイティブモジュールで `onBackPressed()` を上書きしている場合は、フラグとは別に `OnBackPressedDispatcher` への移行が要ります。

もう一点。このフラグは `<application>` にも `<activity>` にも書けて、両方にある場合は `<activity>` 側が優先されます。Expo の標準プラグインが書くのは `<application>` だけなので、`<activity>` に過去の検証で `true` が残っていると、その画面だけ予測型「戻る」が有効なままになります。

実機で起きる症状と、その確かめ方を表にしました。上から順に確かめると、無駄な往復が減ります。

1行目と2行目は、どちらも数分で確かめられます。私自身、確かめる作業より「どこから見ればいいか分からない」時間のほうが長くなりがちでした。

## 期限のあとに残る作業と、急がなくてよい作業

期限が過ぎたいま、targetSdk 36 への引き上げは済んでいる前提で考えます。残っている作業を、急ぐ理由の有無で分けると次のようになります。

<table>
<tr><th>作業</th><th>いまの扱い</th><th>理由</th></tr>
<tr><td><code>targetSdkVersion</code> 36 での提出</td><td>済んでいなければ最優先</td><td>未対応のままだと更新を出せない</td></tr>
<tr><td>edge-to-edge のインセット対応</td><td>済んでいなければ最優先</td><td>表示が実際に崩れる</td></tr>
<tr><td>opt-out が既定どおり効いているかの確認</td><td>今週</td><td>数分で済み、戻る操作の事故を防げる</td></tr>
<tr><td>独自モジュールの <code>onBackPressed()</code> の移行</td><td>該当するなら今週</td><td>opt-out では戻らない</td></tr>
<tr><td>予測型「戻る」に沿ったナビゲーションの本対応</td><td>計画に載せる</td><td>ナビゲーションライブラリ側の対応を待つほうが手戻りが少ない</td></tr>
</table>

私はこの切り分けを、リスクの向きで決めています。提出が止まる変更は取り返しがつきません。戻るのアニメーションが従来のままであることによる損失は、それに比べればあとから取り戻せます。

**提出を止める変更は今週に、体験を変える変更は計画に。** 両方を同じ週に詰め込まないことが、結果的にいちばん早く終わる順序でした。

引き上げそのものの手順は別記事にまとめています（[Rork のプロジェクトで targetSdkVersion 36 を通すまでに直した3か所](/articles/app-dev/rork-android-target-api-36-effective-targetsdkversion-audit)）。

## opt-out を置く三つの方法を比べる

opt-out を置く場所は三つあります。どれを選ぶかで、次の prebuild のあとに残るかどうかが変わります。

<table>
<tr><th>方法</th><th>効く範囲</th><th>prebuild のあと</th><th>向いている場面</th></tr>
<tr><td><code>app.json</code> の <code>android.predictiveBackGestureEnabled</code></td><td><code>&lt;application&gt;</code></td><td>毎回書き戻される</td><td>Expo（CNG）のプロジェクト全般</td></tr>
<tr><td>自前の config plugin</td><td>プラグインに書いた範囲（<code>&lt;activity&gt;</code> も可）</td><td>毎回適用される</td><td>activity 側の指定を掃除したいとき</td></tr>
<tr><td>AndroidManifest.xml の手書き</td><td>書いた要素</td><td>SDK 57 以降の既定では消える</td><td>prebuild を使わない素の React Native だけ</td></tr>
</table>

判断基準は一つです。**Expo のプロジェクトなら、application 側は Expo の設定に任せ、自前のプラグインは Expo が触らない activity 側にだけ使います。** 同じ属性を二つのプラグインが書くと、どちらが後に適用されるかを気にし続けることになるためです。

manifest への手書きが消える仕組みと、prebuild の前に洗い出しておくべきネイティブ差分は、別記事に整理しています（[Expo SDK 57 に上げる前に、prebuild で消えるネイティブ変更を洗い出す](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit)）。

## 実機を触る前に、対象を機械で絞る

複数のアプリを抱えていると、全部を実機で1画面ずつ確認するのは現実的ではありません。そこで、`app.json`・manifest の `<application>`・`<activity>` の三か所を突き合わせて、実際に有効になっている値を出す Node のスクリプトを書きました。引数にアプリのルートを並べて実行します。

```javascript
// audit-back.mjs — 戻る処理・app.json・AndroidManifest の指定を、アプリごとに突き合わせる
import { readdirSync, readFileSync, statSync, existsSync } from 'node:fs';
import { join, basename } from 'node:path';

const roots = process.argv.slice(2);

function walk(dir, out = []) {
  if (!existsSync(dir)) return out;
  for (const name of readdirSync(dir)) {
    // 生成物と依存は見ない。android/ は manifest として別に読む
    if (['node_modules', '.git', 'android', 'ios'].includes(name)) continue;
    const p = join(dir, name);
    if (statSync(p).isDirectory()) walk(p, out);
    else if (/\.(ts|tsx|js|jsx)$/.test(name)) out.push(p);
  }
  return out;
}

const readJson = (p) => (existsSync(p) ? JSON.parse(readFileSync(p, 'utf8')) : null);

// application と activity は優先順位が違うので、別々に返す（activity が優先）
function readManifest(path) {
  if (!existsSync(path)) return null;
  const xml = readFileSync(path, 'utf8');
  const pick = (tag) => {
    const m = xml.match(new RegExp(`<${tag}\\b[^>]*>`, 's'));
    const a = m?.[0].match(/android:enableOnBackInvokedCallback\s*=\s*"(true|false)"/);
    return a ? a[1] : null;
  };
  return { application: pick('application'), activity: pick('activity') };
}

for (const root of roots) {
  const pkg = readJson(join(root, 'package.json')) ?? {};
  const deps = { ...pkg.dependencies, ...pkg.devDependencies };
  const nav = Object.keys(deps).some((d) => d.startsWith('@react-navigation/') || d === 'expo-router');
  const backHandler = walk(root).filter((f) => /BackHandler/.test(readFileSync(f, 'utf8'))).length;

  // Expo（CNG）なら app.json の値が prebuild のたびに application へ書き込まれる。未指定は false
  const app = readJson(join(root, 'app.json'));
  const expoValue = app ? String(app.expo?.android?.predictiveBackGestureEnabled === true) : null;
  const mf = readManifest(join(root, 'android/app/src/main/AndroidManifest.xml'));

  let effective, source;
  if (mf) {
    effective = mf.activity ?? mf.application ?? 'unset';
    source = mf.activity ? 'manifest<activity>' : mf.application ? 'manifest<application>' : 'manifest未指定';
  } else if (expoValue !== null) {
    effective = expoValue;
    source = 'app.json（prebuild前）';
  } else {
    effective = 'unknown';
    source = '判定材料なし';
  }

  const enabled = effective === 'true' || effective === 'unset';   // unset は API 36 で既定有効
  const drift = mf && expoValue !== null && mf.application !== expoValue;
  const flag = drift ? 'DRIFT' : enabled && (nav || backHandler > 0) ? 'REVIEW' : 'ok';
  console.log(
    `${flag.padEnd(6)} ${basename(root).padEnd(12)} predictive=${effective.padEnd(5)} ` +
      `(${source})  nav=${nav ? 'yes' : 'no '}  BackHandler=${backHandler}`
  );
}
```

`<activity>` を `<application>` より先に見ているのは、OS の優先順位に合わせるためです。`DRIFT` は「manifest の値と app.json の値が食い違っている」状態で、次の prebuild で manifest 側が書き換わることを意味します。

条件の違う5つのサンプルプロジェクトを作り、Node 22 で通した出力が次のものです。

```text
REVIEW wallpaper-a  predictive=true  (app.json（prebuild前）)  nav=yes  BackHandler=1
ok     wallpaper-b  predictive=false (app.json（prebuild前）)  nav=yes  BackHandler=1
REVIEW wallpaper-c  predictive=true  (manifest<activity>)  nav=yes  BackHandler=0
DRIFT  healing-d    predictive=true  (manifest<application>)  nav=yes  BackHandler=1
REVIEW bare-e       predictive=unset (manifest未指定)  nav=yes  BackHandler=0
```

読み方は次のとおりです。

- **wallpaper-a**: app.json で有効にしたまま。検証で入れた `true` を戻し忘れた形です
- **wallpaper-b**: 何も指定していない Expo の既定。ここは見なくて構いません
- **wallpaper-c**: application は `false` なのに、activity に `true` が残っています。「特定の画面だけおかしい」の正体はこれです
- **healing-d**: manifest に手で `true` を書いたものの、app.json は既定のまま。次の prebuild で `false` に書き戻されます
- **bare-e**: prebuild を使わない素の React Native で、指定なし。API 36 では有効になります

`ok` の行は「見なくてよい」という意味ではなく、「今回の変更で新しく壊れる筋がない」という意味です。`app.config.js` で設定を組み立てている場合、このスクリプトは値を読めません。その場合は `npx expo config --type public` の出力で `android.predictiveBackGestureEnabled` を確かめていただければと思います。

## activity 側の指定だけを消す config plugin

application 側は Expo の設定に任せるので、自前のプラグインがやることは一つだけです。Expo が触らない `<activity>` 側の指定を消します。

```javascript
// plugins/with-back-invoked-activity-cleanup.js
// application 側の値は Expo 標準の android.predictiveBackGestureEnabled に任せ、
// それより優先される activity 側の指定だけを取り除く
const { withAndroidManifest } = require('@expo/config-plugins');

function removeActivityBackInvokedFlags(androidManifest) {
  const app = androidManifest.manifest.application?.[0];
  if (!app) throw new Error('application 要素が見つかりません');

  const removed = [];
  for (const activity of app.activity ?? []) {
    if (activity.$?.['android:enableOnBackInvokedCallback'] !== undefined) {
      removed.push(activity.$['android:name']);
      delete activity.$['android:enableOnBackInvokedCallback'];
    }
  }
  return { androidManifest, removed };
}

module.exports = function withBackInvokedActivityCleanup(config) {
  return withAndroidManifest(config, (config) => {
    const { androidManifest, removed } = removeActivityBackInvokedFlags(config.modResults);
    if (removed.length) console.log(`[back-invoked] activity の指定を削除: ${removed.join(', ')}`);
    config.modResults = androidManifest;
    return config;
  });
};

module.exports.removeActivityBackInvokedFlags = removeActivityBackInvokedFlags;
```

`app.json` には、Expo の設定とプラグインを並べて置きます。`predictiveBackGestureEnabled` は既定が `false` なので省略しても同じですが、意図を残すために明示しています。

```json
{
  "expo": {
    "android": { "predictiveBackGestureEnabled": false },
    "plugins": ["./plugins/with-back-invoked-activity-cleanup"]
  }
}
```

書き換え部分を関数として外に出しているのは、`@expo/config-plugins` を通さずに検証するためです。manifest の JSON 表現を手で組んで呼ぶと、次の結果になります。

```javascript
const manifest = { manifest: { application: [{
  $: { 'android:name': '.MainApplication', 'android:enableOnBackInvokedCallback': 'false' },
  activity: [{ $: { 'android:name': '.MainActivity', 'android:enableOnBackInvokedCallback': 'true' } }],
}] } };

removeActivityBackInvokedFlags(manifest);
// removed    : [".MainActivity"]
// application: {"android:name":".MainApplication","android:enableOnBackInvokedCallback":"false"}
// activity   : {"android:name":".MainActivity"}

// prebuild は何度も走るので、二回目に何も消さないことも確かめておく
removeActivityBackInvokedFlags(manifest);
// removed    : []
```

application 側の値に一切触れていないことが、この出力で分かります。本対応に進むときは、`predictiveBackGestureEnabled` を `true` にするだけで済み、プラグインはそのまま残せます。プラグインとして残しておくと、「いつ・なぜ入れたか」がリポジトリの履歴に残る点も、しばらく後の自分にとって助かります。

## よくある誤解

**「Expo のプロジェクトでも、opt-out は自分で manifest に書く必要がある」**——いいえ。SDK 54 以降は既定で `false` が書き込まれます（[app config リファレンス](https://docs.expo.dev/versions/latest/config/app/#predictivebackgestureenabled)）。自分で書くと、むしろ二重管理になります。

**「opt-out すれば、AndroidX の戻る処理も止まる」**——いいえ。`OnBackPressedCallback` はフラグの値に関係なく呼ばれると、[Android の公式ガイド](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)に明記されています。止まるのはシステムのアニメーションと `OnBackInvokedCallback` のほうです。

**「Expo は SDK 55 か 56 で既定を有効にしたはず」**——SDK 54 の時点ではその予定が書かれていましたが、2026年11月時点の SDK 58 のリファレンスでも既定は `false` です。アップグレードの前に、その版のリファレンスで確かめるのが確実です。

## 実機で見るのは、戻る操作を自分で握っている箇所です

`REVIEW` が付いたアプリでは、次の3か所を見ます。どれも「戻るを自分で握っている」箇所です。

1. **全画面プレビューからの復帰** — 一覧へ戻る動線です。ここが終了になると、体感としていちばん大きく壊れます
2. **モーダルとボトムシート** — 開いた状態での戻るが、シートを閉じるのか画面ごと戻るのかを見ます。表示状態を握っているコンポーネントが複数あると、ここで取り合いが起きます
3. **ルート画面の終了確認** — `hardwareBackPress` で `true` を返して確認を挟んでいる場合、その分岐が通るかを見ます

確認は Expo Go ではなく開発ビルドで行います。Expo Go には自分の app.json の Android 設定が反映されないためです。また、3ボタンナビゲーションとジェスチャーナビゲーションで見え方が変わるので、実機の設定を切り替えて両方を通しています。

戻るまわりの実装そのものでつまずいている場合は、予測型「戻る」以前の話である可能性もあります（[RorkのAndroidアプリで戻るボタンが効かない — BackHandlerの落とし穴と直し方](/articles/rork-dev/rork-android-back-button-not-working-fix)）。従来の挙動で正しく動くことを確かめてから、有効にした状態を見る順序が、切り分けとしては楽です。

## 次に詰まるのは、本対応に進むときです

opt-out は恒久策ではありません。Google も Expo も、将来の Android で外せなくなる可能性を前提に書いています。本対応に進むときに最初に当たるのは、ナビゲーションの土台が予測型「戻る」に対応しているかどうかです。

Expo は [SDK 56](https://expo.dev/changelog/sdk-56) で、`react-native-screens` と組んだ新しいネイティブスタック（Stack v5）の実験的な提供を始め、予測型「戻る」の初期対応を入れています。まだ実験扱いなので、私は本番のアプリでは opt-out を維持し、手元の検証用ブランチでだけ `predictiveBackGestureEnabled: true` と新しいスタックを組み合わせて試すことにしています。

開発ビルドの作り方に不安がある場合は、先にこちらを済ませておくと検証が楽になります（[Rork アプリに Expo Dev Client を導入する手順](/articles/rork-dev/rork-expo-dev-client-native-module-setup-guide)）。

## いま手を動かすなら

まずは `app.json` の `predictiveBackGestureEnabled` と、`android/` があるなら manifest の `enableOnBackInvokedCallback` を、`grep` で1行ずつ確かめるところから始めていただければと思います。

```bash
grep -n "predictiveBackGestureEnabled" app.json
grep -n "enableOnBackInvokedCallback" android/app/src/main/AndroidManifest.xml
```

どちらにも `true` がなく、`<activity>` の行にも属性がなければ、そのアプリの戻る操作は従来のままです。本対応は、ナビゲーションの土台が整ってからで構いません。
