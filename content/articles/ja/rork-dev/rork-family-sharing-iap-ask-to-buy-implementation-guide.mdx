App Store Connect の売上を開くと、前日にあったはずの月額課金が翌日には消えている——子ども向けのサブスクリプションアプリで、Family Sharing が絡むと実際に起こる場面です。

最初に疑うのは単純なキャンセルですが、RevenueCat のようなダッシュボードを開くと「Refunded」で戻された記録が並び、その多くが Family Sharing 経由の購入だった、というのがよくある展開です。

子どもアカウントから購入リクエストが飛び、親が Ask to Buy（承認購入）で一度許可したものの、後から App Store のサポートに連絡して払い戻しを受けるのです。アプリ側はすでに会員権限を付与してコンテンツを提供しているので、気づくのは翌週の集計を見たとき、ということになりがちです。

Family Sharing と Ask to Buy の挙動を理解しないまま StoreKit を組むと、このパターンはほぼ必ずどこかで現れます。Family Sharing が IAP 収益にもたらす4つのトリガーと、Rork で開発したアプリで安全に動かすための実装パターンを、コード例と Apple 公式ドキュメントの記載を軸に整理していきます。私は、課金の設計では「売上が消えるかもしれない経路を先に数える」ことが出発点だと考えています。

## 「子どもが買ったはずなのに翌日消えていた」— Family Sharing の返金が起きる場面

Family Sharing は、購入者と最大5人の家族が、対象のアプリ内課金を共有できる仕組みです。便利な機能ですが、開発者から見ると独特の挙動があります。

- 子どもアカウントの購入でも、請求先は家族の購入者側（多くは親）の支払い方法になります
- 親は購入後でも App Store のサポートに連絡して、身に覚えのない購入として払い戻しを求められます
- Family Sharing が有効な商品は、購入者だけでなく家族全員が利用できます
- 購入者が共有をやめたり、家族グループを抜けたりすると、家族メンバーは共有されていた購入へのアクセスを失います

つまり「いったん成立した売上」も、返金や共有の解除で後からひっくり返る可能性があります。これを前提に IAP を設計しないと、サーバー側でユーザーに付与した会員権限と、Apple 側の購入状態がずれていきます。ずれが蓄積すると、本来は会員ではないユーザーがプレミアム機能を使い続けたり、逆にきちんと払い続けている家族メンバーが急に締め出されたりします。

Sandbox で購入者1ユーザー分だけ確認し、「決済画面が開いて、領収書が返ってきたから OK」と判断してしまうのは、最初に踏みやすい落とし穴です。Apple 公式の「Testing Family Sharing」には、複数の Sandbox Apple Account で作る検証用の家族（Sandbox Test Family）を使う手順があり、家族が共有を受ける場面も、取り消される場面も再現できます。手順は後の節にまとめました。

## Family Sharing で IAP が消える4つのトリガー

「課金が消える」場面は、大きく4つに分けて考えると整理しやすくなります。

第1のトリガーは「Ask to Buy 後の親による返金リクエスト」です。子どもアカウントから購入が要求され、親が一度承認したあと、App Store サポート経由で「子どもが勝手に買ったので返金してほしい」と連絡し、Apple の判断で払い戻しが行われるパターンです。購入者側には `REFUND` が届きます。Apple の通知タイプの対応表では、`REFUND` は購入者にだけ届き、共有を受けていた家族メンバー側には `REVOKE` が届く扱いです。

第2のトリガーは「共有の解除と家族グループからの脱退」です。購入者がその購入の共有をやめたとき、購入者または家族メンバーがグループを抜けたとき、共有されていた購入は家族メンバーから取り消されます。サブスクリプション自体は購入者のもとで続くため `EXPIRED` ではなく、家族メンバー側に `REVOKE` が届きます。Apple の説明では、`REVOKE` は購入者本人には届きません。

第3のトリガーは「Apple の判断による返金」です。ユーザーの申請を受けて Apple が審査し、開発者に事前の確認がないまま払い戻しが確定することがあります。Family Sharing に限った話ではありませんが、子どもの操作による購入が混じる家族向けアプリでは、見込んでおきたい経路です。

第4のトリガーは「親アカウントの請求トラブル」です。親のカードが期限切れや残高不足になると、更新に失敗して請求の再試行期間に入ります。`DID_FAIL_TO_RENEW` は購入者にも家族メンバーにも届き、subtype が `GRACE_PERIOD` なら猶予期間が有効、空なら猶予期間がないことを示します。エンドユーザーからは「家族の誰かのカードが原因で自分の課金が止まった」と見えるので、分かりにくい状況になります。

4つのトリガーと、サーバーが取るべき動きを一枚にまとめると次のようになります。

**売上は「入金された日」ではなく「Apple に取り消されないと確かめられた日」に確定する——設計の出発点は、この線引きにします。**

これら4つを単独で扱うと実装が分散しがちです。Family Sharing に関する状態変更は、すべて Server Notifications V2 で集約して処理する方針にすると、判断の置き場所が一つに定まります。クライアント側の StoreKit 2 はユーザー体験のために使い、収益の信頼できる単一情報源（Single Source of Truth）はサーバー側に置く、という割り切りです。

## App Store Connect で Family Sharing 共有商品を設定する

Family Sharing 対応の IAP を作るには、まず App Store Connect 側で商品の設定を変えておく必要があります。これを忘れていると、「実装は完璧なのに家族で共有されない」という残念な事態が起きます。

App Store Connect の「アプリ内課金」ページで対象の商品を開き、「Family Sharing」セクションをオンにします。対応している商品種別は次のとおりです。

- 自動更新サブスクリプション（Auto-Renewable Subscriptions）
- 非消費型アイテム（Non-Consumable）

逆に「消費型アイテム」（コインやチケットなど）と「非自動更新サブスクリプション」は Family Sharing に対応していません。子ども向けアプリでよくある「家族プラン」を作るなら、自動更新サブスクリプションを Family Sharing 対応で用意するのが基本になります。

注意点として、App Store Connect で商品の Family Sharing をいったん有効にすると、後から無効にできません（App Store Connect ヘルプに明記されています）。サブスクリプション設計の段階で、有効にするかどうかを慎重に決めておく必要があります。一方で、個々の購入者は、サブスクリプションの設定から自分の購入の共有をいつでもオフにできます。前者は商品設計の判断、後者は先ほどの `REVOKE` の発生源になります。

価格設計についても触れておきましょう。Family Sharing 対応の商品は1人分の価格で家族全員が利用できるので、利用者が多い分だけ ARPU（1ユーザーあたり売上）が下がります。たとえば月額500円の商品を Family Sharing 対応にして、1家族で平均2.7人が使うと仮定します（数字は計算を見やすくするための仮定で、実測値ではありません）。1人あたりの実質的な売上は約185円まで下がる計算です。これを織り込んだうえで、価格を上げる、あるいは家族プランとは別にソロプランを用意する、といった調整を最初から選択肢に入れておくと、あとで慌てずに済みます。

設計でぶれないために、「Family Sharing は『家族全体に課金してもらう』戦略であり、『一人あたりの収益最大化』ではない」とメモに書いて貼っておくのがおすすめです。判断軸が定まっていないと、リリース後の売上を見て「単価を上げたいから Family Sharing をやめたい」と思ってしまうのですが、設定上の制約でそれは事実上不可能です。

## StoreKit 2 で Family Sharing イベントを検知する

クライアント側でも、Family Sharing による購入や脱退を検知して UI に反映する必要があります。StoreKit 2 では `Transaction` の `ownershipType` プロパティで、その購入が「自分自身の購入か、家族から共有されたものか」を判定できます。

下記は、購入直後に Family Sharing 由来のトランザクションを判定し、ローカル状態とサーバー検証の両方をトリガーする実装例です。

```swift
import StoreKit

final class PurchaseManager: ObservableObject {
    @Published var isFamilyShared: Bool = false
    @Published var isPremium: Bool = false

    private var updateListenerTask: Task<Void, Error>?

    init() {
        // バックグラウンドで Transaction.updates を購読し、Family Sharing 由来の付与・取り消しを検知する
        updateListenerTask = listenForTransactions()
    }

    deinit {
        updateListenerTask?.cancel()
    }

    /// 期待動作: アプリ起動中に Family Sharing 共有・脱退・返金が発生した瞬間にこのストリームに通知が流れる
    /// 既存購入の検証は `Transaction.currentEntitlements` で別途行う
    private func listenForTransactions() -> Task<Void, Error> {
        Task.detached { [weak self] in
            for await result in Transaction.updates {
                guard let self else { return }
                guard case .verified(let transaction) = result else {
                    // 改ざん疑いのトランザクションは finish せず無視する
                    continue
                }

                await self.handleTransaction(transaction, jws: result.jwsRepresentation)
                await transaction.finish()
            }
        }
    }

    private func handleTransaction(_ transaction: Transaction, jws: String) async {
        let isFromFamily = transaction.ownershipType == .familyShared
        await MainActor.run {
            self.isFamilyShared = isFromFamily
            // revocationDate が入っていれば家族離脱・返金で取り消されたと判定する
            self.isPremium = transaction.revocationDate == nil
        }

        // 署名付きの JWS 文字列（VerificationResult.jwsRepresentation）をサーバーに送り、最終判定はサーバー側に任せる
        do {
            try await PremiumServerClient.shared.verify(jws: jws)
        } catch {
            // ネットワーク失敗時はローカル状態を保ち、次回起動時に再検証する
            print("server verify failed: \(error.localizedDescription)")
        }
    }
}
```

このコードのポイントは3つあります。1つ目は `Transaction.updates` を継続的に購読することで、アプリの起動中に発生した Family Sharing 由来のイベント（共有開始・脱退・返金）をリアルタイムで受け取れることです。2つ目は `ownershipType` を見て家族共有の購入かどうかを区別していることで、これにより UI に「家族プランを利用中」のバッジを出すなどの差別化ができます。3つ目は `revocationDate` をチェックして、家族離脱や返金で取り消されたケースを検出していることです。

もう一つ、サーバーに送るのは `result.jwsRepresentation`（署名付きの JWS 文字列）です。`transaction.jsonRepresentation` は署名のない JSON の `Data` なので、サーバー側の署名検証には使えません。なお、本記事のコードは構成を示す例で、この環境で実行して検証したものではありません。お使いの SDK のバージョンで型定義と挙動を確かめてから組み込んでください。

注意したいのは、この StoreKit 2 ハンドリングだけで会員権限を判定してはいけないという点です。アプリが起動していない間に発生したイベント（例: 親が深夜に返金リクエストを出した）はクライアントには届きません。あくまでも UX を最新に保つためのレイヤーであり、最終的な権限判断はサーバー側で `App Store Server Notifications V2` を待ち受けて行うのが鉄則です。

## Ask to Buy（承認購入）のフローを正しく扱う

子どもアカウントが Family Sharing で購入を試みると、Ask to Buy のフローが起動して購入リクエストが親に送られます。このとき StoreKit から見ると、`Product.purchase()` の戻り値が次のように分岐します。

- `.pending` — 親の承認待ちです。トランザクションはまだ確定していません
- `.success(.verified(transaction))` — 親が承認し、トランザクションが確定しました
- `.userCancelled` — 子どもが UI でキャンセルしました

ここでよくあるミスが、`.pending` を `.success` 同等に扱ってしまうケースです。承認待ちの状態でユーザーに「購入完了！」と表示してしまうと、その後親が拒否した場合に整合性が壊れます。この実装ミスは、権限の二重付与や、拒否された購入のあとも会員のまま残るといった不整合につながります。

正しい実装は次のとおりです。

```swift
func purchase(_ product: Product) async throws -> PurchaseResult {
    let result = try await product.purchase()

    switch result {
    case .pending:
        // 親の承認待ち。UI は「保護者の承認をお待ちしています」状態で待機する
        // 実際の権限付与は Transaction.updates ストリームで承認後に行う
        return .awaitingApproval

    case .success(let verification):
        guard case .verified(let transaction) = verification else {
            // JWS 検証失敗。改ざん可能性があるので付与しない
            throw PurchaseError.unverified
        }
        await transaction.finish()
        return .completed(transaction)

    case .userCancelled:
        return .cancelled

    @unknown default:
        // StoreKit の将来拡張への防御策
        return .unknown
    }
}
```

ポイントは `.pending` の場合に「承認待ち」状態で UI を停止させ、決して権限を付与しないことです。承認後に飛んでくる `Transaction.updates` のイベントで初めてサーバー検証→権限付与のフローを動かします。

UI 側では、`.pending` の状態を「保護者の承認をお待ちしています」と表示し、ユーザーがアプリを閉じても次回起動時に状態を確認できるよう、ローカルに pending な購入リクエストを保存しておくのがおすすめです。たとえば UserDefaults に `pendingPurchaseProductId` を保存し、起動時に `Transaction.currentEntitlements` でステータスを再確認する形にします。

## サーバーサイド検証 — Server Notifications V2 で Family Sharing イベントを処理する

クライアント側だけで状態を管理すると、すでに述べたとおりアプリ未起動中のイベントを取りこぼします。Apple は **App Store Server Notifications V2** を提供しており、サブスクリプションの発生・更新・返金・家族共有の変更などを、すべてサーバー間通信で受け取ることができます。

V2 の通知タイプのうち、Family Sharing 関連で特に重要なものは次のとおりです。

- `SUBSCRIBED` — 初回の購読や再購読です。購入者の購入後に家族メンバーが共有でアクセスを得たときにも、メンバー分が届きます
- `DID_RENEW` — 自動更新が成功しました
- `REFUND` — 返金が確定しました。Apple の対応表では購入者側に届きます
- `REVOKE` — 家族メンバーが共有でのアクセスを失いました（共有の解除、グループからの脱退、購入者の返金）。購入者本人には届きません
- `DID_FAIL_TO_RENEW` — 親の支払い失敗で更新できませんでした。subtype が `GRACE_PERIOD` なら猶予期間が有効です
- `EXPIRED` — サブスクリプションが満了しました

非消費型アイテムを共有している場合、家族メンバーがアクセスを得たときの通知は `ONE_TIME_CHARGE` です。次のコードは自動更新サブスクリプションを対象にしているので、非消費型も扱うなら、このタイプの分岐を足してください。

Cloudflare Workers で V2 通知を受けるエンドポイントの実装例を示します。Rork で作ったアプリの会員サーバーをこの上に載せる前提です。

```typescript
import { jwtVerify, importJWK } from 'jose';

interface Env {
  KV_PREMIUM: KVNamespace;
  APP_STORE_BUNDLE_ID: string;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    if (request.method !== 'POST') {
      return new Response('method not allowed', { status: 405 });
    }

    const body = await request.json<{ signedPayload: string }>();
    const payload = await verifyAndDecodeJWS(body.signedPayload);

    // 期待動作: notificationType が REFUND/REVOKE のときは KV から該当ユーザーのプラン権限を即座に取り消す
    const { notificationType, subtype, data } = payload;
    const transactionInfo = await verifyAndDecodeJWS(data.signedTransactionInfo);
    // 猶予期間などの更新情報は signedRenewalInfo 側に入っている
    const renewalInfo = data.signedRenewalInfo ? await verifyAndDecodeJWS(data.signedRenewalInfo) : null;
    const userKey = `user:${transactionInfo.appAccountToken}`;

    switch (notificationType) {
      case 'DID_RENEW':
      case 'SUBSCRIBED':
        await env.KV_PREMIUM.put(userKey, JSON.stringify({
          status: 'active',
          ownershipType: transactionInfo.inAppOwnershipType, // FAMILY_SHARED か PURCHASED か
          expiresAt: transactionInfo.expiresDate,
        }));
        break;

      case 'REFUND':
      case 'REVOKE':
        // Family Sharing 脱退や返金 — 即座に権限を剥奪する
        await env.KV_PREMIUM.put(userKey, JSON.stringify({
          status: 'revoked',
          revokedAt: Date.now(),
          reason: notificationType,
        }));
        await notifyClientToRevalidate(userKey);
        break;

      case 'DID_FAIL_TO_RENEW':
        if (subtype === 'GRACE_PERIOD') {
          // 親の支払い失敗だが猶予期間が有効。権限は維持し、ユーザーに通知だけ送る
          await env.KV_PREMIUM.put(userKey, JSON.stringify({
            status: 'grace_period',
            retryUntil: renewalInfo?.gracePeriodExpiresDate,
          }));
        } else {
          // subtype が空 = 猶予期間なしで請求の再試行期間に入った。提供を止める
          await env.KV_PREMIUM.put(userKey, JSON.stringify({ status: 'billing_retry' }));
        }
        break;

      case 'GRACE_PERIOD_EXPIRED':
        // 猶予期間が終わり、請求の再試行だけが続いている
        await env.KV_PREMIUM.put(userKey, JSON.stringify({ status: 'billing_retry' }));
        break;

      case 'EXPIRED':
        await env.KV_PREMIUM.delete(userKey);
        break;
    }

    return new Response('ok', { status: 200 });
  },
};

async function verifyAndDecodeJWS(jws: string): Promise<any> {
  // ⚠ 説明用の簡略版です。署名を検証せずに中身を読むだけなので、このまま本番には出しません
  // 本番では x5c 証明書チェーンを Apple の Root CA まで検証します
  // （公式の app-store-server-library などを利用します）
  const [, payload] = jws.split('.');
  const json = atob(payload.replace(/-/g, '+').replace(/_/g, '/'));
  return JSON.parse(json);
}

async function notifyClientToRevalidate(userKey: string): Promise<void> {
```

この実装の核心は、`REFUND` と `REVOKE` を受け取った瞬間にサーバー側の権限を即座に取り消すことです。クライアントからの問い合わせは KV を見るので、次回 API リクエストが来た時点でユーザーは無料プランに戻ります。Family Sharing からの脱退の場合は、脱退した本人の権限だけを取り消し、購入者本人や他の家族メンバーの記録には触れない設計にします。署名の検証を省いたまま公開してしまうと、偽の通知で権限を書き換えられてしまうため、ここだけは先送りにしないでください。

実装で間違えやすいのが `appAccountToken` の扱いです。これは購入時にクライアントから StoreKit に渡す UUID で、購入者のアプリ内ユーザーとひもづけるために使います。家族メンバー側の端末で共有された権限に、同じ値が付くとは限りません。そのため `appAccountToken` だけを KV のキーにせず、`originalTransactionId` と自社のユーザー ID の対応表をサーバー側に持ち、通知のたびに両方から引けるようにしておきます。細かい挙動は、お手元の SDK と Apple の公式ドキュメントで確かめてください。

## RevenueCat 経由の場合の挙動と注意点

RevenueCat を使うと上記のサーバー実装の大部分を肩代わりしてくれますが、Family Sharing では次の点を押さえておきましょう。

家族共有で得たエンタイトルメントかどうかは、`customerInfo.entitlements.active[id].ownershipType` で見分けられます（SDK のバージョンで型や値が変わりうるので、手元で確かめてください）。見分けたら画面を分岐させます。たとえば「家族プラン中」のバッジを出し、解約導線は「購入者の方が管理します」という案内に切り替えます。自分が買った覚えのない課金だと受け取られ、低評価レビューにつながるのを避けるためです。

注意点として、Family Sharing 由来のエンタイトルメントでは、`EntitlementInfo.willRenew` が家族メンバー側の実態を正しく表さない場面があります。購入者本人が自動更新を続けるかどうかは、家族メンバーの側からは見えないためです。値は SDK のバージョンで変わりうるので、手元で実際に確かめてください。クライアント側で「自動更新を停止しますか？」のような UI を出すと、Family Sharing メンバーには無効な操作になってしまうので、`ownershipType == .familyShared` の場合は管理 UI を出さないように分岐するのが安全です。

RevenueCat の Webhook で Family Sharing 関連のイベントを受け取る場合は、そのイベントが購入者本人のものか、家族メンバーのものかを、届いた JSON の中身で必ず見分けます。フィールド名は更新されることがあるため、最新の公式ドキュメントとサンプルを見ながら分岐を組んでください。家族由来と判定できたキャンセルは、購入者本人の解約フォームに誘導せず、別の Slack チャネルなどに流しておくと、急に増えたときに気づけます。

RevenueCat を使うか自前で Server Notifications V2 を組むかは、月額収益のレンジで判断するのが現実的です。RevenueCat の固定費が気になり始めたら自前運用への移行を検討する流れについては、[RevenueCat の固定費が気になり始めた人のための、App Store Server Notifications V2 自前運用ガイド](/articles/rork-dev/rork-app-store-server-notifications-v2-self-hosted-subscription) で詳しく書きました。

## よくある実装ミスと落とし穴 — 踏みやすい4つの失敗

ここからは、Family Sharing 対応で踏みやすい落とし穴を4つ挙げます。先に知っておけば、数日のデバッグを節約できる内容です。

1つ目の落とし穴は「`ownershipType` を見ずに、すべての検証成功トランザクションで購入者向けの画面を出してしまう」ケースです。家族メンバーにも「あなたが購入したサブスクリプション」として管理画面が見え、解約を試みて混乱が起きます。`ownershipType == .familyShared` のときはサブスクリプション管理画面を出さず、代わりに「家族プランを利用中です。管理は購入者の方にお願いします」と表示するのが安全です。

2つ目の落とし穴は「家族まわりの分岐を一度も再現せずにリリースしてしまう」ケースです。Sandbox の Apple ID を1つ切り替えるだけの確認では、家族共有や Ask to Buy の分岐を通りません。省いたままにすると、本番で初めて挙動を見ることになり、リリース直後にレビュー欄が荒れます。再現の手順は次の節にまとめました。

3つ目の落とし穴は「`Transaction.updates` を購読するタスクをアプリ起動の最初期に開始していない」ケースです。`onAppear` でストリームを開始すると、画面が表示される前に届いたトランザクションを取りこぼします。`@main` で App 構造体が初期化された直後、もしくは AppDelegate の `application(_:didFinishLaunchingWithOptions:)` の中で開始してください。

4つ目の落とし穴は「`REFUND` 通知を受けてもクライアントに反映されない」ケースです。サーバー側で権限を取り消しても、クライアントが KV を再フェッチしないと、UI 上では会員のままになってしまいます。サーバーが `REFUND` や `REVOKE` を受けたら APNs サイレント Push を送るか、API レスポンスに `ETag` を付けて、クライアントが古いキャッシュを使い続けないように設計します。

4つとも、リリース前にチェックリスト化しておけば防げるものです。Family Sharing は機能としては魅力的ですが、エッジケースを潰す手間が単独のサブスクリプションより増えることは、見積もりに入れておきたいところです。

## 本番の前に、家族まわりの分岐を再現する

実機で家族グループを組んでから確かめる方法は、準備に手間がかかるうえ、毎回同じ状態に戻すのも難しいです。まず Xcode の StoreKit Testing で分岐を一通り再現し、そのあとに Sandbox と TestFlight で署名や通知の実物を確かめる二段構えがおすすめです。

StoreKit Testing では、StoreKit 構成ファイルの商品で Family Sharing 対応の設定をオンにできます。Transaction Manager からは、保留中の購入の承認と拒否、返金、権限の取り消しを手元で発火できます。Ask to Buy を有効にする操作の場所は、Xcode のバージョンによって変わります。最新の公式ドキュメントで確認しながら進めてください。

家族への共有そのものは、Sandbox Test Family で確かめられます。Apple の「Testing Family Sharing」に沿うと、手順は次のとおりです。

1. 2つ以上の Sandbox Apple Account を用意し、App Store Connect で Sandbox Test Family を作ります
2. 購入者側のアカウントで共有対象の商品を購入します
3. 別の家族メンバーのアカウントでアプリを開き、`ownershipType` が `familyShared` のトランザクションが届くことを確かめます
4. 取り消しの確認は、iOS の「設定 > 開発者 > Sandbox Apple Account > 管理 > Family Sharing」でメンバーを選び、「Stop Sharing Purchases」を押します。Apple は、テスト環境ではこれが家族メンバーの脱退に相当すると説明しています
5. そのメンバーでアプリを開くと、`revocationDate` と `revocationReason` を持つ更新トランザクションが届きます。Server Notifications V2 を Sandbox で有効にしていれば、サーバーには `REVOKE` が届きます

App Store Connect で商品のメタデータを変えた場合、Sandbox に反映されるまで最大1時間かかると Apple は注記しています。設定を直した直後に動かなくても、あわてず待ってください。

サーバー側は、App Store Server API の「テスト通知の依頼」で、エンドポイントまで通知が届くかを確かめます。署名検証を実装したあとであれば、検証が通る通知と、わざと壊した通知の両方を流して、後者が弾かれることも見ておくと安心です。

リリース前に通しておく4つの場面は、次のとおりです。

## リリース後にウォッチすべきメトリクス — エンタイトルメントのドリフトを早期発見する

Family Sharing 対応のアプリを公開したあとは、「Apple 側の有効な購読者数」と「自分のサーバーで active になっているユーザー数」の差を、定点で見ておきたいところです。実装が健全なら、2つの数字は近い値で並びます。差が開いていく場合は、どこかの通知ハンドラが落ちているか、`appAccountToken` や `originalTransactionId` の対応表がずれているかのどちらかが疑われます。

Apple 側の数字は、App Store Connect の Sales and Trends にあるサブスクリプションのレポートが手がかりになります（取得方法は公式ドキュメントで確認してください）。自分のサーバー側は、KV 上の active レコード数を数えます。差分を Slack などに流し、許容する幅は自分のアプリの規模に合わせて先に決めておきます。許容幅を決めないまま眺めても、いつ動くべきかが分からないからです。差分の検知が翌月の集計まで遅れると、サポート問い合わせや返金リクエストとして表面化してから動くことになるので、日次の確認が結果的に安く済みます。

次に見たいのは、`ownershipType` 別の `REVOKE` の発生数です。Family Sharing 由来の `REVOKE` は、家族構成が変わる頻度に応じて起きるので、本来は低くゆっくり推移します。急に跳ねたら、クライアント UI のどこかに共有を外してしまう操作を誤って誘発する仕組みが入っていないかを疑います。確認ダイアログに「アクセスがすぐに失効します」と添えるだけで済む場合も多いのですが、推移を描いていなければ問題に気づけません。

3つ目は、`.pending` のまま解決しない購入リクエストの割合です。子どもが購入をリクエストしたまま、親が承認も拒否もしない状態です。この割合が高止まりするなら、Ask to Buy の親への通知導線に摩擦があるサインです。親のデバイスで通知が届いていない、商品の説明文が承認シートに収まりきらず読まれていない、といった原因が考えられます。

最後は `DID_FAIL_TO_RENEW` の発生数です。月末など特定の時期に集中するなら、支払い方法の期限切れが重なっているサインです。アプリ内バナーで「家族プランの支払い方法に問題が発生しています」と伝え、iOS のサブスクリプション管理画面へディープリンクを張れば、理由の分からない低評価レビューを減らせます。

ダッシュボードを作る手間は、Server Notifications V2 をすでに実装していれば小さく済みます。KV と売上レポートの数字を突き合わせて差分を出すスクリプトを書けば、最初の形になります。

## 本番リリース前のチェックリスト

ここまでの内容を踏まえて、本番リリース前に確認するポイントを整理します。

- App Store Connect の対象商品で Family Sharing が **有効化されている** ことの確認（有効化後は無効にできません）
- 商品種別が「自動更新サブスクリプション」または「非消費型アイテム」であることの確認（消費型・非自動更新は非対応）
- StoreKit 2 のクライアント側で、`Transaction.updates` をアプリ起動直後から購読していること
- `ownershipType == .familyShared` のときに、解約フォームや支払い管理 UI を表示しない分岐が入っていること
- `Product.purchase()` の `.pending` 状態を、購入完了として扱わず「承認待ち」UI で待機させていること
- サーバー側で `App Store Server Notifications V2` を受信し、`REFUND` と `REVOKE` を受け取った時点で権限を取り消していること
- `DID_FAIL_TO_RENEW` は subtype が `GRACE_PERIOD` かどうかで、権限を保つか止めるかを分けていること
- クライアントが `REFUND` や `REVOKE` の後に古いキャッシュを使い続けないよう、APNs サイレント Push か `ETag` で再検証する仕組みが入っていること
- StoreKit Testing と Sandbox Test Family で、前述の4場面（正常承認・拒否・共有解除・返金）を通していること
- Server Notifications V2 のエンドポイントを、Sandbox と本番で別々に設定していること
- 子どもアカウントから購入された場合の、保護者向けレシート・領収メールが正しい言語で送られる設定になっていること

リリース前の定例作業に組み込み、機能を足すたびに同じ項目を通し直すと、取りこぼしに気づきやすくなります。

StoreKit 2 のトランザクション検証をサーバーでどう行うかを掘り下げたい場合は、[StoreKit 2 の署名付きトランザクションを Cloudflare Worker で検証する](/articles/rork-dev/rork-storekit2-jws-transaction-verification-cloudflare-worker) が参考になります。RevenueCat を使う場合のアクセス判定の組み方は、[Rork のサブスクを RevenueCat の Entitlement で組む](/articles/rork-dev/rork-revenuecat-entitlements-paywall-build-notes) で押さえられます。

## 次の一歩

まずは手元のアプリの App Store Connect 設定を開き、現在販売中のサブスクリプションが Family Sharing 対応になっているかを確認してみてください。もし対応していて、`ownershipType` を見ずに権限付与している実装が混じっているなら、今日のうちに `.familyShared` の分岐を入れるだけでも、家族メンバーに対する解約事故とサポート問い合わせを減らせます。リリース後に気づいて修正するより、今のうちに整えておく方が明確に楽です。

**家族の誰かが抜けたとき、抜けた人の権限だけが静かに消える——その一点を、サーバーで守り切る設計にします。**
