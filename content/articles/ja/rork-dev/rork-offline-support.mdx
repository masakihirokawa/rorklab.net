## 圏外でも落ちないアプリにするために

オフライン対応でいちばん怖いのは、電波が切れた瞬間にアプリが固まったり、ユーザーが入力したデータが消えたりすることです。地下鉄に乗った瞬間や、電波の弱い建物に入ったときに「保存に失敗しました」とだけ出て、書いた内容が戻らない——この体験を一度でもさせると、ユーザーは静かに離れていきます。

Rork Max で生成されるアプリは React Native ベースなので、ネイティブのストレージがそのまま使えます。ここでは「小さな状態の保存」「構造化データのローカル DB」「圏外で書いた変更の同期」の三段階に分けて、実際に動くところまで作っていきます。

## AsyncStorage — 設定や小さな状態の保存に

テーマや言語、最後に開いたタブといった軽い状態には `AsyncStorage` がちょうど良い選択肢です。Rork Max には次のように頼めます。

```
Rork Max へのプロンプト:
「ユーザーの設定（テーマ・言語）を AsyncStorage で保存・読み込みする
ヘルパー関数を作ってください。読み込み失敗時は null を返してください。」
```

生成されるコードに、私はいつも次の2点を足してもらいます。読み込み時の `JSON.parse` を try/catch で囲むことと、壊れた値を掴んだら黙って捨てて初期値に戻すことです。

```javascript
import AsyncStorage from '@react-native-async-storage/async-storage';

const KEY = 'user_settings';

export async function saveSettings(settings) {
  try {
    await AsyncStorage.setItem(KEY, JSON.stringify(settings));
  } catch (e) {
    console.warn('settings save failed:', e);
  }
}

export async function loadSettings() {
  try {
    const raw = await AsyncStorage.getItem(KEY);
    return raw ? JSON.parse(raw) : null;
  } catch (e) {
    // 過去バージョンの壊れた値を掴んだ場合はリセットして初期値に戻す
    await AsyncStorage.removeItem(KEY);
    return null;
  }
}
```

注意したいのは、AsyncStorage は暗号化されないことと、Android では既定の上限が小さい（端末によっては 6MB 程度）ことです。トークンのような秘匿値や、画像・記事本文のようなまとまったデータをここに詰め込むのは避けてください。後者は次の SQLite の出番です。

## expo-sqlite の新 API に注意 — openDatabase は動かなくなりました

ここが、生成 AI に任せると最もハマる箇所です。多くの記事やモデルがいまだに `SQLite.openDatabase()` を使った WebSQL 風のコードを出しますが、この API は expo-sqlite の新しいバージョン（Expo SDK 51 以降）で削除されました。古いコードのまま `expo install` した最新版で動かすと、`openDatabase is not a function` で起動直後に落ちます。

動かない書き方（古い API）:

```javascript
// ❌ Expo SDK 51 以降では openDatabase が存在しない
const db = SQLite.openDatabase('myapp.db');
db.transaction((tx) => {
  tx.executeSql('SELECT * FROM tasks', [], (_, result) => { /* ... */ });
});
```

現在の書き方（非同期 API）:

```javascript
import * as SQLite from 'expo-sqlite';

let db;

export async function initDatabase() {
  db = await SQLite.openDatabaseAsync('myapp.db');
  await db.execAsync(`
    CREATE TABLE IF NOT EXISTS tasks (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      title TEXT NOT NULL,
      completed INTEGER DEFAULT 0,
      synced INTEGER DEFAULT 0,
      created_at TEXT DEFAULT CURRENT_TIMESTAMP
    );
  `);
}

export async function addTask(title) {
  const result = await db.runAsync(
    'INSERT INTO tasks (title) VALUES (?)',
    title,
  );
  return result.lastInsertRowId;
}

export async function getTasks() {
  return db.getAllAsync('SELECT * FROM tasks ORDER BY created_at DESC');
}
```

Rork Max に依頼するときは、プロンプトに「expo-sqlite は openDatabaseAsync / execAsync / runAsync / getAllAsync を使う最新 API で書いてください」と一言添えると、古い書き方を出されずに済みます。上の `synced` 列は次の同期で使うので、テーブル作成の時点で入れておくのがコツです。

## オフラインで書いた変更を後から同期する

ローカルに保存できても、サーバーと食い違ったままでは半分しか解決していません。圏外で追加したタスクを、オンラインに戻ったタイミングでまとめてサーバーへ送る——この「送信待ち行列（アウトボックス）」を持たせると、体感が一気に安定します。

考え方はシンプルで、書き込みはまずローカル DB に確定させ、`synced = 0` の行だけを後で拾ってサーバーに送り、成功したら `synced = 1` に更新するだけです。ユーザーは送信完了を待つ必要がなく、圏外でも操作がすぐ返ります。

```javascript
import NetInfo from '@react-native-community/netinfo';

// 未同期の行をサーバーへ流し込む
export async function flushPending() {
  const net = await NetInfo.fetch();
  if (!net.isConnected || !net.isInternetReachable) return;

  const pending = await db.getAllAsync(
    'SELECT * FROM tasks WHERE synced = 0',
  );

  for (const task of pending) {
    try {
      await fetch('https://api.example.com/tasks', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ title: task.title }),
      });
      await db.runAsync('UPDATE tasks SET synced = 1 WHERE id = ?', task.id);
    } catch (e) {
      // 1件失敗したらそこで打ち切る。残りは次回の flush で再挑戦
      break;
    }
  }
}
```

ポイントは、途中で1件でも失敗したら `break` でループを止めることです。残りは `synced = 0` のまま残るので、次にオンラインへ戻ったときの `flush` で自然に再送されます。失敗をなかったことにせず、かといってユーザーを待たせもしない、という落としどころです。再送のタイミングは、アプリ復帰時（`AppState` の active）とネットワーク復帰時の2つで呼ぶと取りこぼしが減ります。

## ネットワーク状態の監視と、判定の落とし穴

オフライン時にバナーを出すには `NetInfo` で状態を監視します。ここで意外とつまずくのが、`isConnected`（Wi-Fi に繋がっているか）と `isInternetReachable`（実際にインターネットに到達できるか）が別物だという点です。カフェの Wi-Fi に繋がっていてもログイン画面の先に進めない、いわゆる「繋がっているのに通じない」状態を拾うには、両方を見る必要があります。

```javascript
import NetInfo from '@react-native-community/netinfo';
import { useState, useEffect } from 'react';

export function useNetworkStatus() {
  // 初期値は null。判定が確定するまで「オフライン扱い」にしない
  const [isOnline, setIsOnline] = useState(true);

  useEffect(() => {
    const unsubscribe = NetInfo.addEventListener((state) => {
      const reachable = state.isInternetReachable;
      // reachable が null（判定中）のうちは isConnected を信じる
      setIsOnline(state.isConnected && reachable !== false);
    });
    return unsubscribe;
  }, []);

  return isOnline;
}
```

`isInternetReachable` は起動直後にしばらく `null`（判定中）を返します。これを単純に false 扱いすると、起動した瞬間に一瞬だけオフラインバナーがちらつきます。上のように `reachable !== false` と書くと、判定が確定するまでは余計なバナーを出さずに済みます。

## どこまでローカルに持たせるかの線引き

最後に、現場の判断を一つだけ。私自身は2014年から個人開発でアプリを出し続けていて、いまも壁紙系・癒し系のアプリを AdMob 収益で運用しています。そうしたアプリでは「画像の一覧やお気に入りはローカルに持たせて圏外でも見られるようにし、購入状態や課金情報はサーバーを正とする」という線引きにしています。ローカルを正にするものと、サーバーを正にするものを最初に決めておくと、同期のコードが驚くほど素直になります。

逆に、全部をローカルにキャッシュして両者を双方向に同期しようとすると、競合解決という別の沼にはまります。まずは「ローカル優先で書き、サーバーへ片方向に流す」アウトボックス方式から始めるのが、App Store / Google Play に出すうえでも一番壊れにくい入口だと感じています。

オフライン対応は派手な機能ではありませんが、電波が不安定な日本の通勤環境ではユーザー満足度に直結します。同じようにモバイルアプリを作っている方の参考になれば嬉しいです。
