ビルドが通った夜、私は「あとは提出ボタンを押すだけ」と思い込んでいました。ところが App Store Connect を開くと、スクリーンショットのサイズ、プライバシーの申告、レビュー用のデモアカウントと、埋めるべき欄が次々に出てきます。結局その日は提出まで辿り着けず、翌朝に持ち越しました。コードを書く時間よりも、ストアに出すための支度のほうがはるかに長かったのです。

最初にお伝えしたいのは、公開の作業は「ビルド」よりも「ストア側の準備」に時間がかかる、ということです。Rork で作ったアプリを両ストアに出すまでの順番を、私がつまずいた箇所を添えて書き残します。

## 先に決めておくこと：Rork と Rork Max のどちらで出すか

Rork で生成したアプリは Expo（React Native）が土台になっているため、iOS と Android の両方を同じコードベースから出せます。一方、Rork Max は iOS のネイティブアプリを前提にした経路で、公開の入口も App Store が中心です。私が確認した範囲では、Android にも出したい場合は Expo ベースの経路を選ぶことになります。

どちらが優れているという話ではなく、出したいストアで決まります。

- iOS と Android の両方に出したい：Expo ベース（ここで書く手順）
- iOS だけで十分で、ネイティブの機能を深く使いたい：Rork Max
- 迷うとき：まず Expo ベースで両ストアに出し、必要になった時点でネイティブへ寄せます

Rork Max 側の手順は別の記事で詳しく扱っていますので、ここでは Expo ベースの流れを中心に進めます。

## デベロッパーアカウントは、早めに申し込んでおきます

アカウントの審査は、アプリの完成を待ってくれません。私は一度、アプリが仕上がってから Apple Developer Program に申し込み、承認が来るまでの数日間、何もできずに待ちました。それ以来、開発を始める日に申し込むようにしています。

**Apple Developer Program**は年額 99 ドルで、個人でも法人でも登録できます。法人として登録する場合は D-U-N-S 番号が必要になり、取得に時間がかかります。個人名義で出すと、ストア上の販売元が本名で表示される点にも注意が必要です。

**Google Play Console**は登録料が 25 ドルの一回払いです。ここで一つ、見落としやすい条件があります。個人アカウントを新しく作った場合、製品版（本番）を公開する前に、クローズドテストを一定期間、一定人数のテスターで回すことが求められます。数字は変わることがありますので、申し込み時点の Play Console の案内を必ず確認してください。この要件を知らずにいると、公開予定日の直前に「あと 2 週間かかります」という状況になりかねません。

## app.json を整える

ストアに出すアプリの識別子は、あとから変えにくいものです。最初に確定させておきます。

```json
{
  "expo": {
    "name": "My App",
    "slug": "my-app",
    "version": "1.0.0",
    "icon": "./assets/icon.png",
    "ios": {
      "bundleIdentifier": "com.example.myapp",
      "supportsTablet": true,
      "buildNumber": "1"
    },
    "android": {
      "package": "com.example.myapp",
      "versionCode": 1
    }
  }
}
```

ここで押さえておきたい点は 3 つあります。

- `bundleIdentifier` と `package` は、一度ストアに登録すると変更できません
- `version` はユーザーに見える番号、`buildNumber` と `versionCode` は提出のたびに増やす内部番号です
- タブレット対応の指定は `supportsTablet` です（古いサンプルには別の綴りが残っています）

私は以前、`versionCode` を増やし忘れたまま Play Console にアップロードして、「このバージョンコードはすでに使用されています」と弾かれたことがあります。手作業で増やす運用は、いつか必ず忘れます。EAS の `autoIncrement` を使い、番号の管理はビルド側に任せることにしました。

```json
{
  "cli": { "appVersionSource": "remote" },
  "build": {
    "production": { "autoIncrement": true }
  }
}
```

これは `eas.json` の設定です。**番号は人が数えず、ビルドの仕組みに数えさせます。** 提出のたびに胃が痛くなる種を一つ減らせます。

## EAS でビルドする

署名まわりは、EAS に任せるのがいちばん手間がかかりません。

```bash
eas build --platform ios --profile production
eas build --platform android --profile production
```

初回の iOS ビルドでは、配布証明書とプロビジョニングプロファイルの生成を EAS が案内してくれます。Android では、アップロードキーが生成されて EAS 側に保管されます。Google Play には「Play App Signing」があり、配布用の最終的な署名は Google が管理します。ここで大切なのは、アップロードキーの扱いです。紛失すると更新が出せなくなりますので、`eas credentials` で保管状況を一度確認しておくと安心です。

出力は iOS が `.ipa`、Android が `.aab` です。Play Console に上げられるのは `.aab` のほうで、`.apk` ではありません。

## App Store に提出する

### アプリのレコードを作る

App Store Connect で「新規 App」を作り、バンドル ID は `app.json` の値と完全に一致させます。ここで食い違うと、アップロードしたビルドが紐づきません。

### 提出は `eas submit` が楽です

```bash
eas submit --platform ios --latest
```

アップロードが終わると、App Store Connect 側でビルドの処理が始まります。数分から数十分かかることがありますので、焦らず待ちます。

### 審査前に埋める欄

つまずきやすいのは、コードではなく次の欄です。

- スクリーンショット（必要なサイズは App Store Connect の画面に表示されます。古い記事の値は信用せず、画面の指示に従います）
- App のプライバシー（広告 SDK や解析 SDK を入れているなら、その収集内容も申告の対象です）
- プライバシーポリシーの URL
- ログイン機能があるときのデモアカウントと、審査担当者へのメモ
- 年齢制限のアンケート

私が最初のアプリで却下されたのは、機能の不具合ではなく、**ログインが必要なのにデモアカウントを書いていなかった**ためでした。審査担当者は、あなたのアプリを初めて触る人です。その人が最後まで辿れるだけの手がかりを、メモ欄に置いておきます。

審査の所要時間はおおむね 1〜2 日ほどですが、時期や内容で前後します。

## Google Play に提出する

### 最初の 1 本は、内部テストから始めます

Play Console で「アプリを作成」し、まず内部テストトラックに `.aab` を上げます。本番にいきなり出さないのは、ストアに載る直前の動作を、実際の配信経路で確かめたいからです。署名や権限の問題は、ここで見つかることが多くあります。

```bash
eas submit --platform android --latest
```

### ストア掲載情報の文字数

以前の私のメモには、Android のアプリ名の上限を 50 文字と書いていました。現在は 30 文字です。ストアの仕様は静かに変わりますので、数字を覚えるより、入力欄の表示を信じるほうが安全だと痛感しています。

### データセーフティと対象 API レベル

Play Console には「データセーフティ」という申告欄があり、アプリが集めるデータを正直に書く必要があります。申告と実際の挙動が食い違うと、更新が止まる原因になります。もう一つ、新規アプリや更新には、対象にすべき Android の API レベルが毎年引き上げられていきます。Expo の SDK を古いまま放置していると、ある日突然アップロードが弾かれることがあります。SDK の更新は、機能を増やすためだけでなく、**ストアに出し続けるための維持費**だと考えています。

### 段階的ロールアウト

本番トラックでは、公開割合を指定できます。

1. 最初は 5〜10% 程度で出します
2. 数日間、クラッシュ率とレビューを見ます
3. 問題がなければ 50%、そして 100% へ広げます

不具合を抱えたまま全員に配ってしまうと、評価が下がり、あとから取り戻すのに長い時間がかかります。割合を絞っておけば、止める判断をする余裕が生まれるのです。

## 却下されやすいポイント

両ストアに共通して、私が見てきた却下の理由を書き並べます。

- 起動直後のクラッシュ（実機で確認していない場合に起こります）
- スクリーンショットや説明が、実際の機能と食い違い
- プライバシーポリシーの URL が開けない、あるいは未作成
- ログインが必要なのに、審査用の手がかりの欠落
- 申告していない権限や SDK を使用
- 動かないボタンや、準備中のままの画面が残存

Apple は人の目で見る比率が高く、メモ欄の丁寧さがそのまま結果に響きます。Google は自動チェックが先に走り、ポリシー違反が見つかったときに手動の確認に回る印象です。どちらも、**「審査される人の立場で一度触ってみる」**という確認が、最も効きました。

## 公開してからの運用

ストアに出したあとは、更新のたびに同じ道を通ります。

```bash
# バージョンを上げたら
eas build --platform all --profile production
eas submit --platform all --latest
```

見るのは次の 3 つで十分です。クラッシュ率（Crashlytics などで確認）、レビューの内容、ストアコンソールのダウンロード数。私は、新しいバージョンを出した当日と 3 日後に、必ずこの 3 つを見るようにしています。レビューに書かれた不具合の報告は、次の更新の叩き台になります。

## 最初の 1 本で守りたいこと

ここまでの内容を一文にするなら、こうなります。

**提出前の最後の確認は、ビルドではなく、審査される人の目線で行います。**

まずは、今日のうちに両ストアのデベロッパーアカウントを申し込むところから始めていただければと思います。承認を待つ時間は、アプリを仕上げる時間と重ねられます。私もそこから、ようやく一つずつ出せるようになりました。
