「テスト通知をバックグラウンドで送ると出るのに、アプリを開いている状態だと音もなく消える」——運用中の癒し系アプリで通知の A/B テストを始めた直後、私はこの現象を自分の手で再現してしまいました。最初は送信側のペイロードを疑い、サーバのログを一晩ぶん読み返しましたが、芳しい手がかりはありませんでした。行き当たったのは、iOS はアプリが前面にあるとき、通知を OS 側で自動表示しない仕様だということです。

`expo-notifications` 周りは SDK を上げるたびに表示まわりの API が少しずつ入れ替わるため、新しい SDK に載せ替えるたびに、一度はこの罠を思い出すことになります。落としどころさえ分かれば対応は数十行で済みますので、症状の見分け方から順に書き残します。

この記事の API 名・既定値は、2026年11月時点の `expo-notifications`（58.1 系）の公式ドキュメントと型定義で確かめたものです。古い SDK のプロジェクトでは、名前が一段古い場合があります。

## 最初に、3つの送り方で症状を確かめる

原因を取り違えないために、次の 3 パターンを試します。

- ホーム画面に戻して送信：バナーの表示あり
- アプリを開いたまま送信：表示も音もなし
- 通知センターの確認：受信履歴には記録あり

この組み合わせなら、原因はほぼ「フォアグラウンドハンドラの未設定」か「表示プロパティの指定漏れ」です。サーバ側のペイロードやトークン取得の失敗ではありません。受信履歴にも入っていない場合に限って、APNs の鍵や証明書、FCM の設定、`getExpoPushTokenAsync` に渡しているプロジェクト ID を疑います。

## 原因 1: setNotificationHandler を呼んでいない、または遅い

iOS のフォアグラウンド通知は、アプリ側が「表示してください」と明示しない限り表示されません。`expo-notifications` では、この宣言を `setNotificationHandler` で行う設計になっています。

```ts
// app/_layout.tsx（Expo Router のルート）のモジュール先頭。コンポーネントの外に置く
import * as Notifications from "expo-notifications";

Notifications.setNotificationHandler({
  handleNotification: async () => ({
    shouldShowBanner: true,
    shouldShowList: true,
    shouldPlaySound: true,
    shouldSetBadge: true,
  }),
});
```

呼び出し位置は、ルートレイアウトのモジュール先頭や `registerRootComponent` の直前など、最初のレンダーより前に必ず通る場所が安全です。`useEffect` の中に置くと、コールドスタート直後に届いた通知に間に合わないことがあります。私も最初はコンポーネントの中に置いていて、起動直後の 1 通だけ消える、という再現しにくい形で悩まされました。

もう一つ、見落としやすい制限があります。型定義のコメントには、`handleNotification` は 3 秒以内に behavior を返すこと、間に合わなければ通知はそのまま表示され、`handleError` が呼ばれることが書かれています。つまり、ハンドラの中でサーバに問い合わせてから表示を決めるような書き方は、遅い回線では「出さないはずの通知が出る」かたちで崩れるのです。

```ts
// Before：表示するかをネットワーク越しに決めている（3秒を超えると判断が無視される）
handleNotification: async (n) => {
  const muted = await fetch("https://api.example.com/mute").then((r) => r.json());
  return { shouldShowBanner: !muted.value, shouldShowList: true, shouldPlaySound: false, shouldSetBadge: false };
},

// After：判断に使う値は先に手元へ置き、ハンドラは同期的な読み取りだけにする
let mutedCache = false; // 起動時や設定変更時に更新しておく
Notifications.setNotificationHandler({
  handleNotification: async () => ({
    shouldShowBanner: !mutedCache,
    shouldShowList: true,
    shouldPlaySound: !mutedCache,
    shouldSetBadge: false,
  }),
  handleError: (id, error) => {
    console.warn("[notify] handler error", id, error.message);
  },
});
```

After の形にしているのは、ハンドラが「表示の可否を答えるだけの場所」だからです。判断の材料はハンドラの外で用意し、ハンドラの中ではメモリ上の値を読むだけにしています。

## 原因 2: shouldShowAlert だけで書いている

ネット上のサンプルの多くは、いまも古い API のままです。

```ts
// 旧 API：shouldShowAlert は非推奨。shouldShowBanner / shouldShowList へ移す
handleNotification: async () => ({
  shouldShowAlert: true,
  shouldPlaySound: true,
  shouldSetBadge: true,
}),
```

iOS 14 で通知の表示先がバナー（画面上部）と通知センター（リスト）に分かれたため、`shouldShowAlert` の 1 つでは両方を別々に制御できなくなりました。`expo-notifications` の変更履歴では、0.31.0（2025年4月25日・SDK 53 の世代）で `shouldShowAlert` が非推奨になり、型定義にも「代わりに `shouldShowBanner` と `shouldShowList` を指定する」と注記されています。

<table>
<thead>
<tr><th>キー</th><th>iOS での意味</th><th>前面で通知を見せたいとき</th></tr>
</thead>
<tbody>
<tr><td>shouldShowBanner</td><td>画面上部のバナーとして出す</td><td>true</td></tr>
<tr><td>shouldShowList</td><td>通知センターの一覧に残す</td><td>true（あとで見返せるように）</td></tr>
<tr><td>shouldPlaySound</td><td>音を鳴らす</td><td>用途しだい</td></tr>
<tr><td>shouldSetBadge</td><td>アイコンのバッジを更新する</td><td>用途しだい</td></tr>
<tr><td>shouldShowAlert</td><td>旧 API・非推奨</td><td>新しく書かない</td></tr>
</tbody>
</table>

使い分けの基準を一文にすると、**前面で「いま見せたい」ならバナーとリストの両方を true、「あとで見ればよい」ならリストだけ true** です。古い版のまま動いているように見えても、内部で旧キーが読み替えられているだけの場合がありますので、SDK を上げる前に書き方を揃えておくほうが安全だと感じています。

## 原因 3: 権限が provisional のまま

`requestPermissionsAsync()` を呼ばず、`getPermissionsAsync()` の結果を大まかにしか見ていないケースです。iOS には、通知センターへ控えめに届けるだけの「仮の許可（provisional）」という状態があり、この状態ではバナーとして前面に出ません。公式ドキュメントは、iOS ではルートの `status` ではなく `ios.status` を見るよう案内しています。

```ts
import * as Notifications from "expo-notifications";

async function ensureNotificationPermission() {
  const current = await Notifications.getPermissionsAsync();
  // iOS はルートの status ではなく ios.status で判断する（公式の案内）
  const iosStatus = current.ios?.status;
  if (iosStatus === Notifications.IosAuthorizationStatus.AUTHORIZED) return true;
  if (current.status === "granted" && iosStatus === undefined) return true; // Android

  const requested = await Notifications.requestPermissionsAsync({
    ios: {
      allowAlert: true,
      allowSound: true,
      allowBadge: true,
    },
  });
  return requested.ios?.status === Notifications.IosAuthorizationStatus.AUTHORIZED
    || (requested.status === "granted" && requested.ios === undefined);
}
```

`ios.status` には `NOT_DETERMINED`・`DENIED`・`AUTHORIZED`・`PROVISIONAL`・`EPHEMERAL` の 5 つがあります。前面でバナーを出したいなら、確かめるべきは `AUTHORIZED` かどうかです。仮の許可をあえて使う設計については、[許可を聞かずに通知を届ける — Rork アプリの provisional 認可と、Expo の定番コードが握りつぶすもの](/articles/rork-dev/rork-provisional-notification-authorization-quiet-optin-expo) に別の角度から書いております。

なお、2026年11月23日に、iOS で `getPermissionsAsync` が他のモジュールの非同期処理を待たせる、という報告が expo/expo の Issue #54081 に上がっています（11月24日時点で未解決）。起動直後に権限確認と別の初期化を並べている場合、通知と関係のない処理が遅れて見えることがありますので、起動の順番を疑うときの材料として覚えておくと役に立つかもしれません。

## 原因 4: ペイロードが薄くて描画するものがない

サーバから送るペイロードに `title` も `body` もなければ、ハンドラで `shouldShowBanner: true` を返しても、画面に出すものがありません。Expo Push API で送る場合の最小例です。

```json
{
  "to": "ExponentPushToken[YOUR_TOKEN]",
  "title": "新しい壁紙が追加されました",
  "body": "今日のおすすめ画像を見る",
  "sound": "default",
  "badge": 1
}
```

公式ドキュメントでも、`data` だけで `title`・`body` を持たない通知は「ヘッドレス（バックグラウンド）通知」として扱われ、表示ではなく裏の処理に回る前提で書かれています。表示させたい通知と裏で処理させたい通知は、ペイロードの段階で分けておきます。

古いサンプルでは `_displayInForeground` というフラグを付けた例も見かけますが、これは古い Expo クライアント向けの名残です。`setNotificationHandler` を使う現在の構成では、必要ないと考えています。

## 原因 5: 集中モード（フォーカス）に巻き込まれている

iOS 15 以降の集中モードで、アプリが「許可された App」に入っていないと、通知が表示されないことがあります。自分の端末で「設定 → 集中モード → 各モード → 許可された App」を確認します。複数の集中モードを使い分けている方は、それぞれに登録漏れがないかも見ます。

開発者側で直せる範囲ではありませんが、サポートに同じ問い合わせが届いたとき、利用者の設定を切り分ける最初の質問として役に立ちます。

## カテゴリと通知アクションの登録漏れ

通知に「保存」「開く」などのアクションボタンを付けるため `setNotificationCategoryAsync` を使っているアプリでは、サーバが送る `categoryIdentifier` がアプリ側で未登録だと、表示の挙動が不安定になることがあるかもしれません。再現が間欠的なときは、まずここを疑います。

```ts
await Notifications.setNotificationCategoryAsync("daily_pick", [
  { identifier: "save", buttonTitle: "保存", options: { opensAppToForeground: false } },
  { identifier: "open", buttonTitle: "開く", options: { opensAppToForeground: true } },
]);

// 登録済みのカテゴリを一覧で確かめる
const categories = await Notifications.getNotificationCategoriesAsync();
console.log(categories.map((c) => c.identifier));
```

私のアプリでも、カテゴリを A/B テストで切り替えていた時期にこの種の不具合に出会いました。サーバ側だけで挙動を変えたため、古いビルドの利用者にだけ通知が出ない、という観測しにくい状態になっていたのです。**サーバで増やしたカテゴリは、先にアプリ側で配ってから使います。** この順番だけは崩さないようにしています。

## 切り分け用の最小再現コード

ここまでを 1 つにまとめた最小のコードです。ローカル通知を 3 秒後に発火させるだけなので、サーバを介さずに挙動を確かめられます。

```tsx
import * as Notifications from "expo-notifications";
import { Button, View } from "react-native";

Notifications.setNotificationHandler({
  handleNotification: async () => ({
    shouldShowBanner: true,
    shouldShowList: true,
    shouldPlaySound: true,
    shouldSetBadge: true,
  }),
});

export default function DebugScreen() {
  return (
    <View>
      <Button
        title="3秒後にローカル通知"
        onPress={async () => {
          const perm = await Notifications.requestPermissionsAsync();
          if (perm.status !== "granted") return;
          await Notifications.scheduleNotificationAsync({
            content: { title: "テスト", body: "前面表示の確認", sound: "default" },
            // 現行の版ではトリガーに type の指定が必要
            trigger: {
              type: Notifications.SchedulableTriggerInputTypes.TIME_INTERVAL,
              seconds: 3,
            },
          });
        }}
      />
    </View>
  );
}
```

ボタンを押したあと、アプリを前面に置いたまま 3 秒待ちます。バナーが出れば、ハンドラと権限は正しく、問題はサーバ側のペイロードか配信経路にあります。出なければ、ハンドラ未設定よりも手前の段階——権限の拒否や集中モード——を疑います。

## ログで「ハンドラが呼ばれていない」を確かめる

`setNotificationHandler` は呼んでいるはずなのに直らない、というときは、ハンドラの中に `console.log` を置いて、Xcode のコンソールで観測します。

```ts
Notifications.setNotificationHandler({
  handleNotification: async (notification) => {
    console.log("[notify] foreground", notification.request.content.title);
    return {
      shouldShowBanner: true,
      shouldShowList: true,
      shouldPlaySound: true,
      shouldSetBadge: true,
    };
  },
  handleSuccess: (id) => console.log("[notify] presented", id),
  handleError: (id, error) => console.warn("[notify] error", id, error.message),
});
```

`[notify] foreground` が流れていれば、ハンドラ自体は呼ばれています。原因は表示プロパティの組み合わせか、権限の側にあります。ログが一度も出ない場合は、ハンドラの登録位置が遅すぎるか、`expo-notifications` のインポート漏れを疑います。`[notify] error` に `ERR_NOTIFICATION_TIMEOUT` が出ていれば、原因 1 の 3 秒の制限に当たっています。

## よくある誤解を三つ、ほどいておく

一つ目は「`status` が `granted` なら、前面でもバナーが出るはず」という思い込みです。公式は iOS ではルートの `status` ではなく `ios.status` を見るよう案内しており、バナーまで出したいなら `AUTHORIZED` を確かめる必要があります。

二つ目は「ハンドラは非同期なので、いくら待っても答えを待ってくれる」という誤解です。型定義のとおり、3 秒以内に返らなければ通知はそのまま表示されます。`false` を返すつもりの通知が出てしまう不思議は、たいていこれです。

三つ目は「Android 13 以降は `requestPermissionsAsync` を呼べば許可ダイアログが出る」という理解です。公式ドキュメントには、Android 13 では通知チャンネルが一つ以上作られるまで許可のダイアログが出ないこと、`setNotificationChannelAsync` を `getExpoPushTokenAsync` より前に呼ぶ必要があることが書かれています。

## Android との挙動差もあわせて確認する

Android では、通知チャンネル（`setNotificationChannelAsync`）の `importance` が `HIGH` 未満だと、フォアグラウンドでヘッドアップ通知が出ません。iOS の問題を片付けたあとで「Android でも同じことが起きている」と気づく流れが多いので、運用するなら最低限のチャンネル設定も一緒に入れておきます。

```ts
import { Platform } from "react-native";
import * as Notifications from "expo-notifications";

export async function prepareAndroidChannel() {
  if (Platform.OS !== "android") return;
  // Android 13 以降は、チャンネルを作ってから許可を求める
  await Notifications.setNotificationChannelAsync("default", {
    name: "default",
    importance: Notifications.AndroidImportance.HIGH,
    vibrationPattern: [0, 250, 250, 250],
    lightColor: "#FF231F7C",
    sound: "default",
  });
}
```

チャンネルを作る処理を `await` できる関数にしておくと、許可の要求やトークンの取得より前に終わらせる順番を、呼び出し側で守りやすくなります。

## 次に詰まる一歩：通知をタップしたあとの遷移

前面での表示が直ると、次に当たりやすいのが「タップしても目的の画面に移らない」問題です。公式ドキュメントは、アプリが終了していた状態から通知のタップで起動したとき、iOS では `NotificationResponseReceivedListener` をできるだけ早く——モジュールの先頭で——登録するよう勧めています。あわせて、起動直後の応答は `useLastNotificationResponse` か `getLastNotificationResponse` でも確かめる方法が案内されています。

```ts
import * as Notifications from "expo-notifications";
import { useEffect } from "react";
import { router } from "expo-router";

export function useNotificationRouting() {
  const last = Notifications.useLastNotificationResponse();
  useEffect(() => {
    const url = last?.notification.request.content.data?.url;
    if (typeof url === "string") router.push(url);
  }, [last]);
}
```

この形にしておくと、アプリが終了していた状態からの起動でも、起動済みの状態でも、同じ一か所で遷移先を決められます。終了状態からの起動は実機でしか再現しにくいので、TestFlight の版で一度は確かめておくと安心です。

## 予防策と、私の線引き

- ルートレイアウトのモジュール先頭での `setNotificationHandler` 呼び出し
- iOS 14 以降の表示キー（`shouldShowBanner` / `shouldShowList`）への統一
- ハンドラの中での通信の排除（3 秒の制限）
- 権限取得時の `ios.status` まで含めた確認
- Android はチャンネル作成を許可要求とトークン取得より前に
- 設定画面の奥に置くローカル通知のテストボタン（利用者からの報告の切り分けが速くなります）

リリースビルドだけで再現する通知の不具合に出会ったとき、私はまずこの再現コードを設定画面の奥に仕込んで TestFlight で配り、原因がアプリ側か OS 側かを最初の数時間で切り分けるようにしています。最初のうちはペイロードを疑うことから入りすぎて、サーバのログに手がかりのない夜を何度か過ごしました。端末側を先に潰しておくだけで調べる範囲がずいぶん狭まるのだと気づいたのは、何度かこの罠を踏んだあとでした。

**表示を決めるのはアプリ、届けるのはサーバ。** 通知が出ないときは、この境目のどちら側かを先に決めてから手を動かすようにしています。

まずは手元の `setNotificationHandler` が `shouldShowBanner` と `shouldShowList` で書かれているか、そしてハンドラの中に `await` が入っていないかを確かめるところから始めていただければと思います。
