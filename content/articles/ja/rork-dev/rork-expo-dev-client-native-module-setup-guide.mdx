Rork が書いたコードに `react-native-mmkv` を足して保存したところ、手元の Expo Go でアプリが開かなくなりました。スプラッシュのあとに赤い画面が出て、文言はライブラリやバージョンによって「Native module cannot be null」だったり「Failed to create a new MMKV instance」だったりします。コードを読み返しても間違いが見つからず、Rork の AI に修正を頼んでも直りません。私は最初のうち、同じ依頼の言い回しだけを変えて、AI に三度ほど直しを頼みました。結果は芳しくありませんでした。

原因はコードの外にありました。Expo Go は、あらかじめ組み込まれたネイティブライブラリしか動かせない「お試し用のアプリ」です。アプリ専用のネイティブコードが要るライブラリを入れた時点で、Expo Go の出番は終わります。次に使うのは「開発ビルド」——`expo-dev-client` を入れて、そのアプリ専用に作る開発用のアプリです。

もう一つ、2026年11月時点で前提が変わっています。Rork はいま新しい Expo（React Native）プロジェクトを作らず、新規は Swift（iPhone）・Kotlin（Android）・React（Web）です。この記事は、**以前 Rork で作った Expo プロジェクトを、これからも Expo のまま育てる方**に向けて書いています。手順に入る前に、その前提から確かめます。

## まず前提を確かめる: いまの Rork と Expo プロジェクト

Rork の公式ドキュメント「[What happened to Expo?](https://docs.rork.com/expo)」には、Expo プロジェクトはもう新しく作れないこと、既存のものはビルド・公開・GitHub への書き出しがこれまでどおりできることが書かれています（2026年11月時点・公式で確認）。同じページでは、Swift への移行が強く勧められています。

開発ビルドを自分の手元で作るには、コードを Rork の外に持ち出す必要があります。Rork の「[Code Export](https://docs.rork.com/faq/code-export)」によると、書き出しは有料プランで GitHub 経由のみ、ZIP で直接落とす手段はなく、GitHub との同期は双方向です（2026年11月時点）。手元で `expo-dev-client` を足して push すれば、Rork 側にも反映されます。

## Expo Go と開発ビルドの違い

Expo の公式 FAQ は、Expo Go を「学習や試作のための playground」と位置づけ、決まったネイティブライブラリだけが入っていて、インストールしたあとは中身を変えられない、と説明しています。アプリ名やアイコンを変えたり、新しいネイティブライブラリを足したりするには、自分のアプリとして開発ビルドを作ることになります。

開発ビルドは、公式の言い方を借りると「自分専用の Expo Go」です。中身は本番ビルドに近く、追加したネイティブライブラリも入っています。違いは、JavaScript を開発サーバー（Metro）から読み込めることと、開発者メニューや起動画面（ランチャー）が付いていることです。

一度ビルドして端末に入れてしまえば、JavaScript だけの変更は保存してリロードするだけで反映されます。ビルドし直すのは、ネイティブ側が変わったときだけです。**ビルドは「ネイティブの世代」、リロードは「JavaScript の世代」** ——この二つを分けて考えるだけで、迷う場面がかなり減ります。

## 開発ビルドが必要になりやすいライブラリ

Rork の Expo プロジェクトで足されることが多く、Expo Go では動かないことが多いものです。

- `react-native-mmkv`（高速なローカル保存。v4 からは `react-native-nitro-modules` も必要）
- `react-native-purchases`（RevenueCat のサブスクリプション課金）
- `react-native-vision-camera`（高機能なカメラ）
- `@react-native-firebase/*`（Firebase のネイティブ SDK）
- `react-native-onesignal`（プッシュ通知）

反対に、`expo-image`・`expo-secure-store`・`expo-notifications` のような Expo SDK のライブラリだけで足りているあいだは、Expo Go のまま進められることが多いです。ただし Expo の公式ドキュメントにも、`expo-secure-store` のようなネイティブコードを持つライブラリを足したら開発ビルドを作り直す、と書かれています。「Expo Go で動くか」と「開発ビルドを作り直すか」は別の問いです。

## 3つの作り方を比べる

Expo の「Introduction to development builds」は、開発ビルドの作り方を3つ挙げています（2026年11月時点）。できあがるものは同じで、違うのはどこでコンパイルするかです。

<table>
<thead>
<tr><th>作り方</th><th>コマンド</th><th>必要なもの</th><th>向いている場面</th></tr>
</thead>
<tbody>
<tr><td>手元でビルド</td><td><code>npx expo run:ios</code> / <code>npx expo run:android</code></td><td>Xcode または Android Studio。Expo アカウントは不要</td><td>Mac があり、何度も作り直す時期</td></tr>
<tr><td>Expo Build（クラウド）</td><td><code>eas build --profile development --platform ios</code></td><td>Expo アカウント。手元のネイティブツールは不要</td><td>Mac がない・iOS をまず一度動かしたい</td></tr>
<tr><td>Expo Build を手元で実行</td><td><code>eas build --profile development --platform ios --local</code></td><td>Expo アカウント＋手元のネイティブツール</td><td>署名やプロファイルは Expo に任せつつ、回数を気にせず試したい</td></tr>
</tbody>
</table>

手元でビルドする場合の対応表も公式にあります。macOS は Android・iOS シミュレータ・iPhone 実機のすべて、Windows と Linux は Android だけです。公式によると、有料の Apple Developer アカウントなしで iPhone 実機に開発ビルドを入れられるのは、この「手元でビルド」だけです。`--local` は macOS と Linux が対象で、Windows は WSL で動くことはあっても公式のサポート外とされています。

なお、Expo のサービス名は「EAS Build」から「Expo Build」、「EAS Update」から「Expo Update」へ呼び名が変わりました。公式によると中身は同じで、`eas` コマンドと `eas.json` の名前もそのままです。古い記事のコマンドがそのまま通るのは、このためです。

私の線引きは一文です。**Mac が手元にあるあいだは手元でビルドし、iOS の実機署名が絡む日だけクラウドに任せます。**

## 手順1: 設定を整える（prebuild は必須ではありません）

最初に、`app.json` にビルドに必要な識別子が入っているかを見ます。

```json
{
  "expo": {
    "name": "MyRorkApp",
    "slug": "my-rork-app",
    "ios": {
      "bundleIdentifier": "com.yourcompany.myrorkapp"
    },
    "android": {
      "package": "com.yourcompany.myrorkapp"
    }
  }
}
```

識別子は、自分のドメインを逆に並べた文字列にするのが慣例です。ストアに出したあとは変えられないので、ここで決めておきます。

よくある誤解を一つ書き残します。`npx expo prebuild` は `app.json` から `ios/` と `android/` を作るコマンドですが、Expo Build（クラウド）で作るだけなら、手元で実行する必要はありません。むしろ気をつけたいのは、手元で prebuild した `ios/`・`android/` をリポジトリにコミットしてしまった場合です。そのフォルダが正として扱われ、あとから `app.json` を直してもビルドに出てこなくなります。

私も一度、アイコンを `app.json` で直したのに、何度ビルドしても古いアイコンのまま、という晩を過ごしました。`app.json` ばかり見直していて、リポジトリに `ios/` が残っていると気づいたのは、だいぶ時間が過ぎてからでした。いまは、設定が反映されないときは最初に `git ls-files ios android` を打つようにしています。

```bash
# 手元でネイティブ側の中身を確かめたいとき・手元でビルドするときに実行します
npx expo prebuild --clean
```

`--clean` は既存の `ios/` と `android/` を消して作り直します。ネイティブ側を手で直している場合は、先に退避しておくと安心です。手で直した箇所をどう数えて config plugin に移すかは、[prebuild --clean で消える手入れを数える手順](/articles/rork-dev/rork-expo-prebuild-native-drift-inventory-config-plugin)にまとめています。

## 手順2: expo-dev-client を入れて、ビルドする

```bash
npx expo install expo-dev-client
```

手元でビルドする場合は、そのまま次のどちらかです。端末やシミュレータへのインストールと、開発サーバーの起動まで一度に進みます。実機に入れるときは `--device` を付けます。

```bash
npx expo run:ios
npx expo run:android
```

Expo Build（クラウド）を使う場合は、`eas-cli` でログインし、`eas.json` に開発用のプロファイルを作ります。

```bash
npm install -g eas-cli
eas login
eas build:configure
```

```json
{
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "channel": "development",
      "ios": {
        "simulator": true
      }
    },
    "preview": {
      "distribution": "internal",
      "channel": "preview"
    },
    "production": {
      "channel": "production"
    }
  }
}
```

`developmentClient: true` が開発ビルドの印です。`ios.simulator: true` は iOS シミュレータ向けで、実機に入れたいときは外します。実機向けの iOS ビルドには、Apple Developer アカウントと端末の登録が要ります。`channel` は手順4で使うので、ここで分けておきます。

```bash
eas build --profile development --platform ios
eas build --profile development --platform android
```

クラウドのビルドはキューの混み具合で待ち時間が変わります。ビルドの回数枠はプランごとに違い、変わることもあるので、[Expo の料金ページ](https://expo.dev/pricing)で最新の内容をご確認いただければ幸いです。`--local` を使ったビルドが exit code 0 のまま何も出さずに止まる件は、[ログを黙らせていた設定の記事](/articles/rork-dev/eas-local-build-exit-code-0-quiet-empty-stub-check)に書き残しています。

## 手順3: 開発サーバーを起動する

```bash
npx expo start
```

`expo-dev-client` を入れていれば、`npx expo start` だけで開発ビルド向けに起動します。シミュレータなら `i`（iOS）か `a`（Android）、実機なら QR コードを読み取ります。端末のホーム画面から開発ビルドを開くと起動画面（ランチャー）が出て、同じネットワークの開発サーバーを選べます。

旧版のこの記事では `npx expo start --dev-client` を勧めていました。Expo の現行ドキュメントでは、`--dev-client` は `expo-dev-client` を**使わずに**開発ビルドを作った場合のための指定とされています。付けても害はありませんが、必須ではありません。

## どの変更でビルドし直すか

開発ビルドでいちばん迷うのが、「今回の変更でビルドし直すべきか」です。

<table>
<thead>
<tr><th>変更の内容</th><th>ビルドし直す</th><th>補足</th></tr>
</thead>
<tbody>
<tr><td>画面や処理など、JavaScript・TypeScript だけの変更</td><td>不要</td><td>保存してリロードすれば反映されます</td></tr>
<tr><td>ネイティブライブラリの追加・削除・バージョン更新</td><td>必要</td><td>新しいネイティブコードは、いまのビルドに入っていません</td></tr>
<tr><td>アプリ名・アイコン・権限・URL スキームなど <code>app.json</code> の変更</td><td>必要</td><td>ネイティブ側の設定として焼き込まれます</td></tr>
<tr><td>Expo SDK のバージョンを上げた</td><td>必要</td><td><code>npx expo install --check</code> で依存の整合も確かめます</td></tr>
<tr><td>環境変数や Metro の設定だけ</td><td>多くは不要</td><td>開発サーバーの再起動で足りることがほとんどです</td></tr>
</tbody>
</table>

表で分かっていても、「このライブラリはネイティブコードを持っていたか」を毎回覚えておくのは難しいものです。そこで、ビルドした直後にネイティブコードを持つ依存の一覧を保存し、あとから比べる小さなスクリプトを置いています。

```js
// scripts/native-deps.mjs
// 使い方:
//   node scripts/native-deps.mjs save   … 開発ビルドを作った直後に、ネイティブコードを持つ依存の一覧を保存
//   node scripts/native-deps.mjs check  … いまの依存と比べ、リビルドが要るかを表示（要るときは exit 1）
import { readFileSync, writeFileSync, existsSync, readdirSync } from "node:fs";
import { join } from "node:path";

const SNAPSHOT = ".native-deps.json";
const pkg = JSON.parse(readFileSync("package.json", "utf8"));
const names = Object.keys({ ...pkg.dependencies, ...pkg.devDependencies });

// ネイティブコードを持つ印: ios/・android/・*.podspec・expo-module.config.json のどれか
function hasNative(dir) {
  if (!existsSync(dir)) return false;
  if (["ios", "android", "expo-module.config.json"].some((n) => existsSync(join(dir, n)))) return true;
  return readdirSync(dir).some((f) => f.endsWith(".podspec"));
}

const current = {};
for (const name of names) {
  const dir = join("node_modules", name);
  if (!hasNative(dir)) continue;
  current[name] = JSON.parse(readFileSync(join(dir, "package.json"), "utf8")).version;
}

const mode = process.argv[2];
if (mode === "save") {
  writeFileSync(SNAPSHOT, JSON.stringify(current, null, 2) + "\n");
  console.log(`保存しました: ${Object.keys(current).length} 件 → ${SNAPSHOT}`);
  process.exit(0);
}
if (mode !== "check") { console.error("save か check を指定してください"); process.exit(2); }
if (!existsSync(SNAPSHOT)) { console.error(`${SNAPSHOT} がありません。ビルド直後に save を実行してください`); process.exit(2); }

const saved = JSON.parse(readFileSync(SNAPSHOT, "utf8"));
const lines = [];
for (const [n, v] of Object.entries(current)) {
  if (!(n in saved)) lines.push(`追加  ${n}@${v}`);
  else if (saved[n] !== v) lines.push(`更新  ${n} ${saved[n]} → ${v}`);
}
for (const n of Object.keys(saved)) if (!(n in current)) lines.push(`削除  ${n}`);

if (lines.length === 0) { console.log("ネイティブ依存に変化なし: JavaScript の変更だけならリロードで足ります"); process.exit(0); }
console.log("ネイティブ依存が変わっています。開発ビルドを作り直してください:");
for (const l of lines) console.log("  " + l);
process.exit(1);
```

ビルドの直後に `save`、赤い画面を見たら `check` です。`node_modules` の中に `ios/`・`android/`・`.podspec`・`expo-module.config.json` のどれかがあれば「ネイティブを持つ」とみなしています。Node.js 22 で、`expo-image` だけの状態で保存し、MMKV v4 と Nitro Modules を足してから確かめたときの出力です。

```text
$ node scripts/native-deps.mjs save
保存しました: 1 件 → .native-deps.json
$ node scripts/native-deps.mjs check
ネイティブ依存が変わっています。開発ビルドを作り直してください:
  追加  react-native-mmkv@4.0.0
  追加  react-native-nitro-modules@0.31.0
$ echo $?
1
```

このスクリプトは `app.json` の変更を見ていません。そちらも含めて漏れなく拾いたい場合は、Expo の公式ドキュメントが案内している `runtimeVersion` の `"fingerprint"` ポリシー（ネイティブに影響しうる変更をまとめて検知する仕組み）のほうが確実です。私は、手元で気軽に打てる確認としてこのスクリプトを、更新の配信を守る仕組みとして fingerprint を、と役割を分けています。

## 手順4: Expo Update と組み合わせるときの注意

Expo Update（旧 EAS Update）を使っている場合、開発ビルドと本番ビルドが同じチャンネルを見ていると、開発ビルドが本番向けの古い JavaScript を取りに行き、直したはずの不具合が戻って見えることがあります。手順2の `eas.json` でプロファイルごとに `channel` を分けておけば、この取り違えは起きにくくなります。

もう一つは、ネイティブ側が変わったのに `runtimeVersion` が同じままになっている場合です。Expo のドキュメントによると、`"appVersion"` ポリシーはアプリのバージョンを上げたときだけランタイムバージョンが変わるため、ネイティブライブラリを足したのにバージョンを上げ忘れると、古いビルドに互換性のない更新が届きます。`"fingerprint"` ポリシーはネイティブに影響しうる変更があるたびに自動で変わり、その代わりビルドの回数は増えます。

```json
{
  "expo": {
    "runtimeVersion": {
      "policy": "fingerprint"
    }
  }
}
```

ポリシーごとの違いは、Expo 公式の [Runtime versions のページ](https://docs.expo.dev/eas-update/runtime-versions/)に一覧があります。迷ったときは、ネイティブライブラリを入れ替える時期だけでも fingerprint にしておくと、取り違えの事故は起きにくくなります。

## よくある誤解を3つ

**「Expo Go で動かない＝コードが悪い」**。ネイティブライブラリを足したあとの赤い画面は、多くの場合コードではなく実行環境の問題です。AI にコードを書き直させても、Expo Go に入っていないものは入りません。

**「Rork でまた Expo の新規プロジェクトを作れば試せる」**。2026年11月時点で、Rork は Expo の新規プロジェクトを作りません。試すなら既存の Expo プロジェクトを GitHub に書き出し、手元で開発ビルドを作ることになります。

**「開発ビルドを作れば、あとは何をしても反映される」**。反映されるのは JavaScript の変更だけです。ネイティブライブラリや `app.json` を変えたら、ビルドし直して端末に入れ直すまで、古い世代のままです。

## Rork の外で続けるか、Rork に残すか

開発ビルドを手元で作り始めると、「このまま Xcode や Android Studio で続けてもよいのか」が気になってきます。私の判断は、変更の種類で分けています。

<table>
<thead>
<tr><th>変更の種類</th><th>どこでやるか</th><th>理由</th></tr>
</thead>
<tbody>
<tr><td>画面や文言、ロジックの追加</td><td>Rork のチャット</td><td>AI に任せやすく、GitHub 同期で手元にも戻ってきます</td></tr>
<tr><td>ネイティブライブラリの追加と開発ビルド</td><td>手元</td><td>ビルドとインストールは手元の作業で、赤い画面の切り分けも手元が早いからです</td></tr>
<tr><td><code>ios/</code>・<code>android/</code> を手で直す変更</td><td>できるだけ config plugin に寄せる</td><td>prebuild のたびに消えるため、手で直したままにしないようにしています</td></tr>
<tr><td>Swift / Kotlin への作り直し</td><td>Rork の「Add iOS app」</td><td>公式の案内では、Expo のアプリを残したまま同じプロジェクトに足せます</td></tr>
</tbody>
</table>

双方向同期だからこそ、同じファイルを Rork と手元で同時に触らないことだけは守っています。手元で `expo-dev-client` を足したら push を済ませ、Rork でそれを確かめてから次の依頼を出す、という順番です。書き出したコードが別の場所で組み直せるかを先に確かめる手順は、[プラン変更の前に取り直したコードを確かめる記事](/articles/rork-basics/rork-export-rebuild-check-before-plan-change)にまとめました。

## 次に詰まる一歩

開発ビルドが動くと、多くの方が次に当たるのは、TestFlight や Google Play の内部テストに出すときの署名とストア申請です。開発ビルドと違って、ここはストア側の設定も絡みます。[Fastlane と EAS でリリースを自動化する記事](/articles/rork-dev/rork-fastlane-eas-release-automation-complete-guide)で、配信までの流れを扱っています。

反対に、開発ビルドに移る前の段階で、そもそも Expo Go が開けていない場合もあります。[Expo Go が開かないときに先に確かめる2つのログイン](/articles/rork-basics/expo-go-login-both-terminal-and-app-preview-not-opening)を見ておくと、原因の候補を一つ減らせます。

## 次にやること

まずは影響の小さいネイティブライブラリを1つだけ足して、ビルドから起動までを一度通してみていただければと思います。通したら、その場で `node scripts/native-deps.mjs save` を打っておきます。次に赤い画面を見たとき、最初の一手が `check` になるだけで、遠回りはずいぶん短くなります。

**赤い画面を前にしたら、コードを直す前に、いま動いているビルドの世代を確かめます。** AI に依頼を重ねる手前で、この一つだけは自分に問うようにしています。
