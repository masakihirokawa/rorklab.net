リリースから数日後、レビュー欄に「変換確定できないバグあり」という星1の一行を見つけて、胃が痛くなりました。Rorkで作ったメモアプリです。手元の英語キーボードでは何事もなく動いていたので、最初は原因の見当すらつきませんでした。

「日本語を入力すると挙動がおかしい」「変換中に文字が消える」「検索ボックスがガタガタする」——日本のユーザーから届くこの種の声は、たいてい同じ根から来ています。生成されたコードが、日本語IME（変換）の存在を前提にしていないのです。

英語圏の開発者がテストしただけでは見つかりにくい落とし穴なので、Rorkの生成コードでよく見かけるパターンを題材に、React NativeのTextInputと日本語IMEの相性を整理します。手元のコードをその日のうちに直せるよう、手順は短く区切ってお伝えします。なお、ここに出てくる TextInput の props と挙動は、2026年11月時点の React Native 公式ドキュメントと Expo の GitHub issue で確認した範囲で書いています。

## なぜ変換中にイベントが暴発するのか

React Nativeの`TextInput`の`onChangeText`は、英語のようなアルファベット入力を前提に設計されています。1文字打つたびに確定文字として扱われ、即座に親コンポーネントへ通知が飛びます。

ところが日本語IMEでは、とくにiOSの日本語キーボードで、変換確定前の「未確定文字列」（ひらがなで表示されて下線が引かれている状態）も、OSからは入力イベントとして飛んできます。つまり「こんにちは」と打って変換候補を選ぶまでの間に、`onChangeText`が5〜10回以上発火してしまうのです。

このイベント暴発が、次のような現象を引き起こします。

- 検索ボックスでAPIリクエストが1文字ごとに飛び、変換候補が出るたびにネットワーク負荷とレート制限エラーが起きます
- Zustandなどで状態更新すると、その再描画が変換候補ウィンドウを強制的に閉じてしまいます
- キーボードや端末によっては、変換を確定したつもりのEnterで`onSubmitEditing`が発火し、意図しない画面遷移が起きます

一方でWebのHTMLでは、`compositionstart`・`compositionupdate`・`compositionend`というイベントで変換中の状態を明示的に追跡できます。React Nativeにはこれに対応する仕組みが用意されていないため、自前で工夫する必要があります。

## 症状を再現する最小コード

まずは問題がどのように現れるかを確認できる、最小の再現コードを紹介します。日本語環境のシミュレータまたは実機で試してみてください。

```tsx
import { useState } from "react";
import { TextInput, View, Text } from "react-native";

export default function BrokenSearchBox() {
  const [query, setQuery] = useState("");
  const [callCount, setCallCount] = useState(0);

  // ❌ 悪い例：変換中も含めて毎回呼ばれる
  const handleChange = (text: string) => {
    setQuery(text);
    setCallCount((c) => c + 1);
    // 本来はここで検索APIを呼ぶ想定
    console.log("検索API呼び出し:", text);
  };

  return (
    <View style={{ padding: 24 }}>
      <TextInput
        value={query}
        onChangeText={handleChange}
        placeholder="検索..."
        style={{ borderWidth: 1, padding: 12, borderRadius: 8 }}
      />
      <Text>API呼び出し回数: {callCount}</Text>
    </View>
  );
}
```

このコードで「東京駅」と入力すると、確定までに `callCount` が十数回まで増えることがあります（回数は端末とキーボードの設定で変わります）。1回の検索のたびにそれだけのAPIリクエストが飛ぶ検索ボックスは、本番では使えません。

## 解決策1：デバウンスで暴発を吸収する

最もシンプルな対策は、連続した変化を「ある程度まとまってから」処理することです。いわゆるデバウンス（debounce）と呼ばれる技法で、IMEの仕様を知らなくても症状を緩和できます。

```tsx
import { useState, useRef, useEffect } from "react";
import { TextInput, View, Text } from "react-native";

export default function DebouncedSearchBox() {
  const [inputValue, setInputValue] = useState("");
  const [committedQuery, setCommittedQuery] = useState("");
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);

  useEffect(() => {
    // 300ms変更がなければ「確定した」とみなしてAPIへ
    if (timerRef.current) clearTimeout(timerRef.current);
    timerRef.current = setTimeout(() => {
      setCommittedQuery(inputValue);
    }, 300);
    return () => {
      if (timerRef.current) clearTimeout(timerRef.current);
    };
  }, [inputValue]);

  useEffect(() => {
    if (committedQuery.length === 0) return;
    // ここで実際の検索APIを呼ぶ
    console.log("検索API呼び出し（確定後）:", committedQuery);
  }, [committedQuery]);

  return (
    <View style={{ padding: 24 }}>
      <TextInput
        value={inputValue}
        onChangeText={setInputValue}
        placeholder="検索..."
        style={{ borderWidth: 1, padding: 12, borderRadius: 8 }}
      />
      <Text>確定クエリ: {committedQuery}</Text>
    </View>
  );
}
```

ポイントは、入力欄のstate（`inputValue`）とAPIへ投げるstate（`committedQuery`）を分けているところです。入力欄はIMEの変換中も含めて自由に更新させつつ、300ms静止したときだけAPIを呼ぶ設計にします。

**入力欄に見えている文字列と、外へ送る文字列は、別の状態として持つ**——この分け方が、このあとの対策すべての土台になります。

この方法は完璧ではありませんが、Rorkで生成されたコードをそのまま活かしたまま最小の修正で済むのが利点です。APIリクエストの過剰発火を防ぎたい検索ボックスには、まずこの形を試してみてください。

最初のうちは、このデバウンスだけで片づいたと思い込んでいました。ところが、変換に時間をかける方の入力では、300msの静止が「変換の途中」で成立してしまい、確定前の文字列で検索が走ります。芳しい結果ではありませんでした。デバウンスは暴発を減らす手段であって、変換中かどうかを見分ける手段ではない——この違いは覚えておいていただければ幸いです。

### 自分の端末で発火回数を数える

回数の見積もりを鵜呑みにせず、お手元の端末で数えてみるのがいちばん確実です。次の数行を検索ボックスに仕込むと、変換の途中でどれだけ通知が来るかが、ログに時刻つきで並びます。

```tsx
const startRef = useRef(Date.now());

const handleChangeText = (text: string) => {
  const elapsed = Date.now() - startRef.current;
  console.log(`+${elapsed}ms onChangeText:`, JSON.stringify(text));
  setInputValue(text);
};
```

「とうきょうえき」と打って候補を選び、確定するまでのログを眺めると、未確定のひらがなが一文字ずつ流れてくる様子が見えます。ここで数えた回数と間隔が、デバウンスの待ち時間を決める叩き台になります。

## 解決策2：Enterキーでのみ確定するパターン

リアルタイム検索にこだわらないのであれば、「Enterキー押下まで検索しない」という割り切った設計も有効です。むしろこちらのほうが、ユーザーが検索の意思表示をしたタイミングで動くため、UXとしては素直なことが多いです。

```tsx
import { useState } from "react";
import { TextInput, View, Text } from "react-native";

export default function SubmitBasedSearchBox() {
  const [inputValue, setInputValue] = useState("");
  const [searchResult, setSearchResult] = useState<string[]>([]);

  const handleSubmit = () => {
    // このタイミングでは確実に変換確定済み
    console.log("検索実行:", inputValue);
    // モック検索結果
    setSearchResult([`${inputValue}の結果1`, `${inputValue}の結果2`]);
  };

  return (
    <View style={{ padding: 24 }}>
      <TextInput
        value={inputValue}
        onChangeText={setInputValue}
        onSubmitEditing={handleSubmit}
        returnKeyType="search"
        placeholder="検索語を入力してEnter"
        style={{ borderWidth: 1, padding: 12, borderRadius: 8 }}
      />
      {searchResult.map((r, i) => (
        <Text key={i}>{r}</Text>
      ))}
    </View>
  );
}
```

`onSubmitEditing`は、キーボードの「改行」や「検索」キーが押されたときだけ発火します。`returnKeyType="search"`を設定するとキーボードに虫眼鏡アイコンが表示され、ユーザーに「ここで検索が実行される」ことが伝わりやすくなります。

私はRorkで作ったアプリをApp Storeにリリースする際、この方式に切り替えたあとはIME関連のクレームがぱったり消えました。個人的には、検索ボックスはこちらのパターンをデフォルトにすることをおすすめします。

## 解決策3：multiline TextInputで改行と確定を分離する

メモアプリや日記アプリのように、`multiline`（複数行入力）のテキストエリアを使う場合は、また別の問題が発生します。日本語IMEの確定キーと改行キーが混線して、意図しないタイミングで改行が挿入されるケースです。

これを防ぐには、`onKeyPress`で物理キーを監視するのではなく、UIレベルで「保存ボタンを明示的に設ける」設計にしてしまうのが現実的です。

```tsx
import { useState } from "react";
import { TextInput, View, Text, Pressable } from "react-native";

export default function MultilineMemoEditor() {
  const [memo, setMemo] = useState("");
  const [saved, setSaved] = useState(false);

  const handleSave = () => {
    // 保存ボタンが押されたときのみ永続化
    console.log("メモを保存:", memo);
    setSaved(true);
  };

  return (
    <View style={{ padding: 24 }}>
      <TextInput
        value={memo}
        onChangeText={(t) => {
          setMemo(t);
          setSaved(false);
        }}
        multiline
        placeholder="メモを入力..."
        style={{
          borderWidth: 1,
          padding: 12,
          borderRadius: 8,
          minHeight: 120,
          textAlignVertical: "top",
        }}
      />
      <Pressable
        onPress={handleSave}
        style={{
          marginTop: 16,
          padding: 12,
          backgroundColor: "#0066cc",
          borderRadius: 8,
        }}
      >
        <Text style={{ color: "white", textAlign: "center" }}>保存</Text>
      </Pressable>
      {saved && <Text style={{ marginTop: 8 }}>保存しました</Text>}
    </View>
  );
}
```

`multiline`なTextInputで「Enterキーで保存」にしたい気持ちはわかるのですが、日本語の変換確定のためにもEnterキーを使う仕様上、どうしても競合します。ユーザーに明示的な保存アクションを求めるデザインのほうが、結果的にトラブルが少ないです。

## 古い検索結果が後から返ってくる問題

デバウンスで回数を減らしても、もうひとつ残る症状があります。「東京」の検索結果より、あとから打った「東京駅」の結果が先に返り、そのあとで遅れた「東京」の結果が画面を上書きしてしまう並びです。ネットワークの遅い場所ほど起きやすく、手元のWi-Fiでは再現しにくいのがやっかいなところです。

次のように、新しい検索を始める直前に前のリクエストを取り消しておくと、古い結果が画面に残りません。

```tsx
useEffect(() => {
  if (committedQuery.length === 0) return;
  const controller = new AbortController();

  fetch(`https://api.example.com/search?q=${encodeURIComponent(committedQuery)}`, {
    signal: controller.signal,
  })
    .then((res) => res.json())
    .then(setResults)
    .catch((e) => {
      if (e.name !== "AbortError") console.warn("検索に失敗しました", e);
    });

  // committedQuery が変わる直前に、前のリクエストを取り消す
  return () => controller.abort();
}, [committedQuery]);
```

URLの `api.example.com` は説明用の仮のドメインです。ご自身のAPIに置き換えてお試しください。

## 変換中の value を加工しない

デバウンスでも防げない落とし穴が、もうひとつあります。`onChangeText` の中で入力文字列をその場で加工し、そのまま `value` に戻してしまう書き方です。

```tsx
// ❌ 変換中の文字列まで削ったり置き換えたりすると、候補ウィンドウが閉じることがあります
<TextInput
  value={value}
  onChangeText={(t) => setValue(t.replace(/\s/g, "").slice(0, 20))}
/>
```

空白の除去や文字数の切り詰めは、確定したあとにまとめて行うほうが安全です。入力中は受け取った文字列をそのまま保持し、`onEndEditing` か保存ボタンを押した時点で整えます。いまは「見えている文字列には手を触れず、整えるのは確定してから」という線引きで実装するようにしています。

## よくある誤解を三つ

### 誤解1：value を渡さなければ、すべて直る

React Native の公式ドキュメントは `defaultValue` を、`value` を毎回更新して同期させる手間を省きたい場面のための prop として説明しています。たしかに非制御にすると、入力のたびに親から値を書き戻さなくなるので、変換中の再描画が原因の症状は減ります。

ただし、入力欄を外から空にしたいとき（検索後のクリアなど）は `ref.current?.clear()` を呼ぶ形に変わりますし、`value` で表示を整える書き方はできなくなります。

```tsx
import { useRef } from "react";
import { TextInput, Button, View } from "react-native";

export default function UncontrolledSearch({ onSearch }: { onSearch: (q: string) => void }) {
  const inputRef = useRef<TextInput>(null);
  const latest = useRef("");

  return (
    <View style={{ padding: 24, gap: 12 }}>
      <TextInput
        ref={inputRef}
        defaultValue=""
        onChangeText={(t) => { latest.current = t; }}   // 表示には使わず、手元に控えるだけ
        onSubmitEditing={() => onSearch(latest.current)}
        returnKeyType="search"
        style={{ borderWidth: 1, padding: 12, borderRadius: 8 }}
      />
      <Button title="クリア" onPress={() => { inputRef.current?.clear(); latest.current = ""; }} />
    </View>
  );
}
```

`onChangeText` は残しつつ、state ではなく ref に控えるだけにしているのがこの形の要点です。再描画が起きないので、候補ウィンドウに触れずに済みます。万能ではなく、「再描画が原因の症状に効く選択肢のひとつ」と捉えていただくのがよいと思います。

### 誤解2：multiline でも Enter で保存させられる

React Native の `submitBehavior` は、1行の入力では既定で `blurAndSubmit`、multiline では既定で `newline` です（以前の `blurOnSubmit` に代わる prop です）。multiline で `submit` 系に変えれば Enter で `onSubmitEditing` は呼べますが、その代わりに改行が打てなくなります。

メモや日記で改行が打てないのは致命的なので、解決策3で保存ボタンを分けたのはこのためです。「Enter は改行のもの、保存はボタンのもの」と役割を分けておくと、変換の確定と保存が同じキーに乗ることもありません。

### 誤解3：シミュレータで問題なければ実機も大丈夫

iOS シミュレータでハードウェアキーボードを接続したまま打つと、Mac 側の入力ソースで変換が行われ、実機のソフトウェアキーボードとは通知の来方が異なることがあります。私も最初はシミュレータで打って「直った」と判断し、実機で同じ症状を見て手が止まりました。

確かめるときは、シミュレータのメニューでソフトウェアキーボードを表示させるか、できれば実機で、ローマ字入力・かな入力の両方を試してください。Android は Gboard で試すと、iOS と並びの違う通知が来ることもあります。

## @expo/ui の TextField を使っている場合（2026年11月時点）

最近の Rork の生成コードや Expo のテンプレートでは、ネイティブの見た目に寄せるために `@expo/ui` の `TextField`（iOS では SwiftUI の TextField）を使うことがあります。ここには React Native の TextInput とは別の注意点があります。

Expo の GitHub には、iOS 18 以降で日本語・中国語・韓国語の IME が変換中のとき、`@expo/ui` の TextField が「Index out of range」で落ちるという報告が上がっています（[expo/expo #54364](https://github.com/expo/expo/issues/54364)）。2026年11月時点では修正版を確認できていません。英語キーボードだけで試していると、まず見つからない種類の不具合です。

また、New Architecture を有効にした環境で、React Native の TextInput の変換中の文字から下線が消えるという報告もあります（[expo/expo #38422](https://github.com/expo/expo/issues/38422)）。落ちはしませんが、どこまでが未確定なのかが見えにくくなります。

私は、日本語を打ってもらう画面に限っては、こうした報告に修正が入るまで React Native の TextInput を使う線引きにしています。**見た目の新しさより、変換が最後まで通ることを先に取る**——日本語の入力欄では、この順番を入れ替えないようにしております。部品を置き換える判断全体については、[Expo UI の drop-in 置き換えで、依存が本当に1本減る条件](/articles/rork-dev/expo-ui-dropin-replacement-dependency-removal-preconditions)にまとめています。

## Rorkに追加で指示すべきプロンプト例

Rorkでアプリを最初から作る際、日本語ユーザー向けであることを明示的に伝えると、生成コードの質が変わってきます。私が実際に使っているプロンプトの追記例は次のようなものです。

- 「TextInputを使う画面は、日本語IMEの変換中にonChangeTextが暴発することを考慮して、debounceまたはonSubmitEditingで処理を確定させる設計にしてください」
- 「検索ボックスは、入力中は検索APIを呼ばず、`returnKeyType="search"`のEnterキー押下時にのみ検索を実行してください」
- 「multilineのTextInputでは、Enterキーで保存する設計を避け、明示的な保存ボタンを設けてください」
- 「日本語を入力する画面では、@expo/ui の TextField ではなく React Native の TextInput を使ってください」

AIにこうした前提を伝えるだけで、後から日本語特有のバグに悩まされる時間を大幅に減らせます。画面の文言をどの言語で、どの長さで指示するかは、[Rork への依頼を日本語と英語で比べて分かった、画面の文言の決め方](/articles/rork-ai/rork-prompt-japanese-vs-english-decide-strings-length-format-first)で別に書いています。IME の前提と合わせて、最初の依頼文に入れておくと手戻りが減ります。

## 日本語入力で気づきにくい3つの落とし穴

最後に、Rorkで作ったアプリを日本語環境でテストするときに、見落としがちなポイントを3つ挙げておきます。

1. **maxLengthが「未確定文字列」も含めて数える**：`maxLength=10`にしたTextInputで、変換前のひらがなが長く伸びると、確定後の漢字が入らなくなることがあります（端末やキーボードによって挙動は異なります）。制限はやや緩めに設定し、確定後に切り詰めるのが無難です。
2. **絵文字の結合文字対応**：家族絵文字（👨‍👩‍👧‍👦）のような絵文字は、複数のコードポイントをつないだ並びです。`text.length`で数えると見た目と合わず、`[...text].length`でもコードポイント単位なので、まだ1文字にはなりません。見た目どおりに数えたいときは、`Intl.Segmenter`が使える環境ならそれを、使えない環境ではgrapheme単位で分割するライブラリを検討してください。
3. **全角英数字と半角英数字の混在**：パスワードフィールドやメールアドレス欄では、`autoCapitalize="none"`と`keyboardType="email-address"`を明示しておかないと、iOSで全角入力モードに入ったまま打ってしまうユーザーが発生します。

## 次の一歩

まずはお手元のRorkプロジェクトの中から、TextInputを使っている画面をひとつ選んで、`onChangeText`に直接APIコールやstate更新の重い処理を書いていないか確認してみてください。もし書いているなら、この記事のデバウンスまたは`onSubmitEditing`パターンへ差し替えることで、日本語ユーザーの体感品質が目に見えて変わります。

検索ボックスが直ったら、次に当たりやすいのは「2文字で検索すると0件になる」という、検索の仕組み側の問題です。こちらは[2文字の検索語が気づかれないまま0件になる — Expo アプリの日本語検索インデックス](/articles/rork-dev/rork-expo-japanese-search-index-two-char-blind-spot)で、計測のしかたから扱っています。

日本語で入力する方が最初に触れるのは、機能の多さより、変換がすんなり通るかどうかなのだと思います。その手触りだけは、リリース前に必ず自分の指で確かめるようにしています。
