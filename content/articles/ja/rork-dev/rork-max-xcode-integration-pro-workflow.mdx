Rork Max が吐いたプロジェクトを Xcode で開いて、シミュレータで動かして、そのまま Archive してしまった日があります。審査には出せました。ただ実機に入れてスクロールした瞬間に、リストが目に見えて引っかかった。シミュレータでは一度も再現しなかった症状でした。

生成の速さと、出荷できる品質は別の軸にあります。前者を Rork Max が引き受けてくれるようになったぶん、後者の工程が相対的に重くなった、というのが個人開発で半年ほど運用してきた実感です。

以下は、その「後者」だけを工程順に並べたものです。時間を溶かした箇所には、溶かした理由も添えています。

## Rork Max 生成プロジェクトの構造を理解する

まず Xcode でプロジェクトを開いたときに、ディレクトリ構成を正しく把握することが出発点です。

典型的な構成は次のような形になります。

```
MyApp/
├── MyApp.xcodeproj/
├── Sources/
│   ├── App/              ← アプリケーションのエントリポイント
│   ├── Views/            ← SwiftUI View 定義
│   ├── Models/           ← データモデル・Codable 定義
│   ├── Services/         ← API クライアント・永続化層
│   └── Utils/            ← 拡張関数・ヘルパー
├── Resources/
│   ├── Assets.xcassets/
│   ├── Localizations/
│   └── Fonts/
└── .rork/                ← Rork 生成メタデータ（重要）
```

この中で最も注意が必要なのは `.rork/` ディレクトリです。これは Rork Max がプロジェクトの再生成や更新に使う内部メタデータで、手を入れると再生成の挙動が壊れます。

編集してよい場所とそうでない場所を、判断基準ごとに整理しておきます。

<table>
  <thead>
    <tr><th>対象</th><th>手を入れてよいか</th><th>理由</th></tr>
  </thead>
  <tbody>
    <tr><td><code>.rork/</code></td><td>不可</td><td>再生成時の差分計算の基準。書き換えると次回出力が破綻する</td></tr>
    <tr><td><code>Sources/Views/</code></td><td>可（衝突しやすい）</td><td>Rork が最も頻繁に書き換える領域。改変は最小差分で</td></tr>
    <tr><td><code>Sources/Services/</code></td><td>可</td><td>生成後に触る前提の層。API の実装差し替えはここで</td></tr>
    <tr><td><code>Sources/Extensions/</code>（自作）</td><td>推奨</td><td>Rork が生成しない新規ディレクトリ。衝突がそもそも起きない</td></tr>
    <tr><td><code>*.xcodeproj</code></td><td>可（要注意）</td><td>Build Settings の変更は残るが、ターゲット構成の改変は再生成で巻き戻る</td></tr>
  </tbody>
</table>

最後の行が実務上いちばん効きます。Build Settings のフラグ変更は再生成後も残りますが、ターゲットを分割したりスキームを作り替えたりすると、次の生成で静かに元へ戻されることがあります。プロジェクトファイルの構造そのものを触るのは、再生成を打ち切る覚悟が固まってからにしてください。

## Instruments で診断すべき 3 つのプロファイル

生成されたコードは動きます。ただ初期状態では「動く」ところで止まっていることが多い。出荷品質へ持っていく判断材料は、実機での計測からしか出てきません。

冒頭に書いたスクロールの引っかかりも、シミュレータでは一度も観測できませんでした。Mac の CPU で走らせている限り、重い計算はコストとして表面化しないためです。

### 1. Time Profiler — CPU 時間の見直し

アプリ起動時やタブ切り替え時の体感速度が遅いと感じたら、最初に Time Profiler で計測します。生成コードで典型的に遅いのは、次のパターンです。

```swift
// 遅い: 毎回すべての要素を再計算
var body: some View {
    List(items) { item in
        Row(item: item, score: computeScore(for: item))
    }
}
```

`computeScore` が重い計算を含んでいると、スクロール時に毎フレーム再計算が走って体感速度が落ちます。対策は `@State` でキャッシュするか、コンピュテッドプロパティを事前計算しておくことです。

```swift
// 速い: 事前計算してキャッシュ
@State private var cachedScores: [UUID: Double] = [:]

var body: some View {
    List(items) { item in
        Row(item: item, score: cachedScores[item.id] ?? 0)
    }
    .task {
        await computeAllScores()
    }
}
```

計測の際は、必ず Release ビルドを実機に流し込んでください。Debug ビルドの Time Profiler は最適化が効いていないぶんプロファイルの形が変わり、本来ボトルネックでない関数が上位に来ます。私はこれで一度、無関係な関数を丸一日かけて最適化しました。

### 2. Allocations — メモリ使用量の把握

生成コードは、画像の扱いで不要なメモリを消費するケースがあります。Allocations プロファイルで「Transient」ではなく「Persistent」なメモリの増加を追うと、解放漏れが見えてきます。

特に `AsyncImage` や `UIImage(data:)` を多用するリストは要注意です。画像のダウンサンプリングを入れるだけで、メモリ使用量が 1/5 になることもあります。

```swift
// 画像のダウンサンプリング関数
func downsample(image data: Data, to pointSize: CGSize, scale: CGFloat) -> UIImage? {
    let imageSourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary
    guard let imageSource = CGImageSourceCreateWithData(data as CFData, imageSourceOptions) else {
        return nil
    }
    let maxDimensionInPixels = max(pointSize.width, pointSize.height) * scale
    let downsampleOptions = [
        kCGImageSourceCreateThumbnailFromImageAlways: true,
        kCGImageSourceShouldCacheImmediately: true,
        kCGImageSourceCreateThumbnailWithTransform: true,
        kCGImageSourceThumbnailMaxPixelSize: maxDimensionInPixels
    ] as CFDictionary
    guard let downsampledImage = CGImageSourceCreateThumbnailAtIndex(imageSource, 0, downsampleOptions) else {
        return nil
    }
    return UIImage(cgImage: downsampledImage)
}
```

`kCGImageSourceShouldCache: false` を最初のオプションに入れている点が要です。これを落とすと、CGImageSource がデコード済みビットマップを内部に抱え込み、ダウンサンプリングした先のメモリ削減がほぼ相殺されます。関数だけコピーして動かない、という相談を受けたときは、たいていこの行が消えていました。

### 3. SwiftUI Performance — 再描画の「原因」まで遡る

SwiftUI は宣言的なゆえに、どの View がどのタイミングで再描画されるかが直感と合わないことがあります。ここは Xcode 26 で計測手段が変わった領域なので、少し詳しく扱います。

Instruments 26 では SwiftUI 専用のテンプレートが追加され、Update Groups レーンで「SwiftUI がいつ更新作業をしているか」が時間軸上に並ぶようになりました。従来の Time Profiler が「どの関数が重いか」を教えてくれるのに対して、こちらは「どの更新がどれだけメインスレッドを占有したか」を教えてくれます。

さらに有用なのが Cause & Effect Graph です。更新を選択して「Show Cause & Effect Graph」を選ぶと、状態の変更から View の body 再評価までの伝播がノードとして表示されます。View ノードの左側に並ぶのが、その更新を引き起こしたイベントです。

これが効くのは、まさに Rork Max 生成コードで典型的に起こる問題に対してです。`ObservableObject` を監視している View が、関係のないプロパティの変更でも再描画される。従来はこれを目視と当て推量で切り分けていましたが、Cause & Effect Graph なら「この再描画の原因はこのプロパティの mutation だった」と一意に辿れます。

原因が特定できたあとの手当ては 2 通りです。

```swift
// Before: オブジェクト全体を観測 → 無関係な更新でも再描画
struct ScoreBadge: View {
    @ObservedObject var store: SessionStore
    var body: some View { Text("\(store.score)") }
}

// After: 必要な値だけを受け取る → 親でのみ観測が発生する
struct ScoreBadge: View, Equatable {
    let score: Int
    var body: some View { Text("\(score)") }
    static func == (l: Self, r: Self) -> Bool { l.score == r.score }
}
```

値だけを受け取る形に落として `Equatable` を付けておくと、SwiftUI は同値の場合に body の再評価を省けます。Rork Max の生成物は View に `@ObservedObject` を素直に配ってくる傾向があるため、リスト行のような高頻度描画の箇所だけでもこの形へ寄せておくと、Update Groups の占有時間が目に見えて縮みます。

## Rork Max アップデートを取り込みつつ最適化を維持する

実運用で最も悩ましいのが、Rork 側のアップデートを取り込むときに、Xcode 側で加えた最適化を失わないようにすることです。

私が採っているのは、次の 2 分岐アプローチです。

```
main ブランチ           ← Xcode 最適化を反映した手動ブランチ
rork-generated ブランチ ← Rork Max が生成したそのままのコード
```

`rork-generated` ブランチには、Rork Max で再生成するたびに出力をそのまま載せます。そして `main` へ merge することで、Rork 側の更新を自分の最適化と統合します。

この運用のポイントは、**手動で加える最適化を、できるだけ独立したファイルに分離しておくこと**です。`Sources/App/AppDelegate.swift` を直接改変するのではなく、`Sources/Extensions/AppDelegate+Optimizations.swift` のような拡張ファイルを作っておくと、Rork 側のファイルとのコンフリクトを大幅に減らせます。

### force push でマージベースを失わない

ここが、私が最初に設計を間違えた箇所です。

当初は再生成のたびに `rork-generated` を force push で置き換えていました。生成物は毎回まっさらなので、履歴を積む意味がないと考えたためです。ところがこれをやると、`main` と `rork-generated` の共通祖先が毎回失われます。

Git の 3-way merge は、共通祖先との差分を見て「どちらが変更したか」を判定します。マージベースが古いコミットまで後退すると、Rork が触っていないファイルまで「両方が変更した」と見なされ、プロジェクト全体がコンフリクトとして返ってきます。数ファイルの調整で済むはずの再生成が、半日の手作業になっていました。

対処は単純で、force push をやめて、生成物を前回の上に普通のコミットとして積むだけです。

```bash
# 再生成のたびに実行（force push しない）
git switch rork-generated
rsync -a --delete --exclude='.git/' ./rork-output/ ./
git add -A
git commit -m "Rork regenerate $(date +%Y-%m-%d)"

# main 側へ取り込む
git switch main
git merge rork-generated
```

`rsync --delete` を挟んでいるのは、Rork 側で削除されたファイルを確実にツリーから落とすためです。生成物をコピーで上書きするだけだと、消えたはずのファイルが `rork-generated` に残り、それが `main` へ merge されて幽霊ファイルとして復活します。

この形にしてからは、マージベースが前回の生成コミットに固定されるため、コンフリクトは Rork が実際に書き換えたファイルだけに収まるようになりました。

### 衝突が起きたときの対処

Git の merge で衝突が発生したら、基本方針は「Rork 側のロジックは Rork に任せ、自分の最適化は拡張点に閉じ込める」です。どうしても本体に手を入れなければならないときは、コメントで `// RORK:ORIGINAL_KEPT` や `// DOLICE:OPTIMIZATION` のようにマーカーを入れておくと、後で追跡しやすくなります。

マーカーは検索できる形にしておくのが要点で、`git log -S'DOLICE:OPTIMIZATION'` を打てば、その最適化がいつ入っていつ消えたかを追えます。生成物を相手にする以上、自分の変更が知らないうちに巻き戻されている可能性は常に残ります。

## 審査で最も差し戻されるのは privacy manifest

チェックリストへ進む前に、ここだけ独立させて扱います。理由は単純で、私が Rork Max 経由のビルドで実際に差し戻された唯一の項目がこれだったためです。

2024 年 5 月 1 日以降、新規アップロードとアップデートには、Required Reason API を使う場合に `PrivacyInfo.xcprivacy` の `NSPrivacyAccessedAPITypes` へ承認済みの理由コードを記載することが求められています。記載が漏れていると、アップロード直後に ITMS-91053（Missing API declaration）がメールで返ってきます。

厄介なのは、この対象が自分の書いたコードに限られない点です。同梱した SDK が内部で該当 API を呼んでいれば、それも申告対象になります。Rork Max の生成物はテンプレート由来の依存を含むため、自分では一度も書いていない API が指摘対象として挙がってきます。

最小構成の `PrivacyInfo.xcprivacy` は次のような形です。`UserDefaults` を使っているだけでも申告が要る、というのが見落としやすいところです。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>NSPrivacyAccessedAPITypes</key>
  <array>
    <dict>
      <key>NSPrivacyAccessedAPIType</key>
      <string>NSPrivacyAccessedAPICategoryUserDefaults</string>
      <key>NSPrivacyAccessedAPITypeReasons</key>
      <array>
        <string>CA92.1</string>
      </array>
    </dict>
  </array>
</dict>
</plist>
```

アップロード前に自力で気づくには、該当 API の呼び出し箇所を洗い出しておくのが早いです。

```bash
# 依存を含めて Required Reason API の呼び出しを洗い出す
grep -rn "UserDefaults\|systemUptime\|creationDate\|modificationDate\|statfs\|activeProcessorCount" \
  Sources/ Pods/ 2>/dev/null | grep -v "/Tests/"
```

ヒットしたカテゴリを申告し、リリース直前ではなく最初の Archive の前に一度通しておくことを推奨します。そのうえで、`PrivacyInfo.xcprivacy` が Target の Copy Bundle Resources に含まれていることを確認してから Archive してください。ファイルを作っただけでターゲットに追加し忘れると、同じ ITMS-91053 が返ってきます。私が半日を失ったのは、この「作ったのに入っていない」パターンでした。

## App Store 審査前のチェックリスト

privacy manifest を片付けたうえで、私が毎回確認している残りの項目です。

- **Bundle Identifier の最終確認**: 生成時のデフォルト値（`com.rork.appname`）のまま出すとリジェクトされるので、自分の組織ドメインに変更
- **Info.plist のプライバシー説明**: カメラ・位置情報・フォトライブラリを使う場合、`NSCameraUsageDescription` 等の説明文を実運用レベルで書き直す
- **Push Notifications の entitlement**: Rork 側で有効化しても、Apple Developer Portal での Certificate 紐付けが別途必要
- **Dark Mode 対応の目視確認**: 生成時に Dark Mode の色指定が抜けていることがあり、Xcode のプレビューで両モード確認
- **VoiceOver 対応**: アクセシビリティラベルが生成時に不足しがちなので、Accessibility Inspector で再確認
- **起動時間の実機計測**: TestFlight で実機にインストールし、ストップウォッチで起動時間を測る（シミュレータと実機で 2 倍以上ずれることがある）

## 個人開発者の視点から（実体験メモ）

半年運用してみて、自分の中で位置づけが変わったのは「生成物を資産として扱うかどうか」でした。

最初は、Rork Max の出力を自分のコードベースだと思って読んでいました。だから気になった箇所を片端から書き直し、命名を揃え、ディレクトリを整理した。結果として次の再生成でその全部がコンフリクトになり、解消に費やした時間が、最初に節約できた時間を上回りました。

いまは出力を「毎回届く納品物」として扱っています。納品物には手を入れず、必要な変更は自分の側のファイルに書く。この切り分けを守っている限り、再生成は数分で終わります。守れなかった月は、決まって週末が溶けました。

もうひとつ、判断を変えたのは計測のタイミングです。以前は機能をひととおり実装し終えてから Instruments を開いていました。いまは、リスト系の画面をひとつ作った時点で一度だけ実機で計測します。早い段階で一度見ておくと、そのプロジェクトの生成物がどういう癖を持っているかが分かり、以降の実装で同じ罠を踏まなくなるためです。冒頭のスクロールの引っかかりも、この習慣が付いてからは再現していません。

速く作れる道具を手に入れたぶん、どこで立ち止まるかを自分で決める必要が出てきた。そういう感覚でいます。
