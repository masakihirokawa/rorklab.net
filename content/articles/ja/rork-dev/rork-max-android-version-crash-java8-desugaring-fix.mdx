Android 版の壁紙アプリを v2.1.0 に更新した翌朝、Firebase Crashlytics を開くと、見慣れない赤い行が増えていました。

```
java.lang.NoClassDefFoundError: Failed resolution of: Ljava/util/function/Supplier;
```

報告の出どころは Android 6.0.1 の端末ばかりです。最初は「古い端末だから仕方がないのかもしれない」と考え、半日ほど様子を見てしまいました。この見立てが、いちばんの失敗でした。原因は端末の古さではなく、ビルド設定の抜けだったのです。

Rork Max が生成するプロジェクトでは、Glide 5.x や AGP 9.x といった新しい組み合わせの中で Java 8 の API が使われることがあります。Android 7.0（API 24）や 8.0（API 26）より前の端末は、それらを素のままでは解決できません。そのため、特定の OS の方だけがアプリを起動できない、という状態になります。

厄介なのは、手元の検証端末では一度も再現しないことです。開発機が新しいほど発見が遅れ、気づいたときには低評価レビューのほうが先に届いています。以下では、Crashlytics での切り分けから `coreLibraryDesugaringEnabled` による対処、そして「設定を入れたのに直らない」ケースまでを順に書き残します。

## なぜ「特定の OS バージョンだけ」クラッシュするのか

Android は OS のバージョンごとに、実行時に使える Java API の範囲が異なります。Java 8 で加わった `Stream`、`Optional`、`Supplier` は API 24 以上、`java.time` 系は API 26 以上でないと、素のままでは解決できません。

Rork Max が生成するコードは最新の Android 環境を前提としています。そのため、これらのクラスを内部で使うライブラリ（Glide 5.x など）との組み合わせで、古い OS では起動直後に落ちるアプリが出来上がることがあります。

実際にどのクラスが境界線上にあるのかを把握しておくと、クラッシュログを見た瞬間に当たりがつきます。よく踏むものを挙げます。

<table>
<thead>
<tr><th>API</th><th>ネイティブ対応</th><th>よく混入する経路</th></tr>
</thead>
<tbody>
<tr><td><code>java.util.function.Supplier</code> / <code>Consumer</code></td><td>API 24 以上</td><td>Glide 5.x の内部実装</td></tr>
<tr><td><code>java.util.stream.Stream</code></td><td>API 24 以上</td><td>ユーティリティ系ライブラリ</td></tr>
<tr><td><code>java.util.Optional</code></td><td>API 24 以上</td><td>Firebase SDK の一部</td></tr>
<tr><td><code>java.time.*</code>（<code>LocalDate</code> 等）</td><td>API 26 以上</td><td>日付処理を自前実装したとき</td></tr>
<tr><td><code>java.nio.file.*</code></td><td>非対応（別ライブラリが必要）</td><td>ファイル操作の生成コード</td></tr>
</tbody>
</table>

スタックトレースの `Failed resolution of:` の後ろがこの表のどれかに当たるなら、端末固有の不具合ではなくデシュガリング設定の欠落です。

リリース後 28 日間で 50 件以上の `NoClassDefFoundError` が届き、`Crash-free users` が 99.4% まで下がったときは、胃が重くなる思いでした。数字だけ見れば致命的ではないものの、Play Store の評価にじわじわ効いてくる種類の問題です。

## Step 1：Firebase Crashlytics でクラッシュを特定する

まず Crashlytics のダッシュボードで、どの端末・OS バージョンでクラッシュが集中しているか確認します。

「Issues」タブでエラーを開くと「Session details」にデバイス情報が表示されます。「Android 6.0.1 / 7.0 が多い」というパターンが見えたら、Java 8 デシュガリング問題の可能性が高いです。

確認するポイントは以下の通りです。

- OS バージョンの集中（Android 8.0 / API 26 未満に偏っていないか）
- スタックトレース上のエラー種別（`NoClassDefFoundError`、`ClassNotFoundException`）
- 関与している外部ライブラリ（Glide、OkHttp、Firebase SDK など）

Rork Max プロジェクトの場合、Expo の managed workflow から ejected した後の `android/app/build.gradle` を確認します。

## Step 2：app/build.gradle の compileOptions を確認する

Rork Max が生成した Android プロジェクトの `android/app/build.gradle` を開いてください。

```groovy
android {
    compileOptions {
        sourceCompatibility JavaVersion.VERSION_1_8
        targetCompatibility JavaVersion.VERSION_1_8
    }
}
```

`sourceCompatibility` と `targetCompatibility` が `VERSION_1_8` になっていても、それだけでは Android 8.0 未満の実機での動作は保証されません。**デシュガリング（Desugaring）** の設定が別途必要です。

デシュガリングとは、Java 8 以上の構文を古い Android でも理解できる形に変換するプロセスです。有効にするには、同じ `compileOptions` ブロックに1行追加します。

```groovy
android {
    compileOptions {
        sourceCompatibility JavaVersion.VERSION_1_8
        targetCompatibility JavaVersion.VERSION_1_8
        coreLibraryDesugaringEnabled true
    }
}

dependencies {
    coreLibraryDesugaring "com.android.tools:desugar_jdk_libs:2.0.4"
}
```

この修正を入れて Android 6.0.1 のエミュレーターで起動し直すと、同じ操作でもクラッシュしなくなりました。設定は 2 か所だけですが、そこに至るまでに半日かかったことを思うと、「端末のせい」と決めつけた時間がいちばん高くつきました。

なお、`build.gradle.kts` を使っているプロジェクトでは、書き方が `isCoreLibraryDesugaringEnabled = true` と `coreLibraryDesugaring("com.android.tools:desugar_jdk_libs:2.0.4")` になります。Groovy と Kotlin DSL のどちらで生成されているかは、最初に確認しておくと迷いません。

## Step 3：Rork の AI に修正を依頼する際のプロンプト

Rork の AI に修正を依頼する際は、具体的なエラーメッセージとファイル名を添えて指示します。漠然と「クラッシュを直して」と伝えても、AI は何を変えればいいか判断できません。

実際に使っている依頼文はこの形です。

```
android/app/build.gradle の android.compileOptions に
coreLibraryDesugaringEnabled true を追加し、
dependencies に coreLibraryDesugaring "com.android.tools:desugar_jdk_libs:2.0.4" を追加してください。

対象ファイル: android/app/build.gradle のみ
変更しないもの: minSdkVersion、他の依存関係のバージョン
理由: Android 6.0.1 で java.util.function.Supplier が NoClassDefFoundError になるため
```

修正依頼のポイントは「対象ファイル」「追加する行」「エラーの再現条件」の3点を明示することです。加えて「変更しないもの」を書いておくと、結果が安定します。Rork の AI は親切ですが、スコープを広く与えると関係のないコードまで変えてしまうことがあり、私も一度、依存バージョンを勝手に更新されて原因の切り分けがやり直しになりました。それ以来、変更範囲は依頼文の側で先に閉じています。

## デシュガリングを入れても直らなかった2つのケース

設定を追加したのにクラッシュが残ったことが2度あります。どちらも原因は build.gradle の外側にありました。

**1つ目は R8 の縮小との併用です。** `minifyEnabled true` の状態でデシュガリング後のクラスが難読化の対象になり、リフレクション経由の参照が解決できなくなっていました。`proguard-rules.pro` に退避ルールを足して解消しています。

```proguard
-keep class j$.util.** { *; }
-keep class j$.time.** { *; }
-dontwarn java.lang.invoke.**
```

デシュガリングされたクラスは `j$` プレフィックスの下に再配置されるため、`java.*` を対象にしたルールでは守れません。ここを見落としていました。なお、最近の AGP では R8 がデシュガリング用の keep ルールを自動で補う場合もあります。ルールを足す前に、まず `./gradlew assembleRelease` したリリースビルドの実機で再現するかを確かめるのが先です。

**2つ目はビルドキャッシュです。** 設定を入れた直後のビルドで古い dex がそのまま再利用され、「直したはずなのに再現する」状態になりました。設定を変えた直後は必ずクリーンビルドを挟みます。

```bash
cd android && ./gradlew clean
./gradlew assembleRelease --rerun-tasks
```

もう一点、`minSdkVersion` を上げて回避する選択肢もあります。ただし Android 6〜7 が残っている地域では想像以上にユーザーを切り捨てることになります。Google Play Console の「Android バージョン」分布を見てから判断していただければと思います。私のアプリでは API 24 未満が全体の 1.8% で、その方々を切り捨てるより、設定 1 行を足すほうが妥当だと判断しました。

## Step 4：AGP バージョンと Glide の組み合わせに注意する

AGP（Android Gradle Plugin）9.x と Glide 5.0.x を組み合わせた場合に特にこの問題が出やすいです。Rork Max が生成するプロジェクトはデフォルトで最新の AGP を使いますが、`desugar_jdk_libs` のバージョンが古い場合も同様のクラッシュが起きます。

`desugar_jdk_libs` は `2.0.4` 以上にしておくと安心です。古いバージョンでは、一部の Java 8 API が変換されないまま残る場合があります。Glide の Kotlin API や Coroutines 統合を使っている場合も同じ設定で対応できます。

## Step 5：段階公開でリスクを最小化する

個人開発者にとって、リリース後のクラッシュは評価とユーザー離脱に直結します。Play Store の段階公開（5% → 25% → 50% → 100%）を使うことで、被害を最小限に抑えられます。

個人開発の現場で使っている監視基準は以下の通りです。

- `Crash-free users`: 各フェーズで 99.7% 以上を維持
- `ANR rate`: 0.20% 未満を維持
- 様子見の期間: 各フェーズで 24〜48 時間

5% の段階で `Crash-free users` が 99.4% に落ちたら、それ以上は広げず、原因が分かるまで止めます。今回の問題は、この基準のおかげで 25% に届く前に気づくことができました。全員に届く前に手を打てたことが、評価への影響を小さく抑えられた理由だと思っています。

## Step 6：リリース前の予防策として古い端末でのテストを組み込む

Rork Max で生成したコードを AGP 9.x や最新ライブラリと組み合わせて使う場合、リリース前に Android 7.0〜8.0 の実機またはエミュレーターでの動作確認を必ず行うことをお勧めします。

個人開発では実機テストの時間が限られるため、私は Android Studio のエミュレーターで API 24（Android 7.0）と API 28（Android 9）の2つを常時用意しています。このテスト環境があるだけで、Java 8 デシュガリング問題の大半はリリース前に発見できます。

テスト手順は以下のような流れです。まず Rork Max でビルドした APK を API 24 エミュレーターにインストールします。次にアプリの主要な画面をひと通り操作し、スタックトレースが出ないことを確認します。最後に API 28 エミュレーターで同じ操作を繰り返し、新旧の OS で動作に差がないことを確認します。

この工程を CI に組み込むのが理想的ですが、個人開発の場合は手動でも十分です。リリース前の 5〜10 分で、リリース後の評価低下リスクを大幅に下げることができます。

Rork の AI でコードを生成し直すたびに、依存ライブラリは少しずつ変わります。新機能を足した日は、API 24 のエミュレーターで起動だけ確かめる——その一手間を習慣にしています。

## 全体を振り返って：古い端末のせいにする前に

古い OS だけで落ちるときに最初にやることは、Crashlytics で OS バージョンの分布を見ることです。「Android 8.0 未満に集中している」うえに `NoClassDefFoundError` が並んでいれば、`coreLibraryDesugaringEnabled` と `desugar_jdk_libs` の追加で、多くの場合は片がつきます。

**端末の古さを疑う前に、まずビルド設定の抜けを疑います。** 半日を無駄にしたあとで引いた、私なりの線引きです。いま思えば、Crashlytics の OS 分布を開けば最初の 5 分で見えていたことでした。

まずは手元のプロジェクトの `compileOptions` を開いて、`coreLibraryDesugaringEnabled` の行があるかどうかを確かめるところから始めていただければと思います。
