バックグラウンド更新を入れたアプリを出して数週間たった朝、Crashlytics の非致命エラーの一覧に `BGTaskSchedulerErrorDomain Code=1` がずらりと並んでいるのを見つけたことがあります。クラッシュはしていないので、通知も来ません。ウィジェットの中身がしばらく古いままだったのに、誰も気づいていなかったのです。

そのとき私は、Code=1 を見て真っ先に `Info.plist` を疑い、識別子の綴りを三度見直しました。けれども綴りは合っていて、手が止まりました。あとで Apple のドキュメントを読み直して気づいたのは、`Info.plist` の漏れはそもそも Code=1 ではなく Code=3 に出る、ということでした。いま思えば、数字を一度も疑わずに探し始めていたのだと思います。

最初にお伝えしたいのは、**エラーの数字が、どこを探すべきかを半分まで教えてくれる**ということです。本稿は Rork で生成した Expo（React Native）アプリに BGTaskScheduler を組み込んだ前提で、Code=1・2・3 を公式の定義どおりに読み分け、原因を一つずつ潰していく順番を書き残します。

## Code=1 と Code=3 は別の場所を指している

`BGTaskScheduler.submit(_:)` が投げるエラーは `BGTaskSchedulerErrorDomain` に属し、Apple の `BGTaskScheduler.Error.Code` に原因が書かれています（2026年11月時点・公式ドキュメントで確認）。

<table>
<thead>
<tr><th>code</th><th>名前</th><th>Apple が挙げている原因</th><th>直すのは誰か</th></tr>
</thead>
<tbody>
<tr><td>1</td><td>unavailable</td><td>利用者が設定で Background App Refresh を切っている／シミュレーターで動かしている／拡張（エクステンション）から予約しようとしている</td><td>多くは端末側。拡張からの submit だけはアプリ側</td></tr>
<tr><td>2</td><td>tooManyPendingTaskRequests</td><td>同じ種類の保留中リクエストが多すぎる（refresh は合計1件、processing は合計10件まで）</td><td>アプリ側</td></tr>
<tr><td>3</td><td>notPermitted</td><td><code>UIBackgroundModes</code> に必要なモードがない／識別子が <code>BGTaskSchedulerPermittedIdentifiers</code> にない</td><td>アプリ側（Info.plist）</td></tr>
<tr><td>—</td><td>immediateRunIneligible</td><td>即時実行を求めたリクエストが、システムの状態で即時には走らなかった</td><td>新しい種類のタスクを使うときだけ</td></tr>

この表の要点は一つで、**Code=1 は「この環境では予約できない」、Code=3 は「このアプリにはその予約が許されていない」**という違いです。Code=1 の大半は利用者の設定に由来し、コードを何度読み直しても直りません。反対に Code=3 は、ほぼ確実にこちらの設定ミスです。

`immediateRunIneligible` は数字の割り当てを私はまだ公式で確かめられていないため、表では空けています。通常の `BGAppRefreshTaskRequest` と `BGProcessingTaskRequest` だけを使っているアプリなら、見かけるのは 1・2・3 の三つです。

## まず submit の周りに「読める」ログを仕込む

数字で切り分けるには、数字と一緒に端末の状態が手元に届いていなければなりません。`submit` を次のように包んでおくと、Crashlytics の一覧を見ただけで、どの原因の山かが分かるようになります。

```swift
// BackgroundRefresh.swift（メインアプリのターゲットに置く）
import BackgroundTasks
import UIKit
import os

enum BackgroundTaskID {
    static let appRefresh = "net.rorklab.app.refresh"
}

private let log = Logger(subsystem: "net.rorklab.app", category: "bgtask")

func refreshStatusLabel() -> String {
    switch UIApplication.shared.backgroundRefreshStatus {
    case .available:  return "available"
    case .denied:     return "denied"      // 利用者が設定で切っている
    case .restricted: return "restricted"  // 管理プロファイルなどで制限されている
    @unknown default: return "unknown"
    }
}

func scheduleAppRefresh() {
    let request = BGAppRefreshTaskRequest(identifier: BackgroundTaskID.appRefresh)
    request.earliestBeginDate = Date(timeIntervalSinceNow: 15 * 60)

    do {
        try BGTaskScheduler.shared.submit(request)
        log.info("bgtask submitted id=\(request.identifier, privacy: .public)")
    } catch let error as NSError {
        let status = refreshStatusLabel()
        log.error("bgtask submit failed code=\(error.code) status=\(status, privacy: .public)")
        // Crashlytics を使っている場合は、code と status を Custom Key として一緒に送る
        // Crashlytics.crashlytics().setCustomValue(status, forKey: "bg_refresh_status")
        // Crashlytics.crashlytics().record(error: error)
    }
}
```

なぜ `backgroundRefreshStatus` を一緒に送るのかというと、Code=1 の山を「設定で切っている人」と「それ以外」に割るためです。`UIApplication.shared` はメインスレッドで読むものなので、`scheduleAppRefresh()` はアプリが前面にいるとき（`sceneDidEnterBackground` の直前など）に呼びます。

私は以前、`userInfo` もステータスも捨てて `code` だけを送っていました。その結果、Code=1 が増えた理由を確かめるには、利用者に設定画面のスクリーンショットをお願いするしかありませんでした。**数字を送るなら、その数字を読み解く材料も一緒に送る**——いまはこれを線引きにしています。

## 集まったログを code と状態で割る

Crashlytics の BigQuery エクスポートや、自前のログ収集から CSV を書き出せるなら、次のスクリプトで山の形がすぐに見えます。列は `build,os,code,refresh_status,target` の5つで、`target` はログを出したターゲット（`app` か拡張の名前）です。

```python
#!/usr/bin/env python3
"""Crashlytics などから書き出した BGTaskScheduler の submit 失敗ログを集計し、
code ごとに「どこを見るべきか」を出す。列: build,os,code,refresh_status,target"""
import csv, sys
from collections import Counter, defaultdict

HINT = {
    "1": "unavailable: 設定の Background App Refresh／シミュレーター／拡張からの submit",
    "2": "tooManyPendingTaskRequests: refresh は1件・processing は10件まで",
    "3": "notPermitted: Info.plist の BGTaskSchedulerPermittedIdentifiers と UIBackgroundModes",
}

def main(path):
    rows = list(csv.DictReader(open(path, newline="", encoding="utf-8")))
    by_code = Counter(r["code"] for r in rows)
    print(f"total={len(rows)}")
    for code, n in by_code.most_common():
        print(f"  code={code} n={n}  -> {HINT.get(code, '未定義のコード（SDK の版を確認）')}")

    # code=1 を refresh_status と target で割る
    c1 = [r for r in rows if r["code"] == "1"]
    status = Counter(r["refresh_status"] for r in c1)
    target = Counter(r["target"] for r in c1)
    print("code=1 by refresh_status:", dict(status))
    print("code=1 by target:", dict(target))

    off = status.get("denied", 0) + status.get("restricted", 0)
    if c1 and off == len(c1):
        print("verdict: code=1 はすべて OS 設定側。アプリでは直せないので案内文の出し方を見直す")
    elif c1:
        rest = len(c1) - off
        print(f"verdict: code=1 のうち {rest} 件は refresh_status=available。"
              "拡張ターゲットから submit していないか、シミュレーター由来のログが混ざっていないかを先に見る")

    # code=3 がビルド単位で急に出始めたかを見る（prebuild での上書きを疑う）
    per_build = defaultdict(Counter)
    for r in rows:
        per_build[r["build"]][r["code"]] += 1
    for b in sorted(per_build):
        print(f"  build={b} {dict(per_build[b])}")
    first3 = next((b for b in sorted(per_build) if per_build[b]["3"]), None)
    if first3:
        print(f"verdict: code=3 は build={first3} から。その前後の prebuild で Info.plist を diff する")

if __name__ == "__main__":
    main(sys.argv[1] if len(sys.argv) > 1 else "bgtask_errors.csv")
```

動作を確かめるために、説明用に作った8行の CSV（実際のアプリの数値ではありません）を Python 3.10 で流した結果がこちらです。

```text
$ python3 bgtask_triage.py bgtask_errors.csv
total=8
  code=1 n=5  -> unavailable: 設定の Background App Refresh／シミュレーター／拡張からの submit
  code=3 n=3  -> notPermitted: Info.plist の BGTaskSchedulerPermittedIdentifiers と UIBackgroundModes
code=1 by refresh_status: {'denied': 3, 'restricted': 1, 'available': 1}
code=1 by target: {'app': 4, 'widget': 1}
verdict: code=1 のうち 1 件は refresh_status=available。拡張ターゲットから submit していないか、シミュレーター由来のログが混ざっていないかを先に見る
  build=41 {'1': 3}
  build=42 {'1': 2, '3': 3}
verdict: code=3 は build=42 から。その前後の prebuild で Info.plist を diff する
```

読み方は単純です。Code=1 のうち `denied`・`restricted` の行は利用者の設定で、アプリからは直せません。`available` なのに Code=1 の行と、あるビルドから急に現れた Code=3 だけが、こちらで直すべきものです。ビルド番号は文字列として並べているので、桁数が変わる運用なら `int()` で並べ替えてください。

## Code=1 の原因 1：Background App Refresh が切られている

実機でしか出ず、特定の利用者に偏っているなら、ほぼこれです。「設定 > 一般 > Appのバックグラウンド更新」が全体で、またはこのアプリだけ OFF になっていると、`submit` は Code=1 を返します。省電力モード中もバックグラウンド更新は止まりますが、そのときに `submit` がどのコードを返すかは、私は公式の記述を見つけられていません。

アプリから設定を変えることはできないので、対応は「知らせ方」になります。

- 機能を使い始めた瞬間に `backgroundRefreshStatus` を読み、`.denied` のときだけ、一度だけ案内します
- `.restricted` は管理プロファイルなど利用者にも変えられない場合があるため、案内を出さずにログだけ残します
- 案内文は「閉じている間も新しい内容を取りに行くには、設定でこのアプリのバックグラウンド更新を ON にしていただく必要があります」のように、理由と場所を一文で伝えます

私のアプリでも、Code=1 の山を `backgroundRefreshStatus` で割ってみたら、大半が `denied` でした。直せない山だと分かってからは、そこを追いかけるのをやめ、残りの小さな山に時間を使えるようになりました。肩の荷が一つ下りた感覚があったのを覚えています。

## Code=1 の原因 2：シミュレーターで動かしている

Background Tasks の API はシミュレーターでは使えず、実機でのみ動きます。これは Expo の `expo-background-task` のドキュメントにも明記されています。シミュレーターで出る Code=1 は「正しく失敗している」だけなので、追いかける必要はありません。

ここでよくある誤解が、LLDB からタスクを強制発火させればシミュレーターでも検証できる、というものです。Apple の「Starting and Terminating Tasks During Development」には、`_simulateLaunchForTaskWithIdentifier` などのデバッグ用関数は **実機でのみ動く** と書かれています。手順は次のとおりです。

```text
1. submit(_:) が成功した直後の行にブレークポイントを置く
2. 実機でアプリを動かし、ブレークポイントで止める
3. デバッガで次を実行し、アプリを再開すると launch handler が呼ばれる
(lldb) e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"net.rorklab.app.refresh"]
```

これらは非公開の関数なので、開発中だけに使います。App Store に出すビルドに参照を残すとリジェクトの理由になる、と Apple は注意しています。

Expo のタスクを JS 側で組んでいる場合は、`BackgroundTask.triggerTaskWorkerForTestingAsync()` で発火を試せます。こちらもデバッグビルド専用で、本番ビルドでは動きません。

## Code=1 の原因 3：拡張から submit している

ウィジェットの中身を裏で更新したくて、ウィジェット拡張のターゲットに `submit` を書いてしまう——これも Code=1 の典型です。Apple の説明では、unavailable になる理由の一つに拡張からの予約が挙げられています（キーボード拡張で Open Access が許可されていない場合なども含みます）。

役割はこう分けます。データを取りに行くのはメインアプリのバックグラウンドタスク、表示を描き直すのは WidgetKit のタイムラインです。

```swift
// メインアプリで実行し、書き終えたらウィジェットへ知らせる
import BackgroundTasks
import WidgetKit

func handleAppRefresh(task: BGAppRefreshTask) {
    scheduleAppRefresh()                  // 次回分を先に予約しておく
    let work = Task {
        await syncLatestData()            // App Group の共有コンテナへ書き込む
        WidgetCenter.shared.reloadAllTimelines()
        task.setTaskCompleted(success: true)
    }
    task.expirationHandler = {
        work.cancel()                     // 時間切れのときは途中で止めて完了を伝える
        task.setTaskCompleted(success: false)
    }
}
```

拡張の種類や OS の版によっては、`submit` 自体は通ってしまい「予約はできたのに一度も走らない」という形で現れることもあります。その経路は [Widget Extension でも BGTaskScheduler.submit は成功します。走らないのは register が親アプリだけのものだからです](/articles/rork-dev/widget-extension-bgtaskscheduler-submit-register-host-app-only) に詳しく書きました。どちらの形でも、**取得はメインアプリ、表示は拡張**という分け方に戻せば解けます。

## Code=3 なら Info.plist を見る（Expo の識別子を含めて）

Code=3（notPermitted）の原因は、公式には2つだけです。`UIBackgroundModes` に必要なモードがない（refresh なら `fetch`、processing なら `processing`）か、`submit` した識別子が `BGTaskSchedulerPermittedIdentifiers` に文字どおり入っていないかです。

Rork が生成するのは Expo のアプリなので、`expo-background-task` を使っている場合はここに Rork 固有の落とし穴があります。このモジュールが内部で予約する識別子は、自分で決めた文字列ではなく `com.expo.modules.backgroundtask.processing` です。CNG（Continuous Native Generation）で `prebuild` を通す構成なら、この識別子と `UIBackgroundModes` の `processing` は prebuild が自動で入れてくれます。

問題は、自前のネイティブタスクを足そうとして `ios.infoPlist` に配列を自分で書いたときに起きます。両方使うなら両方書きます。

```json
{
  "expo": {
    "plugins": ["expo-background-task"],
    "ios": {
      "infoPlist": {
        "UIBackgroundModes": ["fetch", "processing"],
        "BGTaskSchedulerPermittedIdentifiers": [
          "com.expo.modules.backgroundtask.processing",
          "net.rorklab.app.refresh"
        ]
      }
    }
  }
}
```

Expo の識別子についてはドキュメントに書かれていない時期があり、[expo/expo の Issue #40440](https://github.com/expo/expo/issues/40440) で報告されました。この Issue はすでに閉じられていて、2026年11月時点の SDK 58 のドキュメントには、必要な2つの設定が明記されています。

書いたつもりの値が本当にビルドに入っているかは、`prebuild` のあとに生成された `Info.plist` で確かめます。

```bash
npx expo prebuild --platform ios
/usr/libexec/PlistBuddy -c "Print :BGTaskSchedulerPermittedIdentifiers" ios/*/Info.plist
/usr/libexec/PlistBuddy -c "Print :UIBackgroundModes" ios/*/Info.plist
```

ある日を境に Code=3 が増えたなら、その前後の `prebuild` で配列が上書きされていないかを diff するのが近道です。prebuild の前後で何が変わったかを棚卸しする手順は [Expo SDK 57 に上げる前に、prebuild で消えるネイティブ変更を洗い出す](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit) にまとめています。

## Code=2 は「予約しすぎ」

`submit(_:)` の説明によると、同時に予約できるのは refresh タスクが合計1件、processing タスクが合計10件までで、それを超えると Code=2 になります。保留中のタスクと同じ識別子で `submit` し直した場合は、古いリクエストが置き換わるだけでエラーにはなりません。

Code=2 が出るのは、識別子を日付や連番入りで毎回変えている場合がほとんどです。識別子は固定の定数にし、予約の前に `cancel(taskRequestWithIdentifier:)` で古いものを消す必要は通常ありません。

## エラーは出ないのに走らないとき

`submit` が成功するのに handler が呼ばれない場合は、エラーコードの外にある問題です。公式に書かれている制約は次の2つです。

- `BGTaskSchedulerPermittedIdentifiers` に書いた識別子には、すべて handler が必要で、`register` はアプリの起動処理（`application(_:didFinishLaunchingWithOptions:)`）が終わる前に済ませます
- 同じ識別子を2回 `register` すると、システムはアプリを終了させます

Rork の生成コードを手で直すと、`register` と `submit` の文字列がずれることがあります。私も `app.refresh` と `appRefresh` の表記揺れを見落とし、しばらくタスクが一度も走らないままにしていました。それ以来、識別子は `BackgroundTaskID` のような enum に置き、両方から参照しています。

`earliestBeginDate` は「これより前には走らせない」という下限であって、早く走らせるスイッチではありません。直近の時刻を入れても、システムが走らせる時刻は電池・通信・利用傾向で決まります。私は15分先を目安にしていますが、これは Apple の仕様ではなく、手元で扱いやすかった値です。

## 予約が残っているかを getPendingTaskRequests で確かめる

`submit` が例外を投げなかったことと、iOS がその予約を保持していることは別の話です。保持されているかは `getPendingTaskRequests` で読み出せます。

```swift
func dumpPendingTasks() {
    BGTaskScheduler.shared.getPendingTaskRequests { requests in
        guard !requests.isEmpty else {
            log.error("no pending bgtask requests")
            return
        }
        for request in requests {
            log.info("pending id=\(request.identifier, privacy: .public) earliest=\(String(describing: request.earliestBeginDate), privacy: .public)")
        }
    }
}
```

実機で一度アプリをバックグラウンドへ送り、前面に戻してから呼びます。`submit` の直後から空なら予約そのものが通っておらず、上の Code の表に戻ります。入っているのに走らないなら、`register` の時期と識別子、そして利用者の使い方による待ち時間を疑います。

## よくある誤解

**「Code=1 は Info.plist の漏れ」**——Apple の定義では、識別子やモードの漏れは Code=3（notPermitted）です。Code=1 で `Info.plist` を何度見直しても、多くの場合は答えが出ません。

**「LLDB を使えばシミュレーターでも発火を試せる」**——デバッグ用の関数は実機でのみ動く、と Apple は書いています。シミュレーターの Code=1 は正常な結果として扱ってかまいません。

**「earliestBeginDate を短くすれば早く走る」**——これは下限の指定で、実際の時刻はシステムが決めます。Expo の `minimumInterval` も同じで、最小は15分、既定は12時間です。

## 次に詰まりやすいところ

予約が通り、handler が呼ばれるようになると、次は「走ったのに途中で止まる」に出会います。バックグラウンドの持ち時間は短く、時間切れになると `expirationHandler` が呼ばれます。ここで `setTaskCompleted(success:)` を呼び忘れると、以後の予約が後回しにされやすくなる、という報告も見かけます（公式の明文は確認できていません）。

時間切れの扱いも、実機の LLDB で `_simulateExpirationForTaskWithIdentifier` を使えば発火を待たずに試せます。処理の中身を本番に耐える形で組む段になったら、[Rorkアプリで「閉じてる間も最新」を本番品質で実装する](/articles/rork-dev/rork-background-refresh-bgtask-silent-push-workmanager-production-guide) に、Silent Push と Android の WorkManager まで含めた設計を書いています。

また、Code=1 を追っていたつもりが、実はビルドが TestFlight まで届いていなかった、という回り道を私はしたことがあります。そちらで止まっているなら [Rorkで書き出したアプリがApp Store Connectで「処理中」のまま止まる](/articles/rork-dev/rork-app-store-connect-build-stuck-processing-fix) をご覧ください。

まずは `submit` の失敗ログに `backgroundRefreshStatus` を一つ足して、次のビルドを出していただければと思います。数字の山が二つに割れるだけで、追いかけるべきものがどれなのか、はるかに見えやすくなるはずです。
