試算表に二人のユーザーを並べた夜がありました。一人は月に 50 回、もう一人は毎日 200 回、同じ AI チャット機能を使うという仮定です。1 回あたりの API 原価を仮に 3 円と置くだけで、後者の原価は月 18,000 円を超え、同じ月額料金を払ってもらう設計がそもそも成り立たないことが、数字の上で見えてしまいました。

固定月額は分かりやすい仕組みですが、AI 機能では「軽い方が重い方を支える」かたちになりがちです。ここで検討に値するのが、Stripe の **Meter Billing（使用量ベース課金）** です。Stripe の Meter 系 API を使うと、使用量をイベントとして送るだけで、期間ごとの集計と請求を Stripe に任せられます。

Rork で作った AI アプリに Meter Billing を組み込む流れを、サーバー側の実装を中心に辿っていきます。途中で一度、私自身が初稿で組んだ設計の穴にも触れます。実際に動かして確認できた範囲と、手元では確かめきれていない範囲は、本文で分けて書き残しています。

## 使用量課金が AI アプリに必要な理由

固定月額には、構造的な歪みがあります。AI アプリでは、ユーザーごとの使用量が 10 倍から 100 倍以上離れることが珍しくありません。月 50 回の人と毎日 200 回の人が同額を払う設計では、ヘビーユーザーが増えるほど原価が膨らみます。

使用量課金を取り入れると、次の三つが手に入ります。

- 使った分だけ負担する公平さ（原価の増加を開発者が一人で抱えずに済みます）
- 低い基本料金のエントリープラン（「基本 300 円＋使用量」なら、試したい人の入口が低くなります）
- API 提供や B2B 向けへ広げやすい課金基盤

ただし、解約率が下がるかどうかは、アプリの性質と価格の置き方で変わります。「導入すれば定着する」と言い切れる材料は、私の手元にはありません。先に確かめたいのは、原価と単価の関係です。

## Stripe Meter Billing の全体設計

Meter は三つの部品でできています。

- **Meter**: 何を数えるかの定義です（例: AI 利用の単位数）。集計方法に Sum、Count、Last を選べます。
- **Meter Event**: 実際の使用量をサーバーから Stripe へ送るイベントです。
- **Price with Meter**: Meter の期間内の集計値に対して課金する価格です。

流れは次のとおりです。

```
Rork アプリ → 自前のバックエンド（Cloudflare Workers）に AI リクエストを送る
    ↓
Workers がユーザーを認証し、AI を呼び、成功したら使用量を決める
    ↓
Workers → stripe.billing.meterEvents.create() で Stripe に送信
    ↓
Stripe が請求期間ごとに集計して請求
```

ここで押さえたいのは、**使用量は「AI を呼んだサーバー」が自分で数えて報告する**という一点です。初稿の私は、アプリ側から「使った分」を報告させる構成を書いていました。しかしその構成では、アプリに共有キーを埋め込むことになり、ユーザーは報告を止めることも、他人の顧客 ID 宛てに送ることもできてしまいます。

> **数える側と使う側を、同じ場所に置く。** 報告をクライアントに任せた時点で、請求の根拠は信頼の上にしか立ちません。

## Step 1: Meter と Price を作る

ダッシュボードの Billing → Meters からも作れますが、設定の再現性を考えて API で作る形を示します。

```typescript
// 一度だけ実行するセットアップ用スクリプト
const meter = await stripe.billing.meters.create({
  display_name: 'AI usage units',
  event_name: 'ai_usage', // イベント送信時のキー
  default_aggregation: { formula: 'sum' }, // 送った value を合計する
  customer_mapping: { event_payload_key: 'stripe_customer_id', type: 'by_id' },
  value_settings: { event_payload_key: 'value' }, // 数量を入れる項目名（既定は value）
});
```

集計方法の違いが、旧版で抜けていた点です。**Count は送られた回数を数え、`value` を無視します。** トークン数や重みつきの単位で課金するなら、Sum を選ぶ必要があります。ダッシュボードで「各イベントを 1 として数える」設定のまま `value` を送っても、トークン数は課金に反映されません。

次に、Meter に紐づく Price を作ります。

```typescript
const meteredPrice = await stripe.prices.create({
  currency: 'jpy',
  product: 'prod_xxxxxxxx',
  recurring: { interval: 'month', usage_type: 'metered', meter: meter.id },
  billing_scheme: 'tiered',
  tiers_mode: 'graduated',
  tiers: [
    { up_to: 100, unit_amount_decimal: '0' },   // 無料枠
    { up_to: 500, unit_amount_decimal: '1' },   // 1 単位 1 円
    { up_to: 'inf', unit_amount_decimal: '0.7' }, // 500 超は段階的に安く
  ],
});
```

円未満の単価は `unit_amount` では表せないため、`unit_amount_decimal` を使います。円建てで小数の単価が請求書にどう丸められるかは、私の手元ではテストモードの請求書で確認しきれていません。公開前に、少額の使用量で一度請求書を発行して確かめていただければと思います。

## Step 2: Workers で AI を呼び、使用量を報告する

認証済みのユーザーだけを受け付け、顧客 ID はサーバー側の対応表から引きます。クライアントから `customerId` を受け取らないことが肝心です。

```typescript
import Stripe from 'stripe';

interface Env {
  STRIPE_SECRET_KEY: string;
  METER_RETRY: Queue<RetryPayload>;
}

interface RetryPayload {
  customerId: string;
  value: number;
  identifier: string;
}

function stripeClient(env: Env) {
  // Workers では fetch ベースの HTTP クライアントを明示しておくと安全です
  return new Stripe(env.STRIPE_SECRET_KEY, {
    httpClient: Stripe.createFetchHttpClient(),
  });
}

export async function sendMeterEvent(env: Env, p: RetryPayload): Promise<void> {
  await stripeClient(env).billing.meterEvents.create({
    event_name: 'ai_usage',
    identifier: p.identifier, // 同じ identifier の再送は重複として扱われる
    payload: {
      stripe_customer_id: p.customerId,
      value: String(p.value),
    },
  });
}

// 失敗しても AI の応答は返す。再送で救える失敗だけキューへ積む
export async function recordUsage(env: Env, p: RetryPayload): Promise<void> {
  try {
    await sendMeterEvent(env, p);
  } catch (e) {
    if (e instanceof Stripe.errors.StripeInvalidRequestError) {
      console.error('meter event rejected (fix the request):', e.message);
      return; // リクエストの形が誤っているので再送しても通りません
    }
    await env.METER_RETRY.send(p); // 5xx・レート制限・ネットワーク断
  }
}
```

重複排除に使うのは、Stripe の Meter Event が持つ `identifier` です。[公式の Meter Event ドキュメント](https://docs.stripe.com/api/billing/meter-event/create)では、少なくとも 24 時間のローリング期間で一意性が保たれるとされています。HTTP の Idempotency-Key ヘッダでも二重実行は防げますが、請求の根拠になるイベントの単位で重複を判断できる `identifier` を第一に使うのが、分かりやすい設計だと考えています。

呼び出し側のハンドラは、こうなります。

```typescript
// authenticate は認証基盤（Supabase など）に合わせて実装します。
// JWT を検証して userId を得て、対応表から stripeCustomerId を引く役割です。
export async function handleChat(request: Request, env: Env, ctx: ExecutionContext) {
  const user = await authenticate(request, env);
  if (!user) return new Response('Unauthorized', { status: 401 });

  const { message, requestId } = await request.json<{ message: string; requestId: string }>();

  const answer = await callModel(message, env); // 失敗したら例外 → 課金しない

  ctx.waitUntil(
    recordUsage(env, {
      customerId: user.stripeCustomerId,
      value: 1, // 1 メッセージ = 1 単位
      identifier: `chat_${user.id}_${requestId}`, // 再送されても同じ値になる
    })
  );

  return Response.json({ message: answer });
}
```

`requestId` はアプリが 1 回の送信ごとに作る UUID です。ダブルタップや通信の再試行で同じリクエストが二度届いても、`identifier` が同じなので課金は一度で済みます。

## Step 3: Rork アプリ側は認証トークンだけを送る

アプリ側に Stripe の ID も共有キーも持たせません。

```typescript
import * as Crypto from 'expo-crypto';

export async function sendChatMessage(message: string, accessToken: string) {
  const res = await fetch('https://your-worker.example.workers.dev/api/chat', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${accessToken}`, // ログイン済みユーザーのトークン
    },
    body: JSON.stringify({ message, requestId: Crypto.randomUUID() }),
  });
  if (res.status === 429) throw new Error('monthly_cap_reached');
  if (!res.ok) throw new Error(`chat failed: ${res.status}`);
  return (await res.json()) as { message: string };
}
```

`EXPO_PUBLIC_` で始まる環境変数は、アプリのバンドルに含まれます。秘密を入れる場所ではない、という点は何度見直しても大事です。再送が必要なときは、同じ `requestId` を使い回してください。

## Step 4: 基本料金＋従量課金のサブスクリプション

純粋な従量課金だけでは収益が読みにくくなるため、基本料金と組み合わせる形が扱いやすいと考えています。一つのサブスクリプションに、固定の Price と Meter の Price を並べます。

```typescript
const subscription = await stripe.subscriptions.create({
  customer: customerId,
  items: [
    { price: 'price_base_monthly_300yen' }, // 基本料金
    { price: meteredPrice.id },             // Meter 連携（quantity は不要）
  ],
  payment_behavior: 'default_incomplete',
  payment_settings: { save_default_payment_method: 'on_subscription' },
  expand: ['latest_invoice.payment_intent'],
});
```

最後の `expand` は、API バージョン 2025-03-31.basil 以降では `latest_invoice.payment_intent` が使えなくなり、`latest_invoice.confirmation_secret` が置き換えになっています（この置き換えは私の理解で、手元の環境では未検証です）。使っている API バージョンに合わせて読み替えてください。

## Step 5: 無料枠と段階単価

無料枠は、Step 1 で作った Graduated の最初の段を 0 円にするだけで実現できます。コード側の変更は要りません。請求期間ごとに段階が数え直されます。

```
第 1 段: 0〜100 単位   → 0 円（無料枠）
第 2 段: 101〜500 単位 → 1 円
第 3 段: 501 単位以上  → 0.7 円
```

プランごとに無料枠を変えたいときは、段階が違う Price をプランの数だけ作ります。ライトは 100、スタンダードは 500、といった具合です。

## Step 6: 上限は Stripe に頼れない

ここは初稿でいちばん誤りが大きかった部分です。「Billing Controls で月 3,000 円のスペンドキャップを設定できる」「`billing_thresholds` で上限を作れる」と書いていました。

公式ドキュメントを読み直した範囲では、使用量を止めるハードな上限は見つかりませんでした。次のとおりです。

- **Billing Alerts**: 使用量がしきい値に達したときに `billing.alert.triggered` という Webhook が届きます。通知を止めるのではなく、知らせてくれる仕組みです。
- **`billing_thresholds`**: しきい値に達した時点で**請求書を前倒しで作る**ための設定です。課金や使用を止めません。

したがって、「今月はここまで」という上限は自前で持つ必要があります。実装は後述の集約セクションで、月次カウンタと一緒に示します。ユーザーに「上限があります」と伝える場合は、その上限が自分のコードで守られていることを、先に確かめてください。

## Step 7: 使用量を画面に出す

画面に出す数字は、Stripe の集計に頼らず、アプリ側のカウンタから出すのが無難です。Stripe は使用量を非同期に処理するため、集計に直近のイベントが反映されないことがあります（反映までの時間は公式に具体的な数字がありません）。

Stripe 側の値を確かめたいときは、日単位で集計を取得します。

```typescript
async function usageThisMonth(stripe: Stripe, meterId: string, customerId: string) {
  const now = new Date();
  const start = Date.UTC(now.getUTCFullYear(), now.getUTCMonth(), 1) / 1000;
  const end = Math.floor(now.getTime() / 86400000 + 1) * 86400; // 翌日 0:00(UTC)
  const summaries = await stripe.billing.meters.listEventSummaries(meterId, {
    customer: customerId,
    start_time: start,
    end_time: end,
    value_grouping_window: 'day', // 指定できるのは day と hour のみ。day は UTC 0:00 に揃える
  });
  return summaries.data.reduce((sum, s) => sum + s.aggregated_value, 0);
}
```

旧版では `value_grouping_window: 'month'` と書いていましたが、指定できる値は `day` と `hour` だけです。また、ここで計算しているのは暦月（UTC）であり、請求期間とは一致しない場合があります。

## よくある落とし穴

### 落とし穴 1: 冪等キーが再送でずれる

初稿のリトライ処理は、冪等キーを「5 分窓の番号」から作っていました。再送が窓をまたぐと、キーが変わって二重に計上されてしまいます。送信前に決めた `identifier` を、キューの中身として持ち回る形に改めました。上のコードで `RetryPayload` に `identifier` を含めているのは、そのためです。

### 落とし穴 2: Meter の ID が環境で違う

テストモードと本番では、Meter の ID が別です。コードに直接書かず、Worker の環境変数に置きます。`process.env.NODE_ENV` は Workers で当てにならないので、`wrangler.toml` の vars か secrets で切り替えます。

### 落とし穴 3: アプリの User ID と Stripe の Customer ID の対応

サインアップ時に Stripe Customer を作り、アプリ側の User ID と結びつけて保存します。対応表がないと、どの顧客に報告するかが分からなくなります。

```typescript
const customer = await stripe.customers.create({
  email,
  metadata: { app_user_id: userId },
});
await supabase.from('users').update({ stripe_customer_id: customer.id }).eq('id', userId);
```

### 落とし穴 4: 受理されたイベントが請求に載るとは限らない

Meter Event を受け付けたことと、請求書に載ることは別です。タイムスタンプは過去 35 日以内から未来 5 分以内でなければならず、請求書が確定した後に届いたイベントは、集計には出ても確定済みの請求書を変えないことがあります。無効なイベントは非同期のエラーレポート（`v1.billing.meter.error_report_triggered`）で通知されるので、その Webhook を受けておくと見落としが減ります。

## 報告失敗を取りこぼさない — リトライキュー

Step 2 では、再送で救える失敗をキューに積みました。まず `wrangler.toml` です。

```toml
[[queues.producers]]
queue = "meter-retry"
binding = "METER_RETRY"

[[queues.consumers]]
queue = "meter-retry"
max_batch_size = 10
max_retries = 5
dead_letter_queue = "meter-retry-dlq"
```

消費側は、同じ `identifier` で送り直します。

```typescript
export default {
  async queue(batch: MessageBatch<RetryPayload>, env: Env): Promise<void> {
    for (const msg of batch.messages) {
      try {
        await sendMeterEvent(env, msg.body); // 初回と同じ identifier
        msg.ack();
      } catch {
        msg.retry({ delaySeconds: 300 });
      }
    }
  },
};
```

要点は二つです。**`identifier` は初回送信の前に決め、再送でも使い回す**こと。そして、`max_retries` を使い切って DLQ に落ちた分は課金しないと、先に決めておくことです。取りすぎて信頼を失うより、少し取り漏らす方を選ぶ、という線引きにしています。なお `identifier` の一意性は少なくとも 24 時間とされているので、再送の合計時間がそれを超えない設計にしておく必要があります。この設定では 5 分間隔で最大 5 回、およそ 25 分です。

## 送信回数を絞る — 集約と月次上限

Stripe の Meter Event には、ライブモードで毎秒 1,000 回というレート制限があります（高スループット用の v2 ストリームは別枠で、毎秒 10,000 件）。利用が伸びる前に、自分の側で集計してから送る設計を知っておくと安心です。

ユーザーごとに Durable Object を一つ割り当て、使用量を貯めてアラームでまとめて送ります。同じ場所に月次カウンタを持たせれば、Step 6 の上限チェックもここで済みます。

```typescript
const WINDOW_MS = 5 * 60 * 1000;

export class MeterBuffer {
  constructor(private state: DurableObjectState, private env: Env) {}

  async fetch(request: Request): Promise<Response> {
    const store = this.state.storage;
    const monthKey = `month:${new Date().toISOString().slice(0, 7)}`; // UTC の暦月
    const monthTotal = (await store.get<number>(monthKey)) ?? 0;

    if (new URL(request.url).pathname === '/peek') {
      return Response.json({ monthTotal });
    }

    const { customerId, value } = await request.json<{ customerId: string; value: number }>();
    const pending = (await store.get<number>('pending')) ?? 0;
    await store.put({ [monthKey]: monthTotal + value, pending: pending + value, customerId });

    if ((await store.getAlarm()) === null) {
      await store.setAlarm(Date.now() + WINDOW_MS);
    }
    return Response.json({ monthTotal: monthTotal + value });
  }

  async alarm(): Promise<void> {
    const store = this.state.storage;
    const sending = (await store.get<number>('pending')) ?? 0;
    if (sending <= 0) return;
    const customerId = (await store.get<string>('customerId'))!;
    const seq = (await store.get<number>('seq')) ?? 0;

    // 失敗したら例外のまま終わる → アラームが自動で再実行され、同じ seq・同じ identifier で再送される
    await sendMeterEvent(this.env, {
      customerId,
      value: sending,
      identifier: `flush_${customerId}_${seq}`,
    });

    // 送信中に増えた分は残し、送った分だけ引く
    const rest = ((await store.get<number>('pending')) ?? 0) - sending;
    await store.put({ pending: Math.max(rest, 0), seq: seq + 1 });
    if (rest > 0) await store.setAlarm(Date.now() + WINDOW_MS);
  }
}
```

初稿では、送信後にキーごと削除していました。しかし Stripe の呼び出し中に新しい使用量が加わると、それを消してしまいます。さらに、窓の番号を時刻から作っていたので、アラームの再試行で別の `identifier` になる恐れもありました。通し番号 `seq` を送信成功のときだけ進める形に変えたのは、その二つを一度に塞ぐためです。

ハンドラ側は、このように使います。

```typescript
const id = env.METER_BUFFER.idFromName(user.stripeCustomerId);
const buffer = env.METER_BUFFER.get(id);

const { monthTotal } = await (await buffer.fetch('https://do/peek')).json<{ monthTotal: number }>();
if (monthTotal >= user.monthlyCap) {
  return Response.json({ error: 'monthly_cap_reached' }, { status: 429 }); // 自前の上限
}

const answer = await callModel(message, env);
ctx.waitUntil(buffer.fetch('https://do/add', {
  method: 'POST',
  body: JSON.stringify({ customerId: user.stripeCustomerId, value: 1 }),
}));
```

集約には代償もあります。Stripe に届くまで最大で窓の長さだけ遅れるため、画面に出す数字は Durable Object の `monthTotal` から読み、Stripe は請求の根拠として使い分けます。集約を入れた場合、再送はアラームが担うので、前のセクションのキューは経路から外れます。

**実行して確認できたこと**: この Durable Object のロジックを、保存領域とアラームを模したモックで動かし、(1) 送信が失敗しても同じ `identifier` で再送されること、(2) 送信中に加わった使用量が失われないこと、(3) 成功後に通し番号が進むことを確かめました。Cloudflare 上での実機の動作と、実際の遅延は未検証です。

## 応用例

使用量の「単位」を決めるのは、設計の中で最も手触りの出る部分です。

- **AI チャット**: 1 メッセージ 1 単位が、ユーザーに伝わりやすい設計です。トークン課金は正確ですが、画面での見せ方に工夫が要ります。
- **画像生成・動画生成**: 処理の重さに応じて重みをつけます。
- **音声の文字起こし・要約**: 録音の分数を単位にします。

```typescript
const OPERATION_WEIGHTS = {
  text: 1,
  image: 5,
  audio_minute: 2,
} as const; // 重みは仮の値です。実際の原価比から決めます

// 例: 画像生成は 5 単位
await buffer.fetch('https://do/add', {
  method: 'POST',
  body: JSON.stringify({ customerId, value: OPERATION_WEIGHTS.image }),
});
```

重みを変えるときは、この定数だけを直せばよく、Meter や Price に手を入れる必要はありません。

## 前払いクレジットという選択肢

公平な課金を実現する方法は、もう一つあります。「100 回分で 500 円」のように先に買ってもらう方式です。どちらが合うかはアプリの配信形態でほぼ決まるので、表に整理します。

<table>
<thead>
<tr><th>観点</th><th>従量課金（Stripe Meter）</th><th>前払いクレジット（消耗型 IAP）</th></tr>
</thead>
<tbody>
<tr><td>収益のタイミング</td><td>後払い（期間の終わりに請求）</td><td>先払い（購入時に確定）</td></tr>
<tr><td>ユーザー心理</td><td>「今月いくらになるか」の不安が出やすい</td><td>金額が先に見える安心感</td></tr>
<tr><td>iOS 単体アプリ</td><td>ガイドライン 3.1.1 の制約で使える場面が限られる</td><td>App Store の標準の仕組みに乗れる</td></tr>
<tr><td>実装の中心</td><td>報告と集計の信頼性</td><td>残高管理・復元・失効の方針</td></tr>
<tr><td>未使用分</td><td>発生しない</td><td>失効や返金の方針が必要</td></tr>
<tr><td>B2B・Web への展開</td><td>請求書払いや API 課金に広げやすい</td><td>Web では別の決済導線が必要</td></tr>
</tbody>
</table>

私の整理では、**iOS アプリの中で完結するデジタル機能は消耗型 IAP のクレジット、Web 版や B2B の API があるなら Stripe Meter** です。アプリ内で消費するデジタルサービスの課金は、原則として In-App Purchase を通す必要があります（[App Store Review Guidelines 3.1.1](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase)）。ただし、地域や時期によって外部決済の扱いは変わってきているため、提出前に最新の条文を確かめていただければと思います。

Web と併売するなら、内部の使用量カウンタを一つにそろえ、アプリはクレジット残高から引き、Web は Meter で後払いにする二本立てが運用しやすい形です。前払いには、購入時点で売上が確定し、API 原価を先に払う側の資金繰りが読みやすくなる利点もあります。

## 運用が始まってから見る 3 つの数字

一つ目は**原価と収益の比率**です。AI API の請求と Meter の従量収益を突き合わせます。警戒ラインは、原価が収益の 4 割を超えたあたりを出発点に、自分のアプリの粗利に合わせて置き直してください。

```typescript
function costRatio(aiApiCost: number, meteredRevenue: number) {
  const ratio = meteredRevenue > 0 ? aiApiCost / meteredRevenue : Infinity;
  return { ratio, status: ratio < 0.4 ? 'healthy' : ratio < 0.6 ? 'warning' : 'critical' } as const;
}
```

二つ目は**無料枠の消化率**です。8 割に達した人へアプリ内で知らせておくと、請求で驚かせずに済み、上位プランへの自然な導線にもなります。

三つ目は**異常値**です。平均の 10 倍を使う人は、熱心なファンか自動化による濫用のどちらかです。Billing Alerts を平均の数倍あたりに張り、Webhook が届いたら使用の時間帯を確かめます。
