環境変数を一つ差し替えて、デプロイが終わるのを待っていた日のことです。確認のためにサイトを開くと、白い画面に「Application error: a client-side exception has occurred」とだけ出ていました。

記事のページでも、トップでも同じです。サーバーのログは静かで、ビルドも成功していました。そこで私は、もう一度デプロイしました。それでも直りませんでした。

**再デプロイは、サーバーを新しくするだけで、すでに配られた古い HTML までは新しくしません。** この記事は、その当たり前に気づくまでの遠回りと、そこから引いた線を書き残したものです。個人開発で Next.js のサイトを Cloudflare Workers に載せている方が、同じ晩を短く済ませられるように、手順とコードを動かして確かめた形で並べます。

## コンソールに並んでいた二行

ブラウザの開発者ツールを開くと、赤い行が二つありました。一つは `__name is not defined`、もう一つは `ChunkLoadError` です。

前者は、見た目には私のコードの不具合のように見えます。ところがネットワークタブを見ると、JS のファイルが一本、404 を返していました。404 の本文は HTML です。それを JS として読み込もうとして、後続の処理が連鎖して止まっていたのです。

どのページを開いても落ちたのは、そのチャンクが共通の部品に入っていたためだと考えています。**欠けたのは一本でも、止まるのは画面全体です。** 最初に見るべきはコードではなく、404 になっているファイルの名前でした。

## 何が起きていたか：古い HTML と新しいチャンクのずれ

ビルドのたびに、JS のファイル名にはハッシュが付きます。新しいビルドでは、古いハッシュのファイルは置かれません。ところが、古い HTML を手元やエッジに持っている人には、古いファイル名がそのまま書かれています。

<table>
<thead>
<tr><th>持っているもの</th><th>呼ぶファイル</th><th>新しいビルドの配信先に</th></tr>
</thead>
<tbody>
<tr><td>デプロイ前に作られた HTML</td><td>古いハッシュのチャンク</td><td>ありません。404 になります</td></tr>
<tr><td>デプロイ後に作られた HTML</td><td>新しいハッシュのチャンク</td><td>あります。正常に読めます</td></tr>
</tbody>
</table>

つまり、問題は新しいビルドの中にはありません。**古い HTML が、新しいビルドの前に、まだ配られていること**が原因です。環境変数やシークレットを変えると、Worker は再デプロイされ、新しいビルド ID になります。その直後は、どうしてもこのずれが起きやすくなります。

ブラウザの手元に古い HTML があるだけなら、ハードリロードで直ります。実際、それで直った日もありました。ところが、直らない日がありました。

## 直感に反していたこと：エッジのキャッシュは、再デプロイで消えない

私は、デプロイすれば古いものは全部入れ替わると思っていました。ところが、Workers の前段で `caches.default` に保存していた HTML は、Worker を再デプロイしても残ります。

だから、ハードリロードしても直らない人が出ます。手元ではなく、エッジが古い HTML を返しているからです。再デプロイを何度繰り返しても、エッジの中身は変わりません。私が最初の晩に再デプロイを繰り返したのは、まさにこの思い込みのせいでした。

最終的に私は、設定ファイルのコメントを一行書き換えて再ビルドを走らせ、あわせて三つの手当てを入れました。アセットを配るための `ASSETS` の結びつきを設定に書くこと、エラー画面を自前で用意すること、そしてエッジのキャッシュにビルドの版を持たせることです。以降は、それぞれのコードです。

## 手当て1：デプロイの直後に、チャンクが全部あるかを確かめる

最初に作ったのは、検知のスクリプトです。HTML を取って、そこから呼ばれている JS を全部拾い、一本ずつ実在を確かめます。人の目でネットワークタブを追うより、デプロイのたびに機械に任せるほうが確実でした。

次のスクリプトは Node 22 で動かして確かめています。ステータスだけでなく content-type も見ているのは、200 で HTML が返ってくる型の失敗があるためです。

```js
// check-chunks.mjs — デプロイ後に、HTML が呼ぶ JS が全部実在するかを確かめる
// 使い方: node check-chunks.mjs https://example.com/ https://example.com/en/
const urls = process.argv.slice(2);
if (urls.length === 0) {
  console.error('usage: node check-chunks.mjs <page-url> [...]');
  process.exit(2);
}

let failed = 0;
for (const page of urls) {
  const res = await fetch(page, { headers: { 'Cache-Control': 'no-cache' } });
  const html = await res.text();
  const found = new Set(
    [...html.matchAll(/(?:src|href)="([^"]*\/_next\/static\/[^"]+\.js[^"]*)"/g)].map((m) => new URL(m[1], page).href),
  );
  console.log(`${page} -> HTTP ${res.status}, x-cache=${res.headers.get('x-cache') ?? '-'}, chunks=${found.size}`);
  for (const chunk of found) {
    const r = await fetch(chunk);
    const type = r.headers.get('content-type') ?? '';
    await r.arrayBuffer();
    const ok = r.status === 200 && /javascript/.test(type);
    if (!ok) {
      failed += 1;
      console.log(`  NG ${r.status} ${type || '(no content-type)'} ${chunk}`);
    }
  }
}
console.log(failed === 0 ? 'OK: すべてのチャンクが JS として返りました' : `FAIL: ${failed} 件のチャンクが読めません`);
process.exit(failed === 0 ? 0 : 1);
```

手元で試すために、チャンクを三本呼ぶ HTML を返すだけのローカルサーバーを立てました。一本は 404、もう一本は 200 で HTML を返すように細工しています。実際の出力は次のとおりです。

```text
http://127.0.0.1:36245/ -> HTTP 200, x-cache=-, chunks=3
  NG 404 text/html http://127.0.0.1:36245/_next/static/chunks/b.js
  NG 200 text/html http://127.0.0.1:36245/_next/static/chunks/c.js
FAIL: 2 件のチャンクが読めません
```

終了コードが 1 になるので、デプロイの最後の工程に置けば、壊れたまま気づかずに終わる事態を避けられます。なお、この検査が見ているのは、取りに行った時点で配られているものです。エッジの古い HTML を拾いたいときは、同じページを二回取って、二回目の `x-cache` が HIT になるのを確かめてから流します。

## 手当て2：キャッシュの HTML に、作ったビルドの版を持たせる

次に、エッジの古い HTML を、再デプロイでは消えない問題として扱いました。やることは単純で、保存するときにビルドの版を一緒に持たせ、返す前に照合します。版が違えば捨てて、作り直します。

```js
// version-guard.mjs — エッジキャッシュの HTML を、作ったビルドの版と照合してから返す
const EDGE = 'public, s-maxage=3600';
const BROWSER = 'public, max-age=0, must-revalidate';

export async function cachedRender(cache, request, render, deployVersion) {
  const hit = await cache.match(request);
  if (hit) {
    if (hit.headers.get('X-Deploy-Version') === deployVersion) {
      const html = await hit.text();
      return reply(html, hit.status, deployVersion, 'HIT');
    }
    await cache.delete(request); // 古いビルドで作った HTML は、再デプロイでは消えない。ここで捨てる
  }
  const fresh = await render(request);
  const html = await fresh.text();
  if (fresh.status === 200) {
    await cache.put(
      request,
      new Response(html, {
        status: 200,
        headers: { 'Content-Type': 'text/html; charset=utf-8', 'Cache-Control': EDGE, 'X-Deploy-Version': deployVersion },
      }),
    );
  }
  return reply(html, fresh.status, deployVersion, 'MISS');
}

function reply(html, status, version, cacheState) {
  return new Response(html, {
    status,
    headers: {
      'Content-Type': 'text/html; charset=utf-8',
      'Cache-Control': BROWSER, // ブラウザには残さない。エッジの寿命とは別に決める
      'X-Deploy-Version': version,
      'X-Cache': cacheState,
    },
  });
}
```

Map で作った偽のキャッシュを渡して、次の四つを確かめました。一回目は MISS で、二回目は HIT になること。版を `v1` から `v2` に変えると、HIT せずに作り直されること。ブラウザ向けの `Cache-Control` が `max-age=0, must-revalidate` になること。500 のような 200 以外の応答は、保存されないこと。いずれも期待どおりに通りました。

ここで私がこだわったのは、エッジとブラウザで寿命を分けた点です。エッジには `s-maxage` で一時間残しますが、ブラウザには残させません。**古い HTML を握る場所を、エッジの一か所に絞っておくためです。** ブラウザにも長く残すと、版を照合する機会そのものを失います。

版の値には、デプロイのたびに必ず変わるものを入れます。私は、ビルド時に埋め込む文字列を使っています。値を更新し忘れると、照合は常に一致してしまい、手当て2が何もしなくなります。

実際の Worker に入れるときは、`cache.put` を `ctx.waitUntil` で包んで、応答を返したあとに保存させるのが定石です。ここでは確かめやすさを優先して、await で書きました。

## 手当て3：エラー画面で、1回だけ自動で再読み込みする

最後は、それでも起きたときの受け皿です。Next.js の `global-error.tsx` を用意して、チャンクの読み込み失敗のときだけ、1回だけ自動で再読み込みさせます。利用者の側で、ハードリロードという操作を要らなくするためです。

判定の部分だけを、別のファイルに切り出しました。画面の部品は React ですが、判定は普通の関数です。切り出したのは、ブラウザを立てずに Node で確かめられるようにするためでした。

```js
// reload-once.mjs — チャンク読み込み失敗のときだけ、1回だけ自動で再読み込みする判定
const PATTERN = /ChunkLoadError|Loading chunk [\w-]+ failed|Failed to fetch dynamically imported module|__name is not defined/;

export function isChunkLoadError(error) {
  const text = `${error?.name ?? ''} ${error?.message ?? ''}`;
  return PATTERN.test(text);
}

// storage は sessionStorage を渡す。直近 windowMs 以内に再読み込み済みなら false（ループ防止）
export function shouldReloadOnce(storage, key, now = Date.now(), windowMs = 60_000) {
  try {
    const last = Number(storage.getItem(key));
    if (last > 0 && now - last < windowMs) return false;
    storage.setItem(key, String(now));
    return true;
  } catch {
    return false; // storage が使えない環境では自動再読み込みしない（無限ループより、ボタン表示のほうが安全）
  }
}
```

これを `global-error.tsx` から呼びます。この画面の部品そのものは、今回の検証では描画していません。確かめたのは、上の判定関数です。

```tsx
'use client';
import { useEffect } from 'react';
import { isChunkLoadError, shouldReloadOnce } from './reload-once.mjs';

export default function GlobalError({ error }: { error: Error & { digest?: string } }) {
  useEffect(() => {
    if (isChunkLoadError(error) && shouldReloadOnce(window.sessionStorage, 'chunk-reload-at')) {
      window.location.reload();
    }
  }, [error]);

  return (
    <html lang="ja">
      <body style={{ padding: 24, fontFamily: 'sans-serif' }}>
        <h1>読み込みに失敗しました</h1>
        <p>サイトが更新された直後は、画面が一時的に読めないことがあります。</p>
        <button onClick={() => window.location.reload()}>再読み込み</button>
      </body>
    </html>
  );
}
```

判定関数は、次の場合を確かめました。`ChunkLoadError` と `__name is not defined` はチャンクの失敗として判定されること。無関係な `TypeError` は判定されないこと。一回目は再読み込みを許し、三十秒後は許さず、七十秒後は再び許すこと。そして `sessionStorage` が例外を投げる環境では、再読み込みしないこと。すべて通りました。

## 落とし穴：直したつもりが、別の事故を呼ぶところ

この三つを入れる過程で、私が気をつけた箇所は四つあります。

### 自動再読み込みの無限ループ

再読み込みしても、まだ古い HTML が返れば、また同じエラーになり、また再読み込みします。時刻を保存して一分以内は再読み込みしないのは、そのためです。ここを省くと、利用者の画面が点滅し続けます。

### sessionStorage が使えない環境

プライベートブラウズや、保存を禁じた設定では、読み書きが例外になります。その場合に「再読み込みする」へ倒すと、ループを止められません。私は、迷ったら再読み込みしない側に倒しました。ボタンが残るので、利用者は自分で押せます。

### 500 などの失敗をキャッシュに保存すること

一度の失敗が、一時間のあいだ全員に配られます。保存するのは 200 のときだけにしました。

### ステータスだけで満足する検知

200 で HTML が返る型の失敗は、ステータスでは見分けられません。content-type まで見るのは、そのためです。

## 設計の線引き：古いチャンクを残す道は、選びませんでした

別の対処として、新しいビルドでも古いチャンクを数世代残しておく道があります。そうすれば、古い HTML を持っている人も、そのまま動かせます。

私はこの道を選びませんでした。配信するファイルが増えて、何世代残すかを管理する手間が増えるからです。それに、古い HTML を配り続けること自体が、本来は避けたい状態でした。**ずれを許して残すより、ずれを見つけて、速やかに入れ替えるほうを選んでいます。** ただし、利用者が多く、デプロイの頻度も高いサイトでは、残す道のほうが合うかもしれません。ここは、お持ちのサイトの事情に合わせて選んでいただければと思います。

## 最後に、次の一手を一つだけ

もし今日、一つだけ試していただけるなら、手当て1の検知スクリプトを、デプロイの最後の工程に置いてみてください。数分で入りますし、ここで一本でも NG が出れば、利用者より先に自分が気づけます。

シークレットを一つ差し替えただけで、サイト全体が読めなくなる日が来るとは、私も思っていませんでした。いまも、デプロイの直後は少しだけ身構えながら、まず検知スクリプトを走らせています。
