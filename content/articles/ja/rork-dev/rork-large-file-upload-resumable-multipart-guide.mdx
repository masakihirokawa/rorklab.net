電車の駅間を想定して、アップロード中の 200MB の動画に機内モードを 10 秒だけ挟んでみた夜がありました。進捗バーは 80% あたりから 0% に戻りました。`fetch + FormData` の一括送信は、切断された時点でそれまでの転送をすべて捨てる作りです。手元の Wi‑Fi では素直に通っていたからこそ、その場で胃が痛くなりました。切断への備えが何もなかったのだと気づいたのは、その夜でした。

大容量アップロードの失敗は、サーバーが落ちるから起きるのではありません。モバイルの前提（切れる、止められる、メモリが足りない）と、素直な実装とが噛み合わないところで起きます。ここでは、その噛み合わせを直す実装を、動くコードと一緒に書き残します。

最初にお伝えしたいのは、いちばん効くのはチャンク分割そのものではなく、**「どこまで届いたか」を端末とサーバーの両方に残しておくこと**だという点です。

## なぜ「ただの fetch + FormData」では本番で失敗するのか

モバイルアプリのファイルアップロードを「PC のブラウザと同じ感覚」で設計すると、ほぼ確実に以下の壁にぶつかります。

**① ネットワークの瞬断は日常的に起こります**。電車の駅間、地下街、建物の中、エレベーター、Wi‑Fi からモバイル回線への切り替え — これらの場面では TCP コネクションが切断されます。一括アップロードは切断のたびに最初からやり直しです。1GB のファイルなら、95% までアップロードしてから切れたら 950MB が無駄になります。

**② iOS はバックグラウンド処理を容赦なく打ち切ります**。ユーザーがアプリをスワイプで閉じなくても、ホームに戻って 30 秒経つと、標準的な URLSession ではリクエストが打ち切られます。`BGTaskScheduler` や `NSURLSession.background` を使わない限り、「バックグラウンドでアップロード継続中」は成り立ちません。

**③ メモリ制約が厳しい**。1GB のファイルを `readAsDataURL` で読み込むとクラッシュします。React Native / Expo でメモリを測ると、フォアグラウンドで使えるメモリは機種によって大きく違います。ファイル全体をメモリに載せる実装は、その時点で避けるべき設計です。

**④ サーバー側にも制限があります**。多くの PaaS（Vercel、Cloudflare Workers、Supabase Edge Functions）は、1 リクエストあたりのボディサイズやタイムアウトに上限があります。Cloudflare Workers は 100MB（Free / Pro プランの場合）、Vercel Serverless は 4.5MB（標準）、API Gateway 経由の Lambda は 10MB。一括 POST では届きません。

この 4 つを同時に解決する設計が、**レジュームアブル（再開可能）+ チャンク分割 + バックグラウンド対応** のアップロード基盤です。

## 3 つの選択肢を比較する — どれを採用するか

レジュームアブル・チャンク転送を実現する手段は主に 3 つあります。それぞれ得意領域が違うので、アプリの性質に合わせて選択します。

- **TUS プロトコル（tus.io）**: HTTP ベースのオープン標準。クライアント実装が各言語で揃っており、サーバーも OSS（tusd）や Supabase Storage で動かせます。任意のチャンクサイズと再開に対応し、並列は拡張仕様の扱いです。**一般用途の万能解です**
- **S3 / R2 Multipart Upload**: AWS S3 の公式仕様。Cloudflare R2 や MinIO など S3 互換ストレージで動く。パートは 5MiB〜5GiB（最後のパートだけ小さくても構いません）、最大 10,000 パート、R2 ならオブジェクトは 5TiB 弱まで扱えます。**クラウドストレージに直接入れる前提のアプリ向けです**
- **Supabase Storage Resumable Upload**: Supabase Storage は裏で TUS を採用しており、JS クライアントから数行で使えます。**Supabase バックエンドを使っているなら最短です**

私の採用基準はシンプルです。**Cloudflare R2 をストレージに使っているなら Multipart Upload 一択**、**Supabase を使っているなら Supabase Storage Resumable**、**自前の API サーバーに入れる必要があれば TUS** — 迷ったらこの順番で決まります。

違いを、再開のしかたと端末側の負担で並べると次のとおりです。

Multipart だけは、再開の記録を端末が持ちます。この記事のコードで uploadId と ETag の永続化に紙幅を割いているのは、そのためです。

## Foundation: 進捗・キャンセル・再開を扱うアップロードコアの設計

どの選択肢を採るにしても、クライアント側の「アップロードコア」は共通化できます。以下の 3 つを担う薄い抽象層を先に作ると、後の実装がとても楽になります。

- **UploadTask**: ファイル 1 つ分のアップロードを表す状態機械です（`idle` / `uploading` / `paused` / `failed` / `completed`）
- **ChunkScheduler**: 大きいファイルをチャンクに分割し、並列度と再試行を管理します
- **ProgressBus**: 進捗・失敗・完了イベントを UI と永続層へ流します

React Native + Expo 環境で Zustand を使った最小のコア実装を示します。これをベースに、後述の TUS / Multipart を差し替えて使います。

```typescript
// store/uploadStore.ts
import { create } from 'zustand';
import AsyncStorage from '@react-native-async-storage/async-storage';

type Status = 'idle' | 'uploading' | 'paused' | 'failed' | 'completed';

export interface MultipartState {
  uploadId: string;
  key: string;
  parts: { PartNumber: number; ETag: string }[]; // 完了済みパート
}

export interface UploadTask {
  id: string;
  fileUri: string;
  fileName: string;
  fileSize: number;
  mimeType: string;
  chunkSize: number;           // バイト単位 (例: 5 * 1024 * 1024)
  uploadedBytes: number;       // 再開時のオフセット
  status: Status;
  serverUploadUrl?: string;    // TUS の Upload URL
  multipart?: MultipartState;  // Multipart の再開に必要な記録
  errorMessage?: string;
  retryCount: number;
}

interface UploadState {
  tasks: Record<string, UploadTask>;
  addTask: (task: UploadTask) => Promise<void>;
  updateProgress: (id: string, uploadedBytes: number) => void;
  setStatus: (id: string, status: Status, error?: string) => void;
  setMultipart: (id: string, multipart: MultipartState) => void;
  hydrateFromStorage: () => Promise<void>;
}

const STORAGE_KEY = 'rork-upload-queue-v1';

export const useUploadStore = create<UploadState>((set, get) => ({
  tasks: {},

  addTask: async (task) => {
    set((s) => ({ tasks: { ...s.tasks, [task.id]: task } }));
    await AsyncStorage.setItem(STORAGE_KEY, JSON.stringify(get().tasks));
  },

  updateProgress: (id, uploadedBytes) => {
    const task = get().tasks[id];
    if (!task) return;
    // 1MB 進むたびに永続化（書き込み頻度を抑える）
    const shouldPersist = uploadedBytes - task.uploadedBytes >= 1024 * 1024;
    set((s) => ({
      tasks: { ...s.tasks, [id]: { ...task, uploadedBytes } },
    }));
    if (shouldPersist) {
      AsyncStorage.setItem(STORAGE_KEY, JSON.stringify(get().tasks));
    }
  },

  setStatus: (id, status, error) => {
    const task = get().tasks[id];
    if (!task) return;
    set((s) => ({
      tasks: {
        ...s.tasks,
        [id]: { ...task, status, errorMessage: error },
      },
    }));
    AsyncStorage.setItem(STORAGE_KEY, JSON.stringify(get().tasks));
  },

  setMultipart: (id, multipart) => {
    const task = get().tasks[id];
    if (!task) return;
    set((s) => ({ tasks: { ...s.tasks, [id]: { ...task, multipart } } }));
    // uploadId と完了パートは再開の命綱なので、毎回すぐ書き込みます
    AsyncStorage.setItem(STORAGE_KEY, JSON.stringify(get().tasks));
  },

  hydrateFromStorage: async () => {
    const raw = await AsyncStorage.getItem(STORAGE_KEY);
    if (!raw) return;
    try {
      const tasks = JSON.parse(raw) as Record<string, UploadTask>;
      // 前回 uploading のまま落ちたタスクは paused として復帰
      Object.values(tasks).forEach((t) => {
        if (t.status === 'uploading') t.status = 'paused';
      });
      set({ tasks });
    } catch (e) {
      console.warn('upload-store hydrate failed', e);
    }
  },
}));
```

なぜ「1MB 進むたびに永続化」なのか — チャンク単位で毎回 AsyncStorage に書き込むと、書き込みが I/O ボトルネックになります。進捗の粒度と書き込み頻度のバランスを取るための選択で、チャンクサイズの 2〜3 割を出発点にして、実機で調整してください。ただし uploadId のような再開の鍵は、この間引きの対象にしません。

## 実装 1: TUS プロトコルでレジューム可能なアップロードを構築する

自前のサーバーや Supabase Storage で TUS を使う場合、React Native では [`tus-js-client`](https://github.com/tus/tus-js-client) がほぼそのまま動きます。以下は 1GB の動画を 5MB チャンクでアップロードする実装例です。

```typescript
// lib/uploadTus.ts
import * as tus from 'tus-js-client';
import * as FileSystem from 'expo-file-system/legacy'; // SDK 53 以前は 'expo-file-system'
import { useUploadStore } from '../store/uploadStore';

// TUS サーバーへ Chunk 単位でアップロード
// 期待する動作: 5MB ごとにサーバーに POST/PATCH → 途中切断でも再開可能
export async function uploadWithTus(
  taskId: string,
  endpoint: string,
  fileUri: string,
  fileName: string,
  mimeType: string,
): Promise<void> {
  const store = useUploadStore.getState();
  const task = store.tasks[taskId];
  if (!task) throw new Error(`task not found: ${taskId}`);

  // Expo 上では Blob を直接扱えないため、ファイルをストリームで読み込む
  const fileInfo = await FileSystem.getInfoAsync(fileUri);
  if (!fileInfo.exists) throw new Error('file missing');

  return new Promise((resolve, reject) => {
    const upload = new tus.Upload(
      // ファイルの渡し方は下の注意を参照（ここは概念を示す仮の記述です）
      {
        uri: fileUri,
        name: fileName,
        type: mimeType,
        size: fileInfo.size,
      } as any,
      {
        endpoint,
        chunkSize: 5 * 1024 * 1024, // 5MB
        retryDelays: [0, 1000, 3000, 5000, 10000], // 指数バックオフ
        metadata: { filename: fileName, filetype: mimeType },
        // サーバー側が応答した Upload-Offset を受け取って進捗計算
        onProgress: (bytesUploaded) => {
          store.updateProgress(taskId, bytesUploaded);
        },
        onSuccess: () => {
          store.setStatus(taskId, 'completed');
          resolve();
        },
        onError: (err) => {
          store.setStatus(taskId, 'failed', err.message);
          reject(err);
        },
        // 途中再開用: 前回の serverUploadUrl があればそこから復帰
        uploadUrl: task.serverUploadUrl,
      },
    );

    // 初回アップロード時に URL を発行 → 永続化
    upload.findPreviousUploads().then((previousUploads) => {
      if (previousUploads.length > 0) {
        upload.resumeFromPreviousUpload(previousUploads[0]);
      }
      store.setStatus(taskId, 'uploading');
      upload.start();
    });
  });
}
```

**期待する動作**: アプリがバックグラウンドから復帰したとき、`tus-js-client` はサーバーに `HEAD` リクエストを投げて「今どこまで受け取ったか」を問い合わせ、そのオフセットから続きを送ります。仮に 700MB 送った時点で切断しても、再開時には 701MB 目から送信されます。

**Expo での注意点**: このコードのファイル引数は、動作を説明するための仮の記述です。`tus-js-client` が React Native でどの入力（Blob や URI）を受け付けるかは、バージョンによって扱いが変わります。採用前にライブラリ側の React Native 向けデモで確かめてください。もう一点、1GB 級のファイルを Blob として丸ごとメモリに載せる方式は避けたいところです。メモリを一定に保ちたいなら、次の Multipart のように範囲を指定して読み出す方式のほうが安全です。

なお、`expo-file-system` の `createUploadTask` は TUS には対応していません。ファイル全体を 1 リクエストで送る API で、後述のとおり別の役割で使います。

## 実装 2: S3 / R2 の Multipart Upload で 5GB ファイルを並列転送する

Cloudflare R2 や AWS S3 に直接アップロードする場合、**クライアントがサーバーを経由せずに直接ストレージに書き込める** のが大きなメリットです。サーバーは事前署名 URL を発行するだけで済み、帯域課金も抑えられます。

実装の流れは以下の 3 ステップです。

- **① Initiate Multipart**: サーバーで `CreateMultipartUpload` を呼び、`uploadId` を取得
- **② Upload Parts**: クライアントが各パート用の事前署名 URL に並列 PUT
- **③ Complete Multipart**: 全パート完了後、`CompleteMultipartUpload` で結合

以下がクライアント側のコア実装です。

```typescript
// lib/uploadMultipart.ts
import * as FileSystem from 'expo-file-system/legacy'; // SDK 53 以前は 'expo-file-system'
import { useUploadStore, MultipartState } from '../store/uploadStore';

interface PartUrl {
  partNumber: number;
  url: string;
}

const PART_SIZE = 5 * 1024 * 1024; // R2 / S3 の最小は 5MiB。最後のパート以外は同じサイズにします
const PARALLELISM = 3;              // 出発点です。回線と機種で計測して動かします

// 再開できる Multipart アップロード
// 期待する動作: 初回は uploadId を発行して保存し、2 回目以降は未完了のパートだけ送る
export async function uploadWithMultipart(
  taskId: string,
  fileUri: string,
  fileName: string,
  apiBaseUrl: string,
  authToken: string,
  shouldStop: () => boolean = () => false, // バックグラウンド実行枠の打ち切り用
): Promise<void> {
  const store = useUploadStore.getState();
  const task = store.tasks[taskId];
  if (!task) throw new Error('task not found');

  const fileInfo = await FileSystem.getInfoAsync(fileUri);
  if (!fileInfo.exists) throw new Error('file missing');
  const totalSize = fileInfo.size;
  const totalParts = Math.ceil(totalSize / PART_SIZE);
  const headers = {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${authToken}`,
  };
  const partBytes = (n: number) =>
    Math.min(n * PART_SIZE, totalSize) - (n - 1) * PART_SIZE;

  try {
    store.setStatus(taskId, 'uploading');

    // Step 1: 保存済みの uploadId があれば initiate を呼び直さない（呼び直すと別のアップロードになります）
    let current: MultipartState | undefined = task.multipart;
    if (!current) {
      const initRes = await fetch(`${apiBaseUrl}/uploads/initiate`, {
        method: 'POST',
        headers,
        body: JSON.stringify({ fileName, size: totalSize }),
      });
      if (!initRes.ok) throw new Error(`initiate failed: ${initRes.status}`);
      const init = (await initRes.json()) as { uploadId: string; key: string };
      current = { uploadId: init.uploadId, key: init.key, parts: [] };
      store.setMultipart(taskId, current);
    }
    const session: MultipartState = current;

    // Step 2: まだ終わっていないパートの署名付き URL だけを取り直す（前回の URL は期限切れかもしれません）
    const done = new Set(session.parts.map((p) => p.PartNumber));
    const pendingNumbers: number[] = [];
    for (let n = 1; n <= totalParts; n++) if (!done.has(n)) pendingNumbers.push(n);

    let uploadedBytes = session.parts.reduce((sum, p) => sum + partBytes(p.PartNumber), 0);
    store.updateProgress(taskId, uploadedBytes);

    if (pendingNumbers.length > 0) {
      const partUrlsRes = await fetch(`${apiBaseUrl}/uploads/part-urls`, {
        method: 'POST',
        headers,
        body: JSON.stringify({ uploadId: session.uploadId, key: session.key, partNumbers: pendingNumbers }),
      });
      if (!partUrlsRes.ok) throw new Error(`part-urls failed: ${partUrlsRes.status}`);
      const { parts } = (await partUrlsRes.json()) as { parts: PartUrl[] };

      async function uploadPart(part: PartUrl): Promise<void> {
        const start = (part.partNumber - 1) * PART_SIZE;
        const size = partBytes(part.partNumber);

        // 指定範囲だけを読み出します（ファイル全体は読みません）
        const base64 = await FileSystem.readAsStringAsync(fileUri, {
          encoding: FileSystem.EncodingType.Base64,
          position: start,
          length: size,
        });
        const res = await fetch(part.url, {
          method: 'PUT',
          body: decodeBase64ToUint8Array(base64) as any,
        });
        if (!res.ok) throw new Error(`part ${part.partNumber} failed: ${res.status}`);

        const etag = res.headers.get('ETag')?.replace(/"/g, '');
        if (!etag) throw new Error(`part ${part.partNumber}: ETag missing`);

        // 1 パート終わるたびに記録 → アプリが落ちても、ここまでは失われません
        session.parts.push({ PartNumber: part.partNumber, ETag: etag });
        store.setMultipart(taskId, { ...session, parts: [...session.parts] });
        uploadedBytes += size;
        store.updateProgress(taskId, uploadedBytes);
      }

      const queue = [...parts];
      const workers = Array.from({ length: PARALLELISM }, async () => {
        while (queue.length > 0 && !shouldStop()) {
          const next = queue.shift();
          if (!next) return;
          await retryWithBackoff(() => uploadPart(next), 3);
        }
      });
      await Promise.all(workers);
    }

    // 打ち切られた場合は paused で終えて、次の機会に続きから送ります
    if (session.parts.length < totalParts) {
      store.setStatus(taskId, 'paused');
      return;
    }

    // Step 3: Complete
    const sorted = [...session.parts].sort((a, b) => a.PartNumber - b.PartNumber);
    const completeRes = await fetch(`${apiBaseUrl}/uploads/complete`, {
      method: 'POST',
      headers,
      body: JSON.stringify({ uploadId: session.uploadId, key: session.key, parts: sorted }),
    });
    if (!completeRes.ok) throw new Error(`complete failed: ${completeRes.status}`);

    store.setStatus(taskId, 'completed');
  } catch (e: any) {
    store.setStatus(taskId, 'failed', e.message);
    throw e;
  }
}

function decodeBase64ToUint8Array(base64: string): Uint8Array {
  const binString = atob(base64);
  const bytes = new Uint8Array(binString.length);
  for (let i = 0; i < binString.length; i++) bytes[i] = binString.charCodeAt(i);
  return bytes;
}

async function retryWithBackoff<T>(fn: () => Promise<T>, max: number): Promise<T> {
  let lastErr: any;
  for (let i = 0; i < max; i++) {
    try {
      return await fn();
    } catch (e) {
      lastErr = e;
      await new Promise((r) => setTimeout(r, 500 * Math.pow(2, i)));
    }
  }
  throw lastErr;
}
```

**期待する動作**: 1GB のファイルは 205 個ほどの 5MiB パートに分かれ、3 並列で送られます。途中でアプリが落ちても、再開時は保存済みの `uploadId` と完了パートの ETag を読み戻し、足りないパートだけを送ります。全パートがそろったら `CompleteMultipartUpload` で 1 つのオブジェクトに結合されます。

初版のコードには、この再開の記録がありませんでした。再開のたびに `initiate` を呼び直すと、別の `uploadId` が発行され、送り済みのパートはサーバーに残ったまま孤児になります。Multipart で「再開できる」と言えるのは、`uploadId` と ETag を端末が持っているあいだだけです。

**並列度 3 は出発点です**。接続を増やしても回線そのものが太くなるわけではないので、モバイル回線では頭打ちになる場面があります。Wi‑Fi のときだけ引き上げる、`NetInfo` の接続種別で分岐する、といった形で、必ず自分の端末と回線で計測して決めてください。

## iOS のバックグラウンド転送 — 続けてくれるものと、拾い直すものを分ける

フォアグラウンドで始めた転送を、ユーザーがホームに戻ったあとも続けたいと考える方は多いはずです。私は、仕組みごとの役割を混ぜて考えると設計がぶれやすいのだと、感じています。

<table>
<thead><tr><th>仕組み</th><th>役割</th><th>向いている使い方</th><th>向いていない使い方</th></tr></thead>
<tbody>
<tr><td><code>expo-file-system</code> の <code>createUploadTask</code>（iOS の BACKGROUND セッション）</td><td>転送そのものを OS が肩代わりする</td><td>署名付き URL へ 1 ファイルを 1 リクエストで PUT する</td><td>パート分割や途中再開（ファイル全体を送る API です）</td></tr>
<tr><td><code>expo-background-task</code></td><td>OS が許す短い実行枠で、未完了タスクを拾い直す</td><td><code>uploadId</code> が残るタスクの続きを数パート送る</td><td>長時間の転送そのもの</td></tr>
<tr><td>この記事の Multipart 実装</td><td>アプリが前面にいる間の並列転送</td><td>大容量で、再開が必要なアップロード</td><td>アプリが閉じられた後も走らせ続けること</td></tr>
</tbody>

選び方は、ファイルの大きさと「失敗したらやり直しで構わないか」で決まります。たとえば数百 MB までなら、署名付き URL への 1 本の PUT をバックグラウンドセッションに任せるほうが、実装も小さく、閉じても続きます。`createUploadTask` の BACKGROUND セッションは、アプリが後ろに回っても動き、成功か取り消しまで再試行を続ける設計です（Expo の型定義のコメントによります）。代わりに、途中で切れたらそのファイルは頭からやり直しです。

一方で、1GB を超えるファイルや、回線が不安定な環境では、Multipart の再開記録が効いてきます。その続きを、アプリが後ろに回ったあとで拾い直すのが、次の BackgroundTask です。

なお、以前の版で使っていた `expo-background-fetch` は、Expo SDK 53 で `expo-background-task` に置き換えられ、非推奨になっています。iOS では BGTaskScheduler、Android では WorkManager が使われます。

```typescript
// lib/backgroundUpload.ts
import * as BackgroundTask from 'expo-background-task';
import * as TaskManager from 'expo-task-manager';
import { useUploadStore } from '../store/uploadStore';
import { uploadWithMultipart } from './uploadMultipart';

const TASK_NAME = 'rork-resumable-upload';
const TIME_BUDGET_MS = 20 * 1000; // 実行枠は短く打ち切られます。余裕を持って自分から止めます

// 期待する動作: OS が許したタイミングで起動し、uploadId が残っているタスクを数パートずつ進める
TaskManager.defineTask(TASK_NAME, async () => {
  try {
    await useUploadStore.getState().hydrateFromStorage();
    const tasks = useUploadStore.getState().tasks;
    const pending = Object.values(tasks).filter(
      (t) => (t.status === 'paused' || t.status === 'failed') && t.multipart,
    );

    const deadline = Date.now() + TIME_BUDGET_MS;
    const token = await getAuthToken(); // expo-secure-store から取得
    for (const task of pending) {
      if (Date.now() > deadline) break;
      try {
        await uploadWithMultipart(
          task.id,
          task.fileUri,
          task.fileName,
          process.env.EXPO_PUBLIC_API_URL!,
          token,
          () => Date.now() > deadline,
        );
      } catch (e) {
        console.warn('bg upload failed', task.id, e);
      }
    }
    return BackgroundTask.BackgroundTaskResult.Success;
  } catch (e) {
    return BackgroundTask.BackgroundTaskResult.Failed;
  }
});

export async function registerBackgroundUpload(): Promise<void> {
  await BackgroundTask.registerTaskAsync(TASK_NAME, {
    minimumInterval: 15, // 分単位の目安です。実際の起動間隔は OS が決めます
  });
}

async function getAuthToken(): Promise<string> {
  // 省略: expo-secure-store から JWT を取り出す実装
  return '';
}
```

**iOS が保証しないこと**: BackgroundTask で登録した処理は、iOS が「この時間帯なら実行してよい」と判断したときに呼ばれます。使用パターン、電池の状態、回線の状態に左右されるため、「いま続きを送れ」と命じることはできません。ユーザーがアプリを強制終了した場合は、起動されないこともあります。だからこそ、このタスクは「長い転送を担うもの」ではなく、`shouldStop` で自分から区切れる「短い続き」として設計しています。

**本当に切れ目のない転送が必要なら**、`URLSessionConfiguration.background` を直接扱うネイティブモジュールが必要です。Expo の `createUploadTask` が前述のとおり 1 ファイル 1 リクエストの範囲を受け持ち、それ以上は `react-native-background-upload` のような既存モジュールか、自前のネイティブ実装を検討することになります。採用する場合は、メンテナンスの状況と、お使いの Expo SDK への対応を先に確かめてください。

## ユーザー体験: 進捗表示・キャンセル・エラー復旧の UI 設計

転送の技術的な仕組みが動いても、ユーザーには「今何が起きているか」が伝わらないと離脱されます。以下は Zustand ストアと繋いだ進捗 UI の実装例です。

```tsx
// components/UploadProgressList.tsx
import React from 'react';
import { View, Text, Pressable, StyleSheet } from 'react-native';
import { useUploadStore, UploadTask } from '../store/uploadStore';

export function UploadProgressList() {
  const tasks = useUploadStore((s) => Object.values(s.tasks));

  if (tasks.length === 0) return null;

  return (
    <View style={styles.container}>
      {tasks.map((task) => (
        <UploadRow key={task.id} task={task} />
      ))}
    </View>
  );
}

function UploadRow({ task }: { task: UploadTask }) {
  const percent = Math.min(100, (task.uploadedBytes / task.fileSize) * 100);
  const setStatus = useUploadStore((s) => s.setStatus);

  const statusLabel = {
    idle: '待機中',
    uploading: `アップロード中 ${percent.toFixed(0)}%`,
    paused: '一時停止 — タップで再開',
    failed: `失敗 — ${task.errorMessage ?? ''}`,
    completed: '完了',
  }[task.status];

  return (
    <Pressable
      onPress={() => {
        if (task.status === 'paused' || task.status === 'failed') {
          // 再開トリガー
          setStatus(task.id, 'uploading');
        }
      }}
      style={styles.row}
    >
      <Text style={styles.fileName} numberOfLines={1}>
        {task.fileName}
      </Text>
      <View style={styles.barBg}>
        <View style={[styles.barFill, { width: `${percent}%` }]} />
      </View>
      <Text style={styles.status}>{statusLabel}</Text>
    </Pressable>
  );
}

const styles = StyleSheet.create({
  container: { padding: 16, gap: 12 },
  row: { gap: 6 },
  fileName: { fontSize: 14, fontWeight: '600' },
  barBg: { height: 6, backgroundColor: '#eee', borderRadius: 3 },
  barFill: { height: 6, backgroundColor: '#4F7BFF', borderRadius: 3 },
  status: { fontSize: 12, color: '#666' },
});
```

**見落とされがちだが大事な配慮**:

- **アプリ起動時のレジューム確認**: 前回 `uploading` のまま落ちたタスクは、起動時に `paused` へ落としたうえで「再開しますか？」と尋ねます。自動で再開すると、モバイル回線で大量の転送が走り、通信量の事故につながるおそれがあります
- **キャンセル時のクリーンアップ**: `AbortMultipartUpload` を呼ばないと、未完了のパートがストレージに残り続けます。R2 は既定で 7 日後に自動中止されますが、その間は保存量に数えられます。キャンセル時は、サーバー経由で必ず中止 API を呼びます
- **Wi‑Fi 限定モード**: 設定に「Wi‑Fi のときだけアップロード」を用意します。`NetInfo.fetch()` で接続種別を確認し、モバイル回線では `paused` に留めます

関連記事として、[Rork アプリで画像とメディアのネットワーク通信をデバッグする手順](/articles/rork-basics/rork-network-api-request-debug-guide) も合わせて読むと、「アップロードが遅い原因がコードではなくサーバー側にある」ケースの切り分けに役立ちます。

## よくある落とし穴 — 4 つの起こりやすい障害

実装を追っていて、足を取られやすい場所を 4 つ挙げます。

**① メモリ: チャンク読み込みの Base64 が積み上がる**

`FileSystem.readAsStringAsync` で Base64 を受け取ると、バイナリの約 4/3 倍の文字列が JS ヒープに乗ります。5MiB のパートなら、文字列とバイト列を合わせて 1 パートあたり十数 MB、3 並列で概算 35MB 前後です。ファイル全体を読むわけではないので 1GB でも一定に収まりますが、並列度とパートサイズを同時に上げると、この数字は素直に増えます。パートを送り終えたら参照を手放し、`Promise.all` に積む件数も小さく保ちます。

**② 並列度: 多ければ速いわけではない**

前述のとおり、弱い電波で並列度を上げても、全体の時間が縮むとは限りません。`NetInfo` の接続種別（Wi‑Fi かモバイルか）で並列度を切り替え、計測して決めるのが堅実です。

**③ 低電力モード: バックグラウンドの実行機会が減る**

iOS の低電力モードは、電池が 20% を切ると提案され、バックグラウンドの更新などの活動を抑えます。強制終了されるわけではありませんが、BackgroundTask が呼ばれる機会は確実に減ります。`expo-battery` の `getPowerStateAsync` で `lowPowerMode` を見て、「続きは電源につないだときに送ります」と画面で伝えておくと、離脱を抑えられます。

**④ Android: フォアグラウンドサービスの種別宣言**

Android 14 以降は、フォアグラウンドサービスに種別の宣言が必要です。データ転送なら `dataSync` 種別と `FOREGROUND_SERVICE_DATA_SYNC` 権限を使います。アプリが閉じられたあとも送り続けたい場合は、`react-native-background-actions` の `dataSync` タイプを使うか、`WorkManager` をネイティブで呼びます。Expo EAS では、`app.json` の Android の権限に `FOREGROUND_SERVICE_DATA_SYNC` を追加してください。

どれも、テストのファイルサイズが小さいあいだは表に出てこない種類の問題です。最初の実装で押さえておくほうが、あとから直すよりはるかに軽く済みます。

## サーバー側の実装要点 — 4 つのエンドポイントを最小構成で

ここまでのクライアントは、4 つの API を呼ぶ前提で書いてきました。Cloudflare Workers + Hono + R2 バインディングの最小実装を示します。既存の API に追加し、`wrangler.toml` で `R2_BUCKET` バインディングを繋げば動きます。

```typescript
// api/uploads.ts (Cloudflare Workers + Hono)
import { Hono } from 'hono';
import { AwsClient } from 'aws4fetch';

type Env = {
  R2_BUCKET: R2Bucket;
  R2_ACCOUNT_ID: string;
  R2_ACCESS_KEY_ID: string;
  R2_SECRET_ACCESS_KEY: string;
  R2_BUCKET_NAME: string;
};

const MAX_SIZE = 5 * 1024 * 1024 * 1024; // アプリで扱う上限（R2 の上限ではなく、こちらで決める値です）
const MAX_PARTS = 10000;                  // R2 / S3 のパート数の上限

const app = new Hono<{ Bindings: Env }>();

// 1. Multipart 開始: uploadId とオブジェクトキーを返す
app.post('/uploads/initiate', async (c) => {
  const { fileName, size } = await c.req.json<{ fileName: string; size: number }>();
  if (!Number.isFinite(size) || size <= 0 || size > MAX_SIZE) {
    return c.json({ error: 'invalid size' }, 400);
  }
  // ファイル名はそのままキーに使わず、安全な文字だけに絞ります
  const safeName = String(fileName).replace(/[^\w.\-]+/g, '_').slice(0, 120);
  const key = `u/${crypto.randomUUID()}/${safeName}`;
  const multipart = await c.env.R2_BUCKET.createMultipartUpload(key);
  // 本番では、ここで size・key・ユーザー ID を DB に保存し、complete で突き合わせます
  return c.json({ uploadId: multipart.uploadId, key });
});

// 2. 未完了パートの事前署名 URL を発行（有効期限 1 時間）
app.post('/uploads/part-urls', async (c) => {
  const { uploadId, key, partNumbers } = await c.req.json<{
    uploadId: string;
    key: string;
    partNumbers: number[];
  }>();
  if (
    !Array.isArray(partNumbers) ||
    partNumbers.length === 0 ||
    partNumbers.length > MAX_PARTS ||
    partNumbers.some((n) => !Number.isInteger(n) || n < 1 || n > MAX_PARTS)
  ) {
    return c.json({ error: 'invalid parts' }, 400);
  }

  const aws = new AwsClient({
    accessKeyId: c.env.R2_ACCESS_KEY_ID,
    secretAccessKey: c.env.R2_SECRET_ACCESS_KEY,
    service: 's3',
    region: 'auto',
  });

  const endpoint = `https://${c.env.R2_ACCOUNT_ID}.r2.cloudflarestorage.com`;
  const parts = await Promise.all(
    partNumbers.map(async (n) => {
      const url = new URL(`${endpoint}/${c.env.R2_BUCKET_NAME}/${key}`);
      url.searchParams.set('partNumber', String(n));
      url.searchParams.set('uploadId', uploadId);
      url.searchParams.set('X-Amz-Expires', '3600'); // 有効期限は URL 側に持たせます
      const signed = await aws.sign(url.toString(), {
        method: 'PUT',
        aws: { signQuery: true },
      });
      return { partNumber: n, url: signed.url };
    }),
  );
  return c.json({ parts });
});

// 3. 全パート完了後に Multipart を結合する
app.post('/uploads/complete', async (c) => {
  const { uploadId, key, parts } = await c.req.json<{
    uploadId: string;
    key: string;
    parts: { PartNumber: number; ETag: string }[];
  }>();
  const multipart = c.env.R2_BUCKET.resumeMultipartUpload(key, uploadId);
  const object = await multipart.complete(
    parts.map((p) => ({ partNumber: p.PartNumber, etag: p.ETag })),
  );
  return c.json({ ok: true, key: object.key, size: object.size });
});

// 4. クライアントのキャンセル経路: 未完了 Multipart を中止する
app.post('/uploads/abort', async (c) => {
  const { uploadId, key } = await c.req.json<{ uploadId: string; key: string }>();
  const multipart = c.env.R2_BUCKET.resumeMultipartUpload(key, uploadId);
  await multipart.abort();
  return c.json({ ok: true });
});

export default app;
```

**R2 のネイティブバインディングと aws4fetch を併用する理由**。R2 の Workers バインディングは `createMultipartUpload` / `resumeMultipartUpload` を直接提供しますが、事前署名 URL の発行機能はありません。クライアントが Worker を経由せずにパートを PUT するには事前署名 URL が必要なので、そこだけ `aws4fetch` で S3 互換 REST に SigV4 署名をかけます。開始・完了・中止はバインディング側のほうが速く、簡潔です。

R2 の Multipart では、**最後のパート以外はすべて同じサイズ**にする決まりがあります。クライアントが `PART_SIZE` を固定している理由はここにもあります。アプリの更新でパートサイズを変えるときは、進行中のアップロードを壊さないよう、`multipart` の記録にパートサイズも持たせてください。

**認証を必ず追加します**。これらのルートは、Bearer トークン（JWT、Supabase セッションなど、お使いのもの）を検証するミドルウェアで保護します。未認証で公開すると、誰でも Multipart を開始でき、ストレージ予算を消費されます。`complete` と `abort` では、`uploadId` と `key` が、そのユーザーの `initiate` で発行されたものかも照合してください。

## リリース前のテストシナリオ

アップロードは、「会社の Wi‑Fi で動いたからリリース」が通用しない領域です。リリース前に回しておきたいテストを、期待する結果とあわせて並べます。

**① Network Link Conditioner (iOS) / Chrome DevTools のスロットル**: 「Very Bad Network」（パケットロス 1%、遅延 500ms）でも、どのファイルサイズでも最終的に完了すること。時間がかかるのは構いませんが、失敗で終わるのは不合格です。

**② 機内モードのオン・オフ**: 200MB のアップロードを始め、進捗 30% で機内モードを 10 秒だけオンにして戻します。自動で再開し、0 ではなく保存済みのパートの続きから進むこと。

**③ 強制終了からの復帰**: 500MB のアップロードを 50% まで進め、アプリスイッチャーから強制終了します。再起動すると、タスクは `paused` で表示され、タップすると完了済みのパートを飛ばして続きから送られること。ここで `initiate` が再度呼ばれていたら、`uploadId` の保存が効いていません。

**④ バックグラウンドの挙動**: 方式ごとに期待が違います。BACKGROUND セッションの PUT は、ホームに戻ってもそのまま完了すること。BackgroundTask 経由の Multipart は、OS が実行枠を与えた分だけ進みます。「20 分後に完了している」ことまでは保証されないので、フォアグラウンドに戻ったときに `UploadProgressList` が正しい進捗を表示し、そこから続けられることを確かめます。

**⑤ キャンセルの取りこぼし**: 10 ファイルを、ばらばらの進捗でキャンセルします。ストレージ側で未完了の Multipart が 0 件であること。残っていれば、`abort` が呼ばれていません。

**⑥ 大容量ストレステスト**: アプリで扱い得る最大サイズ（たとえば 2GB の 4K 動画）を、iOS と Android、Wi‑Fi と 4G/5G の 4 条件で試します。完了時間・失敗回数・ピークメモリを記録しておくと、本番で監視する指標の初期値になります。

①〜⑤ は Maestro や Detox で CI に載せられると理想的ですが、載せられないあいだは、リリースのたびに手動で回すだけでも退行を拾う網になります。

## 本番運用チェックリスト

レジューム対応のアップロードを本番に出す前に、確認しておきたい項目です。多いので、リリース前のスプリントで 1 項目ずつ潰していくのがおすすめです。

- **サーバー側**: 未完了の `uploadId` を放置していないか。R2 は既定で 7 日後に自動中止しますが、もっと短くしたいなら、ライフサイクルの設定か、定期的に `abort` を呼ぶ Cron を用意します
- **サーバー側**: パート番号が 1〜10,000 の範囲かを検証しているか（範囲外は拒否されます）
- **サーバー側**: 完了したオブジェクトのサイズが、`initiate` で申告された値と一致するかを確かめているか
- **クライアント**: 再開のたびに署名付き URL を取り直しているか（有効期限の 1 時間を過ぎた URL は使えません）
- **クライアント**: アプリ起動時に `hydrateFromStorage` を呼び、未完了タスクを復元しているか
- **クライアント**: `uploadId` と完了パートの ETag を、1 パートごとに永続化しているか
- **クライアント**: キャンセル時に `abort` を呼んでいるか
- **UX**: 「アップロード中は閉じないでください」ではなく、閉じても続くかどうかを、方式に合わせて正確に伝えているか
- **UX**: 失敗時の文言が「再試行してください」で終わっていないか（「Wi‑Fi に接続してから再開します」など、次の行動を示します）
- **監視**: Sentry / Firebase Crashlytics に「完了率」「所要時間」「失敗理由別の分布」を出しているか
- **監視**: サーバー側で `uploadId` ごとの進捗を追い、1 時間以上動きがないものを自動で中止しているか

関連して、アプリ本体を軽くする観点では [Rork アプリのバイナリサイズを切り分ける手順](/articles/rork-dev/rork-app-bundle-size-reduction-guide) も合わせてご覧ください。アップロード機能を足すと依存パッケージが増えがちで、バイナリサイズも並行して見ていく必要があります。Cloudflare R2 を使う場合は [Rork × Cloudflare R2 のファイルストレージ実装ガイド](/articles/rork-dev/rork-cloudflare-r2-file-storage-guide) に、事前署名 URL を発行するサーバー側の最小実装が載っています。

**再開できるかどうかは、記録を誰が持っているかで決まります。** TUS ならサーバーが、Multipart なら端末が持っています。

まずは、手元のアプリで `uploadId` を保存しているかどうかを確かめてみてください。保存していなければ、強制終了のテスト（③）を 1 回回すだけで、その場で結果が分かります。
