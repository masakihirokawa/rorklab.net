浮世絵の壁紙アプリに、新しい作品を67点まとめて追加した日のことです。2026年9月11日、ID で言えば 1353 から 1419 まででした。画像をストレージへ上げ、件数の上限を書き換えてサーバーへ送り、アプリを開いて新着の並びに新しい作品が出ていることを確かめました。

そこで手を止めてしまったのが、いま思えば失敗の始まりでした。絵師で絞り込むと、追加した67点は1枚も出てこなかったのです。新着にも、全体の一覧にも出ています。それなのに、絞り込みの画面にだけいませんでした。

原因は単純でした。上げたのは件数の上限だけで、カテゴリごとの ID 一覧のファイルを配り忘れていたのです。エラーは一つも出ていません。アプリも落ちていません。だからこそ、気づくのが遅れました。

**数を増やす変更と、居場所を増やす変更は、同じ便で送ります。** 個人開発で壁紙アプリを長く続けてきて、いちばん地味で、いちばん効いた線引きがこれでした。Rork で作る Expo のアプリでも、カタログをサーバーから受け取る構成なら同じ穴があります。その塞ぎ方を、サーバー側とアプリ側の両方から書き残します。

## 何が起きていたのか

私の壁紙アプリでは、サーバーが二種類の答えを返しています。一つは設定の答えで、そこに「いま配っている壁紙の最大 ID」、つまり件数の上限が入っています。アプリはこの値までの ID を順に並べて、全体の一覧と新着を作ります。

もう一つがカテゴリの答えです。カテゴリごとに ID を並べたテキストファイルがサーバーにあり、`category_list.php` がカテゴリ番号とファイル名の対応表を持っています。アプリが `?category=32` のように聞くと、対応するファイルを読み、カンマ区切りの ID を返します。

ここで効いてくるのが、カテゴリの答えにかかる**範囲の絞り込み**です。サーバーはファイルの中の ID のうち、最小 ID 以上・上限以下のものだけを返します。まだ画像を上げていない ID を、アプリに見せないための仕組みです。

あの日の状態を並べると、こうなります。

- 上限: 1419 に更新済み（全体の一覧と新着には 1353〜1419 が出ます）
- カテゴリのファイル: 1352 までしか入っていない旧版のまま
- 結果: 絞り込みの答えに新しい ID が一つも含まれない状態

ファイルそのものが無い場合や、対応表に登録していないカテゴリを聞かれた場合はどうなるのか。サーバーは固定の既定値「1」を返して終わります。アプリを落とさないための、ごく普通の安全策です。その安全策が、異常をきれいに隠してくれていました。

## 直感と逆だった、配る順番の話

私の場合は、最初「上限とカテゴリを同時に上げないと危ない」と考えていました。ところが範囲の絞り込みを読み直して、考えが変わりました。**カテゴリのファイルは先に配っても安全**なのです。

上限より大きい ID は、ファイルに書いてあってもサーバーが落とします。つまりカテゴリを先に配った時点では、新しい ID はどこにも出ません。そのあと上限を上げた瞬間に、全体の一覧と絞り込みの両方へ同時に現れます。

逆の順番、上限を先に上げた場合だけが危険です。上限とカテゴリのあいだに隙間ができ、その時間がそのまま「絞り込みから消えている時間」になります。私の場合は、その隙間を作ったまま作業を終えていました。

整理すると、途中のどの時点で止まっても壊れない順番はこうなります。

1. 画像をストレージへ上げます（上限より上なので、まだ誰にも見えません）
2. カテゴリのファイルと対応表を配ります（範囲の外なので、まだ見えません）
3. 判定スクリプトを通してから、上限を上げます（ここで初めて全部が同時に見えます）
4. キャッシュを通り越して、オリジンの答えを数えます

手順 3 の前に機械の判定を挟むのが、今回いちばん足したかった部分です。

## 上限を上げる前の判定スクリプト

上限を上げる前に、次の三つを確かめます。置いたのに対応表に無いファイル。対応表にあるのに置いていないファイル。そして、新しく見えるようになる ID が、どれか一つ以上のカテゴリに入っているか。

```python
#!/usr/bin/env python3
"""上限（wallpaper_num）を上げる前に、新しい ID がカテゴリに入っているかを確かめる。

使い方: python3 preflight_bump.py <アプリのディレクトリ> <今の上限> <新しい上限>
exit 0 = 上げてよい / exit 1 = 先にカテゴリ側を直す
"""
import re
import sys
from pathlib import Path

SKIP = {"popular"}  # 人気順など「全件を含まない」一覧は判定に使わない


def read_ids(path: Path) -> set[int]:
    return {int(t) for t in re.split(r"[^0-9]+", path.read_text()) if t}


def registered_files(php: Path) -> set[str]:
    # $categoryFiles = [ 1 => '1_ad_1780_to_1804', ... ]; の右辺だけを拾う
    block = re.search(r"\$categoryFiles\s*=\s*\[(.*?)\];", php.read_text(), re.S)
    if not block:
        sys.exit(f"NG  {php.name} に $categoryFiles が見つかりません")
    return set(re.findall(r"=>\s*'([^']+)'", block.group(1)))


def main(app_dir: str, old_num: int, new_num: int) -> int:
    root = Path(app_dir)
    cat_dir = root / "categories"
    files = {p.stem: p for p in cat_dir.glob("*.txt") if p.stem not in SKIP}
    registered = registered_files(root / "category_list.php")
    problems = []

    # 1) 置いたのに登録していない／登録したのに置いていない
    for stem in sorted(set(files) - registered):
        problems.append(f"未登録: categories/{stem}.txt は category_list.php に無い")
    for stem in sorted(registered - set(files)):
        problems.append(f"未配置: {stem}.txt が categories/ に無い（既定の答えが返る）")

    # 2) 新しく見えるようになる ID が、どこかのカテゴリに入っているか
    covered: set[int] = set()
    for stem in registered & set(files):
        covered |= read_ids(files[stem])
    new_ids = range(old_num + 1, new_num + 1)
    orphans = [i for i in new_ids if i not in covered]
    if orphans:
        head = ", ".join(map(str, orphans[:10]))
        problems.append(f"どのカテゴリにも無い ID: {len(orphans)} 件（{head} …）")

    for p in problems:
        print("NG ", p)
    if problems:
        print("→ 上限はまだ上げません。カテゴリ側を直してから再実行してください")
        return 1
    print(f"OK  {len(new_ids)} 件すべてがカテゴリに入っています。上限を {new_num} にしてよい状態です")
    return 0


if __name__ == "__main__":
    if len(sys.argv) != 4:
        sys.exit(__doc__)
    sys.exit(main(sys.argv[1], int(sys.argv[2]), int(sys.argv[3])))
```

小さな模擬ディレクトリで、わざと三つの穴を開けて流すと、次のように止まります。

```text
NG  未登録: categories/9_extra.txt は category_list.php に無い
NG  未配置: 3_new.txt が categories/ に無い（既定の答えが返る）
NG  どのカテゴリにも無い ID: 1 件（12 …）
→ 上限はまだ上げません。カテゴリ側を直してから再実行してください
```

`popular` を判定から外しているのには理由があります。人気順の一覧は「全件の中から選んだ一部」なので、そこに入っているだけで「居場所がある」と数えると、どの絞り込みにも出ない作品を見逃します。全件を分類するカテゴリだけで判定するのです。

もう一つ、この判定は**上限を書き換えるスクリプトの手前**で呼ぶ形を推奨します。別のコマンドとして覚えておくだけだと、急いでいる日ほど飛ばしてしまうからです。私自身は、追加作業の手順書に「上限と一覧を一組で上げる」と書き、配信後にキャッシュを避けて件数を照らす確認までを一続きにしています。

## アプリ側で、黙った既定値を見分ける

サーバーをどれだけ整えても、配り忘れはいつか起きます。そのとき、アプリが既定値の「1」をそのまま受け取って、1番の壁紙を1枚だけ並べてしまうのが、いちばん気づきにくい壊れ方です。

Rork で作った Expo のアプリなら、カテゴリの取得を一か所に集めて、答えの種類を分けておくと扱いやすくなります。

```ts
// lib/catalog.ts — カテゴリの ID 一覧を受け取り、「黙って返された既定値」を見分ける
export const SERVER_FALLBACK = "1"; // サーバーがファイルを読めなかったときに返す固定の答え

export type CategoryResult =
  | { kind: "ok"; ids: number[] }
  | { kind: "fallback"; reason: string } // 一覧が無い・空・未登録のどれか
  | { kind: "error"; reason: string };

export function parseIdList(raw: string): number[] {
  // "1060, 1061, 1062" も改行区切りも受ける。数字以外はすべて区切りとして扱う
  return raw
    .split(/[^0-9]+/)
    .filter((t) => t.length > 0)
    .map((t) => Number.parseInt(t, 10))
    .filter((n) => Number.isSafeInteger(n) && n > 0);
}

export function classify(raw: string, maxId: number): CategoryResult {
  const body = raw.trim();
  if (body === SERVER_FALLBACK) {
    return { kind: "fallback", reason: "server returned the fixed fallback" };
  }
  const ids = parseIdList(body);
  if (ids.length === 0) return { kind: "fallback", reason: "empty list" };
  // 上限より大きい ID は、まだ画像が無い可能性があるので表示から外す
  const visible = maxId > 0 ? ids.filter((id) => id <= maxId) : ids;
  return visible.length > 0
    ? { kind: "ok", ids: visible }
    : { kind: "fallback", reason: "all ids above maxId" };
}

export async function fetchCategory(
  baseUrl: string,
  categoryId: number,
  maxId: number,
  report: (msg: string) => void,
): Promise<CategoryResult> {
  try {
    const res = await fetch(`${baseUrl}?category=${categoryId}`);
    if (!res.ok) return { kind: "error", reason: `HTTP ${res.status}` };
    const result = classify(await res.text(), maxId);
    if (result.kind === "fallback") {
      // 落ちないが、黙らせもしない。どのカテゴリで起きたかを残す
      report(`category ${categoryId}: ${result.reason}`);
    }
    return result;
  } catch (e) {
    return { kind: "error", reason: String(e) };
  }
}
```

`classify` に典型的な答えを流すと、次のように分かれます。

```text
classify("1", 1419)               → fallback（固定の既定値）
classify("", 1419)                → fallback（空の一覧）
classify("1353, 1360, 1500", 1419) → ok [1353, 1360]
classify("1500", 1419)            → fallback（全部が上限より上）
```

画面側では `fallback` のとき、1枚だけの一覧を出すのではなく「このカテゴリは準備中です」のような表示に切り替えるのがよいと思います。`report` には、使っているクラッシュレポートのログ記録をそのまま渡せば十分です。落ちない設計を保ったまま、どのカテゴリで起きたかだけは外へ出ていきます。

アプリ側でも上限で絞っているのは、サーバーの絞り込みと二重になるからです。古い版のサーバーや、途中のキャッシュが少し前の答えを返しても、画像の無い ID を並べずに済みます。

## 配信の直後に、オリジンの答えを数える

最後は配った結果の確認です。ここで二つの罠がありました。

一つ目は、途中のキャッシュです。URL をそのまま叩くと、エッジに残った少し前の答えを見て「直っていない」と慌てることになります。URL の末尾にランダムな値を付けてエッジを回避し、本番環境のオリジンが返している答えを直接見るようにしました。この話は、以前 [エッジに 404 が残った件](/articles/app-dev/image-404-held-at-edge-split-ttl-by-status-and-pair-upload-with-purge) でも別の角度から書いています。

二つ目は、数える範囲です。ローカルのファイルには、まだ上限より上の ID が入っていることがあります。サーバーはそれを落として返すので、ローカルを素のまま数えると、正しく配れていても件数がずれます。**ローカル側もサーバーと同じ範囲で数える**のがこつでした。

```python
#!/usr/bin/env python3
"""配信後、カテゴリごとの件数を「ローカルの正本」と「オリジンの実応答」で突き合わせる。

使い方: python3 check_live.py <アプリのディレクトリ> <category_list の URL> <最小ID> <上限>
"""
import random
import re
import sys
import urllib.request
from pathlib import Path


def ids_in(text: str, lo: int, hi: int) -> list[int]:
    # サーバーと同じ範囲で数える。ここを揃えないと、正しくても件数がずれる
    out = []
    for t in re.split(r"[^0-9]+", text):
        if t and lo <= int(t) and (hi <= 0 or int(t) <= hi):
            out.append(int(t))
    return out


def fetch(url: str) -> str:
    sep = "&" if "?" in url else "?"
    busted = f"{url}{sep}cb={random.randint(1, 10**9)}"  # 途中のキャッシュを通り越して、オリジンの答えを見る
    with urllib.request.urlopen(busted, timeout=15) as r:
        return r.read().decode("utf-8", "replace")


def main(app_dir: str, api: str, lo: int, hi: int) -> int:
    php = (Path(app_dir) / "category_list.php").read_text()
    block = re.search(r"\$categoryFiles\s*=\s*\[(.*?)\];", php, re.S).group(1)
    ng = 0
    for cid, stem in re.findall(r"(\d+)\s*=>\s*'([^']+)'", block):
        path = Path(app_dir) / "categories" / f"{stem}.txt"
        if not path.exists():
            print(f"NG  {cid:>3} {stem:<28} ローカルにファイルがありません（対応表だけ先に書いた状態）")
            ng += 1
            continue
        local = ids_in(path.read_text(), lo, hi)
        remote_raw = fetch(f"{api}?category={cid}").strip()
        remote = ids_in(remote_raw, lo, hi)
        if remote_raw == "1" and local != [1]:
            print(f"NG  {cid:>3} {stem:<28} 既定の答え「1」が返っています（未配置か未登録）")
            ng += 1
        elif len(local) != len(remote):
            print(f"NG  {cid:>3} {stem:<28} ローカル={len(local)} サーバー={len(remote)}")
            ng += 1
    print("OK  全カテゴリ一致" if ng == 0 else f"→ {ng} 件ずれています。上げ忘れのファイルを確かめてください")
    return 1 if ng else 0


if __name__ == "__main__":
    if len(sys.argv) != 5:
        sys.exit(__doc__)
    sys.exit(main(sys.argv[1], sys.argv[2], int(sys.argv[3]), int(sys.argv[4])))
```

手元に立てた模擬サーバーに、一つは古いファイル、一つは未配置の状態を返させて流すと、こう出ます。

```text
NG    2 2_meiji                      ローカル=3 サーバー=2
NG    3 3_new                        既定の答え「1」が返っています（未配置か未登録）
→ 2 件ずれています。上げ忘れのファイルを確かめてください
```

カテゴリが百を超えていても、一件ずつ聞いて数えるだけの単純な処理です。67点の日にこれを流していれば、作業を終える前に気づけていたはずです。

## 落とし穴

- **ID が「1」だけのカテゴリ**: 本当に 1 番の壁紙だけを含むカテゴリがあると、既定値と見分けがつきません。アプリ側の `classify` は既定値として扱うので、そういうカテゴリは作らないか、既定値を別の文字列に変えておきます。
- **上限を書いている場所が一つではない**: 私のサーバーでは、共有ファイルのほかに、各版の入口に「共有ファイルが読めないとき用」の既定値も書いていました。共有ファイルだけ直すと、障害のときにだけ古い上限が配られます。上限の更新はスクリプトで全か所を一度に書き換えています。
- **iOS と Android で設定の置き場が違う**: カテゴリのデータは両方で共有していても、上限の設定は別々ということがあります。片方だけ上げると「iOS では新作が見えるのに Android では見えない」が起きます。
- **新しいカテゴリは二か所そろって初めて答える**: 対応表への登録とファイルの配置のどちらかが欠けると、既定値が返ります。判定スクリプトの「未登録」「未配置」の二行は、そのためにあります。

設定の値を後から足したときに、配信済みの版へ届かない問題は、[Remote Config のキーの件](/articles/rork-dev/remote-config-keys-shipped-version-cannot-read-freeze-window) に書きました。画像をアプリに同梱せずサーバーから配る構成そのものについては、[バイナリを小さく保つための配信の話](/articles/app-dev/wallpaper-app-binary-size-remote-asset-delivery) が入口になります。

## 明日、最初にやること

まずは、ご自身のアプリで「件数や上限を表す値」と「分類の一覧」が別々に配られていないかを確かめてみてください。別々なら、上の判定スクリプトの二つ目の確認、新しい ID がどこかの一覧に入っているかだけでも、上限を上げる手前に置いていただければと思います。

私も、追加作業の手順をそこから組み直しました。新作を並べる日はいまも少し胸が高鳴りますが、上限を書き換える前に一度だけ止まる、その順番だけは崩さないようにしています。
