このガイドの旧版を読み返していたとき、実験が一度も始まらない構成になっていることに気づきました。GrowthBook のインスタンスは作られているのに、機能定義を取りに行く呼び出しがどこにも無かったのです。`useFeatureValue` はデフォルト値を返し続け、管理画面には「データがありません」が並びます。原因を探す夜の長さは、想像がつくと思います。

基盤づくりでつまずく場所は、たいてい統計よりも手前にあります。初期化の抜け、識別子のずれ、ライブラリの取り違え。そこを先に潰しておけば、実験の結果を信じてよいかどうかを、数字の側から判断できるようになります。

今回は **GrowthBook（実験エンジン）と PostHog（プロダクト分析）** を Rork が書き出した React Native アプリに組み込み、最初の実験を回すところまでを順に辿ります。コードは手元で動かして確かめられた部分と、公式ドキュメントとの突き合わせが必要な部分を分けて書きました。必要サンプル数の計算も、旧版の数字を取り下げて計算し直しています。

## なぜ Firebase ではなく GrowthBook + PostHog なのか

Firebase Remote Config と Firebase Analytics の組み合わせは、最初の A/B テストを始めるなら最短経路です。ただ、実験を継続的に回し始めると、いくつかの不便が見えてきます。

ひとつは**統計エンジンの調整余地**です。Firebase A/B Testing の統計処理は内部で完結しており、事前分布や有意水準の設定を利用者側で変えられません。GrowthBook は統計エンジンの種類（ベイズ／頻度論）や閾値を設定で選べ、分散削減の CUPED（Controlled-experiment Using Pre-Experiment Data）のような手法も用意されています。ただし CUPED や逐次検定といった機能は有料プランの範囲に含まれることがあるため、使う前に料金ページで確認してください。

もうひとつは**実験設計と分析の置き場所**です。Remote Config はフラグ配信、Analytics はイベント収集と役割が分かれていて、途中経過を一画面で追えません。GrowthBook は実験の定義・配信ルール・解析を一つの管理画面にまとめ、PostHog をデータソースに指定すれば、PostHog のイベントをそのまま指標に使えます。

三つめが**ベンダーロックインの回避**です。GrowthBook も PostHog も、コア部分はオープンソースとして公開され、Docker で自己ホストできます。ただし、どちらも一部の機能は別ライセンス（商用）の領域にあります。「全部 MIT だから完全に自由」とは言えず、使いたい機能がどちらの側にあるかを確かめてから選ぶのが安全です。

GrowthBook Cloud の無料枠も、PostHog Cloud の月間イベント無料枠も、入口として十分に使えます。プランの上限と価格は改定されるので、決める前に各社の料金ページで最新の内容を確認いただければ幸いです。

実験基盤は、次の 4 つの部品で成り立ちます。

データの流れは単純です。アプリが起動すると、GrowthBook SDK が機能定義 JSON を取りに行きます。フラグはアプリの中で評価され、実験に割り当てられた瞬間に露出ログが PostHog へ流れます。GrowthBook は PostHog のイベントを集計し、勝ち負けを判定します。

ここで押さえておきたいのは、**フラグの評価は端末内で行われ、配信されるのは定義の JSON だけ**という点です。配信側が担うのは「定義を速く、止まらずに返す」ことに限られます。

## ステップ 1：管理画面を用意する

最初の実験を急ぐなら、GrowthBook Cloud で始めるのが近道です。Cloud はフィーチャー JSON の配信経路も用意されているため、後述の Workers キャッシュは不要で、SDK の `apiHost` に Cloud のホストを指定するだけで動きます。

自己ホストに切り替える理由が出てきたときの下書きを、残しておきます。

```bash
# Fly CLI の導入とログイン
brew install flyctl
fly auth login

# アプリの枠だけ作る（デプロイは後で）
fly launch --no-deploy --name my-rork-growthbook --region nrt

# 秘密値は fly.toml に書かず、secrets に置く
fly secrets set \
  JWT_SECRET="$(openssl rand -base64 32)" \
  ENCRYPTION_KEY="$(openssl rand -base64 32)" \
  MONGODB_URI="<Atlas の接続文字列>"
```

```toml
# fly.toml — 公開してよい値だけを [env] に置く
app = "my-rork-growthbook"
primary_region = "nrt"

[build]
  image = "growthbook/growthbook:latest"

[env]
  APP_ORIGIN = "https://my-rork-growthbook.fly.dev"
  API_HOST = "https://my-rork-growthbook.fly.dev:3100"

# 管理画面（3000）と API（3100）は別ポートで待ち受けます
[[services]]
  internal_port = 3000
  protocol = "tcp"
  [[services.ports]]
    port = 443
    handlers = ["tls", "http"]

[[services]]
  internal_port = 3100
  protocol = "tcp"
  [[services.ports]]
    port = 3100
    handlers = ["tls", "http"]
```

この下書きには、旧版からの変更点が 3 つあります。

- 秘密値は `[env]` から外し、`fly secrets` へ移しました（`fly.toml` はリポジトリに入りがちなためです）
- GrowthBook 本体のリポジトリを clone する手順は削りました（公式イメージを指定するので不要です）
- 管理画面と API の 2 ポートを公開する形にしました

最後の点は、旧版が見落としていた箇所です。`API_HOST` に外から届く URL を入れておかないと、SDK が定義を取得できません。

**未検証です。** この Fly.io の設定は構造の下書きで、私の環境で起動まで確かめたものではありません。旧版を直しながら、動かしていないものを動くかのように書いていたことを、いま思うと反省しております。ポートの扱いや推奨イメージのタグは、GrowthBook の自己ホスト手順（公式ドキュメント）と突き合わせてからお使いください。また、Fly.io の料金体系は以前の無料枠・Hobby 枠の説明から変わっており、現在は従量課金です。月額は公式の料金計算で見積もる前提にしてください。

MongoDB には Atlas の無料枠（M0）が使えます。実験の定義と解析設定が中心で、イベントそのものは PostHog 側にあるため、データ量が膨らみにくい構成です。

## ステップ 2：PostHog を実験のデータソースとして繋ぐ

GrowthBook にログインしたら、`Settings > Data Sources` から PostHog を追加します。PostHog 側で Personal API Key を発行し、ホストと Project ID を一緒に登録する流れです。権限は、クエリの読み取りに必要な範囲に絞ってください。

接続が済んだら、PostHog のイベントを GrowthBook の指標として登録します。たとえば、次の 3 つです。

- `subscription_started`：購読開始。メインの指標
- `onboarding_completed`：オンボーディング完遂。サブの指標
- `app_session_duration`：セッション時間の中央値。ガードレール指標

ガードレールは「勝ったように見えても、こちらが悪化していたら採用しない」ための安全弁です。購読率だけを追って定着率を落とす失敗は、よくあります。指標を一つしか持たない実験は、そのぶん危ういのです。

ここで必ず確認したいのが、**露出ログのクエリ**です。GrowthBook のデータソース設定には「Experiment Assignment Query」があり、どのイベント名・どのプロパティを露出として読むかが書かれています。デフォルトの内容は版によって異なる可能性があるため、アプリ側の `trackingCallback` が送るイベント名とプロパティ名を、このクエリと必ず一致させてください。ここがずれると、実験は正常に動いているのに「データが足りません」と表示され続けます。

## ステップ 3：Cloudflare Workers で機能定義の配信をキャッシュする

自己ホストした GrowthBook を直接 SDK から呼ぶと、起動のたびに本体サーバーまで往復します。そこで、機能定義の JSON だけを Workers + KV でキャッシュします。

旧版では `@growthbook/edge-cloudflare` の `handleRequest` に `kvCacheTtl` という設定を渡していましたが、この設定項目は確認できませんでした。Edge SDK 自体も、主な用途は Web ページの HTML を書き換える側にあります。モバイル SDK に定義 JSON を返すだけなら、Worker を自分で書いたほうが見通しがよくなります。

```javascript
// worker.js — 機能定義 JSON の薄いキャッシュ（KV）
const TTL_MS = 60_000;

export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    const key = env.GROWTHBOOK_CLIENT_KEY;

    // SDK が叩くパスだけを通す
    if (request.method !== "GET" || url.pathname !== `/api/features/${key}`) {
      return new Response("Not found", { status: 404 });
    }

    const cached = await env.FEATURES_KV.get("features", "json");
    if (cached && Date.now() - cached.at < TTL_MS) {
      return respond(cached.body, "HIT");
    }

    try {
      const upstream = await fetch(`${env.GROWTHBOOK_API_HOST}/api/features/${key}`);
      if (!upstream.ok) throw new Error(`upstream ${upstream.status}`);
      const body = await upstream.text();
      ctx.waitUntil(env.FEATURES_KV.put("features", JSON.stringify({ at: Date.now(), body })));
      return respond(body, "MISS");
    } catch (e) {
      // 本体が落ちていても、古い定義を返して実験を止めない
      if (cached) return respond(cached.body, "STALE");
      return new Response("Bad gateway", { status: 502 });
    }
  },
};

function respond(body, state) {
  return new Response(body, {
    headers: {
      "content-type": "application/json",
      "cache-control": "public, max-age=30",
      "x-features-cache": state,
    },
  });
}
```

```toml
# wrangler.toml
name = "rork-growthbook-edge"
main = "worker.js"
compatibility_date = "2026-04-01"

[[kv_namespaces]]
binding = "FEATURES_KV"
id = "your-kv-namespace-id"

[vars]
GROWTHBOOK_API_HOST = "https://my-rork-growthbook.fly.dev:3100"
# SDK クライアントキーはアプリに同梱される公開値なので vars で足ります
GROWTHBOOK_CLIENT_KEY = "sdk-xxxxxxxx"
```

このコードは、KV と `fetch` を差し替えたテストで、次の 5 つの経路を私の手元で実際に動かして確かめました。

<thead>
<tr><th>リクエスト</th><th>結果</th><th>上流への呼び出し回数</th></tr>
</thead>
<tbody>
<tr><td>1 回目（キャッシュなし）</td><td>200／MISS</td><td>1</td></tr>
<tr><td>直後の 2 回目</td><td>200／HIT</td><td>1（増えない）</td></tr>
<tr><td>別のキーのパス</td><td>404</td><td>1（増えない）</td></tr>

実際の Workers 上での動作と遅延は、この確認の範囲外です。旧版は「30ms 以下」と書いていましたが、その数字は根拠が示せなかったため取り下げました。遅延は、ご自身の回線とリージョンで測ってください。

```bash
# 10 回測って、合計時間の傾向だけ見る（URL とキーは自分のものに）
for i in $(seq 1 10); do
  curl -s -o /dev/null -w "%{time_total}\n" \
    "https://rork-growthbook-edge.<your-subdomain>.workers.dev/api/features/sdk-xxxxxxxx"
done
```

実装上、押さえておきたい点が 3 つあります。

- **Cache API は使いませんでした。** `workers.dev` ドメインでは Cache API が効かないため、独自ドメインを持っていない構成でも動く KV にしています
- **TTL を 10 秒に下げる運用はできません。** KV の `expirationTtl` には最小値があり、今回は有効期限（最小 60 秒）を KV に任せず、保存時刻をみて Worker 側で判定しています。ただ KV の更新は各地域に反映されるまで 1 分以上かかることがあるため、秒単位の即時反映が必要な実験には向きません
- **KV の書き込みには上限があります。** 更新が頻繁だと無料枠を超えるので、料金とのバランスは最新の仕様で確認してください

なお、旧版にあった `X-App-Bundle-Id` ヘッダーの検査は削除しました。ヘッダーは誰でも偽装でき、認証にはなりません。そもそもクライアントキーが公開値である以上、守るべき秘密がここにはない、と整理しています。

## ステップ 4：Rork アプリに SDK を組み込む

Rork のプロジェクトは Expo ベースなので、ライブラリは `npx expo install` で入れます。旧版のコマンドは `@` が抜けた名前になっていて、そのままでは入りませんでした。

```bash
npx expo install @growthbook/growthbook-react posthog-react-native
npx expo install @react-native-async-storage/async-storage expo-crypto
```

`posthog-react-native` は、導入時点のバージョンの README で追加の依存（ファイルシステムやデバイス情報のためのパッケージ）が必要かを確認しておくと、ビルド時の手戻りを避けられます。

識別子の生成には、旧版の `uuid` ではなく `expo-crypto` の `randomUUID()` を使います。React Native には `uuid` が前提とする乱数の仕組みがなく、別途ポリフィルを入れないと実行時に落ちるためです。

もう一つの要点は、**GrowthBook の初期化を必ず呼ぶこと**です。インスタンスを作っただけでは、機能定義は読み込まれません。

```typescript
// src/providers/ExperimentProvider.tsx
// GrowthBook と PostHog の識別子を揃え、定義の読み込みまで済ませるプロバイダー
import { GrowthBook, GrowthBookProvider } from "@growthbook/growthbook-react";
import PostHog from "posthog-react-native";
import { useEffect, useState, type ReactNode } from "react";
import * as Crypto from "expo-crypto";
import AsyncStorage from "@react-native-async-storage/async-storage";

// 開発中は Worker の URL、Cloud を使うなら Cloud のホストを入れる
const API_HOST = process.env.EXPO_PUBLIC_GROWTHBOOK_API_HOST!;
// リージョンにより us.i.posthog.com か eu.i.posthog.com
const POSTHOG_HOST = "https://us.i.posthog.com";

export const posthog = new PostHog(process.env.EXPO_PUBLIC_POSTHOG_KEY!, {
  host: POSTHOG_HOST,
});

export function ExperimentProvider({ children }: { children: ReactNode }) {
  const [gb, setGb] = useState<GrowthBook | null>(null);

  useEffect(() => {
    let cancelled = false;
    (async () => {
      let id = await AsyncStorage.getItem("anon_user_id");
      if (!id) {
        id = Crypto.randomUUID();
        await AsyncStorage.setItem("anon_user_id", id);
      }
      posthog.identify(id);

      const instance = new GrowthBook({
        apiHost: API_HOST,
        clientKey: process.env.EXPO_PUBLIC_GROWTHBOOK_KEY,
        attributes: { id, country: "JP" },
        // 露出ログ。イベント名とプロパティ名は、管理画面の
        // Experiment Assignment Query と一致させる
        trackingCallback: (experiment, result) => {
          posthog.capture("$feature_flag_called", {
            $feature_flag: experiment.key,
            $feature_flag_response: result.key,
          });
        },
      });

      // 定義の読み込み。2 秒で見切り、失敗時はデフォルト値で動かす
      await instance.init({ timeout: 2000 });
      if (!cancelled) setGb(instance);
    })();
    return () => {
      cancelled = true;
    };
  }, []);

  // 読み込みが終わるまで描画を止めると、起動が遅くなる
  // ここでは children をそのまま描画し、未読み込み中はデフォルト値が返る
  if (!gb) return <>{children}</>;
  return <GrowthBookProvider growthbook={gb}>{children}</GrowthBookProvider>;
}
```

この雛形には、判断が分かれる点が一つあります。`gb` が用意できるまで `children` をそのまま描画しているため、起動直後の数百ミリ秒は `useFeatureValue` を使う画面が**フラグ未適用の状態**で描かれます。実験の対象が「最初に見える画面」なら、この間のちらつきが結果を濁します。その場合は、スプラッシュを保ったまま `init` の完了を待つ作りにしてください。

`trackingCallback` のコードは、`$feature_flag_called` に `result.key`（バリエーションのキー）を載せています。GrowthBook の既定の露出クエリとプロパティ名が合うかどうかは、ステップ 2 で確認した内容に従ってください。旧版の `result.variationId` は、数値のインデックスが入るため、クエリの期待とずれる原因になり得ます。

import { useFeatureValue } from "@growthbook/growthbook-react";

export function OnboardingFinalScreen() {
  // 第 2 引数が「読み込み前」「通信失敗」「フラグ削除後」のすべてで返る値

## ステップ 6：必要サンプル数を先に計算する

結果の読み方より前に、**何人集めれば判断できるのか**を決めます。旧版には「片腕あたり約 11,000 ユーザー」と書いてありましたが、これは誤りでした。

条件は次のとおりです。

- ベースラインの購読開始率：3.2%
- 検出したい最小の効果（MDE）：相対 15%（3.68% への上昇）
- 有意水準 5%（両側）、検出力 80%、バリエーション 2

二つの割合を比べる標準的な式で計算すると、**片腕あたり 22,628 人**になります。旧版のほぼ倍です。

```python
import math
from statistics import NormalDist

def n_per_arm(p1, rel_mde, alpha=0.05, power=0.8):
    p2 = p1 * (1 + rel_mde)
    z = NormalDist().inv_cdf
    za, zb = z(1 - alpha / 2), z(power)
    var = p1 * (1 - p1) + p2 * (1 - p2)
    return math.ceil((za + zb) ** 2 * var / (p2 - p1) ** 2)

print(n_per_arm(0.032, 0.15))  # 22628
print(n_per_arm(0.032, 0.30))  # 6034
```

最小検出効果を相対 30% まで緩めると、必要人数は片腕 6,034 人まで減ります。「小さな差まで見たい」という欲が、どれだけ人数を食うのかが、数字で見えてきます。

日数は、**新しく実験に割り当てられるユーザーが 1 日に何人いるか**で決まります。DAU ではなく、新規に露出した人数です。両腕の合計 45,256 人を、1 日あたりの新規露出で割ります。

## ステップ 7：ベイズ統計の結果をどう読むか

実験が始まると、管理画面に「Chance to Win」（旧称は Chance to Beat Control）や「Risk」といった指標が並びます。表記は画面の版によって異なります。p 値に慣れた方には、最初は戸惑う並びかもしれません。

読み方の骨格は 3 つです。

**Chance to Win が高いだけでは、採用の根拠になりません。** これは「treatment が control より良い確率」を示す値で、「どれだけ良いか」は別の話です。

**Risk は、採用した判断が外れていたときに失う期待値**です。指標そのものの相対的な減少として表されるので、たとえば 0.5% なら「外れても、その指標が平均で 0.5% 下がる程度」と読みます。GrowthBook にはこの許容ラインを組織の設定で変える項目があり、既定値はこちらの想定と違うことがあります。しきい値は、ご自身の事業にとって許せる損失から決めてください。

**サンプルサイズは、ステップ 6 の計算値に達したかで判断します。** 「最低 1 週間、両腕 2,000 人」のような経験則は、曜日効果をならすための下限にはなっても、検出力の根拠にはなりません。旧版はこの二つを混同していました。1 週間という下限は残しつつ、人数の本命はあくまで事前計算の値です。

GrowthBook はベイズ統計のほうが途中経過を見ても崩れにくい、という立場を取っています。それでも、見るたびに止める判断を重ねると、誤って「勝ち」を拾う確率は上がります。公式の統計ドキュメントでも、逐次検定のような別の手法が用意されているのは、そのためです。

**止める条件は、実験を始める前に書き出しておきます。** 「Chance to Win が 99% になったから即停止」は、条件が後付けになった瞬間に、結果の意味が変わってしまうのです。

## SRM（サンプル比率不一致）：結果より先に疑う

50/50 で配信している実験の露出が、ぴったり 50/50 にならないのは普通です。ただ、人数が増えたのに偏りが残るなら、上流のどこかが壊れています。これが SRM です。

偏りが偶然かどうかは、カイ二乗検定で確かめられます。

```python
import math

def srm_p(a, b):
    t = a + b
    e = t / 2
    chi2 = ((a - e) ** 2 + (b - e) ** 2) / e
    return chi2, math.erfc(math.sqrt(chi2 / 2))  # 自由度 1

print(srm_p(10600, 9400))  # (72.0, 約 2e-17)  53/47：偶然とは考えにくい
print(srm_p(10100, 9900))  # (2.0, 約 0.157)    50.5/49.5：偶然の範囲
print(srm_p(10200, 9800))  # (8.0, 約 0.0047)   51/49：要観察
```

1 つめは、旧版が例に挙げた「片腕 10,000 人前後で 53/47」と同じ規模です。p 値は 1 兆分の 1 を大きく下回り、偶然では説明できません。GrowthBook は p 値がごく小さいときに SRM として警告を出す設計ですが、しきい値は設定で変わります。

原因として疑う場所は、次の 3 つです。

- 片方のバリエーションでクラッシュが多く、再起動のたびに再バケットされているケース
- `trackingCallback` の二重呼び出しによる、露出の重複
- キャッシュに残った古い割り当てと、実験前から入っていたユーザーの混入

SRM が出たときに直すのは、結果ではなく基盤です。「結果が悪い」のではなく「基盤が嘘をついている」と読み替えて、指標を見る前に SRM の健全性を確かめる順番にしておくと、遠回りが減ります。

## 実験の停止と片付け

採用が決まったら、フラグを 100% 配信にして実験を Stopped にし、コードから分岐を取り除きます。フラグ自体はすぐ消さず、数日は残します。KV に古い定義が残っていることと、旧バージョンのアプリがまだ問い合わせてくることに備えるためです。

```typescript
// Before — フラグ分岐あり
const variant = useFeatureValue("onboarding-cta-7day-trial", "control");
if (variant === "treatment") {
  return <TrialCtaScreen days={7} />;
}
return <SubscribeScreen />;

// After — treatment を採用し、フラグを削除
return <TrialCtaScreen days={7} />;
```

終わった実験のフラグは、期限を決めて消します。リリースのたびに一覧を見直し、一定期間放置されたものは削除する、というルールにしておきます。手順に書いておかないと、フラグはいつの間にか墓場になり、基盤の信頼を静かに削ります。

## メトリクス設計を間違えると分析が嘘をつく

ダッシュボードでは「勝ち」と出ているのに、翌月の収益は動かないことがあります。そんなすれ違いの多くは、**主指標の選び方**から始まります。

指標を確定する前に、一つだけ自分に問います。「この指標が 10% 動いたとき、本当に気にしているもの（定着・収益・問い合わせ件数）も連動して動くか」と。自信を持って答えられないなら、その指標は代理指標の代理になっています。

## 運用で気をつけたい 3 つの落とし穴

### 識別子のずれ

匿名 ID からログイン後のユーザー ID へ切り替わる瞬間、PostHog 側の識別子だけが変わり、GrowthBook の `attributes.id` が古いままになることがあります。すると、露出とコンバージョンが別人のものとして記録されます。切り替えは必ず共通のフックにまとめ、`posthog.alias()` や `identify()` の直後に GrowthBook の属性も更新します。

```typescript
// 識別子を切り替える唯一の入口にしておく
export function switchUserId(gb: GrowthBook, newId: string) {
  posthog.identify(newId);
  gb.setAttributes({ ...gb.getAttributes(), id: newId });
}
```

### 通信が不安定なときの読み込み

機内モードや電波の弱い場所で起動すると、定義の読み込みが間に合わず、デフォルト値の `control` で評価されます。それ自体は安全側の挙動ですが、本来は `treatment` に入るはずだった人が `control` として数えられると、ノイズになります。

ステップ 4 では `init({ timeout: 2000 })` で見切りをつけています。読み込みに失敗した起動は、そもそも実験に露出しなかった扱いになるので、露出ログを送らない限り分析には混ざりません。**露出ログは、フラグを評価した瞬間にだけ送ります**。この線は崩さないでください。

### App Review でのバリエーション

審査担当者がアプリを開いたとき、`treatment` を引いて、審査メモの説明と異なる画面を見る可能性があります。審査期間中だけ `treatment` の配信を 0% に戻すか、審査用アカウントに `reviewer` 属性を付けて必ず `control` を返すルールを置いておくのが無難です。

## プライバシーと App Store 審査

PostHog の既定の設定は、審査側が好まないほど多くを取得することがあります。次の 3 点は、提出前に確認しておきたい項目です。

- 本番での自動取得（autocapture）の無効化、または取得範囲の絞り込み——設定の形は SDK のバージョンごとに違うため、導入したバージョンの README で確かめます
- 広告識別子など、ATT の対象になる情報を送らない設定
- 利用データ送信への同意を、オンボーディングで明示的に取る導線

同意を取るまで送信しない作りにするなら、PostHog の初期化オプションで既定をオプトアウトにし、同意後に有効化する方法があります（`defaultOptIn: false` と `posthog.optIn()` の組み合わせ。オプション名は SDK のバージョンで型定義を確かめてください）。

プライバシーマニフェスト（iOS 17 以降）と、App Store Connect のプライバシー回答は、PostHog に流すデータの実際の中身と一致させる必要があります。実験基盤を足すことは、第三者にデータを渡す経路を増やすことでもあります。最初から同意の流れを組み込んでおけば、審査での往復を減らせます。

## このスタックが向かないケース

すべての Rork プロジェクトに合う構成ではありません。ステップ 6 の計算がその理由を教えてくれます。

- **新規ユーザーの流入が少ないアプリ。** 1 日の新規露出が数百人なら、相対 15% の差を見るには 3 か月以上かかります。A/B テストに時間を使うより、ユーザーへの聞き取りや画面の観察に振ったほうが得るものは多いでしょう
- **リリース頻度が低く、一人で回している場合。** フラグと実験の管理は、機能開発の時間を確実に奪います。損益分岐点は、ユーザーに見える変更を週に一度は出し、その効果を測りたい段階です
- **時流への即応が事業の核の場合。** 季節イベントのように、出して駄目なら戻す判断のほうが速いなら、実験のサイクルは合いません

この基盤は、効果を検出できるだけの流入があり、変更を定期的に出していて、コアの導線がすでに動いている状況で力を発揮します。意思決定の代わりではなく、意思決定の質を底上げする道具として扱うのが健全です。

## Firebase からの移行手順

すでに Firebase A/B Testing が動いているなら、次の順で移すと手戻りが少なくなります。

**2 週間は並走させます。** Firebase は止めずに、同じイベントを新旧両方へ流して見比べます。新しい基盤への信頼が積み上がり、移行中の不具合も、旧データを残したまま見つけられます。

**指標は 1 つずつ移します。** 一度に再現しようとせず、実験で本当に使う 3〜5 個を先に PostHog で完成させ、GrowthBook で動くのを確かめてから増やします。

**Remote Config の切り替えは最後です。** どこで使われているか分からないコードが残りやすい部分だからです。実験用途を移したあとも、キルスイッチなどの非実験用途のために、しばらく残してください。

三つを同時に切り替えると、巻き戻しが二度、三度と続きます。順番に進めると、カレンダーを一週間余分に使いますが、週末を一つ守れます。

## 次の一歩

ここまでで、実験を回せる土台ができました。最初の実験は、変更コストが低く、効果が見えやすいものを選びます。たとえば、有料プランの料金表記の言い回しを 2 通り比べる、といったものです。コードの変更は小さく、結果の判定も単純で、基盤そのものの健全性（識別子・露出・SRM）を確かめる練習台にもなります。

実験基盤そのものが目的ではありません。ユーザーに毎日少しだけ良い体験を届けるための土台として、長く付き合える形に整えていきたいと、いまも感じています。

次の一歩として、まずは手元の指標でステップ 6 の計算を一度回し、最初の実験が何日で終わるのかを書き出してみてください。
