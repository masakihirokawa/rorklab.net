Rork が書いたプロジェクトを、自宅の iMac のエディタで初めて開いた夜のことです。左のツリーに並ぶファイルの多さに、まず手が止まりました。私は習慣で `components/` から順に読みはじめ、三十分ほど経ってから、どの画面がどの部品を呼んでいるのかがまったく見えていないことに気づきました。部品を先に読んでも、使われ方が分からなければ地図にならないのです。

最初にお伝えしたいのは、**読む順番は「画面の入口から部品へ」であって、その逆ではない**ということです。Expo Router を使ったプロジェクトなら、入口は `app/` フォルダにあります。

## React Native と Expo の分担を一行で

React Native は、JavaScript で書いた画面を、iOS と Android それぞれのネイティブな部品として描画する仕組みです。Expo はその上に載る道具一式で、開発サーバー、ネイティブ部品の標準セット、ビルドと配信の仕組みを引き受けてくれます。

Rork が出力するのは、この組み合わせのプロジェクトです。つまり「Rork 独自の何か」を覚える必要はほとんどなく、Expo の流儀を知っていれば読み解けます。ここを押さえると、読む範囲がぐっと狭まります。

## app/ の中身が、そのまま画面の一覧になる

Expo Router は、ファイルの置き場所がそのまま画面の住所になるファイルベースのルーティングです。タブを持つアプリだと、次のような形になることが多いでしょう。

```
app/
├── _layout.tsx          // 全体の枠（Provider や Stack をここで束ねる）
├── (tabs)/
│   ├── _layout.tsx      // タブバーの定義
│   ├── index.tsx        // ホーム
│   └── profile.tsx      // プロフィール
├── login.tsx
└── item/[id].tsx        // 動的ルート（/item/42 など）
```

読みはじめる場所は、いちばん上の `app/_layout.tsx` です。ここにアプリ全体を包む Provider（認証、テーマ、データ取得の仕組み）が並んでいて、「この先の画面は何を共有しているのか」がひと目で分かります。次にタブの `_layout.tsx`、そして各画面のファイル、という順に降りていきます。

画面の遷移は `Link` か `router.push` で書かれています。

```tsx
import { Link, router } from 'expo-router'

<Link href="/item/42">詳細へ</Link>

// 処理の途中で移動したいとき
router.push('/login')
```

Rork に画面の追加を頼んだあと、思ったところに画面が出てこないことがありました。原因はたいてい、ファイルが想定と違う階層に置かれていることでした。画面が見つからないときは、AI への再依頼より先にこのツリーを疑う、という順番にしています。

## 状態の置き場所は三段に分けて眺める

状態管理は、私が見てきたプロジェクトでは、おおむね三つの層に分かれていました。

- 画面の中だけで使う値: `useState`
- 複数の画面で共有する値（ログイン状態、テーマなど）: Context
- サーバーから取る値: 取得専用のライブラリ（TanStack Query など）か、`services/` に置かれた関数

読み解くときのコツは、「この値は誰が書き換えるのか」を一つずつ追うことです。書き換える場所が一か所なら安心して読めますし、三か所あれば、そこがバグの温床になります。

```tsx
// 共有状態の最小形
export const AuthContext = createContext<{ user: User | null }>({ user: null })

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null)
  return <AuthContext.Provider value={{ user }}>{children}</AuthContext.Provider>
}
```

規模が育ってきたら Zustand のような軽い状態管理を足す選択肢もあります。ただ、最初から入れる必要はないと考えています。Context で困ってから足しても、遅くはありませんでした。

## Expo Go で動くものと、動かなくなる境目

開発の最初は、実機の Expo Go に QR コードを読ませるだけで画面が出ます。この手軽さが Expo のいちばんの強みです。

一方で、Expo Go に最初から入っていないネイティブモジュールを足した瞬間、アプリは開かなくなります。私は以前、保存用のライブラリを足して赤い画面を出し、AI に同じ直しを三度頼んで時間を失いました。コードが悪いのではなく、Expo Go という入れ物のほうが足りていなかったのです。

この境目を越えるのが Dev Client（自分のアプリ専用の開発ビルド）です。導入の手順は [Rork アプリに Expo Dev Client を導入する手順](/articles/rork-dev/rork-expo-dev-client-native-module-setup-guide) に別記事でまとめています。

## ビルドと配信は EAS に任せる

ストアに出す段になると、ビルドと提出は EAS（Expo Application Services）の出番です。

```bash
eas build --platform ios
eas build --platform android
eas submit --platform ios --latest
```

古い解説でよく見かける `expo build:ios` は、すでに使われなくなった旧方式です。そうした記事に出会ったら、EAS Build に読み替えていただければと思います。署名やプロビジョニングの扱いは最初に一度つまずきやすい箇所ですが、EAS が証明書の管理を肩代わりしてくれるので、手元に Xcode の細かい設定を溜め込まずに済みます。

## ios/ と android/ は「手で触らない生成物」と考える

プロジェクトに `ios/` と `android/` が見えるとき、そこは生成物だと捉えるようにしています。ネイティブ側の設定は `app.json` と config plugin に書き、`expo prebuild` でフォルダを作り直します。この流れを守ると、Expo のバージョンを上げるときに慌てません。

SDK 57 では、`prebuild` が既定でネイティブフォルダを消してから再生成するようになりました。手で書き足した行が消える可能性があるため、上げる前の洗い出しを [Expo SDK 57 に上げる前に、prebuild で消えるネイティブ変更を洗い出す](/articles/rork-dev/rork-expo-sdk-57-prebuild-clean-native-changes-audit) に書き残しています。

## 長いリストと再描画は、後から見直す

画面が動いてから見直す箇所として、長い一覧は `FlatList` で描くのが基本です。画面に見えている分だけを描画してくれるので、件数が増えても重くなりにくいのです。

```tsx
<FlatList
  data={items}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <ItemRow item={item} />}
/>
```

一覧が空白になる症状に出会ったときは、[FlatList が空白になるときの切り分け](/articles/rork-dev/rork-flatlist-blank-empty-list-debug) を手がかりにしてください。`useMemo` や `useCallback` は、実際に遅さを感じてから足せば十分です。

## 骨組みを読むための、私の線引き

ここまでの流れを、一文に縮めてみます。

**画面は app/ に、共有する値は Provider に、手で触ったネイティブは config plugin に。** 置き場所を守っておけば、AI が書き足したコードも、自分で直したコードも、あとから辿り直せます。この線引きだけは、急いでいる日でも崩さないようにしています。

次の一歩として、手元のプロジェクトで `app/_layout.tsx` を開き、画面が何枚あって、どれが共有状態を触っているのかを紙に書き出してみていただければ幸いです。それだけで、AI に次の依頼を出すときの言葉が、はるかに具体的になると感じています。
