先日、手元の小さなアプリを一本、Rork Max の Swift 生成で作り直してみました。きっかけは単純で、ホーム画面のウィジェットと Live Activities をどうしても綺麗に出したかったからです。通常の Rork が生成する Expo アプリでも実現はできますが、拡張ターゲットを別言語で書き足す手間が毎回つきまといます。Swift をそのまま吐いてくれるなら、その往復が一段減るはずでした。

実際に触ってみて見えてきたのは、「どちらが優れているか」という問いがそもそも筋違いだということです。問うべきは、自分のアプリ群のどの部分をどちらのエンジンに任せるか、その線をどこに引くかでした。個人開発で複数のアプリを並行運用していると、この線引きの精度が、そのまま月々の保守時間に跳ね返ってきます。

## 2つの生成エンジンは、別の臓器だと考える

まず前提を揃えます。通常の Rork は自然言語の指示から Expo（React Native）アプリを生成します。無料で始められ、有料は月額 $25 からです。一方の Rork Max は iPhone・iPad・Apple Watch・Apple TV・Vision Pro 向けの Swift ネイティブアプリを生成し、Xcode を開かずに App Store 公開まで到達できると謳っています。価格は月額 $200 で、a16z から $2.8M を調達した直後の積極的な拡張期にあります。

価格差は8倍です。この8倍を「高い」と見るか「妥当」と見るかは、何を任せるかで変わります。私の結論を先に書くと、Expo 版は「速く検証して捨てられる層」、Rork Max は「長く運用してプラットフォームに深く食い込む層」に向いています。両者を優劣ではなく、役割の違う臓器として扱うのが出発点です。

## 責務分界の判断表

実際に使い分けるための基準を、運用コストから逆算して表にしました。文章ではなくリストで示します。

- 検証段階のプロトタイプ → Expo 版。1日で作って、響かなければ消す前提
- 標準的な CRUD とフォーム中心の画面 → Expo 版。React Native の資産がそのまま効く
- ウィジェット・Live Activities・Dynamic Island → Rork Max。拡張ターゲットの言語往復が消える
- AR / LiDAR / Metal を使う表現 → Rork Max。Expo では届かない領域
- HealthKit・HomeKit・NFC・App Clips → Rork Max。ネイティブ API への距離が近い
- オンデバイス Core ML での推論 → Rork Max。モデル統合の摩擦が小さい
- 課金（StoreKit / サブスク）→ どちらも可。ただし複数アプリで共通化したいなら Expo 側に寄せる
- 広告 SDK（AdMob 等）→ Expo 版が無難。SDK の実績と情報量が React Native 側に厚い

最後の2行が、個人開発者にとっては最重要だと考えています。私自身、収益の柱は広告と課金です。AdMob の細かなフリークエンシー制御や、サブスクの状態同期といった「お金に直結する層」は、情報量と再利用性の都合で Expo 側に集約したほうが運用が安定しました。逆に、ユーザーの目を引く表現層は Rork Max に寄せると、手書きの拡張コードが減ります。

## 境界には必ず「契約」を置く

2つのエンジンを併用するときに最も危険なのは、それぞれが勝手にデータの形を決めてしまうことです。Expo 側で `is_premium` と書き、Swift 側で `premiumActive` と書く。この程度のズレが、再生成のたびに静かに増殖します。

そこで私は、エンジンをまたぐデータには必ず明示的な契約（スキーマ）を1枚かませます。アプリ本体とウィジェット、あるいは Expo 版と Swift 版の間で共有する状態を、JSON の形で固定するのです。

```typescript
// shared-contract.ts — 生成エンジンをまたいで共有する状態の単一定義
// このファイルだけは AI に再生成させず、人間が管理する
export interface AppSharedState {
  schemaVersion: number;      // 破壊的変更のたびに +1
  isPremium: boolean;         // 課金状態の単一の真実
  adsEnabled: boolean;        // 広告表示の可否
  streakCount: number;        // ウィジェットに出す数値
  lastSyncedAt: string;       // ISO8601。同期の鮮度判定に使う
}

export const CURRENT_SCHEMA_VERSION = 3;

// 受け取り側で必ず通す検証関数。未知の形は黙って捨てず、既定値に落とす
export function parseSharedState(raw: unknown): AppSharedState {
  const o = (raw ?? {}) as Record<string, unknown>;
  return {
    schemaVersion: typeof o.schemaVersion === "number" ? o.schemaVersion : 0,
    isPremium: o.isPremium === true,
    adsEnabled: o.adsEnabled !== false,
    streakCount: typeof o.streakCount === "number" ? o.streakCount : 0,
    lastSyncedAt: typeof o.lastSyncedAt === "string" ? o.lastSyncedAt : "",
  };
}
```

Swift 側はこの形をそのまま受け取る `Codable` を持ちます。

```swift
// SharedState.swift — App Group の UserDefaults 経由で Expo 側と同じ形を読む
struct AppSharedState: Codable {
    var schemaVersion: Int
    var isPremium: Bool
    var adsEnabled: Bool
    var streakCount: Int
    var lastSyncedAt: String
}

func loadSharedState() -> AppSharedState {
    let defaults = UserDefaults(suiteName: "group.net.dolice.sharedapp")
    guard let data = defaults?.data(forKey: "appSharedState"),
          let decoded = try? JSONDecoder().decode(AppSharedState.self, from: data)
    else {
        // 読めないときは既定値。ウィジェットを空白で固めないための保険
        return AppSharedState(schemaVersion: 0, isPremium: false,
                              adsEnabled: true, streakCount: 0, lastSyncedAt: "")
    }
    return decoded
}
```

この契約レイヤーの肝は、`schemaVersion` を必ず持たせることです。Rork Max にウィジェットを再生成させると、受け取り側のコードが知らないうちに書き換わることがあります。バージョン番号を見て「自分が知らない新しい形が来たら既定値に落ちる」という防御を1行入れておくだけで、再生成のたびに起きる原因不明の空白表示を防げました。

## どこから手で書くか、3つの兆候

ノーコード生成に任せきれなくなる瞬間は、だいたい次の3つの兆候として現れます。

1. 同じ修正指示を3回出しても、生成物が指示の外側を毎回少しずつ壊す
2. プラットフォーム固有 API のエラーメッセージが、生成プロンプトでは解消できない
3. 課金やセキュリティに関わる分岐を、人間がレビューできない形で生成が触り始める

この3つのどれかが出たら、その部分は手書きに切り替えます。特に3番目は妥協しません。お金とアカウント削除に関わる処理だけは、生成物の中であっても人間が読んで意味を追える状態を保つ、というのが個人開発で複数アプリを6年運用してきた末の私のルールです。

## 公開フローの「2クリック」をうのみにしない

Rork Max の訴求点である「Xcode なしで2クリック公開」は、初回の体験としては確かに鮮やかです。ただ、App Store の公開で実際に時間を食うのは、ビルドをアップロードする工程ではありません。スクリーンショットの多言語対応、プライバシー項目の申告、審査リジェクトへの再提出。これらは生成エンジンが肩代わりしてくれない領域です。

ですから「2クリック公開」は、初回提出の摩擦が減るという意味で受け取るのが正確です。公開後の更新・課金・広告の組み込みやすさこそが、実運用での評価を左右します。私が小さなアプリで Expo 版と Rork Max を並べて比較したときも、差がついたのは生成直後ではなく、3度目の更新を出すあたりからでした。

## 次の一手

まずは捨てても惜しくない小さなアプリを一本、両方のエンジンで作ってみることをお勧めします。そのとき、本稿で示した `shared-contract.ts` に相当する契約レイヤーだけは最初に固定してください。エンジンの優劣を測るより、自分のアプリ群における責務の線を一度引いてみることが、月々の保守時間をいちばん確実に削ってくれます。

同じように複数アプリを抱えている方の判断材料になれば幸いです。
