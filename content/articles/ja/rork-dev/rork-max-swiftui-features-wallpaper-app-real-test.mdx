生成された壁紙グリッドは、シミュレータでは軽快に動きます。実機に本番サイズの画像を流し込んでスクロールを続けると、しばらくして落ちます。

画面の見た目と、長く動かしたときの振る舞いは、別々に確かめる必要があります。

この記事は、壁紙アプリの典型的な要件を Rork Max の SwiftUI 生成に渡す場面を想定して、生成コードに任せてよい部分、必ずレビューする部分、手書きにしたほうが安全な部分を仕分けた実装ノートです。

**生成コードは「見た目の骨格」までを信頼し、「時間が経ってから効く挙動」は自分の目で確かめます。** 記事全体を通して、この一文に沿って整理します。

## 前提と、この記事で確認していないこと

先に範囲を明記しておきます。

生成結果は、プロンプトや日によって変わります。実際に試す方は、同じ要件でも出力が揺れることに驚くかもしれません。ここで「生成コードはこうなりがち」と書く形は、SwiftUI で壁紙アプリを組むときに出やすいパターンを前提にしたもので、特定のバージョンの出力を保証するものではありません。掲載コードは構造と考え方を示すための抜粋で、この記事の執筆時点でビルドまでは確認していません。ご自身のプロジェクトでコンパイルと実機確認を通してから使ってください。

数値は、メモリの試算（画像1枚あたりのビットマップサイズ）のように計算で確かめられるものだけを載せています。端末ごとの実測値は、後半の手順で各自の環境で取る形にしました。

## 「そのまま使える」部分 — 見た目の骨格

### 壁紙グリッド（LazyVGrid）

「3カラム、正方形セル、角丸、タップで全画面、末尾で追加ロード」という要件は、SwiftUI の `LazyVGrid` と相性が良く、骨格は素直に出ます。

```swift
struct WallpaperGridView: View {
    @StateObject private var viewModel = WallpaperViewModel()
    let columns = [GridItem(.flexible()), GridItem(.flexible()), GridItem(.flexible())]

    var body: some View {
        ScrollView {
            LazyVGrid(columns: columns, spacing: 4) {
                ForEach(viewModel.wallpapers) { wallpaper in
                    WallpaperCell(wallpaper: wallpaper)
                        .onAppear { viewModel.loadMoreIfNeeded(current: wallpaper) }
                }
            }
            .padding(4)
        }
        .onAppear { viewModel.fetchWallpapers() }
    }
}

struct WallpaperCell: View {
    let wallpaper: Wallpaper
    @State private var showDetail = false

    var body: some View {
        AsyncImage(url: URL(string: wallpaper.thumbnailURL)) { image in
            image.resizable().aspectRatio(1, contentMode: .fill)
        } placeholder: {
            Color.gray.opacity(0.3)
        }
        .clipShape(RoundedRectangle(cornerRadius: 8))
        .onTapGesture { showDetail = true }
        .fullScreenCover(isPresented: $showDetail) {
            WallpaperDetailView(wallpaper: wallpaper)
        }
    }
}
```

`onAppear` を起点にしたページネーションは定石です。ViewModel の細部（オフセット管理、エラー処理、重複ロードの抑止）は要件に含めなければ手薄になるので、そこは自分で足します。

ただし、このコードを「そのまま使える」と呼べるのは構造だけです。`AsyncImage` を本番サイズの画像に向けると何が起きるかは、後半の「メモリ」の節で扱います。

### 全画面プレビュー（ピンチズーム）

ピンチズームと閉じるボタンを持つ全画面ビューアも、骨格は素直に出ます。

```swift
struct WallpaperDetailView: View {
    let wallpaper: Wallpaper
    @State private var scale: CGFloat = 1.0
    @State private var lastScale: CGFloat = 1.0
    @Environment(\.dismiss) private var dismiss

    var body: some View {
        ZStack(alignment: .topTrailing) {
            AsyncImage(url: URL(string: wallpaper.fullURL)) { image in
                image
                    .resizable()
                    .aspectRatio(contentMode: .fit)
                    .frame(maxWidth: .infinity, maxHeight: .infinity)
                    .scaleEffect(scale)
                    .gesture(
                        MagnifyGesture()
                            .onChanged { value in scale = lastScale * value.magnification }
                            .onEnded { _ in
                                scale = min(max(scale, 1.0), 5.0)
                                lastScale = scale
                            }
                    )
            } placeholder: {
                ProgressView().frame(maxWidth: .infinity, maxHeight: .infinity)
            }
            .background(Color.black)
            .ignoresSafeArea()

            Button(action: { dismiss() }) {
                Image(systemName: "xmark.circle.fill")
                    .font(.title)
                    .foregroundColor(.white)
                    .padding()
            }
        }
    }
}
```

確認したい点は2つあります。

1つ目はジェスチャーの型です。`MagnificationGesture` は iOS 17 で非推奨になり、`MagnifyGesture`（値は `value.magnification`）が後継です。対応 OS が iOS 16 以前を含むなら、旧型のままにするか `#available` で分けます。

2つ目はスケールの上下限です。ズームの上限と下限は、`onEnded` で丸めるだけだとピンチ中に範囲外へ出ます。滑らかさを求めるなら `onChanged` の側でも `min`/`max` で挟んでください。

## 「手を入れる」部分 — 動くが、前提が合わない

### カテゴリタブ（TabView の使いどころ）

「Nature」「Architecture」「Abstract」のようなカテゴリ別表示は、`TabView` で返ってくることが多いはずです。`TabView` 自体は正しい選択です。ただ、タブごとに高解像度画像の一覧を持つ構成では、各タブの内容がいつ初期化されるかをプロファイルで確かめる価値があります。

タブの中身を表示時まで作らない構成にしたい場合は、プロンプトに理由ごと書き添えるほうが意図が伝わります。

```
カテゴリ切り替えは、選択中のカテゴリの一覧だけを生成する構成にしてください。
理由：各カテゴリが高解像度画像のグリッドを持つため、非表示のカテゴリまで
同時に保持するとメモリを圧迫するからです。
```

「何を作るか」に加えて「なぜそうするか」を書くと、出力の方向が合いやすくなります。

### スライドショーと Timer

自動で壁紙を切り替えるスライドショーは、`Timer` の扱いで差が出ます。生成コードで特に確認したいのは次の3点です。

- `onAppear` で開始した `Timer` を、`onDisappear` で止めているかどうか
- アプリがバックグラウンドに移ったときに、止めているかどうか
- 復帰したときに、二重起動していないかどうか

どれかが抜けると、画面が消えた後もタイマーが動き続けたり、復帰後に切り替えが倍速になったりします。開始と停止を対称に書き、`scenePhase` で前面・背面を見る形が安全です。

```swift
final class SlideShowTimer: ObservableObject {
    private var timer: Timer?

    func start(interval: TimeInterval, action: @escaping () -> Void) {
        stop() // 二重起動を防ぐ
        timer = Timer.scheduledTimer(withTimeInterval: interval, repeats: true) { _ in
            action()
        }
    }

    func stop() {
        timer?.invalidate()
        timer = nil
    }

    deinit { timer?.invalidate() }
}

struct SlideShowView: View {
    @StateObject private var slideTimer = SlideShowTimer()
    @Environment(\.scenePhase) private var scenePhase
    @State private var currentIndex = 0
    let wallpapers: [Wallpaper]

    var body: some View {
        TabView(selection: $currentIndex) {
            ForEach(wallpapers.indices, id: \.self) { index in
                WallpaperFullView(wallpaper: wallpapers[index]).tag(index)
            }
        }
        .tabViewStyle(.page(indexDisplayMode: .never))
        .onAppear { startSlideShow() }
        .onDisappear { slideTimer.stop() }
        .onChange(of: scenePhase) { _, phase in // iOS 17 以降の2引数形式
            if phase == .active { startSlideShow() } else { slideTimer.stop() }
        }
    }

    private func startSlideShow() {
        guard !wallpapers.isEmpty else { return }
        slideTimer.start(interval: 3.0) {
            withAnimation { currentIndex = (currentIndex + 1) % wallpapers.count }
        }
    }
}
```

`WallpaperFullView` は、全画面表示用の自前ビューを指すプレースホルダーです。`wallpapers.isEmpty` の確認を入れているのは、空配列で `% 0` を計算するとクラッシュするからです。

SwiftUI の `Timer.publish` と `onReceive` を使う書き方もあります。どちらを選んでも、**開始と停止の対応が取れているか**を見る点は変わりません。

## 「手書きが安全」な部分 — OS の権限と順序

### 写真ライブラリへの保存と権限フロー

壁紙アプリでは、画像を「写真」に保存する機能が中心になります。注意点を1つ。iOS には、アプリからホーム画面やロック画面の壁紙を直接設定する公開 API はありません。多くの壁紙アプリが行っているのは、画像を写真ライブラリへ保存し、設定手順を案内するところまでです。「壁紙に設定」と書いたボタンが実際に何をするのかは、文言にも正直に反映してください。

保存の前には、追加専用の権限を async/await で確認します。

```swift
import Photos

func requestPhotoLibraryAccess() async -> Bool {
    let status = PHPhotoLibrary.authorizationStatus(for: .addOnly)
    switch status {
    case .authorized, .limited:
        return true
    case .notDetermined:
        let granted = await PHPhotoLibrary.requestAuthorization(for: .addOnly)
        return granted == .authorized || granted == .limited
    default:
        return false
    }
}
```

生成コードで見落とされやすいのは、`.denied`/`.restricted` のときの導線です。権限がない状態でそのまま保存処理に進むと、失敗が黙って消えます。設定アプリへ誘導するか、理由を表示するところまでを仕様に含めてください。`Info.plist` の `NSPhotoLibraryAddUsageDescription` も忘れずに。

### ATT（App Tracking Transparency）の順序

広告を出すアプリでは、トラッキング許可のダイアログを出すタイミングが審査と収益の両方に関わります。Google の AdMob 向けドキュメントでは、広告 SDK を初期化する前に ATT の許可を求める流れが案内されています。実際に掲載する SDK のバージョンの公式ガイドで、現在の推奨順序を確認してください。

生成コードを受け取ったら、次の3点を確認します。

- `ATTrackingManager.requestTrackingAuthorization` を呼ぶ前に、広告 SDK の初期化を始めていないかどうか
- アプリ起動直後ではなく、`applicationDidBecomeActive` 以降など、ダイアログを出せる状態で呼んでいるかどうか
- `Info.plist` に `NSUserTrackingUsageDescription` があるかどうか

ここは画面の見た目では気づけず、審査や本番で露呈しやすい部分です。レビュー対象の筆頭に置いてください。

## 広告バナーを組み込むときの注意

生成されたビューに AdMob バナーを置く場面では、`rootViewController` の取得方法が要点です。

```swift
struct BannerAdView: UIViewRepresentable {
    let adUnitID: String

    func makeUIView(context: Context) -> GADBannerView {
        let banner = GADBannerView(adSize: GADAdSizeBanner)
        banner.adUnitID = adUnitID
        // keyWindow は iOS 13 以降で非推奨。シーン経由で取得する
        banner.rootViewController = UIApplication.shared.connectedScenes
            .compactMap { $0 as? UIWindowScene }
            .flatMap { $0.windows }
            .first(where: { $0.isKeyWindow })?.rootViewController
        banner.load(GADRequest())
        return banner
    }

    func updateUIView(_ uiView: GADBannerView, context: Context) {}
}
```

`UIApplication.shared.keyWindow` は iOS 13 で非推奨になった API です。生成コードに残っていたら `connectedScenes` 経由に直してください。

もう1点。Google Mobile Ads SDK はメジャーバージョンで型名が変わります（新しい世代では `GADBannerView` が `BannerView` に改名されています）。生成コードが古い名前を使っていないか、導入する SDK のリリースノートと突き合わせてください。広告ユニット ID は、テスト用 ID とリリース用 ID を取り違えない仕組みにしておくと安全です。

## 端末解像度の定数 — 最新機種が抜けやすい

壁紙アプリは、端末ごとの画面解像度に合わせた画像を出す場面が多く、機種が増えるたびに定数の更新が要ります。生成コードは基本的な分岐を書けても、新しい機種の寸法までは含まないことがあります。

```swift
// 画面のピクセル寸法から、配信する壁紙の寸法を選ぶ例
// 数値は Apple の Tech Specs で確認してから更新してください
struct WallpaperSize {
    static func optimal(for screen: UIScreen = .main) -> CGSize {
        let native = screen.nativeBounds.size  // ピクセル単位（回転しない値）
        switch (Int(native.width), Int(native.height)) {
        case (1320, 2868): return CGSize(width: 1320, height: 2868) // 16 Pro Max / 17 Pro Max
        case (1290, 2796): return CGSize(width: 1290, height: 2796) // 14 Pro Max / 15 Plus / 15 Pro Max / 16 Plus
        case (1206, 2622): return CGSize(width: 1206, height: 2622) // 16 Pro / 17 / 17 Pro
        case (1179, 2556): return CGSize(width: 1179, height: 2556) // 15 / 15 Pro / 16
        default:           return native
        }
    }
}
```

`UIScreen.main` は iOS 16 以降で非推奨の方向にあるため、ウィンドウシーンの `screen` を渡す形にしておくと後で直しやすくなります。`nativeBounds` を使えば、スケール計算を自前で書かずに済みます。

機種名とピクセル寸法の対応は更新されていく情報です。表を丸写しせず、Apple の公式仕様で確認してください。寸法ごとに画像を分ける設計そのものを見直して、サーバー側で `default` のように最寄りの寸法へフォールバックさせる手もあります。

## 生成コードが最初に破綻するのは、メモリ

先ほど `LazyVGrid` の骨格は素直に出ると書きました。ただし、`AsyncImage` を本番の壁紙データに向けると、スクロールを続けるうちに強制終了へ至る構成になりがちです。

理由は単純です。`AsyncImage` はダウンロードした画像を、原寸のままデコードします。サムネイルとして原寸の壁紙を配信していると、デコード後のビットマップは「幅 × 高さ × 4バイト」を占めます。1290×2796 なら1枚で約14.4MB。3カラムで前後の行を含めて30枚が生きていれば、それだけで400MB を超える計算です。`LazyVGrid` が画面外のセルを即座に解放する保証はなく、`AsyncImage` には明示的なキャッシュがないので、戻ってきたときには再ダウンロードと再デコードがもう一度走り得ます。

Rork Max に落ち度があるわけではありません。「3カラムのグリッド」という要件からは、原寸 4K の画像が流れてくる前提を読み取れないからです。ここは、仕様として渡す側が補う領域です。

### デコードする寸法を先に決める

対策は、デコード段で寸法を落とすことです。`CGImageSourceCreateThumbnailAtIndex` を使うと、フルサイズのビットマップを作らずに目的の寸法へ展開できます。

```swift
import ImageIO
import UIKit

enum ImageDownsampler {
    /// 表示寸法（ポイント）とスケールから、デコード段で縮小した UIImage を返す
    static func downsample(data: Data, to pointSize: CGSize, scale: CGFloat) -> UIImage? {
        let sourceOptions = [kCGImageSourceShouldCache: false] as CFDictionary
        guard let source = CGImageSourceCreateWithData(data as CFData, sourceOptions) else { return nil }

        let maxPixel = max(pointSize.width, pointSize.height) * scale
        let thumbOptions = [
            kCGImageSourceCreateThumbnailFromImageAlways: true,
            kCGImageSourceShouldCacheImmediately: true,
            kCGImageSourceCreateThumbnailWithTransform: true,
            kCGImageSourceThumbnailMaxPixelSize: maxPixel
        ] as CFDictionary

        guard let cgImage = CGImageSourceCreateThumbnailAtIndex(source, 0, thumbOptions) else { return nil }
        return UIImage(cgImage: cgImage, scale: scale, orientation: .up)
    }
}
```

`kCGImageSourceCreateThumbnailFromImageAlways` を true にしているのは、JPEG に埋め込まれた小さなサムネイルを流用させないためです。壁紙のグリッドでは、埋め込みサムネイルだと輪郭が甘くなりがちです。`kCGImageSourceShouldCacheImmediately` を true にすると、デコードがこの関数の中で完了します。スクロール中にメインスレッドで遅れてデコードが走る事態を避けられます。

### 上限付きのキャッシュを挟む

次はキャッシュです。`NSCache` は `totalCostLimit` を指定すると、メモリ圧迫時に古いエントリを手放してくれます。コストにバイト数を渡すのが要点です。

```swift
actor ThumbnailStore {
    static let shared = ThumbnailStore()

    private let cache: NSCache<NSString, UIImage> = {
        let c = NSCache<NSString, UIImage>()
        c.totalCostLimit = 48 * 1024 * 1024   // 48MB
        return c
    }()
    private var inFlight: [String: Task<UIImage?, Never>] = [:]

    func thumbnail(for url: URL, pointSize: CGSize, scale: CGFloat) async -> UIImage? {
        let key = "\(url.absoluteString)|\(Int(pointSize.width * scale))"
        if let cached = cache.object(forKey: key as NSString) { return cached }
        if let running = inFlight[key] { return await running.value }

        let task = Task<UIImage?, Never> {
            guard let (data, _) = try? await URLSession.shared.data(from: url) else { return nil }
            return ImageDownsampler.downsample(data: data, to: pointSize, scale: scale)
        }
        inFlight[key] = task
        let image = await task.value
        inFlight[key] = nil

        if let image, let cg = image.cgImage {
            cache.setObject(image, forKey: key as NSString, cost: cg.bytesPerRow * cg.height)
        }
        return image
    }
}
```

`inFlight` を持たせる理由は、同じ URL への要求が重なるのを1本にまとめるためです。グリッドを速くスクロールすると、同じセルの読み込みが何度も走ります。素直に書くと同一画像のデコードが並列で起き、メモリのピークが跳ね上がります。

呼び出し側は、`AsyncImage` を置き換える薄いビューにまとめます。

```swift
struct WallpaperThumbnail: View {
    let url: URL
    let side: CGFloat
    @State private var image: UIImage?

    var body: some View {
        Group {
            if let image {
                Image(uiImage: image).resizable().aspectRatio(1, contentMode: .fill)
            } else {
                Color.gray.opacity(0.3)
            }
        }
        .frame(width: side, height: side)
        .clipped()
        .task(id: url) {
            image = await ThumbnailStore.shared.thumbnail(
                for: url,
                pointSize: CGSize(width: side, height: side),
                scale: UIScreen.main.scale
            )
        }
    }
}
```

`.task(id: url)` が地味に効きます。`onAppear` でタスクを起こす書き方では、セルが再利用されたときに古い読み込みが残り得ます。`id` を指定した `task` は、`id` が変わった時点で前の読み込みをキャンセルします。

### 数字で確かめる手順

直したつもりで終わらせないために、残りメモリを数値で見る方法を用意しておきます。`os_proc_available_memory()` は、アプリが強制終了されるまでに使える残量をバイトで返します。

```swift
#if DEBUG
import os

func logMemoryHeadroom(_ label: String) {
    let available = Double(os_proc_available_memory()) / 1_048_576
    os_log("[mem] %{public}@ available=%{public}.1fMB", label, available)
}
#endif
```

記録のやり方は次のとおりです。

1. 実機（できれば搭載メモリの小さい古い機種）で、グリッドを200行ぶんスクロールし続けてください。
2. 数行ごとに `logMemoryHeadroom` を呼び、残量の最小値を控えてください。
3. 「生成コードそのまま」「ダウンサンプリングのみ」「ダウンサンプリング＋キャッシュ」の3構成で、同じ操作を繰り返します。
4. Xcode の Instruments（Allocations / VM Tracker）でも、同じ傾向が出るかを見てください。

結果の絶対値は、端末・画像サイズ・データ量で大きく変わります。**見るべきは絶対値ではなく、構成を変えたときの差の大きさ**です。

代償もあります。デコード段で縮小する分、CPU 時間は増えます。`Task` に載せている限りスクロールを妨げにくいはずですが、古い端末では同時実行数を絞る調整が必要になる場合があります。

### 仕様の渡し方を変える

生成を依頼するときの書き方も変えられます。「3カラムのグリッド」だけで渡すのではなく、次のように条件を添えます。

```
3カラムのグリッド。画像は原寸 4K で配信されるため、セルの表示寸法にデコード段で縮小すること。
上限付きのキャッシュを持たせ、同一 URL の並列読み込みは1本に束ねること。
```

制約と理由を書くと、ダウンサンプリングやキャッシュが最初から入った出力になりやすくなります。ただし、毎回そうなる保証はありません。受け取ったあとのレビューは省略できません。

## アニメーションは、骨格を任せやすい領域

フェードイン、スケールアップ、スライドインのような定番のアニメーションは、軽い指示でも筋の良いコードが返りやすい領域です。タップでハートを弾ませるいいねボタンなら、次の形が基本になります。

```swift
struct LikeButton: View {
    @State private var isLiked = false
    @State private var bounce = false

    var body: some View {
        Button {
            isLiked.toggle()
            guard isLiked else { return }
            bounce = true
            Task {
                try? await Task.sleep(for: .milliseconds(250))
                bounce = false
            }
        } label: {
            Image(systemName: isLiked ? "heart.fill" : "heart")
                .foregroundColor(isLiked ? .red : .white)
                .font(.title2)
                .scaleEffect(bounce ? 1.4 : 1.0)
                .animation(.spring(response: 0.3, dampingFraction: 0.6), value: bounce)
        }
    }
}
```

`spring` のパラメータ（`response` は 0.3 前後、`dampingFraction` は 0.5〜0.6 前後）は、弾み方の好みで調整する値です。確認したいのは、`withAnimation` の中身が空のまま残っていないか、アニメーションの対象になる状態が実際に変化しているかです。生成コードには、動きに寄与しない記述が混ざることがあります。

## UIKit との混在 — 段階的に移す

既存の UIKit アプリに SwiftUI の画面を足していく場合は、`UIHostingController` で SwiftUI ビューを UIKit のフローに組み込むのが基本です。ナビゲーションが `NavigationStack` と `UINavigationController` の二重になると、戻る操作や遷移の一貫性が崩れやすくなります。

進め方として無理がないのは、新しい画面から SwiftUI で作り、既存の UIKit 画面には手を入れない方針です。全画面を一度に作り直す必要はありません。

境界でのデータの受け渡しは、`@State` や `@Binding` を前提にした生成コードと相性が悪い箇所です。`UIViewControllerRepresentable` の `Coordinator` を挟む橋渡し部分は、手書きにするか、動作を確認済みのパターンを流用するほうが安全です。

## StoreKit 2 — 払い戻しの判定を忘れない

課金は StoreKit 2 を前提に組むのが現在の標準です。Apple が StoreKit 2 を推奨していることは、公式ドキュメントで確認できます。「広告削除」のような非消耗型の購入判定は、`Transaction.currentEntitlements` を走査する形になります。

```swift
actor BillingManager {
    static let shared = BillingManager()

    func isAdFree() async -> Bool {
        for await result in Transaction.currentEntitlements {
            if case .verified(let transaction) = result,
               transaction.productID == "com.example.app.adfree",
               transaction.revocationDate == nil {
                return true
            }
        }
        return false
    }
}
```

`com.example.app.adfree` は自分のプロダクト ID に置き換えてください。確認したいのは `revocationDate == nil` の判定です。これが抜けると、払い戻された購入に対しても機能を開放し続けます。生成コードでここが欠けていないかは、必ず見てください。広告表示の判定を、課金状態とリワード広告による一時解除などの合成で行う場合は、判定を1か所のメソッドに集約しておくと、判定漏れが起きにくくなります。

## 時間の使い方を計測する

生成を取り入れたときの効果は、体感ではなく自分のプロジェクトの数字で見るのが確実です。次の3つを記録しておくと、後から振り返れます。

- 1画面あたり、生成までに要した時間と、レビュー・修正に要した時間を残します。
- レビューで見つかった欠陥の種類（ライフサイクル、権限、メモリ、API の古さ）を数えます。
- 手戻りの原因が「要件の書き方」と「生成の質」のどちらにあったかを分けて書きます。

欠陥の種類を数えていくと、先ほどの仕分け表のどの行に時間をかけるべきかが、自分のプロジェクトの言葉で見えてきます。

## まとめ — 生成の外側にある仕事

見た目の骨格は、生成に任せて時間を節約できる領域です。一方で、タイマーの後始末、権限の非同期処理、メモリを意識した構成、課金の境界条件は、生成が出した「動くように見えるコード」を、時間をかけて検証する領域です。

生成コードの責任は、最終的にアプリを出す側にあります。信頼する部分と疑う部分を分ける目を持っておけば、生成は品質を下げる要因ではなく、見落としを補う道具になります。

最初の一歩として、既存アプリの小さな画面を1つ選び、この記事のチェックリストを片手に、生成コードをレビューしてみてください。1時間もあれば、どこを任せ、どこに自分の確認を足すべきかが見えてきます。
