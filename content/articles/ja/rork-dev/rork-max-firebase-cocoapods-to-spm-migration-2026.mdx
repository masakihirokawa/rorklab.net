2026年に入って、Firebase の公式ドキュメントに気になる告知が載りました。Firebase Apple SDK の新しいバージョンは、2026年10月以降 CocoaPods に公開されなくなる——という内容です。告知のとおり、10月7日の Firebase 13.0.0 から、配信は Swift Package Manager とバイナリ配布だけになりました。この記事を見直している11月下旬は、CocoaPods の trunk 自体が新しい podspec の受付を止める12月2日の、ちょうど1週間ほど前にあたります。

私が保守している iOS アプリは4本です——Beautiful HD Wallpapers、Ukiyo-e Wallpapers、Relaxing Healing、Law of Attraction Everyday。いずれも Firebase の Crashlytics と Analytics を組み込んでいますので、4本とも例外なくこの変更の射程に入ります。

「October 2026 まで時間があるから後でいい」と最初は思いました。しかし実際に移行を始めてみると、想定外の問題がいくつも出てきました。特に Dropbox でプロジェクトを同期している場合の競合コピー問題は、公式ドキュメントに載っていません。dSYM アップロードスクリプトのパスは公式の手順に書かれているものの、CocoaPods 版から書き換えるときの見落としどころは、自分で踏んでみて初めて分かりました。

最初に **Relaxing Healing** を先行検証の対象に選び、その実録をもとに残り3本を移行しました。Rork Max でプロジェクトを管理している方には特有の注意点もあります。移行を検討している方の手間を少しでも省ければと思い、実録として残します。

## なぜ今 CocoaPods から移行しなければならないのか

CocoaPods はかつての iOS 開発の主流パッケージマネージャでした。2010年代に登場し、依存関係の解決という面で多くの開発者を助けてきました。しかし Apple が Swift Package Manager（SPM）を Xcode 11 からネイティブに統合してから、徐々に役割が移り変わってきました。

Firebase チームも公式に SPM 対応を進めており、新機能は SPM 版で先に提供されるケースが増えています。そして今回のアナウンスで、CocoaPods 経由のパッケージ配信が2026年10月に終了することが明示されました。

公式の移行ガイドとリリースノートを2026年11月時点で確かめ直すと、起きたことは次の順番でした。

<table>
<tr><th>日付（2026年）</th><th>出来事</th><th>CocoaPods で使っているアプリへの影響</th></tr>
<tr><td>9月9日</td><td>Firebase 12.19.0。12.x の最後の予定マイナー版で、CocoaPods へ公開される最後の定期リリース</td><td>ここから先の新機能は Podfile では届かない</td></tr>
<tr><td>10月7日</td><td>Firebase 13.0.0。Swift Package Manager とバイナリ配布のみ</td><td><code>pod update</code> しても 13 は入らない</td></tr>
<tr><td>10月22日</td><td>Firebase 12.19.3。Cloud Firestore のセキュリティ更新で、CocoaPods に依存するプロジェクトも対象</td><td>12 系に重大な修正が出る余地はあるが、予定されたものではない</td></tr>
<tr><td>12月2日</td><td>CocoaPods trunk が新しい podspec の受付を恒久的に停止（11月2〜6日に試験停止）</td><td>既存の版は引き続きインストールできる</td></tr>
</table>

要するに、Firebase 12 が CocoaPods に公開される最後のメジャー版で、v12 以前はこの先もインストールできます。Firebase の FAQ にも、更新しなくてもアプリは止まらないと書かれています。

つまり、今日いきなりビルドが通らなくなるわけではありません——ただ、Firebase 13 以降の修正や新機能は、CocoaPods 経由では届きません。App Store の審査基準の変化や iOS の新バージョンへの対応が、少しずつ遅れていくリスクが生まれます。

個人開発者として、このリスクを放置するわけにはいきません。古い SDK が引き起こすクラッシュや審査リジェクトは、そのまま収益の損失に直結します。1日も止めたくないアプリだからこそ、余裕のあるうちに計画的に移しておきたいと考えました。

また、CocoaPods の保守者自身が、公式ブログで trunk の読み取り専用化を段階的に告知してきました。既存のビルドは壊さない方針ですが、trunk 経由で依存が更新されることは、12月2日以降もうありません。

## 期限から逆算する——急ぐ場合と、v12 で待てる場合

最初は「10月まで時間がある」と構えていました。いま思えば、期限の日付そのものより、期限のあとに何が止まるのかを一次情報で確かめていなかったことのほうが問題でした。

**期限の日付ではなく、期限のあとに止まるものを確かめてから、順番を決める**——いまは、この線引きで判断しています。

<table>
<tr><th>状況</th><th>選択</th><th>根拠</th></tr>
<tr><td>新しい Firebase の機能や修正が必要</td><td>今すぐ SPM へ移行</td><td>13.0.0（10月7日）以降は CocoaPods に公開されていない</td></tr>
<tr><td>当面は今の版で足りている</td><td>v12 以前に固定して CocoaPods を継続することも可能</td><td>既存の v12 以前は引き続きインストール可能。ただし CocoaPods trunk は2026年12月2日に新規受付を止める</td></tr>
<tr><td>Xcode を最新にできない環境</td><td>移行前に Xcode の要件を確認</td><td>Firebase 13 の Swift パッケージは Xcode 26.2 より前では解決されない（リリースノート・2026年11月時点）</td></tr>

</table>

「待てる」という選択肢を先に示しておくのは、移行を急かすためではありません。急ぐ理由と待てる理由を並べたうえで、自分のアプリの事情に合わせて選んでいただければ幸いです。

## 私の環境——Rork Max と Firebase の組み合わせ

現在運営している4本の iOS アプリはすべて Firebase を利用しています。

- **Beautiful HD Wallpapers**: Crashlytics + Analytics + Remote Config
- **Ukiyo-e Wallpapers**: Crashlytics + Analytics
- **Relaxing Healing**: Crashlytics + Analytics + Performance Monitoring
- **Law of Attraction Everyday**: Crashlytics + Analytics + Remote Config

これらは Rork Max を活用して開発・メンテナンスを行っていますが、Firebase の設定自体は Xcode 上で直接行っています。Rork Max が生成するプロジェクト構造にも Podfile が含まれる場合があるため、その扱いには注意が必要です（後述）。

最初に **Relaxing Healing** を先行検証に選んだのは、利用しているモジュールが `FirebaseCore`・`FirebaseCrashlytics`・`FirebaseAnalytics`・`FirebasePerformance` の4つと最も多く、ここで問題が出れば他のアプリでも同じパターンに当たるはずだと判断したからです。Firebase Performance Monitoring は Crashlytics よりも少ない記事しかなく、SPM 版の設定情報が薄いため、先に当たっておきたかったという理由もあります。

## 移行前の準備——CocoaPods 依存関係の棚卸し

移行を始める前に、現在の Podfile を丁寧に確認します。Firebase 以外に CocoaPods で入れているライブラリがある場合、それらが SPM 対応しているかどうかを事前に調べておく点が肝心です。

```ruby
# Relaxing Healing の Podfile（移行前）
platform :ios, '14.0'
use_frameworks!

target 'RelaxingHealing' do
  pod 'Firebase/Core'
  pod 'Firebase/Crashlytics'
  pod 'Firebase/Analytics'
  pod 'Firebase/Performance'
end
```

SPM 移行後、同等の機能は以下のパッケージで提供されます。

- `Firebase/Core` → `FirebaseCore`
- `Firebase/Crashlytics` → `FirebaseCrashlytics`
- `Firebase/Analytics` → `FirebaseAnalytics`（または `FirebaseAnalyticsWithoutAdIdSupport`）
- `Firebase/Performance` → `FirebasePerformance`

注意点として、`FirebaseAnalytics` は広告識別子（IDFA）へのアクセスを含む場合があります。ATT フレームワークによる許諾が不要な場合は `FirebaseAnalyticsWithoutAdIdSupport` を選ぶと審査リジェクトのリスクが下がります。私のアプリでは ATT プロンプトを表示しているため通常版を使っていますが、ここは各アプリのポリシーに合わせて選んでいただければと思います。

Firebase 以外に CocoaPods にしか存在しないライブラリがある場合は、Podfile を完全には削除できません。旧版のこの記事では「Firebase 分だけ SPM へ移す混在構成も可能」と書いていましたが、Firebase の移行ガイドは、同じターゲットで CocoaPods と SPM を混ぜると依存の循環やビルドエラーにつながるとして勧めていません。訂正いたします。そうした場合の公式の道筋は、Firebase を `Firebase.zip` の XCFramework で手動導入し、ほかの依存の移行を待つ形です。今回の4本はいずれも Firebase のみが CocoaPods 依存だったため、Podfile を完全に削除できました。

## `Podfile.lock` を捨てる前に、いま動いているバージョンを写し取る

移行の順番でひとつだけ、後から効いてきた判断があります。**SPM に入れる Firebase のバージョンを、いまビルドが通っている版に固定してから始める**ことです。

`pod deintegrate` の勢いで `Podfile.lock` まで消してしまうと、次に Xcode の Package Dependencies で「Up to Next Major Version」を選んだ瞬間、SPM への移行と Firebase 本体のバージョンアップが同時に起きます。この状態で何かが壊れると、原因が「SPM の構成」なのか「新しい Firebase」なのか切り分けられません。私は Relaxing Healing でこれをやってしまい、リンクエラーの調査に1時間ほど余計に使いました。

削除する前に、解決済みのバージョンを控えておきます。

```bash
# Podfile.lock から Firebase の解決済みバージョンだけを抜き出す
grep -E '^[[:space:]]+- Firebase' Podfile.lock | sed 's/^[[:space:]]*//'

# 出力例
#   - Firebase/Analytics (11.8.0)
#   - Firebase/Core (11.8.0)
#   - Firebase/Crashlytics (11.8.0)
#   - Firebase/Performance (11.8.0)
```

この番号を Xcode の Package Dependencies で **Exact Version** として指定します。移行を2段階のコミットに分けると、後から原因を辿れる形になります。

<table>
<tr><th>段階</th><th>やること</th><th>ここで起きた問題の原因</th></tr>
<tr><td><strong>第1コミット</strong></td><td><code>Podfile.lock</code> と同じバージョンを Exact Version で SPM に追加</td><td>ビルド失敗・リンクエラー・dSYM 未アップロードは<strong>SPM 構成側</strong>と確定できる</td></tr>
<tr><td><strong>第2コミット</strong></td><td>Up to Next Major Version へ切り替えて最新版へ更新</td><td>起動時クラッシュ・計測値の変化は<strong>Firebase 側のバージョン差分</strong>と確定できる</td></tr>
</table>

第1コミットが通った時点で `Package.resolved` が生成されます。このファイルは必ずコミットします。SPM における `Podfile.lock` の役割を担うファイルで、これを追跡していないと、別の Mac でクローンしたときに異なるバージョンが引かれます。Xcode のプロジェクト構造によって置き場所が変わるため、見つからない場合は検索します。

```bash
find . -name "Package.resolved" -not -path "*/DerivedData/*"
# .../MyApp.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved
```

## 戻せる状態を作ってから `pod deintegrate` を叩く

`pod deintegrate` は Podfile を消すコマンドではなく、`.xcodeproj` の中身（Build Phases・xcconfig 参照・Framework の紐付け）を書き換えるコマンドです。実行後に「やっぱり戻したい」と思っても、手作業での復元はまず現実的ではありません。

私は Dropbox のバージョン履歴があるから大丈夫だろうと考えていたのですが、これは誤算でした。`.xcodeproj` は複数ファイルの集合体で、Dropbox の巻き戻しは1ファイル単位です。整合性の取れた状態へまとめて戻す用途には向いていません。

始める前に、git で退避点を作ります。

```bash
# 移行前に必ず1コミット作ってタグを打つ
git add -A
git commit -m "chore: snapshot before SPM migration"
git tag pre-spm-relaxing-healing

# 万一戻すとき（Podfile / Podfile.lock / .xcodeproj がまとめて復元される）
git checkout pre-spm-relaxing-healing -- .
pod install
```

あわせて、SPM が生成する作業ファイルを追跡対象から外しておきます。ここを外しておかないと、後述する Dropbox 競合コピーの断片がそのままリポジトリに入り込みます。

```
# .gitignore に追加
.swiftpm/
DerivedData/
*.xcworkspace/xcuserdata/
*.xcodeproj/xcuserdata/
```

タグ名にアプリ名を含めているのは、4本を順番に移行していく過程で `pre-spm` だけだとどのアプリの退避点か分からなくなったためです。細かい話ですが、2本目以降の作業がずいぶん楽になりました。

## 実際の移行手順——Relaxing Healing での先行検証

### Step 1: CocoaPods の Firebase Pod を削除して完全除去

まず `pod deintegrate` を実行します。Podfile から行を削除するだけではなく、CocoaPods が `.xcodeproj` に注入した設定を綺麗に取り除くためにこのコマンドが必要です。

```bash
# プロジェクトルートで実行
cd /path/to/RelaxingHealing
pod deintegrate

# Podfile と関連ファイルを削除
rm -f Podfile Podfile.lock
rm -rf Pods/
```

`pod deintegrate` を実行すると、`.xcodeproj` から CocoaPods 関連の設定が削除されます。この後、`.xcworkspace` ではなく `.xcodeproj` を直接 Xcode で開くようにします。`.xcworkspace` は CocoaPods が生成するファイルで、Pods が不要になったら使いません。

なお公式の移行手順では、`pod deintegrate` を **Xcode を閉じた状態で** 実行し、CocoaPods が生成した `.xcworkspace` も削除する順番です。パッケージの追加は **File → Add Package Dependencies** から行います。

### Step 2: Xcode の Swift Package Dependencies に Firebase を追加

Xcode でプロジェクトを開き、パッケージ依存関係を設定します。

1. プロジェクトナビゲーターでプロジェクトを選択
2. 「Package Dependencies」タブを開く
3. 「+」ボタンをクリック
4. `https://github.com/firebase/firebase-ios-sdk` を入力して検索
5. バージョンを選択（現在の安定版を推奨）
6. 必要なモジュールだけチェックして追加

```
✅ FirebaseCore
✅ FirebaseCrashlytics
✅ FirebaseAnalytics（または FirebaseAnalyticsWithoutAdIdSupport）
✅ FirebasePerformance
```

モジュールは使っているものだけを追加します。全部にチェックを入れると、使っていない Firebase SDK まで含まれてビルドサイズと時間が増加します。Podfile と見比べながら、必要なものだけ選びます。最初のビルドは SPM のパッケージダウンロードが走るため数分かかりますが、2回目以降はキャッシュが効いて早くなります。

追加したのにビルドで Firebase のライブラリが見つからないと言われる場合は、モジュールがターゲットに紐付いていません。公式 FAQ のとおり、ターゲットの **Build Phases → Link Binary with Libraries** に該当のライブラリがあるかを見ます。ウィジェットや通知拡張のようにターゲットが複数あるアプリでは、ここで漏れやすいのです。

### Step 3: Build Settings の CocoaPods 残存設定をクリーンアップ

`pod deintegrate` は多くの設定を取り除きますが、一部の設定が残ることがあります。Xcode の Build Settings で `PODS` と検索して、残存している参照がないかを確認します。

```
⚠️ 残存しがちな設定（削除が必要）:
  Header Search Paths: $(PODS_ROOT)/...
  Library Search Paths: $(PODS_ROOT)/...
  Framework Search Paths: $(PODS_ROOT)/...
```

ただし `-ObjC` だけは、機械的に消さずに残します。公式のインストール手順では、Analytics を推移的に含める構成で `-ObjC` が必要とされています。この記事の旧版は「SPM では不要」と書いていましたが、誤りでしたので訂正します。いまは外さずに残し、ビルドと実機確認が通ってから整理する順番にしています。

それ以外を削除したら、ビルドを走らせて通ることを確認します。ビルドが通れば基本的な移行は完了です。

## 落とし穴 1: Dropbox 競合コピー問題

ここが最も詰まった箇所でした。プロジェクトを Dropbox で同期しているため、SPM が生成する `.swiftpm/xcuserdata` ディレクトリが Dropbox の競合コピーを引き起こしたのです。

症状としては、Xcode を開くたびに `error: cannot find module 'Firebase' in scope` のエラーがエディタに表示されます。しかしビルドを実行すると通る——という不安定な状態です。エディタのインデックスが正常に機能せず、補完も壊れた状態になります。

原因は `.swiftpm/xcuserdata` を Dropbox が同期しようとして、複数の Mac 間でファイルロックの競合が起きていたことでした。CocoaPods 時代にも似た症状に当たったことがあるのですが、SPM では競合の起きるパスが変わるため、同じ穴にもう一度落ちました。

解決策は `xattr` コマンドで該当ディレクトリを Dropbox の同期対象外にすることです。Dropbox のヘルプセンターが「ファイルやフォルダを無視する」方法として案内している属性で、macOS では次の形になります。

```bash
# プロジェクトのルートで実行
xattr -w com.dropbox.ignored 1 ".swiftpm"
xattr -w com.dropbox.ignored 1 "$(find . -name 'xcshareddata' -path '*swiftpm*' 2>/dev/null | head -1)"

# Derived Data が Dropbox 内にある場合も同様に
# （通常は ~/Library/Developer/Xcode/DerivedData に置くことを推奨）
```

この設定を適用した後、Xcode を完全に終了し、Dropbox の同期が完了するのを待ってから再起動します。再起動後はエディタのエラーが消えて正常な状態に戻ります。`xattr` による Dropbox 除外は再起動後も維持されるため、一度設定すれば以後の操作で繰り返す必要はありません。

Dropbox でプロジェクトを管理している個人開発者の方は、移行前にこのステップを先に済ませておくと、後から詰まるのを防げます。

なお、Dropbox の競合コピーが発生した場合は「ファイル名 (競合しているコピー 〜).xcuserdata」のようなファイルが生成されます。これが `.xcodeproj` 内に混入すると、Xcode が同名のファイルが2つあると判断してエラーになることがあります。移行後に原因不明のビルドエラーが出たときは、次の1行で競合コピーを探すところから始めています。

```bash
find . \( -name '*競合しているコピー*' -o -name '*conflicted copy*' \) -not -path '*/DerivedData/*'
```

## 落とし穴 2: dSYM アップロードスクリプトのパス変更

Firebase Crashlytics を使っている場合、クラッシュのシンボル解析のために dSYM ファイルをアップロードするビルドフェーズスクリプトが必要です。CocoaPods 版での設定はこうなっていました。

```bash
# CocoaPods 版（旧・移行後は動かない）
"${PODS_ROOT}/FirebaseCrashlytics/run"
```

SPM 移行後は `$PODS_ROOT` が存在しないため、このスクリプトはビルドエラーになります。この問題が厄介なのは、スクリプトが**サイレントに失敗する設定**になっていた場合、ビルドは通るのに dSYM がアップロードされず、App Store Connect でクラッシュレポートがシンボル化されないという状況が続くことです。

SPM 版での正しいパスは以下の通りです（公式の手順と同じ書き方です）。

```bash
# Swift Package Manager 版（新）
"${BUILD_DIR%/Build/*}/SourcePackages/checkouts/firebase-ios-sdk/Crashlytics/run"
```

このパスが Xcode のバージョンや DerivedData の場所によって変わることを考慮して、動的に検索するスクリプトを使うとより堅牢です。

```bash
#!/bin/bash
# Firebase Crashlytics dSYM upload — SPM版
# Xcode の Run Script Build Phase に追加

FIREBASE_RUN=$(find "${BUILD_DIR%/Build/*}/SourcePackages/checkouts" \
  -name "run" \
  -path "*/Crashlytics/run" \
  2>/dev/null | head -1)

if [ -z "$FIREBASE_RUN" ]; then
  echo "error: Firebase Crashlytics run script not found."
  exit 1
fi

"$FIREBASE_RUN"
```

見つからないときに `exit 0` で通してしまうと、冒頭で触れた「ビルドは通るのに dSYM が届かない」状態を、スクリプト自身が作ってしまいます。旧版の記事ではここを `exit 0` にしていましたが、`exit 1` に改めました。

もう一点、このスクリプトは Run Script フェーズの**最後**に置きます。公式の手順では、Input Files にも次の項目を並べる形です。

```
${DWARF_DSYM_FOLDER_PATH}/${DWARF_DSYM_FILE_NAME}
${DWARF_DSYM_FOLDER_PATH}/${DWARF_DSYM_FILE_NAME}/Contents/Resources/DWARF/${PRODUCT_NAME}
${DWARF_DSYM_FOLDER_PATH}/${DWARF_DSYM_FILE_NAME}/Contents/Info.plist
$(TARGET_BUILD_DIR)/$(UNLOCALIZED_RESOURCES_FOLDER_PATH)/GoogleService-Info.plist
$(TARGET_BUILD_DIR)/$(EXECUTABLE_PATH)
```

スクリプトのサンドボックス（`ENABLE_USER_SCRIPT_SANDBOXING`）と `ENABLE_DEBUG_DYLIB` を両方有効にしている場合は、`.../Contents/Resources/DWARF/${PRODUCT_NAME}.debug.dylib` も追加します。入力ファイルが足りないと、サンドボックスがスクリプトからのファイル読み取りを拒み、これも「静かに届かない」原因になります。

また、**Build Settings → Debug Information Format** が `DWARF with dSYM File` になっているかを必ず確かめます。公式の手順では、ビルド種別を問わずこの値を指定する形です。`DWARF` のみではシンボルファイルが出力されず、クラッシュレポートで行番号が表示されません。

```
Release ビルドの設定:
  ✅ DWARF with dSYM File → シンボル化されたクラッシュレポートが見られる
  ❌ DWARF のみ → 行番号なし、アドレスのみ表示
```

## 落とし穴 3: ビルドの編集時エラーが消えない

SPM 移行直後によく起きる問題として、ビルドは通るのに Xcode エディタ上で `module 'FirebaseCore' not found` のエラーが赤く表示され続けることがあります。補完も壊れた状態になります。

これは Xcode のインデックスキャッシュが古い状態のままになっているために起きます。

```bash
# ステップ1: Derived Data を削除
rm -rf ~/Library/Developer/Xcode/DerivedData/<AppName>-*

# その後 Xcode を再起動

# ステップ2: Clean Build Folder (Cmd+Shift+K)

# ステップ3: File → Packages → Reset Package Caches
```

この3ステップで大抵は解消されます。それでも残る場合は、プロジェクトを閉じてから `.xcodeproj` を再度開き直すと直ることがほとんどです。初回移行後に1〜2回発生しますが、以後は安定します。

この現象は移行直後のほか、Xcode のメジャーアップデート後にも発生することがあります。その場合も同じ手順で解消できます。Derived Data の削除は「プロジェクトを壊す操作」ではなく「ビルドキャッシュを再構築させる操作」なので、躊躇わずに実行して大丈夫です。削除した Derived Data は次回のビルド時に自動的に再生成されます。

## 移行後のビルド時間最適化

Firebase を SPM で追加した後、初回フルビルドが以前より大幅に遅くなるケースがあります。これは SPM パッケージの初回コンパイルキャッシュが生成されるためで、正常な動作です。しかし毎回遅い場合は対応が必要です。

Build Phases の Run Script で「Based on dependency analysis」を有効にすると、変更がない場合はスクリプトの実行をスキップするようになります。

```
Build Phases → Run Script（各フェーズ）
→ ✅「Based on dependency analysis」にチェックを入れる
→ Firebase Crashlytics の dSYM スクリプトも毎回実行しなくなる
```

Relaxing Healing では、この設定を有効にした後で差分ビルド時間が6分から約90秒に戻りました。コードを書いている間はフルビルドではなく差分ビルドが走るため、この設定の効果は日常的な開発体験に直結します。

4本を並行して保守していると、1本のビルドが遅いだけでその日の切り替え回数が目に見えて減ります。差分ビルドを90秒台に戻せたことは、移行そのものよりも日々の作業に効きました。

## 残り3本への展開——パターン化による効率化

Relaxing Healing での経験をもとに、残り3本（Beautiful HD Wallpapers・Ukiyo-e・Law of Attraction）の移行を行いました。各アプリ共通の事前準備リストを作ることで、1本あたりの移行時間を短縮できました。

最初の Relaxing Healing では試行錯誤で4時間かかりましたが、2本目以降は平均30分程度で完了しました。その差を生んだのは主に2点——Dropbox 競合コピーへの先手対応と、dSYM スクリプトのテンプレートを使い回せたことです。

```bash
#!/bin/bash
# pre-spm-migration.sh — 各アプリの移行前に実行

echo "1. CocoaPods を除去..."
pod deintegrate

echo "2. Podfile 関連ファイルを削除..."
rm -f Podfile Podfile.lock
rm -rf Pods/

echo "3. Dropbox 同期除外を設定..."
xattr -w com.dropbox.ignored 1 ".swiftpm" 2>/dev/null || true

echo "4. 現在の dSYM スクリプト内容をバックアップ..."
grep -r "PODS_ROOT.*Crashlytics" . --include="*.pbxproj" > dSYM_backup.txt 2>/dev/null || true

echo "完了。Xcode で .xcodeproj を開いて Firebase を Package Dependencies から追加してください。"
```

このスクリプトを実行してからXcodeを開くことで、移行後に遭遇する典型的な問題のうち2つを予防できます。

## AppLovin MAX メディエーションとの共存

Beautiful HD Wallpapers では AdMob メディエーションに AppLovin MAX を利用しています。AppLovin MAX の iOS SDK も CocoaPods で管理していたため、Firebase と同時に SPM 移行を検討しました。

AppLovin MAX は SPM 対応済みですが、メディエーションアダプタ（Liftoff・InMobi・Unity Ads）が個別に SPM 対応しているかを確認する必要があります。2026年5月時点では主要アダプタの多くが SPM 対応済みですが、マイナーなアダプタでは CocoaPods のみの場合があります。対応状況は各パートナーの公式ドキュメントで確かめるのが確実です。

```
AppLovin MAX SPM 移行確認リスト（2026-05時点）:
✅ AppLovin MAX SDK 本体: SPM 対応済み
✅ Liftoff アダプタ: SPM 対応済み
✅ InMobi アダプタ: SPM 対応済み
✅ Unity Ads アダプタ: SPM 対応済み
⚠️ 一部マイナーアダプタ: 要個別確認
```

AppLovin MAX を CocoaPods から SPM に移行する場合も、Firebase と同じ流れで進められます。旧版では「`AppLovinSettings.plist` が別途必要」と書いていましたが、2026年11月時点の AppLovin 公式の統合手順にはその記述がなく、SDK キーは初期化コードの `ALSdkInitializationConfiguration` に渡す形でした。こちらも訂正いたします。移行後は、初期化コードが SPM 版の import のまま通るかを最初に確かめます。

もう一点、前述のとおり Firebase は同じターゲットでの CocoaPods と SPM の混在を勧めていません。広告の SDK だけしばらく CocoaPods に残す段階を挟むなら、その期間はできるだけ短く切るのがよいと、いまは考えています。

## Rork Max ユーザーへの注意点——プロジェクト再生成時のPodfile復活

Rork Max でプロジェクトを管理している場合、**プロジェクトの再生成時に Podfile が復元される可能性**があります。

Rork Max は iOS プロジェクトを生成する際に、設定によっては Podfile を含むプロジェクト構造を出力します。SPM 移行後に Rork Max でコードを再生成した場合、手動で削除した Podfile が復活しないよう注意が必要です。

対処法を2つご紹介します。

**方法A**: Rork Max 側の設定で CocoaPods の出力を止めるやり方です。ただし、そうした設定項目があるかは、2026年11月時点の Rork 公式の情報では確認できていません。見つからない場合は方法B に頼ります。

**方法B**: Rork Max での再生成後に実行する確認スクリプトをワークフローに組み込みます。

```bash
#!/bin/bash
# post-rork-generate.sh — Rork Max 再生成後に必ず実行する

if [ -f "Podfile" ]; then
  echo "⚠️  Podfile が検出されました（Rork Max が再生成した可能性）"
  echo "🗑  CocoaPods ファイルを削除して SPM の設定を保持します..."
  rm -f Podfile Podfile.lock
  rm -rf Pods/
  echo "✅  削除完了。Xcode で Package Dependencies を確認してください。"
fi
```

このスクリプトは数秒で終わりますが、気づかないうちの後戻りを防ぐ安全網になります。Rork Max でコードの再生成を行う頻度が高い方は、CI パイプラインに組み込んでおくと安心です。

## Firebase バージョン管理——移行後の更新戦略

SPM 移行後のもう一つのメリットは、Firebase SDK のバージョン管理が Xcode の UI だけで完結することです。CocoaPods では `pod update Firebase` をターミナルで実行し、`Podfile.lock` の差分を目で追う必要がありましたが、SPM では Xcode の「Package Dependencies」タブから GUI でバージョンを更新できます。

ただし、Firebase のメジャーバージョンアップ時は破壊的変更が含まれることがあります。私が実践しているのは、まず1本のアプリで新バージョンを試してから残りのアプリに展開するという段階的な更新です。Relaxing Healing が先行検証アプリの役割を果たしており、そこで問題がなければ他のアプリに同じバージョンを適用します。

バージョン指定には「Up to Next Major Version」を使うのが一般的ですが、安定性を優先する場合は「Exact Version」を指定しておき、意図したタイミングだけ更新するという方法もあります。個人開発でアプリが安定して動いているなら、メジャーバージョンの更新は変更ログを確認してからにすることをお勧めします。

Firebase SDK のバージョンアップ情報は GitHub のリリースページや公式ブログで確認できます。特にメジャーリリース前後は Crashlytics と Analytics の初期化コードの書き方が変わることがあります。

私自身、リリースノートを読み飛ばしたままマイナー更新を適用し、Analytics の自動収集イベントの扱いが変わっていたことに数日経ってから気づいたことがあります。焦らず、TestFlight で確認してからリリースするペースを保つほうが、結局は速いと感じています。

## 移行後の動作確認チェックリスト

SPM 移行が完了したら、以下の項目を実機で確認します。

```
□ アプリが起動する（クラッシュなし）
□ Firebase Analytics のイベントが Firebase Console に届いている
□ テストクラッシュ（fatalError("Crash was triggered") など）が記録される
□ dSYM がシンボル化されている（App Store Connect で行番号確認）
□ Release ビルドで Archive → Distribute が完走する
□ TestFlight にアップロードして実機で動作確認
□ Build Settings に $(PODS_ROOT) の参照がゼロ件
□ プロジェクトルートに Podfile がない
```

dSYM のシンボル化確認が最も見落とされやすい項目です。Archive 直後に Firebase Console の Crashlytics ページでテストクラッシュを確認して、スタックトレースに行番号とクラス名が表示されているかを目で確かめます。アドレスのみが表示されている場合は dSYM アップロードが機能していません。

なお、旧版のチェックリストにあった `Crashlytics.crashlytics().crash()` という呼び出しは、公式の API にありません。公式のサンプルは `fatalError("Crash was triggered")` で、Xcode のデバッガを切り離した状態（Run 後にアプリを終了し、端末から起動し直す）で実行します。デバッガが付いたままだと、クラッシュレポートは送られないのです。

## よくある誤解を三つ、公式の文言で正しておきます

**「10月を過ぎたら、CocoaPods のアプリは動かなくなる」**——そうではありません。Firebase の FAQ は、v12 以前は CocoaPods のエコシステムが続く限りインストールでき、動作すると明記しています。`pod install` を回している CI も、そのまま動きます。止まったのは、新しい版が届くことです。

**「CocoaPods に残ると、12 系にはもう何も来ない」**——必ずしもそうではありません。10月22日の 12.19.3 は Cloud Firestore のセキュリティ更新で、CocoaPods に依存するプロジェクトも対象だと書かれていました。ただし 12.19.0 が最後の予定されたリリースとされているので、当てにして待つものではないと、私は受け止めています。

**「Firebase だけ SPM へ移して、ほかは CocoaPods のまま混ぜればよい」**——Firebase の移行ガイドは、同じターゲットでの混在を、依存の循環やビルドエラーの原因になるとして勧めていません。ほかの依存が SPM に対応していないなら、Firebase は手動導入（`Firebase.zip`）で揃えるのが公式の案内です。

## 次に詰まる一歩——第2コミットで Firebase 13 へ上げる前に

第1コミットで SPM への移行が通ると、次は Up to Next Major Version に切り替えて 13 系へ上げる段階です。2026年11月時点のリリースノート（13.0.0〜13.2.0）を読んで、私が先に確かめておきたいと感じたのは次の三つでした。

- 最小対応 OS が iOS 15.0 へ上がっていること（冒頭の Podfile は `platform :ios, '14.0'` でした）
- `FirebaseMLModelDownloader` が削除されていること
- 13.0.0 の時点では、Firebase 13 に対応した Google Sign-In の SPM 版がまだ出ておらず、後日とされていたこと

三つ目は、ログインに Google アカウントを使っているアプリなら、第2コミットの前に現状を必ず見ておきたい項目です。

クラッシュの収集をどこまで Crashlytics に任せるかは、[無料枠で始める EAS Observe と、それでも Crashlytics を残す理由](/articles/rork-basics/eas-observe-free-tier-native-crash-gap-first-setup)で、ネイティブのクラッシュを誰が拾うかという観点から整理しています。申請の前日にどの依存から確かめるかは、[ストア申請の前日に、依存ライブラリのどれから確かめるか](/articles/rork-business/store-submission-dependency-check-order-for-non-engineers)が順番の叩き台になると思います。`.swiftpm/` や `xcuserdata` を追跡から外す考え方は、[Rork のコードをエクスポートしたら、git init より先に .gitignore を用意します](/articles/rork-basics/rork-export-gitignore-before-git-init)と同じ根を持っています。

## 全体を振り返って——まず1本、12 系に固定したまま移す

CocoaPods の期限はもう過ぎたように見えて、実際に止まったのは「新しい版が届くこと」だけです。焦って 13 まで一気に上げるより、いま動いている版のまま SPM へ移し、そのあとで上げる——この二段構えが、4本を通していちばん効きました。最初の Relaxing Healing で4時間かかった時間のほとんどは、Dropbox 競合と dSYM スクリプトのパスの調査でした。

Rork Max を使っている方は、プロジェクト再生成後に Podfile が戻っていないかだけ、毎回見ていただければと思います。それ以外の手順は、一般的な iOS プロジェクトと変わりません。

移行後しばらくは、Crashlytics のダッシュボードを普段より頻繁に見るようにしています。設定ミスは、エラーではなくクラッシュレポートの欠落として表れることが多いからです。1週間問題なく届いていれば、移行はひと区切りと考えてよいと思います。それまでは App Store への更新を控え、TestFlight で様子を見るほうが安全です。

まずは、Firebase のモジュールがいちばん少ないアプリの `Podfile.lock` から、解決済みのバージョンを書き写すところから始めていただければ幸いです。12月2日を過ぎても、その数行があれば戻り道は残ります。
