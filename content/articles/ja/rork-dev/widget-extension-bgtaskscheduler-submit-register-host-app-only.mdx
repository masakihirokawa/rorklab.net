夕方になるとホーム画面のウィジェットが昨日の一枚のまま止まる、という問題を片づけた翌週のことでした。次に届いた要望は「アプリを一度も開かない日でも、朝には次の壁紙に変わっていてほしい」というものです。

素直に考えれば、更新の主語はウィジェット側にあります。表示しているのはウィジェットなのですから、次の画像を用意する仕事も同じターゲットに持たせればよい——そう考えて、Widget Extension のコードに `BGAppRefreshTaskRequest` を組み込みました。

ビルドは通りました。`submit` も `true` を返しました。それなのに、翌朝の画面は前日のままでした。原因にたどり着くまで半日かかっております。

## submit は通り、register だけが拒まれます

先に結論をお伝えします。`BGTaskScheduler` は、拡張から依頼を出すことは許していますが、依頼を受け取る側になることは許していません。SDK のヘッダには `registerForTaskWithIdentifier:usingQueue:launchHandler:` に対して拡張では使えない旨の注釈が付いており、その理由が「Only the host application may register launch handlers」と一行だけ添えられています（[BackgroundTasks.framework の BGTaskScheduler.h](https://github.com/xybp888/iOS-SDKs/blob/master/iPhoneOS13.0.sdk/System/Library/Frameworks/BackgroundTasks.framework/Headers/BGTaskScheduler.h)）。

同じヘッダの説明文には、拡張から依頼を出せる場合があること、そして背景作業のために起動されるのはホストアプリだけであることが、続けて書かれています。つまり `submit` の成功は「受け付けました」以上の意味を持ちません。

Apple の公式リファレンスにも、launch handler の登録はすべて `applicationDidFinishLaunching` が終わるまでに済ませること、同じ識別子を二度登録するとアプリが終了させられることが書かれています（[register(forTaskWithIdentifier:using:launchHandler:)](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/register%28fortaskwithidentifier:using:launchhandler:%29)）。拡張にはその起動の流れがありませんので、登録を置く場所が構造の上で存在しないのです。

私が書いてしまったのは、次のような拡張側のコードでした。動きはします。ただし、受け手がどこにもいません。

```swift
// WallpaperWidget/RefreshScheduler.swift（この設計は行き止まりです）
import BackgroundTasks

enum RefreshScheduler {
    static func scheduleFromWidget() {
        let request = BGAppRefreshTaskRequest(identifier: "net.dolice.wallpaper.dailyRefresh")
        request.earliestBeginDate = Calendar.current.date(byAdding: .hour, value: 6, to: Date())
        do {
            try BGTaskScheduler.shared.submit(request)
            // ここは通ります。true が返り、ログにも「予約できた」と出ます。
            // しかし launchHandler は拡張に登録できないため、誰も起きてきません。
            NSLog("[widget] submitted dailyRefresh")
        } catch {
            NSLog("[widget] submit failed: \(error)")
        }
    }
}
```

`submit` が例外を投げないので、ログには成功しか残りません。落ちないぶん、気づくのが遅れます。私はこの種の無言の失敗をいちばん警戒しております——落ちる不具合より、黙って何もしない不具合のほうが、見つかるまでに時間がかかるからです。

本番運用でいちばん怖いのは、対処のしようがある不具合ではなく、こうして誰にも報告されない取りこぼしなのかもしれません。クラッシュしていれば計測に乗りますが、これは乗りません。

## Info.plist の台帳は親アプリ側にしかありません

もう一つ、拡張に更新を持たせようとすると必ずぶつかる壁があります。識別子の許可リストです。

`BGTaskScheduler` の `NotPermitted`（Code=3）は、`UIBackgroundModes` に適切なモードが含まれていないか、識別子が `BGTaskSchedulerPermittedIdentifiers` に無い場合に返ります。ここで大事なのは、その配列が置かれるべき場所がアプリの Info.plist だという点です（[BGTaskScheduler.Error.Code.unavailable の説明](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/error/code/unavailable) と併せて読むと、Code=1 と Code=3 の役割分担がはっきりします）。

### 拡張の Info.plist に書いても効きません

Xcode のターゲット一覧で Widget Extension を選び、そちらの Info.plist に `BGTaskSchedulerPermittedIdentifiers` を足したくなります。私も一度そうしました。エラーは何も出ません。何も起きないだけです。

### Rork や Expo の構成では app.config 側に書きます

Rork が出力するのは React Native と Expo の構成ですので、Info.plist を手で編集するのではなく、設定ファイル側に寄せます。

```js
// app.config.js — 親アプリの Info.plist に入る場所へ書きます
export default {
  expo: {
    ios: {
      bundleIdentifier: "net.dolice.wallpaper",
      infoPlist: {
        UIBackgroundModes: ["fetch", "processing"],
        BGTaskSchedulerPermittedIdentifiers: [
          "net.dolice.wallpaper.dailyRefresh"
        ]
      }
    }
  }
};
```

`BGAppRefreshTask` に要るのは `fetch` で、`processing` は `BGProcessingTask` を使うときのものです。私はこのあと触れる expo-background-task も併用するため両方を入れていますが、片方しか使わないなら、使う側だけに絞っておくほうが審査で説明しやすくなります。

### 識別子は 1 か所で定義して両方から参照します

親アプリと拡張で識別子の文字列がずれると、`register` と `submit` が別々のタスクを指すことになり、これも無言で外れます。私は共有ターゲットに定数を置いて、両方からそれを参照する形にしております。

```swift
// Shared/RefreshTaskID.swift — 親アプリと Widget Extension の両方に含めます
public enum RefreshTaskID {
    public static let daily = "net.dolice.wallpaper.dailyRefresh"
    public static let appGroup = "group.net.dolice.wallpaper"
    public static let widgetKind = "DailyWallpaperWidget"
}
```

## 更新の主語を親アプリへ戻します

行き止まりを認めたあと、設計を書き直しました。更新の主語は親アプリです。ウィジェットは、書き込まれた結果を読んで描くだけの存在に戻します。

親アプリ側は三つの仕事を順番に引き受けます。起動時に `register` すること、目覚めたときに次の画像を決めて App Group へ書くこと、そして書き終えてから `WidgetCenter` に再読み込みを頼むことです。

```swift
// AppDelegate.swift（ホストアプリ側。register はここでしか行えません）
import BackgroundTasks
import WidgetKit

func application(_ application: UIApplication,
                 didFinishLaunchingWithOptions options: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {

    // didFinishLaunching が終わる前に済ませます。同じ識別子を二度登録するとアプリが終了させられます。
    BGTaskScheduler.shared.register(forTaskWithIdentifier: RefreshTaskID.daily,
                                    using: nil) { task in
        handleDailyRefresh(task as! BGAppRefreshTask)
    }
    scheduleNextRefresh()
    return true
}

func scheduleNextRefresh() {
    let request = BGAppRefreshTaskRequest(identifier: RefreshTaskID.daily)
    // 直近すぎる時刻を指定すると、OS 側で丸められて意図とずれます。
    request.earliestBeginDate = Calendar.current.date(byAdding: .hour, value: 6, to: Date())
    do {
        try BGTaskScheduler.shared.submit(request)
    } catch {
        NSLog("[app] submit failed: \(error)")
    }
}

func handleDailyRefresh(_ task: BGAppRefreshTask) {
    // 次の実行を先に予約します。ここを忘れると 1 回きりで終わります。
    scheduleNextRefresh()

    let work = Task {
        let picked = await DailyWallpaperPicker.pickNext()
        SharedStore.write(picked)                     // App Group のコンテナへ保存します
        WidgetCenter.shared.reloadTimelines(ofKind: RefreshTaskID.widgetKind)
        task.setTaskCompleted(success: true)
    }

    task.expirationHandler = {
        work.cancel()
        task.setTaskCompleted(success: false)
    }
}
```

書き込みと再読み込みの順番は入れ替えられません。先に `reloadTimelines` を呼ぶと、ウィジェットは古い値を読み直すだけになります。私はここを一度取り違えて、直したはずの症状が再発しました。

拡張から予約したい場面が残る場合でも、`submit` だけを拡張に置き、`register` とハンドラは親アプリに置く形になります。依頼者と受取人を分けて考えると、構成が一気に見通しやすくなります。

どちらを採用する場合でも、私は最初の一歩として親アプリ単独の構成から始めることを推奨します。拡張からの予約を足すのは、親アプリ側で確実に起きることを確認してからで遅くありません。切り分けの手数がそのぶん減ります。

## 予算は 2 つあり、混同すると診断を誤ります

もう一段深いところに、私が長く取り違えていた点があります。ここで効いてくる予算は 1 つではありません。

一つ目は `BGAppRefreshTask` が実際に起きられるかどうかで、これは利用頻度や電池残量を見た OS の裁量です。二つ目は WidgetKit がタイムラインを描き直せる回数で、[WidgetCenter の解説](https://developer.apple.com/documentation/widgetkit/widgetcenter)にあるとおり、再読み込みの要求は出せても即座の実行が約束されるものではありません。Apple の「[Keeping a widget up to date](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date)」によれば、よく見られるウィジェットで 1 日あたりおおむね 40〜70 回、間隔にして 15〜60 分ほどが目安とされています（2026年11月時点・公式で確認）。この数字はあくまで目安で、ウィジェットごとに別々に配分されます。

この二つを一つだと思っていると、診断が必ずずれます。私が踏んだ落とし穴もここでした。回避の仕方は単純で、症状をどちらの層のものか先に決めてから手を動かすことです。実際に見分ける手がかりは次のとおりです。

## submit が true を返しても、そのまま信じないでください

無言の失敗を防ぐために、私は予約と実行を自己申告させるようにしました。予約が残っているかは `getPendingTaskRequests` で確認できます。実行されたかどうかは、ハンドラの中から App Group へ時刻を書いて、開発用の画面に出しています。

```swift
// 開発ビルドの設定画面に置いている自己申告ビューです
import BackgroundTasks
import SwiftUI

struct RefreshDiagnosticsView: View {
    @State private var pending: [String] = []
    @State private var lastRun: Date? = SharedStore.lastRefreshAt()

    var body: some View {
        List {
            Section("予約されている依頼") {
                if pending.isEmpty {
                    Text("なし（submit が通っていても、ここが空なら消えています）")
                } else {
                    ForEach(pending, id: \.self) { Text($0) }
                }
            }
            Section("最後に走った時刻") {
                Text(lastRun.map { $0.formatted() } ?? "記録なし")
            }
        }
        .task {
            let requests = await BGTaskScheduler.shared.pendingTaskRequests()
            pending = requests.map(\.identifier)
        }
    }
}
```

見るべき順番は決めてあります。App Group の最終実行時刻が空なら親アプリが起きていないので、識別子と Info.plist を疑います。時刻は新しいのに表示が古いなら、起きてはいるので `reloadTimelines` の側を疑います。この 2 段階に分けるだけで、切り分けの時間がはっきり短くなりました。

Code=1 が返ってくる場合の原因の並べ方は、[BGTaskScheduler.submit が Error Code=1 で失敗するときの切り分け手順](/articles/rork-dev/rork-ios-bgtaskscheduler-submit-error-code-1-unavailable-fix)にまとめてあります。本稿の内容と合わせると、拡張まわりの取りこぼしまで含めて追えるはずです。

## 背景タスクを使わずに済む構成と、使う場合の選び方

register を親アプリへ移したあと、私はもう一度立ち止まりました。そもそも、この更新に背景タスクは要るのだろうか、という問いです。

壁紙のように「次に出す一枚」が前もって決められる場合、ウィジェットのタイムラインに数日ぶんのエントリを先に積んでおけば、OS が時刻どおりに切り替えてくれます。誰も起きる必要がありません。背景タスクが要るのは、次の一枚をネットワークから取ってくる、ユーザーの操作履歴から選び直す、といった「その時点にならないと決まらない」更新のときだけです。

<thead>
<tr><th>構成</th><th>向いている更新</th><th>主な制約</th><th>Rork／Expo での書き方</th></tr>
</thead>
<tbody>
<tr><td>タイムラインに数日ぶんのエントリを積む</td><td>次の内容が前もって決まっているもの</td><td>エントリを作った時点で手元にある画像しか出せません</td><td>Widget Extension の Swift だけで完結します</td></tr>
<tr><td>親アプリの BGAppRefreshTask（Swift で書く）</td><td>短時間の取得と書き込みで済むもの</td><td>実行の時刻と回数は OS の裁量です。UIBackgroundModes に fetch が要ります</td><td>AppDelegate を触るため、config plugin で差し込みます</td></tr>
<tr><td>expo-background-task（JavaScript で書く）</td><td>JS 側のロジックを使い回したいもの</td><td>iOS では BGTaskScheduler を使い、識別子は固定です。シミュレータでは動きません</td><td>app.config の plugins と JS のタスク定義で済みます</td></tr>
</tbody>
</table>

判断の基準は一つにまとめられます。**次の一枚が今の時点で決められるならタイムラインに積み、決められないときだけ親アプリを起こします。** 私の壁紙アプリでは、配信予定が前もって決まっている枠はタイムラインへ寄せ、新着を取りにいく枠だけを背景タスクに残しました。起こす回数そのものが減ったので、電池への言い訳を考える必要もなくなりました。

タイムラインに積む側は、たとえば次のように書きます。`policy: .atEnd` にしておくと、積んだエントリを使い切ったところで WidgetKit がもう一度タイムラインを取りにきます。

```swift
// DailyWallpaperWidget/Provider.swift — 背景タスクなしで 1 週間ぶんを先に渡します
import WidgetKit

struct Provider: TimelineProvider {
    func getTimeline(in context: Context,
                     completion: @escaping (Timeline<WallpaperEntry>) -> Void) {
        let calendar = Calendar.current
        let start = calendar.startOfDay(for: Date())
        let entries: [WallpaperEntry] = (0..<7).compactMap { offset in
            guard let day = calendar.date(byAdding: .day, value: offset, to: start),
                  let item = BundledSchedule.item(for: day) else { return nil }   // 配信予定表から引きます
            return WallpaperEntry(date: day, item: item)
        }
        completion(Timeline(entries: entries, policy: .atEnd))
    }
    // placeholder と getSnapshot は省略しています
}
```

ここでいう `BundledSchedule` は、拡張から読める場所（拡張のバンドルか App Group のコンテナ）に置いた配信予定表です。予定表を親アプリが書き換えたときだけ `reloadTimelines` を呼べば、残りは OS に任せられます。

## Rork／Expo の構成で register を親アプリに置く

Rork が書き出すのは Expo の構成ですので、`ios/` フォルダの AppDelegate を手で直しても、Continuous Native Generation（CNG）で prebuild をやり直すたびに作り直されます。私は一度、手で足した `register` の行が prebuild のあとに消えていて、翌朝また止まったウィジェットを前に手が止まりました。

ネイティブの Swift で書くなら、AppDelegate への差し込みは config plugin に持たせます。SDK 57 以降の AppDelegate.swift の形で詰まったときの確かめ方は、[prebuild が standard Expo SDK 57 Swift AppDelegate で止まったときの3行](/articles/app-dev/expo-enable-scene-support-prebuild-standard-appdelegate-error)に書き残しております。

JavaScript で済ませたい場合は、`expo-background-task` が親アプリ側で BGTaskScheduler を扱ってくれます。Expo の公式ドキュメント（2026年11月時点・SDK 58 の版で確認）によると、iOS では `UIBackgroundModes` の `processing` と、識別子 `com.expo.modules.backgroundtask.processing` が必要で、CNG を使っていれば prebuild が自動で足します。手で `BGTaskSchedulerPermittedIdentifiers` を書く必要はありません。

ウィジェットへ値を渡す部分は、Widget Extension をターゲットとして追加する `@bacons/apple-targets` の `ExtensionStorage` が使えます。App Group の UserDefaults に書き、そのあとで再読み込みを頼む形です。

```ts
// src/background/dailyWallpaper.ts — タスクの定義はモジュールの最上位に置きます
import * as BackgroundTask from 'expo-background-task';
import * as TaskManager from 'expo-task-manager';
import { ExtensionStorage } from '@bacons/apple-targets';
import { pickNextWallpaper } from './picker';

const TASK_NAME = 'daily-wallpaper-refresh';
const storage = new ExtensionStorage('group.net.dolice.wallpaper');

TaskManager.defineTask(TASK_NAME, async () => {
  try {
    const next = await pickNextWallpaper();
    storage.set('nextWallpaper', JSON.stringify(next)); // 先に書きます
    storage.set('lastRefreshAt', Date.now());           // 自己申告用の時刻です
    ExtensionStorage.reloadWidget('DailyWallpaperWidget'); // 書いてから頼みます
    return BackgroundTask.BackgroundTaskResult.Success;
  } catch {
    return BackgroundTask.BackgroundTaskResult.Failed;
  }
});

export async function enableDailyRefresh() {
  // 単位は分です。指定した間隔より前には走りませんが、いつ走るかは OS が決めます
  await BackgroundTask.registerTaskAsync(TASK_NAME, { minimumInterval: 60 * 6 });
}
```

この形でも、拡張は読むだけ、親アプリが起きて書く、という分担は変わりません。JavaScript で書いていても、背景で起こされているのは親アプリなのです。

## 実機で今すぐ起こして確かめる

背景タスクは、予約してから実際に起こされるまで何時間も空くことがあります。翌朝まで待って確かめていては、一日に一つしか仮説を試せません。

Apple の開発者ドキュメント「Starting and Terminating Tasks During Development」には、デバッガから起動を再現する方法が載っています。`submit` が通ったあとの行にブレークポイントを置き、実機で止まったところで次を実行してから再開します。

```text
(lldb) e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"net.dolice.wallpaper.dailyRefresh"]
```

期限切れの扱いを確かめたいときは、ハンドラの中で止めてから `_simulateExpirationForTaskWithIdentifier:` を同じ形で呼びます。`expirationHandler` が呼ばれ、`setTaskCompleted(success: false)` まで届くかを見られます。

注意したいのは二点です。この再現は実機でしか働きません。そして非公開の関数ですので、開発中だけに使い、提出するビルドに呼び出しを残すと審査で却下の理由になると、同じドキュメントに書かれています。

拡張から `submit` した識別子でこれを実行しても、ハンドラは呼ばれません。受け手がいないことを、翌朝を待たずにその場で確かめられるわけです。

## よくある誤解を3つ

一つ目は「`submit` が例外を投げなければ、タスクは走る」という思い込みです。`submit` は依頼を受け付けたことしか意味しません。受け手の登録は別の呼び出しで、拡張からは行えません。

二つ目は「ウィジェットの許可リストはウィジェットの Info.plist に書く」というものです。`BGTaskSchedulerPermittedIdentifiers` が効くのは、背景で起こされる側、つまり親アプリの Info.plist です。

三つ目は「`reloadTimelines` を呼べば、その場で描き直される」という期待です。Apple の「Keeping a widget up to date」は、再読み込みを 1 日の予算の中で配分すると説明しています。呼び出しは依頼であって命令ではありません——ただし、親アプリが前面にあるあいだの再読み込みは予算に数えないとも書かれていますので、アプリを開いた瞬間に揃えるのは確実にできます。

## AppIntent から即時に更新したくなったときの限界

iOS 17 以降のウィジェットはボタンを置けますので、その場で次の画像に切り替えたくなります。ところが `AppIntent` の `perform()` の中で再読み込みを頼んでも、反映が数分遅れる、実機でだけ再現しない、という報告が[開発者フォーラムの相談](https://developer.apple.com/forums/thread/737206)に複数あがっています。私の手元でも、シミュレータでは即座に切り替わるのに実機では待たされる、という差が出ました。

そこで、押した瞬間は App Group に書いた値をそのまま描き、システムの再読み込みは後追いで構わないという設計にしています。**見た目の即応は自分の書き込みで作り、正しさの担保はシステムの再読み込みに預けます。** この分担にしてから、実機とシミュレータの差で悩む場面が減りました。

## 複数のアプリに展開して残した運用ルール

複数の壁紙アプリへ同じ構成を広げるとき、判断がぶれないように短い決まりを置きました。背景更新の登録は親アプリだけの仕事にすること、識別子は共有ターゲットの定数からしか読まないこと、そして書き込みが終わってから再読み込みを頼むこと。この三つです。加えて、次の一枚が前もって決められる枠は背景タスクに載せず、タイムラインに積むことにしました。

もし今、拡張のターゲットに `BGTaskScheduler` を書きかけているのでしたら、まず `register` の行を親アプリ側へ移してみてください。私の場合、この一行の引っ越しだけで、翌朝の画面がようやく変わりました。
