壁紙アプリの画像に自動でカテゴリの候補を付ける仕組みを見直していた晩、Gemini API の廃止予定のページを開いて、しばらく画面の前で手が止まりました。12月1日の行に書かれていたのは「停止」ではなく、別のモデルへの**自動ルーティング**だったからです。

最初のうち、私は廃止といえばエラーが返るものだと思い込んでいました。エラーが返れば Crashlytics にも出ますし、ログを見れば翌朝には気づけます。ところが回されるだけなら、アプリは何事もなかったように動き続けます。変わるのは、返ってくる答えの言い回しや長さ、それに請求の単価です。

最初にお伝えしたいのは、**止まる期限より、回される期限のほうが気づきにくい**ということです。12月1日まで、今日を入れて残り5日。Rork で AI 機能を足したアプリをお持ちの方に向けて、前日までにできる確かめ方と、当日以降に何か起きたときの切り分け方を順に書き残します。

## 12月1日に起きること（2026年11月時点・公式で確認）

Gemini API の [Deprecations](https://ai.google.dev/gemini-api/docs/deprecations) のページでは、12月1日から次の呼び出しが後継モデルへ回されると案内されています。

あわせて押さえておきたいのは、回されたあとの料金は**回り先のモデルの単価**で数えられる点です。2.5 系の単価を前提に月の上限を決めていた場合、そこも見直しの対象になります。具体的な単価は変わることがあるため、この記事には書かず、[料金のページ](https://ai.google.dev/gemini-api/docs/pricing)で当日の値を確かめていただければと思います。開発者フォーラムには、2.5 Pro を残してほしいという投稿も立っていました。答えの癖に合わせて作り込んだ処理ほど、影響が出やすいのだと思います。

なお、`-001` などの版番号付きの名前や、`-preview` の付いた名前、`-tts` のような用途別の名前を使っている場合は、それぞれの行を同じページで確かめてください。扱いと日付が同じとは限りません。私も以前、推奨された移行先そのものが先に止まっていたことがあり、その突き合わせの記録は [推奨された移行先が、すでに停止していました](/articles/rork-ai/gemini-deprecation-recommended-replacement-already-shutdown-audit) に残しています。

## よくある三つの思い込み

手順に入る前に、私自身がはまりかけた思い込みを三つだけ置いておきます。

**1. 「廃止されたらエラーが出るから、そのとき直せばいい」**——12月1日の扱いは停止ではなく自動ルーティングです。HTTP のステータスは成功のまま返るので、エラー監視には何も上がりません。気づく手がかりは、答えの形・長さ・請求額のほうに出ます。

**2. 「新しいモデルに回るのだから、答えは良くなるだけ」**——`gemini-2.5-flash` の回り先は Flash-Lite 系です。世代は新しくても、軽量の系統に移るので、長い指示の守り方や出力の長さが変わることは十分ありえます。良くなるか悪くなるかは、アプリの入力で並べてみるまで分かりません。

**3. 「アプリのモデル名を書き換えれば、今週中に全員へ届く」**——アプリ本体に書かれた名前を替えるには、ストアの審査と、利用者の更新の両方が要ります。更新しない方の端末では、12月1日以降も古い名前で呼ばれ続け、回された先の答えを受け取ります。

## 手順1: アプリが呼んでいるモデル名を洗い出す

Rork で作ったアプリでは、モデル名がどこに書かれているかを自分で把握していないことが少なくありません。私も、画面のコードには無いと思っていたら、サーバー側の関数に直書きされていました。

Rork のチャットでは、次のように一度だけ頼むのが確実です。

> このプロジェクトで Gemini API を呼んでいる箇所を、ファイル名とモデル名の一覧にしてください。モデル名が環境変数や設定ファイルから読まれている場合は、その変数名も書いてください。コードは変更しないでください。

書き出したコードが手元にある場合は、ターミナルで探すこともできます。名前を文字列で直書きしている箇所と、環境変数や設定ファイルに逃がしている箇所の両方を拾います。

```bash
# 書き出したプロジェクトの直下で実行します（macOS / Linux）
grep -rnE "gemini-2\.5-(flash|pro)" \
  --include='*.ts' --include='*.tsx' --include='*.js' --include='*.mjs' \
  --include='*.json' --include='*.toml' --include='.env*' . \
  | grep -v node_modules

# モデル名を変数で受け取っている箇所も見ておきます
grep -rnE "GEMINI_MODEL|modelName|model:\s*['\"]gemini" \
  --include='*.ts' --include='*.tsx' --include='*.js' . | grep -v node_modules
```

一つ目で何も出ず、二つ目だけが当たる場合は、名前が `.env` や Cloudflare Workers の `wrangler.toml`、Supabase の Secrets のような、コードの外に置かれている可能性があります。ダッシュボード側の値も忘れずに開いてみてください。

見つかった場所が、**アプリ本体の中**なのか、**Supabase の Edge Function や Cloudflare Workers のようなサーバー側**なのかを、ここで分けておきます。この違いが、手順4の判断に効いてきます。置き場所の考え方は [API キーを環境変数に置くか Edge Function に置くか](/articles/rork-ai/rork-api-key-placement-env-variables-vs-supabase-edge-function) にもまとめています。

## 手順2: 同じ入力で、いまのモデルと回り先を並べる

12月1日を待たなくても、回り先のモデルは今日から名前を指定して呼べます。そこで、同じ入力を両方に投げて、答えを横に並べます。

次のスクリプトは、Node.js 18 以降で追加のパッケージなしに動く形にしています。`inputs.json` には、アプリで実際に送っている文面を10件ほど、文字列の配列で入れてください。アプリが JSON の答えを前提にしているなら、`REQUIRED_KEYS` にパース後に必ず要るキーを並べておくと、形の崩れを機械で拾えます。

```javascript
// compare-models.mjs — 同じ入力を2つのモデルに送り、答えの形・長さ・時間を並べます
// 実行: GEMINI_API_KEY=YOUR_API_KEY node compare-models.mjs inputs.json
import { readFile } from "node:fs/promises";

const PAIRS = [["gemini-2.5-flash", "gemini-3.5-flash-lite"]]; // 2.5-pro を使っていれば ["gemini-2.5-pro", "gemini-3.8-flash"] を足します
const REQUIRED_KEYS = []; // 例: ["category", "confidence"]。JSON を前提にしない処理なら空のまま
const KEY = process.env.GEMINI_API_KEY;
if (!KEY) throw new Error("GEMINI_API_KEY が未設定です");

function inspect(out) {
  const cleaned = out.replace(/^\x60{3}(json)?\s*|\x60{3}\s*$/g, "").trim();
  try {
    const obj = JSON.parse(cleaned);
    const missing = REQUIRED_KEYS.filter((k) => !(k in obj));
    return { isJson: true, fenced: cleaned !== out.trim(), missing };
  } catch {
    return { isJson: false, fenced: false, missing: REQUIRED_KEYS };
  }
}

async function ask(model, text) {
  const started = Date.now();
  const res = await fetch(
    `https://generativelanguage.googleapis.com/v1beta/models/${model}:generateContent`,
    {
      method: "POST",
      headers: { "Content-Type": "application/json", "x-goog-api-key": KEY },
      body: JSON.stringify({ contents: [{ parts: [{ text }] }] }),
    }
  );
  const ms = Date.now() - started;
  if (!res.ok) return { model, ms, error: `${res.status} ${await res.text()}` };
  const data = await res.json();
  const out = data.candidates?.[0]?.content?.parts?.map((p) => p.text ?? "").join("") ?? "";
  return {
    model,
    servedBy: data.modelVersion, // 応答に含まれるモデルの版
    ms,
    chars: out.length,
    tokens: data.usageMetadata?.totalTokenCount,
    ...inspect(out),
    head: out.slice(0, 60),
  };
}

const inputs = JSON.parse(await readFile(process.argv[2], "utf8"));
for (const [oldModel, newModel] of PAIRS) {
  for (const [i, text] of inputs.entries()) {
    const [a, b] = [await ask(oldModel, text), await ask(newModel, text)];
    console.log(`#${i + 1}`, JSON.stringify(a), "\n   ", JSON.stringify(b));
  }
}
```

1件ごとに2行が出て、上がいまのモデル、下が回り先です。見るのは、答えの中身の良し悪しより先に、**形が同じかどうか**です。`isJson` が片方だけ `false` になる、`fenced` が片方だけ `true` になる（答えがコードブロックの囲みに包まれる）、`chars` が倍近く変わる、`head` の冒頭に前置きの一文が付く——アプリの画面やパース処理が壊れるのは、たいていこのどれかです。

`ms` と `tokens` も同じ行で見比べておくと、費用と待ち時間の見当がつけやすくなります。10件ではぶれが大きいので、気になる差が出た入力だけ、3回ずつ投げ直して傾向を見るようにしています。なお、このスクリプトの出力をここに載せていないのは、私の手元の入力と皆さまのアプリの入力では結果がまるで違うからです。数字は、ご自身の入力で出たものだけを信じていただければと思います。

## 手順3: 答えの形をアプリ側で固定しておく

並べてみて形が揺れるなら、モデルを替える前に、答えの形を指定する側を固めます。Gemini API では `generationConfig` に `responseMimeType: "application/json"` と `responseSchema` を渡すと、決めた形の JSON で返すよう指定できます（[構造化出力の公式ドキュメント](https://ai.google.dev/gemini-api/docs/generate-content/structured-output)）。

Before は、プロンプトの文面だけで形を頼んでいた書き方です。

```javascript
// Before: 文面で頼んでいるだけ。モデルが替わると囲みや前置きが付くことがあります
body: JSON.stringify({
  contents: [{ parts: [{ text: `次の画像説明からカテゴリを1つ選び、JSON で返してください: ${caption}` }] }],
}),
```

After は、形そのものを API に渡す書き方です。

```javascript
// After: 返す形を API 側で固定します。モデルが替わっても、キーと型は崩れにくくなります
body: JSON.stringify({
  contents: [{ parts: [{ text: `次の画像説明に合うカテゴリを1つ選んでください: ${caption}` }] }],
  generationConfig: {
    responseMimeType: "application/json",
    responseSchema: {
      type: "OBJECT",
      properties: {
        category: { type: "STRING", enum: ["nature", "city", "abstract", "animal", "other"] },
        confidence: { type: "NUMBER" },
      },
      required: ["category"],
    },
  },
}),
```

`enum` で選べる値を絞っておくのがいちばん効きます。回り先のモデルが言い回しを変えても、`"Nature"` や `"自然"` のような表記の揺れが画面に届かなくなるからです。手順2のスクリプトの `body` をこの形に差し替えて、もう一度並べてみると、形の差がどこまで縮んだかが分かります。

AI の答えをキャッシュしている場合は、キャッシュのキーにモデル名が入っているかも確かめてください。入っていないと、切り替え後も古いモデルの答えが混ざって表示されます。考え方は [モデルを替えた日にキャッシュを掃除する](/articles/rork-ai/ai-answer-cache-key-model-and-prompt-version-sweep-on-swap) に書きました。

## 手順4: 自分で切り替えるか、回されるのに任せるか

ここで手順1の仕分けが効いてきます。選べる道は三つあり、どれが正しいかは名前の置き場所で決まります。

<table>
<thead><tr><th>やり方</th><th>向いている場合</th><th>よいところ</th><th>気をつけたい点</th></tr></thead>
<tbody>
<tr><td>12月1日より前に自分で書き換える</td><td>名前がサーバー側にあり、手順2で形の差が小さかった</td><td>替えた時刻が分かり、戻す判断も自分でできます</td><td>書き換えた直後のログを一度は見る必要があります</td></tr>
<tr><td>回されるのに任せる</td><td>名前がアプリ本体にあり、審査が12月1日に間に合わない</td><td>今週の作業が増えません</td><td>変わった瞬間を見届けられません。手順3の形の固定を先に入れておくことが前提です</td></tr>
<tr><td>名前をサーバーから渡す形へ移す</td><td>次の廃止でも同じことを繰り返したくない</td><td>以後は審査なしでモデルを替えられます</td><td>移す作業そのものに審査が1回要ります。今回の期限には間に合わないこともあります</td></tr>
</tbody>
</table>

判断を一文にするなら、**名前がサーバーにあるなら自分で替え、アプリにあるなら形を固めて任せ、次の更新で名前をサーバーへ移す**——この順番がいちばん手戻りが少ないと感じています。

私自身は、**期限の日付は Google が決め、切り替える時刻は自分が決める**という線引きにしています。回されるのを待つと、変わった瞬間を自分で見届けられないからです。サーバー側で替えるときは、利用の少ない時間帯に替え、その晩のうちに手順2と同じ見方でログを数件だけ読み返すようにしています。

## 12月1日以降に何かおかしいと感じたら

回されたあとに出る不具合は、エラー画面ではなく「なんとなく変」というかたちで届きます。私が想定している症状と、確かめる順番を表にしておきます。

いちばん上の行が、いちばん起きやすいと思っています。答えの中身ではなく、答えを包む形が変わるだけで、アプリは「答えがなかった」と判断して既定値を出してしまうからです。最後の行のタイムアウトの考え方は、[ヘッダまで・全体・無通信の3つのタイムアウトを同じ応答で測った記録](/articles/rork-ai/stalled-response-body-header-total-idle-timeout-measured-three-ways) が参考になるかもしれません。

手順2のスクリプトでは、応答の `modelVersion` も `servedBy` として出しています。12月1日以降、ここに回り先の名前が出るのかどうかは、私はまだ確認できていません。当日に一度だけ旧名で呼んでみて、何が返るかを見ておくつもりです。

## 同じ週のもう一つの期限

同じ週の11月30日には、Claude API の Sonnet 4.5 も提供を終えます。こちらは回されるのではなく止まる側の期限なので、気づきやすい代わりに、気づいたときにはもう動いていません。両方を使っているアプリの方は、[Sonnet 4.5 を呼んでいないかの洗い出し](/articles/rork-ai/scan-app-for-old-claude-model-ids-before-sonnet-4-5-retires) とあわせて、手順1の grep を一度に回しておくと手戻りが少なくて済みます。

## 次にすること

まずは手順1の一覧を作り、モデル名が書かれている場所を「アプリ本体」と「サーバー側」に分けるところまで、今日のうちに済ませていただければと思います。その一覧さえあれば、並べる作業も、手順4のどの道を選ぶかも、それほど重くはありません。答えが変わる日を、知らないうちに迎えないこと——この一点だけは、小さなアプリでも守るようにしています。
