壁紙アプリの設定画面を試作し直していた夜、私は同じ依頼を二度送りました。一度目は日本語で「通知と表示の設定画面を作ってください」、二度目はほぼ同じ内容を英語で。並べて見比べるつもりだったのは、色や余白の違いでした。

ところが、目に留まったのは見た目ではありませんでした。日本語で頼んだほうは「保存」「キャンセル」といった文言が各画面のコードにそのまま書き込まれ、英語で頼んだほうは「Save changes」のような長めのラベルが、幅を決め打ちしたボタンの中で窮屈そうに収まっていたのです。

最初にお伝えしたいのは、**依頼を何語で書くかより、文言をどこに置き、どれだけの長さを許し、日付や金額をどう書くかを、依頼の中で先に決めておくほうが効く**ということです。言語を選ぶ話ではなく、言語に任せてしまっていた部分を取り戻す話になります。

## 並べてみて、違いが出たのは三か所でした

同じ依頼を二つの言語で何度か出してみて、私の手元で差が出やすかったのは次の三つです。生成のたびに細部は変わるので、「必ずこうなる」ではなく「こちらに寄りやすい」という程度に読んでいただければ幸いです。

<table>
<thead><tr><th>見るところ</th><th>日本語で頼んだとき</th><th>英語で頼んだとき</th></tr></thead>
<tbody>
<tr><td>文言の置き場所</td><td>画面ごとのコードに直書きされやすい</td><td>同じく直書き。ただし後から日本語を足す前提が抜けやすい</td></tr>
<tr><td>長さの前提</td><td>短い語に合わせた幅・余白になりやすい</td><td>長い語に合わせて組まれ、日本語にすると間が空きやすい</td></tr>
<tr><td>日付・数字の書式</td><td>「11月14日」のような書式を文字列で組み立てがち</td><td>「Nov 14」形式が前提になり、日本語端末でも英語のまま出やすい</td></tr>
</tbody>

どちらが優れている、という結果にはなりませんでした。要するに、**依頼の言語がそのまま「アプリの第一言語」の前提として紛れ込む**のです。日本語で頼めば日本語だけのアプリとして、英語で頼めば英語だけのアプリとして組まれる——それ自体は自然なことで、困るのは後から二つめの言語を足す日です。

## 長さは、言語によって何倍も変わります

いちばん分かりやすいのはボタンの文言です。「保存」は 2 文字、英語の「Save changes」は 12 文字、ドイツ語にすると「Änderungen speichern」で 20 文字になります。ストアの説明文を多言語で回していると、この伸び縮みには毎回手を焼きます。

日本語で頼んで組まれた画面は、2 文字に合わせた幅で落ち着いていることが多く、あとで英語を流し込むと文字が切れたり二行に折れたりします。逆に英語で頼んだ画面は、日本語にするとボタンの中ががらんと空きます。どちらの方向でも、**幅を数字で決め打ちしないこと**を依頼の段階で伝えておくのが近道でした。

改行の位置や、日本語の太字が Android で効かない件は、それぞれ別の記事で掘り下げています（[「、」が行頭に落ちた — Rork が組んだ名言カードと日本語の禁則処理](/articles/rork-dev/rork-japanese-line-breaking-kinsoku-text-layout-quote-card)、[日本語の見出しだけ太字にならない — Android で fontWeight が効かないときの切り分けと直し方](/articles/rork-dev/rork-japanese-bold-fontweight-android-fontfamily-fix)）。ここでは、その手前の「依頼の書き方」に絞ります。

## 最初は、言語の違いを生成の癖だと思っていました

正直に書くと、私は最初、英語で頼んだほうが「きちんとした」コードが返ってくるのだろうと考えて、しばらく英語の依頼に寄せていました。結果は芳しくありませんでした。英語のラベルが直書きされた画面を、あとから一つずつ日本語に置き換える作業が待っていただけだったのです。

気づいたのは、置き換えの途中で同じ「Cancel」を何か所も続けて直していたときでした。生成の癖ではなく、私が依頼の中で「文言は一か所にまとめる」と言っていなかっただけのことでした。

**文言の置き場所は依頼の言語に任せず、最初の一通で決めます。** いまはこの一文を、新しい画面を頼むときの最初の確認にしています。

## 依頼文には、三つの決めごとを足します

Rork の公式ドキュメントでも、目指す体験と一緒に「制約」を添えると組み上がりが整うと案内されています（[How to prompt successfully](https://docs.rork.com/introduction/introduction/prompting-strategy)）。文言まわりの制約は、次の三行で足りました。日本語で書いても英語で書いても、同じ内容を入れておけば結果の差はぐっと小さくなります。

```text
設定画面を作ってください。落ち着いた雰囲気で、操作は一つの流れに絞ります。
文言について、次の三点を守ってください。
1. 画面に出す文字はすべて constants/strings.ts にまとめ、ja と en の両方を用意する。コードには直書きしない。
2. ボタンやラベルの幅を数値で固定しない。文字が 3 倍の長さになっても崩れない組み方にする。
3. 日付・数字・金額は文字列で組み立てず、端末の言語に合わせて Intl で書式化する。
```

一行目は公式の案内どおり、雰囲気と範囲を伝える部分です。二行目以降が、今回の比較から引いた決めごとになります。

## 返ってきたコードは、このかたちになっているか見ます

依頼どおりに組まれると、文言の置き場所はおおむね次のようなかたちになります。端末の言語は `expo-localization` の `getLocales()` で読めます。公式ドキュメントでは、`languageCode` は `null` になりうること、Android では設定アプリから言語を変えてもアプリが再起動しないことが説明されています（[Localization - Expo Documentation](https://docs.expo.dev/versions/latest/sdk/localization/)）。そのため、言語の判定は一か所にまとめ、英語へ落とす道を必ず残します。

```typescript
// constants/strings.ts
import { getLocales } from "expo-localization";

const strings = {
  ja: { save: "保存", cancel: "キャンセル", lastUpdated: "最終更新" },
  en: { save: "Save changes", cancel: "Cancel", lastUpdated: "Last updated" },
} as const;

type Lang = keyof typeof strings;
type Key = keyof (typeof strings)["en"];

// languageCode は null になりうるので、必ず en に落とす
export function currentLang(): Lang {
  const code = getLocales()[0]?.languageCode ?? "en";
  return code in strings ? (code as Lang) : "en";
}

export function t(key: Key): string {
  return strings[currentLang()][key];
}

// 日付は文字列を組み立てず、言語ごとの書式に任せる
export function formatDate(date: Date): string {
  const tag = getLocales()[0]?.languageTag ?? "en-US";
  return new Intl.DateTimeFormat(tag, { year: "numeric", month: "short", day: "numeric" }).format(date);
}
```

`getLocales()` を呼び出しのたびに読み直しているのは、Android で言語を切り替えたあと、前の言語のまま表示され続けるのを避けるためです。毎回の呼び出しが気になる規模になったら、フォアグラウンド復帰のときだけ読み直すかたちに変えれば足ります。

## 直書きが残っていないかは、手元で数えます

依頼で伝えても、修正を重ねるうちに直書きの文言が紛れ込むことがあります。書き出したプロジェクトの直下で、次のスクリプトを動かすと、JSX の中に直接書かれた文字列を一覧にできます。Node だけで動き、追加のパッケージは要りません。

```javascript
// scripts/find-hardcoded-strings.mjs
// 使い方: node scripts/find-hardcoded-strings.mjs app components
import { readdirSync, readFileSync, statSync } from "node:fs";
import { join } from "node:path";

const roots = process.argv.slice(2).length ? process.argv.slice(2) : ["app", "components"];
// >テキスト< の部分と、title= / placeholder= / label= に直接渡された文字列を拾う
const patterns = [
  />\s*([^<>{}\s][^<>{}]*?)\s*</g,
  /\b(?:title|placeholder|label|accessibilityLabel)=["']([^"']+)["']/g,
];

function walk(dir, out = []) {
  let entries = [];
  try { entries = readdirSync(dir); } catch { return out; }
  for (const name of entries) {
    if (name === "node_modules" || name.startsWith(".")) continue;
    const p = join(dir, name);
    if (statSync(p).isDirectory()) walk(p, out);
    else if (/\.(tsx|jsx)$/.test(name)) out.push(p);
  }
  return out;
}

let total = 0;
for (const file of roots.flatMap((r) => walk(r))) {
  const lines = readFileSync(file, "utf8").split("\n");
  lines.forEach((line, i) => {
    for (const re of patterns) {
      for (const m of line.matchAll(re)) {
        const text = m[1].trim();
        // 記号だけ・数字だけは対象外にする
        if (!/[A-Za-z぀-ヿ一-鿿]/.test(text)) continue;
        total++;
        console.log(`${file}:${i + 1}  ${text}`);
      }
    }
  });
}
console.log(`\n直書きの候補: ${total} 件`);
process.exitCode = total > 0 ? 1 : 0;
```

正規表現で拾っているだけなので、型の指定などを誤って拾うこともあります。それでも、件数が 0 に向かって減っていくのを見るのは、置き換えの進み具合を測るには十分でした。一覧が出たら、そのまま Rork に貼って「この文言を constants/strings.ts へ移してください」と頼めば、手で直すよりはるかに早く片づきます。

言語を増やしていく段階の、未翻訳の抜けを見つける仕組みは [言語を増やすたびに未翻訳が本番へ漏れる — Rork(Expo) アプリの文言カタログ運用と抜け検出の設計](/articles/app-dev/rork-expo-i18n-translation-completeness-missing-key-fallback-design) にまとめています。

## 結局、どちらの言語で頼めばよいのか

私自身は、いまは考えやすい日本語で依頼を書き、上の三行だけは毎回添えるようにしております。雰囲気や手触りを伝える部分は、自分のいちばん得意な言葉で書いたほうが、意図がずれにくいと感じるからです。

一方で、英語圏だけに出すアプリなら英語で頼むほうが、画面の文言をそのまま使える場面は多くなります。日本語と英語のあいだを取り持つのは依頼の言語ではなく、依頼に添えた決めごとのほうなのだと思います。

まずは次に新しい画面を頼むとき、依頼の最後に「文言は constants/strings.ts にまとめ、ja と en を用意する」の一行だけを足してみていただければと思います。二つめの言語を足す日の作業が、それだけで一つ減ります。
