壁紙アプリの試作で、詳細画面の「保存」ボタンの下に小さな説明文を一行足してほしい、と頼んだ夕方のことです。返ってきた答えは、頼んだ一行に加えて、ボタンの余白とアイコンの大きさまで整え直していました。

いつもなら一行だけを足して終わる種類の依頼です。「今日は妙に気が利く」と思いながら、同時に手が止まりました。気が利いたのか、余計なことをしたのか、私には見分けがつかなかったのです。いま思えば、そこで手が止まったのは幸いだったのかもしれません。

あとで気づいたのですが、そのときモデルメニューには **GPT-6.2 Astra** と表示されていました。私が選んだ覚えのあるのは GPT-6 Astra です。

## 何が替わったのか — 11月18日の変更履歴

Rork の変更履歴（rork.com/changelog）の 11 月 18 日の項には、次のことが書かれています。

- **GPT-6.2 Astra** が GPT-6 Astra の後継、**GPT-6.2 Sol** が GPT-6.1 Sol の後継として加わりました
- 旧版を選んでいたプロジェクトは、**同じ effort のまま新版で作る**ようになります
- どちらも Pro と Max のプランに含まれます

同じ日の項には、1 つのプロジェクトで公開できる Web サイトの数の上限（20 件）を外したこと、そして in-app event が審査待ちのときに App Review への送信が失敗していた問題を直したことも並んでいます。モデルの件とは別の話ですが、ストアへ出す前の方は目を通しておくと安心です。

要するに、私が何もしなくても、作り手側のモデルは一段新しくなっていたのです。

## 最初にやりかけた失敗 — 依頼文を書き換えようとしました

余白まで整えられた答えを見て、私が最初に考えたのは「依頼文が曖昧だったのだろう」ということでした。「説明文を一行だけ足してください。ほかは変えないでください」と書き直して、もう一度送ろうとしていたのです。

送る直前にメニューの表示に気づき、手を止めました。もしモデルが替わったことで答え方が変わったのなら、依頼文をいくら直しても原因には届きません。逆に、モデルのせいだと決めつけて画面ごと作り直すのも、早すぎる判断です。

**違いを感じたら、直す前に、何が替わったのかを一つずつ数えます。** この順番を守るために、いまは次の 3 点を先に確かめるようにしています。

## 確かめること 1 — メニューのモデル名と effort

最初に見るのは、モデルメニューの表示そのものです。

- モデル名が「6.2」になっているか
- effort が、以前に自分で選んだ段のままか

変更履歴のとおりなら、effort は動いていないはずです。ここで effort まで変わっていたら、それは自動の切り替えではなく、別の誰か（あるいは過去の自分）が触った可能性があります。共同で作っているプロジェクトなら、なおさら確かめておく価値があります。

effort の段の選び方は、[Opus 5.5 と GPT-6 Sol で一覧画面を作り分けた記事](/articles/rork-basics/gallery-grid-screen-opus-5-5-vs-gpt-6-sol-effort-choice) に書き残しました。段を上げるかどうかは、切り替えの確認が終わってから考えても遅くありません。

## 確かめること 2 — 旧モデルで作った最後の版に印をつける

次に、旧モデルで作った最後の版がどれかを覚えておきます。Rork では答えのたびにプロジェクト全体が一つの版として保存され、Undo や Revert で戻る操作そのものにクレジットはかかりません。戻り方の選び方は [Undo・Revert・メッセージ編集の記事](/articles/rork-ai/rork-undo-revert-edit-message-choosing-the-way-back) にまとめています。

GitHub にプロジェクトを書き出している方は、切り替わる前の最後のコミットにタグを打っておくと、あとで差分を取るのが楽になります。

```bash
# 切り替わる前の最後の状態に印をつける（コミットは自分の履歴に合わせて選ぶ）
git tag before-gpt-6-2 <切り替え前のコミット>
git push origin before-gpt-6-2

# 新しいモデルで一つ頼んだあと、何本のファイルが動いたかを数える
git diff --stat before-gpt-6-2 HEAD
```

`git diff --stat` を使うのは、答えの良し悪しを「見た目の印象」ではなく「動いたファイルの本数と行数」で比べたいからです。私の詳細画面の件では、一行を頼んだのに 3 本のファイルが動いていました。数字で見えると、気が利いたのか、手を広げすぎたのかを落ち着いて判断できます。

## 確かめること 3 — 同じ「物差しの依頼」を一度だけ送る

三つ目は、毎回同じ文面で送る小さな依頼を一つ決めておくことです。私は「設定画面の見出しの文字を一段小さくしてください」という依頼を物差しにしています。答えが短く、動くべきファイルが 1 本だけだと分かっているからです。

切り替え後にこの依頼を一度だけ送り、次の二つを見ます。

1. 動いたファイルが 1 本で収まったか
2. 頼んでいない箇所（余白・色・並び順）に触れていないか

物差しで差が出なければ、詳細画面で起きたことは依頼文の書き方の問題だったと考えられます。差が出たなら、新しいモデルは手を広げやすい傾向がある、と覚えておき、依頼文に「変更は◯◯の 1 ファイルに限ってください」と範囲を書き添えるようにします。どちらにしても、画面を作り直す必要はありません。

## もう一つの「モデル」と取り違えない

ここで、取り違えやすい点を一つお伝えします。今回替わったのは、**Rork がアプリを作るときに使うモデル**です。皆さまのアプリが中で呼んでいる AI のモデル（アプリのコードに書いたモデル名）は、この切り替えでは一文字も変わりません。

私自身、最初は両方が一緒に替わったのかと思い、アプリのコードを開いて探しかけました。アプリ側のモデル名には別の期限があり、たとえば 11 月 30 日の Claude Sonnet 4.5 の提供終了は、アプリのコードを自分で直さないと間に合いません。その棚卸しのやり方は [古い Claude のモデル ID をアプリから探す記事](/articles/rork-ai/scan-app-for-old-claude-model-ids-before-sonnet-4-5-retires) に書きました。

**作る道具のモデルと、アプリが呼ぶモデルは、別の帳簿につけます。** 個人開発で複数のアプリを並べて運用していると、この二つを一つの頭で覚えておくのは難しく、私はメモの見出しから分けるようにしています。

## まとめに代えて — 次にやること

まずは物差しにする依頼を一つ決めて、切り替え後のプロジェクトで一度だけ送ってみていただければと思います。動いたファイルの本数を見るだけで、作り直すべきかどうかの答えは、たいてい出ます。

モデルが替わるたびに慌てていた頃に比べると、いまはこの 3 点を確かめるあいだ、肩の荷が少し軽くなったように感じています。
