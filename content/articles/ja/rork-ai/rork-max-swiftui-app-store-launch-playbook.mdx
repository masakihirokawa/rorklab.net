Rork Max に「連続日数つきの瞑想タイマー」と頼むと、数分で Xcode プロジェクトが手元に届きます。シミュレータで動いた瞬間は、たしかに気持ちが高ぶります。

ただ、その画面は「動いた」ところまでです。ストアに出す商品になるまでには、見た目からは分からない作業がいくつも残っています。

**生成コードは、仕上げの出発点として扱います。** この考え方のもとで、初日に確認すること、設計の直し方、課金と保存の実装、審査前の点検、公開後の見方を順に整理します。

なお、Apple の仕様や審査の扱いは更新されます。本稿で「公式で確認した」と書いた箇所以外は、筆者の理解と推測です。提出前には、必ず最新の App Review Guidelines と App Store Connect のヘルプで確認してください。

## 生成直後の初日チェックリスト

プロジェクトを Rork Max からダウンロードしたら、ビルドの前に次の項目を確認します。後工程で見つけるより、初日に潰す方が手戻りが小さくなります。

## 設計の見直し：1つの View に詰まったロジックを分ける

生成コードを読んでいて気づきやすいのは、画面遷移・データ取得・表示ロジックが1つの View に集まっていることです。機能を足すたびに肥大化するので、最初に ViewModel を切り出します。

```swift
// 生成直後に多い形（イメージ）
struct ContentView: View {
    @State private var items: [Item] = []
    @State private var isLoading = false

    var body: some View {
        NavigationStack {
            // 取得・加工・表示がここに集まる
        }
    }
}

// 分離後
struct ContentView: View {
    @StateObject private var viewModel = ContentViewModel()

    var body: some View {
        NavigationStack {
            ItemListView(items: viewModel.items)
                .toolbar { ItemToolbar(viewModel: viewModel) }
                .task { await viewModel.load() }
        }
    }
}

@MainActor
final class ContentViewModel: ObservableObject {
    @Published var items: [Item] = []
    @Published var isLoading = false

    func load() async {
        isLoading = true
        defer { isLoading = false }
        // 取得処理
    }
}
```

`ItemListView` と `ItemToolbar` は、分割後の部品を表すための名前です（自作する View で、`ToolbarContent` のような SwiftUI の既存の型名とは別の名前にしてください）。このコードはイメージを示すもので、そのままではビルドできません。

iOS 17 以上を対象にするなら、`ObservableObject` の代わりに `@Observable` マクロを使う選択肢もあります。どちらが適切かは、対応 iOS とチームの慣れで決めます。

エラー処理も、生成コードで手薄になりやすい箇所です。正常系だけが丁寧で、失敗時は `print` だけで終わっていることがあります。ネットワーク失敗や権限拒否のとき、ユーザーに何を見せて、どう再試行させるのか。ここは自分で決めるしかありません。

## SwiftData：スキーマの版管理を最初から入れる

Rork Max が SwiftData を使ったコードを出すかどうかは、依頼内容によって変わります。使う場合は、リリース後のモデル変更に備えて、最初から `VersionedSchema` で版を持たせておくと安心です。

保存済みデータを持つ既存ユーザーがいる状態で、モデルを変えるのは慎重に行う作業です。プロパティの追加のような軽微な変更は自動で移行できる場合もありますが、どの変更がどう扱われるかは、実機とシミュレータの両方で旧版から更新して確かめる必要があります。

```swift
enum AppSchemaV1: VersionedSchema {
    static let versionIdentifier = Schema.Version(1, 0, 0)
    static var models: [any PersistentModel.Type] {
        [Item.self]
    }

    @Model
    final class Item {
        var title: String
        var createdAt: Date

        init(title: String, createdAt: Date = .now) {
            self.title = title
            self.createdAt = createdAt
        }
    }
}

enum AppMigrationPlan: SchemaMigrationPlan {
    static var schemas: [any VersionedSchema.Type] {
        [AppSchemaV1.self]
    }

    static var stages: [MigrationStage] { [] }
}

@main
struct MyApp: App {
    var body: some Scene {
        WindowGroup { ContentView() }
            .modelContainer(for: AppSchemaV1.Item.self, migrationPlan: AppMigrationPlan.self)
    }
}
```

最初は空の `stages` で構いません。重要なのは、後から版を足せる形を最初から持っておくことです。`static let versionIdentifier` と書いているのは、Swift 6 の言語モードで可変の static プロパティが並行性エラーになるためです。このコードの動作確認は、筆者の環境では行っていません。

Core Data を選ぶ場合は、`NSManagedObject` のサブクラスを手書きした古い構成になっていないかを確認し、SwiftUI では `@FetchRequest` に寄せると扱いやすくなります。

## StoreKit 2：取引リスナーと購入の復元

サブスクリプションや買い切り課金を入れるなら、まず **アプリ起動直後から `Transaction.updates` を購読する** ことが出発点です。アプリ外で完了した購入や、家族共有・返金による権利の変化は、この更新から届きます。

```swift
@MainActor
final class StoreManager: ObservableObject {
    @Published private(set) var entitledProductIDs: Set<String> = []
    private var updatesTask: Task<Void, Never>?

    init() {
        updatesTask = Task { await listenForUpdates() }
        Task { await refreshEntitlements() }
    }

    private func listenForUpdates() async {
        for await result in Transaction.updates {
            await handle(result: result)
        }
    }

    private func handle(result: VerificationResult<Transaction>) async {
        guard case .verified(let transaction) = result else { return }
        await refreshEntitlements()
        await transaction.finish()
    }

    func refreshEntitlements() async {
        var ids: Set<String> = []
        for await result in Transaction.currentEntitlements {
            if case .verified(let t) = result {
                ids.insert(t.productID)
            }
        }
        entitledProductIDs = ids
    }
}
```

この `StoreManager` は、アプリのライフサイクル全体で1つだけ生成して保持する想定です（`App` 構造体に `@StateObject` として置く、など）。画面ごとに作ると、リスナーが重複します。

もう1つ、**購入の復元の導線** が必要です。App Review Guidelines の 3.1.1 は、アプリ内課金で購入した機能の復元手段を求めています。設定画面などに「購入を復元」ボタンを置き、`AppStore.sync()` を呼びます。

StoreKit のテストは、Xcode の StoreKit Configuration File を使うとサンドボックスなしで確認できます。購入、キャンセル、返金、更新の各経路を、提出前に一通り通しておくことをおすすめします。

## TestFlight：審査の前に実機で回す

TestFlight は、本審査の前に実機の動作を確かめる場です。内部テスターは App Store Connect のユーザーに限られ、外部テスターを招待するには Beta App Review が必要になります。

回す期間と人数に、決まった正解はありません。私は、課金・通知・バックグラウンド動作のように環境で挙動が変わる機能は、最低でも数日は実機で触る価値があると考えています。

クラッシュの把握には、Xcode Organizer のレポートに加えて、Sentry や Firebase Crashlytics のような外部ツールを入れる選択肢があります。ベータ期間に原因を特定しやすくなる反面、SDK を足すとプライバシー情報（次の節）の申告内容も増えます。

ベータ版のリリースノートには、テスターに見てほしい機能と、期待する操作を具体的に書きます。「どこを見てほしいか」が書かれているだけで、返ってくる指摘の質は変わります。

## 審査で指摘されやすい点

ここでは、Rork Max に限らず生成コードで見落としやすい3点を取り上げます。いずれも筆者個人の審査結果ではなく、Apple の公開情報にもとづく一般的な注意点です。

### プライバシーマニフェスト（PrivacyInfo.xcprivacy）

Apple は、2024年5月1日以降にアプリを提出する際、特定の API（Required Reason API）を使うアプリとサードパーティ SDK に、使用理由の申告を求めています。プロジェクトに `PrivacyInfo.xcprivacy` を含め、使っている API の分類と理由コードを記載します。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>NSPrivacyTracking</key>
    <false/>
    <key>NSPrivacyTrackingDomains</key>
    <array/>
    <key>NSPrivacyCollectedDataTypes</key>
    <array/>
    <key>NSPrivacyAccessedAPITypes</key>
    <array>
        <dict>
            <key>NSPrivacyAccessedAPIType</key>
            <string>NSPrivacyAccessedAPICategoryUserDefaults</string>
            <key>NSPrivacyAccessedAPITypeReasons</key>
            <array>
                <string>CA92.1</string>
            </array>
        </dict>
    </array>
</dict>
</plist>
```

これは `UserDefaults` だけを使い、トラッキングも収集もしないアプリの最小例です。実際には、`UserDefaults` 以外にファイルのタイムスタンプ、システム起動時間、ディスク容量などの API が対象になりえます。また、分析 SDK や広告 SDK を入れた場合は `NSPrivacyCollectedDataTypes` に収集データの種類を記載する必要があります。理由コードの意味は、Apple の「Describing use of required reason API」で確認してください。

### 購入の復元

先ほどの StoreKit 2 の節のとおり、復元の導線がないと審査で指摘される可能性があります。設定画面など、見つけやすい場所に置きます。

### プレースホルダーのまま残った表示

生成コードには、`Image(systemName: "photo")` のような仮の画像や、仮の文言が残っていることがあります。App Review Guidelines の 2.1（App Completeness）は、完成度の低いビルドや仮の内容を含む提出を認めていません。

提出前に `systemName:` と `Lorem` と `TODO` を検索し、本来の素材に置き換わっているかを確認します。

提出前の最後に、審査担当者用のデモアカウントの用意、ログインが必要な機能の説明、課金商品の審査用スクリーンショットも見直しておきます。

## 公開ページ（ASO）の準備

公開しても、見つけてもらえなければ使われません。App Store Connect では、検索に関わる項目として、アプリ名・サブタイトル・キーワード（100文字まで、カンマ区切り）が用意されています。

キーワード欄は、文字数の上限があるため、区切りのカンマ以外の記号や空白を省いて詰めます。アプリ名やサブタイトルに入れた語を重複させる必要はないと言われています。ただし、この最適化の効果は公式に保証されたものではなく、検索順位への影響は検証しにくい領域です。

スクリーンショットは、検索結果に表示される先頭の数枚が最初の接点になります。機能を説明する短いコピーを添え、何ができるアプリかを一目で伝える画像にしておくと、離脱を減らせる可能性があります。

公開後の指標は、初日のインストール数よりも、数日後に戻ってきた人の割合を見る方が、アプリの手応えをつかみやすいと考えています。目標とする数値はジャンルで大きく変わります。自分のアプリの初期値を測り、そこからの変化を追うのが現実的です。

## 公開後の運用

公開はゴールではなく、運用の始まりです。最初の数週間は、次の3つに時間を使います。

1つ目は、**レビューへの返信** です。低評価のレビューには、具体的な対処を添えて返信します。ユーザーに届くだけでなく、これから入れるか迷っている人も読みます。

2つ目は、**クラッシュの監視** です。Xcode Organizer の Crashes を定期的に見て、新しい種類のクラッシュが出たら優先して修正します。生成コードは、想定外の入力や端末条件への備えが薄いことがあるため、最初の数週間は特に注意します。

3つ目は、**小さな更新を続ける** ことです。更新頻度が検索順位に影響するかどうかについて、Apple の公式な説明は確認できていません。順位対策としてではなく、報告された不具合を直して届ける手段として、更新の流れを止めない方が現実的です。

## 結び：出発点から先を自分で引き受ける

Rork Max が数分で出すコードは、アイデアを形にする出発点として、大きな価値があります。

その先の、設計の整理、データの保存、課金、プライバシー、審査対応は、アプリの責任者が引き受ける仕事です。まずは今日、手元の生成プロジェクトで `PrivacyInfo.xcprivacy` の有無と、`systemName:` の検索結果を確かめてみてください。
