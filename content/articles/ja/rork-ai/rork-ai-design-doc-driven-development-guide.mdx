Rork を使ってアプリを作ったとき、最初はこんな経験をします。「カレンダーアプリを作って」と指示したら、確かにカレンダーアプリが出来上がった。でも、思い描いていたものとは少し違う。修正を重ねるうちに、最初からもっと詳しく説明すればよかったと気づく。

これは Rork の問題ではなく、指示の問題です。自然言語でアプリを作る場合も、「AIに考えさせない」仕様設計が開発速度を決めます。

このガイドでは、Rork で意図通りのアプリを最速で量産するための設計書戦略を、実際の経験をもとに詳しく解説します。

## Rork への指示設計の基本思想

Rork は自然言語の指示からアプリを生成するツールです。しかし「自然言語で良い」ということと「曖昧で良い」は別です。

Rork への理想的な指示の構造は、次の3層です。

```
Layer 1: コア機能（何ができるアプリか・一文で）
Layer 2: 画面設計（どんな画面があり・それぞれ何ができるか）
Layer 3: データ設計（何を保存し・どこに保存し・どう表示するか）
```

この3層が揃った指示は、Rork が正確に解釈できる仕様書になります。

## Layer 1：コア機能の定義

コア機能は「できること」「できないこと」をセットで定義します。

**悪い例**:
```
日記アプリを作って
```

**良い例**:
```
毎日の日記を記録するアプリ。
テキスト入力・写真添付・気分（5段階評価）の記録ができる。
カレンダービューで過去の記録を確認できる。
検索機能・SNSシェア・タグ付けは今回なし。
```

「今回なし」を明示することが重要です。これがないと、Rork は「もしかして必要かも」という判断をして余計な機能を追加することがあります。

## Layer 2：画面設計の詳細化

Rork は画面の設計を細かく指定するほど意図に近いアプリを生成します。各画面について「何が表示されるか」「ユーザーは何ができるか」「画面遷移の条件」を記述します。

```
## 画面設計

### ホーム画面（起動時に表示）
- 今日の日付と曜日（大きく表示）
- 今日の日記が未入力なら「今日の記録をつける」ボタン
- 今日の日記が入力済みなら一行プレビューと「編集」ボタン
- 下部に今週のカレンダー（入力済みの日はドット表示）

### 日記入力画面
- テキスト入力エリア（最大1000文字）
- 写真添付ボタン（最大3枚・カメラロールから選択）
- 気分スライダー（1〜5・アイコン表示）
- 保存ボタン（入力がある場合のみアクティブ）
- 戻るボタン（未保存の場合は確認ダイアログ）

### カレンダー画面
- 月表示カレンダー
- 記録がある日はドット・気分に応じた色
- 日付タップで該当日の日記詳細を表示
```

この粒度で書くと、Rork が生成する画面が「なんか違う」という状況が大幅に減ります。

## Layer 3：データ設計

何をどこに保存するかを明示します。Rork はデフォルトでローカルストレージを使いますが、Firebase や Supabase を使いたい場合は指定が必要です。

```
## データ設計

### 日記エントリ
- id: string（UUID）
- date: string（YYYY-MM-DD形式）
- text: string（最大1000文字）
- mood: number（1〜5）
- photos: string[]（URLの配列、最大3件）
- createdAt: timestamp
- updatedAt: timestamp

### 保存先
- Firebase Firestore を使用
- コレクション名: diary_entries
- ドキュメントIDはentry.idと同一

### 認証
- Firebase Authentication（メールアドレス＋パスワード）
- 匿名ログインは不要
- ユーザーごとにデータが分離される構造
```

データ設計が明確だと、Rork が生成する型定義やデータ操作コードの品質が上がります。

## プロンプトの組み立て方：完全テンプレート

上記の3層を統合したプロンプトテンプレートを紹介します。

```
# [アプリ名]

## コア機能
[一文の説明]

### 含む機能
- 機能1
- 機能2
- 機能3

### 含まない機能（今回のスコープ外）
- 機能A
- 機能B

## 技術スタック
- フレームワーク: React Native / Expo
- バックエンド: Firebase / Supabase / なし（ローカルのみ）
- 認証: Firebase Auth / なし

## 画面設計
### [画面名]
- 表示要素: 〜
- ユーザーアクション: 〜
- 遷移先: 〜

### [次の画面名]
（同様に）

## データ設計
### [エンティティ名]
- フィールド: 〜（型）

### 保存先と構造
（コレクション名・ドキュメント構造）

## デザイン方針
- カラー: ダーク系 / ライト系 / [指定色]
- トーン: ミニマル / カラフル / プロフェッショナル
- フォント: [使いたいフォント名]（なければデフォルト）

## 非機能要件
- オフライン動作: 必要 / 不要
- パフォーマンス: 〜
```

## 修正ループを最小化するチェックリスト

Rork にプロンプトを渡す前に、以下を確認すると修正ループが大幅に減ります。

- [ ] 「今回実装しないこと」が明示されているか
- [ ] 全画面に「表示するもの」「できること」が書かれているか
- [ ] データの型と保存先が指定されているか
- [ ] 認証の要否が明示されているか
- [ ] デザインのトーンが指定されているか（指定なしだとデフォルトになる）

## アプリを量産するためのパーツ再利用

複数のアプリを開発するなら、共通パーツをストックしておくと効率が上がります。

### 認証パーツ（メールアドレス認証）

```
## 認証
Firebase Authentication を使用。
メールアドレス＋パスワードでの登録・ログイン。
ログイン状態は AsyncStorage に保持。
未ログインの場合はログイン画面にリダイレクト。
パスワードリセットはメール送信で対応。
```

### エラーハンドリングパーツ

```
## エラーハンドリング
- 通信エラー: 画面上部にトースト表示（3秒後に消える）・再試行ボタンあり
- 認証エラー: モーダルで具体的なエラーメッセージを表示
- バリデーションエラー: 入力フィールドの下にインラインで表示
- 空状態: データがない場合は専用の空状態コンポーネントを表示
```

### Firebase 設定パーツ

```
## Firebase 設定
- Authentication: メールアドレス認証のみ有効
- Firestore: ルールはユーザーごとのread/writeのみ許可
- Storage: 画像ファイルの保存（最大10MB/ファイル）
- セキュリティルール: ログイン済みユーザーのみアクセス可
```

これらをスニペットとして保存しておき、新しいアプリの設計書に貼り付けるだけで大幅な時間短縮になります。

## 設計書→Rork→検証のサイクルを短くする

最後に、Rork との開発サイクル全体を効率化するポイントをお伝えします。

**1回目のプロンプト**: 設計書全体を渡して骨格を生成
**確認するポイント**: 画面遷移が正しいか・データが正しく保存されているか
**2回目以降の修正**: 1点ずつ、具体的に指定して修正

「全体的に直して」ではなく「ホーム画面の○○を〇〇に変えて。それ以外は変更しないで」という形式で修正すると、意図しない部分への変更が防げます。

修正の際も「何を変えるか」だけでなく「何を変えないか」を指定することが、Rork × 設計書戦略の基本です。

これを意識するだけで、アプリ開発のペースは確実に上がります。
