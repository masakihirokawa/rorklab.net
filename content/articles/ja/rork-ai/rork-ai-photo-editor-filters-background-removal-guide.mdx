## 「写真アプリを作りたい」のに、どこから手をつければいいかわからない問題

カメラで撮った写真にフィルターをかけて、背景を消して、AI でイラスト風に変換します。ユーザーとしては当たり前に使っている機能ですが、いざ開発者として実装しようとすると、最初の一歩で立ち止まります。画像のピクセル操作はどのレイヤーで行うのか。背景除去 API は何を基準に選ぶのか。10 秒以上かかる処理の最中に、画面には何を出しておくのか。

このアプリを Rork で構築したとき、最初に痛感したのは「画像処理アプリは、アルゴリズムよりも UI と待ち時間の設計で差がつく」ということでした。アルゴリズムや API はライブラリが吸収してくれます。けれども、処理の待ち時間をどう感じさせるか、フィルターのプレビューをどの粒度で見せるか、編集のアンドゥをどう管理するか。この 3 つはコードを書く前に決めておかないと、後から差し込むコストが跳ね上がります。

以下は、フィルター適用・背景除去・AI スタイル変換・エクスポートの 4 機能を備えたアプリを組み上げるまでの実装記録です。動くコードと、なぜその判断にしたのかを併記しています。

## 起動から 90 秒 — フォトエディタの寿命を決める最初の関門

フォトエディタが使われ続けるかどうかは、初回起動から最初の成功体験までの短さでほぼ決まる、と考えて設計しています。ここでの成功体験は、起動 → 写真選択 → ワンタップでフィルター適用 → シェア候補の表示、までの一連の流れです。90 秒という線は、筆者が置いた設計上の目標値であり、業界統計から導いた数字ではありません。自分のアプリでは、起動完了までの時間と 7 日継続率を同じ画面に並べて、どこで折れるのかを実測してください。

最初の画面で外したくない項目は、次の 3 つです。

1. **写真ライブラリの許可ダイアログを、起動直後に出さない** — 何のアプリかを伝える前の許可リクエストは、断られやすくなります。使い方が一目でわかる画面を先に見せ、写真を選ぶ操作の直前で許可を求めます。保存だけなら、iOS には書き込み専用の許可（`MediaLibrary.requestPermissionsAsync(true)`）があり、全写真への権限は要りません
2. **フィルター適用後のシェアボタンを、画面下部の親指が届く位置に固定する** — スクロールしないと現れない位置にあると、「シェアできるアプリ」だと伝わりません。固定の前後でシェア率を比べ、差は自分の数字で確かめていただければと思います
3. **最初の 30 秒で、ユーザー自身の写真が変化する瞬間を見せる** — 他人の写真を加工するデモではなく、自分の写真がワンタップで変わる体験を最初に置きます

フォトエディタの分岐点は機能の多さではなく、最初の数十秒で「自分の写真が良くなった」と感じられるかどうかです。

### コードレベルの判断: 画像圧縮のタイミングを 2 段階に分ける

フィルター適用前に画像をプレビュー解像度（長辺 1080px）へ縮小し、書き出しのときだけ元解像度に対して操作を再生する「2 段階処理」にすると、メモリの問題を抑えやすくなります。12 メガピクセル（4032 × 3024）の画像は、デコード後に約 48MB（1 画素 4 バイト × 約 1,220 万画素）を占めます。操作のたびにこの画像を丸ごと抱えると、バックグラウンドで終了されやすくなります。

```typescript
// services/image-pipeline.ts
import { ImageManipulator, SaveFormat } from 'expo-image-manipulator';

// 編集操作は「コンテキストに適用する関数」として記録しておく
type EditOp = (ctx: ReturnType<typeof ImageManipulator.manipulate>) => void;

interface ImageState {
  originalUri: string;        // 編集中は触らない
  previewUri: string;         // 長辺 1080px、フィルタープレビュー用
  exportPipeline: EditOp[];   // 書き出し時に再生する操作リスト
}

const PREVIEW_LONG_EDGE = 1080;

export async function loadImageForEditing(uri: string): Promise<ImageState> {
  // 操作なしで render して、元画像の縦横を取得する
  const probe = await ImageManipulator.manipulate(uri).renderAsync();
  if (Math.max(probe.width, probe.height) <= PREVIEW_LONG_EDGE) {
    // 小さい画像は拡大しない
    return { originalUri: uri, previewUri: uri, exportPipeline: [] };
  }

  // 長辺側だけを指定する（もう一方は縦横比から決まる）
  const ctx = ImageManipulator.manipulate(uri);
  ctx.resize(
    probe.width >= probe.height
      ? { width: PREVIEW_LONG_EDGE }
      : { height: PREVIEW_LONG_EDGE },
  );
  const preview = await (await ctx.renderAsync()).saveAsync({
    compress: 0.85,
    format: SaveFormat.JPEG,
  });

  return { originalUri: uri, previewUri: preview.uri, exportPipeline: [] };
}

export async function exportWithFullQuality(
  state: ImageState,
): Promise<string> {
  // 全操作を 1 つのコンテキストで再生し、JPEG への保存は最後の 1 回だけにする
  const ctx = ImageManipulator.manipulate(state.originalUri);
  for (const op of state.exportPipeline) op(ctx);
  const ref = await ctx.renderAsync();
  const result = await ref.saveAsync({
    compress: 0.92,
    format: SaveFormat.JPEG,
  });
  return result.uri;
}
```

この設計の利点は 2 つあります。ひとつは、プレビューが小さな画像の上で動くため、応答が軽くなること。もうひとつは、書き出しで JPEG を書くのが 1 回で済むことです。操作ごとに JPEG で保存し直すと、世代を重ねるたびに画質が落ちます（操作ごとに保存し直す実装は、よく見かける形です）。また、`resize` に幅だけを渡すと、縦長の写真では長辺が 1080px を大きく超えます。長辺基準にするなら、縦横を見て指定する側を切り替える必要があります。

プレビューの所要時間やクラッシュ率は、端末によって大きく変わります。ここでは具体的な数字を掲げません。`performance.now()` でフィルター適用の時間を測り、クラッシュ率は Crashlytics などで端末別に確認してください。

## アプリのアーキテクチャ設計 — 画像処理パイプラインの考え方

フォトエディタアプリの核心は「非破壊編集」の設計にあります。元画像を直接変更するのではなく、編集操作をスタックとして積み上げ、いつでも任意の状態に戻れるようにします。この設計を最初に決めておかないと、アンドゥ機能の追加で全体をリファクタリングする羽目になります。

Rork に以下のようなプロンプトを渡して、基本構造を生成します。

```typescript
// アプリの状態管理 — 編集履歴スタック
// Rork プロンプト例:
// 「非破壊編集に対応した画像エディタの状態管理を作って。
//   編集操作はスタックで管理し、undo/redo に対応。
//   各操作は type, params, timestamp を持つ。」

interface EditOperation {
  id: string;
  type: 'filter' | 'crop' | 'background_removal' | 'style_transfer';
  params: Record<string, unknown>;
  timestamp: number;
}

interface EditorState {
  originalUri: string;           // 元画像（絶対に変更しない）
  currentUri: string;            // 現在の表示用画像
  operations: EditOperation[];   // 適用済み操作スタック
  undoneOperations: EditOperation[]; // redo 用スタック
  isProcessing: boolean;
  processingProgress: number;    // 0-100
}

// undo: operations の末尾を undoneOperations に移動
// redo: undoneOperations の末尾を operations に戻す
// 新しい操作追加時: undoneOperations をクリア（分岐禁止）
```

なぜ `undoneOperations` を別配列で管理するのか。Redux のような状態管理ライブラリにはタイムトラベル機能がありますが、画像処理の場合は各操作に「処理済みの中間画像」が紐づくため、一般的なステート管理とは別のレイヤーで管理した方が、メモリ効率とパフォーマンスの両面で有利になります。

### 画面構成の設計

フォトエディタの画面遷移は極力シンプルにします。編集画面内でタブやモーダルを重ねすぎると、ユーザーは「今どの操作モードにいるのか」を見失います。

- **ホーム画面**: カメラ起動 / ギャラリーから選択
- **エディタ画面**: 画像プレビュー + 下部にツールバー（フィルター / 背景除去 / スタイル変換 / 切り抜き）
- **エクスポート画面**: 保存先選択 + シェアシート

ツールバーのアイコンを横スクロールにするか固定 4 つにするかは迷いましたが、機能を 4 つに絞って固定表示にしました。横スクロールは「まだ見えていない機能がある」ことを暗示してしまい、全機能を把握する前に離脱されるリスクがあります。

## 画像フィルター機能の実装 — リアルタイムプレビューの設計が鍵

画像フィルターはフォトエディタの基本機能ですが、実装で最も差が出るのは「プレビューの応答速度」です。フィルターを選ぶたびに 2 秒待たされるアプリと、指で触れた瞬間に反映されるアプリでは、ユーザー体験がまるで別物になります。

```typescript
// ---- カラーマトリクス（4x5・行優先・オフセット列は 0〜1 の正規化値）----
type Matrix = number[];

// a を先に、b を後に適用した合成行列
function concat(b: Matrix, a: Matrix): Matrix {
  const out = new Array(20).fill(0);
  for (let r = 0; r < 4; r++) {
    for (let c = 0; c < 5; c++) {
      let v = 0;
      for (let k = 0; k < 4; k++) v += b[r * 5 + k] * a[k * 5 + c];
      if (c === 4) v += b[r * 5 + 4];
      out[r * 5 + c] = v;
    }
  }
  return out;
}

function buildColorMatrix(p: FilterParams): Matrix {
  const s = p.saturation;
  const saturate: Matrix = [
    0.213 + 0.787 * s, 0.715 - 0.715 * s, 0.072 - 0.072 * s, 0, 0,
    0.213 - 0.213 * s, 0.715 + 0.285 * s, 0.072 - 0.072 * s, 0, 0,
    0.213 - 0.213 * s, 0.715 - 0.715 * s, 0.072 + 0.928 * s, 0, 0,
    0, 0, 0, 1, 0,
  ];
  const k = 1 - p.sepia; // CSS の sepia() と同じ係数を、元画像とブレンドする
  const sepia: Matrix = [
    0.393 + 0.607 * k, 0.769 - 0.769 * k, 0.189 - 0.189 * k, 0, 0,
    0.349 - 0.349 * k, 0.686 + 0.314 * k, 0.168 - 0.168 * k, 0, 0,
    0.272 - 0.272 * k, 0.534 - 0.534 * k, 0.131 + 0.869 * k, 0, 0,
    0, 0, 0, 1, 0,
  ];
  const c = p.contrast;
  const o = (1 - c) / 2;
  const contrast: Matrix = [
    c, 0, 0, 0, o,
    0, c, 0, 0, o,
    0, 0, c, 0, o,
    0, 0, 0, 1, 0,
  ];
  const b = 1 + p.brightness; // CSS の brightness() と同じ乗算
  const brightness: Matrix = [
    b, 0, 0, 0, 0,
    0, b, 0, 0, 0,
    0, 0, b, 0, 0,
    0, 0, 0, 1, 0,
  ];
  return concat(brightness, concat(contrast, concat(sepia, saturate)));
}

// プレビュー用。imageUri には縮小版（previewUri）を渡す
function FilteredImage({
  uri, params, style,
}: { uri: string; params: FilterParams; style?: StyleProp<ViewStyle> }) {
  const image = useImage(uri);
  const [size, setSize] = useState({ width: 0, height: 0 });
  const matrix = useMemo(() => buildColorMatrix(params), [params]);

  return (
    <View
      style={style}
      onLayout={(e) => setSize({
        width: e.nativeEvent.layout.width,
        height: e.nativeEvent.layout.height,
      })}
    >
      <Canvas style={{ width: size.width, height: size.height }}>
        {image && size.width > 0 && (
          <SkiaImage
            image={image}
            x={0}
            y={0}
            width={size.width}
            height={size.height}
            fit="contain"
          >
            <ColorMatrix matrix={matrix} />
          </SkiaImage>
        )}
      </Canvas>
    </View>
  );
}

```

先に、プレビューの作り方で外しやすい点を書いておきます。React Native の `filter` スタイルは、New Architecture 限定の機能です。公式ドキュメントによると、iOS で使えるのは `brightness` と `opacity` だけで、`contrast`・`saturate`・`sepia` などは Android 専用です。つまり、`filter` の文字列でプリセットを作ると、iOS ではコントラストも彩度もセピアも変わりません。両 OS で同じ見た目を出すために、上のコードは Skia のカラーマトリクスでプレビューを描いています。

ここで重要なポイントが2つあります。まず、フィルターのプレビューにはサムネイルサイズの画像を使います。フル解像度の画像に 6 種類のフィルターをリアルタイム適用すると、低スペック端末ではフレームレートが目に見えて落ちます。サムネイルでプリセットを選ばせて、「適用」を押したときだけフル解像度で処理する 2 段階設計が実用的です。

次に、スライダーを `onValueChange` でリアルタイム更新するか、`onSlidingComplete` で確定時のみ更新するかという判断です。`onValueChange` でも軽く動く端末がある一方で、スライダーの追従が目に見えて遅れる端末もあります。そこで、プレビュー画像の解像度を端末のメモリに応じて決めるようにしました。その実装は後述します。

### 端末のメモリからプレビュー解像度を決める

「端末に応じて解像度を変える」と書いたものの、実際に何を見て決めるのかが問題になります。React Native からは総メモリ量を直接読めないため、`react-native-device-info` の `getTotalMemory()` と、初回のフィルター適用にかかった実測時間の両方を使いました。

静的な端末リストで分岐させる方法もありますが、新機種が出るたびにリストの更新が必要になり、更新漏れの端末は想定より重い設定で動いてしまいます。実測値で自己補正する方式なら、リストの保守は要りません。

```typescript
// services/preview-resolution.ts
import DeviceInfo from 'react-native-device-info';

type Tier = 'low' | 'mid' | 'high';

const TIER_WIDTH: Record<Tier, number> = {
  low: 640,
  mid: 900,
  high: 1280,
};

// フィルター 1 回の適用がこの時間を超えたら 1 段下げる
const DEGRADE_THRESHOLD_MS = 180;
// 逆にこの時間を下回り続けたら 1 段上げる
const UPGRADE_THRESHOLD_MS = 45;

let currentTier: Tier | null = null;
let fastStreak = 0;

async function detectInitialTier(): Promise<Tier> {
  const totalBytes = await DeviceInfo.getTotalMemory();
  const totalGb = totalBytes / 1024 ** 3;
  // 目安の境界値。対象端末で実測して調整する
  if (totalGb < 3) return 'low';
  if (totalGb < 6) return 'mid';
  return 'high';
}

export async function getPreviewWidth(): Promise<number> {
  if (currentTier === null) {
    currentTier = await detectInitialTier();
  }
  return TIER_WIDTH[currentTier];
}

// フィルター適用のたびに実測時間を渡して自己補正する
export function reportFilterDuration(ms: number): void {
  if (currentTier === null) return;

  if (ms > DEGRADE_THRESHOLD_MS) {
    fastStreak = 0;
    if (currentTier === 'high') currentTier = 'mid';
    else if (currentTier === 'mid') currentTier = 'low';
    return;
  }

  if (ms < UPGRADE_THRESHOLD_MS) {
    fastStreak += 1;
    // 一度の偶然で上げない。連続 8 回を条件にする
    if (fastStreak >= 8) {
      if (currentTier === 'low') currentTier = 'mid';
      else if (currentTier === 'mid') currentTier = 'high';
      fastStreak = 0;
    }
  }
}
```

降格は 1 回で、昇格は 8 回連続を条件にしています。非対称にしているのは、ユーザー体験の損失が非対称だからです。解像度が 1 段低いことに気づくユーザーはほとんどいませんが、スライダーが 200ms 遅れて追従することには全員が気づきます。迷ったら下げる側に倒す、という判断です。

`reportFilterDuration` は、フィルター適用を包む場所で `performance.now()` の差分を渡すだけで機能します。ティアを AsyncStorage に永続化したくなりますが、これは行わない選択にしました。バックグラウンドのアプリ状況によって同じ端末でも所要時間は変動するため、セッションごとに測り直したほうが実態に合います。

## AI 背景除去の実装 — API 選定とフォールバック設計

背景除去は、ユーザーが最も「AI っぽい」と感じる機能です。実装のアプローチは大きく2つあります。

- **クラウド API 方式**: remove.bg、Clipdrop、Photoroom などの専用 API を呼びます
- **オンデバイス方式**: TensorFlow Lite や Core ML でローカル処理します

私はこの構成で、「クラウド API をメインに、簡易オンデバイス処理をフォールバックにする」ハイブリッドを選びます。理由は、一般に背景除去の精度はクラウド API のほうが高い一方で、ネットワークがない場面でも最低限の機能は残したいからです。

**ひとつ、日付つきの注意があります。** remove.bg の公式 API ページには、2026 年 12 月 1 日から背景除去が Leonardo.Ai に移ると書かれています（「Leonardo API Migration」の案内もあります）。以下のコードは remove.bg のエンドポイントを例にしているため、この日付以降に使う場合は、移行先の仕様を確認してから差し替えてください。サービス層を差し替え可能に作る理由が、まさにここにあります。

```typescript
// 背景除去サービス — クラウド API + フォールバック設計
// エラーハンドリングとリトライを含む本番品質の実装

interface BackgroundRemovalResult {
  success: boolean;
  imageUri?: string;
  method: 'cloud' | 'ondevice' | 'failed';
  error?: string;
  processingTimeMs: number;
}

const CLOUD_API_TIMEOUT_MS = 30000;
const MAX_RETRIES = 2;
const RETRY_DELAY_MS = 1000;
const MAX_UPLOAD_BYTES = 22 * 1024 * 1024;

async function removeBackground(
  imageUri: string,
  apiKey: string,
): Promise<BackgroundRemovalResult> {
  const startTime = Date.now();

  // 1. クラウド API を試行（リトライ付き）
  for (let attempt = 0; attempt <= MAX_RETRIES; attempt++) {
    try {
      const result = await callCloudApi(imageUri, apiKey);
      return {
        success: true,
        imageUri: result.outputUri,
        method: 'cloud',
        processingTimeMs: Date.now() - startTime,
      };
    } catch (error) {
      const isLastAttempt = attempt === MAX_RETRIES;
      const isRetryable = isRetryableError(error);

      if (isLastAttempt || !isRetryable) {
        console.warn(
          `Cloud API failed (attempt ${attempt + 1}/${MAX_RETRIES + 1}):`,
          error instanceof Error ? error.message : 'Unknown error'
        );
        break;
      }

      // 指数バックオフで待機
      await sleep(RETRY_DELAY_MS * Math.pow(2, attempt));
    }
  }

  // 2. フォールバック: オンデバイス処理
  try {
    console.log('Falling back to on-device processing...');
    const onDeviceResult = await processOnDevice(imageUri);
    return {
      success: true,
      imageUri: onDeviceResult.outputUri,
      method: 'ondevice',
      processingTimeMs: Date.now() - startTime,
    };
  } catch (onDeviceError) {
    return {
      success: false,
      method: 'failed',
      error: onDeviceError instanceof Error
        ? onDeviceError.message
        : 'Background removal failed',
      processingTimeMs: Date.now() - startTime,
    };
  }
}

async function callCloudApi(
  imageUri: string,
  apiKey: string,
): Promise<{ outputUri: string }> {
  // ローカル URI から Blob を取得（FormData で送るので Base64 化は不要）
  const response = await fetch(imageUri);
  const blob = await response.blob();

  // ファイルサイズチェック（remove.bg 公式ページの記載: 最大 22MB）
  if (blob.size > MAX_UPLOAD_BYTES) {
    throw new Error('Image too large. Maximum size is 22MB.');
  }

  const formData = new FormData();
  formData.append('image_file', blob, 'image.png');
  formData.append('size', 'auto');

  const controller = new AbortController();
  const timeoutId = setTimeout(
    () => controller.abort(),
    CLOUD_API_TIMEOUT_MS,
  );

  try {
    const apiResponse = await fetch('https://api.remove.bg/v1.0/removebg', {
      method: 'POST',
      headers: { 'X-Api-Key': apiKey },
      body: formData,
      signal: controller.signal,
    });

    if (!apiResponse.ok) {
      const errorBody = await apiResponse.text().catch(() => '');
      throw new ApiError(
        `API returned ${apiResponse.status}: ${errorBody}`,
        apiResponse.status,
      );
    }

    const resultBlob = await apiResponse.blob();
    // ローカルファイルとして保存し URI を返す
    const outputUri = await saveBlobToFile(resultBlob, 'bg_removed.png');
    return { outputUri };
  } finally {
    clearTimeout(timeoutId);
  }
}

// リトライ可能なエラーかどうかを判定
function isRetryableError(error: unknown): boolean {
  if (error instanceof ApiError) {
    // 429 (Rate Limit) と 5xx はリトライ可能
    return error.statusCode === 429 || error.statusCode >= 500;
  }
  // ネットワークエラーはリトライ可能
  if (error instanceof TypeError && error.message.includes('network')) {
    return true;
  }
  return false;
}

class ApiError extends Error {
  constructor(message: string, public statusCode: number) {
    super(message);
    this.name = 'ApiError';
  }
}

function sleep(ms: number): Promise<void> {
  return new Promise(resolve => setTimeout(resolve, ms));
}
```

### なぜリトライ戦略が重要なのか

画像処理 API は、通常の REST API よりもタイムアウトやレート制限に遭遇しやすい傾向があります。画像データの送受信にはそれなりの帯域を使いますし、サーバー側の推論処理にも時間がかかるためです。リトライなしで「処理に失敗しました」とだけ表示するアプリは、ユーザーの信頼を一瞬で失います。

指数バックオフ（1秒 → 2秒 → 4秒）を入れているのは、429（Rate Limit）エラーへの対策です。同じ間隔でリトライし続けると、API サーバー側のレート制限がさらに厳しくなる場合があります。

### remove.bg・Clipdrop・Photoroom — 選ぶときに見る観点（2026 年 10 月時点）

3 つを横並びで「どれが一番か」と決める書き方はしません。サービスの提供条件は動きが速く、この記事を書いている間にも変わるからです。確認できた事実と、採用前に自分で見る点を分けて整理します。

- **remove.bg**: 公式ページでは、最初の 50 回の API 呼び出しが無料と案内されています。入力画像は最大 22MB、出力は最大 50 メガピクセルです。ただし PNG 出力は 10 メガピクセルまでで、それを超える透明画像は WebP や ZIP で受け取る必要があります。前述のとおり、2026 年 12 月 1 日に Leonardo.Ai への移行が予定されています
- **Clipdrop**: 運営元が Stability AI から Jasper に移っています（Jasper による買収の発表があります）。API の提供条件や料金は変わっていることがあるため、採用前に最新の公式ページで確認してください
- **Photoroom**: EC の商品画像向けの機能に力を入れているサービスです。背景除去のあとに背景の差し替えまで API で任せられるかは、公式の最新仕様で確認してください

どれを選ぶ場合も、同じ 10〜20 枚を各 API に通して、縁を目視で比べてから決めていただければと思います。枚数の内訳は、人物の髪、ガラスや薄い布のような半透明の被写体、商品写真を、それぞれ数枚ずつです。精度の差は、この比較でいちばん正直に出ます。

### API の精度差より、返ってきたマスクの縁の処理で差がつく

背景除去 API を比較していると精度の話ばかりになりますが、実際にユーザーから「切り抜きが雑」と言われる原因の多くは、API の推論精度ではなく、返ってきた透明 PNG をそのまま合成していることにあります。

原因は 2 つです。ひとつはアルファチャンネルの縁が硬すぎること。1 ピクセルで不透明から透明へ落ちるため、別の背景に載せると輪郭がカッターで切ったように浮きます。もうひとつは色被り（スピル）で、緑の芝生の前で撮った人物の髪の縁に緑が残り、白背景に載せると緑の輪郭線として見えてしまいます。

どちらも、API を変えても解決しません。クライアント側でアルファに軽いフェザーをかけ、縁の帯だけ彩度を落とすと、見た目が変わります。React Native では `@shopify/react-native-skia` でこの後処理を書けます。

```typescript
// services/matte-refine.ts
import { Skia, TileMode, BlendMode } from '@shopify/react-native-skia';

interface RefineOptions {
  featherSigma: number;    // Skia のぼかしは標準偏差（sigma）指定。長辺比で決める
  despillStrength: number; // 0.0 〜 1.0
  edgeBandPx: number;      // 縁として扱う帯の幅（ピクセル）
}

/**
 * 背景除去 API が返した透明 PNG の縁を整える。
 * 1) 縁の帯だけ彩度を落とす（内側は元の色のまま）
 * 2) アルファをぼかして、硬いエッジを和らげる
 */
export function refineMatte(
  cutoutPngBytes: Uint8Array,
  options: RefineOptions,
): Uint8Array | null {
  const data = Skia.Data.fromBytes(cutoutPngBytes);
  const image = Skia.Image.MakeImageFromEncoded(data);
  if (!image) return null;

  const width = image.width();
  const height = image.height();
  const surface = Skia.Surface.Make(width, height);
  if (!surface) return null;
  const canvas = surface.getCanvas();

  // 1) 元の色のまま画像を描く
  canvas.drawImage(image, 0, 0);

  // 2) 縁の帯だけ彩度を落とす。
  //    別レイヤーに「彩度を落とした画像」を描き、被写体を縁の幅だけ縮めた
  //    アルファで内側をくり抜く（DstOut）。残るのは縁の帯だけになる。
  //    レイヤーは SrcATop で重ね、元のアルファを増やさない
  const s = 1 - options.despillStrength;
  const desaturate = Skia.ColorFilter.MakeMatrix([
    0.213 + 0.787 * s, 0.715 - 0.715 * s, 0.072 - 0.072 * s, 0, 0,
    0.213 - 0.213 * s, 0.715 + 0.285 * s, 0.072 - 0.072 * s, 0, 0,
    0.213 - 0.213 * s, 0.715 - 0.715 * s, 0.072 + 0.928 * s, 0, 0,
    0, 0, 0, 1, 0,
  ]);
  const layerPaint = Skia.Paint();
  layerPaint.setBlendMode(BlendMode.SrcATop);
  canvas.saveLayer(layerPaint);

  const edgePaint = Skia.Paint();
  edgePaint.setColorFilter(desaturate);
  canvas.drawImage(image, 0, 0, edgePaint);

  const cutPaint = Skia.Paint();
  cutPaint.setImageFilter(
    Skia.ImageFilter.MakeErode(options.edgeBandPx, options.edgeBandPx, null),
  );
  cutPaint.setBlendMode(BlendMode.DstOut);
  canvas.drawImage(image, 0, 0, cutPaint);
  canvas.restore();

  // 3) アルファだけをぼかして DstIn で掛け、縁をなだらかにする。
  //    DstIn は描く側のアルファだけを使うので、色は失われない
  const featherPaint = Skia.Paint();
  featherPaint.setImageFilter(
    Skia.ImageFilter.MakeBlur(
      options.featherSigma,
      options.featherSigma,
      TileMode.Decal,
      null,
    ),
  );
  featherPaint.setBlendMode(BlendMode.DstIn);
  canvas.drawImage(image, 0, 0, featherPaint);

  return surface.makeImageSnapshot().encodeToBytes();
}
```

よくある失敗を、ひとつ挙げておきます。アルファだけを取り出すために色行列で RGB を 0 にしてから描くと、被写体が黒く塗りつぶされた「影絵」が返ってきます。上のコードは、色をそのままにして、DstIn の合成でアルファだけを掛けています。なお、Skia の API 名や引数はバージョンで差が出ます。手元の型定義を確認し、必ず実機で縁を目視してください。

`featherSigma` は画像の長辺に比例させるのが自然です。長辺 4000px の写真に sigma 1.0 のフェザーをかけても効きませんし、長辺 800px のサムネイルに sigma 3.0 をかけると被写体が溶けます。長辺の 0.05% 程度（4000px なら 2.0、800px なら 0.4）を出発点にして、被写体の種類で微調整してください。`edgeBandPx` も同じく、長辺の 0.1% 前後（4000px なら 4px）から試すのが無難です。

`despillStrength` は、人物なら 0.35 前後、商品写真なら 0.15 前後から始めるのが目安です。商品写真は色の忠実さが購買判断に直結するため、スピル除去を強くかけすぎると、今度は「実物と色が違う」という指摘につながります。ここは用途で分けたほうが安全です。

この後処理は、API の往復に比べれば小さなコストで済むはずです。ただし端末と画像サイズで変わるので、処理時間は自分の端末で測ってください。私なら、API を乗り換える前に、まずここを疑います。

**API が返すのは素材であって、完成品ではありません。縁と色を整えるところまでが、アプリの仕事です。**

## AI スタイル変換の統合 — Replicate API による画風変換

AI スタイル変換は、ユーザーの写真を「水彩画風」「油絵風」「アニメ風」などに変換する機能です。この機能を入れるかどうかで、「ただのフィルターアプリ」と「AI フォトエディタ」では受け取られ方が大きく変わります。

実装には Replicate API を使います。Replicate は Stable Diffusion ベースのモデルを API として呼び出せるプラットフォームで、img2img（画像から画像への変換）に使えます。モデルのバージョンは入れ替わるため、コードにはモデルページで確認したバージョン ID を設定します。公式モデルなら `/v1/models/{owner}/{model}/predictions` の形で、`version` なしで呼べます。出力ファイルの URL は永続する前提で扱わず、受け取ったらすぐ端末に保存してください（保持期間は Replicate の Data retention のドキュメントで確認できます）。

```typescript
// AI スタイル変換 — Replicate API を使った画風変換
// 注意: 本番ではこの関数ごとバックエンドに置く（トークンをアプリに入れない。落とし穴 3 を参照）

// Replicate のモデルページで確認した、バージョン ID（64 文字）を設定する。
// 'latest' のような文字列は指定できない
const SDXL_VERSION_ID = 'REPLACE_WITH_VERSION_ID_FROM_MODEL_PAGE';

interface StyleTransferResult {
  success: boolean;
  outputUri?: string;
  error?: string;
  style: string;
}

const STYLE_PROMPTS: Record<string, { prompt: string; strength: number }> = {
  watercolor: {
    prompt: 'watercolor painting, soft brushstrokes, artistic, delicate colors',
    strength: 0.65,
  },
  oilpainting: {
    prompt: 'oil painting on canvas, thick impasto brushwork, rich vibrant colors, classical art',
    strength: 0.70,
  },
  anime: {
    prompt: 'anime style illustration, clean lines, vibrant colors, soft hand-painted backgrounds',
    strength: 0.60,
  },
  sketch: {
    prompt: 'pencil sketch drawing, detailed linework, crosshatching, black and white',
    strength: 0.75,
  },
  cyberpunk: {
    prompt: 'cyberpunk neon art style, glowing neon lights, futuristic, high contrast',
    strength: 0.55,
  },
};

async function applyStyleTransfer(
  imageUri: string,
  styleId: keyof typeof STYLE_PROMPTS,
  replicateApiToken: string,
): Promise<StyleTransferResult> {
  const style = STYLE_PROMPTS[styleId];
  if (!style) {
    return { success: false, error: `Unknown style: ${styleId}`, style: styleId };
  }

  try {
    // 画像を Base64 に変換（送る前に長辺 1280px 程度へ縮小しておく）
    const imageBase64 = await imageToBase64(imageUri);
    const dataUri = `data:image/png;base64,${imageBase64}`;

    // Replicate API で予測を作成
    const createResponse = await fetch('https://api.replicate.com/v1/predictions', {
      method: 'POST',
      headers: {
        'Authorization': `Bearer ${replicateApiToken}`,
        'Content-Type': 'application/json',
      },
      body: JSON.stringify({
        // img2img 対応モデル（Stable Diffusion XL）のバージョン ID
        version: SDXL_VERSION_ID,
        input: {
          image: dataUri,
          prompt: style.prompt,
          prompt_strength: style.strength,
          num_inference_steps: 30,
          guidance_scale: 7.5,
        },
      }),
    });

    if (!createResponse.ok) {
      const errorText = await createResponse.text();
      throw new Error(`Replicate API error: ${createResponse.status} ${errorText}`);
    }

    const prediction = await createResponse.json();

    // ポーリングで完了を待つ（最大 60 秒）
    const result = await pollPrediction(prediction.id, replicateApiToken, 60000);

    if (result.status === 'succeeded' && result.output) {
      const outputUrl = Array.isArray(result.output) ? result.output[0] : result.output;
      const localUri = await downloadAndSave(outputUrl, `style_${styleId}.png`);
      return { success: true, outputUri: localUri, style: styleId };
    }

    return {
      success: false,
      error: result.error || 'Style transfer failed',
      style: styleId,
    };
  } catch (error) {
    return {
      success: false,
      error: error instanceof Error ? error.message : 'Unknown error',
      style: styleId,
    };
  }
}

async function pollPrediction(
  predictionId: string,
  apiToken: string,
  timeoutMs: number,
): Promise<{ status: string; output?: string | string[]; error?: string }> {
  const deadline = Date.now() + timeoutMs;
  const pollInterval = 2000; // 2秒間隔

  while (Date.now() < deadline) {
    const response = await fetch(
      `https://api.replicate.com/v1/predictions/${predictionId}`,
      { headers: { 'Authorization': `Bearer ${apiToken}` } },
    );

    if (!response.ok) {
      throw new Error(`Poll failed: ${response.status}`);
    }

    const data = await response.json();

    if (data.status === 'succeeded' || data.status === 'failed' || data.status === 'canceled') {
      return data;
    }

    // 処理中 — 待機して再試行
    await sleep(pollInterval);
  }

  throw new Error('Style transfer timed out');
}
```

### Strength パラメータの調整が成否を分ける

`prompt_strength`（0.0〜1.0）は「元画像をどれだけ変化させるか」を制御します。この値が高すぎると元の構図が保てなくなり、低すぎるとフィルターをかけたのかどうかも判別できない程度にしか変わりません。

出発点の目安は、スタイルごとに次の範囲です。モデルとバージョンで挙動が変わるため、固定値にせず自分の素材で確かめてください。

- 水彩画: 0.60〜0.70（構図は保ちつつ、筆のタッチ感を出す）
- 油絵: 0.65〜0.75（テクスチャの変化を大きくするため、やや高め）
- アニメ: 0.55〜0.65（顔の特徴を残すために低めに設定）
- スケッチ: 0.70〜0.80（線画への変換なので、大きく変化させて構いません）

ユーザーがスライダーで `strength` を調整できる UI を足すと、「AI が勝手に変えすぎた」という不満を、ユーザー自身の手で解消できます。

## 処理中 UI の設計 — ユーザーを待たせない工夫

AI 処理には時間がかかります。所要時間は API とモデル、通信状況で大きく変わるので、次のコードの `estimatedSeconds` には、自分で計測した中央値を入れてください。この待ち時間をどう演出するかで、アプリの印象が決まります。

```typescript
// プログレス表示コンポーネント — 段階的フィードバック
import React, { useEffect, useState, useRef } from 'react';
import { View, Text, Animated, StyleSheet, Easing } from 'react-native';

interface ProcessingOverlayProps {
  isVisible: boolean;
  operationType: 'filter' | 'background_removal' | 'style_transfer';
  estimatedSeconds: number;
}

const OPERATION_MESSAGES: Record<string, string[]> = {
  filter: ['フィルターを適用中...'],
  background_removal: [
    '画像を分析中...',
    '被写体を検出中...',
    '背景を除去中...',
    '仕上げ処理中...',
  ],
  style_transfer: [
    '画像を解析中...',
    'AIモデルを準備中...',
    'スタイルを変換中...',
    'ディテールを調整中...',
    '最終仕上げ中...',
  ],
};

export function ProcessingOverlay({
  isVisible,
  operationType,
  estimatedSeconds,
}: ProcessingOverlayProps) {
  const [messageIndex, setMessageIndex] = useState(0);
  const progressAnim = useRef(new Animated.Value(0)).current;
  const messages = OPERATION_MESSAGES[operationType] || ['処理中...'];

  useEffect(() => {
    if (!isVisible) {
      setMessageIndex(0);
      progressAnim.setValue(0);
      return;
    }

    // プログレスバーアニメーション
    Animated.timing(progressAnim, {
      toValue: 0.9, // 90%まで自動進行（残り10%は完了時に一気に埋める）
      duration: estimatedSeconds * 1000,
      easing: Easing.out(Easing.quad), // 最初は速く、徐々に遅く
      useNativeDriver: false,
    }).start();

    // メッセージの段階的切り替え
    const intervalMs = (estimatedSeconds * 1000) / messages.length;
    const timer = setInterval(() => {
      setMessageIndex(prev => Math.min(prev + 1, messages.length - 1));
    }, intervalMs);

    return () => clearInterval(timer);
  }, [isVisible, estimatedSeconds, messages.length, progressAnim]);

  if (!isVisible) return null;

  const progressWidth = progressAnim.interpolate({
    inputRange: [0, 1],
    outputRange: ['0%', '100%'],
  });

  return (
    <View style={styles.overlay}>
      <View style={styles.card}>
        <Text style={styles.message}>{messages[messageIndex]}</Text>
        <View style={styles.progressTrack}>
          <Animated.View
            style={[styles.progressFill, { width: progressWidth }]}
          />
        </View>
        <Text style={styles.estimate}>
          推定残り時間: 約{estimatedSeconds}秒
        </Text>
      </View>
    </View>
  );
}

const styles = StyleSheet.create({
  overlay: {
    ...StyleSheet.absoluteFillObject,
    backgroundColor: 'rgba(0,0,0,0.7)',
    justifyContent: 'center',
    alignItems: 'center',
  },
  card: {
    backgroundColor: '#1C1C1E',
    borderRadius: 16,
    padding: 24,
    width: '80%',
    alignItems: 'center',
  },
  message: { color: '#FFF', fontSize: 16, marginBottom: 16 },
  progressTrack: {
    width: '100%', height: 4, backgroundColor: '#333',
    borderRadius: 2, overflow: 'hidden',
  },
  progressFill: { height: '100%', backgroundColor: '#007AFF', borderRadius: 2 },
  estimate: { color: '#888', fontSize: 12, marginTop: 12 },
});
```

注意すべきは、プログレスバーを90%で止めている点です。AI APIの処理時間は不定で、推定時間を超えることがあります。バーが100%に達したのに処理が終わらないと、ユーザーは「フリーズした」と誤解します。90% で緩やかに減速させ、実際の完了時に一気に 100% まで埋めるのが定石です。

## よくある間違いと落とし穴 — 実装前に知っておくべきこと

### 落とし穴 1: 画像のメモリ管理を怠る

React Native で大きな画像を複数枚メモリに保持すると、特に Android でクラッシュします。4000x3000ピクセルの写真1枚は非圧縮で約 48MB のメモリを消費します。フィルタープレビュー用に6枚コピーを作ると 288MB です。

対策は、プレビュー用の画像を長辺 1080px 以下（前述の端末ティアなら 640〜1280px）に縮小することです。最終出力のときだけフル解像度で処理します。また、編集画面を離れる際には、一時ファイルを明示的に削除します。

```typescript
// 一時ファイルのクリーンアップ — 画面離脱時に削除する
import { useEffect, useRef } from 'react';
import { File } from 'expo-file-system';

function useImageCleanup(tempImageUris: string[]) {
  // 最新の配列を ref で保持し、アンマウント時だけ削除する
  // （配列を依存に入れると、更新のたびに削除が走ってしまう）
  const urisRef = useRef(tempImageUris);
  urisRef.current = tempImageUris;

  useEffect(() => {
    return () => {
      urisRef.current.forEach((uri) => {
        try {
          const file = new File(uri);
          if (file.exists) file.delete();
        } catch {
          // 削除失敗は無視（OS が回収する）
          console.warn('Failed to clean up temp image:', uri);
        }
      });
    };
  }, []);
}
```

`expo-file-system` は、現行の SDK では `File` クラスで操作します。以前の `getInfoAsync` や `deleteAsync` は非推奨になり、メインのモジュールから呼ぶと実行時にエラーになります（旧 API を使い続けるなら `expo-file-system/legacy` から import します）。

### 落とし穴 2: EXIF データの Orientation を無視する

iPhone で撮影した写真は、ピクセルデータとは別に EXIF メタデータで回転情報を保持しています。EXIF を無視して画像処理すると、横向きで表示されたり上下が逆になったりします。

```typescript
// EXIF orientation を考慮した画像読み込み
import { ImageManipulator, SaveFormat } from 'expo-image-manipulator';

async function normalizeImageOrientation(uri: string): Promise<string> {
  // 操作なしで render → 保存し、回転情報を反映した画像を作る
  const ref = await ImageManipulator.manipulate(uri).renderAsync();
  const result = await ref.saveAsync({ format: SaveFormat.PNG });
  return result.uri;
}
```

このたった数行を入れ忘れるだけで、「iPhone で撮った写真が横向きになる」というレビューが積み上がります。アップロード先でだけ向きが変わる場合は、[Rork アプリの EXIF Orientation 正規化とメタデータ削除](/articles/rork-dev/rork-image-exif-orientation-normalize-strip-metadata-upload) に切り分けの手順をまとめています。

### 落とし穴 3: API キーをクライアントに埋め込む

Rork で生成されたコードは、API キーを直接コンポーネント内に記述しがちです。remove.bg や Replicate のAPIキーがアプリのバンドルに含まれると、逆コンパイルで簡単に抜き取られます。

必ずバックエンド（Supabase Edge Functions や Cloudflare Workers）を経由させます。

```typescript
// ❌ 危険: クライアントに API キーを直接記述
const result = await fetch('https://api.remove.bg/v1.0/removebg', {
  headers: { 'X-Api-Key': 'YOUR_API_KEY' }, // 絶対にやらない
});

// ✅ 安全: 自前のバックエンド経由で API を呼ぶ
const result = await fetch('https://your-backend.workers.dev/api/remove-bg', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${userAuthToken}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ imageBase64 }),
});
// バックエンド側で API キーを付与し、remove.bg に転送する
```

この記事の前半のコードは、読みやすさのために `apiKey` を引数で渡しています。本番では、呼び出し全体をバックエンドへ移してください。その際、認証もレート制限もないエンドポイントを公開すると、他人があなたの API 枠を使えてしまいます。ユーザー認証と回数制限は、最初から入れておきます。

### 落とし穴 4: 無料 API 枠の消費を監視しない

remove.bg は、公式ページで最初の 50 回の API 呼び出しが無料と案内されています。ユーザーが気軽に「やり直し」を繰り返すと、あっという間に枠を使い切ります。API のレスポンスヘッダーで残り枠を読み取り、閾値を割ったら機能を段階的に絞る仕組みが要ります。具体的な実装は後述します。

remove.bg はレスポンスヘッダーに `X-Credits-Charged` と、アカウント API 側に残高を返します。これをバックエンドで保持し、残高の帯に応じてクライアントに機能の制限レベルを返す設計にしました。

```typescript
// backend: Cloudflare Workers 側の残枠ガード
interface QuotaState {
  remaining: number;
  level: 'normal' | 'conserve' | 'exhausted';
}

const CONSERVE_THRESHOLD = 40;   // ここを割ったら無料ユーザーの回数を絞る
const EXHAUSTED_THRESHOLD = 5;   // ここを割ったら課金ユーザー専用に切り替える

export async function resolveQuota(kv: KVNamespace): Promise<QuotaState> {
  const cached = await kv.get('removebg:remaining');
  const remaining = cached ? Number(cached) : await fetchRemainingFromApi();

  let level: QuotaState['level'] = 'normal';
  if (remaining <= EXHAUSTED_THRESHOLD) level = 'exhausted';
  else if (remaining <= CONSERVE_THRESHOLD) level = 'conserve';

  return { remaining, level };
}

// 実処理のたびにヘッダーから消費量を差し引き、KV を更新する
export async function commitUsage(
  kv: KVNamespace,
  response: Response,
): Promise<void> {
  const charged = Number(response.headers.get('X-Credits-Charged') ?? '1');
  const current = Number((await kv.get('removebg:remaining')) ?? '0');
  const next = Math.max(0, current - charged);
  // TTL を短くして、管理画面での手動追加も自然に反映されるようにする
  await kv.put('removebg:remaining', String(next), { expirationTtl: 900 });
}
```

`conserve` に落ちたときに全面停止しないのが肝心です。無料ユーザーの 1 日あたりの回数を 3 回から 1 回に絞り、`exhausted` で初めて課金ユーザー専用にします。段階を挟まずに「本日は利用できません」と出すと、不満がストアレビューに出やすくなります。

もうひとつ、クライアント側でも同じ枠を持たないことをお勧めします。端末に回数を保存すると、アプリの再インストールで簡単にリセットされます。枠の判定はサーバー側に一本化し、クライアントは返ってきた `level` を表示に反映するだけにしました。

### 落とし穴 5: 大きな画像の Base64 変換でメモリが溢れる

API に画像を送る際に Base64 エンコードすると、データ量が約 33% 増えます。10MB の画像は約 13.3MB の文字列になり、変換中は元のデータと文字列が同時にメモリに載ります。マルチパートフォームデータ（FormData）で送信するほうが、メモリ効率では有利です。Replicate のようにデータ URI で渡す API では、送る前に長辺を縮小しておきます。

## エクスポートとシェア機能の実装

編集した画像をカメラロールに保存し、SNSにシェアする機能は必須です。ここで見落としがちなのが「保存形式の選択肢」です。透明背景を維持するなら PNG が必須ですし、ファイルサイズを抑えたいなら JPEG が適しています。

```typescript
// エクスポート機能 — 形式選択 + カメラロール保存 + シェア
import * as MediaLibrary from 'expo-media-library';
import * as Sharing from 'expo-sharing';
import { ImageManipulator, SaveFormat } from 'expo-image-manipulator';
import { File } from 'expo-file-system';

interface ExportOptions {
  format: 'png' | 'jpeg';
  quality: number;   // 0.0 - 1.0 (JPEG のみ有効)
  maxWidth?: number; // リサイズ（オプション。縦横比は保たれる）
}

async function exportImage(
  imageUri: string,
  options: ExportOptions,
): Promise<{ savedUri: string; fileSize: number }> {
  // 1. フォーマット変換 + リサイズ
  const ctx = ImageManipulator.manipulate(imageUri);
  if (options.maxWidth) ctx.resize({ width: options.maxWidth });
  const ref = await ctx.renderAsync();
  const result = await ref.saveAsync({
    compress: options.quality,
    format: options.format === 'png' ? SaveFormat.PNG : SaveFormat.JPEG,
  });

  // 2. カメラロールに保存（保存だけなので、書き込み専用の許可を求める）
  const { status } = await MediaLibrary.requestPermissionsAsync(true);
  if (status !== 'granted') {
    throw new Error('カメラロールへのアクセスが許可されていません');
  }

  const asset = await MediaLibrary.createAssetAsync(result.uri);
  // 「AI Photo Editor」アルバムに整理
  // （書き込み専用の許可ではアルバムの検索ができない端末もあるため、
  //   失敗してもアセット自体は保存済みとして扱う）
  try {
    const album = await MediaLibrary.getAlbumAsync('AI Photo Editor');
    if (album) {
      await MediaLibrary.addAssetsToAlbumAsync([asset], album, false);
    } else {
      await MediaLibrary.createAlbumAsync('AI Photo Editor', asset, false);
    }
  } catch (e) {
    console.warn('Album organization skipped:', e);
  }

  // ファイルサイズ取得
  const file = new File(result.uri);
  const fileSize = file.exists ? file.size : 0;

  return { savedUri: result.uri, fileSize };
}

async function shareImage(imageUri: string): Promise<void> {
  const isAvailable = await Sharing.isAvailableAsync();
  if (!isAvailable) {
    throw new Error('この端末ではシェア機能が利用できません');
  }

  await Sharing.shareAsync(imageUri, {
    mimeType: imageUri.endsWith('.png') ? 'image/png' : 'image/jpeg',
    dialogTitle: '編集した画像をシェア',
  });
}
```

背景除去の結果を書き出すときは、PNG を選んでください。JPEG は透明を持てないため、切り抜いた背景が黒や白に塗りつぶされます。

保存先に専用のアルバムを作るのは、ユーザーが「このアプリで編集した写真」をあとから探しやすくするためです。カメラロールに直接保存するだけでは、他の写真に埋もれてしまいます。

## フリーミアムモデルでの収益化設計

AI フォトエディタの収益化で最も相性がいいのは「フリーミアム + 従量課金のハイブリッド」です。

金額と回数は、構成を示すための例です。

- **無料ユーザー**: 基本フィルター6種 + 1日3回までの背景除去
- **月額プラン（例: ¥480）**: 全フィルター + 背景除去無制限 + 低解像度スタイル変換
- **年額プラン（例: ¥3,800）**: 全機能 + 高解像度スタイル変換 + 新スタイル先行アクセス

背景除去とスタイル変換は API の呼び出しコストがかかるため、無制限無料にはできません。1日3回の無料枠は、機能の価値を体験してもらいつつ、よく使う人には課金を案内するための出発点です。実際の回数は、1 回あたりの API 原価と、無料ユーザーの利用実績から決めます。

RevenueCat を使えば、サブスクリプション管理・レシート検証・解約率分析を一括で処理できます。Rork のプロンプトで「RevenueCat で月額/年額のサブスクリプションペイウォールを実装して」と指示すれば、基本的な課金フローは自動生成されます。そこに上記の無料枠ロジックを手動で追加するのが現実的なワークフローです。

## 収益化の設計 — 数値は自分のアプリで測る

フォトエディタの収益化でつまずきやすいのは、最初から多機能を有料にしてしまうことです。無料機能の体験が薄いと、有料にしたい動機が生まれません。逆に、無料の範囲で「もう少し触りたい」と感じてもらえれば、ペイウォールが自然な次の一歩になります。

ここでは、他社の平均値のような数字は並べません。出典のない「成功パターンの目安」は、判断を誤らせるからです。代わりに、何を測ってどう使うかを表にします。

この表の指標を揃えたうえで、次の設計を試す価値があります。

- **初回 7 日間だけ AI 機能を広く開放する** — 7 日後に「先週の写真をもう一度この AI で加工したい」と思わせる仕掛けになります。効果は A/B で確かめ、API 原価が許容範囲に収まるかも合わせて見ます
- **広告は「保存時のインタースティシャル」と「フィルター変更時のリワード動画」の 2 系統に絞る** — 購読ユーザーには広告を出さない実装にします。フリーミアムと広告を同居させる場合は、どちらの収益が食われるかを上の表で追います
- **App Tracking Transparency (ATT) のダイアログは、起動直後ではなく、利用の流れが見えてから出す** — ATT が必要になるのは、トラッキングを行う場合です。出すと決めたなら、目的を先に説明する画面を挟み、許可率の変化を記録します

フォトエディタは競争の激しいカテゴリです。運用コスト（API 原価と広告）を回収できる順位帯がどこなのか、自分の数字から逆算しておくと、続けるか絞るかの判断が早くなります。

### 特化するなら、どこに絞るか

汎用のフォトエディタは埋もれやすい領域です。ゼロから設計し直すなら、次のような特化を検討します。

1. **ペット写真特化** — 犬猫の自動マスク + 背景置換 + 品種別フィルター。対象が絞れるぶん、スタイル変換のプロンプトも作り込めます
2. **赤ちゃん写真特化** — ノイズ除去・肌色補正・成長記録の自動整理を組み合わせ、月額制で家族に共有できる設計
3. **フリマ出品特化** — 商品撮影に向けた自動背景除去 + 影付け + 被写体の強調

特化すると、ASO のキーワード競争は緩くなる傾向があります。ただし効果の大きさは分野で違うため、インストール単価は自分のストアで計測して判断してください。

## 次のステップ — このアプリを自分のものにする

ここまでの実装で、フィルター・背景除去・スタイル変換・エクスポートの4機能を備えたフォトエディタが動く状態になっています。ここからの差別化は「どのスタイルを追加するか」と「どのユーザー層に絞るか」で決まります。

たとえばウェディング写真に特化し、背景をチャペルや花畑へ差し替える機能を足せば、招待状アプリという別の市場が見えてきます。ペット写真に特化して犬種判定とスタイル変換を組み合わせる道もあります。

AI の画像処理能力は日々進化しています。重要なのは、APIを差し替え可能な設計にしておくことです。今日 remove.bg を使っていても、来月には条件の違うサービスに乗り換えることになるかもしれません。実際に、remove.bg は 2026 年 12 月 1 日の移行を告知しています。サービス層を抽象化し、APIクライアントを疎結合にしておけば、切り替えコストを最小限に抑えられます。

カメラ機能の基本実装については [Rork Max カメラ・ギャラリー機能の実装](/articles/rork-dev/rork-max-camera-gallery) にまとめています。画像キャッシュがメモリを圧迫し始めたときの計測と上限設計は [壁紙アプリの画像キャッシュが静かに膨らんでメモリで落ちる](/articles/rork-dev/rork-image-cache-memory-bloat-wallpaper-app-field-notes) が、AI 画像生成のクレジット管理は [Rork の AI 画像生成アプリで「クレジットが合わない」を消す](/articles/rork-ai/rork-ai-image-credit-ledger-moderation-field-notes) が、それぞれ直接の続きになります。

縁の 2 ピクセルに手を入れるかどうかで、同じ API の出力がまるで違って見えます。手元の切り抜きを一度、白背景に載せて確かめてみていただければと思います。

まずは今日、手元の写真 10 枚（人物・半透明の被写体・商品）を背景除去 API に通し、結果を白と黒の背景に載せて縁を見比べてください。縁に違和感が出たなら、API を替える前に、上の後処理を試す番です。
