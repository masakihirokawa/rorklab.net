提出ボタンを押す直前に、審査担当者から「このアイコンの権利はどうなっていますか」と尋ねられた場面を想像してみます。AI に何十枚も出してもらった案のうち、どれを採用したのか。どのツールの、どの規約の下で作ったのか。三か月後の自分がその問いに答えられるかどうかは、正直なところ心もとありません。

私は浮世絵壁紙の配信で、元になった古い紙の写真ごとに「どこから来たものか」を書き残しております。修復は自分の手で行っていますが、出どころの記録がなければ、配信してよい理由をあとから説明できません。AI で作った画像も、この点では同じなのだと思います。

お伝えしたいのは、AI が作った画像を使ってよいかを一言で決める方法ではありません。決められない部分は決められないと認めたうえで、**あとから説明できる状態を提出前に作っておく**ことが、個人開発でできる現実的な備えです。この記事は、AI に作らせたアイコンやイラストをストアに出そうとしている方が、提出前の半日で「台帳」「規約」「類似」「寸法」の4点を確かめ終え、審査で聞かれても答えられる記録を手元に残すための手順です。

## 公式が求めているのは「作ったか、使用許諾があるか」です

App Store 審査ガイドラインの 5.2.1 は、保護されたサードパーティの素材（商標・著作物・特許になっているアイデア）を許可なく使わないこと、そしてアプリは知的財産を所有するか使用許諾を受けている人または法人が提出することを求めています。5.2 の冒頭にも、アプリに入れてよいのは自分で作ったか使用許諾を得ているコンテンツだ、という趣旨の一文があります。

ここには、AI 生成かどうかを問う文言はありません。見られているのは、**出どころを説明できるか**です。Google Play 側にも知的財産となりすましに関するポリシーがあり、考え方は同じ方向です（いずれも2026年11月時点の公式ページで確認しています）。

AI 生成画像の権利が国や制度でどう扱われるかは、私には断定できません。ツールごとの利用規約でも書き方が違います。ここでは法的な結論は出さず、次の4点を確認する手順に絞ります。

<tbody>
<tr><td>1. 台帳</td><td>画像1枚ごとの出どころ</td><td>CSV の1行</td><td>1枚あたり数分</td></tr>

## 出どころ別に、どこまで記録すればよいかを先に決めます

画像の出どころは、生成だけではありません。自作・購入素材・無料素材が混ざるのが普通です。出どころごとに「説明に必要なもの」が違うので、先に一覧にしておきます。

<table>
<thead><tr><th>出どころ</th><th>説明に必要なもの</th><th>アイコンに使うときの判断</th></tr></thead>
<tbody>
<tr><td>AI で生成</td><td>ツール名・プラン・確認日つきの規約・プロンプトの保存場所</td><td>規約で商用利用が読み取れ、類似の確認を残せたときだけ</td></tr>
<tr><td>自分で描いた・撮った</td><td>元データ（レイヤー付きの制作ファイルや撮影データ）の保存場所</td><td>もっとも説明しやすいので、顔になる素材は優先して使います</td></tr>
<tr><td>購入した素材</td><td>購入履歴とライセンスの種類（標準・拡張など）</td><td>ロゴや商標としての利用を禁じる条項がないかを見てから</td></tr>
<tr><td>無料素材・パブリックドメイン</td><td>配布元の URL・ライセンス名・クレジット表記の要否</td><td>配布元が消えても説明できるよう、ページの写しを残します</td></tr>
</tbody>
</table>

判断の基準を一文にすると、**アイコンのようにアプリの顔になる画像は、出どころをもっとも短く説明できるものから選ぶ**、です。説明に三行かかる画像は、画面の中の挿絵に回したほうが安心です。

## 確認1：画像ごとに「台帳」を1行つくります

最初にやることは、使うつもりの画像を1枚ずつ表に書き出すことです。専用のツールは要りません。プロジェクトの直下に、CSV を1つ置きます。

<table>
<thead><tr><th>列</th><th>書くこと</th><th>例</th></tr></thead>
<tbody>
<tr><td>file</td><td>プロジェクトからの相対パス</td><td>assets/images/icon.png</td></tr>
<tr><td>source</td><td>生成・自作・購入・無料素材のどれか</td><td>生成</td></tr>
<tr><td>tool</td><td>使ったツール名と、プロンプトの保存場所</td><td>画像生成ツールA（プロンプトは prompts/icon.txt）</td></tr>
<tr><td>date</td><td>作った日（YYYY-MM-DD）</td><td>2026-10-02</td></tr>
<tr><td>license_note</td><td>規約のどこを根拠にしたか</td><td>商用利用の条項（2026-10-02 保存の PDF）</td></tr>
<tr><td>similarity_check</td><td>類似を調べた日と調べ方</td><td>画像検索・J-PlatPat 2026-10-03 該当なし</td></tr>
</tbody>
</table>

最初のうち、私は「採用が決まってからまとめて書こう」と考えて、候補の画像を何枚も同じフォルダに溜めておりました。結果は芳しくありませんでした。書き出し直した版と最初の版が混ざり、どれがどのプロンプトから来たのかを辿れなくなったのです。いまは、画像を採用した**その場で1行足す**ことを決まりにしています。

## 確認2：使ったツールの規約を、日付つきで残します

台帳の license_note に「確認済み」とだけ書いても、規約は書き換わることがあります。確認した日と、読んだ条項の見出しを一緒に残します。可能であれば、規約ページを PDF か保存したテキストにして、台帳と同じ場所に置いておきます。

見る点は次の三つです。

- 生成した画像を商用アプリに使ってよいかどうか
- 無料プランと有料プランで、使える範囲に違いがあるかどうか
- 生成物の権利が、利用者とサービス側のどちらにあると書かれているか

どれも読み取れないときは、そのツールで作った画像を**アイコンのような顔になる素材には使わない**、という判断も十分に成り立ちます。プランを途中で変えた場合は、生成した日がどちらのプランの期間だったかも台帳に書いておくと、あとで迷いません。

## 確認3：既存の作品や商標に似ていないかを見ます

生成した画像が、既存のキャラクターやロゴに近いことはありえます。審査ガイドライン 4.1 の Copycats の項目は、人気アプリの名前や見た目を少し変えただけのものを出さないよう求めています。

私が行っているのは、地味な作業です。採用候補のアイコンを画像検索にかけ、似たものが上位に出ないかを見ます。アプリ名は、ストア内の検索と、特許庁の商標検索（J-PlatPat）の両方で調べます。検索に何も出なければ安全だという話ではなく、**調べた記録を台帳の similarity_check に残す**ことに意味があります。

もう一つ、プロンプトに既存のブランド名・作品名・作家名を入れて作った画像は、似ているかどうかを調べる前に候補から外しています。似せようとして作ったものを、あとから「似ていません」と説明するのは難しいからです。

## 確認4：提出サイズの条件を、スクリプトで機械的に見ます

ここは判断ではなく、機械が得意な確認です。公式の記述を整理すると、次のとおりです（2026年11月時点・各公式ページで確認）。

<table>
<thead><tr><th>対象</th><th>条件</th><th>出典</th></tr></thead>
<tbody>
<tr><td>iOS のアイコン（元画像）</td><td>正方形。1024x1024 が目安。角丸や透明なピクセルを含めない</td><td>Expo 公式「App icons」</td></tr>
<tr><td>iOS 26 以降の新しい形式</td><td>Icon Composer で作った .icon を ios.icon に指定できます（Expo SDK 54 から）</td><td>Expo SDK 54 の変更履歴</td></tr>
<tr><td>Google Play のアイコン</td><td>32 ビット PNG（アルファ付き）、512x512px、1024KB 以下。角丸や影は Play 側が付けるので、四角いまま渡します</td><td>Play Console ヘルプ・Google Play アイコンのデザイン仕様</td></tr>
<tr><td>Google Play のフィーチャー グラフィック</td><td>JPEG または 24 ビット PNG（アルファなし）、1024x500px</td><td>Play Console ヘルプ「プレビュー アセットを追加する」</td></tr>
</tbody>
</table>

見た目では気づきにくい透明ピクセルや、透けていないのに残っている alpha チャンネルは、書き出しや加工の途中で混ざります。AI ツールが出した画像は透過 PNG で渡されることも多く、そのまま差し込むと引っかかりやすい場所です。台帳と合わせて確認できるように、次のスクリプトを用意しました。

```python
#!/usr/bin/env python3
"""画像素材の出どころ台帳と、ストア提出サイズの確認（v2）。

使い方:
  python3 asset_ledger_check.py <プロジェクトのルート> [台帳CSV]

台帳CSV（既定: assets-ledger.csv）の列:
  file,source,tool,date,license_note,similarity_check
  file はプロジェクトのルートからの相対パス。date は YYYY-MM-DD。
"""
import csv
import re
import sys
from pathlib import Path
from PIL import Image  # pip install pillow

SKIP_DIRS = {"node_modules", ".git", "ios", "android", ".expo", "dist"}
EXTS = {".png", ".jpg", ".jpeg", ".webp"}
REQUIRED = ("source", "tool", "date", "license_note", "similarity_check")
DATE_RE = re.compile(r"^\d{4}-\d{2}-\d{2}$")


def has_transparency(img: Image.Image) -> bool:
    if img.mode in ("RGBA", "LA", "PA"):
        return img.getchannel("A").getextrema()[0] < 255
    return "transparency" in img.info


def has_alpha_channel(img: Image.Image) -> bool:
    # 全ピクセルが不透明でも、チャンネルがあるだけで弾かれる場面がある
    return img.mode in ("RGBA", "LA", "PA") or "transparency" in img.info


def size_notes(rel: str, name: str, w: int, h: int, kb: float, img_fmt: str, alpha_ch: bool, alpha_px: bool):
    notes = []
    in_icon_pkg = any(p.endswith(".icon") for p in rel.split("/")[:-1])
    if in_icon_pkg:
        return notes  # Icon Composer の .icon の中のレイヤーは寸法を問わない
    if "feature" in name:
        if (w, h) != (1024, 500):
            notes.append(f"フィーチャー グラフィックは 1024x500 です（{w}x{h}）")
        if alpha_ch:
            notes.append("フィーチャー グラフィックに alpha があります（JPEG か 24 ビット PNG に）")
        return notes
    if "play" in name and "icon" in name:
        if (w, h) != (512, 512):
            notes.append(f"Play 用アイコンは 512x512 です（{w}x{h}）")
        if img_fmt != "PNG":
            notes.append(f"Play 用アイコンは PNG です（{img_fmt}）")
        if kb > 1024:
            notes.append(f"Play 用アイコンが 1024KB を超えています（{kb:.0f}KB）")
        return notes
    if "icon" in name and not any(k in name for k in ("splash", "adaptive", "notification", "monochrome")):
        if w != h:
            notes.append(f"アイコンが正方形ではありません（{w}x{h}）")
        elif w != 1024:
            notes.append(f"1024x1024 ではありません（{w}x{h}）")
        if alpha_px:
            notes.append("透明なピクセルを含んでいます（iOS のアイコンは不透明に）")
        elif alpha_ch:
            notes.append("透けて見えませんが alpha チャンネルが残っています（ITMS-90717 の原因になります）")
    return notes


def main() -> int:
    if len(sys.argv) < 2:
        print(__doc__)
        return 2
    root = Path(sys.argv[1]).resolve()
    ledger_path = Path(sys.argv[2]) if len(sys.argv) > 2 else root / "assets-ledger.csv"

    ledger = {}
    if ledger_path.exists():
        with ledger_path.open(encoding="utf-8", newline="") as f:
            for row in csv.DictReader(f):
                ledger[(row.get("file") or "").strip()] = row

    problems = 0
    for path in sorted(root.rglob("*")):
        if not path.is_file() or path.suffix.lower() not in EXTS:
            continue
        if SKIP_DIRS & set(path.relative_to(root).parts):
            continue
        rel = path.relative_to(root).as_posix()
        with Image.open(path) as img:
            w, h = img.size
            fmt = img.format or "?"
            alpha_ch = has_alpha_channel(img)
            alpha_px = has_transparency(img)
        kb = path.stat().st_size / 1024
        notes = []

        row = ledger.get(rel)
        if row is None:
            notes.append("台帳に行がありません")
        else:
            for col in REQUIRED:
                if not (row.get(col) or "").strip():
                    notes.append(f"台帳の {col} が空です")
            d = (row.get("date") or "").strip()
            if d and not DATE_RE.match(d):
                notes.append(f"台帳の date が YYYY-MM-DD ではありません（{d}）")

        notes += size_notes(rel, path.name.lower(), w, h, kb, fmt, alpha_ch, alpha_px)

        status = "要確認" if notes else "OK"
        problems += bool(notes)
        print(f"[{status}] {rel}  {w}x{h}  {kb:.0f}KB  {fmt}  alpha={'有' if alpha_ch else '無'}")
        for n in notes:
            print(f"        - {n}")

    for rel in sorted(ledger):
        if rel and not (root / rel).exists():
            print(f"[要確認] {rel}  台帳にあるがファイルが見つかりません")
            problems += 1

    print(f"\n要確認: {problems} 件")
    return 1 if problems else 0


if __name__ == "__main__":
    sys.exit(main())
```

ファイル名で役割を見分けています。`icon` を含むものは iOS 向けの元アイコン、`play` と `icon` の両方を含むものは Play 用の 512px 版、`feature` を含むものはフィーチャー グラフィックとして扱います。スプラッシュ・アダプティブ・通知用の画像と、Icon Composer の `.icon` の中にあるレイヤーは寸法の確認から外しています（台帳の確認は行います）。

手元の検証用フォルダで動かした結果です。環境は Linux 上の Python 3.10.12 と Pillow 12.3.0 です（macOS でも同じ手順で動く書き方にしてあります）。四隅の1ピクセルだけを透明にした `icon-rounded.png`、全ピクセルが不透明なのに RGBA で保存した `icon-rgba-opaque.png`、1000x1024 の `store-icon.png`、日付の書式を崩した行などを、意図的に混ぜてあります。

```text

[要確認] assets/images/feature-graphic.png  1024x500  3KB  PNG  alpha=有
        - フィーチャー グラフィックに alpha があります（JPEG か 24 ビット PNG に）
[要確認] assets/images/icon-rgba-opaque.png  1024x1024  6KB  PNG  alpha=有
        - 透けて見えませんが alpha チャンネルが残っています（ITMS-90717 の原因になります）
[要確認] assets/images/icon-rounded.png  1024x1024  6KB  PNG  alpha=有
        - 台帳に行がありません
        - 透明なピクセルを含んでいます（iOS のアイコンは不透明に）
[OK] assets/images/icon.png  1024x1024  5KB  PNG  alpha=無
[要確認] assets/images/play-icon.png  512x512  2KB  PNG  alpha=有
        - 台帳の similarity_check が空です
        - 台帳の date が YYYY-MM-DD ではありません（2026/10/05）
[要確認] assets/images/splash-icon.png  400x400  1KB  PNG  alpha=有
        - 台帳に行がありません
[要確認] assets/images/store-icon.png  1000x1024  5KB  PNG  alpha=無
        - 台帳に行がありません
        - アイコンが正方形ではありません（1000x1024）
[要確認] assets/images/old.png  台帳にあるがファイルが見つかりません

要確認: 7 件
```

`icon-rounded.png` は、左上のたった1ピクセルを透明にしただけのファイルです。`icon-rgba-opaque.png` に至っては、画面で見ても透明な部分はどこにもありません。それでも App Store Connect にアップロードすると ITMS-90717 で止まることがあります。目視ではなく機械に任せる理由が、この2行に詰まっています。終了コードが 1 になるので、提出前のチェックに組み込むこともできます。

## よくある誤解を3つ

**「AI で作った画像はストアに出せない」**。2026年11月時点で私が読んだ範囲の App Store 審査ガイドラインと Play のポリシーには、アプリの素材が AI 生成であることを理由に一律で禁じる条文は見当たりません。問われるのは、権利を持っているか、許諾を受けているかです。

**「AI 生成だと申告しないとリジェクトされる」**。これも、アイコンやスクリーンショットについて申告を求める項目は、私が確認した範囲では見つかりませんでした。Google Play の AI 生成コンテンツに関するポリシーは、アプリの機能として AI で生成したものを利用者に見せる場合が主な対象です。素材の作り方とは別の話なので、混同しないようにしています。

**「角丸を付けた画像を渡したほうが見栄えがよい」**。iOS も Google Play も、角丸やマスクは配信する側が付けます。Google Play のアイコンのデザイン仕様は、四角いアセットを渡すよう求めています。自分で付けた角丸は、透明ピクセルと二重の角という2つの問題を連れてきます。

## この方法が言えないこと

この手順は、権利の問題が起きないことを保証するものではありません。台帳はあくまで、**何を根拠に採用したかを後から説明するための記録**です。規約の読み方に迷う場合や、収益の大きいアプリでは、専門家に相談する価値があります。

また、スクリプトが見ているのは画像の寸法・形式・透明度と、台帳の空欄だけです。画像が既存の作品に似ているかどうかは見ていません——そこだけは、人の目と記録で補うしかないのです。

## 次に詰まるのは、差し替えたアイコンが反映されない場面です

台帳を整えた結果としてアイコンを差し替えると、次に当たりやすいのが「直したはずなのに古いアイコンのまま」「alpha を外したのにまた弾かれる」という場面です。多くは、ビルドに古い画像が残っているか、書き出しの設定が元に戻っているかのどちらかです。

alpha チャンネルの見分け方と外し方は、[見た目は不透明なのに「アイコンに alpha チャンネルがあります」と弾かれる場合の確かめ方](/articles/rork-business/app-store-icon-alpha-channel-itms-90717-opaque-looking-png-check-before-upload)にまとめてあります。審査で止まったときの返信の組み立ては、[App Store でリジェクトされた時の対処辞典](/articles/rork-business/rork-app-store-rejection-survival-playbook)が参考になるはずです。画像以外の同梱物も同じ発想で棚卸ししたい方は、[ライセンス表示に載せる依存は、lockfile の dev/prod では決まりません](/articles/rork-dev/rork-oss-license-inventory-shipped-artifact-boundary)もあわせてご覧ください。

## 次に1つだけやるなら

提出予定のアプリで、いま使っている画像のうち**アイコンの1枚**だけ、台帳に1行書いてみていただければと思います。出どころを書こうとして手が止まるなら、そこが提出前に確認すべき場所です。

**画像は、使ってよいかを悩む前に、説明できるかを整えておく。** この順番だけは、どれほど提出を急ぐ日でも入れ替えないようにしています。
