夜に壁紙アプリの設定画面を作り直していて、生成が終わったプレビューを実機で開いたところ、画面がただ真っ黒のまま動かなかったことがあります。エラーの赤い画面も出ません。何を直せばいいのか、手がかりがひとつもない状態でした。

最初にお伝えしたいのは、真っ黒の画面は「壊れている」という一種類の症状ではない、ということです。原因の置き場所が少なくとも3つあり、それぞれ直す相手が違います。私は最初のうち、どこが悪いのかを見ないまま「真っ黒になりました、直してください」と同じ依頼を重ねてしまいました。結果は芳しくありませんでした。動いていた一覧画面まで書き換わり、どこから壊れたのかも分からなくなったのです。

ここには、その遠回りを繰り返さないための順番を書き残します。結論は次の三つです。

- 止まっている場所は「端末とアプリ」「画面の描画」「ネイティブ」の3か所のどれか
- 黄色い帯を一本差し込むだけで、前半と後半のどちらで止まっているかが分かること
- 頼み直すときは、止まっている段階と、確かめたことを3行で添えること

料金・画面名・エラー文言は、2026年11月時点で Expo と Rork の公式ドキュメントを確認して書いています。

## 真っ黒の画面は、3か所のどこかで止まっています

プレビューが映るまでには、大きく分けて三つの段階があります。

<table>
<thead><tr><th>段階</th><th>何が起きているか</th><th>最初に見る場所</th><th>主な直し方</th></tr></thead>
<tbody>
<tr><td>1. 端末とアプリ側</td><td>Expo Go などがプロジェクトを開けていない</td><td>Expo Go に出ている文言</td><td>ログイン・SDK の版・再読み込みを確かめる</td></tr>
<tr><td>2. 画面の描画</td><td>アプリは動いているが、何も見えない状態になっている</td><td>Rork の Logs パネル</td><td>表示条件・色・高さ・スプラッシュを確かめる</td></tr>
<tr><td>3. ネイティブ側</td><td>アプリそのものが起動直後に落ちている</td><td>端末のログ（adb logcat／Console）</td><td>落ちた瞬間の数行を読み、そのまま依頼に貼る</td></tr>
</tbody>
</table>

上から順に確かめるのが近道です。1 は数十秒で済み、3 はいちばん手間がかかります。手間の少ない順に潰していけば、AI に頼む内容も自然と具体的になります。

## 1. 端末とアプリ側を先に疑います

QR コードを読んでも何も映らない場合は、生成されたコードより前の段階を疑います。ここでの答えは、たいてい Expo Go の画面に文字で出ています。

ひとつ目はログインです。Expo の changelog（2026年9月3日）によれば、iOS の最新の Expo Go では、ターミナルの Expo CLI と Expo Go アプリの両方に、同じアカウントでログインしていないと開発中のアプリを開けなくなりました。2026年11月時点の公式の記載では、この要件は iOS の実機だけで、Android 版はいずれ広げる予定、シミュレーターと development build には当てはまりません。Android で真っ黒なら、ログインより先にほかの原因を疑う方が早いのです。順番は別の記事でも整理しています。

- [Expo Go が開かないときに先に確かめる2つのログイン](/articles/rork-basics/expo-go-login-both-terminal-and-app-preview-not-opening)
- [Rork Companion のプレビューが動かないときの確認](/articles/rork-basics/rork-companion-preview-not-working-fix)

ふたつ目は SDK の版です。Expo Go は、一つのビルドに一つの SDK だけを積んでいます。プロジェクトの <code>package.json</code> にある <code>expo</code> の版と、端末の Expo Go が対応する版が食い違うと、「Project is incompatible with this version of Expo Go」と表示されます。ストアの Expo Go は新しい SDK に追いつくまで時間がかかることがあり、その場合は development build に切り替えるのが公式の案内です。

みっつ目に見たいのは「アプリを完全に閉じてから開き直すと変わるか」です。変わるなら、コードではなく端末側の状態の問題でした。ここで AI に修正を頼むと、直す必要のないコードまで書き換わってしまいます。

## 2. 画面の描画を疑います

Expo の公式ドキュメント（Runtime issues）では、スタックトレースで原因が掴めないときの進め方として「動いていた版のコードに戻し、変更を一つずつ当て直す」手順が示されています。真っ黒でエラーも出ないときは、この方法がよく効きます。

私自身、個人開発のアプリでも同じ型の失敗を何度か踏みました。多いのは次の四つです。

- 背景も文字も黒になっている状態（ダークテーマの指定が、片方にしか効いていません）
- データの読み込み前に `null` を返したまま、読み込みが終わらず何も描かれない状態
- 親の View に高さがなく、中身が高さ 0 で潰れている状態
- スプラッシュ画面を閉じる処理が呼ばれず、最初の画面に切り替わらない状態

### 黄色い帯を一本差し込みます

見分けるには、診断用の部品を一時的に差し込むのがいちばん早いです。次のコードは、画面の最上位に明るい背景と文字を置くだけのものです。

```tsx
import { View, Text } from "react-native";

// 診断用: 黒の背景に埋もれていないかを確かめる（確認が済んだら外します）
export default function DebugBanner({ label }: { label: string }) {
  return (
    <View style={{ backgroundColor: "#ffd54f", padding: 12, zIndex: 9999 }}>
      <Text style={{ color: "#000", fontWeight: "700" }}>{label}</Text>
    </View>
  );
}
```

これを画面の先頭に置いて、黄色い帯が見えるかどうかで分かれます。見えるなら、アプリは動いていて、その下の描画が空になっています。見えないなら、描画より手前（端末側かネイティブ側）で止まっている可能性が高くなります。

帯の `label` に、いま持っている状態を流し込むと、さらに絞り込めます。たとえば帯に一覧の件数を出し、まだ届いていなければ「未取得」と表示するようにしておけば、「データが来ていない」のか「来ているのに描かれていない」のかが、その場で分かります。

もう一つ、黄色い帯が見えないからといって、すぐ「描画より手前」と決めつけないでください。画面全体を覆う `position: "absolute"` の View が帯の上に重なっているだけ、ということもあるのです。上のコードで `zIndex` を大きめにしているのはそのためで、それでも見えないときに初めて、3 の段階へ進みます。

### スプラッシュが閉じない場合の Before / After

四つ目は見落としやすいので、コードで補足します。`expo-splash-screen` の `preventAutoHideAsync()` を呼んだまま `hideAsync()` に到達しない場合、アプリは動いていても画面はスプラッシュのまま止まります。スプラッシュの背景を黒にしていると、利用者からは「真っ黒で動かない」と見えるのです。

Before は、読み込みが例外を投げると準備完了の印が立たない書き方です。

```tsx
import { useEffect, useState } from "react";
import * as SplashScreen from "expo-splash-screen";

SplashScreen.preventAutoHideAsync();

export default function App() {
  const [ready, setReady] = useState(false);

  useEffect(() => {
    (async () => {
      await loadFontsAndSettings(); // ここで例外が出ると、下の行に届きません
      setReady(true);
    })();
  }, []);

  useEffect(() => {
    if (ready) SplashScreen.hideAsync();
  }, [ready]);

  if (!ready) return null;
  return <MainScreen />;
}
```

After は、成功しても失敗しても必ず準備完了にして、失敗したことは画面とログに残す書き方です。Expo の公式ドキュメントの例も、`try / catch / finally` の `finally` で準備完了にしています。

```tsx
import { useEffect, useState } from "react";
import * as SplashScreen from "expo-splash-screen";

SplashScreen.preventAutoHideAsync();

export default function App() {
  const [ready, setReady] = useState(false);
  const [loadError, setLoadError] = useState<string | null>(null);

  useEffect(() => {
    (async () => {
      try {
        await loadFontsAndSettings();
      } catch (e) {
        console.error("初期読み込みに失敗:", e); // Rork の Logs パネルに [error] で出ます
        setLoadError(String(e));
      } finally {
        setReady(true); // 成否にかかわらずスプラッシュを閉じる
      }
    })();
  }, []);

  useEffect(() => {
    if (ready) SplashScreen.hideAsync();
  }, [ready]);

  if (!ready) return null;
  if (loadError) return <DebugBanner label={`読み込み失敗: ${loadError}`} />;
  return <MainScreen />;
}
```

`loadFontsAndSettings` と `MainScreen` は、お手元のプロジェクトにある読み込み処理と最初の画面に置き換えてください。「描画の問題だ」と思い込んでコードの見た目ばかり直していた夜が、私にもありました。いま思えば、読み込み処理の `try / finally` を確かめるのが先でした。

### Rork の中で読めるログを先に開きます

描画の段階で止まっているなら、端末のログまで行かなくても、Rork の画面の中で手がかりが見つかることがあります。Rork のドキュメントによれば、**More → Code** を開くと、ファイルの一覧の下に **Logs** というパネルがあり、プレビューで動いたアプリが出力した内容が `[log]` `[warn]` `[error]` などの区分つきで流れます。

上の After のように `console.error` を一行入れておけば、ここに理由が出ます。エラーの表示がプレビューに出ている場合は、その上の **Fix with Rork** から直してもらうのがいちばん早い、とも案内されています。

## 3. ネイティブ側で落ちていないかを確かめます

帯も見えず、再読み込みでも変わらないときは、アプリが起動直後に落ちている可能性があります。この場合、JavaScript の側には何も残らないことが多く、Logs パネルも静かなままです。Expo の公式ドキュメントでも、ネイティブのクラッシュは端末のログを読むことが前提になっています。

Android では、USB でつないだ端末のログを `adb logcat` で流します。全部を読む必要はありません。私は次の三行で、落ちた瞬間だけを拾うようにしております。

```bash
# 1) 古いログを消してから、アプリを開き直す
adb logcat -c
# 2) エラー以上の行だけを流す
adb logcat '*:E'
# 3) 落ちた行と JavaScript 側の出力に絞る場合
adb logcat | grep -E "FATAL EXCEPTION|AndroidRuntime|ReactNativeJS"
```

iOS では、Mac の Console アプリで左の一覧から端末を選び、ストリーミングを開始してから、アプリを開き直します。検索欄にアプリ名を入れると、関係のない行がかなり減ります。

Windows だけで作業している方は、iOS の側は無理に追わなくて構いません。落ちたことが分かれば、次の「AI にどう伝えるか」に進めます。

ログを開くのは気が重い作業かもしれません。私も最初は、黒い文字の洪水を前に手が止まりました。ただ、読むのは全体ではなく、落ちた瞬間の前後の数行です。`FATAL EXCEPTION` や `Error` の行を一つ見つけて、そのまま依頼文に貼れば足ります。

## よくある誤解を三つだけ正しておきます

**誤解1:「真っ黒なのは、AI が書いたコードが壊れているから」** 1 の段階で見たとおり、iOS の Expo Go のログインや SDK の版の食い違いでも、プレビューは開きません。コードに手を入れる前に、Expo Go に出ている文言を一度読むだけで、無駄な依頼を一往復減らせます。

**誤解2:「前の版に戻すと、クレジットが減ったり作業が全部消えたりする」** Rork のドキュメントでは、各回答がプロジェクト全体の版として保存され、戻ること自体にはクレジットがかからないと書かれています（2026年11月時点）。ただし、二つ以上前に戻す **Revert** は取り消せず、それより後の版は履歴の先頭から外れます。直前の一回だけを戻したいなら **Undo** で足ります。

**誤解3:「同じ依頼を繰り返せば、いずれ直る」** Rork の FAQ では、エラーが繰り返すときは、Rork に Web でエラーを調べさせる、別の AI モデルに切り替える、動いていた版に戻して別のやり方で実装し直す、の三つが案内されています。同じ文面を送り続ける選択肢は、そこにはありません。

## Undo・Revert・Edit message の使い分け

戻し方は三つあり、どれを選ぶかで失うものが変わります。画面名は2026年11月時点の Rork のドキュメントに合わせています（FAQ では Restore と呼ばれている機能です）。

<table>
<thead><tr><th>操作</th><th>どこにあるか</th><th>何が起きるか</th><th>選ぶとき</th></tr></thead>
<tbody>
<tr><td>Undo</td><td>最後の回答の下</td><td>直前の変更だけを戻し、そのやり取りを消す。確認の画面は出ない</td><td>最後の一回で真っ黒になった</td></tr>
<tr><td>Revert</td><td>それより前の回答の下</td><td>その回答の直後の状態に戻す。後の版は履歴の先頭から外れ、取り消せない</td><td>どこから壊れたか分かっていて、二つ以上前に戻りたい</td></tr>
<tr><td>Edit message</td><td>自分の過去の発言にカーソルを合わせる</td><td>その発言の直前に戻し、書き直した依頼で答え直させる</td><td>依頼の書き方が悪かったと分かっている</td></tr>
</tbody>
</table>

判断の基準は一つで、**「最後の一回のせいだと言い切れるなら Undo、言い切れないなら Review changes で差分を見てから Revert」** です。Review changes は、各回答の **⋯** メニューから開け、その回答で変わったファイルを前の版と並べて見られます。真っ黒になった回答で、画面の外側の部品（レイアウトやテーマ）が変わっていないかを確かめてから戻すと、戻しすぎを防げます。

## 切り分けたあとに、AI へ伝える内容を変えます

伝え方は、止まっていた段階ごとに変えます。

- 黄色い帯が見えた場合: 「画面は動いているが、一覧の部分だけ何も描かれない。読み込み前に null を返していないか確認して」
- スプラッシュのまま止まる場合: 「初期読み込みが例外を投げても hideAsync が呼ばれるよう、try / finally で包んで」
- 帯も見えず、ログに FATAL が出た場合: その行を貼って「この例外で起動直後に落ちている。原因の候補を三つ挙げて、いちばん小さい変更から試して」
- 何も分からない場合: Undo か Revert で動いていた版へ戻し、変更を一つずつ頼み直します

「真っ黒です」だけでは、AI も推測で直すしかありません。どの段階で止まっているかを一文添えるだけで、返ってくる修正は絞り込まれます。

## 依頼に添える3行のメモ

切り分けた結果は、そのまま依頼文の先頭に置けます。私が使っているのは次の形です。

```text
止まっている段階: 2（画面の描画）
確かめたこと: 黄色い帯は見える／items: 未取得 と出る／アプリを閉じて開き直しても同じ
気になっている箇所: 一覧画面で、データ読み込み前に何も返していない可能性
```

この3行があると、返ってくる修正が「全体を作り直す」方向に広がりにくくなります。逆に、止まっている段階が分からないまま依頼を重ねると、動いていた部分まで書き換わることがあります。冒頭の夜の私が、まさにそうでした。

**頼み直す前に、止まっている段階を一文で言えるようにしておく。** この線引きだけは、疲れている夜ほど守るようにしています。

## 次に詰まりやすいところ

プレビューが映るようになったあとに当たりやすいのは、「開発中は動くのに、リリース用のビルドだけ白い画面になる」という場面です。審査で Guideline 2.1 を返されたときの確かめ方は [App Review で「白い画面」と言われたときに Expo のリリースビルドで疑う3か所](/articles/app-dev/app-review-guideline-2-1-blank-screen-expo-release-build-checklist) にまとめています。

ログイン機能を足した直後に、起動のたびに一瞬ログイン画面がちらつくようになったら、[起動のたびに一瞬ログイン画面が出る expo-router アプリを三状態で組み直す](/articles/app-dev/expo-router-protected-routes-unknown-state-sign-in-flash-fix) が近い話です。Android で落ちているのに利用者からは「固まる」と見えるケースは、[Android のクラッシュが白い画面のまま残るとき](/articles/app-dev/expo-updates-android-crash-blank-activity-looks-frozen) で扱っています。

まずは、次に真っ黒の画面に出会ったとき、依頼を送る前に黄色い帯を一つ差し込んでみてください。見えるか見えないかで、次に開くべき画面が決まります。
