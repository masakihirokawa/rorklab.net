設定画面の文言を一行だけ直してほしい、と頼んだ夜のことです。返ってきた答えを開くと、文言は確かに直っていました。ところが一覧画面に戻ると、並び順の見出しが消えています。

「見出しが消えています。戻してください」と頼みました。次の答えでは見出しが戻り、今度は設定画面の余白が崩れていました。三回目の依頼を打ち込む前に、胃のあたりが少し重くなったのを覚えております。

直してもらうたびに、どこかが動く。そう感じたとき、先に確かめていただきたいのは「どう直してもらうか」ではなく、**「どこへ戻るか」**です。Rork には戻る手段が三つあり、しかも戻ること自体にクレジットはかかりません。

## 最初にお伝えしたいのは、戻るのは無料だということです

Rork の公式ドキュメントには、各回の答えがプロジェクト全体の保存された一つの版になっている、と書かれています。エージェントの一回の答えが終わるたびに、ファイルとチャット履歴が一緒に保存される仕組みです。ですから、チャットと中身がずれることはありません。

そして Undo も Revert も、**戻る操作そのものにクレジットはかかりません**。かかるのは、何かの仕事をするメッセージだけです。

この二点を知っているだけで、迷い方が変わります。三回目の依頼を重ねる前に、無料で一歩引くことができるのです。

## 戻り方は三つあります

違いを先に表で並べます。内容は、公式ドキュメントの「Undo a change and go back a version」に書かれている挙動を、私が読み直して整理したものです。

<table>
  <thead>
    <tr><th>戻り方</th><th>どこにあるか</th><th>戻る先</th><th>チャットはどうなるか</th><th>やり直せるか</th></tr>
  </thead>
  <tbody>
    <tr><td>Undo</td><td>いちばん新しい答えの下</td><td>直前の版</td><td>その一往復だけが消える</td><td>確認なしで戻る。直前の版に戻るだけなので失うものは小さい</td></tr>
    <tr><td>Revert</td><td>それより前のすべての答えの下</td><td>その答えの直後の版</td><td>その答えまでが残り、後ろはすべて消える</td><td>できない。確認ダイアログが出る</td></tr>
    <tr><td>メッセージ編集（Edit message）</td><td>自分の過去のメッセージにカーソルを重ねると出る</td><td>そのメッセージを送る前の版</td><td>後続が消え、書き直した文面への答えが返る</td><td>戻して再試行を一度に行う操作</td></tr>
  </tbody>
</table>

見落としやすいのは、Revert が「取り消せない」と明記されている点です。後ろの版は履歴の先頭ではなくなるため、直前の一回だけを戻したいなら、Revert ではなく Undo を選ぶのが安全です。

## どれで戻るかを、三つの問いで決めます

私は戻る前に、次の三つを順番に自分へ聞くようにしております。

一つ目は、「悪くなったのは直前の一回だけか」です。はいなら Undo です。さきほどの設定画面の例では、二回目の答えで余白が崩れたので、二回目だけを Undo すれば、見出しが戻った状態の版に着地します。

二つ目は、「答えは悪くなく、頼み方が悪かったのではないか」です。はいなら、自分のメッセージを編集して送り直します。公式ドキュメントは、これを「会話が横にそれたときのいちばんきれいな出口」と位置づけています。Rork は、そのメッセージを送る前の状態までプロジェクトを戻し、後続を落としてから、新しい文面に答えてくれます。

三つ目は、「数回前の答えのほうが明らかに良かったか」です。はいなら Revert です。確認ダイアログが出ますので、そこで一度手を止めます。戻した先より後ろの作業はすべて失われますから、本当に必要なのは Undo の一回分ではないかを、もう一度だけ見直します。

**戻る一手は無料、進む一手は有料です。先に戻ってから頼み直します。** この順番を、私は個人開発の作業のなかで守るようにしています。

## 戻る前に、何が変わったかを見ます

戻る先を決めかねるときは、答えの下の「⋯」メニューから「Review changes」を開きます。その答えが触ったすべてのファイルが、一つ前の版との差分として全画面で表示されます。

同じメニューには、その答えを動かしたモデルと、使ったクレジット、エージェントが抱えていた文脈の大きさも出ます。「この一回で何が変わり、いくらかかったか」が、戻るかどうかの判断材料になります。

実行時に何か起きているのに画面にエラーが出ないときは、「More → Code」の下にある Logs パネルを見ます。アプリがプレビューで出力した内容が、`[log]` や `[error]` といったレベルつきで並びます。

## 戻れないものが三つあります

戻る前に、これだけは知っておいてください。

一つ目は、公開したものです。Revert は公開済みの Web アプリや提出済みのビルドを取り消しません。再び公開するまで、公開側は元のままです。

二つ目は、環境変数と秘密の値です。Secrets は版の一部ではありませんので、Revert のあとに「More → Secrets」を開いて、必要な値が残っているかを見ておきます。

三つ目は、手で編集したコードです。有料プランではコードを直接編集できますが、公式ドキュメントはこれを「独自の取り消しを持たない唯一の部分」と呼び、Save したあとは編集がプロジェクトの一部になると書いています。可能なら、手で直さずにチャットで頼み、版として残しておくほうが安全です。

エージェントが作業している最中は Revert できません。止めたいときは、送信ボタンが変わる停止ボタンを押します。途中までの作業は保存され、終わっていないビルドには課金されません。長い回が間違った方向へ進んでいると気づいたら、早めに止めるほうが安上がりです。

## 戻ったあとの頼み方を、短く決めておきます

戻っただけでは、同じ依頼を同じ形で送れば、同じ場所に着地するかもしれません。公式の「How to get out of an error loop」には、本物の入力で地面を作る、範囲を絞る、直したと言われたら検証させる、という方針が書かれています。

私はこれを、次のような短い依頼文に落としております。

```
直前の状態に戻しました。いま直したいのは設定画面の文言だけです。
変更してよいのは SettingsScreen のファイルだけで、他の画面と
ライブラリには触らないでください。
直したあとで、変更したファイルと、その行を引用して教えてください。
```

一文目で現在地を伝え、二文目で触ってよい範囲を決め、三文目で検証を求める形です。「直したと言われたのに何も変わっていない」状況を避けたい、という動機で組んでいます。

エラーのダイアログが出たときは、「Fix with Rork」のボタンが、既定では押した瞬間に修正の依頼を送ります。Account settings の Preferences にある「Auto-send error fixes」をオフにすると、送る前に依頼文を読めます。クレジットが気になる方は、そこを一度見ておくと安心です。

クレジットそのものの見方は、[思ったより早く残高が減る前に、Build クレジットと Cloud クレジットを分けて見る](/articles/rork-business/rork-build-credits-cloud-credits-separate-balances-check)に、モデルごとの使い分けは[Sonnet 5.5・GPT-6.1 Sol・Opus 5.5 のどれに頼むかを、修正の種類で先に決めておきます](/articles/rork-ai/rork-model-menu-three-fix-types-credit-destination-ledger)に書き残しました。無料のまま試している方は、[Rork の無料枠は月35クレジットですが、実際にぶつかるのは1日5という上限のほうです](/articles/rork-basics/rork-free-tier-daily-five-credit-cap-planning)も合わせてご覧いただければ幸いです。

## 次に試していただきたいこと

いま開いているプロジェクトで、直近の答えの下にある「⋯」を開き、「Review changes」を一度だけ押してみてください。何も壊れていない日にこの画面を見ておくと、壊れた日に迷う時間が確実に短くなります。

私自身、直してもらうほうに気を取られて、戻る手段を後回しにしがちでした。戻り方を先に決めておく。この線引きだけは、疲れている夜でも守っていきたいと感じています。
