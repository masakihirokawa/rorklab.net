開発用の API を向いたまま、本番用のビルドを作ってしまった——その可能性に気づくきっかけは、アプリの挙動ではなく、ビルドログのたった1行でした。

```
> Task :app:createBundleReleaseJsAndAssets UP-TO-DATE
```

環境変数の `EXPO_PUBLIC_API_URL` を本番の値に変え、Android のリリースビルドをやり直したとします。ビルドは「BUILD SUCCESSFUL」で終わります。ところが、できたアプリの中身は、前回の開発用の値のままかもしれません。Expo の GitHub に、まさにこの症状の報告が上がっておりました。

環境ごとに値を切り替える運用は、私も壁紙アプリの広告や接続先の設定で続けております。切り替えの確認を「ビルドが通ったかどうか」だけで済ませていた時期があり、この報告を読んだとき、胃のあたりがひやりとしました。

最初にお伝えしたいのは、結論です。**値だけを変えたビルドは、Gradle から見ると「何も変わっていないビルド」で、JavaScript のバンドルを作り直さずに飛ばすことがあります。** 以下、公式の報告で確認できたこと、私が手元の模型で再現したこと、まだ確かめていないことを分けて書き残します。

## この記事が役に立つ場面

次のどれかに心当たりがある方を想定しています。

- `.env` や環境変数の値だけを変えて、Android のリリースビルドを同じフォルダで回し直しました
- 本番用の APK や AAB なのに、開発用のサーバーへ通信している気配があります
- ビルドログに `UP-TO-DATE` が並んでいて、どれが問題なのか分かりません

逆に、毎回まっさらな環境でビルドしている方や、JavaScript のソースも一緒に変えた方は、この症状に当たりにくいはずです。理由は次の節で触れます。

## 症状から原因を切り分ける

まず、手元の状況がこの不具合なのか、別の原因なのかを分けます。症状が似ていても、原因が違えば直し方も変わります。

1行目に当てはまる方が、この記事の主な読者です。2行目から4行目は「タスクは動いているのに値がおかしい」系で、原因が Gradle ではなく Expo の読み込み規則にあります。

報告は [expo/expo の Issue 49630](https://github.com/expo/expo/issues/49630) です。2026年9月1日に立ち、SDK 57・React Native 0.86・macOS・素の Android プロジェクト（bare workflow）で確認されています。同じ Issue には Expo 側の自動検証も付いており、「再現した」と書かれています。シェルの環境変数だけでなく、`.env` ファイルを書き換えた場合も同じだったそうです。

## なぜ飛ばされるのか

`EXPO_PUBLIC_` で始まる値は、実行時ではなく、バンドルを作るときに文字列として埋め込まれます。埋め込みを担うのは `babel-preset-expo` で、本番用のバンドルでは `process.env.EXPO_PUBLIC_API_URL` という式が、その時点の値の文字列に置き換わります。値が変われば、バンドルの中身も変わるはずなのです。

ところが Gradle は、タスクに「入力」として教えられたものしか見ていません。修正の Pull Request の説明によると、React Native のバンドルを作るタスクが入力として宣言しているのは、プロジェクトの中の `.js`・`.jsx`・`.ts`・`.tsx` のファイルと、エントリーファイルや `--dev`・`--minify` といった設定値です。バンドラはプロセスの環境変数を受け継いで動きますが、その環境変数は入力の一覧に入っていません。

`.env` ファイルも、二つの理由で入力から漏れます。拡張子が `.js` や `.ts` ではないこと、そして Expo の CLI が自分のプロセスの中で読むため、Gradle には変数として届かないことです。

入力も出力も前回と同じに見えるので、Gradle は「やる必要はありません」と判断し、`UP-TO-DATE` と表示して終わります。要するに、バンドラの側は環境に依存しているのに、Gradle の側はそれを知らない——この食い違いが原因です。

## 最小のかたちで再現してみる

報告を読むだけでは、手応えがありません。そこで、Android も Expo も使わず、Gradle だけで同じ食い違いを作ってみました。バンドルを作るタスクを真似て、入力は `src` フォルダだけ、出力は1ファイル、中身は環境変数から埋め込みます。

```groovy
tasks.register('createBundle') {
  inputs.dir('src')                                   // 入力: ソースだけ
  outputs.file(layout.buildDirectory.file('index.bundle'))
  doLast {
    def out = layout.buildDirectory.file('index.bundle').get().asFile
    out.parentFile.mkdirs()
    // バンドラが環境変数を埋め込む動作の代わり
    out.text = "var API = '" + (System.getenv('EXPO_PUBLIC_API_URL') ?: '') + "';\n"
  }
}
```

値を変えて2回回した結果は、次のとおりです（Gradle 8.14.3）。

```
# 1回目: EXPO_PUBLIC_API_URL=https://dev.example.invalid
> Task :createBundle
var API = 'https://dev.example.invalid';

# 2回目: EXPO_PUBLIC_API_URL=https://prod.example.invalid
> Task :createBundle UP-TO-DATE
var API = 'https://dev.example.invalid';
```

2回目は `UP-TO-DATE` になり、出力は開発用の値のままでした。ビルドは成功扱いなので、ログを流し読みしていると、まず気づけません。

## 直し方：環境変数を「入力」として宣言する

対処の考え方は、`EXPO_PUBLIC_` で始まる環境変数を、バンドルのタスクの入力として Gradle に教えることです。私の模型にも、同じ考え方で宣言を足してみました。

```groovy
def pub = providers.environmentVariablesPrefixedBy('EXPO_PUBLIC_')
tasks.named('createBundle') { inputs.property('expoPublicEnv', pub) }
```

`environmentVariablesPrefixedBy` は、指定した接頭辞で始まる環境変数だけを読む Gradle の API です。関係のない環境変数まで入力にしてしまうと、ちょっとした違いで毎回作り直しになりますので、接頭辞で絞るのが肝心です。

宣言を足したうえで、同じ順に3回回しました。

```
# 1回目: dev の値
> Task :createBundle                 → https://dev.example.invalid
# 2回目: prod の値
> Task :createBundle                 → https://prod.example.invalid
# 3回目: prod の値のまま
> Task :createBundle UP-TO-DATE
```

値が変わった2回目は再実行され、変わらない3回目だけが飛ばされました。速さを保ったまま、値の取り違えを防げるかたちです。

実際のプロジェクトに当てはめるなら、`android/app/build.gradle` の末尾に、次のような宣言を足すことになると思います。`createBundle` で始まり `JsAndAssets` で終わるタスクすべてに、環境変数と `.env` 系ファイルの両方を入力として渡します。

```groovy
// android/app/build.gradle の末尾（Expo 側の修正が入るまでの暫定）
def expoPublicEnv = providers.environmentVariablesPrefixedBy('EXPO_PUBLIC_')
def projectRoot = rootProject.projectDir.parentFile   // android フォルダの1つ上
def envFiles = files(['.env', '.env.local', '.env.production', '.env.production.local']
  .collect { new File(projectRoot, it) })

tasks.matching { it.name.startsWith('createBundle') && it.name.endsWith('JsAndAssets') }
  .configureEach {
    inputs.property('expoPublicEnv', expoPublicEnv)
    inputs.files(envFiles).withPathSensitivity(PathSensitivity.RELATIVE)
  }
```

ここで、確かめていないことを分けておきます。模型での動きは確認しましたが、上の `build.gradle` への書き足しは、私は手元の Android プロジェクトで試しておりません。ファイル名の並びは、Expo のドキュメントにある本番モードの読み込み対象に合わせたものです。また、`android` フォルダを `npx expo prebuild` で毎回作り直す運用では、書き足した内容が消えます。その場合は、次の節の別の手を選んでいただくほうが確実です。

## 直るまでの逃げ道と、選び方

Expo 側では、この入力を自動で宣言する修正が [Pull Request 49839](https://github.com/expo/expo/pull/49839) として出されています。説明によると、`EXPO_PUBLIC_*` の環境変数と、プロジェクトの `.env`・`.env.*` ファイルの両方を、すべての `createBundle*JsAndAssets` タスクの入力にする内容です。2026年11月24日に確かめた時点でも、まだ取り込まれておりませんでした。なお、この Pull Request は自動の検証から生まれたもので、人のレビューが済んでいない旨が冒頭に明記されています。

取り込まれるまでの手は、大きく四つです。

<table>
<thead><tr><th>手</th><th>確実さ</th><th>ビルドの速さ</th><th>prebuild で消えるか</th><th>向いている場面</th></tr></thead>
<tbody>
<tr><td>`./gradlew assembleRelease --rerun-tasks`</td><td>高い</td><td>遅くなる（全タスクを実行し直す）</td><td>消えない（コマンドの指定）</td><td>本番用を作るときだけ、たまに回す</td></tr>
<tr><td>`build.gradle` に入力を宣言する</td><td>高い（ただし実機で未確認）</td><td>ほぼ変わらない</td><td>消える</td><td>`android` フォルダを手で管理している</td></tr>
<tr><td>まっさらな環境でビルドする</td><td>高い</td><td>初回分だけ遅い</td><td>関係しない</td><td>CI や、本番用を別のフォルダで作る運用</td></tr>
<tr><td>Expo の修正を待つ</td><td>取り込まれた版から</td><td>変わらない</td><td>関係しない</td><td>当面は本番用のビルドを作らない</td></tr>
</tbody>
</table>

私なら、**本番用のビルドだけは `--rerun-tasks` を付ける**、を最初に選びます。速さを少し差し出す代わりに、考えることが一つ減るからです。`android` フォルダを手で管理していて、開発用と本番用を頻繁に行き来する方は、宣言を足す手のほうが日々の負担は軽いと思います。

EAS のクラウドビルドでも起きるのかどうかは、報告でも「未確認」の扱いでした。私も確かめておりませんので、断定はいたしません。

## よくある思い込みを三つ、ほどいておきます

一つ目は、「BUILD SUCCESSFUL と出たのだから、値も新しくなっている」という思い込みです。Gradle の成功は「やるべきタスクがすべて終わった」という意味で、`UP-TO-DATE` で飛ばしたタスクも、成功として数えられます。中身が狙いどおりかどうかは、別に確かめる必要があります。

二つ目は、「`.env` を書き換えれば、次のビルドに反映される」という思い込みです。上で触れたとおり、`.env` は Expo の CLI が読むもので、Gradle はその変化を知りません。開発サーバーでは値がすぐ反映されて見えるので、なおさら気づきにくいのです。

三つ目は、「`process.env` から読めば、書き方は何でもよい」という思い込みです。Expo のドキュメントでは、埋め込まれるのは `process.env.EXPO_PUBLIC_KEY` のようにドットで静的に書いた式だけで、`process.env['EXPO_PUBLIC_KEY']` や分割代入は対象外とされています。この場合はタスクが動いていても値が入りませんので、切り分け表の3行目にあたります。

## できあがった APK の中身を、公開前に確かめる

結局のところ、いちばん確実なのは「できあがったものの中身を見る」ことです。APK は zip 形式なので、バンドルのファイルを取り出して、接続先の文字列を探せます。

```bash
# 開発用の接続先が残っていないかを数える（0 なら見つからない）
unzip -p android/app/build/outputs/apk/release/app-release.apk \
  assets/index.android.bundle | grep -a -c 'dev.example.invalid'

# 本番用の接続先が入っているかを確かめる（1 以上なら入っている）
unzip -p android/app/build/outputs/apk/release/app-release.apk \
  assets/index.android.bundle | grep -a -c 'prod.example.invalid'
```

`dev.example.invalid` の部分は、皆さまの開発用の接続先に置き換えてください。リリース用のバンドルは Hermes のバイトコードになっていることが多く、テキストのままではありませんが、`grep -a` で文字列そのものを探す使い方です。この確認は、私の模型では試しておりませんので、見つからなかったときに「入っていない」と言い切る前に、本番用の値のほうも探して、両方の結果を並べて判断していただければと思います。

**成功の表示は、中身の保証ではありません。** この線引きを忘れかけた日は、ログの `UP-TO-DATE` を探すところから確かめ直すようにしています。

## 次に詰まりやすいところ

この不具合を避けられても、環境変数まわりでは、もう一段の落とし穴が待っています。SDK 58 からは `.env.staging` のような、モードに対応しないファイルが読まれなくなりました。どのファイルが勝つかを機械で数える方法は、[SDK 58 から .env.staging は読み込まれません](/articles/app-dev/expo-sdk58-env-staging-file-not-loaded-local-wins-audit-script) にまとめております。

また、接続先の取り違えは、審査の場面では「起動しても白い画面」という形で表に出ることがあります。そのときに疑う箇所は [App Review で「Guideline 2.1・白い画面」と言われたとき](/articles/app-dev/app-review-guideline-2-1-blank-screen-expo-release-build-checklist) で整理しました。

デプロイのあとに古い状態が残り続けるという点では、Web 側にも似た構図があります。そちらは [デプロイ直後に出る Application error は、なぜ再デプロイでは直らないのか](/articles/rork-dev/why-redeploy-does-not-fix-application-error-stale-html-calls-missing-chunk) で、原因の側から掘り下げております。

次にビルドの接続先を切り替えるときは、まずビルドログを開いて、`createBundle` の行が `UP-TO-DATE` になっていないかだけ、確かめていただければと思います。
