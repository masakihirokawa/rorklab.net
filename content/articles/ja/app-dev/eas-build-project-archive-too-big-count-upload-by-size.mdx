壁紙アプリの新しい一本を、EAS で初めてビルドしようとした夜のことです。ターミナルは「Compressing project files」のあたりで長く止まり、やがて赤い一行が出ました。

`Project archive is too big. Maximum allowed size is 2.0 GB.`

コードは数百ファイルしかありません。それなのに 2 GB という数字が出てくる理由が、すぐには分かりませんでした。胃のあたりが重くなったのを覚えております。

最初にお伝えしたいのは、この失敗は「コードが大きい」からではなく、「送るつもりのなかったものが一緒に入っている」から起きるという点です。原因は、ほとんどの場合プロジェクトの外れのほうにあります。

先に結論を三つだけ置きます。

- 上限は圧縮後のアーカイブで測られます。150 MiB を超えると警告、2 GiB を超えると失敗です。
- 何が入るかは、公式の `eas build:inspect --stage archive` で手元に書き出すのがいちばん確かです。ログインせずに素早く見たいときは、後半のスクリプトで大きい順に並べます。
- `.easignore` は `.gitignore` に足されるのではなく、リポジトリ内のすべての `.gitignore` と入れ替わります。置き場所もリポジトリのルートだけです。

以下の内容は、2026年11月時点の Expo 公式ドキュメント（.easignore の節と、アップロードの仕組みを説明した expo.fyi の記事）と、eas-cli のソースコードで確かめています。

## 上限は二段階で、測られるのは「圧縮後」のサイズです

EAS CLI は、手元のプロジェクトを一時ディレクトリに写してから、gzip をかけた tar に固めて送ります。eas-cli のソースでは、その tar のファイルサイズを見て次のように扱っています。

<table>
<tr><th>圧縮後のアーカイブ</th><th>起きること</th><th>表示される文言（要旨）</th></tr>
<tr><td>150 MiB 以下</td><td>何も出ません</td><td>「Compressed project files（所要時間とサイズ）」</td></tr>
<tr><td>150 MiB 超</td><td>警告が出て、ビルドは続きます</td><td>「Your project archive is …. You can reduce its size … in .easignore file.」</td></tr>
<tr><td>2 GiB 超</td><td>アップロード前に失敗します</td><td>「Project archive is too big. Maximum allowed size is …」</td></tr>
</table>

ここで見落としやすいのが「圧縮後」という点です。ソースコードやJSONはよく縮みますが、PNG・JPEG・動画はもともと圧縮されているので、ほとんど縮みません。画像の多いプロジェクトでは、**画像の生の合計が、ほぼそのままアーカイブのサイズになる**と考えておくと見当を外しません。

警告の段階で気づけば、まだ引き返せます。私は最初の警告を「ネットワークが遅いだけだろう」と読み流しました。ここが分かれ道でした。

なお `node_modules` は、どの設定でもアーカイブに入りません。`.git` ディレクトリも既定では送られません。ですから「依存が重い」という線は、先に消しておいて大丈夫です。

## まず公式の確かめ方：eas build:inspect で中身を書き出します

Expo のドキュメントには、アップロードされるファイルをそのまま手元のディレクトリへ写すコマンドが載っています。ビルドは始まりません。

```bash
# 事前に eas login が必要です。出力先は存在しないディレクトリを指定します
eas build:inspect --platform android --stage archive --output ./eas-archive

# 何が重いかを見ます（KB・大きい順）
du -ak ./eas-archive | sort -rn | head -15

# 実際に送られる大きさに近い値（gzip をかけたときのバイト数）
tar -czf - -C ./eas-archive . | wc -c
```

使うときの注意を三つ書き残します。

- 出力先がすでにあると止まります。消してから実行するか、`--force` を付けます。
- `eas.json` で `cli.requireCommit` を `true` にしている場合は、先にコミットしておきます。このコマンドはコミットを促してくれません。
- `./eas-archive` をプロジェクトの中に作ると、次のビルドでそれ自体が上がります。確かめ終えたら消すか、`.easignore` に書いておきます。

このコマンドの結果がいちばん確かです。ただ、ログインが要ることと、写し終えるまで待つことを考えると、私は「当たりをつける」段階では次のスクリプトを先に使っています。

## ログインせずに、大きい順に数えるスクリプト

この記事の初版では、`git ls-files` に無視ルールを1枚だけ読ませるスクリプトを載せていました。検証用の小さなリポジトリで確かめ直したところ、二つの点で実際のアップロードとずれていましたので、ここで訂正いたします。

- `.easignore` が無いとき、EAS はサブディレクトリにある `.gitignore` も読みます。ルートの1枚だけを読ませると、そこで外されるはずのファイルまで数えてしまいます。
- `.easignore` で外したファイルでも、git で追跡中なら一覧に残っていました。EAS は追跡中かどうかに関係なく外します。

直した版がこちらです。プロジェクトの中で `sh eas-upload-size.sh` と実行します。

```bash
#!/bin/sh
# EAS に送られるファイルを、送る前に手元で数えるためのスクリプトです
set -eu
cd "$(git rev-parse --show-toplevel)"   # .easignore はリポジトリのルートから読まれます

if [ -f .easignore ]; then
  echo "適用されるルール: .easignore（.gitignore はすべて読まれません）"
  set -- --exclude-from=.easignore
else
  echo "適用されるルール: 各ディレクトリの .gitignore"
  set -- --exclude-per-directory=.gitignore
fi

LIST=$(mktemp); IGN=$(mktemp)
# 追跡中(-c)と未追跡(-o)を並べ、ルールに当たる追跡中ファイル(-c -i)を引きます
git ls-files -c -o "$@" | grep -v -e '^node_modules/' -e '/node_modules/' | sort -u > "$LIST"
git ls-files -c -i "$@" | sort -u > "$IGN"
comm -23 "$LIST" "$IGN" > "$LIST.final"

echo "--- 大きい順（KB） ---"
tr '\n' '\0' < "$LIST.final" | xargs -0 -r du -k 2>/dev/null | sort -rn | head -10
echo "--- 最上位2階層ごとの合計（KB） ---"
tr '\n' '\0' < "$LIST.final" | xargs -0 -r du -k 2>/dev/null \
  | awk '{n=split($2,p,"/"); k=(n>2)?p[1]"/"p[2]:p[1]; s[k]+=$1} END{for(k in s) print s[k], k}' | sort -rn | head
echo "--- 件数 / 生の合計 / gzip 後の見積もり（バイト） ---"
wc -l < "$LIST.final"
tr '\n' '\0' < "$LIST.final" | xargs -0 -r cat 2>/dev/null | wc -c
tar -czf - -T "$LIST.final" 2>/dev/null | wc -c
rm -f "$LIST" "$IGN" "$LIST.final"
```

何をしているかを短く書きます。追跡中と未追跡のファイルを、EAS と同じルールの読み方で並べます。そのうえで「追跡中だがルールに当たるもの」を差し引きます。最後に、生の合計と、gzip をかけたときの見積もりを並べて出します。

Linux（git 2.34）の検証用リポジトリで動かしたときの出力です。`.gitignore` は `node_modules/` だけ、`app/.gitignore` で `big.bin` を外し、`assets/original/` に 3 MB と 0.5 MB の画像を置いています（片方はコミット済み、片方は未追跡です）。

```text
適用されるルール: 各ディレクトリの .gitignore
--- 大きい順（KB） ---
2932	assets/original/a.png
492	assets/original/b.png
4	src/index.ts
...
--- 件数 / 生の合計 / gzip 後の見積もり（バイト） ---
5
3500024
3501211
```

`app/sub/big.bin` は一覧に出ていません。サブディレクトリの `.gitignore` が効いているからです。画像は gzip をかけても縮まず、見積もりは生の合計とほぼ同じになりました。macOS でも同じ書き方で動くはずですが、私はこの版を Linux でしか走らせていません。macOS の `du` や `tar` で数字の出方が違うときは、`eas build:inspect` の結果を正としてください。

## 重さの正体は、たいてい三種類です

実際に私が見つけたのは、次のようなものでした。どれも「git には載せていないつもりだった」ものばかりです。

- 原寸の素材置き場です。`assets/original/` のような、配信前の高解像度画像や動画が入っています。
- ローカルでビルドしたときの残り物です。`android/app/build/`、`android/.gradle/`、`ios/Pods/`、`ios/build/` などが当たります。
- 書き出しの途中ファイルです。zip、`.psd`、画面録画などが紛れ込みます。

壁紙アプリは、素材そのものが商品です。原寸の画像をプロジェクトの中に置く癖があって、これが一番効きました。アプリに入れるのは縮小後の数十枚なのに、置き場には元の画像が全部あったのです。

ビルドの残り物は、サイズだけでなくビルドの失敗にもつながります。手元の `android/build` が残ったまま上がって EAS だけが落ちる例は、[EAS Build だけ「No matching variant」で落ちるとき](/articles/app-dev/eas-build-no-matching-variant-stale-windows-autolinking-cache) に書きました。

## よくある誤解を三つ訂正します

**一つ目は「git に add していないから上がらない」です。** 既定の動き（コミットを必須にしない設定）では、EAS CLI は `git clone --depth 1` に近いかたちで作業ディレクトリを写します。未コミットのファイルも、未追跡のファイルも、無視ルールに当たらなければ入ります。`eas.json` の `cli.requireCommit` を `true` にすると浅いクローンそのものになり、未追跡のファイルは入らなくなります。ただし、その場合でも `.easignore` は効き、当たったファイルはクローンから消されます（そのときは「コミットと中身が一致しない」という警告が出ます）。

**二つ目は「.easignore は .gitignore に足される」です。** 公式ドキュメントでは、`.easignore` を作ると、リポジトリ内のすべての `.gitignore` の代わりに使われると書かれています。ルートの1枚だけでなく、サブディレクトリの `.gitignore` も読まれなくなります（詳しくは [.easignore を置くと .gitignore は読まれなくなります](/articles/rork-dev/easignore-replaces-gitignore-eas-build-upload-scope) に書きました）。

**三つ目は「.easignore は eas.json の隣に置けばよい」です。** 2026年11月時点のドキュメントでは、Git を使う通常の流れで `.easignore` を読むのはリポジトリのルートだけです。モノレポでアプリのディレクトリに置いても読まれません。`eas.json` の隣も読むようにする変更は eas-cli に提案されていますが、私が確かめた時点では取り込まれていませんでした。Git を使わない流れ（`EAS_NO_VCS=1`）では、`EAS_PROJECT_ROOT` で指したディレクトリから読まれます。

## .gitignore に書いたのに入っているとき

「無視しているはずなのに入る」場合は、ルールの当たり方を確かめます。

```bash
# .easignore が無いとき：どの .gitignore のどの行が当たっているかを表示します
git check-ignore -v assets/original/wall_0001.png
echo "exit=$?"   # 0 なら無視される、1 なら無視されない

# .easignore があるとき：check-ignore は .easignore を読まないので、こちらで確かめます
git ls-files -c -o -i --exclude-from=.easignore | grep 'assets/original/' | head
```

`git check-ignore` は、`.gitignore` と git 自身の設定を読みます。`.easignore` は読みません。ここを取り違えると「当たっているはずなのに」と同じ場所を何度も見直すことになりますので、二つを分けて書きました。

終了コードが 1 なら、そのファイルは無視されていません。たとえば `assets/original` と書いたつもりが、ファイルの置き場所は `app/assets/original` だった、ということが起こります。先頭に `/` を付けるとルール文を置いたディレクトリからの位置に固定されますので、パスを一文字ずつ見直す価値があります。

## 減らし方は三つあり、場面で選びます

<table>
<tr><th>方法</th><th>向いている場面</th><th>気をつけること</th></tr>
<tr><td><code>.easignore</code> で外す</td><td>手元には置いておきたいが、ビルドには要らないもの</td><td>.gitignore の写し漏れ。外しすぎ</td></tr>
<tr><td><code>cli.requireCommit: true</code></td><td>未追跡の大きなファイルが多く、送る中身をコミットと揃えたいとき</td><td>コミットしないとビルドできません。.easignore も引き続き効きます</td></tr>
<tr><td>素材をプロジェクトの外へ移す</td><td>原寸画像や動画など、そもそもアプリの外で扱うもの</td><td>参照しているスクリプトのパスを直す必要があります</td></tr>
</table>

私は、原寸素材はプロジェクトの外へ移し、ビルドの残り物は `.easignore` で外す、という分け方にしています。素材を外へ移すと、EAS だけでなくエディタの検索やバックアップも軽くなるからです。

`.easignore` を書くときは、まず `.gitignore` の中身をすべて写してから、重いものを足します。

```
# .gitignore の内容をまず写します（サブディレクトリの .gitignore も忘れずに）
node_modules/
.expo/
dist/
.env

# 今回の原因だった、ビルドに要らないものを足します
/assets/original/
android/app/build/
android/.gradle/
ios/Pods/
ios/build/
*.psd
*.zip

# 確かめ用に書き出したディレクトリ
/eas-archive/

# git で管理していないが、ビルドに要るファイルは最後に ! で戻します
# !generated/config.json
```

公式ドキュメントの例には `/android` と `/ios` をまるごと外す行もあります。これは、ネイティブのディレクトリを持たず、ビルド機で prebuild に作らせている場合の書き方です。`ios/` や `android/` に手で入れた変更をコミットしているプロジェクトで同じ行を書くと、その変更ごと消えます。手入れが残っているかどうかは、[prebuild --clean で消える手入れを、上げる前に数える](/articles/rork-dev/rork-expo-prebuild-native-drift-inventory-config-plugin) の手順で確かめてから決めていただければと思います。

## 外しすぎた夜のこと

`.easignore` を初めて書いたとき、私は勢いで `assets/` を丸ごと外しかけました。合計は見事に下がりました。ところが `eas build:inspect` の出力を開くと、アプリアイコンもスプラッシュの画像も見当たりません。そのままビルドしていたら、ビルド機の側で画像が見つからずに止まっていたはずです。

サイズが下がったことと、ビルドに要るものが残っていることは、別々に確かめないといけないのだと気づいたのは、このときでした。

**削るときは合計を、残すときは中身を見ます。** いまはこの二つを、`.easignore` を書き換えるたびに順番に確かめるようにしております。

## 次にすること

まず、いまのプロジェクトで上のスクリプトを一度走らせていただければと思います。gzip 後の見積もりが 150 MiB を超えていたら、次のビルドの前に `.easignore` を見直し、最後に `eas build:inspect --stage archive` で中身を確かめてみる価値があります。何も出なければ、アップロードは原因ではないと分かっただけでも収穫です。
