Play Console の段階公開を 5% に動かした翌朝、Crashlytics には「Crash-free users 99.76%」と出ていました。手元の基準は 99.7% です。超えているのだから 25% へ進めてよい、と指が動きかけて止まりました。母数の欄が 420 だったからです。

数字は同じでも、420 人の 99.76% と 2 万人の 99.76% は、別の情報です。前者は「たまたま 1 人しか落ちなかった」可能性を含み、後者はほぼ確定した値です。画面は両方に同じ書式で同じ顔をした数字を出します。

私は 5% → 25% → 50% → 100% の四段で出し、Crash-free users が 99.7% を下回るか ANR が 0.20% を超えたら halt（比率を戻す）と決めています。以前の記事（[Android 壁紙アプリ v2.1.0 公開後の保守](/articles/app-dev/android-wallpaper-app-v2-post-release-maintenance-crashlytics-claude-in-chrome)）に書いたとおり、v2.0.0 では二度止めました。その線引き自体は変えません。変えたのは、線と比べる「数字の信頼度」を一緒に見ることです。

ここでは、母数込みで進む・待つ・止めるを決める小さな Python スクリプトと、それを毎朝回したときに起きる意外な副作用を、手元で乱数を回して確かめた結果としてお伝えします。

## 同じ 99.76% でも、母数で読める範囲がこれだけ変わる

Crash-free を「クラッシュしなかったユーザーの割合」と読むと、それはユーザー数 n のうち k 人が落ちたという二項データです。観測値が同じでも、真の値の幅は n で決まります。95% の Wilson 区間（後述）で並べると次のようになります。

4 行とも観測は 99.76% 前後で、目標の 99.7% を上回っています。それでも 2 万人の時点ですら、区間の下端 99.68% は目標をわずかに割っています。「超えているから進める」は、思っていたよりずっと遅い段階まで成立しません。

最初の 5% で見える数字は、おおむね「方向の目安」です。これを判定の根拠にするなら、根拠にしてよい条件を先に決めておく必要があります。

## 進む・待つ・止めるを、区間と目標の位置関係で決める

判定は単純です。真の値の区間が、許容ライン（99.7% なら クラッシュ率 0.3%）に対してどこにあるかを見ます。

- 区間の上端でも許容内なら、確かに良いので進む
- 区間の下端でも許容を超えていて、件数も偶然で済まないなら、確かに悪いので止める
- 区間が許容ラインをまたいでいるなら、まだ決められないので待つ

以下がそのまま動くスクリプトです。標準ライブラリだけで、Crashlytics の画面に出ている「ユーザー数」と「クラッシュしたユーザー数」を手で渡します。

```python
#!/usr/bin/env python3
"""段階公開の「進む／待つ／止める」を、母数込みで判定する。
使い方: python3 rollout_gate.py --users 420 --crashed 1 --target 99.7
標準ライブラリのみ。Crashlytics / Play Console に出ている「ユーザー数」と
「クラッシュしたユーザー数」を手で入れて使います。"""
import argparse
import math
import sys

Z = {90: 1.645, 95: 1.960}  # 片側 95% = 1.645 / 両側 95% = 1.960


def wilson(k: int, n: int, z: float) -> tuple[float, float]:
    """クラッシュ率 k/n の Wilson 区間 (low, high)。n が小さくても 0〜1 に収まる。"""
    if n <= 0:
        raise ValueError("users must be > 0")
    p = k / n
    z2 = z * z
    denom = 1 + z2 / n
    center = (p + z2 / (2 * n)) / denom
    half = z * math.sqrt(p * (1 - p) / n + z2 / (4 * n * n)) / denom
    return max(0.0, center - half), min(1.0, center + half)


def judge(users: int, crashed: int, target_pct: float, z: float = Z[95],
          min_crashed: int = 3) -> dict:
    allowed = 1 - target_pct / 100          # 許容するクラッシュ率 (99.7 → 0.003)
    low, high = wilson(crashed, users, z)
    if low > allowed and crashed >= min_crashed:
        verdict = "HALT"                    # 下限でも許容超え、かつ件数が偶然では済まない
    elif high <= allowed:
        verdict = "PROCEED"                 # 上限でも許容内 = 確実に良い
    else:
        verdict = "WAIT"                    # 区間が許容ラインをまたぐ = まだ決められない
    return {
        "users": users, "crashed": crashed,
        "observed_crash_free": 100 * (1 - crashed / users),
        "crash_free_low": 100 * (1 - high), "crash_free_high": 100 * (1 - low),
        "verdict": verdict,
    }


def users_needed_for_zero_crash(target_pct: float, z: float = Z[95]) -> int:
    """クラッシュ 0 件のまま PROCEED と言えるのは何ユーザー目からか。
    k=0 の Wilson 上限 = z²/(n+z²) <= allowed を n について解く。"""
    allowed = 1 - target_pct / 100
    return math.ceil(z * z * (1 / allowed - 1))


def days_to_decide(users: int, needed: int, users_per_day: float) -> int:
    """あと何日で needed ユーザーに届くか。users_per_day は「この段階で新規に
    新バージョンを開くユーザー数」の直近の実測値を入れる。"""
    if users >= needed:
        return 0
    if users_per_day <= 0:
        raise ValueError("users_per_day must be > 0")
    return math.ceil((needed - users) / users_per_day)


def main() -> int:
    ap = argparse.ArgumentParser()
    ap.add_argument("--users", type=int, required=True)
    ap.add_argument("--crashed", type=int, required=True)
    ap.add_argument("--target", type=float, default=99.7)
    ap.add_argument("--per-day", type=float, default=0,
                    help="この段階で 1 日に増える新バージョン利用ユーザー数(実測)")
    ap.add_argument("--min-crashed", type=int, default=3,
                    help="この件数に満たない間は HALT にせず WAIT にする")
    ap.add_argument("--conf", type=int, choices=sorted(Z), default=95)
    a = ap.parse_args()
    if a.crashed > a.users:
        print("crashed が users を超えています", file=sys.stderr)
        return 2
    r = judge(a.users, a.crashed, a.target, Z[a.conf], a.min_crashed)
    print(f"{r['verdict']}: {r['crashed']}/{r['users']} users crashed "
          f"(観測 {r['observed_crash_free']:.2f}% / 真の値は "
          f"{r['crash_free_low']:.2f}〜{r['crash_free_high']:.2f}% の範囲)")
    if r["verdict"] == "WAIT":
        need = users_needed_for_zero_crash(a.target, Z[a.conf])
        print(f"  目標 {a.target}% を 0 件で確かめるには約 {need} ユーザー必要")
        if a.per_day > 0:
            print(f"  今の増え方なら、あと約 {days_to_decide(a.users, need, a.per_day)} 日")
    return {"PROCEED": 0, "WAIT": 10, "HALT": 20}[r["verdict"]]


if __name__ == "__main__":
    sys.exit(main())
```

Wilson 区間を選んだ理由は、母数が小さく、クラッシュが 0〜数件という領域で、普通の正規近似（観測値 ± 誤差）が壊れるからです。k が 0 のとき正規近似の幅は 0 になり、「0 件だから完全に安全」という誤った自信を生みます。Wilson は k=0 でも幅を保ち、0〜1 の外にもはみ出しません。終了コードを 0・10・20 に分けているので、シェルスクリプトや CI から呼んで分岐にも使えます。

実際に動かすと、こう返ります。

```text

WAIT: 1/420 users crashed (観測 99.76% / 真の値は 98.66〜99.96% の範囲)
  目標 99.7% を 0 件で確かめるには約 1277 ユーザー必要

$ python3 rollout_gate.py --users 2000 --crashed 14
```

## クラッシュが 0 件でも、すぐには進めない

意外だったのは、0 件でも進めない段階が長いことでした。k=0 のときに PROCEED と言えるユーザー数は、目標値だけで決まります（95% 区間）。

目標を 99.7% に置くと、1,277 人が新バージョンを開いて、一人も落ちなくて、はじめて「確かに良い」と言えます。目標を 0.2 ポイント上げて 99.9% にするだけで、必要な人数は 3 倍になります。数字を厳しくするほど、判断が遅れる側に効くわけです。

ここで効いてくるのが、`--per-day` に入れる「この段階で 1 日に増える利用ユーザー数」です。たとえば 5% の段階で 1 日に 150 人ずつ増えるなら、420 人から 1,277 人までは約 6 日かかります。標準にしていた「1 段階 24〜48 時間」では、最初の 5% の段階では統計的な判断に届かないことを、数字として先に知っておけます。

私はこの結果を受けて、判断の置き場所を変えました。5% の段階は「進む根拠を集める」場ではなく、「確かに悪いものだけを止める」場と割り切ります。進めるかどうかの根拠は、25% 以降の母数で集めます。この割り切りは、数字を疑うことではなく、数字の重さを量ることなのだと感じています。

## 毎朝見ていると、良いリリースを止めてしまう

もうひとつ、数字の見方で効いたのが「見る回数」です。判定を 50 ユーザー増えるごとにやり直す運用を想像してください。1 回ごとの誤検知は小さくても、回数を重ねるとどこかで一度は赤くなります。

これを確かめるため、乱数で二種類のリリースを作りました。良いリリースは真のクラッシュ率 0.2%（Crash-free 99.8%）、悪いリリースは 0.8% です。どちらも 2,000 ユーザーまで 50 人ごとに判定し、一度でも HALT が出たら止めたと数えます。各 4,000 回、乱数の種は固定です。

```python
"""良いリリース(真のクラッシュ率 0.2%)と悪いリリース(0.8%)を乱数で作り、
50 ユーザーごとに判定を回したとき、いつ・どれだけ HALT が出るかを数える。"""
import random
from rollout_gate import judge, Z

def run(true_rate, z, min_crashed, trials=4000, max_users=2000, step=50, seed=7):
    rnd = random.Random(seed)
    halted = 0; first = []
    for _ in range(trials):
        k = 0
        for n in range(1, max_users + 1):
            if rnd.random() < true_rate:
                k += 1
            if n % step == 0 and judge(n, k, 99.7, z, min_crashed)["verdict"] == "HALT":
                halted += 1; first.append(n); break
    first.sort()
    med = first[len(first) // 2] if first else None
    return 100 * halted / trials, med

for label, z, mk in [("z=1.645 件数条件なし", Z[90], 0), ("z=1.96  件数条件なし", Z[95], 0),
                     ("z=1.645 かつ 3件以上", Z[90], 3), ("z=1.96  かつ 3件以上", Z[95], 3)]:
    good, _ = run(0.002, z, mk)
    bad, med = run(0.008, z, mk)
    print(f"{label}: 良いリリースで誤HALT {good:5.1f}% / 悪いリリースで検出 {bad:5.1f}% (中央値 {med} ユーザー目)")
```

「95%」という数字から想像するより、良いリリースが誤って止まる確率は高いままです。件数条件なしだと、問題のないリリースの 6 本に 1 本が、5% の段階の途中で赤くなりました。50 ユーザーで 1 件だけ落ちても、観測のクラッシュ率は 2% になるため、下端が許容ラインを超えてしまうのが理由です。

一方、「3 件以上落ちるまでは止めない」という条件を足すと、悪いリリースの検出はほとんど落とさずに（98.0%→96.0%）、誤って止める割合は 16.8% から 5.0% まで下がりました。検出が遅れる代償は、中央値で 200 ユーザー目から 400 ユーザー目まで、およそ 200 人分です。この 200 人分の遅れを許せるかどうかが、私の判断軸になりました。個人開発で、夜のうちに誤検知で止めても気づくのは翌朝なので、誤って止めるほうが痛いと考えて、件数条件つきを標準にしています。

検証用のテストは次のとおりです。

```python
import math, unittest
from rollout_gate import wilson, judge, users_needed_for_zero_crash, days_to_decide, Z

class T(unittest.TestCase):
    def test_zero_crash_boundary(self):
        n = users_needed_for_zero_crash(99.7)
        self.assertEqual(judge(n, 0, 99.7)["verdict"], "PROCEED")
        self.assertEqual(judge(n - 1, 0, 99.7)["verdict"], "WAIT")
    def test_small_sample_never_halts_on_one_crash(self):
        self.assertEqual(judge(50, 1, 99.7)["verdict"], "WAIT")
        self.assertEqual(judge(50, 1, 99.7, min_crashed=0)["verdict"], "HALT")
    def test_clear_regression_halts(self):
        self.assertEqual(judge(2000, 14, 99.7)["verdict"], "HALT")
    def test_interval_stays_in_range(self):
        for n, k in [(1, 0), (1, 1), (10, 10), (100000, 0)]:
            lo, hi = wilson(k, n, Z[95]); self.assertTrue(0 <= lo <= hi <= 1)
    def test_days(self):
        self.assertEqual(days_to_decide(300, 900, 200), 3)
        self.assertEqual(days_to_decide(900, 900, 200), 0)

unittest.main(verbosity=1)
```

2 本目のテストは、実は最初に書いた期待が外れて気づいたものです。「50 人中 1 件ならさすがに待つはず」と思って書いたところ、件数条件なしでは HALT が返りました。直感より先に、数字が過敏だったことになります。件数条件の下限を引数にしたのは、この失敗のあとです。

## 区間では見えないものがある

ここまでの区間は、ユーザーがそれぞれ独立に落ちる、という前提に立っています。実際のクラッシュは独立ではありません。特定の端末や OS の組み合わせ、特定の画面操作に集中します。ヘビーユーザーほど落ちやすいという偏りも、段階公開の序盤ではそのまま出ます。

そのため私は、次の例外を一行だけ足しています。**クラッシュが 3 件に届いていなくても、同じ例外・同じ端末機種に集まっているなら、母数に関係なく止めて原因を見ます。** 区間の外側にある判断で、スクリプトには入れていません。Crashlytics のイシュー一覧で、新バージョンの「新規イシュー」の影響ユーザー数を見ると、この集中に気づけます。

もうひとつは分母です。Crash-free は「ユーザー」基準、Play Console の ANR 率などは「セッション」や「日次」基準のものが混ざります。ANR にも同じ考え方は使えますが、分母の定義を確かめてから `--users` に入れてください。分母の取り違えは、区間の計算より大きなズレを生みます。

## 毎回の運用に落とし込む

実際の運用は、次の三行です。

1. 段階を上げる直前と、翌朝の 1 回だけ、`rollout_gate.py` を回す（日中に何度も見ない）
2. HALT なら止める。WAIT なら、`--per-day` の日数を見て、次の確認日を決める。PROCEED なら上げる
3. 5% の段階で WAIT のままなら、無理に結論を出さず 25% へ進む条件を別に決める（例: 新規イシューが集中していないこと）

比率を戻す操作は、Google Play Developer API でも行えます。以下は公式ドキュメントの形に沿って書いたもので、この記事のために実機では実行していません。実行前に、対象トラックと versionCode をご自身の値で確かめてください。

```python
# 未実行の参考コードです。YOUR_PACKAGE_NAME と versionCode は自分の値に置き換えます。
from googleapiclient.discovery import build
from google.oauth2 import service_account

creds = service_account.Credentials.from_service_account_file(
    "service-account.json",
    scopes=["https://www.googleapis.com/auth/androidpublisher"])
svc = build("androidpublisher", "v3", credentials=creds)

def set_rollout(package: str, version_code: int, status: str, fraction: float | None = None):
    """status は "inProgress"（段階公開中）か "halted"（停止）。"""
    edit = svc.edits().insert(packageName=package, body={}).execute()
    release = {"versionCodes": [str(version_code)], "status": status}
    if status == "inProgress" and fraction is not None:
        release["userFraction"] = fraction     # 例: 0.25
    svc.edits().tracks().update(
        packageName=package, editId=edit["id"], track="production",
        body={"track": "production", "releases": [release]}).execute()
    svc.edits().commit(packageName=package, editId=edit["id"]).execute()

# set_rollout("YOUR_PACKAGE_NAME", 49, "halted")
```

## 落とし穴

- **母数を見ずに、観測の Crash-free だけを基準線と比べる**: 区間がまたいでいる限り、超えた・割ったのどちらも断言できません。
- **件数条件なしで、短い間隔で何度も判定する**: 良いリリースを止める確率が上がります。確認の回数と間隔を先に決めます。
- **目標値だけを厳しくする**: 99.7% から 99.9% に上げると、判断に必要な人数が 3 倍になり、判断が遅れます。
- **0 件を「完全に安全」と読む**: k=0 でも、小さい母数の上端は広いままです。
- **端末や例外の集中を、全体の数字に埋もれさせる**: 件数が少なくても、同じ原因なら止めます。

## 次の一歩

次の公開では、5% の段階に入る前に、自分のアプリで「1 日に増える利用ユーザー数」を一度だけ見ておいてください。その数字を `--per-day` に入れると、目標値に届くまでの日数が出ます。その日数が許せない長さなら、数字が悪いのではなく、段階の刻み方か目標値のほうを見直す合図です。

数字の揺れに、私は何度も振り回されてきました。今回の計算が、同じように朝の画面の前で手を止めている方の、判断の足場になれば幸いです。

関連して、段階公開の全体の組み立ては [Rork アプリの段階的リリース戦略](/articles/rork-dev/rork-phased-release-staged-rollout-hotfix-strategy)、クラッシュを読める形にする準備は [Rorkアプリの本番クラッシュを「読める」レポートに変える](/articles/rork-dev/rork-crashlytics-actionable-crash-reports-staged-distribution-field-notes) にまとめています。
