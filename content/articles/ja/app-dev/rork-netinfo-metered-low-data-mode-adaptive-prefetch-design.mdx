私が運用している壁紙アプリのレビューに、あるとき「Wi-Fi のないところで開いたら、あっという間にギガが減った」という指摘が届きました。原因はすぐに分かりました。一覧画面で次のページの高解像度画像を片っ端から先読みしていたのです。Wi-Fi なら快適さに貢献する挙動が、従量制のモバイル回線では利用者の通信量を静かに食いつぶしていました。画像を多く扱うアプリほど、この「良かれと思った先読み」が逆効果になりやすいと感じています。

ここでは Rork で生成した Expo アプリを題材に、回線の性質を読み取って先読みと画質を適応的に切り替える通信設計を整理します。鍵になるのは、回線を「つながっているか／いないか」の二値で見るのをやめ、「従量制か」「低速か」「低データモードか」まで踏み込んで判断することです。

## 「オンラインか否か」だけで判断するのをやめる

多くのアプリは `isConnected` だけを見て、つながっていれば全部やる、という作りになっています。しかし利用者の回線は一様ではありません。NetInfo の `details` には、判断に使える情報がもっと含まれています。

`isConnectionExpensive` は OS が判断した「従量制相当」のフラグで、テザリング経由の Wi-Fi なども含まれます。これを尊重するだけでも、レビューにあったような「ギガが溶ける」事故の多くは防げます。

低データモードについては補足が要ります。iOS の Low Data Mode / Android のデータセーバーは、アプリから直接「オンかどうか」を読む統一 API が乏しいのが実情です。実務では、`isConnectionExpensive` を低データモードの代理シグナルとして扱い、加えて「アプリ内に節約スイッチを用意して利用者自身に選ばせる」二段構えにするのが現実的です。OS の意思（従量制判定）とアプリの設定（明示スイッチ）を両方ポリシーに合流させます。

## 通信判定を一箇所に集約する

回線の判定を画面ごとに散らすと、必ず判断がばらつきます。回線情報を1つのポリシーに変換するレイヤーを作り、各画面はそのポリシーだけを見るようにします。

```typescript
// net/networkPolicy.ts
import NetInfo, { NetInfoState } from "@react-native-community/netinfo";

export type PrefetchLevel = "full" | "lite" | "off";
export type ImageQuality = "high" | "medium" | "low";

export interface NetworkPolicy {
  prefetch: PrefetchLevel;   // 先読みの強さ
  imageQuality: ImageQuality; // 取得する画質
  allowAutoplay: boolean;     // 動画・GIF の自動再生可否
}

// 回線状態 + アプリの節約設定 を 1 つのポリシーへ変換する
export function derivePolicy(
  state: NetInfoState,
  saverEnabled: boolean
): NetworkPolicy {
  // つながっていない
  if (!state.isConnected) {
    return { prefetch: "off", imageQuality: "low", allowAutoplay: false };
  }

  const expensive = !!(state.details as any)?.isConnectionExpensive;
  const gen = (state.details as any)?.cellularGeneration as string | undefined;
  const isSlowCellular = state.type === "cellular" && (gen === "2g" || gen === "3g");

  // 利用者が節約を選んでいる、または OS が従量制と判断、または低速
  if (saverEnabled || expensive || isSlowCellular) {
    return { prefetch: "off", imageQuality: "medium", allowAutoplay: false };
  }

  // 通常のモバイル（4g/5g・非従量制）
  if (state.type === "cellular") {
    return { prefetch: "lite", imageQuality: "high", allowAutoplay: false };
  }

  // Wi-Fi（非従量制）— 全力で先読み
  return { prefetch: "full", imageQuality: "high", allowAutoplay: true };
}
```

このポリシーを React のコンテキストで配ると、各画面は `useNetworkPolicy()` を読むだけで一貫した判断ができます。

```typescript
// net/NetworkPolicyProvider.tsx
import React, { createContext, useContext, useEffect, useState } from "react";
import NetInfo from "@react-native-community/netinfo";
import { derivePolicy, NetworkPolicy } from "./networkPolicy";
import { useDataSaver } from "../settings/useDataSaver"; // アプリ内の節約スイッチ

const Ctx = createContext<NetworkPolicy>({
  prefetch: "lite", imageQuality: "high", allowAutoplay: false,
});

export function NetworkPolicyProvider({ children }: { children: React.ReactNode }) {
  const saver = useDataSaver();
  const [policy, setPolicy] = useState<NetworkPolicy>(Ctx._currentValue);

  useEffect(() => {
    // 購読開始時に現在値を一度取得し、以後は変化を購読
    const unsub = NetInfo.addEventListener((state) => {
      setPolicy(derivePolicy(state, saver));
    });
    NetInfo.fetch().then((state) => setPolicy(derivePolicy(state, saver)));
    return () => unsub();
  }, [saver]);

  return <Ctx.Provider value={policy}>{children}</Ctx.Provider>;
}

export const useNetworkPolicy = () => useContext(Ctx);
```

ポイントは、節約スイッチ（`saver`）の変化も依存に入れることです。利用者が設定でスイッチを切り替えた瞬間にポリシーが再計算され、先読みの挙動が即座に追従します。

## ポリシーに従って先読みを段階化する

ポリシーができたら、一覧画面の先読みをそれに従わせます。全部先読みする・何もしない、の二択ではなく、`full / lite / off` の3段で振る舞いを変えます。

```typescript
// hooks/useAdaptivePrefetch.ts
import { Image } from "expo-image";
import { useNetworkPolicy } from "../net/NetworkPolicyProvider";

export function useAdaptivePrefetch() {
  const policy = useNetworkPolicy();

  // 表示中インデックスの「次に何枚先読みするか」をポリシーで決める
  const lookahead = policy.prefetch === "full" ? 12
    : policy.prefetch === "lite" ? 3
    : 0;

  return async (urls: string[], currentIndex: number) => {
    if (lookahead === 0) return; // off のときは先読みしない
    const slice = urls.slice(currentIndex + 1, currentIndex + 1 + lookahead);
    // 画質に応じて URL を差し替える（後述の variantUrl）
    const targets = slice.map((u) => variantUrl(u, policy.imageQuality));
    // expo-image のディスクキャッシュへ静かに先読み
    await Image.prefetch(targets, { cachePolicy: "disk" });
  };
}
```

画質の差し替えは、画像配信側がサイズ違いを返せる前提で URL を組み替えます。CDN のクエリでも、保存済みのバリアント名でも構いません。

```typescript
// net/variantUrl.ts
import { ImageQuality } from "./networkPolicy";

export function variantUrl(base: string, quality: ImageQuality): string {
  const width = quality === "high" ? 1080 : quality === "medium" ? 720 : 480;
  // 例: CDN のリサイズパラメータ。base 側に既存クエリがある場合は & で連結
  const sep = base.includes("?") ? "&" : "?";
  return `${base}${sep}w=${width}&q=${quality === "low" ? 60 : 80}`;
}
```

`FlatList` では、可視範囲が変わったタイミングで先読みを呼びます。`onViewableItemsChanged` から現在の先頭インデックスを取り、ポリシーが `off` なら何も起きません。

```typescript
const prefetchNext = useAdaptivePrefetch();

const onViewableItemsChanged = useRef(({ viewableItems }: any) => {
  const first = viewableItems[0]?.index ?? 0;
  prefetchNext(allUrls, first); // 内部でポリシーを参照
}).current;

// <FlatList ... onViewableItemsChanged={onViewableItemsChanged} />
```

## 表示そのものの画質もポリシーに合わせる

先読みだけでなく、実際に表示する画像もポリシーに従わせると一貫します。低データモードでは中画質を取得し、後から Wi-Fi に戻ったときに高画質へ差し替える、という運用も可能です。

```typescript
function AdaptiveImage({ base }: { base: string }) {
  const policy = useNetworkPolicy();
  return (
    <Image
      source={{ uri: variantUrl(base, policy.imageQuality) }}
      // 取得済みの低画質をすぐ見せ、高画質が来たら差し替える
      placeholder={{ uri: variantUrl(base, "low") }}
      transition={150}
      cachePolicy="disk"
    />
  );
}
```

## 導入の手順

既存の画面に後付けで組み込む場合は、次の順序で進めると安全です。私自身、個人開発の壁紙アプリへ適用したときもこの順で入れました。

1. 判定の集約レイヤー（`derivePolicy` と `NetworkPolicyProvider`）を先に入れ、まずはログ出力だけで現状の回線分布を観察します。
2. 一覧の先読みを `useAdaptivePrefetch` に置き換え、`off` のときに通信が止まることを実機の従量制回線で確認します。
3. 表示画像を `AdaptiveImage` に差し替え、低データモード設定での画質低下と、Wi-Fi 復帰後の高画質差し替えを確認します。

この順なら、各段で挙動を切り分けて確認でき、回避すべき「先読みが暴走したまま出荷する」落とし穴を踏みません。広告（AdMob）中心のアプリでも、通信の作法は App Store のレビュー評価に直結します。

## つまずきやすい点と本番運用での所感

実装してみて引っかかった点を共有します。まず、`isConnectionExpensive` はプラットフォームや OS バージョンで取得可否や精度に差があります。`undefined` のときに「従量制ではない」と決めつけると先読みが暴れるので、私は不明なときは安全側（`lite` 相当）に倒すようにしました。判定が取れないときこそ控えめに、が基本です。

次に、節約スイッチの存在を利用者に気づいてもらうことです。OS の判定だけに頼ると、Wi-Fi だがギガを気にしている、といった事情を拾えません。設定画面に「通信を控えめにする」スイッチを置き、初回起動の文脈でも軽く触れておくと、レビューでの不満が目に見えて減りました。

最後に、効果測定です。私はポリシーの分布（full / lite / off がそれぞれ何割で発動したか）と、先読みで実際に表示に間に合った率を記録しました。先読みを絞っても体感速度がほとんど落ちないことが数字で見えると、安心して節約側に寄せられます。広告中心の収益でも、通信量への配慮はレビュー評価を通じて長期の定着に効いてきます。

通信設計の要点は、回線を二値で見ないことに尽きます。従量制と低データモードを尊重するだけで、利用者の財布と信頼を同時に守れます。まずは判定の集約レイヤーから作ってみてください。
