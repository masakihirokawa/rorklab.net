iOS のシミュレータではウィジェットがきちんと並んでいるのに、`npx expo run:android` を叩いた途端、Kotlin のエラーが画面を埋めます。触ったのは依存の版を一つ上げたことだけで、昨日まで通っていたビルドが止まっている——そういう朝に、この記事を開いてくださった方が多いのだと思います。

最初にお伝えしたいのは、この不具合は **expo-widgets 58.0.20 で直っている** ということです。影響を受けるのは 58.0.17・58.0.18・58.0.19 の3つの版だけで、2026年11月18日時点の最新は 58.0.29 です。いまから対処する方は、まず版を上げるところから始めていただければ足ります。

それでも「上げたのに落ちる」という声は、たいてい版そのものではなく、手元に残った古い設定やキャッシュが原因です。ここからは、壊れている版の見分け方、上げても直らないときの切り分け、そして以前の回避策（版の固定・autolinking 除外）を外す手順を、順に辿ります。

## このエラーが出ていたら、この件を疑ってください

Kotlin のコンパイルで、次のような行が `CustomNotificationBuilder.kt` や `CustomNotificationRenderer.kt` から出ていれば、ほぼこの件です。

```text
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationBuilder.kt:17:18 Unresolved reference 'jakex7'.
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationBuilder.kt:30:12 Unresolved reference 'PeekNotificationViews'.
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationBuilder.kt:36:8 Unresolved reference 'setPeekContent'.
e: .../expo-widgets/android/src/main/java/expo/modules/widgets/notifications/CustomNotificationRenderer.kt:11:18 Unresolved reference 'jakex7'.
```

上は expo/expo の Issue #51653 に貼られた出力からの抜粋で、報告者は新規の `create-expo-app` に `npx expo install expo-widgets`（当時は 58.0.18）を足しただけで再現しています。アプリ側のコードをいくら見ても原因は出てきません。**パッケージの特定の版が、Android でだけ存在しない部品を参照している** のです。

原因は名前の食い違いでした。58.0.17 で Android 向けのカスタム通知が加わった際、新しいコードは `io.github.jakex7.peek` を import していましたが、`build.gradle` が取り込んでいるのは `io.github.expo.peek:peek-emittables` のほうでした。参照先の部品が依存に存在しないため、コンパイルの段階で止まります。iOS には関係しないので、iOS だけで確かめていると気づけません。

58.0.20 の変更履歴（CHANGELOG.md）には、この修正と並んで「expo-widgets を使う Android アプリが起動時に `constructor cannot be null` で落ちる」不具合の修正も書かれています。ビルドは通ったのに起動直後に落ちる、という形で同じ時期の版に当たった方も、上げれば両方が解消します。

あわせて確かめると、`expo@58.0.26` が同梱する推奨版の一覧（bundledNativeModules.json）では、expo-widgets は `~58.0.29` になっていました。SDK 58 の推奨どおりに入れれば、壊れた範囲には入りません。

## 直し方：推奨版まで上げる

範囲を自分で書くより、SDK に合う版を Expo CLI に選んでもらうのが確実です。

```bash
npx expo install expo-widgets
npx expo install --check        # 他のパッケージも推奨からずれていないかを確認
```

そのうえで、実際に入った版を `node_modules` から確かめます。`package.json` の記述ではなく、こちらが正解です。

```bash
node -p "require('expo-widgets/package.json').version"
# 58.0.29 のように 58.0.20 以上なら修正済み
```

ネイティブの `android` フォルダを生成して使っている場合は、作り直してからビルドします。

```bash
npx expo prebuild -p android --clean
cd android && ./gradlew :expo-widgets:compileDebugKotlin
```

`--clean` は既存の `android` フォルダを消してから作り直します。ネイティブ側を手で書き換えている場合は、先に退避しておいてください。EAS Build だけを使っていて手元に `android` フォルダがない方は、この手順は不要です。

## 以前の回避策を外す（固定・除外を元に戻す）

この記事を最初に書いた10月20日、私は Issue のページで状態を見て「まだ Open」と書き、58.0.16 への固定と Android からの除外を2つの逃げ道としてご紹介しました。実際には、Issue は起票した当日に閉じられ、同じ日に 58.0.20 が公開されていました。Issue の一覧画面の表示と、配布物の中身を突き合わせなかった——これが私の見落としです。読んでくださった方の手元に回避策が残っているかもしれないと思うと、胃のあたりが重くなりました。

そこから引いた線引きは一つです。**Issue の開閉ではなく、node_modules に入った版の中身で判断します。** 以来、依存の不具合を記事に書くときは、変更履歴と配布物の両方を見てから書くようにしております。

固定と除外を外す手順は次のとおりです。

1. `package.json` の `expo.autolinking.android.exclude` に `expo-widgets` があれば外します（配列が空になるなら `autolinking` ごと削除してかまいません）
2. `npx expo install expo-widgets` を実行し、`"58.0.16"` の固定を推奨範囲（`~58.0.29` など）に戻します
3. `npx expo prebuild -p android --clean` で Android 側を作り直します
4. Android 側でウィジェットの関数を `Platform.OS` で避けていた分岐があれば、残すかどうかを決め直します

除外していたあいだ、Android ではウィジェットそのものが組み込まれていませんでした。外したあとは、Android 実機でホーム画面にウィジェットを置けるところまで一度確かめておくと安心です。

判断の基準を一文で言えば、**Android でウィジェットを出すなら上げる、出さないなら除外、固定は期限つきの一時退避** です。私の壁紙アプリでも、ウィジェットは iOS 側の付加機能として始めましたが、除外は「出さない」と決めた場合の設定であって、不具合よけの道具として長く置くものではないと感じています。

## よくある誤解を3つ

- **「Issue が閉じたから、自分のアプリも直っている」**：閉じたのは上流のコードで、手元の lockfile が 58.0.17〜19 を指していれば何も変わりません。確かめるのは `node_modules` の版です
- **「58.0.16 は安全な版だから、固定しておけば安心」**：この件については影響なしですが、その後の 58.0.20〜58.0.29 で入った Android 側の修正（起動時のクラッシュ、WorkManager の更新、Peek 0.3.3 への更新など）を受け取れなくなります
- **「除外は副作用のない回避策」**：除外は Android のビルドから expo-widgets を丸ごと外す設定です。エラーが消えるのは、ウィジェットが消えたからです

## 自分のプロジェクトを数秒で判定するスクリプト

`package.json` と `node_modules` を毎回見比べるのは手間なので、判定だけを行う小さなスクリプトを置いておきます。以前の版から、壊れた範囲を 58.0.17〜58.0.19 に絞り、固定や除外が「残っている」ことも知らせるように直しました。Node だけで動き、ネットワークには接続しません。

```js
// check-expo-widgets-android.mjs
// 使い方: node check-expo-widgets-android.mjs [プロジェクトのパス]
import { readFileSync, existsSync } from "node:fs";
import { join, resolve } from "node:path";

const root = resolve(process.argv[2] ?? ".");
const readJson = (p) => JSON.parse(readFileSync(p, "utf8"));

const pkgPath = join(root, "package.json");
if (!existsSync(pkgPath)) {
  console.error(`package.json が見つかりません: ${pkgPath}`);
  process.exit(2);
}
const pkg = readJson(pkgPath);
const declared = { ...pkg.dependencies, ...pkg.devDependencies }["expo-widgets"];
if (!declared) {
  console.log("expo-widgets は依存に入っていません。この件の対象外です。");
  process.exit(0);
}

const installedPath = join(root, "node_modules", "expo-widgets", "package.json");
if (!existsSync(installedPath)) {
  console.error("node_modules に expo-widgets がありません。先に npm install を実行してください。");
  process.exit(2);
}
const installed = readJson(installedPath).version;
const [major, minor, patch] = installed.split(/[.-]/).map(Number);

const excluded = (pkg.expo?.autolinking?.android?.exclude ?? []).includes("expo-widgets");
const pinned = /^\d+\.\d+\.\d+$/.test(declared); // ^ や ~ がなければ固定
const broken = major === 58 && minor === 0 && patch >= 17 && patch <= 19;
const old = major === 58 && minor === 0 && patch <= 16;

console.log(`宣言: ${declared}（${pinned ? "固定" : "範囲指定"}）`);
console.log(`導入済み: ${installed}`);
console.log(`Android の autolinking から除外: ${excluded ? "はい" : "いいえ"}`);

const notes = [];
if (broken) notes.push("要対処: 58.0.17〜58.0.19 は Android のビルドが止まります。npx expo install expo-widgets で 58.0.20 以上へ");
if (excluded) notes.push("確認: 除外が残っています。Android でウィジェットを出すなら exclude から外してください");
if (old && pinned) notes.push("確認: 58.0.16 以前に固定されています。一時退避のつもりなら推奨範囲へ戻してください");

if (notes.length === 0) {
  console.log("判定: OK（この件の影響はありません）");
  process.exit(0);
}
notes.forEach((n) => console.log(`判定: ${n}`));
process.exit(broken ? 1 : 3);
```

終了コードは、問題なしが 0、壊れた範囲が 1、前提が足りないときが 2、回避策の残りがあるときが 3 です。CI の最初の手順に置けば、依存の自動更新や lockfile の取り違えで壊れた版が戻ってきても、Gradle を回す前の数秒で止められます。

確かめた範囲を書いておきます。私はこのスクリプトを、58.0.18・58.0.20・58.0.16 固定・58.0.29 かつ除外ありの4つの模擬プロジェクト（`package.json` と `node_modules/expo-widgets/package.json` だけを置いたもの）で動かし、終了コードが 1・0・3・3 になることを確認しました。実際のアプリでの Gradle ビルドは、私の手元では確かめていません。

## 次に当たりやすい壁：Android では時刻で切り替わらない

ビルドが通ってウィジェットが出たあと、多くの方が次に当たるのが「時刻で表示が変わらない」問題です。こちらは不具合ではなく、2026年11月18日時点の仕様です。

- `updateTimeline()` は型定義に `@platform ios` と書かれており、Android では何もしません
- 最新の 58.0.29 でも、Android のウィジェット定義を作る config plugin は `android:updatePeriodMillis="0"` を書き出します
- 報告の Issue #51633 は Open のままで、Expo 側の自動調査では「機能要望（現状は想定どおりの動作）」と分類され、ドキュメントにこの点を明記する PR #51697 が出ています（11月18日時点で未マージ）

つまり Android では、アプリが動いているあいだに `updateSnapshot()` を呼んだときだけ表示が変わります。毎朝0時に切り替わる壁紙ウィジェットのような設計は、いまの expo-widgets だけでは組めません。回避の設計は [iOS では時刻どおりに変わるウィジェットが、Android では「Initial」のまま動かない](/articles/rork-dev/expo-widgets-android-update-timeline-no-op-widget-stays-initial) に書きました。

また、Expo のパッチは短い間隔で出ます。自分のアプリにいまどの版が入っているかを定期的に確かめる方法は [30日で9回出た Expo のパッチのうち、自分のアプリに入っているのはどれかを確かめる](/articles/rork-basics/expo-patch-cadence-which-version-your-app-actually-has) に、`expo install` の推奨がパッチごとにどれだけ動くかは [expo のパッチを1つ上げると、expo install の推奨が何個動くのかを数えました](/articles/rork-dev/expo-install-bundled-native-modules-patch-drift-audit) にまとめています。Android のビルドがキャッシュ由来に見える場合は、[EAS Build だけ「No matching variant」で落ちるとき、まず疑う手元の android/build](/articles/app-dev/eas-build-no-matching-variant-stale-windows-autolinking-cache) もあわせてご覧ください。

## 今日やること

まずはプロジェクトの直下で `node -p "require('expo-widgets/package.json').version"` を一度だけ実行し、表示が 58.0.20 以上かを見ていただければと思います。そこが 58.0.17〜58.0.19 なら上げる、それ以外で固定や除外が残っていれば外す——判断はそれだけで済みます。依存の不具合を書くときに中身まで見る、という線引きは、私もこれからも守っていくつもりです。
