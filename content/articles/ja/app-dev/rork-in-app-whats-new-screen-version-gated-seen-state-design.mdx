新機能を入れても気づかれない、という壁に個人開発で何度もぶつかってきました。App Store の「このバージョンの新機能」欄はほとんど読まれませんし、プッシュ通知は許可していない人には届きません。残る確実な接点は、更新後に最初に開いたその瞬間の画面です。リテンションに効く機能ほど、ここで気づいてもらえるかどうかが効いてきます。

ところがこの「新着情報」画面は、作り方を一つ間違えると一気に嫌われます。インストールしたばかりの人にまで「新機能のお知らせ」が出る、開くたびに同じ案内が出る、こうなると体験を損ねるだけです。これは私自身が初期に踏んだ落とし穴でもあります。境界を正しく引いて「更新した人に、一度だけ」を成立させる設計をまとめます。

## 「更新した人にだけ」をどう判定するか

判定に必要なのは二つの値です。いま動いているアプリの「現在バージョン」と、このユーザーが「前回どのバージョンを使っていたか」。後者を毎回保存しておき、起動時に前者と突き合わせます。

- 保存値が無い → 新規インストール。新着情報は出さない。
- 保存値 < 現在 → 更新された。新着情報を出す候補。
- 保存値 = 現在 → 同じバージョンで再起動しただけ。出さない。

現在バージョンは `expo-application` から取得します。`app.json` の `version` を手で持ち回るより確実です。

```ts
// lib/appVersion.ts
import * as Application from "expo-application";

// "1.4.0" のような表示用バージョン。null になり得るのでフォールバックを置く。
export const CURRENT_VERSION = Application.nativeApplicationVersion ?? "0.0.0";

// 文字列バージョンを比較可能な配列にする素朴なセムバー比較。
export function isNewer(a: string, b: string): boolean {
  const pa = a.split(".").map((n) => parseInt(n, 10) || 0);
  const pb = b.split(".").map((n) => parseInt(n, 10) || 0);
  for (let i = 0; i < Math.max(pa.length, pb.length); i++) {
    const x = pa[i] ?? 0;
    const y = pb[i] ?? 0;
    if (x !== y) return x > y;
  }
  return false;
}
```

## 前回バージョンの記録と判定をまとめる

判定ロジックは小さな関数一つに閉じ込めます。ここで大事なのは「新着情報を出すか」と「前回バージョンを更新するか」を分けて考えることです。前回バージョンの保存は、新着情報を出したかどうかに関わらず、必ず行います。さもないと、新着情報のデータがまだ無い更新でも、次の本命の更新時に「2バージョン分まとめて」案内が出てしまいます。これが見落としやすい注意点です。

```ts
// lib/whatsNew.ts
import AsyncStorage from "@react-native-async-storage/async-storage";
import { CURRENT_VERSION, isNewer } from "./appVersion";

const LAST_VERSION_KEY = "whatsNew.lastVersion";

export type WhatsNewDecision =
  | { show: false }
  | { show: true; fromVersion: string; toVersion: string };

export async function evaluateWhatsNew(): Promise<WhatsNewDecision> {
  const last = await AsyncStorage.getItem(LAST_VERSION_KEY);

  // 前回バージョンは常に最新へ更新する（判定の後始末を先に確定）。
  const persist = () =>
    AsyncStorage.setItem(LAST_VERSION_KEY, CURRENT_VERSION);

  // 新規インストール: 記録だけ残して何も出さない。
  if (!last) {
    await persist();
    return { show: false };
  }

  // 同一 or 何らかの理由で現在が古い: 出さない。
  if (!isNewer(CURRENT_VERSION, last)) {
    await persist();
    return { show: false };
  }

  // 更新された: 出す候補。fromVersion を呼び出し側に渡す。
  const decision: WhatsNewDecision = {
    show: true,
    fromVersion: last,
    toVersion: CURRENT_VERSION,
  };
  await persist();
  return decision;
}
```

新規インストールで `persist()` だけして `show: false` を返すのが肝です。これで初回は静かに記録だけ取り、次回以降の更新から正しく一度だけ出せます。この挙動は実機の新規インストールで必ず確認することを推奨します。

## 表示するデータをバージョンに紐づける

新着情報の本文は、バージョンをキーにしたデータとしてアプリ内に持ちます。ネットワークに依存させないことで、オフラインでも更新直後に必ず表示できます。`fromVersion` より新しいエントリだけを並べると、2バージョン飛ばして更新した人にも、その間の変更をまとめて見せられます。

```ts
// data/whatsNew.ts
export type WhatsNewEntry = {
  version: string;
  items: string[]; // この更新で変わったことを2〜4個まで
};

// 新しい順でなくてよい。表示時にソートする。
export const WHATS_NEW: WhatsNewEntry[] = [
  { version: "1.4.0", items: ["お気に入りの並び替えに対応しました", "ウィジェットの更新が速くなりました"] },
  { version: "1.3.0", items: ["ダークモードの配色を調整しました"] },
];

export function entriesSince(from: string, isNewer: (a: string, b: string) => boolean) {
  return WHATS_NEW
    .filter((e) => isNewer(e.version, from)) // from より新しいものだけ
    .sort((a, b) => (isNewer(a.version, b.version) ? -1 : 1));
}
```

エントリが空のときは、たとえバージョンが上がっていても画面を出さないようにします。内部的なバグ修正だけの更新で「新着情報」を出しても、ユーザーには中身がなく、かえって不信感につながります。項目は2〜4個に絞り、ユーザーから見て体験が変わったことだけを、誇張しない言葉で書きます。

## 起動フローのどこに差し込むか

新着情報は、オンボーディングや同意系の表示と競合します。優先順位を明確にして、同じ起動で複数のモーダルが重ならないようにします。これを怠ると、更新直後に許可ダイアログと新機能案内が連続で出る本番事故につながります。その対処が次の優先順位表です。

<table>
  <thead>
    <tr><th>状況</th><th>出すもの</th></tr>
  </thead>
  <tbody>
    <tr><td>新規インストール初回</td><td>オンボーディングのみ（新着情報は出さない）</td></tr>
    <tr><td>更新後の初回起動</td><td>新着情報（中身がある場合のみ）</td></tr>
    <tr><td>同意・権限が未取得</td><td>同意系を優先し、新着情報は次回へ送る</td></tr>
    <tr><td>同一バージョンで再起動</td><td>何も出さない</td></tr>
  </tbody>
</table>

```ts
// App 起動時の組み立て例
import { evaluateWhatsNew } from "./lib/whatsNew";
import { entriesSince } from "./data/whatsNew";
import { isNewer } from "./lib/appVersion";

async function decideStartupModal() {
  if (await hasPendingConsent()) return { type: "consent" }; // 同意系が最優先
  const d = await evaluateWhatsNew();
  if (d.show) {
    const items = entriesSince(d.fromVersion, isNewer);
    if (items.length > 0) return { type: "whatsNew", items }; // 中身がある時だけ
  }
  return { type: "none" };
}
```

同意系を先に通し、新着情報は中身があるときだけ出す。この二段の門があるだけで、「更新したらいきなり許可ダイアログと新機能案内が連続で出てうんざりした」という事故を避けられます。

## 複数アプリで使い回す

私は壁紙系のアプリを6本ほど並行で運用しているため、新着情報のためだけに各アプリのコードを毎回触るのは現実的ではありません。判定ロジック（`whatsNew.ts` と `appVersion.ts`）は共通モジュールとして全アプリで共有し、変わるのは `data/whatsNew.ts` の文面だけにしています。個人的にはこの「ロジックは共通・文面だけ差し替え」の形を強く推奨します。

文面データはアプリごとに別ファイルですが、書式（`version` と `items` の形）を完全にそろえておくと、リリース時に「今回の更新で変わったこと」を各アプリのデータへ流し込むだけで済みます。App Store の「このバージョンの新機能」欄と、アプリ内の新着情報を同じ原稿から生成するようにしておくと、表現のぶれもなくなります。

## 見られたかどうかを後で活かす

もう一歩進めるなら、新着情報を実際に表示した事実も記録しておくと、次の設計判断に使えます。たとえば「更新したのに新機能タブを一度も開いていない人にだけ、控えめな一行バナーで再案内する」といった出し分けが、`whatsNew.lastVersion` と同じ仕組みの延長で組めます。仕組みを一度共通化しておくと、機能追加のたびに「気づかれないかもしれない」という不安が減り、作ったものをきちんと届けられるようになります。

導入は次の順で進めると安全です。

1. `appVersion.ts` で現在バージョンを取り、`evaluateWhatsNew` を一つ立てる。
2. 新規インストールと更新初回の挙動を実機で確認する。
3. `data/whatsNew.ts` に1バージョン分の文面を入れ、起動フローへ差し込む。

まずはこの一関数と、バージョン1件分の文面から始めてみてください。次のアップデートで、更新した人にだけ静かに一度、新機能が届くようになります。お読みいただきありがとうございました。
