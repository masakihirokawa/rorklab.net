壁紙アプリのスクリーンショットを差し替えようとして、書き出したばかりの PNG を App Store Connect にドラッグした夕方のことです。画面の端に赤い文字が出て、受け付けてもらえませんでした。Figma の画面ではきれいに見えていたのに、ファイルの寸法は要求の 2 倍になっていたのです。書き出し設定の「2x」を、前の作業のまま残していたのが原因でした。

同じ週に、今度は Google Play 側で別の理由で止まりました。App Store 用に作った縦長の画像を使い回そうとしたところ、縦横比の条件に合わなかったのです。どちらも、デザインの良し悪しとは関係のないところで手が止まっていました。原因がいつも同じ種類の確認漏れだと気づいたのは、似た失敗を何度か重ねたあとでした。

最初にお伝えしたいのは、**スクリーンショット作りで時間を失うのは、デザインよりも「寸法・透過・倍率」の三つ**だということです。ここからは、Figma の母艦フレーム 1 つから両ストア分を書き出す組み方と、書き出した直後に機械で検査する手順を、私が実際に回している順番で書き残します。

## この記事で持ち帰っていただきたいこと

- 両ストアで同じ画像が通らない理由と、母艦フレームの寸法の決め方
- 弾かれたときに、どこを疑えばよいかの切り分け表
- 言語を増やしても崩れない Figma の組み方（Auto Layout と文字列変数）
- 書き出したファイルの寸法とアルファを、アップロード前に検査するスクリプト

## まず寸法を決めます — 両ストアの条件は「似ているようで違う」

寸法の数字は、書き写した瞬間から古くなり始めます。以下は 2026 年 11 月時点で、各ストアの公式ヘルプに沿って整理したものです。作業の当日にも、公式ページと App Store Connect の画面で必ず確かめていただければと思います。

### App Store の受け付けサイズ

[App Store Connect のスクリーンショット仕様](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications)では、端末の画面サイズごとに受け付ける寸法が列挙されています。母艦にするのは、いちばん大きい区分です。

<thead>
<tr><th>区分</th><th>受け付ける寸法（縦向き・px）</th><th>母艦にするか</th></tr>
</thead>
<tbody>
<tr><td>iPhone 6.9 インチ</td><td>1320 × 2868／1290 × 2796／1260 × 2736</td><td>1320 × 2868 を母艦にします</td></tr>
<tr><td>iPad 13 インチ</td><td>2064 × 2752／2048 × 2732</td><td>iPad 対応アプリのときだけ別の母艦を作ります</td></tr>
<tr><td>より小さい iPhone・iPad の区分</td><td>公式ページの表を参照</td><td>UI が同じなら作りません（大きい区分から縮小されます）</td></tr>
</tbody>
</table>

ほかに押さえておきたい条件は次の三つです。

- 1 つの区分につき、アップロードできるのは 10 枚までです
- 形式は JPEG・JPG・PNG で、アルファチャンネル（透過）は含められません
- UI が端末や言語で変わらないなら、大きい区分の 1 セットで足ります。小さい端末向けは App Store Connect が縮小して表示します

どの区分が「必須」として表示されるかは、アプリの対応端末によって App Store Connect のメディアマネージャー側で変わります。表の数字よりも、提出画面に出ている必須欄を正としてください。

### Google Play の受け付けサイズ

[Play Console ヘルプ（プレビュー アセットの追加）](https://support.google.com/googleplay/android-developer/answer/9866151)の条件は、寸法の自由度が高いかわりに、縦横比に上限があります。

ファイルサイズの上限は、確認したページのスマートフォン向けの記載には見当たりませんでした。書かれていない数字を決め打ちせず、アップロード時の警告を目安にしています。

### 同じ画像を両方に使い回せない理由

ここが、私がいちばん長く見落としていた点です。比率の条件は表の最後の行に小さく書かれているので、読み飛ばしやすいのかもしれません。App Store の 1320 × 2868 は、長辺が短辺の約 2.17 倍あります。Google Play は「長辺は短辺の 2 倍まで」なので、**App Store 用の書き出しをそのまま Google Play に上げることはできません**。

そこで母艦は二つに分けます。

<table>
<thead>
<tr><th>母艦</th><th>寸法</th><th>比率</th><th>使う場所</th></tr>
</thead>
<tbody>
<tr><td>appstore</td><td>1320 × 2868</td><td>約 1:2.17</td><td>App Store（iPhone）</td></tr>
<tr><td>play</td><td>1080 × 1920</td><td>9:16</td><td>Google Play（スマートフォン）。おすすめ枠の条件にも合います</td></tr>
</tbody>
</table>

二つの母艦は、同じコンポーネント（見出し・端末の枠・背景）を共有させます。縦の余白だけが違う、という状態にしておけば、直すのは常にコンポーネント側の一か所で済みます。

## Figma に母艦を組みます

### ページとフレームの切り分け

ページは用途で分けておくと、言語が増えても迷いません。

- Components：見出し、端末の枠、背景、バッジを置きます
- Master：appstore と play の母艦フレームを置きます
- Export：書き出し専用のフレームを、言語ごと・連番ごとに置きます

フレーム名は `appstore_1320x2868_ja_01`、`play_1080x1920_en_03` のように、媒体・寸法・言語・連番の順に並べます。Figma の書き出しはフレーム名をそのままファイル名にするので、あとで検査スクリプトが媒体を読み取る手がかりにもなります。

### 端末の枠は「置くだけ」にします

端末の枠を作るプラグインは便利ですが、機種の世代が変わると画面領域の寸法も変わります。枠の中に実機のスクリーンショットを貼ったとき、上下に細い隙間ができたら、まず寸法の取り違えを疑うのがいちばん早い見つけ方です。

アプリの画面は、実機かシミュレータで撮ったものを貼ります。Rork で作ったアプリでも同じで、撮った PNG を枠の中に収めるだけです。ストアの審査は、実際のアプリと違う画面を載せることを嫌います。作り込んだモックではなく、実際の画面を使うほうが安全です。

### 文字は「いちばん長い言語」から逆算します

見出しは画面上部の 20〜30% に置く構成が扱いやすいです。1320 px 幅の母艦なら、見出し 64〜80 px、補足 36〜44 px あたりから試し、実機の小さな画面で読めるかを確かめて決めます。

日本語を基準にすると、英語は 1.2〜1.3 倍、ドイツ語は 1.5 倍を超えることが珍しくありません。私は最初のうち、日本語で整えたレイアウトに英語を流し込み、見出しが 4 行にあふれて組み直す、という手戻りを何度も繰り返しました。いまは**いちばん長い言語の訳文を先に母艦へ流し込み、そこに収まる幅で全体を設計する**ようにしています。

見出しのテキストは Auto Layout の中に入れ、行数が増えたら背景の帯ごと伸びるようにしておきます。訳文が届いたあとの調整が、ほとんど要らなくなります。

### 文字列変数で言語を切り替える

言語ごとにページを複製してテキストを打ち替えるやり方は、言語が三つを超えたあたりで管理しきれなくなりました。いまは Figma の**変数（Variables）の文字列型**を使っています。

1. ローカル変数のパネルで「copy」というコレクションを作ります
2. モードを言語ごとに追加します（ja、en、de……）
3. `headline_01`、`sub_01` のような文字列変数を作り、モードごとに訳文を入れます
4. 母艦の見出しテキストを選び、テキストの内容に変数を割り当てます
5. Export ページのフレームごとに、変数のモードを切り替えます

こうしておくと、訳文の修正は変数のパネルで一か所を直すだけになり、全フレームに反映されます。モードの数はプランごとに上限があり、その数字は今回確認しきれていません。[Figma ヘルプの「Modes for variables」](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)でご自身のプランの上限を確かめていただければ幸いです。上限を超える場合は、ページの複製と組み合わせるのが現実的です。

## 書き出し設定 — PNG か JPG か、1x か 2x か

書き出しで迷う選択肢は、実質この二つだけです。

<table>
<thead>
<tr><th>選択</th><th>向いている場面</th><th>気をつける点</th></tr>
</thead>
<tbody>
<tr><td>PNG・1x</td><td>文字や UI の輪郭を劣化させたくないとき（基本はこちら）</td><td>フレームに塗りがないと透過のまま書き出されます</td></tr>
<tr><td>JPG・1x</td><td>写真や壁紙が主役で、ファイルを軽くしたいとき</td><td>透過は持てないので、アルファで弾かれる心配はありません。細い文字の周りに滲みが出ることがあります</td></tr>
<tr><td>2x・3x</td><td>使いません</td><td>母艦の寸法がすでに要求サイズなので、倍率を掛けると要求外になります</td></tr>
</tbody>
</table>

判断の基準は一文で足ります。**UI と文字が主役なら PNG・1x、写真が主役で文字が太いなら JPG・1x** です。私の壁紙アプリでは画像が主役なので JPG を使うこともありますが、見出しの細い文字に滲みが出た回は PNG に戻しました。

## 書き出した直後に、機械で検査します

ここからが、私がいちばん時間を取り戻せた部分です。アルファチャンネルの有無は、画面で見ても判別できません。寸法の 2 倍違いも、サムネイルでは気づけません。そこで、アップロードの前に必ず次のスクリプトを通しています。

**何を解決するか**: Export フォルダの全ファイルについて、媒体ごとの寸法・縦横比とアルファの有無を一度に確かめます。

```python
#!/usr/bin/env python3
"""書き出したスクリーンショットを、ストアに上げる前に検査する。
使い方: python3 check_shots.py export/*.png
ファイル名の先頭で媒体を判定する（appstore_ / play_）。"""
import sys
from pathlib import Path
from PIL import Image

APPSTORE_SIZES = {  # (幅, 高さ) 縦向き。横向きは入れ替えて判定
    (1320, 2868), (1290, 2796), (1260, 2736),   # iPhone 6.9 インチ
    (2064, 2752), (2048, 2732),                 # iPad 13 インチ
}

def check(path: Path) -> list[str]:
    errors = []
    with Image.open(path) as im:
        w, h = im.size
        has_alpha = im.mode in ("RGBA", "LA") or "transparency" in im.info
    if has_alpha:
        errors.append("アルファチャンネルあり（背景を塗って書き出し直す）")
    name = path.name
    if name.startswith("appstore_"):
        if (w, h) not in APPSTORE_SIZES and (h, w) not in APPSTORE_SIZES:
            errors.append(f"App Store の受け付けサイズ外: {w}x{h}")
    elif name.startswith("play_"):
        short, long_ = sorted((w, h))
        if short < 320 or long_ > 3840:
            errors.append(f"Google Play の寸法範囲外: {w}x{h}")
        if long_ > short * 2:
            errors.append(f"Google Play の縦横比超過（長辺が短辺の2倍超）: {w}x{h}")
    else:
        errors.append("ファイル名の先頭が appstore_ / play_ ではない")
    return errors

if __name__ == "__main__":
    failed = 0
    for arg in sys.argv[1:]:
        p = Path(arg)
        errs = check(p)
        print(("NG " if errs else "OK ") + p.name + ("" if not errs else " — " + " / ".join(errs)))
        failed += bool(errs)
    sys.exit(1 if failed else 0)
```

Pillow が入っていなければ、先に `python3 -m pip install pillow` を実行します。Python 3.10・Pillow 12.3 の環境で、わざと失敗するファイルを混ぜて走らせた結果がこちらです。

```text
$ python3 check_shots.py export/*.png
NG appstore_1320x2868_en_01.png — アルファチャンネルあり（背景を塗って書き出し直す）
OK appstore_1320x2868_ja_01.png
NG appstore_1320x2868_ja_02.png — App Store の受け付けサイズ外: 2640x5736
OK play_1080x1920_ja_01.png
NG play_1320x2868_ja_01.png — Google Play の縦横比超過（長辺が短辺の2倍超）: 1320x2868
```

2 行目の NG は 2x で書き出したもの、最後の NG は App Store 用の母艦を Google Play に流用したものです。冒頭でお話しした二つの失敗が、そのまま並んでいます。

**なぜこう書くか**: 判定をファイル名の先頭に寄せたのは、Figma のフレーム名がそのままファイル名になるからです。命名の規則を守るだけで、検査の設定を別に持たずに済みます。また、NG が 1 件でもあれば終了コードが 1 になるので、書き出しフォルダを同期する前のシェルスクリプトに組み込むこともできます。

透過が残っていたときは、Figma に戻って母艦フレームに塗りを入れて書き出し直すのが本筋です。急ぐときは、次のスクリプトで背景色を合成して不透明にしています。

```python
#!/usr/bin/env python3
"""透過 PNG を、指定色の背景に合成して不透明 PNG に直す。
使い方: python3 fix_alpha.py export/appstore_*.png --bg "#FFFFFF" """
import sys
from PIL import Image
args = sys.argv[1:]
bg = "#FFFFFF"
if "--bg" in args:
    i = args.index("--bg"); bg = args[i + 1]; del args[i:i + 2]
for path in args:
    im = Image.open(path)
    if im.mode in ("RGBA", "LA") or "transparency" in im.info:
        rgba = im.convert("RGBA")
        base = Image.new("RGB", rgba.size, bg)
        base.paste(rgba, mask=rgba.split()[3])
        base.save(path)
        print("fixed", path)
```

```text
$ python3 fix_alpha.py export/appstore_1320x2868_en_01.png
fixed export/appstore_1320x2868_en_01.png
$ python3 check_shots.py export/appstore_1320x2868_en_01.png
OK appstore_1320x2868_en_01.png
```

なお、このスクリプトは画像のモードで判定しているので、見た目は不透明でもアルファの層を持つ PNG は NG になります。ストア側もアルファチャンネルの有無で判定するので、厳しめに倒しています。

## よくある誤解

**「端末サイズごとに全部用意しないといけない」**——いまの App Store は、UI が同じなら大きい区分の 1 セットで足ります。小さい区分を作るのは、端末ごとに見せ方が違うときだけです（公式の仕様ページに、大きい区分から縮小される旨の記載があります）。

**「1 枚で両ストアに使える寸法がある」**——App Store の iPhone 6.9 インチの寸法は、どれも長辺が短辺の 2 倍を超えます。Google Play の縦横比の条件と両立しないので、母艦は二つに分けるのが確実です。

**「Retina 向けに 2x で書き出すべき」**——ストアの要求サイズはすでに実ピクセルの数字です。母艦をその寸法で作っていれば、倍率は 1x が正解です。

## 次に詰まりやすいところ

スクリーンショットが通ると、提出画面で次に止まりやすいのは、アプリ本体の審査です。リリースビルドで白い画面が出て差し戻される例は多いので、[App Review で「Guideline 2.1・白い画面」と言われたときに疑う 3 か所](/articles/app-dev/app-review-guideline-2-1-blank-screen-expo-release-build-checklist)を先に読んでおくと、提出の往復が減ります。

スクリーンショットやアイコンに AI で作った画像を使う場合は、[出どころの台帳と 4 つの確認](/articles/rork-ai/ai-generated-app-icon-image-ledger-four-checks-before-store-submit)を済ませてからのほうが安心です。Apple 側の手続きがまだの方は、[Rork のアプリを公開する前に Apple 側で自分が済ませておく手続き](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)も合わせてご覧ください。

## 結びに

デザインに時間をかけたぶんだけ、寸法や透過のような単純な理由で止まると、胸のあたりが重くなります。だからこそ、単純な確認ほど人の目ではなく機械に任せるようにしました。

**見た目は私が決め、寸法と透過はスクリプトに確かめてもらいます。** この分担にしてから、提出の日に慌てることはほとんどなくなりました。

まずは、いま手元にある書き出しフォルダに check_shots.py を一度走らせてみていただければと思います。NG が出なければ、それだけで次の提出の不安が一つ減ります。
