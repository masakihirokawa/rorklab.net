去年の9月、正式版が配られた翌日にレビュー欄の空気が変わりました。書かれていたのは「落ちる」ではなく、「上の文字がバーに重なっている」「下のボタンが押しづらい」という見た目の話でした。

こちらのコードは1行も変わっていません。変わったのは、ユーザーの端末のほうでした。

個人開発でアプリを何本か抱えていると、新しい OS が出た直後の数日は妙に落ち着きません。私はこの数年、予備の iPhone を1台だけ検証機として切り離して、自分のアプリを一通り触るようにしています。Mac も Xcode も使わない、地味な手順です。

最初にお伝えしたいのは、**新しい OS で確かめるべきなのは開発中のビルドではなく、いまストアに並んでいる版だ**ということです。この記事はそのための段取りを、見る順番・切り分け方・直し方の順に書き残します。

27.1 が一般の端末に来ない、という並びは私も最初は戸惑いました。予備機の「ソフトウェアアップデート」を何度開いても 27.1 が出てこず、端末側の不具合を疑ってしまったのです。版の番号が飛ぶ年もある、と頭に入れておくと、余計な回り道をせずに済みます。

## 正式版のあとに残る時間差を、正しく数える

正式版が公開されると、ユーザーの端末は数日のうちに新しい OS へ入れ替わっていきます。一方でこちらの修正版は、書き直して、ビルドして、審査を通ってから届きます。つまり**ユーザーの環境が先に変わり、こちらの対応は必ず後追いになります**。この時間差を短くする方法は、先に見ておくこと以外にありません。

ベータ期にはもうひとつ制約があります。ベータ SDK でビルドしたアプリは TestFlight には配れても審査には出せません。詳しくは[ベータ SDK でビルドしたアプリは、TestFlight には配れても審査には出せません](/articles/rork-dev/rork-beta-sdk-build-testflight-ok-app-store-submission-blocked)にまとめてあります。

ですので「新しい OS で確かめる → 直す → 出す」という流れのうち、ベータ期には最後の一手だけが閉じられません。正式版が出たいまは、三つ目まで手を動かせます。それでも、レビューが積み上がってから原因を探すのとは、負荷がまるで違います。レビュー欄を先に開いてしまった年は、胃が痛くなる数日になりました。

## 予備機を1台、検証機として切り離す

メイン端末は検証に使わないでください。

ベータから元のバージョンへ戻すには、端末を消去して復元する必要があります。そして新しい iOS で取ったバックアップは、古い iOS の端末へは戻せません。メイン端末をベータにすると、次の正式版が出るまで実質的に戻れない状態を抱えることになります。連絡や決済に使っている端末で背負う種類のリスクではありません。

予備機の準備は3手で終わります。

1. 予備の iPhone に Apple ID でサインインし、バックアップを取ります
2. 設定 → 一般 → ソフトウェアアップデート から、いま配られている最新の正式版（11月時点では 27.2 系）を入れます。次のベータを試す時期になったら、同じ画面の「ベータ版アップデート」から選びます
3. App Store から、自分の公開中のアプリを普通にインストールします

3 が要点です。開発ビルドでも、Rork Companion のプレビューでもなく、**いまユーザーが手にしているのとまったく同じ配信中の版**を入れます。

ここで一度失敗しました。ある年、手元の開発ビルドで新しい OS を確かめて「問題なし」と判断したところ、翌週のレビューに下端のボタンが押せないと書かれたのです。開発ビルドは、バンドルされているアセットも、有効になっている設定も、ストア版と少しずつ違っていました。「手元では出なかったのにレビューには書かれている」の多くは、この差から来るのだと気づいたのは、そのレビューに返信を書き終えたあとでした。

それ以来の線引きは一つです。**確かめるのはストアの版、直すのは手元の版。** この順番を入れ替えないようにしています。

引き出しの古い端末で構いません。SIM も不要です。Wi-Fi につながって、App Store にサインインできれば足ります。ただし、その端末が iOS 27 の対応機種に入っているかだけは、先に Apple の対応機種一覧で確かめてください。

## 触る順番は、崩れやすい順に決めておく

端末が用意できたら、闇雲に触らずに順番を決めます。上から順に、影響範囲が広くて修正コストが低いものを並べています。

上の3つで、体感としては見つかる不具合の大半を拾えます。逆に下へ行くほど、遭遇率は下がる代わりに、気づかれないまま放置されやすくなります。

4番は今年から足した項目です。iOS 27 では、アプリの起動や復帰の扱いを Scene（UIScene）を前提にした仕組みへ寄せる流れがはっきりしました。公開中の版は古い SDK でビルドされたまま動いているので、すぐに何かが壊れるとは限りません。ただ、次に SDK を上げたときに影響が出やすい場所でもあるので、いまの挙動を予備機で一度見ておくと、比べる基準になります。

順番を先に決めておく理由は、時間が限られているからというより、**同じ観点で全アプリを横断できる**ようにするためです。壁紙アプリを複数本運用していると、1本ずつ丁寧に触る余裕はありません。「全部の1番を見る、次に全部の2番を見る」と横に流したほうが、判断がぶれずに済みます。

予備機で何かを見つけたとき、最初に迷うのは「OS のせいか、自分のコードか、依存パッケージか」です。私が使っている切り分けの表を置いておきます。

## JS 側で先に潰しておけるもの

予備機の結果を待たずに、いま手を入れられる箇所が3つあります。いずれも Rork が生成したコードでよく見かける書き方の、少し先の話です。

### 下端は SafeAreaView ではなく insets で受ける

```tsx
import { SafeAreaProvider, useSafeAreaInsets } from 'react-native-safe-area-context';
import { View, Pressable, Text, StyleSheet } from 'react-native';

function Footer() {
  const insets = useSafeAreaInsets();

  return (
    <View style={[styles.footer, { paddingBottom: insets.bottom + 12 }]}>
      <Pressable style={styles.button}>
        <Text style={styles.label}>保存</Text>
      </Pressable>
    </View>
  );
}

export default function App() {
  return (
    <SafeAreaProvider>
      <Footer />
    </SafeAreaProvider>
  );
}

const styles = StyleSheet.create({
  footer: { paddingHorizontal: 16, paddingTop: 12 },
  button: { minHeight: 44, alignItems: 'center', justifyContent: 'center' },
  label: { fontSize: 17 },
});
```

`SafeAreaView` は、端末から返る安全領域をそのまま padding として当てます。手軽ですが、下端に自分の余白をもう少し足したくなったときに、二重の余白か不足のどちらかへ振れます。

`useSafeAreaInsets` は同じ値を数値で返します。数値であれば `insets.bottom + 12` のように自分の設計と足し合わせられます。OS 側でホームインジケータの扱いが変わっても、変わるのは `insets.bottom` の値だけで、レイアウトの式はそのまま生き残ります。ここを数値で持っておくかどうかが、毎年、新しい OS が出る時期の作業量を決めています。

### 文字サイズの上限は、枠が固定の要素にだけ置く

```tsx
<Text
  style={{ fontSize: 15 }}
  maxFontSizeMultiplier={1.4}
  numberOfLines={1}
  ellipsizeMode="tail"
>
  設定を保存
</Text>
```

`allowFontScaling={false}` で全体の拡大を止めてしまうのは避けたいところです。文字を大きくして読んでいる方の設定を、こちらの都合で無効化することになります。

その代わり、ボタンやタブのラベルのように**枠の高さが決まっている要素だけ**、倍率の上限を置きます。本文は拡大されるままにしておいて、崩れると操作できなくなる箇所だけを守る、という線引きです。

### バージョン分岐は、プラットフォームごとに意味が違う

```tsx
import { Platform } from 'react-native';

// iOS の Platform.Version は "27.2" のような文字列
// Android の Platform.Version は API レベルを表す数値（36 など）
const iosMajor =
  Platform.OS === 'ios' ? parseInt(String(Platform.Version), 10) : 0;

export const isIOS27OrLater = iosMajor >= 27;
```

`Platform.Version` は、iOS では OS のバージョン文字列、Android では API レベルの数値を返します。返ってくるものの意味そのものが違います。

`Platform.Version >= 27` とだけ書いた分岐は、iOS では「iOS 27 以降」を、Android では「API レベル 27 以降」つまり Android 8.1 以降を指します。動いてしまうぶん、後から読んで気づきにくい書き方です。上のように `Platform.OS` で先に分けて、名前で意味を固定しておくほうが安全です。

なお、新しい OS が出たからといって、いきなり分岐を足す必要はありません。まずは分岐なしで触ってみて、実際に挙動が変わっていた箇所にだけ入れます。先回りで書いた分岐は、たいてい要らなかったと後で分かります。

## よくある誤解を三つ、先にほどいておく

### 「新しい OS で崩れたら、SDK を上げれば直る」

公開中の版は、ビルドした時点の SDK のまま新しい OS の上で動いています。崩れの多くはレイアウトの書き方の問題で、SDK を上げても直りません。逆に SDK を上げると、ネイティブの再ビルドと審査が必要になり、Scene への移行のような自分の変更範囲も増えます。**崩れを直すことと、SDK を上げることは別の作業**として分けて考えたほうが、判断がぶれません。

### 「Rork Companion や Expo Go で問題なければ、ストア版も大丈夫」

プレビュー用のアプリは、ストア版とは別のバイナリです。ネイティブモジュールの組み合わせも、権限の説明文も、アイコンや起動画面も違います。プレビューで見えるのは JS の動きまでで、ストア版の確認の代わりにはなりません。

### 「JS の修正なら、EAS Update で全部の端末に届く」

EAS Update の更新は、ランタイムバージョン（runtimeVersion）が一致するビルドにしか届きません。ストアに複数の版が残っていて、古い版のランタイムバージョンが違う場合、その版のユーザーには更新が届かないままになります。配ったのに直らない、というときの切り分けは[Rork で EAS Update を配信したのに反映されない — 原因を切り分ける5つの典型パターン](/articles/rork-dev/rork-eas-update-ota-not-reflecting-troubleshooting)にまとめてあります。

## 見つけた後、どこまで直せて、どこから待つか

不具合を見つけたら、まず依存関係のずれを確かめます。

```bash
npx expo install --check
npx expo-doctor
```

`expo install --check` は、インストール済みのパッケージが今の SDK と噛み合っているかを見て、ずれていれば正しいバージョンを提示します。`expo-doctor` は設定ファイルやネイティブ側の食い違いを含めて点検します。OS の変化を疑う前に、この2つで足元を固めておくと切り分けが速くなります。

そのうえで、修正の届け方は2つに分かれます。

<table>
<thead>
<tr><th>修正の種類</th><th>例</th><th>届け方</th><th>ユーザーに届くまで</th></tr>
</thead>
<tbody>
<tr><td>JS レイヤー</td><td>レイアウト、文字サイズ、条件分岐、文言、画面遷移の処理</td><td>EAS Update</td><td>審査なし。ランタイムバージョンが合うビルドに、次回起動以降に届きます</td></tr>
<tr><td>ネイティブ設定</td><td>権限の説明文、Info.plist、ネイティブモジュールの追加・更新</td><td>再ビルドして審査に提出</td><td>審査とユーザーの更新を待つぶん、日単位でかかります</td></tr>
</tbody>
</table>

この線引きが分かっていると、新しい OS が出た直後にやることの順番が決まります。まず JS で直せるものを全部直して配り、ネイティブ側の修正は1本にまとめて審査へ出します。慌てて2回3回と審査に出すと、そのたびに数日を失います。

## SDK 58 へ上げるのは、いまか、春か

iOS 27 に合わせた Expo SDK 58 が出ていて、Scene を前提にした起動の仕組みや React Native の新しい版が入っています。上げるかどうかは、急ぎの崩れを直し終えてから決めるのが私のやり方です。

<table>
<thead>
<tr><th>選択</th><th>向いている状況</th><th>気をつけること</th></tr>
</thead>
<tbody>
<tr><td>いまの SDK のまま運用を続ける</td><td>予備機で大きな崩れがなく、JS の修正だけで落ち着いた</td><td>Apple は例年、新しい SDK でのビルドを審査の条件にする時期を告知します。日付は App Store Connect の告知で確かめてください</td></tr>
<tr><td>年内に SDK 58 へ上げる</td><td>通知や起動まわりのネイティブ修正がどうせ必要になった</td><td>削除された API の洗い出しを先に。審査を1本にまとめる好機でもあります</td></tr>
</tbody>
</table>

判断の基準は一文で足ります。**ネイティブの再ビルドがどのみち必要なら、そのついでに上げます。JS の修正だけで済むなら、春まで待ちます。** 上げると決めたら、先に[SDK 58 で削除された React Native の API を、アップグレード前に洗い出すスクリプト](/articles/app-dev/expo-sdk58-removed-react-native-apis-scan-script-before-upgrade)で手元のコードを点検しておくと、作業の見通しが立ちます。

## 次に詰まりやすいところ

予備機での確認を終えて修正を配ったあと、次に当たりやすいのは「配ったのに一部のユーザーだけ直らない」という場面です。原因の多くは、先ほどのランタイムバージョンのずれか、ユーザーがアプリを再起動していないことです。

ネイティブ修正を審査に出すときは、一度に全員へ配らず段階的に出すと、予備機では見つけられなかった崩れを小さな範囲で拾えます。その組み立て方は[Rork アプリの段階的リリース戦略 — 壊さない本番運用を作る](/articles/rork-dev/rork-phased-release-staged-rollout-hotfix-strategy)に書きました。

27.3 のベータが進んでいるいまは、予備機を「次のベータ」に回すかどうかを決める時期でもあります。ストア版の確認を 27.2 で終えたら、同じ端末をベータへ進めて、同じ表の1番から順に触る——これを毎回くり返すのが、いちばん負担の少ない回し方なのだと思います。

## 今日やることは1つだけ

予備の iPhone を 27.2 に上げて、ストアから自分のアプリを入れ、表の1番から3番だけを触ってみてください。それだけで今日は十分です。

あの数日の落ち着かなさは、毎年少しずつ小さくなっています。予備機が1台あるだけで、レビュー欄を開く前に自分の目で確かめられる——この順番だけは、これからも崩さないようにしております。
