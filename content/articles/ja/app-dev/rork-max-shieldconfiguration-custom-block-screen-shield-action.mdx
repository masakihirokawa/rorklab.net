個人開発でフォーカスタイム系のアプリを Rork Max で組んでいたとき、時間になるとブロックはかかるのに、出てくるのが Apple 既定の灰色の画面のままで、自分の作ったアプリだと気づいてもらえない、という状態が続きました。ユーザーからすると、丁寧に作ったオンボーディングを抜けた先で、急に無機質なシステム画面に突き放される感覚になります。

この「遮蔽画面」は差し替えられます。ただ、メインアプリのコードからは触れません。ブロック中の画面は別プロセスの拡張が描いているためで、そこに手を入れるには専用の App Extension を2つ足す必要があります。ひとつは見た目を差し替える `ShieldConfiguration` 拡張、もうひとつはその画面のボタンが押されたときの挙動を決める `ShieldAction` 拡張です。

前提として、Family Controls のエンタイトルメント取得と `ManagedSettingsStore` で実際にシールドをかける土台は済んでいるものとします。ここではその先の、画面の作り替えに絞ってお話しします。

## なぜメインアプリから遮蔽画面を描けないのか

`store.shield.applications` にトークンを渡すと、対象アプリを開いた瞬間にシステムが遮蔽画面を差し込みます。この画面を描いているのはあなたのアプリではなく、`ManagedSettingsUI` の枠組みで動く別プロセスです。React Native 側からはもちろん、Swift のメインターゲットからも直接は触れません。

差し替えの入口は `ShieldConfigurationDataSource` の一点だけです。システムが遮蔽画面を出す直前にこのクラスへ問い合わせ、返した `ShieldConfiguration` の内容で画面を組み立てます。つまり私たちが決められるのは「どんな部品を、どの色で並べるか」であって、任意の SwiftUI ビューを流し込めるわけではありません。ここを勘違いすると、凝ったレイアウトを描こうとして詰まります。

## ステップ1: ShieldConfiguration 拡張を追加する

Xcode で新しいターゲットとして「Shield Configuration」拡張を追加します。Rork Max のように Expo ベースでビルドしている場合は、`eas build` のたびに手作業でターゲットを足し直すのは現実的ではないので、config-plugin 側で拡張ターゲットと Info.plist、エンタイトルメントを注入する形にしておきます。私は本体のネイティブモジュールと同じ config-plugin にまとめて、拡張の追加漏れが起きないようにしています。

拡張の `Info.plist` では、`NSExtensionPointIdentifier` に `com.apple.ManagedSettingsUI.shield-configuration-service` を、`NSExtensionPrincipalClass` に自作クラス名を指定します。ここが違っているとビルドは通るのにシステムから呼ばれず、既定画面のまま、という無言の失敗になります。

```swift
import ManagedSettings
import ManagedSettingsUI
import UIKit

class FocusShieldConfiguration: ShieldConfigurationDataSource {
  override func configuration(shielding application: Application) -> ShieldConfiguration {
    return ShieldConfiguration(
      backgroundBlurStyle: .systemThinMaterialDark,
      backgroundColor: UIColor(red: 0.08, green: 0.10, blue: 0.16, alpha: 1),
      icon: UIImage(named: "ShieldLeaf"),
      title: ShieldConfiguration.Label(
        text: "いまは集中の時間です",
        color: .white
      ),
      subtitle: ShieldConfiguration.Label(
        text: "この時間帯は自分で選んで閉じたアプリです。あと少しだけ、続けてみませんか。",
        color: UIColor(white: 0.75, alpha: 1)
      ),
      primaryButtonLabel: ShieldConfiguration.Label(
        text: "集中に戻る",
        color: .white
      ),
      primaryButtonBackgroundColor: UIColor(red: 0.20, green: 0.55, blue: 0.90, alpha: 1),
      secondaryButtonLabel: ShieldConfiguration.Label(
        text: "5分だけ開く",
        color: UIColor(white: 0.65, alpha: 1)
      )
    )
  }

  // カテゴリ単位でブロックした場合はこちらも返す
  override func configuration(shielding application: Application,
                              in category: ActivityCategory) -> ShieldConfiguration {
    return configuration(shielding: application)
  }
}
```

`secondaryButtonLabel` を `nil` にすればボタンは1つになります。文言は具体的にしておくと効きます。「ブロック中」という事実の通知ではなく、「自分で選んだ約束だ」と思い出してもらう一言に変えるだけで、ユーザーの受け取り方がかなり変わります。私自身、文言を「アクセスがブロックされています」から上のような一文にしただけで、レビューでの評価の温度が明らかに上がりました。

## ステップ2: ボタンの挙動を ShieldAction で決める

見た目だけ変えても、ボタンを押したときの挙動はまだシステム任せです。ここを制御するのがもうひとつの拡張、`ShieldActionDelegate` です。`Info.plist` の `NSExtensionPointIdentifier` は `com.apple.ManagedSettings.shield-action-service` になります（先ほどの UI 側とは別物です）。

```swift
import ManagedSettings
import Foundation

class FocusShieldAction: ShieldActionDelegate {
  private let appGroup = "group.com.example.focus.shield"

  override func handle(action: ShieldAction,
                       for application: ApplicationToken,
                       completionHandler: @escaping (ShieldActionResponse) -> Void) {
    switch action {
    case .primaryButtonPressed:
      // 「集中に戻る」→ そのまま画面を閉じる
      completionHandler(.close)

    case .secondaryButtonPressed:
      // 「5分だけ開く」→ 猶予を記録してからシールドを一時解除
      grantTemporaryPass(minutes: 5)
      completionHandler(.defer)

    @unknown default:
      completionHandler(.none)
    }
  }

  private func grantTemporaryPass(minutes: Int) {
    let defaults = UserDefaults(suiteName: appGroup)
    let until = Date().addingTimeInterval(TimeInterval(minutes * 60))
    defaults?.set(until.timeIntervalSince1970, forKey: "passUntil")
    // 実際のシールド解除は監視側（DeviceActivityMonitor）で passUntil を見て行う
  }
}
```

返せる応答は3つだけです。`.close` は遮蔽画面を閉じてホームへ戻す、`.defer` はいったん画面を引っ込めて再評価に委ねる、`.none` は何もしません。

<thead>
<tr><th>応答</th><th>画面の挙動</th><th>使いどころ</th></tr>

<tbody>
<tr><td><code>.close</code></td><td>遮蔽画面を閉じ、ホーム画面へ戻す</td><td>「やめておく」を選ばせたいとき</td></tr>
<tr><td><code>.defer</code></td><td>画面を引っ込め、状態を再評価</td><td>猶予を与えて一時的に通したいとき</td></tr>

</tbody>
</table>

ここで大事なのは、`ShieldAction` 拡張そのものはシールドを外す権限を持たないと割り切ることです。実際に `store.shield.applications = nil` を叩くのは、時間監視を担う `DeviceActivityMonitor` 側です。ボタン拡張は「5分の猶予を与える」という意思だけを App Group に書き残し、解除の判断は監視側で `passUntil` を見て行う——このように役割を分けておくと、どのプロセスが起きていても破綻しません。ボタン拡張は一瞬だけ起きてすぐ死ぬので、そこで重い処理や解除ロジックを抱えさせると取りこぼします。

## 拡張がプロセス外で動くことからくる制約

この2つの拡張は、メインアプリとは別の、省メモリで短命なプロセスで動きます。ここを見落とすと、シミュレータでは動くのに実機やリリースビルドで崩れる、という厄介な落とし穴にはまります。私が実際にぶつかった点と対処を挙げておきます。

### アイコンは拡張のバンドルから読まれる

`UIImage(named:)` が読むのは拡張ターゲット自身のバンドルであって、メインアプリのアセットカタログではありません。アイコンは拡張側のターゲットにも含めるか、Asset Catalog を共有ターゲットに設定する必要があります。ここを忘れると `icon` が黙って `nil` になり、既定のアイコンが出ます。

### ネットワークは待てない

ネットワークです。遠隔から画像や文言をその場で取ってこようとしても、拡張の実行はごく短時間で、通信の完了を待てません。動的に出し分けたい文言や画像は、メインアプリが動いているうちに App Group へ書き出しておき、拡張はそれを読むだけにします。

### 状態共有は App Group 経由に寄せる

状態共有はすべて App Group 経由です。App Group 名が1文字でも食い違うと `UserDefaults(suiteName:)` は例外を投げずに `nil` を返すので、発見が遅れます。私は Capability 設定画面から両ターゲットの App Group をコピー&ペーストで突き合わせることを、毎回のチェック項目にしています。

## 審査とユーザー体験で見られる点

Family Controls を使うアプリは、そもそもエンタイトルメントの用途審査があります。遮蔽画面を作り替える場合、ここで一点、率直にお勧めしたいことがあります。ブロックを回避させる文言や、他社アプリを不当に貶める表現をシールドに載せないことです。遮蔽画面はユーザーが自分で選んだ制限を思い出す場であって、こちらの主張を差し込む場ではありません。淡々と、選んだ約束を静かに支える文面にとどめることを個人的には推奨します。審査でもユーザーの信頼の面でも安全です。

## ボタンの逃げ道を残すか、塞ぐか

「5分だけ開く」のような逃げ道を1つ残すかどうかは、アプリの性格で分かれます。ペアレンタルコントロール寄りなら逃げ道は塞ぐべきですし、自分を律するためのフォーカスアプリなら、逃げ道を用意したうえで「今日は何回使ったか」を後で見せるほうが、長く使ってもらえる実感があります。私の場合、猶予の回数を App Group に貯めて、翌朝それを穏やかに振り返らせる作りにしてから、継続率が目に見えて安定しました。収益の面でも、この手のアプリはブロックの強さそのものより、続けられたという手応えがサブスク継続に効きます。私自身、AdMob の広告収益に頼るより、こうした継続体験を土台にした少額サブスクのほうが、App Store 上でも息の長い数字になると感じています。

遮蔽画面は、ユーザーが一日に何度も目にする、意外と大切な接点です。既定のままにせず、自分のアプリの声で語らせてあげてください。実装は拡張2つ分の手間ですが、割に合うだけの印象の差が出る箇所だと感じています。
