壁紙アプリの更新版を手元の端末で起動したときのことです。いつものように壁紙が全面に出るはずの画面が、何もない一色のまま止まっていました。読み込み中の印も出ていません。指で左へ送ると、2枚目はすぐに出ます。右へ戻ると、1枚目はやはり空のままでした。

最初に疑ったのは画像の取得でした。回線が遅いのか、キャッシュが壊れたのか、URL が間違っているのか。ところが辿ってみると、1枚目は画像が届かなかったのではなく、ページそのものが組み立てられていませんでした。描く前の段階で抜けていたのです。

原因は、ページャーに「このページから始めて」と伝える時刻でした。寸法がまだ決まっていない段階で位置を渡していたため、初期ページの組み立てが飛ばされていたのです。Android で実際に入れた修正と、Rork が生成する Expo のコードで同じ穴を塞ぐ書き方を、順に書き残します。

## 何が起きていたのか

症状を整理すると、次の三つがそろっていました。

- 起動直後、最初に表示されるはずのページだけが空
- スワイプすると2枚目以降は正常に描画される
- 2枚目へ送ってから戻っても、1枚目は空のまま

最後の一つが決め手でした。一度スワイプすれば読み込みの経路は動いているはずなのに、1枚目だけが戻ってきません。それなら問題は画像の取得ではなく、その手前にあります。ページャーがどのページを組み立てるかを決める段階です。

いま思えば、ここに気づくまでに遠回りをしたのは、空白を「表示の失敗」とだけ見ていたからかもしれません。

Android 版では、画面を作った直後に ViewPager2 へ開始位置を同期で渡していました。アダプターがまだ自分の大きさを測り終えていない時点です。その結果、開始位置への移動だけが受け付けられ、そこに置くべきページの組み立て（バインド）が抜け落ちていました。2枚目以降はスワイプのたびに改めて組み立てられるので、正常に見えます。

## Android での実際の修正

直し方そのものは、拍子抜けするほど小さなものでした。位置の指定を、レイアウトが終わったあとのキューに回すだけです。

```java
// 修正前: 画面生成の直後に同期で位置を渡していた
// アダプターの寸法がまだ決まっておらず、初期ページのバインドが飛ぶ
viewPager.setAdapter(adapter);
viewPager.setCurrentItem(adapter.getStartPosition(), false);

// 修正後: レイアウト完了後に実行されるよう post で後ろへ回す
viewPager.setAdapter(adapter);
viewPager.post(() ->
    viewPager.setCurrentItem(adapter.getStartPosition(), false)
);
```

`post` に渡した処理は、そのビューのメッセージキューに積まれ、測定とレイアウトの一巡が済んだあとに動きます。順番が入れ替わるだけで、初期ページはきちんと組み立てられるようになりました。

ここで私が手を止めたのは、「同じことがほかの実装でも起きるのではないか」という点です。iOS 版の点検表には、UIPageViewController の初期ページを viewDidLoad で渡している箇所がないかを確かめる項目を足しました。iOS で実際に症状を見たわけではなく、Android で起きた順番の問題が、同じ構造の画面にも起きうるという予防の項目です。

**ページャーには、寸法が決まってから位置を渡します。** この順番だけは、どの実装でも先に決めておくようにしています。

## Expo の FlatList で、同じ穴が開く書き方

Rork でカルーセルを作ると、横向きの FlatList に `pagingEnabled` を付けた形がよく出てきます。ここでも、同じ順番の問題が別の顔で現れます。

最初に、よくある書き方を置きます。マウント直後に ref から `scrollToIndex` を呼び、前回見ていたページへ移ろうとする形です。

```tsx
// ❌ 起動直後に1枚目が空、または先頭から動かないことがある書き方
import { useEffect, useRef } from "react";
import { FlatList, Image, useWindowDimensions } from "react-native";

type Wallpaper = { id: string; uri: string };

export function WallpaperCarousel({
  items,
  startIndex,
}: {
  items: Wallpaper[];
  startIndex: number;
}) {
  const listRef = useRef<FlatList<Wallpaper>>(null);
  const { width } = useWindowDimensions();

  useEffect(() => {
    // マウント直後はまだ各ページの位置が測られていない
    // getItemLayout も onScrollToIndexFailed も無いので、開発ビルドでは
    // "scrollToIndex should be used in conjunction with getItemLayout or onScrollToIndexFailed" で止まる
    listRef.current?.scrollToIndex({ index: startIndex, animated: false });
  }, [startIndex]);

  return (
    <FlatList
      ref={listRef}
      data={items}
      horizontal
      pagingEnabled
      keyExtractor={(w) => w.id}
      renderItem={({ item }) => (
        <Image source={{ uri: item.uri }} style={{ width, height: "100%" }} />
      )}
    />
  );
}
```

この形には、穴が三つ重なっています。

- **位置を渡す時刻が早すぎます**。`useEffect` はコミット直後に動くため、FlatList が子の寸法を測り終える前に `scrollToIndex` が走ります
- **位置を計算する手段がありません**。`getItemLayout` が無いと、FlatList は描画していないページの位置を知りません。開発ビルドでは上のコメントにある文言で止まり、本番では位置合わせが黙って失敗します
- **幅を画面全体から取っています**。`useWindowDimensions` の幅は端末の画面幅です。カルーセルが余白や分割表示の中に置かれていると、ページの幅とスクロールの一単位がずれ、半端な位置で止まります

なかでも三つ目は、いちばん表に出にくい穴です。スマートフォンの全画面表示では二つの幅が一致するため、余白のある配置や分割表示にして初めて症状が見えます。

## 幅が決まってから、最初のページを渡す

直した形では、カルーセルを包む View で実際の幅を測り、幅が決まるまでは FlatList そのものを出しません。位置は ref で後から動かすのではなく、`initialScrollIndex` として最初の描画に含めます。

```tsx
// ✅ 幅を測ってから FlatList を出し、初期ページを最初の描画に含める
import { useCallback, useState } from "react";
import {
  ActivityIndicator,
  FlatList,
  Image,
  LayoutChangeEvent,
  StyleSheet,
  View,
} from "react-native";

type Wallpaper = { id: string; uri: string };

export function WallpaperCarousel({
  items,
  startIndex,
}: {
  items: Wallpaper[];
  startIndex: number;
}) {
  const [pageWidth, setPageWidth] = useState(0);

  const onLayout = useCallback((e: LayoutChangeEvent) => {
    // 小数点以下の揺れで再描画が続かないよう整数に丸める
    const w = Math.round(e.nativeEvent.layout.width);
    setPageWidth((prev) => (prev === w ? prev : w));
  }, []);

  // データが届く前に FlatList を出すと initialScrollIndex が先頭で確定してしまう
  const ready = pageWidth > 0 && items.length > 0;
  const safeIndex = Math.min(Math.max(startIndex, 0), Math.max(items.length - 1, 0));

  return (
    <View style={styles.frame} onLayout={onLayout}>
      {!ready ? (
        <ActivityIndicator size="large" style={StyleSheet.absoluteFill} />
      ) : (
        <FlatList
          // 幅が変わったら作り直す（回転・分割表示の切り替え）
          key={`carousel-${pageWidth}`}
          data={items}
          horizontal
          pagingEnabled
          showsHorizontalScrollIndicator={false}
          keyExtractor={(w) => w.id}
          initialScrollIndex={safeIndex}
          // 全ページが同じ幅なので、位置は掛け算で決まる
          getItemLayout={(_, index) => ({
            length: pageWidth,
            offset: pageWidth * index,
            index,
          })}
          // 初期ページの前後だけを先に組み立てる
          initialNumToRender={1}
          windowSize={3}
          onScrollToIndexFailed={({ index }) => {
            // getItemLayout がある限り通常は来ない。来たら黙って先頭に戻さず記録だけ残す
            console.warn(`carousel: scrollToIndex failed at ${index}`);
          }}
          renderItem={({ item }) => (
            <Image
              source={{ uri: item.uri }}
              style={{ width: pageWidth, height: "100%" }}
              resizeMode="cover"
            />
          )}
        />
      )}
    </View>
  );
}

const styles = StyleSheet.create({
  frame: { flex: 1, backgroundColor: "#d9d9d9" },
});
```

書き方の理由を、順に添えておきます。

- **onLayout で測るのは、ページの幅がカルーセルの枠で決まるから**です。画面幅ではなく枠の幅を使えば、余白や分割表示の中でも一単位がずれません
- **幅が 0 のあいだは、FlatList を出しません**。0 の幅で `getItemLayout` を計算すると、どのページの位置も 0 になり、結果として先頭に貼り付きます
- **データが空のあいだも出しません**。`initialScrollIndex` は最初の描画でしか読まれません。空の配列で一度出てしまうと、あとからデータが届いても先頭のままになります。これが、ドキュメントを読んだだけでは気づけなかった点でした
- **key に幅を含めます**。端末の回転や分割表示の切り替えで幅が変わったとき、古い位置計算のまま残らないよう、FlatList ごと作り直します。作り直すと位置は `startIndex` に戻るので、見ていたページを保ちたい場合は親で現在位置を持ち、`startIndex` に渡し直してください
- **枠に背景色を付けます**。万一1枚目の画像が遅れても、白い画面ではなく「まだ何かが来る」色に見えます。Android 版でも、ページの背景と画像のプレースホルダーを同じ色で指定し、何もない白に見える状態をなくしました

## 開発ビルドだけで動く見張り

一度直した空白は、レイアウトを触った日に戻ってきやすいものです。そこで、開発ビルドのときだけ「最初に見えたページが、渡したページと一致しているか」を確かめる小さなフックを足しました。

```tsx
// 開発ビルドだけで動く、初期ページの見張り
import { useCallback, useEffect, useRef } from "react";
import type { ViewToken } from "react-native";

export function useInitialPageWatch(expectedIndex: number, label: string) {
  const firstSeen = useRef<number | null>(null);

  const onViewableItemsChanged = useCallback(
    ({ viewableItems }: { viewableItems: ViewToken[] }) => {
      if (firstSeen.current !== null) return;
      const first = viewableItems.find((v) => v.isViewable)?.index;
      if (typeof first === "number") firstSeen.current = first;
    },
    []
  );

  useEffect(() => {
    if (!__DEV__) return;
    // 初回の描画と画像の差し込みが落ち着くまで少し待つ
    const t = setTimeout(() => {
      if (firstSeen.current === null) {
        console.warn(`[${label}] 1.5秒たっても見えているページがありません`);
      } else if (firstSeen.current !== expectedIndex) {
        console.warn(
          `[${label}] 最初に見えたのは ${firstSeen.current} 番、期待は ${expectedIndex} 番です`
        );
      }
    }, 1500);
    return () => clearTimeout(t);
  }, [expectedIndex, label]);

  return onViewableItemsChanged;
}
```

使う側では、FlatList に `onViewableItemsChanged` として渡し、`viewabilityConfig={{ itemVisiblePercentThreshold: 60 }}` を添えます。`onViewableItemsChanged` は描画のたびに作り直すと開発ビルドで警告が出るため、フックの中で `useCallback` に包んでいます。

この見張りは本番では何もしません。私は、カルーセルの周りの余白や枠の構成を変えたときに、シミュレーターで一度だけ起動してログを見るようにしています。数秒で済むので、点検というより習慣に近いものです。

実装し直す途中で、何度か足を取られた点を残しておきます。

もう一つ、`react-native-pager-view` を使う場合も考え方は同じです。開始位置は、マウント直後に `setPage` を呼んで動かすのではなく、`initialPage` として最初から渡すほうが順番の問題を避けられます。私はページ送りの手触りを細かく調整したかったため FlatList を選びましたが、どちらを選んでも「位置は最初の描画に含める」という線引きは変わりません。

## 次に確かめること

いま手元にカルーセルがある方には、次の順で確かめることを推奨します。

1. `onLayout` で測った枠の幅を一度だけログに出し、`useWindowDimensions` の幅と並べます。一致していなければ、ずれの原因はそこにある可能性が高いです
2. 初期ページを ref の `scrollToIndex` で動かしていないかを探します。この場合は `initialScrollIndex` と `getItemLayout` の組に置き換えます
3. データが届く前に FlatList が一度描画されていないかを、上の見張りのログで確かめます

三つとも数分で終わる確認です。まずは一つ目だけでも試していただければと思います。

私自身、画像の取得ばかりを疑ったあとで、原因が位置を渡す一行の順番だったと分かったときは、肩の荷が下りるのと同時に少し情けなくもありました。同じ空白に向き合っている方の時間が、ほんの少しでも短くなれば幸いです。
