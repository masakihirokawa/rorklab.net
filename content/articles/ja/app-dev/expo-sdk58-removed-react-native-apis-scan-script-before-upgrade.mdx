アップグレードの前夜に、いちばん避けたいのは「上げてみて、赤い画面が出てから原因を探す」ことです。SDK 58 の公式お知らせ（expo.dev/changelog の SDK 58）を読み直したところ、React Native 側の API がまとまって削除されていました。SDK 58 は React Native を 0.86 から 0.88 へ上げるため、0.87 と 0.88 の二回分の変更が一度に来ます。

どれも、一つひとつは小さな変更です。ただ、個人開発で長く触っているアプリほど、どこに何が残っているのかを自分の記憶だけでは数えきれません。そこで、ソースを走査して該当行を出すだけの小さなスクリプトを書きました。

最初に書いた版は、サンプルで動かして「拾えている」と思っておりました。ところが、書き方の違う画面をいくつか足して走らせ直すと、本当に止まる箇所の半分しか拾えていませんでした。この記事は、その見落としを直した改訂版です。

## 先に結論です

削除された API の使用箇所は、`grep` を何回か打つより、規則を一か所に書いたスクリプトで一度に出すほうが漏れにくいと感じています。ただし、スクリプトにも「書き方の癖」で見落とす場所があります。私が見落としたのは、複数行の import、別名を付けた import、props の中のアロー関数、そして別パッケージの同名コンポーネントの四つでした。

**名前ではなく、どこから import した名前なのかで探します。** 改訂版は、この一点だけを守るように組み直しています。

## SDK 58 で消えるもの・変わるもの（2026年11月時点・公式で確認）

公式のお知らせの「Notable breaking changes」と「Deprecations」から、ソースに残りうるものだけを抜き出しました。区分は、残っていると何が起きるかで分けています。

「削除」と「型エラー」は、残っていると上げた当日にビルドか型検査が止まります。「挙動」は止まらずに結果だけが変わるので、いちばん気づきにくい種類です。「非推奨」はいまは動くので、当日ではなく次の機会に直せば足ります。

## 最初の版で見落としていた四つ

最初の版を、書き方を少しずつ変えたサンプルで走らせ直したときの出力がこちらです。

```text
app/home.tsx:1  InteractionManager  → requestIdleCallback に置き換えます
app/home.tsx:11  InteractionManager  → requestIdleCallback に置き換えます
app/home.tsx:14  StatusBar の削除済み props  → 削除された props です。背景色は画面側の View に持たせます
app/store.ts:2  react-native 深い import  → react-native の公開 export へ。急ぐなら tsconfig の customConditions で先送りできます
app/store.ts:7  File.write() が await されていません  → await を付けるか、従来の挙動なら writeSync() を使います

5 件
```

同じサンプルには、本当は止まる箇所が八つあります。五件のうち一件（14行目）は `expo-status-bar` の `StatusBar` で、React Native の `StatusBar` ではありません。数えてみると、拾えていたのは八つのうち四つでした。

見落としの原因は、四つとも「行」や「名前」だけで判断していたことです。

<thead><tr><th>書き方</th><th>最初の版で起きたこと</th><th>改訂版での扱い</th></tr></thead>

小さなサンプルが一つだけだと、自分の書き癖しか試せません。私の手癖では import を一行に収めることが多く、複数行の import をほとんど書かないので、最初の版で困らなかったのだと思います。いまは点検スクリプトを書いたら、**自分が書かない書き方のサンプルを一つ足して走らせる**ところまでを一回の作業にしております。

## 点検スクリプト（改訂版）

依存は Node だけです。Node 22.23 で動かしています。`node sdk58-removed-api-scan.mjs ./my-app` のようにプロジェクトのルートを渡します。「削除」と「挙動」が 1 件でもあれば終了コード 1、「非推奨」だけなら 0 を返すので、CI に載せても非推奨で止まることはありません。

```js
// sdk58-removed-api-scan.mjs — Expo SDK 58 で削除・変更された API の使用箇所を洗い出します
// 使い方: node sdk58-removed-api-scan.mjs <プロジェクトのルート>
// 終了コード: 削除済み API が 1 件でもあれば 1（非推奨・設定の警告だけなら 0）
import { readdirSync, readFileSync, statSync, existsSync } from 'node:fs';
import { join, extname, relative } from 'node:path';

const root = process.argv[2] ?? '.';
const EXT = ['.ts', '.tsx', '.js', '.jsx', '.mjs', '.cjs'];
const SKIP = new Set(['node_modules', 'ios', 'android', 'dist', 'build', 'web-build']);

const walk = (d) =>
  readdirSync(d).flatMap((n) => {
    if (SKIP.has(n) || n.startsWith('.')) return [];
    const p = join(d, n);
    return statSync(p).isDirectory() ? walk(p) : EXT.includes(extname(p)) ? [p] : [];
  });

const lineOf = (text, index) => text.slice(0, index).split('\n').length;

// react-native から import している名前（複数行の import・as の別名にも対応）
const rnImports = (text) => {
  const names = new Map(); // ローカル名 → 元の名前
  for (const m of text.matchAll(/import\s*(?:type\s*)?\{([^}]*)\}\s*from\s*['"]react-native['"]/g)) {
    for (const part of m[1].split(',')) {
      const [orig, local] = part.replace(/\btype\s+/, '').trim().split(/\s+as\s+/);
      if (orig) names.set((local ?? orig).trim(), { orig: orig.trim(), line: lineOf(text, m.index) });
    }
  }
  return names;
};

// 開始タグを、{ } の入れ子を数えながら > まで読みます（props の中の => で切れないように）
const openingTags = function* (text, tag) {
  const re = new RegExp(`<${tag}(?=[\\s/>])`, 'g');
  for (const m of text.matchAll(re)) {
    let depth = 0, i = m.index + m[0].length;
    for (; i < text.length; i++) {
      const c = text[i];
      if (c === '{') depth++;
      else if (c === '}') depth--;
      else if (c === '>' && depth === 0) break;
    }
    yield { index: m.index, body: text.slice(m.index, i + 1) };
  }
};

// 行単位の規則: [重さ, 名前, 正規表現, 直し方]
const LINE_RULES = [
  ['削除', 'InteractionManager', /\bInteractionManager\b/, 'requestIdleCallback に置き換えます'],
  ['削除', 'react-native 深い import', /['"]react-native\/Libraries\//, '公開 export へ。急ぐなら tsconfig の customConditions で先送り（React Native 0.89 のあとに外れる予定）'],
  ['削除', 'NativeMethods 型', /\bNativeMethods\b/, 'ViewInstance などの instance 型へ置き換えます'],
  ['削除', 'expo-sqlite libSQL', /\bsyncLibSQL\b|\blibSQLOptions\b/, 'libSQL は削除されています。同期の仕組みを別に用意します'],
];

// react-native から import したタグだけを見る規則: [重さ, タグ名, 属性の正規表現, 直し方]
const TAG_RULES = [
  ['削除', 'Modal', /\sanimated(?=\s*=|\s|\/?>)/, 'animationType に置き換えます'],
  ['削除', 'StatusBar', /\s(backgroundColor|translucent|networkActivityIndicatorVisible)(?=\s*=|\s|\/?>)/, '削除された props です。背景色は画面側の View に持たせます'],
];

const hits = [];
const add = (sev, rel, line, name, fix) => hits.push({ sev, rel, line, name, fix });

for (const p of walk(root)) {
  const text = readFileSync(p, 'utf8');
  const rel = relative(root, p);
  const lines = text.split('\n');
  const rn = rnImports(text);

  lines.forEach((l, i) => {
    if (/^\s*(\/\/|\*|\/\*)/.test(l)) return; // コメント行は数えません
    for (const [sev, name, re, fix] of LINE_RULES) if (re.test(l)) add(sev, rel, i + 1, name, fix);
  });

  for (const [local, { orig, line }] of rn) {
    if (orig === 'Touchable') add('削除', rel, line, 'Touchable（ルート export）', 'Pressable などへ置き換えます');
    if (orig === 'ImageBackground') add('非推奨', rel, line, 'ImageBackground', 'View と絶対配置の Image へ。今は動きます');
    for (const [sev, tag, attr, fix] of TAG_RULES) {
      if (orig !== tag) continue;
      for (const t of openingTags(text, local)) if (attr.test(t.body)) add(sev, rel, lineOf(text, t.index), `${tag} の削除済み props`, fix);
    }
  }

  // expo-file-system の File.write() は SDK 58 から非同期です
  if (/from\s*['"]expo-file-system(\/next)?['"]/.test(text)) {
    lines.forEach((l, i) => {
      const prev = i > 0 ? lines[i - 1] : '';
      if (/\.write\(/.test(l) && !/\b(await|return)\s/.test(l) && !/\.then\(/.test(l) && !/\bawait\s*$/.test(prev)) {
        add('挙動', rel, i + 1, 'File.write() が await されていません', 'await を付けるか、従来の挙動なら writeSync() を使います');
      }
    });
  }
}

// 設定ファイル: useLibSQL は SDK 58 で効かなくなりました（エラーにはなりません）
for (const f of ['app.json', 'app.config.js', 'app.config.ts']) {
  const p = join(root, f);
  if (existsSync(p) && /useLibSQL/.test(readFileSync(p, 'utf8'))) add('非推奨', f, 1, 'expo-sqlite の useLibSQL', '効果がなくなりました。設定から外します');
}

hits.sort((a, b) => a.rel.localeCompare(b.rel) || a.line - b.line);
for (const h of hits) console.log(`[${h.sev}] ${h.rel}:${h.line}  ${h.name}  → ${h.fix}`);
const blocking = hits.filter((h) => h.sev !== '非推奨').length;
console.log(hits.length ? `\n${hits.length} 件（止まるもの ${blocking} 件）` : '該当なし');
process.exitCode = blocking ? 1 : 0;
```

規則は三つの層に分けました。名前だけで分かるもの（`LINE_RULES`）、`react-native` から import したかどうかで決まるもの（`rnImports` と `TAG_RULES`）、そして設定ファイルです。`Modal` と `StatusBar` をタグ単位にしたのは、`<RNStatusBar` から `/>` までが三行にまたがる書き方を拾うためです。あとから項目が増えたら、配列に一行足すだけで済みます。

見落としを確かめたのと同じサンプル（`app/home.tsx`・`app/store.ts`・`app.json`）と、何も混ぜていない空のプロジェクトで試しました。

終了コードは 1 でした。`expo-status-bar` の `StatusBar`（14行目）、コメントの中の `InteractionManager`（9行目）、`await` を付けた `File.write()`（6行目）は、どれも数えられていません。空のプロジェクトでは「該当なし」と表示され、終了コードは 0 でした。

なお、この出力は私が用意した小さなサンプルの結果です。実際のアプリでの件数ではありません。実際のアプリで何件出るかは、手元で走らせてみないと分からないところです。

## よくある誤解を三つ

**一つ目は、「customConditions には legacy の名前を一つ書けばよい」というものです。** 公式のお知らせでは、`"customConditions": ["react-native", "react-native-legacy-deep-imports"]` と二つ並べ、`"react-native"` は残すように書かれています。`expo/tsconfig.base` がもともと `"react-native"` を設定しているので、上書きするときに消さないことが要点です。この逃げ道は React Native 0.89 のあとに外される予定で、SDK 58 の期間中に移行するよう案内されています。

**二つ目は、「`expo-status-bar` の `StatusBar` も同じ props が消えた」というものです。** 削除されたのは React Native の `StatusBar` の props です。`expo-status-bar` は別のコンポーネントなので、このスクリプトでは対象外にしました。そちらの props の扱いは、`expo-status-bar` のドキュメントで確かめていただければと思います。

**三つ目は、「`useLibSQL` が残っているとビルドが止まる」というものです。** お知らせでは、設定の `useLibSQL` は「非推奨で、効果がなくなった」と書かれています。止まるのはコード側の `syncLibSQL()` と `libSQLOptions` で、設定の `useLibSQL` は外し忘れても動きます。スクリプトで「非推奨」と「削除」を分けたのは、この違いを出力の上でも区別したかったからです。

## 出力の読み方と、直す順番

出力を眺めて、直す順番を次のように決めています。

1. 型エラーになるもの（深い import・`NativeMethods`）を先に。`customConditions` で先送りはできますが、一回きりの猶予と考えるほうが安全です
2. 動作が変わるもの（`File.write()` の非同期化）を次に。`await` を忘れると、書き込み完了を待たずに次の処理へ進みます。画面上は何も起きず、あとから読んだファイルが空という形で現れやすい種類の変更です
3. 画面の見た目に出るもの（`StatusBar`・`Modal`）はその次に。動作確認を実機で兼ねられます
4. 「非推奨」（`ImageBackground`・`useLibSQL`）は、上げる当日には触りません。差分を小さく保つほうが、問題が出たときに戻しやすいからです

## ソースを読んでも分からない変更は、別の道具で

このスクリプトが拾えない変更も、三つ書き留めておきます。

- **Node.js**: Expo のツール類は 22 系なら 22.13 以上、24 系なら 24.3 以上、または 26 以上が必要で、奇数の 23 と 25 は対象外です。`node -v` で確認します
- **R8**: リリースビルドで `android.enableMinifyInReleaseBuilds=true` が既定になります。リフレクションを使うライブラリは ProGuard の keep ルールが必要になることがあります。止めたい場合は `expo-build-properties` で `false` にできます。上げる前に測っておく数字は[R8 が既定になる前に測っておく4つの数字](/articles/rork-dev/expo-sdk58-r8-default-android-baseline-measurement)に書きました
- **iOS のシーン・ライフサイクル**: iOS 27 の SDK が UIScene のライフサイクルを求めるため、プレビルドが `SceneDelegate.swift` と `Info.plist` の `UIApplicationSceneManifest` を生成します。`ios` フォルダを手で管理している場合や、AppDelegate のメソッドを直接上書きしている場合は、公式の移行ガイド（expo.fyi/ios-scene-lifecycle）に沿って確認します

## 直し終えたあとに、次に当たりやすいこと

一覧を空にしたあと、私が次に気にしているのは「直したものが、また戻ってくること」です。依存の更新や、ほかの画面からのコピーで、消したはずの `InteractionManager` が戻ってくることがあります。終了コードを返すようにしたのは、CI に一行足すだけで再発を止められるからです。

```yaml
# .github/workflows/check.yml の steps に足す一行
- run: node scripts/sdk58-removed-api-scan.mjs .
```

もう一つは、SDK 58 のほかの変更です。環境変数の読み込み規則は[SDK 58 から .env.staging は読み込まれません。手元の .env 系ファイルを、70行ほどのスクリプトで棚卸しします](/articles/app-dev/expo-sdk58-env-staging-file-not-loaded-local-wins-audit-script)に、Stripe を使うプロジェクトのビルドは[Stripe を入れた Expo SDK 58 で pod install が止まる — precompiled modules を切るか、直るまで待つかの判断](/articles/app-dev/expo-sdk58-stripe-pod-install-fails-precompiled-modules-turn-off-or-wait)に書きました。依存パッケージ側の推奨がどれだけ動くかは、[expo のパッチを1つ上げると、expo install の推奨が何個動くのかを数えました](/articles/rork-dev/expo-install-bundled-native-modules-patch-drift-audit)で数えています。削除・挙動・非推奨の三つに分けて、上げる当日の手順まで並べたものは[Expo SDK 58 に上げる前に、自分のコードで消える API を一覧にしておく](/articles/rork-basics/expo-sdk58-removed-api-audit-script-before-upgrade)にまとめています。

まずは、手元のプロジェクトのルートでスクリプトを一度だけ走らせ、「止まるもの」の件数を書き留めるところから始めていただければと思います。その数字が、上げる日の段取りを決める叩き台になると、私はいまも感じています。
