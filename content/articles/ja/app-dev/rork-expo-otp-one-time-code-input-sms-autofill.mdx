個人開発で運用しているアプリに電話番号の確認を足したとき、最初は素朴に6つの TextInput を横並びにしました。見た目は整っていたのですが、テスターから「SMSで届いたコードが上に出てこない」「貼り付けたら1マス目にしか入らない」と立て続けに指摘が届きました。マスを分けた瞬間に、iOS の自動入力もクリップボードの一括貼り付けも壊れていたのです。私自身、App Store に複数のアプリを出しながら、この「確認コード欄」だけは何度も作り直してきました。

コードを入れる画面は、サインアップや決済の直前という、いちばん離脱されたくない場所に置かれます。ここで一手間かかるだけで、せっかく興味を持ってくれた人が離れてしまいます。今回は Expo（React Native）で、SMS の自動入力・貼り付け・削除のすべてが自然に動く入力欄を組み立てていきます。

## マスを分けると自動入力が届かなくなる

確認コード欄でまず引っかかるのが「見た目」と「入力の実体」の食い違いです。デザイン上は1文字ずつ独立したマスに見せたい。けれど OS の自動入力は、ひとつの入力フィールドに対して「6桁の文字列」をまとめて流し込もうとします。

6つの TextInput に分けてしまうと、iOS はどのフィールドへ挿し込めばよいか判断できず、キーボード上部の候補（コードのサジェスト）自体が出なくなります。Android の SMS 自動入力も同様に、単一のフィールドを前提に動きます。貼り付けも「フォーカスされた1マス」にしか入りません。

ここから導かれる方針はひとつです。見た目は分割し、入力の実体は1つにまとめる。つまり透明な TextInput を1枚だけ置き、その値を1文字ずつ描画して「マスが並んでいるように見せる」構成にします。

## iOSとAndroidの自動入力を最初に指定する

先に自動入力の指定を固めておきます。ここを後回しにすると、UIを作り込んだあとで「なぜか候補が出ない」と時間を溶かします。両OSで必要な属性は異なります。

  <thead>
    <tr><th>目的</th><th>iOS</th><th>Android</th></tr>
  </thead>
  <tbody>
    <tr><td>コードの自動入力</td><td><code>textContentType="oneTimeCode"</code></td><td><code>autoComplete="sms-otp"</code></td></tr>
    <tr><td>キーボード種別</td><td colSpan={2}><code>keyboardType="number-pad"</code>（数字コードの場合）</td></tr>
    <tr><td>入力途中の自動修正抑制</td><td colSpan={2}><code>autoCorrect={false}</code> / <code>textContentType</code> は上記を優先</td></tr>
  </tbody>
</table>

注意したいのは、`importantForAutofill` を古い記事の見よう見まねで指定すると、逆に Android の `sms-otp` が無視される場合があることです。まずは上の最小構成から始め、必要になってから足すのが安全です。

```tsx
import { TextInput } from "react-native";

// 実体となる単一の入力欄。見た目は後段のマスで描くため透明にします
<TextInput
  value={code}
  onChangeText={handleChange}
  keyboardType="number-pad"
  textContentType="oneTimeCode" // iOS: SMS のコードを候補表示
  autoComplete="sms-otp"        // Android: SMS 自動入力
  maxLength={6}
  autoFocus
  style={{ position: "absolute", opacity: 0 }}
/>
```

## 単一のTextInputでセグメント表示を作る

土台ができたら、値を1文字ずつ描画してマスを並べます。ポイントは、描画側のマスはあくまで「表示専用」で、タップやキー入力は隠れた TextInput が受け持つことです。マスをタップしたら隠れた入力欄へフォーカスを戻す、という橋渡しだけを用意します。

```tsx
import { useRef, useState } from "react";
import { Pressable, TextInput, View, Text } from "react-native";

const LENGTH = 6;

export function OtpInput({ onComplete }: { onComplete: (v: string) => void }) {
  const [code, setCode] = useState("");
  const inputRef = useRef<TextInput>(null);

  const handleChange = (raw: string) => {
    // 数字以外を除去し、桁数で頭打ちにします
    const next = raw.replace(/[^0-9]/g, "").slice(0, LENGTH);
    setCode(next);
    if (next.length === LENGTH) {
      onComplete(next); // 6桁そろったら自動で次へ進めます
    }
  };

  const cells = Array.from({ length: LENGTH }, (_, i) => code[i] ?? "");

  return (
    <Pressable onPress={() => inputRef.current?.focus()}>
      <View style={{ flexDirection: "row", gap: 8 }}>
        {cells.map((ch, i) => (
          <View
            key={i}
            style={{
              width: 44, height: 52, borderRadius: 10,
              borderWidth: 1,
              borderColor: i === code.length ? "#3b82f6" : "#d1d5db",
              alignItems: "center", justifyContent: "center",
            }}
          >
            <Text style={{ fontSize: 22 }}>{ch}</Text>
          </View>
        ))}
      </View>
      <TextInput
        ref={inputRef}
        value={code}
        onChangeText={handleChange}
        keyboardType="number-pad"
        textContentType="oneTimeCode"
        autoComplete="sms-otp"
        maxLength={LENGTH}
        autoFocus
        style={{ position: "absolute", opacity: 0 }}
      />
    </Pressable>
  );
}
```

現在フォーカスされているマス（`i === code.length`）の枠色を変えるだけで、カーソルが無くても「次はここ」という視線誘導ができます。この一手間が、実機で触ったときの安心感を大きく左右します。

## 貼り付けと削除でつまずかないようにする

自動入力とセグメント表示ができても、実際の利用ではここでハマります。ふたつの落とし穴を先に潰しておきます。

### 貼り付け：6桁を一度に受け取る

ひとつ目は貼り付けです。SMS 本文からコードだけを長押しコピーして貼る人は少なくありません。6つのマスに分けた実装だと1マスにしか入りませんが、単一 TextInput 方式なら `handleChange` が一度に6文字を受け取るため、`slice(0, LENGTH)` を通すだけで各マスに正しく分配されます。上のコードは貼り付けをすでに吸収できています。

### 削除：Backspaceを一本で拾う

ふたつ目は削除です。数字パッドの削除キーは、値が空のときに `onChangeText` を発火しない端末があります。1マスずつ確実に消したい場合は `onKeyPress` で Backspace を拾い、末尾を落とす処理を足します。

```tsx
import type { NativeSyntheticEvent, TextInputKeyPressEventData } from "react-native";

const handleKeyPress = (e: NativeSyntheticEvent<TextInputKeyPressEventData>) => {
  if (e.nativeEvent.key === "Backspace") {
    setCode((prev) => prev.slice(0, -1));
  }
};

// <TextInput ... onKeyPress={handleKeyPress} /> として付与します
```

このとき `onChangeText` と `onKeyPress` が二重に発火して1回のタップで2文字消える端末がありました。私は削除を `onKeyPress` 側に一本化し、`onChangeText` では「増えた分だけ」を扱うよう役割を分けることで安定させています。細かい話ですが、実機を数台またいで検証しないと気づきにくい挙動です。

## 検証で手が止まった場面と対処

ここまでの実装を実機に載せると、いくつか本番運用で効いてくる注意点が見えてきます。

### シミュレータと実機で確認範囲を分ける

iOS のシミュレータでは SMS の自動入力候補が出ないため、「動かない」と誤解しがちです。これは実機に SMS が届いて初めて候補が出る仕組みなので、シミュレータでの確認はセグメント表示と貼り付けまでに留め、自動入力は実機で確かめるのが確実です。

Android の `sms-otp` は、送信する SMS の本文にアプリと結びつくハッシュや所定の書式が必要な場合があります。ここが満たされないと候補が出ず、原因がUI側に無いのに延々とレイアウトを疑ってしまいます。自動入力が出ないときは、まず「送信文面の要件」を疑うのが近道です。

コード欄では、貼り付けの直後にキーボードが残って完了ボタンを隠す、という細かなつまずきもあります。6桁そろった時点で `Keyboard.dismiss()` を呼び、確認ボタンへ視線が向くようにすると、最後の一押しが軽くなります。

## 私が採用している判断

確認コード欄は、凝ったライブラリを入れるより、単一 TextInput を透明で置いて自前のマスを描く構成を推奨します。依存が増えないぶん Expo のアップデートに強く、自動入力・貼り付け・削除という三点を自分の手でコントロールできるためです。

私自身は、マスの数を `LENGTH` 定数ひとつで変えられるようにしておき、4桁と6桁のどちらの案件でも同じ部品を使い回しています。地味な画面ですが、ここが滑らかだと登録全体の印象が変わります。実装の参考になれば幸いです。お読みいただきありがとうございました。
