サブスクの管理画面を開くと、新規の登録数はそれなりに動いているのに、月末の継続課金の数字だけが積み上がらない——Rork Max でリリースしたアプリを運用していると、最初に手が止まるのがこの場面ではないでしょうか。

新規獲得の数字ばかり眺めてしまうのは、私にも覚えのある癖です。視線を「すでに一度お金を払ってくださった方」に移したとき、打ち手の見え方が変わったのだと気づいたのは、しばらく経ってからでした。

ここからは、オファーコードの署名、ウィンバックの判定、プッシュ通知とメールの連動までを、StoreKit 2 と Google Play Billing の両方で実装できるところまで辿ります。コードの仕様は Apple・Google の公式ドキュメントで確かめ直しました。署名のタイムスタンプ単位のように、間違えても動いているように見えてしまう箇所には、そのつど印を付けています。

**数字は他人の平均ではなく、自分のアプリの解約理由から始めます。** この線引きだけは、最初にお伝えしておきたいと思います。

## なぜ「再獲得」から見直すのか

新規ユーザーを獲得する単価と、離れた方を呼び戻す単価は、アプリごとにまったく違います。インターネット上の「平均」をそのまま信じるより、自分の数字で比べるほうが確実です。

比べるための物差しは、次の3つだけで足ります。

<table>
<thead><tr><th>指標</th><th>計算式</th><th>数字の出どころ</th></tr></thead>
<tbody>
<tr><td>新規の獲得単価</td><td>広告費 ÷ 有料に転換した人数</td><td>広告管理画面と App Store Connect / Play Console</td></tr>
<tr><td>再獲得の単価</td><td>(値引きの総額 + 配信費) ÷ 復帰した人数</td><td>オファー配信ログと課金イベント</td></tr>
<tr><td>復帰後の継続率</td><td>復帰から6か月後も課金中の人数 ÷ 復帰した人数</td><td>自前の購読ステータス履歴</td></tr>
</tbody>
</table>

具体例で確かめておきます。以下は**仮定の数字**で、実績ではありません。月額600円のプランに「3か月50%オフ」のオファーを出し、1,000人に配信して50人が戻ったとします。復帰した1人あたりの値引きは 600円 × 50% × 3か月 = 900円。配信費が合計1,000円なら1人あたり20円で、再獲得の単価は920円です。

ここで見落としやすい点があります。この900円は「失った売上」ではありません。戻ってこなければ0円だった売上の一部を、割り引いて受け取っているだけです。比べる相手は、同じ人数を広告で連れてくる費用と、復帰後の継続率です。

過去に支払ったことのある方は、製品の価値を一度は認めた状態にあります。解約理由が「価格」「タイミング」「機能不足」のどれかによって、効く施策は変わります。この記事の実装が、理由別にオファーを出し分ける構成になっているのは、そのためです。

## 全体アーキテクチャ — 4層構造

実装に入る前に、システム全体を4層に分けて整理します。

第1層は **データ収集層**。ユーザーの利用状況・サブスクリプション状態・解約理由を蓄積します。Cloudflare D1 や Firestore などのバックエンドが選択肢です。

第2層は **ロジック判定層**。「いつ・誰に・どんなオファーを出すか」を決定します。ルールベースのシンプルなものから、機械学習モデルを使った高度なものまで、段階的に発展させられます。

第3層は **配信実行層**。プッシュ通知、メール、アプリ内ポップアップ、App Store のオファーコード配布を実行します。

第4層は **計測・分析層**。各施策の効果を測定し、次の施策にフィードバックします。

## ステップ1: StoreKit 2 のオファー署名 — 秒かミリ秒かで一日が消える

iOS 側のオファー配布から始めます。StoreKit 2 のプロモーショナルオファーは、サーバーで署名を作り、アプリがその署名を添えて購入を呼び出す設計です。署名が間違っていても、画面上は「購入に失敗しました」としか出ません。原因の切り分けに時間を取られやすい箇所なので、先に仕様を押さえておきます。

Apple のドキュメント「Generating a signature for subscription offers」では、署名の対象は次の順で `U+2063`（INVISIBLE SEPARATOR）を挟んで連結した文字列です。

<table>
<thead><tr><th>順</th><th>項目</th><th>注意点</th></tr></thead>
<tbody>
<tr><td>1</td><td>appBundleId</td><td>アプリの Bundle ID</td></tr>
<tr><td>2</td><td>keyIdentifier</td><td>App Store Connect で作成した鍵の Key ID</td></tr>
<tr><td>3</td><td>productIdentifier</td><td>購入するサブスクの商品 ID</td></tr>
<tr><td>4</td><td>offerIdentifier</td><td>App Store Connect で設定したオファー ID</td></tr>
<tr><td>5</td><td>applicationUsername</td><td>空文字でもかまいません（その場合は区切り文字が連続します）</td></tr>
<tr><td>6</td><td>nonce</td><td>サーバーが作る UUID。署名に使う文字列は<strong>小文字</strong>にします</td></tr>
<tr><td>7</td><td>timestamp</td><td>UNIX エポックの<strong>ミリ秒</strong>（秒ではありません）</td></tr>
</tbody>
</table>

署名アルゴリズムは SHA-256 の ECDSA で、鍵は App Store Connect からダウンロードする PKCS#8 の秘密鍵です。出力は DER 形式のバイナリで、それを Base64 にしてアプリへ返します。

```typescript
// サーバー側: プロモーショナルオファーの署名生成（Node.js 20 以上）
import { createPrivateKey, randomUUID, sign } from "node:crypto";

// 不可視文字をソースに直接貼ると、コピーや整形で消えます。エスケープで書きます
const SEP = "\u2063";

interface OfferParams {
  appBundleId: string;
  productId: string;
  offerId: string;
  applicationUsername: string; // 空文字でも可。入れる場合は後で引ける値にする
  privateKeyPem: string; // PKCS#8 形式の秘密鍵（環境変数やシークレットから読む）
  keyId: string; // App Store Connect で発行された Key ID
}

export function signPromotionalOffer(params: OfferParams) {
  const nonce = randomUUID().toLowerCase();
  const timestamp = Date.now(); // ミリ秒。Math.floor(Date.now() / 1000) は誤りです

  const payload = [
    params.appBundleId,
    params.keyId,
    params.productId,
    params.offerId,
    params.applicationUsername,
    nonce,
    String(timestamp),
  ].join(SEP);

  // EC 鍵への sign() は既定で DER 形式を返します
  const signature = sign(
    "sha256",
    Buffer.from(payload, "utf8"),
    createPrivateKey(params.privateKeyPem)
  );

  return {
    offerId: params.offerId,
    keyId: params.keyId,
    nonce,
    signature: signature.toString("base64"),
    timestamp,
  };
}
```

署名・nonce・timestamp は、購入リクエスト1回につき1度しか使えません。サーバーは購入の直前に、毎回新しく作って返します。

アプリ側は、返ってきた Base64 を `Data` に戻してから `purchase` に渡します。

```swift
// iOS 側: オファー適用
import StoreKit

struct SignedOffer: Decodable {
    let offerId: String
    let keyId: String
    let nonce: UUID
    let signature: String // サーバーが返す Base64
    let timestamp: Int
}

enum OfferError: Error {
    case productNotFound
    case invalidSignature
}

func applyPromotionalOffer(productId: String, offer: SignedOffer) async throws {
    guard let product = try await Product.products(for: [productId]).first else {
        throw OfferError.productNotFound
    }
    guard let signatureData = Data(base64Encoded: offer.signature) else {
        throw OfferError.invalidSignature
    }

    let result = try await product.purchase(options: [
        .promotionalOffer(
            offerID: offer.offerId,
            keyID: offer.keyId,
            nonce: offer.nonce,
            signature: signatureData,
            timestamp: offer.timestamp
        )
    ])

    switch result {
    case .success(let verification):
        switch verification {
        case .verified(let transaction):
            await transaction.finish()
        case .unverified(_, let error):
            throw error
        }
    case .userCancelled, .pending:
        break
    @unknown default:
        break
    }
}
```

署名が通らないときは、次の表の上から順に疑います。私は「鍵やアルゴリズムより先に、単位と大文字小文字を見る」と決めています。

<table>
<thead><tr><th>疑う順</th><th>よくある原因</th><th>確かめ方</th></tr></thead>
<tbody>
<tr><td>1</td><td>timestamp が秒になっている</td><td>13桁の数字（ミリ秒）になっているかログで見る</td></tr>
<tr><td>2</td><td>nonce が大文字のまま署名されている</td><td>署名に入れる文字列を <code>toLowerCase()</code> に通す</td></tr>
<tr><td>3</td><td>区切りが通常の空白やパイプになっている</td><td><code>"\u2063"</code> のエスケープで書かれているか確認する</td></tr>
<tr><td>4</td><td>項目の並び順が違う</td><td>上の表の 1〜7 の順と見比べる</td></tr>
<tr><td>5</td><td>Key ID と秘密鍵が別の鍵のもの</td><td>App Store Connect で作った鍵の ID と .p8 を組で管理する</td></tr>
<tr><td>6</td><td>同じ署名を使い回している</td><td>購入のたびにサーバーで新規発行する</td></tr>
</tbody>
</table>

### ウィンバックオファーは別の仕組みです

名前が似ているので混同しやすいのですが、App Store Connect には、署名を自前で作るプロモーショナルオファーとは別に、離れた購読者向けの**ウィンバックオファー**があります。資格の判定を Apple 側が行うのが違いです。設定できる条件は次のとおりです。

<table>
<thead><tr><th>項目</th><th>内容</th></tr></thead>
<tbody>
<tr><td>設定の単位</td><td>購読の商品ごと（サブスクグループ単位ではありません）</td></tr>
<tr><td>最低の課金期間</td><td>1〜24か月、または3・4・5年から選びます</td></tr>
<tr><td>最後に購読してからの期間</td><td>1〜24か月の範囲で指定します（必須）</td></tr>
<tr><td>同じオファーの再利用間隔</td><td>2〜24か月（任意）</td></tr>
<tr><td>上限</td><td>1つの購読につき350件まで。同時に動かせるのはストアフロントごとに5件まで</td></tr>
<tr><td>オファーの種類</td><td>都度払い・前払い・無料</td></tr>
</tbody>
</table>

対象になるのは、グループ内で最後に失効した商品に限られます。出し分けの条件を自前のサーバーで細かく握りたい場合はプロモーショナルオファー、Apple の資格判定とストア上の露出に任せたい場合はウィンバックオファーを選ぶ、という使い分けになります。対応する OS やアプリ内での呼び出し方は、Apple の最新ドキュメントで確認してから実装に入ってください（出典: [App Store Connect ヘルプ「ウィンバックオファーを設定する」](https://developer.apple.com/help/app-store-connect/manage-subscriptions/set-up-win-back-offers)）。

## ステップ2: Google Play Billing のオファー選択

Android 側は、サーバーで署名を作る iOS とは仕組みが違います。オファーは Play Console でベースプランに紐づけて作り、アプリは `queryProductDetails` が返す `subscriptionOfferDetails` の中から使いたいオファーを選び、その `offerToken` を `BillingFlowParams` に渡します。

つまり、オファートークンはサーバーから配るものではなく、`ProductDetails` から取り出すものです。サーバーの役割は「このユーザーにはどのオファー ID を使わせるか」を決めて、アプリに伝えるところまでになります。

```kotlin
// Android 側: サーバーが指定したオファー ID を探して購入フローを開く
import com.android.billingclient.api.BillingClient
import com.android.billingclient.api.BillingFlowParams
import com.android.billingclient.api.QueryProductDetailsParams

suspend fun launchOfferFlow(
    activity: Activity,
    productId: String,
    targetOfferId: String?
) {
    val productList = listOf(
        QueryProductDetailsParams.Product.newBuilder()
            .setProductId(productId)
            .setProductType(BillingClient.ProductType.SUBS)
            .build()
    )

    val params = QueryProductDetailsParams.newBuilder()
        .setProductList(productList)
        .build()

    val productDetailsResult = billingClient.queryProductDetails(params)
    val productDetails = productDetailsResult.productDetailsList?.firstOrNull() ?: return
    val offers = productDetails.subscriptionOfferDetails ?: return

    // 指定のオファーが返ってこなければ、オファーなしのベースプランに戻す
    val offer = offers.firstOrNull { it.offerId == targetOfferId }
        ?: offers.firstOrNull { it.offerId == null }
        ?: return

    val productDetailsParamsList = listOf(
        BillingFlowParams.ProductDetailsParams.newBuilder()
            .setProductDetails(productDetails)
            .setOfferToken(offer.offerToken) // ProductDetails から取り出したトークン
            .build()
    )

    val billingFlowParams = BillingFlowParams.newBuilder()
        .setProductDetailsParamsList(productDetailsParamsList)
        .build()

    billingClient.launchBillingFlow(activity, billingFlowParams)
}
```

ベースプランのオファーなしの項目は `offerId` が `null` で返ってきます。この性質を使って、指定のオファーが見つからなかったときの戻り先にしています。

画面に出す価格や無料期間は、選んだオファーの `pricingPhases` から読み取ります。「3か月50%オフ」とボタンに書いておきながら、実際には通常価格で購入が走る——そんな食い違いを避けるためです。オファーの対象条件（新規向け・アップグレード向けなど）の細かい設定は、Play Console のヘルプで確認してください。

## ステップ3: ウィンバックオファーの判定ロジック

「誰に・いつ・どのオファーを出すか」のロジックを実装します。ルールベースから始めて、データが溜まってから機械学習に移行するのが現実的です。

```typescript
// src/lib/winback-offer-engine.ts
interface UserProfile {
  userId: string;
  cancelDate: Date;
  cancelReason?: "price" | "not_using" | "found_alternative" | "missing_feature" | "other";
  totalLifetimeRevenue: number;
  monthsActive: number;
  lastSessionDays: number;
}

interface OfferRecommendation {
  productId: string;
  offerId: string;
  channel: "push" | "email" | "in_app";
  message: string;
}

export function recommendWinbackOffer(
  profile: UserProfile,
  sentWindows: number[] = [] // 配信済みの窓（7 / 30 / 90）を台帳から渡す
): OfferRecommendation | null {
  const daysSinceCancel = Math.floor(
    (Date.now() - profile.cancelDate.getTime()) / (1000 * 60 * 60 * 24)
  );

  // タイミング: 解約から 7日 / 30日 / 90日の「窓」に入り、まだ送っていないときだけ
  const window = [7, 30, 90].find(
    (d) => daysSinceCancel >= d && daysSinceCancel < d + 3
  );
  if (window === undefined || sentWindows.includes(window)) return null;

  // 解約理由別のオファー
  switch (profile.cancelReason) {
    case "price":
      return {
        productId: "com.example.app.subscription.monthly",
        offerId: "winback_50_off_3months",
        channel: "push",
        message: "戻ってきてくれませんか？3か月50%オフでお試しいただけます。",
      };

    case "not_using":
      return {
        productId: "com.example.app.subscription.monthly",
        offerId: "winback_first_month_free",
        channel: "email",
        message: "最近のアップデートで使いやすくなりました。1か月無料でお試しください。",
      };

    case "missing_feature":
      return {
        productId: "com.example.app.subscription.monthly",
        offerId: "winback_first_month_free",
        channel: "email",
        message: "気になっていた点が変わっていないか、1か月無料でお確かめください。",
      };

    case "found_alternative":
      // 競合に流れたユーザーには年間プラン提示で長期囲い込み
      return {
        productId: "com.example.app.subscription.yearly",
        offerId: "winback_yearly_30_off",
        channel: "in_app",
        message: "年間プランが30%オフでご利用いただけます。",
      };

    default:
      // LTV が高かったユーザーには手厚いオファー
      if (profile.totalLifetimeRevenue > 50) {
        return {
          productId: "com.example.app.subscription.yearly",
          offerId: "winback_loyal_50_off",
          channel: "push",
          message: "また一緒に過ごしたいです。年間プラン50%オフでお戻りください。",
        };
      }
      return null;
  }
}
```

このロジックの肝は、「解約理由別に異なるオファーを出す」点です。価格で離れた方には値引きを、機能不足で離れた方には変更点の訴求と無料期間を、という出し分けを仮説として置きます。

もうひとつ、地味ですが効くのが「窓」の考え方です。日次バッチで `daysSinceCancel` がちょうど7日の人だけを拾う書き方だと、バッチが1日止まっただけでその方には二度とオファーが届きません。逆に再実行すれば二重に届いてしまいます。3日ほどの幅を持たせ、配信済みの窓を台帳に残しておけば、止まった日も再実行した日も安全です。

## ステップ4: プッシュ通知との連動

プッシュ通知でオファーを届ける実装です。FCM（Firebase Cloud Messaging）を使った例を示します。

```typescript
// src/lib/push-notification-sender.ts
import { getMessaging } from "firebase-admin/messaging";

interface OfferNotification {
  userId: string;
  fcmToken: string;
  offerId: string;
  productId: string;
  message: string;
  deepLink: string; // アプリ内のオファー画面へのディープリンク
}

export async function sendOfferPushNotification(args: OfferNotification) {
  const messaging = getMessaging();

  await messaging.send({
    token: args.fcmToken,
    notification: {
      title: "特別なお知らせがあります",
      body: args.message,
    },
    data: {
      type: "winback_offer",
      offerId: args.offerId,
      productId: args.productId,
      deepLink: args.deepLink,
    },
    apns: {
      payload: {
        aps: {
          sound: "default",
          badge: 1,
          "mutable-content": 1,
        },
      },
    },
    android: {
      priority: "high",
      notification: {
        clickAction: "OPEN_OFFER",
      },
    },
  });

  // 配信ログを記録（A/Bテスト・効果分析のため）
  await logOfferDelivery({
    userId: args.userId,
    offerId: args.offerId,
    sentAt: new Date(),
  });
}
```

deepLink の設計が重要です。プッシュ通知をタップしたら、即座にアプリ内のオファー画面が開き、ボタン1つで購入確認に進める導線を作ります。「アプリを開いてからオファーを探す」というステップを残すと、ほとんどのユーザーは離脱します。

## ステップ5: 解約理由の収集

ウィンバックの精度は、解約理由の収集精度に依存します。App Store / Google Play 自体は解約理由を提供してくれないため、自前で収集する仕組みを入れます。

```swift
// iOS 側: 解約画面の前に理由を聞く
import SwiftUI
import StoreKit

struct CancellationFlowView: View {
    @State private var selectedReason: CancelReason?
    @State private var feedback: String = ""

    var body: some View {
        VStack(spacing: 16) {
            Text("解約の前に、お聞かせください")
                .font(.title2)

            Text("私たちのアプリのどこを改善できるか、教えていただけませんか？")
                .multilineTextAlignment(.center)
                .padding()

            ForEach(CancelReason.allCases) { reason in
                Button {
                    selectedReason = reason
                } label: {
                    HStack {
                        Image(systemName: selectedReason == reason ? "circle.fill" : "circle")
                        Text(reason.label)
                        Spacer()
                    }
                    .padding()
                }
```

## ステップ6: A/Bテストと効果計測

## メール配信チャネルを併設する

プッシュ通知が定番の配信路ですが、アプリのウィンバックではメールが見落とされがちです。プッシュと並行してメール配信を用意しておくと、通知をオフにしてしまった休眠ユーザーにも届けられます。

基本は、初回のサインアップ時に明示的な同意を取ってメールアドレスを収集し、プッシュトークンと同じユーザー ID に紐づけて保存しておくことです。ウィンバックエンジンがオファーを推奨したとき、ユーザーの状態に応じて配信路を選びます。直近まで使っていた方にはプッシュ、完全に離れてしまった方にはメール、という具合です。

```typescript
// src/lib/email-winback-sender.ts
import { Resend } from "resend";

interface EmailWinbackArgs {
  userEmail: string;
  userName?: string;
  offerId: string;
  productId: string;
  discountPercent: number;
  appStoreUrl: string;
  unsubscribeUrl: string;
}

export async function sendEmailWinback(args: EmailWinbackArgs) {
  const resend = new Resend(process.env.RESEND_API_KEY!);

  const subject = `${args.userName ? args.userName + "さん、" : ""}特別なご提案があります`;

  await resend.emails.send({
    from: "Rork Max App <hello@example.com>",
    to: args.userEmail,
    subject,
    html: buildEmailHtml(args),
    text: buildEmailText(args),
    headers: {
      "List-Unsubscribe": `<${args.unsubscribeUrl}>`,

  await logEmailDelivery({

```

ここで地味に効くのが `List-Unsubscribe` ヘッダーです。Gmail も Apple Mail も、このヘッダーがあると配信解除リンクを目立つ位置に表示してくれます。解除導線がはっきり見えることで、迷惑メール報告がぐっと減ります。迷惑メール報告は送信者レピュテーションを傷つけ、それが今後すべての配信に響きますので、このヘッダーは必ず入れておきたいところです。

## サブスクのライフサイクルで見落としがちな境界ケース

実装が一通り動き始めてから慌てやすいのが、サブスクリプションの状態遷移にひそむ境界ケースです。代表的なものを挙げておきます。

**グレースピリオド（支払い猶予期間）**。クレジットカードの期限切れや決済失敗が起きたとき、猶予期間のあいだユーザーは利用を続けられ、裏では課金のリトライが走ります。Apple では App Store Connect で有効にしたうえで、3日・16日・28日から選びます（週額プランは最大6日です）。選んだ値はアプリ内のすべての購読商品に共通で適用されます。Google は Play Console でベースプランごとに猶予期間の長さを設定します。どちらも「自動で付いてくる」前提にせず、自分のアプリでの設定値を確認しておく必要があります。アプリ側では「グレースピリオド中」を独立した状態として扱い、権限としてはアクティブ扱いにしつつ、支払い方法の更新を促すバナーを出すのが定石です。

**返金**。Apple の返金処理は非同期です。今日返金した方が、数時間から数日のあいだ記録上はまだ権限を持っているように見えることがあります。レシートの再検証に頼らず、App Store Server Notifications を購読して、返金イベントを受け取った瞬間に権限を取り消す設計にしておきます。

**ファミリー共有**。Apple のファミリー共有では、1つのサブスクで最大6人まで権限が及びます。RevenueCat を使えば自動で処理されますが、自前で組む場合は App Store Server API でファミリー共有の関係を検証する必要があります。

**再課金のタイミング**。期間の途中で解約してすぐ再課金した方に対し、両プラットフォームとも二重請求はしませんが、サーバー側では「これは新規ではなく再契約だ」と認識し、オンボーディングメールや試用特典を重複して出さないようにします。直前のサブスク状態を記録し、新規フローを起動する前に確認します。

## RevenueCat か自前レシート検証か

Rork Max で作ったアプリを運用していると、誰もが一度は迷う選択があります。RevenueCat のようなサービスを使うか、レシート検証を自前で組むか、という問いです。

RevenueCat の利点は、StoreKit 2 と Google Play Billing の差異を吸収してくれること、グレースピリオドやファミリー共有といった境界ケースを自動で扱ってくれること、そしてクロスプラットフォームの指標をひとつのダッシュボードで見られることです。多くの個人開発者にとって、節約できる時間は売上連動の手数料を大きく上回ります。

一方で、規模が大きくなると売上に対する手数料が無視できなくなります。仮に手数料が売上の1%だとすると、月10,000ドルの継続収益に対して月100ドルで、これは売上に比例して増えていきます（実際の料金体系は RevenueCat の公式ページで確認してください）。自前のレシート検証は一度組んでしまえば、その後はいくら伸びても追加費用なしで回せます。

私なら、月次継続収益が5,000ドルに届くまでは RevenueCat で進め、そこで一度見直す、という順序にします。この5,000ドルは目安であって、手数料と自前化の工数を並べて決める数字です。立ち上げ期に節約できる時間は、手数料よりはるかに価値があります。手数料が気になる規模になる頃には、自前化の複雑さに見合う節約かどうかを判断するためのデータが手元に揃っています。

移行する場合は慎重に計画してください。レシート検証の移行は課金中の全顧客に触れる作業で、小さなバグでもサブスク状態の破損につながり、復旧には大きなコストがかかります。最低でも3週間は確保し、切り替え前に十分な並行稼働期間を取ることをおすすめします。

## ステップ7: 実運用での落とし穴

実装中に詰まりやすいポイントです。

**間違い1: オファー署名の有効期限切れ**

署名・nonce・timestamp は、購入リクエスト1回につき1度しか使えません（nonce は24時間キャッシュされる、とドキュメントにもあります）。サーバーで作り置きして使い回すと、2回目以降は通りません。クライアントが購入ボタンを押したときに署名を取得し、すぐに決済画面を出す流れにします。

**間違い2: 過剰なプッシュ通知**

ウィンバックオファーのプッシュ通知を頻繁に送ると、ユーザーがアプリ通知を OFF にする原因になります。1ユーザーあたり月3回を初期の上限にして、通知をオフにした人の割合を見ながら動かしていきます。

**間違い3: 解約済みユーザーへの通知配信**

FCM トークンが残っているからといって、アプリを削除した方に送り続けると、配信失敗が増えて配信指標が読みにくくなります。FCM が無効なトークンとして返してきたものは削除し、長く開かれていない端末は配信対象から外す仕組みを入れます（日数は自分のアプリの利用頻度に合わせて決めます）。

**間違い4: ディープリンクの不具合**

オファー画面へのディープリンクが正しく動作しないと、ユーザーがアプリを開いただけで終わってしまいます。リリース前に必ず実機テストで、プッシュ通知タップ → オファー画面表示 → 購入確認、までの一連のフローを確認します。

**間違い5: A/Bテストの早期判断**

「3日間で treatment が control より売上が高い」という結果が出ても、それが統計的に有意とは限りません。最低2週間、できれば1か月のデータで判断します。

## 運用しながら確かめたい5つの仮説

ウィンバックの基盤を作ったあと、時間をかけて確かめていきたい点が5つあります。いずれも「こうだった」という結果ではなく、数字を取りながら検証する仮説として置いておきます。

ひとつめ。**解約理由の質は、手を入れ続けないと劣化するのではないか**。理由の選択肢を見ても、深く考えずに素早くタップして通り過ぎる方は一定数いるはずです。半年に一度は文言を見直し、「その他」の回答を定期的に分類し直します。新しく追加すべきカテゴリが、そこから見えてきます。

ふたつめ。**効くのは値引きそのものより、パーソナライズではないか**。「この機能をよく使ってくださっていましたね」と、その方の使い方に触れた文面と、汎用的な「戻ってきてください」を、同じ条件で比べてみる価値があります。差が出るかどうかは、前の章の表の件数が貯まってから判断します。

みっつめ。**ウィンバックは一回限りの転換ではなく、長いループではないか**。一度戻り、使い続け、また離れ、再び戻る——この往復を含めた累計の売上で見ないと、施策の価値を見誤ります。

よっつめ。**再獲得した方の継続曲線を、新規と並べて見ます**。復帰した方が新規よりも速く離れていくなら、オファーが強すぎて、本当は関心のない方を値引きで呼び戻している可能性があります。基準は自分のアプリの新規の継続率に置き、下回るならオファーの設計を見直します。

いつつめ。**高単価で離れた方には、メールのほうが届くのではないか**。通知をオフにしている方には、プッシュは届きません。チャネル別のウィンバック率を分けて取っておけば、この仮説は自分のアプリで確かめられます。

まずは基本形を作ること。教訓は、データが貯まってから自然と姿を現します。

## 全体を振り返って — まず1つの施策から始める

ここまでの実装を一気にやろうとすると、手が止まります。最初の1か月は「解約理由の収集」と「いまの解約率の計測」だけ。次の1か月で「最も多い解約理由に対応するオファー1つ」だけ。そのくらいの歩幅で十分です。

私なら、最初の一手は「料金で解約した方へのプッシュ通知とオファー1つ」に絞ります。小さく始めておけば、署名のような詰まりやすい箇所も一度で済み、効果が出たかどうかも切り分けられるからです。

完璧な設計を目指して何も実装しないより、不完全でも1つの施策を回し始めるほうが、学べることは多くなります。まずは、自分のアプリの月次解約率を表計算に1行書き出すところから始めていただければと思います。
