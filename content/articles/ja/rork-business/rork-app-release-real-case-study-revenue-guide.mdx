リリース申請の直前、ビルドは通っているのに、手元のチェックリストには「Apple Developer Program の年会費」の行がありませんでした。費用の見積もりを組み直した夜のことです。作る部分ばかりに意識が向いて、出ていくお金と、審査で止まる理由を後回しにしていた——そのことに気づいたのは、申請ボタンの前でした。

この記事は、Rork で作ったアプリを企画からストア公開、収益化の改善まで進める道筋を、つまずきやすい順に書き残したものです。「Rork で作れる」という情報は多くありますが、「公開してから何が起きるか」まで書かれたものは多くありません。その隙間を、確認できた事実と試算の区別をつけながら埋められればと思います。

**「作る」は Rork にお任せできても、「何を、どう出し、どう育てるか」を決めるのは私自身です。** この線引きが、以降の全工程の背骨です。

## 企画フェーズ：何を作るかの決め方

アプリのジャンルを決める際、私が確認している指標があります。

**ストア分析ツールでの需要確認**

狙いたいカテゴリの上位アプリについて、ダウンロード推定数と収益推定を見ます。「ダウンロードが多く、収益推定が見えていて、かつ 1〜3 位のアプリに明確な弱点がある」カテゴリが理想です。

なお、以前よく使われていた App Annie（のちの data.ai）は 2024 年に Sensor Tower へ統合されています。現在は Sensor Tower などで確認するのが現実的です。無料で見られる範囲には限りがあるため、ストアの上位ランキングやレビューの中身と併せて見るようにしています。

壁紙・ライフスタイル系は競合が多い一方、ユーザーがアプリを乗り換えやすい分野です。「刺さるテーマ」を持つアプリは、大手と正面から競わずにファンを得られる余地があります。

**収益モデルの設計を先に決める**

開発を始める前に「どうやって収益を上げるか」を決めます。主な選択肢は 3 つです。

- **AdMob のみ**: 実装は簡単です。ただし表示回数を稼ぐため、頻繁に開かれるアプリである必要があります。月間 50 万〜100 万インプレッション以上を見込めなければ、広告だけでの収益は限られるというのが私の目安です。
- **サブスクリプションのみ**: 月次収益は安定しやすい反面、無料版に十分な価値がないと課金に進んでもらえません。
- **ハイブリッド（AdMob + サブスクリプション）**: 無料ユーザーには広告、課金ユーザーには広告なしの体験を提供します。私が主に使っているモデルです。

ハイブリッドの設計原則は「広告を邪魔にしすぎない。ただし課金する理由になる程度には存在感を出す」ことです。インタースティシャルを毎回出せば離脱しますし、バナーだけでは課金の動機になりません。一例として、「数回に 1 回のインタースティシャル + 常時バナー（プレミアムでは非表示）」という組み合わせを出発点にし、離脱率を見ながら間隔を調整しています。広告と課金が互いの収益を食い合う地点は、[Rork アプリの収益設計 — 広告と課金が食い合う地点をどう避けるか](/articles/rork-business/rork-app-monetization-complete-strategy)で掘り下げています。

## 開発フェーズ：Rork での具体的な進め方

Rork で開発を進める際は、最初に全体の画面構成を自然言語でまとめた文書を用意します。

```
アプリ名: [アプリ名]
コンセプト: [ひとことで]

画面一覧:
1. スプラッシュ → ホーム（初回のみ）
2. ホーム: [内容の説明]
3. 詳細ページ: [内容の説明]
4. お気に入り一覧
5. 設定画面: [サブスクリプション管理・通知設定]
6. プレミアムアップグレード画面

収益化:
- AdMob バナー: ホーム画面下部
- AdMob インタースティシャル: 詳細ページ 5 回に 1 回
- サブスクリプション: 月額・年額の 2 プラン（RevenueCat で管理）

バックエンド:
- 画像データ: Supabase Storage
- ユーザーデータ: Supabase Database（お気に入り・設定）
- 課金管理: RevenueCat
```

この文書を最初のプロンプトに貼り付けます。全体設計が明確なほど、「やっぱり別の画面が必要だった」という手戻りが減ります。

**開発中に起きやすい問題と対処**

React Native（Expo）で作ったアプリでは、似た問題が繰り返し起きます。

*画像の読み込みが遅い*: Supabase の画像を FlatList にたくさん並べ、標準の Image コンポーネントで描画すると、スクロールが重くなりがちです。`expo-image` へ切り替えると改善することが多いので、Rork には次のように伝えます。

```
Image コンポーネントをすべて expo-image に置き換えてください。
contentFit は "cover"、cachePolicy は "memory-disk" にしてください。
```

*入れ子のナビゲーションで戻る挙動がおかしい*: Stack → Tabs → Stack のように層が深いと、戻るボタンの挙動が想定とずれることがあります。Expo Router には `router.back()` のほかに、スタックを閉じる `router.dismiss()` があります。どちらが正しいかは画面の構造次第なので、「どの画面から、どこへ戻したいか」を具体的に書いて指示すると、やり直しが少なく済みます。

*AdMob の初期化が遅い*: 初期化が遅れると、最初の広告表示も遅れます。Expo Router を使うプロジェクトでは、`app/_layout.tsx` のようなルートのレイアウトで一度だけ `mobileAds().initialize()` を呼ぶよう指示します。初期化の完了を待ってから広告を要求する形にしておくと、読み込み失敗も減らせます。

## App Store 審査フェーズ：引っかかりやすいポイント

審査で止まりやすい項目は決まっています。事前に潰しておくだけで、やり取りの往復が減ります。

**Guideline 2.1（App Completeness）**

クラッシュする、主要機能が動かない、といった状態は当然リジェクトの対象です。TestFlight で実機を丁寧に確認すれば、提出前に見つけられます。生成されたコードは、シミュレーターと実機で挙動が違うことがあるため、実機での確認を省かないようにしています。

**Guideline 4.1（Copycats）**

Apple の公式ガイドラインには、他の人気アプリをそのまま真似したり、名前や UI を少し変えただけで自分のものとして出したりしてはいけない、という趣旨が書かれています。壁紙・タイマー・電卓のように似たアプリが多い分野では、この点が問われやすくなります。対策は、「このアプリでしかできないこと」を最低 1 つ作ることです。UI の細部や、ターゲットを絞った切り口でも構いません。

**Guideline 3.1.1（In-App Purchases）**

サブスクリプションを実装する場合は、提出前に次の 4 点をサンドボックスアカウントで確認します。

- 購入が完了するか
- 購入直後にプレミアム機能が解除されるか
- キャンセル後に正しく元の状態へ戻るか
- 再インストール後も購入の復元が動くか

課金フローが壊れていれば、審査で止まります。ここは審査に出す前に、必ず自分の手で一周してください。

**プライバシー情報（PrivacyInfo.xcprivacy）**

Apple は、アプリや SDK に「プライバシーマニフェスト」（PrivacyInfo.xcprivacy）を含めること、特定の API を使う場合はその理由を宣言することを求めています。宣言が足りないと、App Store Connect から指摘のメールが届いたり、アップロード時に ITMS-91053 のようなエラーが出たりすることがあります。AdMob や Firebase、RevenueCat などの SDK を追加したら、各 SDK を最新版に保ち、ビルドの警告に宣言漏れが出ていないかを確認します。Rork に任せきりにせず、出力された内容は自分の目で確かめておくと安心です。

## リリース後の最初の 1 ヶ月

公開した直後は、何もしなければほとんどダウンロードは発生しません。最初の動きは、自分で作る必要があります。

私が行っている「リリース直後の定石」は次の 4 つです。

1. **身近な方への案内**: 最初の 10〜20 ダウンロードは、知人への案内でまかないます。ただし、評価やレビューの依頼を見返りと引き換えにすることは避けます。
2. **SNS への投稿**: X・Instagram・Threads などで、アプリが実際に動く様子を見せます。静止画より短い動画のほうが届きやすいと感じています。
3. **レビュー依頼の実装**: Expo では `expo-store-review` の `requestReview()` を使えます。お気に入り登録の直後のように、良い体験をした瞬間に出すのが基本です。ボタンから呼ぶ、起動直後に出す、といった使い方は公式ドキュメントでも避けるよう案内されています。
4. **ASO（キーワード最適化）の初期設定**: タイトル・サブタイトル・キーワードフィールドを埋めます。最初から完璧でなくて構いません。まず入れて、毎月見直します。

**最初の収益までの期間感（試算）**

ここからは実績ではなく、前提を置いた試算です。数字は私の想定であり、カテゴリや国によって大きく変わります。

<thead>
<tr><th>前提</th><th>値</th></tr>

<tbody>
<tr><td>1 日のアクティブユーザー（DAU）</td><td>100 人</td></tr>
<tr><td>1 人あたりの 1 日の広告表示回数</td><td>3 回</td></tr>
<tr><td>eCPM（1,000 回表示あたりの収益）</td><td>1〜3 ドル</td></tr>

この前提だと、月の表示回数は 100 人 × 3 回 × 30 日 = 9,000 回です。収益は 9〜27 ドル、円にすると約 1,350〜4,050 円になります。つまり 100 DAU の段階では、広告収益は「月数百円から数千円」の規模です。

サブスクリプションは、100 DAU で転換率 1〜3% と仮定すると 1〜3 人です。月額 500 円なら月に 500〜1,500 円で、ここからストア手数料が引かれます。

少ないと見るか、始まりと見るか。私は後者です。**1 円でも、使った方が自分の意思で支払ってくださったという事実は、数字以上の手応えになります。** 広告だけで月数万円を目指すなら、DAU を桁で伸ばす計画が必要になる、というのも同じ試算から見えてきます。

## 収益を伸ばすための改善サイクル

最初の収益が出たら、次の 3 つを順に回します。

**ダウンロードを伸ばす（アクイジション）**

ASO の継続的な見直しは、費用をかけずに続けられる施策です。月に 1 回、競合のキーワードの変化を確認し、自分のキーワードフィールドを更新します。スクリーンショットの比較テストは、App Store Connect の Product Page Optimization で行えます。

**継続率を上げる（リテンション）**

プッシュ通知は、使い方次第で継続率に効きます。「毎日の○○が届きました」のように習慣に結びつく通知が合うと感じています。「3 日間開いていません」のような呼び戻し型は目に留まりやすい一方、頻度が高いと通知の許可を外される原因になります。私の運用では、週 1 回程度を出発点に置いています。通知設計を含めた継続率の育て方は、[Rork アプリのリテンション・LTV 最大化 — Day1 から長期ユーザーを育てる設計](/articles/rork-business/rork-retention-ltv-maximization-guide)で詳しく扱っています。

**課金率を上げる（マネタイズ）**

アップグレード画面を出すタイミングが肝心です。お気に入りに追加した直後や、特定の機能を 2 回使った後のように、価値を感じた瞬間に出すほうが、起動直後に出すより反応が良いと考えています。

「年額プランを先に見せる」「月額との差額を明示する」といった画面の工夫も、転換に影響します。RevenueCat ではペイウォールの比較検証ができるので、変更したら必ず数値で確かめます。

## 長期運用の実態

リリースから半年〜1 年がたつと、収益が保たれるアプリと、右肩下がりのアプリに分かれていきます。

私の観察では、分かれ目の一つは更新の頻度です。ただし、更新が検索順位を押し上げる仕組みについて、Apple が公式に明言しているわけではありません。ここは経験則として受け取ってください。事実として言えるのは、放置したアプリには新しい競合が重なっていき、レビューへの返信や不具合の修正も止まる、ということです。

Rork は「小さな改善を素早く出す」ことに向いています。ボタンの色を変える、新しいコンテンツを足す、といった変更を、AI への指示で済ませられます。この機動力が、個人での長期運用を現実的にしてくれます。

## 最後に

**まず、公開前のチェックリストに「費用」「実機確認」「課金フローの一周」の 3 行を足してみてください。**

Rork が解決してくれるのは「作る」部分です。何を作るか、どう出すか、どう収益化し、どう改善するか——その判断は、引き続き自分の手元に残ります。この記録が、これから公開に向かう方の叩き台になれば幸いです。
