月次の収益レポートを開いて、先月と今月の数字がほとんど同じだと気づいた夜がありました。ダウンロードは順調に積み上がっているのに、収益のグラフだけが横に寝たままです。胃のあたりが重くなったのを、いまでも覚えております。

姉妹記事の [Rork で作るモバイルアプリの収益化入門](/articles/rork-business/rork-mobile-app-monetization-foundations-ads-iap-subscription) では、収益化モデルの全体像と判断軸を整理しました。本記事はその先、つまり「止まった収益を動かすために、何を実装し、何を運用するか」の具体的な話です。

最初にお伝えしたいのは、ここに書く施策の効果は、アプリの種類や地域によって大きく変わるということです。数字は目安として読んでいただき、ご自身のアプリでは必ず小さく試してから広げていただければ幸いです。

## 月10万円の壁の正体

「月10万円」は、個人開発が副業として成り立つ最初の目安だと感じています。そして多くの方が、ここで止まります。月1万円までは、アプリを作って広告を載せれば運次第で届くことがあります。けれども、その先は「同じやり方の延長」では動きません。

私が壁と呼んでいるのは、次のような状態です。アプリは作れていて、ストアにも出ていて、ある程度ダウンロードもされています。それでも収益が月数千円から1万円前後で止まっているのです。この状態から抜けるには、収益化を「実装」の仕事から「運用」の仕事へ切り替える必要がありました。

## 戦略マップ — 4 つのレバー

動かせるレバーは、大きく 4 つです。順番に深掘りします。

ひとつめは広告 eCPM の最大化です。eCPM は 1,000 表示あたりの収益で、表示回数が同じでも eCPM が上がれば収益はそのまま増えます。

ふたつめは IAP の価格と訴求の最適化です。商品の並べ方、価格、購入までの導線を整えて、課金率と客単価の両方を押し上げます。

みっつめはサブスクの継続率です。月次解約率が下がると、1 人のユーザーから受け取れる総額（LTV）が大きく伸びます。

よっつめは ASO による自然流入の増加です。アプリ本体を変えなくても、ストアの見せ方だけで入口の数が変わります。

4 つを同時に動かそうとして、私は一度、何が効いたのか分からなくなりました。いまは、アプリの状況を見て 1 つずつ深掘りする進め方にしています。

## 広告 eCPM を押し上げる実装

広告で稼ぐアプリの場合、まず見直すのは eCPM です。実際に効果を確認できたものを 3 つ挙げます。

ひとつめはメディエーションの活用です。AdMob 単独ではなく、複数の広告ネットワークを組み合わせると、表示のたびに最も入札額の高い広告が選ばれます。私の手元では、導入前後で eCPM が目に見えて改善しました。ネットワークの顔ぶれと提供状況は変わりやすいので、導入時に各社の最新の対応状況を確かめておくと安心です。

```typescript
// AdMob Mediation の基本設定
import mobileAds, {
  AdsConsent,
  AdsConsentStatus,
  MaxAdContentRating,
} from "react-native-google-mobile-ads";

// 起動時に一度だけ実行
mobileAds()
  .setRequestConfiguration({
    maxAdContentRating: MaxAdContentRating.PG,
    tagForChildDirectedTreatment: false,
    tagForUnderAgeOfConsent: false,
  })
  .then(async () => {
    // GDPR 同意取得（EU 圏ユーザーには必須）
    const consentInfo = await AdsConsent.requestInfoUpdate();
    if (consentInfo.status === AdsConsentStatus.REQUIRED) {
      await AdsConsent.showForm();
    }

    // SDK 初期化
    await mobileAds().initialize();
  });

// メディエーション設定は AdMob ダッシュボードで行う
// ローカルコードは標準の AdMob 実装そのまま
```

ふたつめはビディングの有効化です。従来のウォーターフォール方式からリアルタイム入札に切り替えると、eCPM がさらに上向くことが多くなります。AdMob の管理画面でビディングの対象ネットワークを有効にするだけで、アプリ側のコードは変わりません。

みっつめは広告フォーマットの組み合わせです。壁紙アプリ（『[綺麗な壁紙](https://apps.apple.com/jp/app/id706533906)』など）で落ち着いたのは、ホーム下部のバナーを常時、画像の詳細表示では数回に 1 回のインタースティシャル、壁紙の設定時には任意のリワードという形でした。リワード広告の eCPM はバナーよりはるかに高くなりやすく、「設定時の任意操作」に結びつけると使い心地を損ないません。

**広告は、ユーザーの手を止めない場所にだけ置く。** 最初のうちは表示回数を稼ぎたくて置きすぎ、レビューが荒れました。この線引きはそこから引いたものです。

## IAP の価格と訴求を整える

IAP では、課金率と客単価の両方を見ます。効果が大きかった施策は 3 つです。

ひとつめは、価格段階を 3 つ用意することです。商品が 1 つだと「買うか、買わないか」の判断になりますが、3 つあると「どれを買うか」の判断に変わります。比較対象があると中位が選ばれやすくなる、いわゆるデコイ効果です。私のアプリでも中位プランの選択率がいちばん高くなりました。

```typescript
const TIER_PRODUCTS = [
  { sku: "starter", price: "¥240", features: ["広告非表示"] },
  { sku: "standard", price: "¥480", features: ["広告非表示", "Pro 機能", "テンプレート 50 種"], recommended: true },
  { sku: "deluxe", price: "¥980", features: ["広告非表示", "Pro 機能", "テンプレート 200 種", "クラウドバックアップ"] },
];

function PricingScreen() {
  return (
    <View>
      {TIER_PRODUCTS.map((tier) => (
        <View key={tier.sku} style={tier.recommended ? styles.recommended : styles.normal}>
          {tier.recommended && <Badge text="おすすめ" />}
          <Text style={styles.price}>{tier.price}</Text>
          {tier.features.map((f) => <Text key={f}>✓ {f}</Text>)}
          <Button title="購入" onPress={() => handlePurchase(tier.sku)} />
        </View>
      ))}
    </View>
  );
}
```

ふたつめは、期限付きオファーです。たとえば初回起動から 24 時間だけ割引にすると、未購入の方の一部が動いてくださいます。ただし、ダークパターンと紙一重の施策でもあります。本当に期限のあるオファーだけに使い、見せかけのカウントダウンは避けるようにしています。

```typescript
function useFirstLaunchTimer() {
  const [secondsLeft, setSecondsLeft] = useState<number>(0);

  useEffect(() => {
    const init = async () => {
      const firstLaunch = await AsyncStorage.getItem("first_launch_at");
      const firstLaunchAt = firstLaunch ? parseInt(firstLaunch) : Date.now();
      if (!firstLaunch) {
        await AsyncStorage.setItem("first_launch_at", String(Date.now()));
      }

      const offerEndsAt = firstLaunchAt + 24 * 60 * 60 * 1000; // 24 時間
      const interval = setInterval(() => {
        const remaining = Math.max(0, offerEndsAt - Date.now());
        setSecondsLeft(Math.floor(remaining / 1000));
      }, 1000);

      return () => clearInterval(interval);
    };
    init();
  }, []);

  return secondsLeft;
}
```

みっつめは、購入前に体験していただくことです。「広告を消すとこうなります」という状態を短時間だけ試せるようにしたところ、課金率が目に見えて上がりました。「買わないと使えない」から「使ってみて気に入ったら買える」へ、設計の向きを変えただけです。

## サブスク継続率を守る

サブスクで収益を伸ばすには、月次解約率（チャーン）を下げ続けることが近道です。解約率が半分になれば、LTV はおおよそ倍になります。効果を確認できた施策は 3 つです。

ひとつめは、決済失敗からの自動リカバリーです。カードの有効期限切れや与信エラーによる解約は、ユーザーの意思ではなく事務的な失敗です。適切にフォローすれば、かなりの割合を取り戻せます。以下は Web 側で Stripe を使う場合の例で、App Store や Google Play 経由の購読では、各ストアの猶予期間や課金リトライの設定が同じ役割を担います。

```typescript
// Stripe Webhook での決済失敗時の自動リカバリフロー
async function handleInvoicePaymentFailed(invoice: Stripe.Invoice) {
  const userId = invoice.metadata?.userId;
  const subscription = await stripe.subscriptions.retrieve(invoice.subscription as string);

  // 1. ユーザーへすぐ通知（リトライまでの時間を稼ぐ）
  await sendEmail(userId, {
    template: "payment_failed_retry",
    data: {
      retryUrl: invoice.hosted_invoice_url,
      nextAttemptAt: new Date(invoice.next_payment_attempt! * 1000),
    },
  });

  // 2. アプリ内バナーを表示するフラグを立てる
  await db.user.update({
    where: { id: userId },
    data: {
      paymentIssue: true,
      paymentIssueResolveBy: new Date(invoice.next_payment_attempt! * 1000),
    },
  });

  // 3. Stripe の Smart Retries が 3 回までリトライしてくれる
  // それでも失敗したら subscription.deleted イベントが来る
}
```

ふたつめは、価値の継続的な可視化です。ユーザーが「今月も払う価値があるか」を考えるのは、請求の通知が届く前後です。その手前で、今月の利用状況をまとめて送ります。私のアプリでは、利用統計を月末に届けるようにしてから、解約率が下がりました。

```typescript
// 毎月 25 日に送信する月次サマリーの例
async function sendMonthlySummary(userId: string) {
  const monthStart = startOfMonth(new Date());
  const monthEnd = endOfMonth(new Date());

  const usageStats = await db.usageEvent.aggregate({
    where: {
      userId,
      occurredAt: { gte: monthStart, lte: monthEnd },
    },
    _count: { _all: true },
    _sum: { quantity: true },
  });

  await sendEmail(userId, {
    template: "monthly_value_summary",
    data: {
      totalActions: usageStats._count._all,
      timeSavedMinutes: estimateTimeSaved(usageStats),
      topFeatures: await getTopFeatures(userId, monthStart, monthEnd),
    },
  });
}
```

みっつめは、解約まわりの導線です。Web 課金なら、解約ボタンを押した時点で「次回だけ割引」「一時停止」といった選択肢を見せられます。一方、App Store の購読は端末の設定側で解約される仕組みなので、アプリ内では設定画面への案内と、ストアが用意しているオファーの活用が中心になります。どちらの場合も、解約への道を 1 タップ先に残しておくことだけは外しません。

## ASO で入口を広げる

広告費をかけてダウンロードを買う方法は、個人開発では費用対効果が合いにくく、最終的に消耗しがちです。そこで自然流入、つまり ASO に力を入れました。効果があったのは 3 つです。

ひとつめは、タイトル・サブタイトル・キーワード欄の見直しです。限られた文字数の中に、検索されるのに競合の少ない語を優先して入れます。語の選定にはキーワード調査ツールを使いますが、ツールの数字は参考値で、最後は自分のアプリで検索して確かめます。

ふたつめは、スクリーンショットの出し分けテストです。App Store の製品ページ最適化や Google Play のストア掲載情報の試験運用で、画像の組み合わせごとにストア訪問からの変換率を比べられます。私のアプリでは、機能の画面そのままより、得られることを短い言葉で添えた画像のほうが反応が良い傾向でした。

みっつめは、多言語対応です。日本語と英語だけだったアプリを十数言語に広げると、ダウンロード数が目に見えて伸びることがあります。翻訳の下書きは AI に任せられる範囲が大きく、多言語化の入口はずいぶん低くなりました。ただし、ストア文言の最終確認は母語話者の目を通したほうが安全です。

## 見落としやすい落とし穴

ひとつめは、施策を一度に複数入れることです。何が効いたのか分からなくなります。1 つ変えたら 2 週間以上は見る、という間隔が、結局は最短でした。

ふたつめは、短期の収益に寄りすぎることです。広告を増やしたり課金を急かす画面を入れたりすると、その月の数字は上がっても、レビューが下がり、ランキングが落ち、長い目で見ると総額は減ります。私はこれを繰り返してから、ようやく身に付きました。

みっつめは、計測を後回しにすることです。Firebase Analytics などで行動を追っていないと、どこで離脱しているのかが見えません。収益を動かしたいなら、計測の整備がいちばん先です。

よっつめは、1 本のアプリに頼りきることです。ストアの規約変更や OS の更新、競合の参入で、収益が急に変わることがあります。収益源を複数に分けておくことは、個人開発の体力そのものです。

いつつめは、価格の根拠が薄いことです。「他のアプリが 480 円だから」ではなく、使ってくださる方が何にどれだけ価値を感じているかから逆算します。新しい価格を決める前に、数人のユーザーに話を聞くようにしています。

## 収益が伸びるアプリに共通していたこと

運用してきたアプリを見返すと、収益が安定するものには似た点がありました。

ひとつめは、価値提案がひと言で言えることです。「これができるアプリ」と言い切れるものは伸びます。「いろいろできる便利アプリ」は、最初にダウンロードされても続きません。

ふたつめは、毎日開く理由があることです。通知、新しいコンテンツ、進捗の見える化。何かが一つ、組み込まれています。

みっつめは、ユーザーとの対話が続いていることです。レビューへの返信や問い合わせへの丁寧な対応のような、地味な積み重ねが、口コミでじわじわ効いてきます。

## 次の一歩

収益が止まったときは、「作る」から「運用する」へ意識を切り替える合図なのだと思います。アプリを増やす前に、いまあるアプリの数字を見直す時間を取っていただければ幸いです。

最初の一歩として、ご自身のアプリの月次収益と、ユーザー 1 人あたりの月次収益（ARPU）を書き出してみていただければと思います。そのうえで、4 つのレバーのどれが最も手薄かを見ます。私も、いまも月初に同じ表を作って、いちばん弱いところから手を入れるようにしております。
