夜、表計算ソフトを開いて「アプリを出すまでにかかるお金」を書き出していたときのことです。Rork は無料、Supabase も無料、ビルドを担う Expo のサービス（以前の EAS）も無料——縦に並べた列の合計が、ほぼ 0 円になりました。

けれど、その表には欠けているものがありました。**いつ**払うか、という列です。

金額が小さくても、請求が重なる日は一点に集まります。そして一部のサービスは、請求ではなく「止まる」という形で、こちらに支払いを迫ってきます。ここでは、公式の料金ページを 2026年11月20日にあらためて確かめ、初年度の請求の順番を並べ直した記録をお伝えします。最初の版から料金の名前が一つ変わっていたので、その点も含めて書き直しました。

想定している読者は、Rork で画面を作り始めたばかりで、「どこからお金がかかるのか」「いつ何を払うのか」を一度で見通したい方です。最後に、その日付を予定表へ取り込むための小さなスクリプトも置いておきます。

## 請求が届く順番は、作業の順番とほぼ同じです

並べてみて気づいたのは、お金の動く順番が、作業の進み方にそのまま重なることでした。

1. **画面を作る段階**——Rork Free で足ります。ただし Free は Design mode だけで、日次の上限 5 クレジットのほうが月の枠より先に効いてきます。減り方の見通しは[無料枠の日次上限を扱った記事](/articles/rork-basics/rork-free-tier-daily-five-credit-cap-planning)に整理しました。
2. **動くアプリにしたくなる段階**——最初の請求は、ほぼ確実に Rork の有料プラン $20 になります。公式は、デザインを動くアプリに変える Build mode を有料プランの機能としているためです。ビルドはそれを走らせたメッセージの費用に上乗せされ、クラウドの iOS シミュレータは動いているあいだ 1 分 0.2 クレジットずつ減ります。
3. **ストアに出す段階**——ここで Apple の 99 USD と Google Play の US$25 が重なります。Apple 側で自分が済ませる手続きは[公開前に Apple 側で済ませておく手続きの記事](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)にまとめました。
4. **リリース直前の追い込み**——Expo の無料ビルドは月 15 本ずつです。数字だけ見れば足りそうですが、低優先度のキューは混む時間帯に 90 分以上待つことがある、と料金ページ自体に書かれています。本数より「待ち時間」が先に効くのです。
5. **公開から数週間後**——Supabase の無料プロジェクトが、使われない週に止まっていないかを確かめる時期です。

つまり初年度の請求は、1 月から 12 月へ均等に並ぶのではなく、「出す直前」に集まります。待ち時間まで含めた日数の見積もりは、[リリースまでに待たされる日数を内訳にした記事](/articles/rork-basics/rork-one-week-release-promise-waiting-days-breakdown)と合わせて読んでいただくと、予定が立てやすくなると思います。

Apple の 99 USD は毎年、Google Play の US$25 は最初の一度きりです。2 年目以降も続くのは前者だけ、という違いは、早めに頭に入れておくと楽になります。

## 「請求される」と「止まる」は、別の問題です

私が見落としかけたのは、ここでした。それまでは請求額だけを見張っておりましたが、無料枠の終わり方は、サービスごとにまったく違うのです。

Supabase の停止は、請求書を伴わないぶん、気づくのが遅れやすい種類の出来事です。画面は開くのにデータだけ返ってこない、という症状になりうるからです。Apple の失効も、更新を忘れたあとに App Store からアプリが見えなくなった、という相談が開発者フォーラムに繰り返し上がっています。

**請求書より先に、止まる日付を予定表に入れておく。** これが、今回の棚卸しで引いた線引きです。

## よくある三つの誤解

**誤解 1: 「Rork Free のまま、ストアまで出せる」** 公式は Free を Design mode の範囲とし、動くアプリにして公開するには有料プランが要る、と書いています。「無料で作れる」は「無料で出せる」とは違うのです。

**誤解 2: 「余ったクレジットは翌月に持ち越せる」** プランに含まれる月の枠は、使い残しても繰り越されません。持ち越せるのは、追加で買った分（1 クレジット $0.22）だけです。月末に慌てて使い切る必要はありませんが、ためておくこともできない、と覚えておくと計画が楽になります。

**誤解 3: 「Supabase Pro は、プロジェクトをいくつ作っても $25」** $25 に含まれる計算資源は 1 プロジェクト分（Micro）で、2 つ目からは 1 つにつき計算資源の費用が加わります。公式の例では、Micro のプロジェクト 2 つで月 $35 です。

## 予定表に入れる日付を、ファイルで作ります

ここまでの日付を手で予定表に打ち込むと、私はたいてい 1 行どこかを落とします。そこで、標準ライブラリだけで動く Python スクリプトで `.ics` ファイルを作り、カレンダーに読み込ませることにしました。Mac の標準のカレンダーでも、Google カレンダーでも取り込めます。

解決するのは「年に一度・月に一度・週に一度の日付が、それぞれ別の場所に散らばる」問題です。

```python
#!/usr/bin/env python3
# first_year_bills.py — 初年度の請求日と「止まる日」を .ics に書き出す
# 使い方: python3 first_year_bills.py 2026-11-20 2026-12-05 > bills.ics
#   1つ目: Rork の有料プランを始めた日 / 2つ目: Apple に登録した日
import sys
import uuid
from datetime import date, datetime, timedelta, timezone

def event(summary, start, rrule=None, alarm_days=0):
    stamp = datetime.now(timezone.utc).strftime("%Y%m%dT%H%M%SZ")
    lines = [
        "BEGIN:VEVENT",
        f"UID:{uuid.uuid4()}@first-year-bills",
        f"DTSTAMP:{stamp}",
        f"DTSTART;VALUE=DATE:{start:%Y%m%d}",
        f"DTEND;VALUE=DATE:{start + timedelta(days=1):%Y%m%d}",
        f"SUMMARY:{summary}",
    ]
    if rrule:
        lines.append(f"RRULE:{rrule}")
    if alarm_days:
        lines += [
            "BEGIN:VALARM",
            "ACTION:DISPLAY",
            f"DESCRIPTION:{summary}",
            f"TRIGGER:-P{alarm_days}D",
            "END:VALARM",
        ]
    lines.append("END:VEVENT")
    return lines

def main():
    if len(sys.argv) != 3:
        sys.exit("usage: first_year_bills.py RORK_PAID_START APPLE_ENROLL")
    rork_paid = date.fromisoformat(sys.argv[1])
    apple = date.fromisoformat(sys.argv[2])
    today = date.today()
    first_of_next = (today.replace(day=1) + timedelta(days=32)).replace(day=1)

    out = ["BEGIN:VCALENDAR", "VERSION:2.0", "PRODID:-//first-year-bills//JA"]
    out += event("Rork Free クレジットのリセット（暦月の初め）",
                 first_of_next, "FREQ=MONTHLY;BYMONTHDAY=1")
    out += event("Rork 有料プランの更新日（初回購入日が起点）",
                 rork_paid, f"FREQ=MONTHLY;BYMONTHDAY={rork_paid.day}", 2)
    out += event("Apple Developer Program の更新（99 USD）",
                 apple.replace(year=apple.year + 1), "FREQ=YEARLY", 30)
    out += event("Supabase 無料プロジェクトの状態を確かめる",
                 today + timedelta(days=6), "FREQ=WEEKLY")
    out.append("END:VCALENDAR")
    sys.stdout.write("\r\n".join(out) + "\r\n")

if __name__ == "__main__":
    main()
```

macOS の標準の `python3` で、次のように動かします。

```bash
python3 first_year_bills.py 2026-11-20 2026-12-05 > bills.ics
grep -c BEGIN:VEVENT bills.ics   # 4 と表示されれば、4 件の予定ができています
open bills.ics                    # カレンダーが開き、取り込み先を尋ねられます
```

なぜこう書くのか、を三つだけ添えます。

- **終日の予定にしている**——時刻つきにすると、海外のサービスの更新日が時差で前後の日にずれて見えます。日付だけで持つほうが、請求のメールと照らし合わせやすいのです
- **Apple だけ 30 日前、Rork は 2 日前に通知**——年に一度の更新は、カードの期限切れなど準備に時間がかかることがあるためです
- **Supabase は「6 日後から毎週」**——1 週間の停止条件より 1 日早く、自分で開く日を作っています

一つだけ注意があります。初回購入日が 29〜31 日の場合、`BYMONTHDAY` だけでは短い月に予定が出ません。その場合は、月末近くの別の日に置き換えて登録してください。Rork 側の更新日が短い月にどう扱われるかは、公式の文書では確認できておりません。

Before と After で言えば、以前の私は「請求メールが来たら考える」状態で、After は「止まる 1 日前に、自分の側から開く」状態です。後者のほうが、ほんの少しだけ胃が軽くなりました。

## 次に詰まりやすいのは、プランを動かす前の確認です

日付が予定表に入ると、次に考えたくなるのは「有料プランをいつやめるか」です。やめる前に、Rork から取り出したコードが外で組み直せるかを確かめておくと安心です。その段取りは[プラン変更の前に、取り直したコードが Rork の外で組み直せるか確かめる記事](/articles/rork-basics/rork-export-rebuild-check-before-plan-change)に書きました。

Supabase をまだつないでいない方は、[Rork に Supabase をつなぐときに要る二つの値を扱った記事](/articles/rork-ai/rork-connect-supabase-two-values-publishable-key-project-url)から始めると、無料プロジェクトのどこを見ればよいかが分かります。

金額の大きい項目より、日付のずれた項目のほうが、あとで手間を増やします。アプリを長く運用していると、年に一度だけ来る支払いほど記憶から落ちる、と感じるのです。

まずは今日、上のスクリプトに二つの日付を渡して、予定表に 4 件を入れるところから始めていただければと思います。
