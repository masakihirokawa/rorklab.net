ある朝、個人開発で運用しているアプリのレビュー欄に「ホーム画面にウィジェットが欲しい」という要望が並んでいるのを見つけたとき、私が最初に考えたのは機能の作り方ではなく、その機能を何年運用し続けられるか、でした。

ウィジェット、Live Activities、Dynamic Island。これらは Apple のネイティブ領域に深く根を張った機能で、React Native（Expo）の世界からは橋を一本架けないと届きません。Rork の標準ビルドは React Native でクロスプラットフォームに作りますが、Rork Max はネイティブ Swift を生成し、こうした Apple 固有機能をそのまま引き出せます。料金は標準の Rork が月25ドルから、Rork Max が月200ドル。この8倍の差を「機能の価格」として見ると判断を誤ります。本当に見るべきは、その機能を抱えたまま何年も運用する総コストです。

## なぜ「ウィジェットが欲しい」が分岐点になるのか

通常の画面追加や API 連携であれば、React Native のまま十分に戦えます。判断が割れるのは、OS の実行環境そのものに食い込む機能が要件に入ったときです。

ウィジェットは独立した拡張ターゲットで動き、タイムラインという独自の更新モデルを持ちます。Live Activities はロック画面と Dynamic Island に常駐し、ActivityKit を通じて状態を更新します。React Native からこれらを使う場合、結局はネイティブモジュール（Swift で書いた拡張）を自分で抱え、JS 側とブリッジでつなぐことになります。つまり「クロスプラットフォームで一本化したかったのに、Apple 専用のネイティブコードを別途維持する」状態に陥ります。

ここが分岐点です。Apple 固有機能が一過性の飾りなら React Native のまま拡張で粘る価値があります。けれど、その機能がアプリの中心的な体験になるなら、ネイティブを別管理する負債が毎年効いてきます。

## 機能単価ではなく「1機能あたりの年間維持コスト」で見る

月200ドルという数字は、年間にすると2,400ドルです。一見すると高く見えますが、これを「この価格で実装できる機能の数」ではなく「この価格で維持し続ける機能の数」に置き換えると、判断材料の質が変わります。

私が実際に使っている概算の手順は次の通りです。

1. その Apple 固有機能を React Native + 自前ネイティブモジュールで作った場合の、年間の保守時間を見積もる（OS アップデート追従・拡張ターゲットのビルド調整・ブリッジの再検証）。
2. その時間に自分の時間単価を掛けて、年間の隠れコストを出す。
3. Rork Max の年間2,400ドルと比較する。同時に、Rork Max なら不要になる「ブリッジ保守」の時間も差し引く。
4. 機能が1つだけなら React Native 拡張が安いことが多い。機能が2つ3つと増え、いずれも Apple 固有なら、Rork Max の固定費のほうが安くなる損益分岐点が現れる。

ポイントは、ネイティブモジュールの維持コストは「作った瞬間」ではなく「毎年の iOS メジャーアップデートのたびに」発生することです。WidgetKit のリロードポリシーや ActivityKit の挙動は版を追うごとに調整が入ります。一度書いて終わりではない機能ほど、固定費でまとめて面倒を見てもらう設計が効いてきます。

## React Native からウィジェットへ橋を架ける現実

「React Native のまま拡張で粘る」を選ぶ場合、何を抱えることになるのかを具体的に見ておきます。ウィジェット本体はどのみち Swift で書きます。

```swift
import WidgetKit
import SwiftUI

struct StatusEntry: TimelineEntry {
    let date: Date
    let summary: String
}

struct StatusProvider: TimelineProvider {
    func placeholder(in context: Context) -> StatusEntry {
        StatusEntry(date: Date(), summary: "—")
    }

    func getSnapshot(in context: Context, completion: @escaping (StatusEntry) -> Void) {
        completion(StatusEntry(date: Date(), summary: readShared()))
    }

    func getTimeline(in context: Context, completion: @escaping (Timeline<StatusEntry>) -> Void) {
        let entry = StatusEntry(date: Date(), summary: readShared())
        // 15分後に一度だけ更新（リロード予算を浪費しない方針）
        let next = Calendar.current.date(byAdding: .minute, value: 15, to: Date())!
        completion(Timeline(entries: [entry], policy: .after(next)))
    }

    private func readShared() -> String {
        let defaults = UserDefaults(suiteName: "group.com.example.app")
        return defaults?.string(forKey: "widget_summary") ?? "—"
    }
}
```

React Native アプリでこのウィジェットにデータを渡すには、App Group を共有ストレージにして、JS 側からネイティブモジュール経由で書き込む必要があります。

```ts
// JS 側。ネイティブモジュールを自前で用意し、App Group の UserDefaults に書く
import { NativeModules } from "react-native";

const { WidgetBridge } = NativeModules;

export async function pushWidgetSummary(summary: string) {
  // WidgetBridge は Swift 側で App Group に書き込み、WidgetCenter.reloadAllTimelines() を呼ぶ
  await WidgetBridge.setSummary(summary);
}
```

このブリッジ（`WidgetBridge`）は自分で書いて、自分で iOS のアップデートに追従させ続けます。Rork Max を選ぶと、この層がそもそも要らなくなります。ウィジェットも本体も同じ Swift の世界にあるので、App Group のキー名のズレや、拡張ターゲットの署名設定でつまずく時間が消えます。私自身、ブリッジ起因の不具合は「機能のバグ」ではなく「境界のバグ」で、再現も修正も読みにくいと感じています。この読みにくさを毎年買い続けるかどうかが、判断の核心です。

## Live Activities が入るなら天秤はさらに傾く

Live Activities と Dynamic Island は、ウィジェット以上にネイティブ寄りの機能です。ActivityKit でアクティビティを開始し、プッシュまたはアプリ内から状態を更新します。

```swift
import ActivityKit

struct DeliveryAttributes: ActivityAttributes {
    struct ContentState: Codable, Hashable {
        var stage: String
        var etaMinutes: Int
    }
    var orderId: String
}

func startDelivery(orderId: String) throws {
    let attributes = DeliveryAttributes(orderId: orderId)
    let initial = DeliveryAttributes.ContentState(stage: "受付", etaMinutes: 30)
    _ = try Activity.request(
        attributes: attributes,
        content: .init(state: initial, staleDate: nil)
    )
}
```

React Native からこれを扱うには、開始・更新・終了の各操作を全てネイティブ側に持たせ、JS とブリッジでやり取りします。ウィジェットの App Group 共有とは別系統の保守がもう一つ増えるわけです。ここまで来ると、Apple 固有機能が2系統になり、前述の損益分岐点を越えやすくなります。私の見立てでは、Live Activities が「あると嬉しい」ではなく「これが体験の主役」になるアプリは、最初から Rork Max で組むほうが数年単位では軽くなります。

## 片方に寄せきれないときの両刀運用

現実には「iOS は深く、Android も捨てたくない」というアプリが少なくありません。その場合の落としどころは、全部を一本化しようとしないことです。

個人開発で複数のアプリを抱える私が現実的だと考える分割は、共通のビジネスロジック（料金計算・在庫判定などの仕様の核）を切り出して両系統で参照できる形にし、UI と OS 統合機能はそれぞれのネイティブに任せる構成です。Android と汎用画面は React Native 版 Rork、iOS の中心体験とウィジェット・Live Activities は Rork Max、という住み分けにします。

両刀にすると固定費は両方かかりますが、それでも成立する条件があります。

1. iOS と Android でリリースサイクルを完全同期させない（同日リリースを諦め、各プラットフォームの審査と検証に余裕を持たせる）。
2. 仕様変更は「核のロジック」を先に確定させ、各 UI 層へは後追いで反映する順序を固定する。
3. 機能フラグで「この機能は iOS のみ先行」を明示し、Android 版の遅れを欠陥ではなく計画として扱う。

両刀運用は贅沢に見えますが、Apple 固有機能を React Native に無理やり背負わせ続けるより、境界が素直で読みやすくなる場面があります。

## 最後に、何を基準に決めるか

決め手は機能の派手さではありません。「その Apple 固有機能を、来年も再来年も自分が面倒を見られるか」です。一機能・補助的なら React Native のまま拡張で粘る。中心的・複数なら Rork Max の固定費で保守時間を買う。Android が主軸なら無理に寄せない。この3つの問いに順に答えれば、月25ドルと月200ドルのどちらが自分にとって安いかは、わりとはっきり見えてきます。

まず手元のアプリで、いま要望に挙がっている Apple 固有機能を1つ書き出し、それを React Native + 自前ネイティブモジュールで何年運用するつもりか、を見積もってみてください。その数字が、価格表よりずっと正確な答えを返してくれます。
