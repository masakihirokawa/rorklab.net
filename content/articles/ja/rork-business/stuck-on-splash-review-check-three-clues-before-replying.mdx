土曜の朝、ストアのレビュー欄を開くと、星ひとつのレビューに「起動画面から進みません」とだけ書かれていました。端末名も、いつからなのかも書かれていません。返信欄にカーソルを置いたまま、何と書けばよいのか分からず、しばらく手が止まりました。

個人開発でアプリを長く運用していると、この種の一行は何度か届きます。最初のうち、私は「再インストールをお試しください」と急いで返していました。結果は芳しくありませんでした。直ったかどうかが分からないまま、同じ症状のレビューが別の言語でもう一件届いたのです。

最初にお伝えしたいのは、起動画面で止まる症状には、返信だけで片づくものと、次の配信で直さなければならないものが混ざっているということです。返信の前に3つの手がかりを確かめておくと、この二つを分けられます。

## なぜ「起動画面のまま」になるのか

Rork で作ったアプリ（React Native と Expo の構成）は、起動するとまず起動画面（スプラッシュ画面）を出し、アプリの中身の準備ができたところでそれを閉じます。閉じる合図を出すのはアプリ自身のコードです。

要するに、「起動画面のまま」というのは、閉じる合図が出なかった状態です。理由は大きく三つに分かれます。

- アプリの中身を読み込む途中で落ちて、起動をやり直しているとき
- 中身は読めているのに、閉じる合図の前に何かを待ち続けているとき
- 配信した更新（EAS Update）が合わず、前の版に戻ったうえで、どこかで引っかかっているとき

三つ目については、Expo の GitHub に、エラー回復で前の更新に戻ったあと起動画面のまま止まるという報告が上がっており、11月21日の時点で未解決です（[expo/expo#53933](https://github.com/expo/expo/issues/53933)）。Expo のエラー回復は、新しい更新で起動に失敗すると、前の更新やアプリに同梱された版へ戻して起動し直す仕組みです（[Error recovery](https://docs.expo.dev/eas-update/error-recovery/)）。仕組みそのものは利用者を守るためのものですが、戻った先で止まると、利用者からは「起動画面のまま」としか見えません。

## 手がかり1: どの更新で起動しているか

いちばん先に知りたいのは、そのアプリがいまどの中身で動いているかです。ところが、起動画面で止まっている人には画面の中を見てもらえません。そこで私は、**ふだんから設定画面の隅に、起動中の更新の情報を1行だけ出しておく**ようにしています。

```tsx
// components/BuildInfoLine.tsx
// 設定画面の最下部に置く1行。サポートで「この行を教えてください」と頼めるようにする
import * as Updates from 'expo-updates';
import { Text } from 'react-native';

export function BuildInfoLine() {
  // 開発中（Expo Go や開発ビルド）では updateId が null になる
  const id = Updates.updateId ? Updates.updateId.slice(0, 8) : 'embedded';
  const source = Updates.isEmergencyLaunch
    ? 'emergency' // 更新の読み込みに失敗し、同梱版で起動した
    : Updates.isEmbeddedLaunch
    ? 'embedded'  // アプリに同梱された版で起動した
    : 'ota';      // 配信した更新で起動した

  return (
    <Text style={{ fontSize: 11, opacity: 0.5, textAlign: 'center' }}>
      {`${Updates.runtimeVersion ?? '-'} / ${Updates.channel ?? '-'} / ${id} / ${source}`}
    </Text>
  );
}
```

`isEmergencyLaunch` が立っているのは、配信した更新の読み込みに失敗して、同梱された版で起動したときです。この値が `emergency` になっている人が複数いるなら、返信で済む話ではありません。直前に配った更新を疑う番です。

一方で、止まっている本人はこの行を見られません。ですから、この行が役に立つのは「一度は開けたが、ある日から止まった」人や、同じ端末の家族の方に見てもらう場面です。手がかりとしては半分ですが、ゼロよりはずっと前に進めます。

## 手がかり2: 直前に何を配ったか

二つ目は、自分の側の記録です。レビューの日付と、自分が更新を配った日付を並べます。

- ストアの審査を通した新しい版を出した日
- EAS Update で中身だけを配った日（Rork の画面から公開した場合も含む）
- 段階的な公開の割合を上げた日

止まったという報告が、どれかの直後に集まっているなら、その配信が原因の候補です。逆に、何も配っていない時期の報告であれば、利用者の端末側（空き容量・通信・OS の更新）を先に疑ってよいのかもしれません。

私はここで一度、失敗しております。報告を読んだとたんに直前の更新を取り下げたところ、本当の原因は端末側の容量不足でした。取り下げた更新には別の修正も入っていたので、無関係な不具合まで戻してしまったのです。**取り下げるのは、日付を並べてから。** これだけは、急いでいる日にも省かないようにしています。

段階的な公開で割合を上げる前の見極め方は、[最初の5%でクラッシュなしの割合を見る前に待つべき件数](/articles/app-dev/staged-rollout-first-five-percent-crash-free-needs-sample-size-wait-before-proceed)に書きました。

## 手がかり3: 起動画面を閉じる処理が待ち続けていないか

三つ目は、コードの側です。Rork が書いたコードでも、起動画面を閉じる前に、フォントの読み込み・ログイン状態の確認・設定の取得などを待っていることがあります。そのどれか一つが返ってこないと、起動画面は閉じません。通信の弱い場所で開いた人だけが止まる、という症状はたいていこれです。

対策は、待つ時間に上限を置くことです。

```tsx
// app/_layout.tsx の一部
// 準備が終わらなくても、8秒で起動画面を閉じて先へ進める
import * as SplashScreen from 'expo-splash-screen';
import { useEffect, useState } from 'react';

SplashScreen.preventAutoHideAsync();

const SPLASH_LIMIT_MS = 8000;

export function useAppReady(prepare: () => Promise<void>) {
  const [ready, setReady] = useState(false);

  useEffect(() => {
    let done = false;
    const finish = () => {
      if (done) return;
      done = true;
      setReady(true);
      SplashScreen.hideAsync().catch(() => {}); // 二重に閉じても落とさない
    };
    const timer = setTimeout(finish, SPLASH_LIMIT_MS);
    prepare()
      .catch((e) => console.warn('prepare failed', e)) // 失敗しても先へ進む
      .finally(() => {
        clearTimeout(timer);
        finish();
      });
    return () => clearTimeout(timer);
  }, []);

  return ready;
}
```

なぜ失敗しても先へ進めるのかというと、起動画面で止まるよりも、中身が一部欠けた画面が出る方が、利用者は次の行動を選べるからです。設定が取れなければ既定値で開き、ログイン確認が返らなければログイン画面を出します。そのほうが「動かない」という一行は減るのです。8秒という値は私の目安で、アプリの重さに合わせて決めていただければと思います。

Rork に直してもらうときは、「起動画面を閉じる前に待っている処理を全部挙げて、8秒で先へ進むようにしてください」と、待っているものを列挙してもらうところから頼むと話が早く進みます。ログを添えて頼む段取りは、[エラーが出ないのに一覧が空のとき、直す前にログを頼む](/articles/rork-basics/rork-list-empty-no-error-ask-for-logs-before-fix-request)と同じです。

## 返信の文面をどう分けるか

3つの手がかりを確かめたら、返信を書きます。私は次のように分けています。

<table>
<thead>
<tr><th>確かめた結果</th><th>返信で伝えること</th><th>自分の側でやること</th></tr>
</thead>
<tbody>
<tr><td>直前の配信と時期が重なる</td><td>不具合として把握したこと、次の更新で直す予定</td><td>配信の取り下げを検討し、手がかり3を確認</td></tr>
<tr><td>配信と重ならず、報告が1件だけ</td><td>空き容量の確保と、アプリの再起動を一度</td><td>同じ症状が続くか、数日見る</td></tr>
<tr><td>通信の弱い場面で起きている</td><td>通信の安定した場所で一度開くこと</td><td>待ち時間の上限を入れる</td></tr>
</tbody>
</table>

「再インストールをお試しください」は、私はもう最初には書きません。再インストールすると端末に残っていたデータが消えることがあり、直らなかったときに失うものが大きいからです。

Android でクラッシュが白い画面のまま残り、「固まる」と書かれる別の症状は、[落ちたはずなのに「固まる」と書かれるとき](/articles/app-dev/expo-updates-android-crash-blank-activity-looks-frozen)で扱いました。起動画面ではなく白い画面のまま、という報告なら、こちらを先にご覧ください。

## まず今日できること

まずは、設定画面の隅に起動中の更新の情報を1行だけ置いて、次の版に入れていただければと思います。止まった本人には見えなくても、次に届く一行を読み解く手がかりになります。私自身、この1行を置いてから、レビュー欄を開く朝に胃が痛くなることが少し減ったと感じています。
