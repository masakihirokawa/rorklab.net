iOS 27 の変更点を一つずつ読み返していた夜、年齢確認の API に見慣れないエラーが三つ増えていることに気づきました。`declinedOnboarding`、`invalidAccount`、そして `network`。名前だけ見れば意味は分かりそうですが、私のアプリのコードは、この三つを受け取ったときに何をするのかを一行も決めていませんでした。

調べていくと、11 月 16 日に Expo の Issue（[#53549](https://github.com/expo/expo/issues/53549)）として、ちょうどこの件が報告されていました。`expo-age-range` は iOS 27 で増えた三つのケースに専用のエラーコードを付けておらず、JS 側からは区別できない、という内容です。Issue は報告とほぼ同時にクローズされていますが、11 月 17 日の時点で `main` のソースを読む限り、三つの対応はまだ入っていません。

最初にお伝えしたいのは、コードが付くのを待つ必要はない、という点です。エラーの「行き先」を先に三つ決めておけば、いまの版のままでも審査に出せるかたちにできます。

## いま JS に届くエラーの顔ぶれ

`expo-age-range` の iOS 側（`AgeRangeModule.swift` と `AgeRangeExceptions.swift`）を読むと、`requestAgeRangeAsync` から JS に届くものは次のように整理できます。iOS 26 より前の OS では確認の画面を出さず、`lowerBound: 18`（大人と同じ扱い）で返ってくる点も、あわせて覚えておくと迷いません。

Issue の報告者は、三つの意味を二つに分けて説明しています。`network` は一時的な失敗なので、少し待ってもう一度試します。`declinedOnboarding` と `invalidAccount` は、そのアカウントからは年齢の情報が得られないので、`ERR_AGE_RANGE_NOT_AVAILABLE` と同じ「情報なしで進む」道へ送ります。この整理には、私も同意しております。

## メッセージの文字列で分けようとして、手が止まりました

コードが無いなら、エラーの文言で見分ければよい——最初に書きかけたのは、`message` に「network」が含まれるかを調べる一行でした。ところが、届く文言は Swift のエラーをそのまま文字にしたもので、Expo が約束している値ではありません。OS の版や端末の言語設定で変わらない保証もありません。

そこで考え方を逆にしました。分かっているコードだけを確実に振り分け、**コードの無いものは「一度だけ待って試し、だめなら情報なしで進む」へまとめて送ります**。新しい三つのうち `network` だけは再試行で救える可能性があり、残りの二つは再試行しても結果が変わらないだけなので、一度の再試行で失うものはほとんどありません。

**分かるものは名前で分け、分からないものは利用者を止めない側へ倒します。** これが、今回いちばん大事にした線引きです。

## 三つの行き先に振り分ける最初のコード

次のコードは、年齢確認の結果を「進める」「待って再試行」「年齢情報なし」「実装を直す」に振り分けます。Rork で作ったアプリ（Expo）なら、年齢確認を呼んでいる画面の近くに置くだけで使えます。

```ts
import { requestAgeRangeAsync } from 'expo-age-range';

type AgeGateResult =
  | { kind: 'ok'; lowerBound: number | null; upperBound: number | null }
  | { kind: 'declined' }      // 利用者が共有を断った
  | { kind: 'noSignal' }      // 年齢情報が得られない（アカウント・サービス側の事情）
  | { kind: 'bug'; code: string }; // 依頼の形が不正。開発者が直す

const NO_SIGNAL_CODES = new Set(['ERR_AGE_RANGE_NOT_AVAILABLE']);

function codeOf(e: unknown): string | null {
  // ネイティブ由来のエラーは code を持つことがあるが、iOS 27 の3種は持たない
  const c = (e as { code?: unknown } | null)?.code;
  return typeof c === 'string' && c.startsWith('ERR_AGE_RANGE_') ? c : null;
}

const wait = (ms: number) => new Promise((r) => setTimeout(r, ms));

export async function checkAgeRange(threshold: number): Promise<AgeGateResult> {
  for (let attempt = 0; attempt < 2; attempt++) {
    try {
      const res = await requestAgeRangeAsync({ threshold1: threshold });
      return { kind: 'ok', lowerBound: res.lowerBound, upperBound: res.upperBound };
    } catch (e) {
      const code = codeOf(e);
      if (code === 'ERR_AGE_RANGE_USER_DECLINED') return { kind: 'declined' };
      if (code === 'ERR_AGE_RANGE_INVALID_REQUEST') return { kind: 'bug', code };
      if (code && NO_SIGNAL_CODES.has(code)) return { kind: 'noSignal' };
      // ここに来るのはコードの無いエラー（iOS 27 の network / declinedOnboarding / invalidAccount など）
      if (attempt === 0) {
        await wait(3000); // 通信の失敗なら、3 秒ほど待つと通ることがある
        continue;
      }
      return { kind: 'noSignal' };
    }
  }
  return { kind: 'noSignal' };
}
```

なぜこう書くのかを、三点だけ補っておきます。

- **`message` を一度も読まない**ようにしています。将来 Expo が三つにコードを付けたときは、`NO_SIGNAL_CODES` に足すか、再試行の対象を名前で絞るだけで済みます。
- **再試行は 1 回、待ち時間は 3 秒**にしています。年齢確認は起動直後や購入の直前に出ることが多く、何度も回すと利用者が画面の前で待たされます。
- **`bug` は利用者に見せる道ではありません**。境界の値を直すべきサインなので、開発中にだけ気づけるよう、ログや自分宛ての通知に流しておくのが安全です。

## 画面に出す文言を、行き先ごとに一つずつ

行き先が決まると、文言も迷わなくなります。私が下書きに置いたのは、次の三つでした。

- **待って再試行（2 回目も失敗する前）**: 「年齢の確認に少し時間がかかっています。もう一度お試しいただけます」
- **年齢情報なし**: 「年齢の情報を確認できなかったため、一部の機能を制限した状態で始めます。設定からいつでも確かめ直せます」
- **共有を断った**: 文言は出さずに、年齢情報なしと同じ扱いで進めます。同じ画面は何度も出しません

ここで「年齢情報なしのときに何を制限するか」は、アプリの中身と、配信する地域に求められる要件で決まります。私自身は、まず「制限した状態で始められる」ことを保証し、制限の中身はあとから詰める順番にしました。アプリが利用者の前で止まってしまうことのほうが、審査でも利用者の評価でも、はるかに痛いからです。

ストアの年齢区分そのものの考え方は、[共有ボタンだけなら「ソーシャルメディア機能」には当たりません](/articles/rork-business/app-store-social-media-capability-share-sheet-not-feed-13plus)で書いた内容とつながっています。

## Rork に頼むときは、行き先を先に渡します

Rork のチャットで年齢確認を足してもらうときも、エラーの行き先を先に書いておくと、生成されるコードがぶれにくくなります。私が下書きした依頼文の骨組みは、次のようなかたちです。

```text
年齢確認（expo-age-range の requestAgeRangeAsync）を、設定画面の「年齢を確かめる」から呼んでください。
結果は4つに分けます。
1. 成功: lowerBound を保存し、通常の画面へ
2. ERR_AGE_RANGE_USER_DECLINED: 制限モードで続行。同じ確認は自動で再表示しない
3. ERR_AGE_RANGE_INVALID_REQUEST: 利用者には出さず、console.warn だけ
4. それ以外（code が無いものを含む）: 3 秒待って1回だけ再試行し、だめなら制限モードで続行
error.message の文字列では判定しないでください。
```

最後の一文は、先ほど私が書きかけた「文言で見分ける」道に、生成されるコードが進まないための保険です。依頼の段階で「何で判定しないか」まで書いておくのが、いちばん手戻りが少ないと感じております。

## 審査に出す前に、手元で確かめる二つのこと

1. **iCloud にサインインしていないシミュレータで呼びます**。`ERR_AGE_RANGE_NOT_AVAILABLE` が返り、「年齢情報なし」の文言と制限モードに進むかを見ます。
2. **境界の値をわざと 1 歳差にして呼びます**（例: `threshold1: 16, threshold2: 17`）。`ERR_AGE_RANGE_INVALID_REQUEST` が利用者の画面に出ず、ログだけに残るかを見ます。

正直に書いておくと、iOS 27 で増えた三つのケースを、私の手元の実機でまだ再現できておりません。Issue の報告者も、Apple のドキュメントにもとづく対応で、実機では観測していないと断っています。だからこそ、コードの無いエラーを「止めない側」へまとめて送る書き方にしておく意味があるのだと思います。

公開前の手続き全体は、[Rork のアプリを公開する前に、Apple 側で自分が済ませておく手続き](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)にまとめています。審査で指摘を受けた場合の動き方は、[App Store でリジェクトされた時の対処辞典](/articles/rork-business/rork-app-store-rejection-survival-playbook)が手がかりになるはずです。

まずは、いま年齢確認を呼んでいる箇所の `catch` を開き、`message` を読んでいる行が無いかだけを確かめていただければ幸いです。そこが一行でも見つかれば、今日の作業はもう半分済んでいます。
