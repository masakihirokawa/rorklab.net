## App Store に選ばれる意味 — 数字で見るフィーチャーの威力

更新の公開日をカレンダーに書き込んだ夜、「この更新を Apple の編集チームに知らせる方法はないのだろうか」と、App Store Connect のメニューを上から順に開き直したことがあります。結論から言うと、入口はちゃんとありました。ただ、そこへたどり着くまでの私の理解は、半分が思い込みでした。

App Store の「Today」タブや「Apps」タブのバナーに載る「フィーチャー（注目アプリ）」は、個人開発者にとって憧れの枠です。掲載されたときの伸び方は、アプリのジャンルや掲載面によって大きく異なり、Apple が数字として示しているわけでもありません。ですので、ここでは掲載後の数字を語るのではなく、**推薦を出す側が事前に整えられること**に絞ってお話しします。

フィーチャーには主に以下の種類があります。

- **Today タブのストーリー記事**: Apple エディターが執筆する読み物形式。最も高い露出
- **Apps タブのバナー枠**: カテゴリ別の推薦表示
- **カテゴリ別「編集が選ぶ」**: 特定カテゴリ内のキュレーション

これらの枠は、Apple の Editorial チームが選んでいます。Apple は公式の案内で、デザインの質、独自性、アクセシビリティ、ローカライズ、最新の Apple 技術の活用といった点を見ていると説明しています。選定の中身までは外から分かりません。それでも、案内されている観点は自分のアプリで点検できます。Rork で作った個人開発のアプリであっても、点検を積み重ねておけば、推薦文に書ける材料は確実に増えます。

## ポイント 1: Apple のデザインガイドラインを土台にする

フィーチャーを考えるうえでの最初の土台は、**Apple Human Interface Guidelines（HIG）への準拠**です。Editorial チームがどこまで重く見ているかは分かりませんが、「Apple のプラットフォームに馴染んでいるか」は、使った瞬間に伝わる部分だと感じています。

### Rork Max で HIG 準拠を実現するコツ

Rork が出力する React Native / Expo のプロジェクトでは、iOS のネイティブに近いナビゲーションをそのまま使えます。次の設定を出発点にしています。

```tsx
// ✅ 推奨: iOS ネイティブ感を出すナビゲーション設定
import { Stack } from 'expo-router';

export default function AppLayout() {
  return (
    <Stack
      screenOptions={{
        // iOS 標準の大きなタイトル付きヘッダーを維持
        headerLargeTitle: true,
        headerTransparent: false,
        // 標準の遷移アニメーション
        animation: 'slide_from_right',
      }}
    />
  );
}
// 期待する出力: iOS標準のナビゲーションスタック（カード遷移）が有効になる
```

**チェックリスト（HIG 対応）**:

- セーフエリア（ノッチ・Dynamic Island・ホームインジケーター）を正しく避けている
- SF Symbols を使用してアイコンに統一感を持たせている
- 最小タッチターゲットサイズ 44×44pt を守っている
- Dynamic Type（文字サイズ変更）に対応している
- ダークモード・ライトモード両方に対応している

Rork へのプロンプトに「iOS Human Interface Guidelines に沿ってください」と添えると、方向は揃いやすくなります。ただ、セーフエリアや Dynamic Type の取りこぼしは残りますので、生成のあとに実機で文字サイズを最大にして確かめるところまでが一組の作業だと考えています。

## ポイント 2: アクセシビリティを後回しにしない

Apple は **アクセシビリティを重く見ている**ことを公式に何度も示しており、フィーチャーの観点としても案内されています。VoiceOver や動的テキストサイズへの対応は、あとから足すと画面ごとに手戻りが出ます。作り始めの段階で入れておく方が、結局は軽く済みます。

```tsx
// ✅ アクセシビリティ対応の実装例
import { View, Text, TouchableOpacity, AccessibilityInfo } from 'react-native';

export function ProductCard({ name, price, onPress }: Props) {
  return (
    <TouchableOpacity
      onPress={onPress}
      // VoiceOver 用の説明文
      accessible={true}
      accessibilityLabel={`${name}、価格 ${price}円`}
      accessibilityHint="タップして詳細を表示"
      accessibilityRole="button"
    >
      <View>
        <Text>{name}</Text>
        <Text>{price}円</Text>
      </View>
    </TouchableOpacity>
  );
}
// 期待する出力: VoiceOver使用時に「商品名、価格 ○○円。タップして詳細を表示。ボタン」と読み上げられる
```

**最低限実装すべきアクセシビリティ機能**:

- すべてのボタン・インタラクティブ要素に `accessibilityLabel` を設定
- 画像に `accessibilityLabel`（代替テキスト）を設定
- `reduceMotion` が有効な場合にアニメーションを抑制
- カラーコントラスト比 4.5:1 以上（テキストの視認性確保）

## ポイント 3: 体感の速さを見直す

Editorial チームが実際に触って判断すると言われています。その前提に立てば、**起動の速さ・スクロールの滑らかさ・反応の速さ**は、推薦文よりも先に伝わってしまう部分です。

### 起動時間を最適化する

```tsx
// ✅ App.tsx での最適化例：重い処理を遅延させる
import { useEffect, useState } from 'react';
import * as SplashScreen from 'expo-splash-screen';

// スプラッシュスクリーンを保持しつつ必要なものだけ読み込む
SplashScreen.preventAutoHideAsync();

export default function App() {
  const [isReady, setIsReady] = useState(false);

  useEffect(() => {
    async function prepare() {
      try {
        // 本当に必要な初期化のみ（認証確認・必須データなど）
        await Promise.all([
          checkAuthStatus(),
          loadEssentialConfig(),
        ]);
        // 重いデータ読み込みは後回し（analyticsなど）
      } catch (e) {
        console.error(e);
      } finally {
        setIsReady(true);
        await SplashScreen.hideAsync();
      }
    }
    prepare();
  }, []);

  if (!isReady) return null;
  return <RootNavigator />;
}
// 期待する出力: スプラッシュ表示→必要な初期化完了→即座にメイン画面表示
```

Apple が具体的な秒数を公開しているわけではありません。次の表は、私が自分のアプリで置いている目安です。公式の基準値ではない点をご承知おきください。

<table>
<thead>
<tr><th>見る場面</th><th>目安</th><th>確かめ方</th></tr>
</thead>
<tbody>
<tr><td>コールドスタート（再起動後の初回起動）</td><td>2秒以内に操作できる状態</td><td>実機で手元のストップウォッチ。シミュレータの数字は当てにしない</td></tr>
<tr><td>ウォームスタート（2回目以降）</td><td>1秒以内</td><td>同上。バックグラウンドから戻した場合も別に測る</td></tr>
<tr><td>スクロール</td><td>60fps を保つ</td><td>長いリストを高速でスワイプし、引っかかりを目で確かめる（Reanimated を使うと楽になります）</td></tr>
<tr><td>API 応答から画面更新まで</td><td>3秒以内。超える場合は待ち状態を見せる</td><td>回線を意図的に細くして試す</td></tr>
</tbody>
</table>

数字そのものより、**測る場面を先に決めておく**ことの方が効きます。私は速さの話になると、つい開発機の体感で「十分速い」と判断しがちで、古い端末で触ってはじめて遅さに気づくことが何度もありました。

## ポイント 4: 語れる「ストーリー」を持つ

Today タブの記事は広告ではなく、**Apple のエディターが書く読み物**です。編集チームが「このアプリには語るべき話がある」と感じられるかどうかが、鍵になるのだと思います。

### Apple が好む「ストーリー」のパターン

- **社会課題を解決する**: 環境問題・障がい者支援・メンタルヘルスなど
- **独自の視点・デザイン**: 「これは今まで見たことがない」と感じさせる UI/UX
- **開発者の実体験から生まれた**: 「自分が困っていたから作った」という背景
- **特定コミュニティへの貢献**: 地域文化・伝統工芸・少数言語など
- **タイムリーな話題**: 季節イベント・大型スポーツ大会・社会的なトレンド

私が自分のアプリで「語れる話」を探すときは、機能の多さではなく、手を動かした作業そのものを見直します。たとえば浮世絵壁紙なら、古い紙の傷みを自分の手で一枚ずつ直してから配信していること。機能表には載りませんが、推薦文にはいちばん書きたくなる部分です。

ストーリーは、後からお化粧して作れるものではないかもしれません。企画の段階でこの視点を持っておくことが、フィーチャーへの近道になるのだと考えています。

## ポイント 5: App Store Connect の Featuring Nominations を使う

「Apple に推薦を出す」と聞くと、代理店や知り合いのツテが要る話に聞こえます。実際は App Store Connect の中に、誰でも開ける入口があります。

`App > 対象アプリ > サイドバーの Featuring > Nominations` を開き、Nominations の横の「＋」から Create Nomination。初回だけ Get Started を挟みます。操作できるのは Account Holder / Admin / App Manager / Marketing のいずれかのロールです。個人開発でアカウントを1人で持っているなら、ロールを気にする必要はありません。

推薦は3つの型から選びます。

<table>
<thead>
<tr><th>型</th><th>Apple の説明</th><th>個人開発での使いどころ</th></tr>
</thead>
<tbody>
<tr><td><strong>App Launch</strong></td><td>新規アプリの公開または予約注文</td><td>1本目。長く温めていた新作</td></tr>
<tr><td><strong>App Enhancements</strong></td><td>新機能・機能追加・その他の重要なアップデート</td><td>既存アプリの大型更新。個人開発でいちばん現実的な枠</td></tr>
<tr><td><strong>New Content</strong></td><td>アプリ内の新しいコンテンツ・オファー・イベント</td><td>素材やシーズン企画が増えていくタイプのアプリ</td></tr>
</tbody>
</table>

**型と関連アプリは、提出後には変更できません。** ここだけは下書きの段階で決め切ります。それ以外の項目は提出後でも編集できます。関連アプリは同一アカウントから最大10本まで束ねられるので、シリーズものを出している方は横並びで見せられます。

### リードタイムは最低3週間

Apple は App Store Connect のヘルプで、提出はできるだけ早く、**最低でも3週間のリードタイム**を確保するよう案内しています。公開日は「特定の1日」でも「期間」でも指定でき、判定は端末のローカルタイムゾーン基準です。

個人開発で複数のアプリを回していると、この3週間を確保できずに見送る回が出てきます。私自身、公開日を決めてからフォームを開いて、間に合わないと気づいたことがありました。いま思えば、足りなかったのはフォームの知識ではなく、推薦を工程表の最初に置くという順番の発想でした。

この3週間は審査（App Review）とは別枠です。審査を通した後に推薦を出すのでは間に合いません。ビルドを作る前に、公開予定日から逆算して推薦の下書きを先に置いておく。順番を入れ替えるだけで、間に合う確率が変わります。

下書きは Save as Draft でいくらでも寝かせられます。CSV での一括提出もあり、こちらは1回あたり50件まで、アップロードした時点で自動的に提出されます（下書き保存はできません）。複数アプリを運用している場合はテンプレートをダウンロードして使い回すのが速いです。

## 推薦文の 1,000 文字をどう割り振るか

フォームで文字数の上限が明示されているのは3つだけです。

<table>
<thead>
<tr><th>項目</th><th>上限</th><th>役割</th></tr>
</thead>
<tbody>
<tr><td>Nomination Name</td><td>60 文字</td><td>自分が後から見分けるための名前。審査対象ではない</td></tr>
<tr><td>Nomination Description</td><td>1,000 文字</td><td>本体。何が起きるのかを伝える</td></tr>
<tr><td>Helpful Details</td><td>500 文字</td><td>アクセシビリティやチームの背景など、記事の素材になる話</td></tr>
</tbody>
</table>

上限は語数ではなく文字数です。英語で書けば 1,000 文字はおよそ 160 語で、思っているより短く感じるはずです。日本語で書くと同じ内容が半分の文字数で入りますが、読み手は Editorial チームなので英語で書く方が安全です。

私が使っている割り振りは次のとおりです。

<table>
<thead>
<tr><th>配分</th><th>書く内容</th></tr>
</thead>
<tbody>
<tr><td>冒頭 約120文字</td><td>何のアプリで、いつ、何が起きるのか。1文で言い切る</td></tr>
<tr><td>次 約300文字</td><td>今回の更新の中身。機能名・対応 OS・対応言語を名詞で並べる</td></tr>
<tr><td>次 約300文字</td><td>それが利用者にとって何を変えるのか。形容詞ではなく行動の変化で書く</td></tr>
<tr><td>末尾 約200文字</td><td>公開予定日と、その日までに揃っているもの</td></tr>
<tr><td>残り 約80文字</td><td>バッファ。推敲で必ずはみ出します</td></tr>
</tbody>
</table>

冒頭の1文が要です。Editorial チームは大量の推薦を読みます。「壁紙アプリの新バージョンです」では、続きを読む理由になりません。「iOS 26 のロック画面ウィジェットに対応し、16言語で同時公開します」なら、読み手の中に絵が浮かびます。

Helpful Details の 500 文字は、実績を書く場所ではありません。Apple の説明は「他とどう違うのかを知りたい」です。受賞歴やダウンロード数より、**記事1本分の素材になる話**を置いた方が届きます。VoiceOver の読み上げ順をどう組み直したか。多言語対応をどうやって1人で回しているか。地味な話ほど、書ける人が少ない話です。

Supplemental Materials には URL を5本まで添えられます。TestFlight の公開リンクも入れられるので、公開前のビルドを触ってもらう導線をここで作れます。素材を「後から送ります」と書くくらいなら、TestFlight のリンクを1本入れる方が早いです。

### 提出前に自分でやる確認

- Nomination Description を英語に直して、文字数カウンタで 1,000 以内か測る
- 冒頭1文だけを読み返して、アプリを知らない人に絵が浮かぶか確かめる
- 公開予定日から3週間以上あるか、カレンダーで数える
- 型と関連アプリを最終確認する（提出後は変えられません）
- Supplemental Materials の URL を、ログアウト状態のブラウザで開いて確認する

最後の項目は毎回やっています。自分だけがアクセスできる URL を送ってしまうのは、静かで気づきにくい失敗です。

## ポイント 6: リリース直後の品質を崩さない

掲載の判断にこれらがどう使われるかは公開されていません。それでも、**クラッシュレート・ユーザー評価・エンゲージメント**がリリース直後に荒れていると、せっかく届いた方に悪い第一印象を残すことになります。守りの指標として、事前に基準を決めておきます。

### TestFlight でのベータテストを徹底する

```bash
# EAS Build を使って TestFlight ビルドを作成
npx eas build --platform ios --profile preview

# 出力例:
# ✅ Build #12 completed
# 📱 TestFlight URL: https://testflight.apple.com/join/xxxxx
# ⏱ Build time: 8m 32s
```

**リリース前のチェックポイント**:

- ベータテスターは、機種と OS が散らばるように 20 名前後を目安に集める
- クラッシュレートの上限を自分で決めて、超えたら公開を延ばすと先に約束しておく（Sentry などで計測）。具体的な数字は Apple が示していないため、アプリごとに決めます
- App Store Connect の「TestFlight フィードバック」を全件読み、返せるものには返す
- 公開後 24 時間は、初期レビューへの返信に時間を空けておく

### リリース直後のレビュー獲得戦略

```tsx
// ✅ 適切なタイミングでレビューを促す実装
import * as StoreReview from 'expo-store-review';

async function requestReviewAtRightMoment(
  userHasCompletedAction: boolean,
  sessionCount: number,
) {
  // ユーザーが価値を感じた瞬間（3回以上使用・タスク完了後）にのみリクエスト
  if (userHasCompletedAction && sessionCount >= 3) {
    const canRequest = await StoreReview.hasAction();
    if (canRequest) {
      await StoreReview.requestReview();
    }
  }
}
// 期待する出力: ユーザーが価値を感じたタイミングでのみレビュー依頼ダイアログが表示される
```

## ポイント 7: App Store のビジュアル資産を整える

ストアで最初に目に入るのは、**アイコン・スクリーンショット・プレビュー動画**です。ここが荒れていると、中身の良さが伝わる前に閉じられてしまいます。

### アイコンで押さえたいこと

- **シンプルで記憶に残るデザイン**: 1〜2つの要素に絞る
- **背景色に工夫**: グラデーションや独自カラーで個性を出す
- **意味が一目で伝わる**: アプリの本質的な価値を象徴する
- **サイズ対応**: 1024×1024px で作成（縮小時にも鮮明に見えること）

### スクリーンショットでストーリーを語る

```
スクリーンショット構成の推奨例（全6枚）:

1枚目: アプリの核心的な価値を1文で表したキャッチコピー + 最重要画面
2枚目: 主要機能1（ユーザーが最も時間を過ごす画面）
3枚目: 主要機能2（差別化になる特徴的な機能）
4枚目: 使いやすさ・シンプルさの証明
5枚目: コミュニティ・実績・信頼性（レビュー数・ユーザー数など）
6枚目: CTA（「今すぐ無料で始める」など）
```

アプリのスクリーンショット制作には、[Figmaを使ったApp Storeスクリーンショット制作ガイド](/articles/app-dev/figma-app-store-screenshot-guide)も参考になります。

## フィーチャー申請のタイムライン — 逆算スケジュール

Apple が示す最低ラインは、公開予定日の3週間前です。ただし3週間前に慌てて書いた推薦文は、たいてい冒頭1文が弱くなります。私は次の順で組んでいます。

- **公開10週前**: 企画とデザインを固める。この時点で Nomination Description の冒頭1文を書いてみる。書けなければ、企画がまだ言語化できていません
- **公開8週前**: TestFlight ベータ開始。Supplemental Materials に入れる公開リンクを用意する
- **公開6週前**: 推薦を下書きで作り、型と関連アプリを確定。Helpful Details の素材を書き出す
- **公開4週前**: アイコン・スクリーンショット・プレビュー動画を最終化。クラッシュレートを確認
- **公開3.5週前**: 推薦を提出（最低ラインの3週間に半週の余裕を足しています）
- **公開3週前**: App Store Connect に全素材をアップロードし、App Review に提出
- **公開当日**: 公開。レビュー依頼の導線を有効化
- **公開後2週間**: エンゲージメント指標を毎日確認。不具合は即日で潰す

推薦の提出（3.5週前）が App Review の提出（3週前）より先に来る点が、この表の肝です。審査結果を待ってから推薦を出すと、公開日と3週間ルールの間に挟まれて動けなくなります。

## 最後に、明日やること

7つのポイントを並べましたが、明日から着手できるのは1つだけで十分です。

**App Store Connect の Featuring > Nominations を開いて、下書きを1つ作ってください。** 提出しなくて構いません。名前を付けて、型を選んで、Description の冒頭1文だけを英語で書く。ここまでで10分ほどです。

その1文が書けないとき、原因はたいてい推薦のやり方ではなく、アプリ側にあります。「誰の、何が、いつ変わるのか」が自分の中で決まっていないのです。私は何度もその壁にぶつかり、手が止まる夜を過ごしました。推薦フォームは、その曖昧さを最短で映し出す鏡としても使えます。

**推薦は、完成してから出すものではなく、企画を言葉にする道具として先に置く。** この線引きを、公開日が迫っているときほど思い出すようにしています。

審査でつまずいた経験がある方は、[Rork アプリの App Store リジェクト対応の実務](/articles/rork-business/rork-app-store-rejection-survival-playbook)が地続きの内容です。キーワード欄の設計から見直したい場合は、[App Store キーワード欄の日本語 ASO 設計](/articles/rork-business/rork-app-store-keyword-field-japanese-aso-guide)もあわせてどうぞ。

フィーチャーは運の話にされがちですが、少なくとも入口は全員に開いています。下書きを1つ置いておくところから、始めてみてください。
