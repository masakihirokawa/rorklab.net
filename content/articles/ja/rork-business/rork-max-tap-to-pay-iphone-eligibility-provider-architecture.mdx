対面でお金を受け取る手段を、専用端末なしで持てないか——小さな物販や、イベントでの手売りをしていると、一度は考える話だと思います。私自身、個人開発の傍らで小さなグッズを対面で手渡す機会があり、そのたびに「iPhone だけで決済できたら、荷物も気持ちも軽いのに」と思っていました。Tap to Pay on iPhone は、まさにその願いを叶える仕組みで、追加の読み取り機なしに、iPhone を非接触カードやスマホ決済にかざしてもらうだけで支払いを受けられます。

ただ、いざ組み込もうとすると、コードよりも先に越える壁がいくつもあります。この記事は、Rork Max で作るアプリに Tap to Pay を入れられるかどうかを、事業の目線で見極めるための整理です。実装の断片も示しますが、それ以上に「始める前に知っておくべき前提」を率直にお伝えします。ここを飛ばして手を動かすと、後で振り出しに戻ることになりがちだからです。

## まず、コードの前に立ちはだかる前提

Tap to Pay は、技術的な難しさよりも先に、資格と契約の要件が重くのしかかります。私が最初に面食らったのも、まさにここでした。順に見ていきます。

<table>
<thead>
<tr><th>要件</th><th>内容</th><th>個人開発への影響</th></tr>
</thead>
<tbody>
<tr><td>組織アカウント</td><td>組織（法人）レベルの Apple Developer アカウントが必要。アカウントホルダーとしてログインして権利を申請する</td><td>個人名義のアカウントでは申請できない</td></tr>
<tr><td>権利（entitlement）</td><td><code>com.apple.developer.proximity-reader.payment.acceptance</code> を有効化。開発用と配布用をそれぞれ Apple に申請する</td><td>審査・承認を待つ期間が要る</td></tr>
<tr><td>決済事業者（PSP）</td><td>実際の決済処理には Stripe・Square・Adyen などの決済事業者との契約と SDK が必要</td><td>手数料と加盟店審査が発生する</td></tr>
<tr><td>提供地域</td><td>Tap to Pay は対応国・地域が限られる</td><td>自分の事業の所在地が対象かの確認が先</td></tr>

この表の一番の要点は、個人名義では入口に立てないことと、決済そのものは自作できないことの二つです。カードの読み取りは Apple の `ProximityReader` が担いますが、その先の「実際にお金を動かす」部分は、必ず決済事業者を通します。ここを理解しないまま「iPhone だけで完結する」と思い込むと、設計を一度壊すことになります。

## ProximityReader と決済事業者の役割分担

では、何を Apple が担い、何を決済事業者が担うのか。ここを分けて捉えると、設計の見通しが一気に良くなります。

<table>
<thead>
<tr><th>担い手</th><th>役割</th></tr>
</thead>
<tbody>
<tr><td>Apple の ProximityReader</td><td>iPhone を読み取り端末として起動し、非接触カードやスマホをかざす体験、金額表示や案内の画面を提供する</td></tr>
<tr><td>決済事業者（PSP）の SDK</td><td>読み取った決済情報を安全に処理し、承認・売上計上・返金・入金までの一連を担う</td></tr>
<tr><td>あなたのアプリ</td><td>商品や金額の管理、決済の開始指示、結果に応じた画面遷移や記録を担う</td></tr>
</tbody>
</table>

実務では、多くの決済事業者が Tap to Pay を自社 SDK の中に包んで提供しています。つまり、あなたが直接 `ProximityReader` の低レベル API を叩くよりも、Stripe Terminal や Square の Mobile Payments SDK のような、決済事業者が用意した層を通すのが現実的です。事業者側が権利の設定や読み取りの初期化をまとめて面倒を見てくれるため、自作する範囲がぐっと狭まります。

私の助言としては、最初から低レベルの `ProximityReader` を自前で組もうとしないことです。決済という「間違えられない領域」で、承認や返金の整合まで自作するのは、個人開発の体力に見合いません。決済事業者の SDK に寄せ、自分のアプリは「金額を渡し、結果を受け取る」だけに絞るのが、堅実な設計だと考えています。

## 決済事業者の SDK に寄せた最小の流れ

具体的なイメージを持てるよう、決済事業者の SDK に寄せた場合の呼び出しの骨組みを示します。ここでは概念を伝えるための擬似的な形で書いています。実際のメソッド名や初期化は、契約した決済事業者のドキュメントに従ってください。

```swift
// 決済事業者の SDK に寄せた、対面決済の最小の骨組み（概念図）
final class InPersonCheckout {
    let terminal: PaymentProviderTerminal   // 決済事業者が提供する層

    /// 1回の対面決済を実行する。
    func charge(amount: Int, currency: String) async throws -> ChargeResult {
        // 1. 読み取り端末（iPhone）を対面決済モードで用意する
        //    権利や ProximityReader の初期化は SDK 内部で面倒を見てくれる
        try await terminal.prepareReader()

        // 2. 金額を指定して決済意図を作る（サーバー側で作るのが安全）
        let intent = try await terminal.createPaymentIntent(amount: amount, currency: currency)

        // 3. カードやスマホをかざしてもらい、読み取る
        let collected = try await terminal.collectPaymentMethod(for: intent)

        // 4. 決済を確定する。承認・売上計上は事業者側が担う
        let result = try await terminal.confirm(collected)
        return result
    }
}
```

ここでの設計上の要点は二つです。第一に、金額や決済意図の生成は、可能な限りサーバー側で行うことです。クライアントだけで金額を決めると、改ざんの余地を残します。第二に、`ProximityReader` の細部を自分のコードから直接触らないことです。SDK の内側に閉じ込め、自分のアプリは金額と結果だけを扱う、と割り切ります。

## Rork Max でどこまで踏み込めるか

Rork Max はネイティブ Swift を生成するので、決済事業者の iOS SDK を組み込む土台としては相性が良いです。従来の Expo / React Native では、Tap to Pay のようにネイティブ権利と密接に結びついた機能は、ブリッジ越しでは扱いづらい領域でした。ネイティブ生成に踏み込めることで、決済事業者の SDK をそのまま抱え込めるのは、はっきりした利点です。

一方で、期待しすぎないほうがよい点もあります。Rork Max がコードを生成できても、組織アカウントの取得も、権利の申請も、決済事業者との加盟店契約も、人が進める手続きです。ここは自動化できません。私の見立てでは、Tap to Pay は「技術で解ける部分は全体の三割ほどで、残る七割は事業側の段取り」という性格の機能です。

## つまずきやすい落とし穴と回避策

実際に検討を進める中で、私がつまずいた点と、その回避策を残しておきます。

第一に、権利（entitlement）の申請を後回しにしないことです。コードが書けても、承認待ちで本番リリースが止まります。私の場合は、決済事業者の選定と並行して早めに申請しておくことをお勧めします。

第二に、金額の生成をクライアント任せにしないことです。改ざんの余地を残す落とし穴なので、サーバー側での生成をお勧めします。本番運用では、この整合が監査の対象にもなります。

第三に、返金や取り消しの整合を軽く見ないことです。対処を決済事業者の SDK に寄せ、自作の範囲を狭めることで回避します。ここを自前で抱えると、少額の食い違いが積み上がって後で苦しくなります。

## 個人開発者に現実的な進め方

最後に、では個人でどう進めるかです。私自身が同じ立場で考えた道筋を、そのまま共有します。

第一に、事業の所在地が Tap to Pay の対応地域かを最初に確かめます。ここが対象外なら、他の対面決済手段を検討したほうが早いです。前提が崩れる確認を最優先にする、という順番を守ります。

第二に、法人化と組織アカウントの是非を、決済の必要性と天秤にかけます。対面決済のためだけに法人化するのは重い判断です。まずは決済事業者が提供する、アプリ開発を伴わない読み取りアプリ（事業者純正のレジアプリ）で用が足りないか、を検討する価値があります。自作アプリに組み込むのは、そこに独自の価値が乗るときだけで十分です。

第三に、組み込むと決めたら、決済事業者を先に選びます。手数料、入金サイクル、加盟店審査の通りやすさ、SDK の使いやすさは事業者ごとに差があります。技術より先に、事業条件で比べます。

第四に、アプリ側は薄く保ちます。決済の複雑さは事業者の SDK に預け、自分のコードは「金額を渡し、結果を記録する」だけに絞る。この割り切りが、保守の負担を長期にわたって軽くします。

Tap to Pay は、対面での小さな商いに新しい選択肢をもたらす、魅力的な仕組みです。ただ、その入口は技術よりも事業側の段取りにあります。まずは自分の事業が対象地域か、組織アカウントを取る覚悟があるか、この二点を確かめるところから始めてみてください。前提を丁寧に踏むほど、後の実装は驚くほど素直に進みます。同じ対面決済の導入を考えている方の、判断の一助になれば幸いです。
