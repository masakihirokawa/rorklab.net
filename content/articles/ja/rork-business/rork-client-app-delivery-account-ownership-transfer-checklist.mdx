Apple と Google の移管ヘルプを左右に並べて読んでいた夕方、私は一つの思い込みに気づきました。移管は「あとで管理画面のボタンを押せば済むもの」だと、どこかで考えていたのです。読み進めるほど、押す前に揃えておく条件と、押したあとに切れてしまう設定の多さに手が止まりました。

私自身は個人開発で、自分のアプリを自分のアカウントから出してきました。アプリを他人の名義へ移した経験はありません。この記事は、その前提で書いています。Apple・Google・Expo の公式ページを読み、手元のサンプルプロジェクトで確かめられる部分だけを実際に動かしました。移管の体験記ではなく、「最初に何を決めておけば後で迷わないか」の整理として受け取っていただければ幸いです。

最初にお伝えしたいのは、結論です。**納品するアプリは、最初から相手の開発者アカウントで作るのが、いちばん後戻りの少ない選び方です。** 以下は、その理由と、どうしても先に自分の名義で出すときの段取りです（記載はすべて2026年11月時点・各社の公式ヘルプで確認した内容です）。

## 先に決める選択肢は3つです

Rork で作ったアプリを相手に渡すとき、公開アカウントの持ち方は大きく3通りに分かれます。

<table>
  <thead>
    <tr><th>やり方</th><th>向いている場面</th><th>手間が出る場所</th><th>後から変えにくいもの</th></tr>
  </thead>
  <tbody>
    <tr><td>最初から相手のアカウントで作る</td><td>相手がすでに開発者登録を済ませている、または一緒に登録できる</td><td>相手に招待を出してもらう手間が最初に一度だけ</td><td>ほぼなし</td></tr>
    <tr><td>自分のアカウントで公開し、あとで移管する</td><td>相手の登録が間に合わない、まず審査を通したい</td><td>移管の条件確認と、紐づく設定の付け替え</td><td>Sign in with Apple のユーザー、売上レポート</td></tr>
    <tr><td>自分のアカウントで公開し続ける</td><td>運用まで任される契約</td><td>責任の範囲と、相手が離れるときの出口を決めておく</td><td>ストアの販売者名が自分のまま</td></tr>
  </tbody>
</table>

判断の基準は一文で足ります。**相手が2週間以内に開発者登録を終えられるなら1つ目、終えられないときだけ2つ目を選び、3つ目は運用契約があるときに限ります。** Apple の法人登録は確認に日数がかかることがあるため、登録が終わる見込みを契約の前に聞いておくと、この判断がぶれません。

2つ目を選ぶときに大切なのは、「移管できるかどうか」より「移管すると何が残り、何が切れるか」を見積もりの段階で説明できることです。

## Apple：移管できる条件と、止まりやすい状態

App Store Connect ヘルプの「App transfer criteria」には、移管の基準が一覧で書かれています。読んで手が止まりやすいと感じた箇所を、確かめ方と並べました。

<table>
  <thead>
    <tr><th>条件</th><th>止まる場面</th><th>確かめ方</th></tr>
  </thead>
  <tbody>
    <tr><td>App Store に出した版が少なくとも1つある</td><td>一度も公開していない新規アプリ</td><td>App Store Connect のアプリ一覧で配信中の版を確認</td></tr>
    <tr><td>審査待ち・審査中・リリース待ちなどの状態にない</td><td>申請を出したまま移管しようとしたとき</td><td>最新の版の状態表示</td></tr>
    <tr><td>予約注文の対象になっていない</td><td>プレオーダー中のアプリ</td><td>価格と配信状況の画面</td></tr>
    <tr><td>アプリ内課金の ID が受け取る側の別アプリと重ならない</td><td>相手が似た ID 体系で別アプリを出している</td><td>双方の課金項目の製品 ID を並べて比べる</td></tr>
    <tr><td>双方が最新の契約に同意済み</td><td>相手が規約更新の同意を済ませていない</td><td>App Store Connect の「契約」の画面</td></tr>
  </tbody>
</table>

移管後もアプリは App Store に出たままで、レビューと評価、Bundle ID はそのまま残ります。そして **Bundle ID は、一度ビルドをアップロードしたあとは変更できません。** 納品の最初に、相手のブランドで通用する ID を一緒に決めておく項目です。

付け替えが要るものもヘルプに明記されています。

- 自動更新サブスクリプション：アプリ固有の共有シークレットを、移管を始める前に送る側が生成して渡します。
- TestFlight：ベータ版のテストを止め、ビルドとテスターを外してから移管します。
- プッシュ通知・Apple Pay・iCloud・Game Center：それぞれ受け取る側で設定し直す手順があります。
- Sign in with Apple：ユーザーの識別子がチームごとに違うため、移管の前後で引き継ぎの手続きが要ります。移管後に引き継げる期間は60日です。

なかでも Sign in with Apple は、移管前の識別子（sub）をサーバー側に保存していないと、既存ユーザーを新しいチームの識別子に結び直せません。Apple の開発者フォーラムにも、この保存を忘れて困っている相談が繰り返し出ています。ログイン機能のあるアプリを預かるなら、作り始めの段階で sub を保存する設計にしておくのが安全です。

Apple のヘルプは、移管が終わるとアプリが送る側のアカウントから消えるとも書いています。控えを取ってから始めることは、大げさではなく手順の一部です。

## Google Play：引き継がれないものを先に知っておく

Google Play の移管は、送る側が依頼を出し、受け取る側の所有者が承認する流れです。受け取る側のアカウントは登録が完了している必要があり、新しく作るなら登録料がかかります。処理には日数がかかることがあるため、公開日の直前に依頼しないほうが安心です。

引き継がれるのは、ユーザー、統計、レビューと評価、サブスクリプション、提出済みのアプリのコンテンツ申告などです。一方で、次のものは引き継がれません。

<table>
  <thead>
    <tr><th>引き継がれないもの</th><th>移管前にやっておくこと</th></tr>
  </thead>
  <tbody>
    <tr><td>売上・支払い・一括エクスポートのレポート</td><td>先にダウンロードして、自分の手元に保管する</td></tr>
    <tr><td>移管前に作られた注文</td><td>返金は元のアカウント側で対応することになるため、その期間を相手に伝えておく</td></tr>
    <tr><td>クローズドテストのテスターグループ</td><td>受け取る側で作り直し、テスターに再参加をお願いする</td></tr>
    <tr><td>Google アナリティクス・Firebase などの連携</td><td>移管後に付け替える前提で、連携の一覧を作っておく</td></tr>
  </tbody>
</table>

アプリ内課金だけを持つアプリは、移管後にいったん非公開になり、再公開が必要になる点にも注意が要ります。また Android では2026年から開発者認証が国ごとに始まっています。受け取る側のアカウントが認証を済ませているかも、移管の前に一度確かめておくと安心です。

## Expo と EAS：ストアの外にも名義があります

ストアの移管だけを見ていると見落としやすいのが、ビルドと配信を担う Expo の側です。Rork から書き出したプロジェクトには、Expo のアカウント名（owner）と EAS のプロジェクト ID が入っています。Expo の公式ドキュメント「App transfers」には、プロジェクトを別の Expo アカウントへ移す手順がまとまっています。

ここで押さえておきたいのは、証明書や鍵の持ち主が一つではないことです。

- iOS の配布証明書とプッシュ通知の鍵（APNs キー）は、Apple の開発者チームに属します。チームが変われば、受け取る側のチームで作り直すことになります。
- Android のアップロード鍵は EAS に保管されていることが多く、`eas credentials` から取り出して相手に渡せます。Play App Signing を使っていれば、署名鍵そのものは Google 側にあります。
- expo-updates の配信先 URL はプロジェクト ID に結びついています。プロジェクトを移すときは、配信中の版がどの URL を見ているかを控えておきます。

## 手元のプロジェクトで「自分の名前に紐づく設定」を洗い出す

公式ヘルプを読んでも、実際のプロジェクトのどこに自分のアカウントが入っているかは、見てみないとわかりません。最初に書いたスクリプトは `eas.json` の `production` しか見ておらず、別名のプロファイルに残った自分の Team ID を拾えませんでした。そこで、全プロファイルと Sign in with Apple・entitlements・expo-updates まで見る形に書き直しました。

```js
// audit.mjs v2 — 使い方: node audit.mjs <プロジェクトのフォルダ>
// app.json と eas.json の「全プロファイル」から、移管のときに確かめる設定を拾います
import { readFileSync, existsSync } from "node:fs";
import { join } from "node:path";

const dir = process.argv[2] ?? ".";
const has = (f) => existsSync(join(dir, f));
const json = (f) => (has(f) ? JSON.parse(readFileSync(join(dir, f), "utf8")) : null);

if (has("app.config.js") || has("app.config.ts")) {
  console.log("注意  app.config.js/ts があります。値は実行時に決まるため、npx expo config で確かめてください");
}

const app = json("app.json")?.expo ?? {};
const eas = json("eas.json") ?? {};
const rows = [];
const add = (kind, label, value) => value && rows.push([kind, label, value]);

// 名義が入る場所（移管で付け替える）
add("付け替え", "Expo owner", app.owner);
add("付け替え", "EAS projectId", app.extra?.eas?.projectId);
add("付け替え", "expo-updates の URL", app.updates?.url);
for (const [name, p] of Object.entries(eas.submit ?? {})) {
  add("付け替え", `submit.${name} Apple ID`, p.ios?.appleId);
  add("付け替え", `submit.${name} Apple Team ID`, p.ios?.appleTeamId);
  add("付け替え", `submit.${name} ascAppId`, p.ios?.ascAppId);
  add("付け替え", `submit.${name} Play 鍵ファイル`, p.android?.serviceAccountKeyPath);
}
add("付け替え", "Firebase iOS 設定", has("GoogleService-Info.plist") && "GoogleService-Info.plist");
add("付け替え", "Firebase Android 設定", has("google-services.json") && "google-services.json");
add("付け替え", "Apple の権限（entitlements）", app.ios?.entitlements && Object.keys(app.ios.entitlements).join(", "));
add("付け替え", "Sign in with Apple", app.ios?.usesAppleSignIn && "使用中（移管前に sub を保存）");

// 変えない場所（移管しても残る・変えると別アプリになる）
add("変えない", "iOS Bundle ID", app.ios?.bundleIdentifier);
add("変えない", "Android package", app.android?.package);
add("変えない", "URL scheme", app.scheme);

for (const [kind, label, value] of rows) console.log(`${kind}  ${label}: ${value}`);
console.log(`--- 付け替え ${rows.filter((r) => r[0] === "付け替え").length} 件 / 変えない ${rows.filter((r) => r[0] === "変えない").length} 件`);
```

Linux 上の Node.js 22 で、`production` と `client` の2つの submit プロファイルを持つサンプルに対して動かした結果です。

```text
付け替え  Expo owner: my-expo-name
付け替え  EAS projectId: 0000-aaaa
付け替え  expo-updates の URL: https://u.expo.dev/0000-aaaa
付け替え  submit.production Apple ID: me@example.com
付け替え  submit.production Apple Team ID: ABCDE12345
付け替え  submit.production ascAppId: 1234567890
付け替え  submit.production Play 鍵ファイル: ./play-key.json
付け替え  submit.client Apple Team ID: ZYXWV98765
付け替え  Firebase Android 設定: google-services.json
付け替え  Apple の権限（entitlements）: aps-environment
付け替え  Sign in with Apple: 使用中（移管前に sub を保存）
変えない  iOS Bundle ID: com.example.sample
変えない  Android package: com.example.sample
変えない  URL scheme: sample
--- 付け替え 11 件 / 変えない 3 件
```

行を「付け替え」と「変えない」に分けたのには理由があります。Bundle ID・package・URL scheme は移管しても残り、変えると別のアプリとして扱われてしまうため、「変える作業」ではなく「変えていないことを確かめる作業」の側に置いています。ascAppId は数字のアプリ ID で、受け取る側の App Store Connect で同じ値になっているかを確かめる行として残しました。`app.config.js` で値を組み立てているプロジェクトは、このスクリプトでは読み切れないため、注意の一行を出して `npx expo config` での確認に回しています。

出力された「付け替え」の行が、そのまま引き継ぎ書の項目になります。

## 移管のあとで起きやすいことの切り分け

移管そのものより、移管のあとに「何かが動かない」と言われる場面のほうが多いかもしれません。症状から辿れるように並べました。

<table>
  <thead>
    <tr><th>症状</th><th>原因の候補</th><th>確かめ方</th><th>直し方</th></tr>
  </thead>
  <tbody>
    <tr><td>App Store Connect で移管を始められない</td><td>最新の版が審査待ち・審査中、または契約の未同意</td><td>版の状態と「契約」の画面</td><td>審査が終わるのを待ち、双方で契約に同意してから再開</td></tr>
    <tr><td>移管後にプッシュ通知が届かない</td><td>APNs キーが送る側のチームのまま</td><td>通知サーバーに登録した鍵の Team ID</td><td>受け取る側のチームで鍵を作り、サーバーと EAS に登録し直す</td></tr>

## よくある誤解

**「移管すればレビューも消える」**——消えません。Apple も Google も、レビューと評価は移管後のアプリに残ると書いています。消えるのは送る側の手元からアプリが見えなくなることのほうです。

**「Bundle ID は移管のときに相手のものへ変えられる」**——変えられません。アップロード後の Bundle ID は固定で、移管はその ID ごとアプリを渡す仕組みです。相手の会社名を ID に入れたいなら、最初のビルドの前に決めるしかありません。

**「ストアを移せば、ビルドの環境も一緒に移る」**——移りません。ストアの移管と、Expo のプロジェクトや証明書、Firebase の連携は別々の作業です。ストアだけを移して安心すると、次の更新のビルドで止まります。

## 見積もりの前に、相手に4つ聞いておく

最初のうち、私は移管を「最後に一度だけ発生する手続き」として、見積もりの外に置いて考えていました。けれど上の切り分け表を書いてみると、作業の半分以上は移管の前の準備と、移管の後の付け替えでした。それからは、**移管は納品の一部として工数に入れ、契約書の前に名義を決める**という線引きにしています。そのために聞くのは次の4点です。

1. Apple Developer Program と Google Play のデベロッパーアカウントを、すでにお持ちですか。
2. お持ちでない場合、個人と法人のどちらで登録されますか（登録名がストアの販売者名として表示されます）。
3. 売上や課金の管理は、いつから相手の側で担いますか。
4. 公開後に不具合が出たとき、アカウントの権限は誰が持ちますか。

この4点が決まれば、たいていは「最初から相手のアカウント」で足ります。

## 次に詰まる一歩

名義が決まると、次に当たるのは Apple 側の登録手続きの待ち時間です。相手と一緒に登録を進めるときは、[Rork のアプリを公開する前に、Apple 側で自分が済ませておく手続き](/articles/rork-basics/rork-apple-developer-account-steps-rork-cannot-automate)の順番で進めると、待ちの長い手続きから先に片づけられます。

相手のブランドで ID を決めるときは、[変えられる名前と、変えられない名前](/articles/rork-basics/rork-app-id-immutable-before-first-release)のスクリプトで、Rork が既定で入れた ID が残っていないかを先に確かめていただければと思います。すでに個人名義で出してしまったアプリを法人へ移す場合は、[個人アカウントで出した iOS アプリを、あとから法人へ移せるか](/articles/rork-basics/ios-app-transfer-individual-to-organization-account-checklist)に、移す前に外すものを書き残しています。Android で配信国が広いアプリなら、[開発者認証で新規インストールが止まる4か国の確かめ方](/articles/rork-business/android-developer-verification-2026-four-country-install-share-audit)も合わせてご覧ください。

## 明日、最初にやること

いま進めている案件があれば、プロジェクトのフォルダで `node audit.mjs .` を一度回し、「付け替え」の行の数を数えてみていただければと思います。その数が、移管をするときの作業量のいちばん正直な目安になります。

Apple と Google の手順は更新されることがあります。実際に移管するときは、各社の最新のヘルプで条件を読み直していただければ幸いです。私もこの読み直しだけは、案件ごとに欠かさないようにしています。
