6月6日から12日の Rork Lab は、**「リリースした後に効いてくる判断」**に重心を置いた一週間でした。前回の週間ハイライトで「課金まわりのリリース後の運用に重心を置く」と書いていた予定を、ようやく形にできた週でもあります。サブスクの返金処理、壁紙アプリのバイナリサイズ設計、ディープリンクの取りこぼし対策。どれも、リリース前のチェックリストには載りにくいのに、運用が始まると確実に向き合うことになるテーマです。

並行して、Rork を半年使い続けた評価軸の言語化と、Rork Max の料金プランを損益分岐で見る判断ガイドという、少し引いた視点の記事も2本出しました。今週も、手元で確かめたことを軸に振り返ります。

## サブスクの返金は「アプリに伝わらない」前提で設計する

今週いちばん書いてよかったと感じているのが、プレミアム記事の [サブスクの返金にアプリが気づかない — REFUND 通知と Voided Purchases で権限を失効させる実装メモ](/articles/rork-dev/rork-subscription-refund-detection-entitlement-revocation) です。

返金が成立しても、アプリ側の Premium フラグは立ったままになります。ユーザーは返金を受け取りながら有料機能を使い続けられる、という構造的な穴で、私自身も自分のアプリ群で課金導線を整備する中で「失効の経路を最初に決めていなかった」ことに後から気づいた口です。App Store Server Notifications V2 の REFUND、Google Play の SUBSCRIPTION_REVOKED と Voided Purchases API、RevenueCat のリスナーと起動時照合。経路は3つの構成に分けて整理し、クライアント側は deny by default を最後の砦にする、という順序で書きました。返金そのものを減らす側の工夫にも触れています。

[Rork Max 製アプリの課金実装](/articles/rork-business/rork-max-pricing-2026-decision-guide)に限らず、サブスクを持つアプリ全般に効く内容なので、課金導線を持っている方は失効経路の有無だけでも確認してみてください。

## 壁紙アプリ12年の感覚で、バイナリサイズの境界線を引き直した

もう1本のプレミアム記事が [壁紙アプリのバイナリサイズを抑える — 画像をバンドルから切り離す設計判断](/articles/app-dev/wallpaper-app-binary-size-remote-asset-delivery) です。

壁紙アプリは構造上、コンテンツを増やすほどバイナリが素直に膨らみます。Beautiful HD Wallpapers を運用してきた中で、同梱画像とリモート配信の境界をどこに引くか、初回表示を遅くしないプレフェッチをどう組むか、という判断を何度もやり直してきました。今回はその判断を、実測値と一緒に一本にまとめています。On-Demand Resources や Play Asset Delivery を「使うべきか」という問いにも、個人開発の運用コストの観点から答えを出しました。サイズを削ると審査やダウンロード転換率以外にも波及がある、というのが計測してみての発見です。

## ディープリンクと Expo オフライン起動 — 「効かない」ときの切り分けを残した

[Rork Max でディープリンクを実装する — Universal Links と URL Schemes](/articles/rork-dev/rork-deeplink-guide) は、タップ一つで目的の画面までユーザーを運ぶための実装ガイドです。URL Scheme と Universal Links の使い分けから、AASA / assetlinks の落とし穴、React Navigation との統合、コールド起動での取りこぼし対策までを通しで書きました。ディープリンクは「設定したのに効かない」が起きやすい領域なので、効かないときに最初に疑う場所を明示しています。

[expo start --offline が forbidden で止まる — 企業プロキシ(403)と依存バージョン検証の切り分け](/articles/app-dev/expo-offline-validate-dependencies-versions-forbidden-fix) は、同じ `forbidden` という表示でも原因が2系統ある、という切り分けの記事です。企業プロキシが返す HTTP 403 と、Expo CLI の validateDependenciesVersions ガード。私のプロジェクトで実際に踏んだ依存バージョン競合の例も3つ載せました。地味なテーマですが、検索で辿り着いた誰かの数時間を守れる記事だと考えています。

## 半年運用レビューと料金判断 — 少し引いた視点の2本

[Rork は『AIモバイルアプリビルダー』として何を変えたのか — 半年運用してわかった評価軸](/articles/rork-ai/rork-ai-mobile-app-builder-review-2026) は、Rork を半年使い続けた現時点での率直な評価です。「ビルダー」と呼ぶには違和感がある、という書き出しから、効く局面・詰まる局面・Lovable / Bolt / FlutterFlow と比べたときの本当の差を整理し、「Rork で始めるべきか」を3問で決める判断軸を置きました。6月時点の Rork Max のネイティブ Swift 生成についても追記しています。

[Rork Max 料金判断ガイド 2026 — プロジェクト別・損益分岐でプラン選び](/articles/rork-business/rork-max-pricing-2026-decision-guide) は、料金を「月額固定 + 実行課金」で分解し、副業の週末開発者・継続収益のある個人開発者・受託会社の3パターンで損益分岐を見る実務ガイドです。プラン選びの記事は機能比較になりがちですが、個人で複数アプリを回してきた立場としては、**自分の開発リズムに対して課金モデルが合うか**のほうが先に決まる、と感じています。
