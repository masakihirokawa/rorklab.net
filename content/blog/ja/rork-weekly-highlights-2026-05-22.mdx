## 個人開発の収益を「自動で守る」運用基盤を3本のプレミアム記事に分解した

今週、Rork Lab のテーマの中心になったのが「リリースを挟まずに収益とユーザー体験を守る運用設計」です。3本のプレミアム記事を意図的に連動させて出しました。

最初の1本は [Rork × Firebase Remote Config で AdMob を本番のまま安全に切り替える — 起動広告と頻度キャップを「リリースなし」で動かす運用](/articles/rork-dev/rork-firebase-remote-config-admob-runtime-tuning-production) です。Beautiful HD Wallpapers の Android 版で、起動広告のロード成功率が低下した日に「アプリをアップデート申請せずに頻度キャップだけ調整する」必要に迫られた経験から書きました。Remote Config の整数キーに `interstitialMinIntervalSec` を入れるだけで済ませようとして、初期値のキャッシュとデフォルト値の取り違えで本番が壊れかけた話まで含めて、運用上の落とし穴を一本にまとめています。

2本目が [クラッシュ率上昇時にAdMobを自動で絞る『収益を守る自動制動』アーキテクチャ — Rork × Firebase Remote Config × Crashlytics の連動設計](/articles/rork-dev/rork-admob-crashlytics-remote-config-auto-throttle-architecture) です。Crashlytics の crash-free users が 99.5% を切り始めたとき、私が手動で広告頻度を絞っていた作業を、Cloud Functions + Remote Config で自動化した実体験を書きました。手動運用では夜中の異常に気付けず、レビューが荒れてから慌てる、という経験を何度か繰り返した末の設計です。閾値の決め方や、誤検知でアプリ全体の収益を落とさないためのヒステリシスの取り方まで踏み込んでいます。

3本目が [個人開発で『本番障害の自動応答』を仕組み化する ― Crashlytics・Sentry・Slack 通知・段階的ロールバックの設計](/articles/rork-dev/rork-incident-auto-response-architecture) です。アプリを4本同時に運用していると、自分が寝ている時間帯にクラッシュが集中することがあります。Slack 通知を4階層に分け、深夜の軽微なものはミュート、致命的なものだけ電話通知、という運用に切り替えるまでの試行錯誤と、Remote Config を使った段階的ロールバックの実装パターンをまとめました。

3本を一気に出した理由は単純で、これらは個別には機能しないからです。**Crashlytics の異常を Sentry が補完し、Remote Config が応答し、Slack が人間に届ける**、という連鎖でようやく「夜中に勝手に直っている」状態が成立します。読者の方が同じ運用基盤を組むときに、最初の1本でつまずいて2本目以降に進めない、ということがないよう、3本セットで設計を見せる形にしました。

加えて、[Firebase App Check を Rork に段階的に enforcement する — AdMob 不正検知と Crashlytics を壊さない実運用設計](/articles/rork-dev/rork-firebase-app-check-staged-enforcement-admob-crashlytics) も同じ運用基盤の文脈の記事です。App Check を一気に enforced にすると AdMob のリクエストが弾かれたり Crashlytics 報告が失敗したりするケースがあり、unenforced → 部分 enforced → 全 enforced の段階的移行が必要だった、という実体験を書きました。

## AdMob Bidding と Slack 通知 4 階層を本番投入した所感

[Rork アプリで AdMob Bidding を本番投入した実装メモ — 5 AdNetwork 同時入札の eCPM 推移と運用設計](/articles/rork-business/rork-admob-bidding-five-network-production-implementation) は、Liftoff・InMobi・Unity Ads・AppLovin・Google AdMob の5社を同時に Bidding 構成で回したときの eCPM 推移をまとめた記事です。導入当初の数日は eCPM が下がることが多い、というのは経験的に分かっていたのですが、今回は具体的な日次推移を計測できる体制で投入したので、数値も含めて記事にしました。

[AdMob のダッシュボードを毎日見ない運用に切り替えた所感 — Rork アプリで Slack 通知 4 階層を組んでから 2 ヶ月](/articles/rork-business/rork-admob-not-checking-daily-slack-4-tier-notifications) は、上記アーキテクチャの「実際に2ヶ月運用した感想」のような位置づけです。AdMob ダッシュボードを毎朝開く習慣を、4 階層の Slack 通知に置き換えたことで、何が変わって何が残ったかを正直に書きました。**「ダッシュボードを毎日見ないと不安」という感覚は、通知設計の質の問題でもある**、というのが現時点の私の結論です。
